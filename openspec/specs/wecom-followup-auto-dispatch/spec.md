## Requirements
### Requirement: 每日定时扫描并发送已批准跟进信
系统 SHALL 提供一个独立的定时批处理任务，工作日固定时刻运行，扫描跟进信 README 表格中「发送状态」列严格等于 `🆕 待发` 且未标注 `🔒人工发送` 的全部行，逐行复用既有推送逻辑（`push_followup`）完成发送与状态回填。

#### Scenario: 存在已批准且非硬截止的待发行
- **WHEN** 定时任务触发时，README 中存在「发送状态」为 `🆕 待发` 且无 `🔒人工发送` 标注的行
- **THEN** 系统对该行执行发送，成功后状态回填为 `✅ 已推送 <时间戳>`

#### Scenario: 无待发行
- **WHEN** 定时任务触发时，README 中不存在满足条件的行
- **THEN** 系统本轮不发送任何消息，正常结束

### Requirement: 硬截止标记行结构性跳过
自动发信任务 MUST 跳过任何标注 `🔒人工发送` 的行，即使其状态列为 `🆕 待发`（与 `wecom-followup-review-state` capability 对应需求呼应，作为消费方契约重申）。

#### Scenario: 硬截止行被跳过
- **WHEN** 扫描到的行标注了 `🔒人工发送`
- **THEN** 该行不被本任务处理，不发送、不回填，留给人工触发路径

### Requirement: 单行失败不阻塞其余行
批处理逐行发送时，若某一行推送失败（如门禁拒绝、网络异常），MUST 记录该行失败原因并继续处理其余符合条件的行，不得因单行失败中断整批。

#### Scenario: 某行发送失败，其余行继续处理
- **WHEN** 批处理中第 N 行推送失败
- **THEN** 系统记录该行失败原因（审计+日志），继续处理第 N+1 行及之后的行，批次结束后汇总本轮成功/失败清单

### Requirement: 时限承诺——不保证准点，只保证下次可用窗口即处理
本任务 SHALL 采用"错过即等下一次可用窗口自动补跑"的可靠性模型（复用既有计划任务 `-StartWhenAvailable` 机制），MUST NOT 承诺固定时刻内必达；对时限有硬性要求的跟进信不适用本任务（见"硬截止标记行结构性跳过"）。

#### Scenario: 运行窗口因宿主机关机错过
- **WHEN** 计划触发时刻宿主机处于关机/合盖状态
- **THEN** 任务在宿主机下次开机后自动补跑，不额外发送"已错过"类告警

### Requirement: 疑似漏标硬截止的机器判据兜底
自动发信任务在处理「发送状态」为 `🆕 待发` 且未标 `🔒人工发送` 的行前，SHALL 检查其"交期要点"列是否含明确日期（严格 `YYYY-MM-DD` 格式，MUST NOT 识别"本周五"/"8月初"等相对表述）且距今少于 3 天（含已过期，用绝对值判定）；命中时 MUST 结构性跳过该行（不发送、不回填）并告警通知人工核实，即使起草者忘记标注 `🔒人工发送`。本机制是漏标安全网，不替代人工判断，不改变"起草者须显式标注"的既有约定。

#### Scenario: 未标记但交期要点含临近明确日期
- **WHEN** 某行「发送状态」为 `🆕 待发`、未标 `🔒人工发送`，且"交期要点"列含一个与今日相差不足 3 天的 `YYYY-MM-DD` 格式日期
- **THEN** 自动发信任务结构性跳过该行，记录疑似漏标原因，并发送告警通知人工核实

#### Scenario: 交期要点仅含相对表述不触发
- **WHEN** "交期要点"列内容为"本周五前"/"8月初"等相对表述，不含严格 `YYYY-MM-DD` 格式日期
- **THEN** 不触发本判据，该行按其余条件正常处理

#### Scenario: 明确日期距今较远不触发
- **WHEN** "交期要点"列含 `YYYY-MM-DD` 格式日期，但距今不少于 3 天
- **THEN** 不触发本判据，该行按其余条件正常处理

### Requirement: 部署位置固定于笔记本，不迁移至 .51
本任务 SHALL 部署并仅运行于当前承载企微智能机器人 BotID 的笔记本本机，MUST NOT 迁移至 `.51` 服务器或任何其他主机，以规避同 BotID 多实例并发连接风险。

#### Scenario: 部署位置校验
- **WHEN** 部署本任务
- **THEN** 计划任务的宿主机为现有 `ZhuopinAibotDevListener`/`ZhuopinDecisionReminderDaily` 所在的同一台笔记本
