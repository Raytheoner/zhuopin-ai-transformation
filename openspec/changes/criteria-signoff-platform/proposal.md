# criteria-signoff-platform Proposal

> 🔴 **状态：design 审未过**。本包按根 `CLAUDE.md` §5「机制/工具类模块的 openspec 触发门槛」命中第 ① 条（**改变全项目口径**——判据签认是跨场景约定），故必走 openspec **含 design 审**。起草方（CC 无头泳道 OP-0903-C3）**不自行通过**。

## Why（为什么做）

**rule-of-three 已触发（5 > 3）**：FI5／FI6／FI8／FI9／FI10 五个财务场景各需一套「判据签认」逻辑，2026-09-03 收工时是**五份各自手抄的本地实现**。不收进底座，五份必各自漂移——本项目在 `#345`（35 份路径引导手抄副本）上已经吃过一次**完全同形状**的亏。

Shao Peishen 2026-09-03 答 EE-1 = **(a) 把 `criteria_signoff` 收进平台底座做成公共模块**。

漂移不是假想：五份实现虽在同一天由同一泳道写出，**已经开始分岔**——
- 五份都写了 `assert "unsigned" in config.RULE_VERSION`，但**五份都只查了一个方向**（"未签完却不自陈"），无一份查反向（"签完了仍挂 unsigned"）；
- 五份都只断言 `config.X is None`，**无一份堵住「填了数、同时把那条 assert 也改了」**这条两步绕过；
- 判据的「该谁签」在五份里是**注释文字**（`# 差旅标准：…须财务侧产出并签认`），不是可查询的结构化字段，故无法整体查缺。

## What Changes（改什么）

**新增**：平台底座子系统 `zhuopin_platform/criteria_signoff/`
- `Criterion` —— 一条判据：`key` / `question`（要定什么）/ `owner`（该谁签）/ `note` / `signoff` / `raw_value`。frozen，未签认时读 `.value` 抛。
- `Signoff` —— 签认落档记录：`signed_by`（实名）/ `signed_on` / `evidence`（落档凭据）/ `rule_version`，**四项全必填、无默认值、拒占位词**。
- `CriteriaRegistry` —— 场景级注册表：整体查缺（`require_all_signed`）、状态查询（`unsigned_keys` / `is_signed`）、`RULE_VERSION` 双向一致性校验（`assert_rule_version`）。
- 异常族：`CriterionNotSignedOffError` / `CriterionContractError` / `UnknownCriterionError`，**全部 fail-loud，无一可吞**。

**不改**：🔴 本包**不动五个场景包**（FI5/FI6/FI8/FI9/FI10 的迁移是 A4 段的事，且须等本 design 审过）。**不部署、不触碰 `.51`**。

**🔴 刻意不收进底座的四类**（防止底座反过来绑死场景，详见 design D3）：具体判据名与值形状；三类非判据缺口（权限 / 存在性 / 前置）；L2 默认侧等模型层纪律；与 `AuditLogger` 的联动。四项均列为 design 定夺项，**不由起草方自行拍板**。

### 本次退休哪一个既有守卫（机制类变更包强制，协议〇.9 措施 B / 队列 #308）

**退休对象**：五份场景本地的判据声明与其守卫用例——`FI5/FI6/FI8/FI9/FI10` 各自 `config.py` 里由 `test_unsigned_criteria_stay_none` 守着的裸 `None` 常量（4+4+3+3+3 = **17 条**）与该用例本身（**5 份**）＋ `test_rule_version_marked_unsigned`（**5 份**）。收进底座后，17 条常量收为 5 张注册表声明，10 份守卫用例收为底座 1 份（`tests/test_criteria_signoff.py`）。

🔴 **一处须点名、不并入 17 条的**：FI10 的 `SLOW_MOVING_CRITERIA`（L9 呆滞口径）**性质上确实是一条判据**，但它的缺口成因是「**无源可取**」而非「未签认」——`#474` 要求从 SC7 取，而 SC7 那份口径②期 2027-01 尚未落地。它在 FI10 里由独立用例 `test_l9_slow_moving_source_absent` 守，未并入那条 parametrize。**本包不代判它归不归注册表**（归了则 owner 填谁？姚祖怡尚未确认口径本身），列为 design 定夺项 ②′。

**one-in-one-out 记账**：+1 底座模块 / −10 份手抄守卫用例。

🔴 **但退休动作本身不在本包内**：本包（A3 段）只建底座，**实际退休发生在 A4 段**（改五个场景包），两段成对。**若 A4 不执行，本包就是「只增不减」**——底座与五份手抄并存，是比现状更差的状态（同一件事两处守、迟早对不上）。故：
- design 审通过时 MUST 同时批准 A4 段执行，二者不得拆开批；
- 若 design 审否决 A4，则本包应整体撤回，而非留在仓库里。

已在 `tasks.md` 把该配对关系写成显式验收条件。

### 伴生文件的 .gitignore 覆盖（队列 #328 子项②）

**不适用**：本变更**不新增任何自动生成文件形态**——`criteria_signoff` 是纯内存数据结构，无锁文件、无快照、无状态文件、无日志、无备份副本、无重命名退路产物，不写盘。判据签认的落档凭据（`evidence` 字段）指向的是**人工产出的既有文档**（如《报销政策判据表》），由人放进 `3-治理与合规/` 并正常入 git，不由本模块生成。

核实方式：本包新增文件仅 `zhuopin_platform/criteria_signoff/{__init__,errors,models,registry}.py` 与 `tests/test_criteria_signoff.py` 五个源文件，均为普通 `.py`，`git check-ignore -v` 对其**无命中**（即不被忽略，会正常入库），已实测。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？**
   本包是**机制模块，自身不含任何业务判据**——它恰恰是「用来盛放判据缺口的容器」。真正的默会经验在**五个财务场景各自的 17 条判据**里，它们此刻全部未签认，逐条为：
   - FI5（4 条）：差旅标准表 / 招待限额表 / 超预算拦截阈值 / 异常报销风险分级边界；
   - FI6（4 条）：金额突增口径 / 频率异常口径 / **关联方识别口径** / 高风险 escalation 门限；
   - FI8（3 条）：资金缺口门限 / 大额逾期应收催收门限 / 历史回款周期取样口径；
   - FI9（3 条）：资本化/费用化判据 / 高新认定政策库 / 研发费用占比口径（🔴 准则口径与高新口径分子分母不一致，混用即错）；
   - FI10（3 条）：NRV 估算口径 / 库龄超期门限 / 项目终止未耗物料预警口径。（另有 `SLOW_MOVING_CRITERIA` 一条，缺口成因是「无源可取」而非「未签认」，见上「退休」节 ②′。）
   本包对它们的贡献是：把「只在注释里说了句须签认」变成**结构化、可整体查缺、读了就炸**。
2. **由谁显性化？**
   - 机制本身（本包）：**CC 泳道 fin-criteria 起草，Shao Peishen 签认**（判据签认属跨场景约定 ⇒ 口径类，须其拍板）。
   - 17 条业务判据：持有人 **财务侧（唐燕萍线）**，backup 待定；其中 FI8 银行余额取数**授权**另需 **CFO 办公室**（🔴 那是权限、不是判据，不走本模块）；FI10 的 L9 呆滞口径挂 **姚祖怡**（且当前**无源可取**，SC7 那份口径②期 2027-01 尚未落地）。
   - 🔴 backup 双人制与台账登记：MUST 在 A4 段随五场景迁移一并登记进《跨场景前置数据与知识库任务总表》§一.2 知识资产台账，**本段未登记，已列为 tasks 待办**。
3. **用什么方法提取？**
   - 机制本身：**AI 起草·专家批改**（本 proposal + design 即起草物，交 Shao Peishen 批改）。
   - 17 条业务判据：**AI 起草·专家批改工作坊**为主（判据表逐条列草案交财务侧批改），**L2 改判判例累积**为辅（FI5/FI6 上线后由改判反推边界）。知识型前置按「启动前 8 周」倒排——五场景排期 2027-04，首轮工作坊倒排至 **2027-02** 前，**本包不代排**。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：**档 0（骨架，未过 design 审）**。
  🔴 **本包刻意不宣称档 1**。理由与五个财务场景包同：档 1 ＝「mock 验证」，而本模块的 mock 验证只能验「未签认时抛异常」，**它本来就是全部逻辑**——没有第二半可验。真正的价值兑现要等 A4 迁移后、五个场景确实经它取判据，那时才谈档位。此处宣称档 1 等于把「还没人用」说成「验证通过」。
- **晋下一档的条件**（逐条）：
  1. design 审通过（Shao Peishen），且**同时批准 A4 段执行**（见上「退休」节，二者不得拆批）；
  2. A4 段完成：五个场景包 `config.py` 改为注册表声明，本地 17 条裸 `None` 与 10 份手抄守卫用例删除，五场景单测全绿且**判据缺口数量前后一致**（迁移不得顺手补数）；
  3. `openspec validate --all --strict` 全绿、底座全量回归零回归；
  4. 根 `CLAUDE.md` §4 与 `5-平台底座/CLAUDE.md` 子系统表同步补 `criteria_signoff` 行（🔴 两处**原文原样**，须同改，见 design 风险段）。
- **价值指标**（风险型）：
  - **基线**：五个财务场景 17 条未签认判据，分散在 5 份手抄实现里；「填了数同时改掉守卫」两步即可静默绕过；「该谁签」不可机器查询，整体查缺**无法进行**。
  - **目标**：绕过所需步数由 2 步升为**不可能**（构造期不变式，非用例断言）；任一时刻可一条命令列出全部未签认判据及其 owner；判据签认漂移事故 **0 起**。
  - 🔴 **基线由业务 Champion 确认**：本指标由起草方自评，**未经财务侧 Champion（唐燕萍线）确认存档**，属 design 审待确认项。
- **LLM 判据黄金集**：**不适用**——本模块不含任何 LLM 运行时判断，是纯确定性数据结构与校验。（五个财务场景各自是否含 LLM 判断，由其各自变更包回答，本包不代答。）

- **红线核对**：
  - **mock 先行**：✅ 本模块不接任何数据源，纯内存结构，无真实库访问。
  - **audit 留痕**：⚠️ **本包未接 `AuditLogger`**——五份本地实现均无此联动，本包不凭空加（design 定夺项 ④）。🔴 但须注意：签认本身是「AI 辅助决策的口径来源」，IATF 16949 要求可追溯，**是否须在签认/读取时留痕由 design 审裁定**，不由起草方自决。

  - **L2 门禁**：✅ 不适用——本模块不产生任何业务结论、不触发任何通知、不执行任何动作。
  - **ISO 26262 / MISRA**：✅ 不适用——非嵌入式、非安全相关代码。
- **部署**：🔴 **本包不部署、不触碰 `.51`**（opener 硬边界）。底座包为可编辑安装的 Python 包，路径引导已由 `bootstrap.py` 承接，新增子包无需任何部署动作。
