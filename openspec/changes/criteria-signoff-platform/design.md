## D0 · 这件事的成因（一句话）

`#345` 是「35 份路径引导手抄副本」，代价是任一份漂了都测不出来。**判据签认此刻正在同一条路上**——五份实现同一天由同一泳道写出，**当天就已分岔三处**（见 proposal §Why）。收进底座不是重构洁癖，是止损。

## D1 · 契约边界：什么是真共通，什么是场景特有

这是本包**唯一真正的设计工作**。判法是一句话：**把这条东西收进底座后，底座会不会开始替场景决定业务？** 会 ⇒ 不收。

### D1.1 收进来的四件事（五份实现里逐份核对，5/5 命中）

| # | 共通物 | 五份实现里的形态 | 底座里的形态 |
|---|--------|------------------|--------------|
| 1 | 判据有**身份**与**说明** | 常量名 ＋ 上一行注释 | `Criterion.key` / `.question` |
| 2 | 判据**该谁签** | 注释文字（「须财务侧产出并签认」） | `Criterion.owner`（**结构化，可查询**） |
| 3 | 未签认 ⇒ `None`，**读它必抛** | 常量 `= None` ＋ 一条 `assert is None` 用例；**「读了会怎样」五份都还没实现**（引擎未建） | `Criterion.value` property，抛 `CriterionNotSignedOffError` |
| 4 | `RULE_VERSION` 须自陈 `unsigned` | 五份各写一遍 `assert "unsigned" in ...`，**五份都只查了一个方向** | `assert_rule_version()`，**双向查** |

> 第 3 行值得单独说一句：五份实现只做到了「值是 `None`」，**「读到 `None` 会 fail-loud」是它们各自 config docstring 里的一句承诺，尚无代码兑现**（因为引擎都还没建）。本包把那句承诺变成了代码——这是收进底座相对五份手抄的**净增量**，不是搬运。

### D1.2 🔴 刻意**不**收进来的（每条都是主动否掉，不是漏了）

| 不收的东西 | 出现次数 | 为什么不收 |
|-----------|---------|-----------|
| 具体判据名（`TRAVEL_STANDARD_TABLE` 等）、值的形状、领域文案 | 18 | 场景数据。进底座 ＝ 底座替场景定业务口径，正是本包要防的反向绑死 |
| **权限缺口**（FI8 `BANK_BALANCE_ACCESS`，须 CFO 办公室） | **1** | rule-of-three 未触发；且它不是「还没定个数」，是「**能不能取都没人批**」，解除方式与判据完全不同 |
| **存在性未核实**（FI9 `TIMESHEET_SYSTEM_EXISTS`） | **1** | 同上；它不是「还没接」，是「**不知道有没有**」，解除方式是去核实、不是去签认 |
| **前置未满足**（FI10 `CHIP_PRICE_API`，队列 `#475`） | **1** | 同上；解除方式是上游选型签约 |
| L2 默认侧（`needs_manual_review=True`）、`disclaimer` 必填、`confirmed_by` 无默认 | **5/5** | **命中了 rule-of-three，但出圈**——属模型层纪律，不属判据签认。硬塞进本模块会让 `criteria_signoff` 变成「财务场景公共基类」，那是另一件事、另一个包 |
| 与 `AuditLogger` 的联动 | **0/5** | 五份本地实现都没有。凭空加＝起草方自己发明了一条要求 |
| 判据的持久化 / 文件格式 / CLI | 0/5 | 同上，无一处要求 |

**关于那三类「1 次」缺口，必须说清一件事**：它们与判据的**机械形状确实一样**（值恒 `None`、读了要炸、有一段说明文字），所以「顺手一起收了」的诱惑很大。不收的理由有两条，第二条比第一条重要：

1. rule-of-three 未触发（各 1 次）；
2. 🔴 **五个场景包明确要求它们「性质各不相同、分别立牌不合并」**（FI10 `__init__` 与 FI8 config 首部均有原文）。把四种解除路径（签认 / 授权 / 核实 / 等前置）压成一个 `None`，等于把「谁该去做什么才能解除」这个信息抹掉——而那恰是这些立牌的全部价值。

⇒ ✅ **已裁：`G-2 = (a)` 不收**（Shao Peishen 2026-09-03）。三条**原样留在各自场景包内**，A4 迁移时不得顺手并入；「合并成一个 `None`」的做法已被明确否决。详见 §定夺项（已裁决）②。
📌 **另需注意 `SLOW_MOVING_CRITERIA` 不在这三条之列** —— 它经 `EE-4` 后已变成一条标准待签认判据，按 `G-3 = (a)` **归进注册表**（owner ＝ 财务侧），故场景侧判据总数由 17 变 **18**。详见 §定夺项（已裁决）②′。

## D2 · fail-loud 怎么落地（三处实现选择，均为防绕过）

### D2.1 `raw_value` / `value` 拆成两个名字

存的值叫 `raw_value`（**名字刻意起丑**：读起来就像"你正在绕过保护"，因为你确实是），读值走 `value` property 并在未签认时抛。

**为什么不直接叫 `value` 一个字段**：dataclass 字段是裸属性，`c.value` 会静默返回 `None`——那就等于没有守卫。

**为什么 `value` 选 property 而非 `get_value()` 方法**：**属性天生传不了参数**。方法迟早会被人加上 `default=`；属性从语法上就加不了。这是用语言特性替代纪律。

### D2.2 不变式挪到构造期，不留在用例里

五份手抄的守法是「用例断言 `is None`」。**那条防线是两步可破的**：填个数、顺手把断言也改了——两次改动、一个 commit、CI 全绿。

本包把它改成**构造期不变式**：`raw_value` 非 `None` 而 `signoff` 为 `None` ⇒ 当场抛。想绕过就必须构造一个假的 `Signoff`，而 `Signoff` 四项必填、拒占位词——**你得编一个人名、一个日期、一份文件路径**。这不再是"顺手"，而是明知故犯且留下了名字。

**这是本包对五份手抄的第二处净增量。**

### D2.3 状态查询与读值彻底分开

`is_signed()` / `unsigned_keys()` / `signed_keys()` 只返回**布尔与 key，永不返回值**。所以它们无法被当作旁路（`if reg.is_signed(k): v = reg.value_of(k) else: v = 默认` 这种写法仍然要你**亲手写下那个默认值**，藏不住）。

### D2.4 反例用例：怎么证明守卫在承重

opener 要求「关掉守卫即失败」。本包做了两层，**第二层是实测、不是声称**：

1. **常驻元测试**：`test_guard_is_load_bearing` 用一个把 `.value` 守卫关掉的子类跑同一条断言，断言它**必须报 `DID NOT RAISE`**。
2. **一次性变异实测（2026-09-03 已跑）**：把 `models.py` 里 `value` 的 fail-loud 守卫**整段删掉**后重跑套件 ⇒ **4 条用例转红**（`test_reading_unsigned_criterion_raises` / `..._via_registry_raises` / `..._error_message_says_who_should_sign` / `test_signed_returns_new_object_and_leaves_original_unsigned`）；还原后 **45 passed**。

⇒ 那 45 条绿灯**不是碰巧绿的**。

📌 **2026-09-03 补（OP-0903-D2，`G-1` 落地）**：新增的日期格式校验按同一套做法各做了一层 —— 一次性变异实测（拆掉 `Signoff.__post_init__` 里那行校验）⇒ **8 条转红**、还原后 **59 passed**；常驻元测试 `test_date_check_is_load_bearing`（monkeypatch 掉 `_require_iso_date`）把该证明留在套件里。本文件用例数 **45 → 59**。

## D3 · 底座不绑死场景的三道自律

1. **底座不认识任何场景**：`criteria_signoff` 的**可执行代码**里没有任何场景侧标识名（`grep` 实测：`TRAVEL_STANDARD_TABLE` / `BANK_BALANCE_ACCESS` / `CHIP_PRICE_API` 等 0 命中），没有一处按场景分支。`scenario` 是构造参数（字符串），不是枚举——**新场景不需要改底座**。
   ⚠️ 如实说明：`FI5`/`FI6` 等**确实出现在 docstring 与注释里**（7 处，`__init__`/`models`/`registry`），作用是**记来源**（这条约束是从哪五份实现抽出来的）与举例。它们不参与任何逻辑，删掉不影响行为——但保留它们比留一段无出处的抽象契约更有用。
2. **底座不决定判据的值的类型**：`raw_value: Any`。阈值是浮点、标准是字典、政策库是对象，底座一律不管。唯一约束是「不得为 `None`」，而那是**语义约束不是类型约束**。
3. **底座不替场景决定何时校验**：`require_all_signed()` 是给场景在引擎启动前**自己**调的，底座不劫持任何 import 期钩子、不自动运行。

### ① 占位词黑名单要不要留 ⇒ ✅ **G-1 ＝ (a) 留，另补日期格式校验**

**裁决原文**：「**(a) 留**；🔴 **另补 `YYYY-MM-DD` 日期格式校验**（现在 `2026-13-45` 能过）。」

**当时的呈报**（保留备查）：`Signoff` 拒绝 `TBD` / `待定` / `n/a` / `无` 等 13 个占位词作为签认人、日期或凭据。支持留 —— 空签认人和 `signed_by="TBD"` 是同一件事的两件外衣，只拦前者等于没拦；反对留 —— 这条是起草方新加的、五份本地实现里没有，且黑名单永远列不全。

**为什么「列不全」不构成反对**：黑名单不是穷举式防线，作用是**把「顺手糊弄」的成本抬到「明知故犯」**。列不全的那部分由 `Signoff` 四项必填兜住 —— 你得编一个真人名、一个日期、一份**可被第三方翻出来核对**的凭据路径，那已经不是顺手，是留了名字的作假。它与 D2.2 的构造期不变式是**同一道防线的两半**，只留一半等于漏。

**🔴 已落地（2026-09-03，OP-0903-D2）**：
- 黑名单 13 词**原样保留、一字未动**；
- `models.py` 新增 `_ISO_DATE_RE` ＋ `_require_iso_date()`，在占位词那道**之后并列**再校一道。两步都不能省：⑴ 正则定死书写形态（`date.fromisoformat` 自 Python 3.11 起**也认 `20260903`** 这类紧凑写法，只靠它会漏）；⑵ `date.fromisoformat` 定死这一天真实存在（正则拦不住 `2026-13-45`）；
- 反例用例 8 条（`2026-13-45` / `2026-02-30` / `2026/09/03` / `20260903` / `2026-9-3` / `03-09-2026` / `2026-09-03T00:00:00` / `2026年9月3日`）＋ 正例 4 条（含闰日 `2024-02-29`）；另有一条 `test_date_check_is_additional_not_a_replacement_for_the_blacklist` **守「别拿日期校验顶替黑名单」**；

### ②′ FI10 的 `SLOW_MOVING_CRITERIA`（L9 呆滞口径）归不归注册表 ⇒ ✅ **G-3 ＝ (a) 归进去**

**裁决原文**：「**(a) 归进注册表**；owner ＝ **财务侧**；`question` 须写明「FI10 先出、SC7 后对齐（EE-4），签认前须知会 SC7 口径确认人」；🔴 **连带：`tasks.md` 4.3 验收数 17 → 18**。」

🔴 **它为什么从「不该进」变成了「该进」—— 这条成因必须传下去**：
- **EE-4 之前**：它是「**无源可取**」—— 要从 SC7 取，而 SC7 呆滞口径**根本不存在**（实测 `sc7_inventory/business_rules.py` 只有 R1 金额阈值 / R2 未认证供应商两条；`SC7/CLAUDE.md` 三处明写呆滞处置属②期深化 2027-01）。这种形态属**前置未满足**，与 §② 的 `CHIP_PRICE_API` 同类，**不该进注册表**。
- **EE-4 之后**（Shao Peishen 2026-09-03 裁「FI10 先定口径、SC7 后对齐」）：它变成了「**我方自己出口径、找人签认**」—— 这就是一条标准的待签认判据，**该进注册表**。
- ⇒ **裁决之间会互相改变彼此的性质。答完一条要回头看它是否解掉了另一条的前提。** 起草方写 design 时尚未意识到这层联动，是审读环节查出来的。

**owner 为什么是财务侧、不是姚祖怡**：口径要用于**存货跌价计提**（进财务报表），计提口径本就该财务签；姚祖怡是 SC7 业务口径的确认人，让她签一条会影响财报的口径超出其职责面。但 SC7 将来要来对齐 ⇒ 故**把知会义务写进 `question`**，两边都不丢。

**🔴 已落地（2026-09-03，OP-0903-D2）—— 落在哪、以及为什么落在这里**：
- 本段**只做「登记」的落档**，写进 `tasks.md` 4.1（含逐字的 `Criterion` 声明形态：`key` / `owner` / `question` / `note`）与 4.3（验收数 **17 → 18**）；

### ④ 签认／读取要不要接 `AuditLogger` 留痕 ⇒ ✅ **G-5 ＝ (a) 不接，改反向依赖**

**裁决原文**：「**(a) 不接**（保底座零依赖）；🔴 **改反向依赖** ＝ 引擎 `record(AuditEvent)` 时把当时的 `RULE_VERSION` 写进 `decision`，**并进 A4**。」

**不接的三条理由，第三条最硬**：
1. **零依赖是 `criteria_signoff` 可被任意场景安全引用的原因之一**（D3 自律）。接上即产生对 `audit` 的依赖；
2. 五份本地实现 **0/5** 有此需求，接上就是起草方自己发明了一条要求；
3. 🔴 **IATF 可追溯的诉求已经被满足了，而且满足得比 jsonl 更好**：`Signoff` 四字段（**实名 / 日期 / 落档凭据 / 规则版本**）本身就是完整审计轨迹，且它**写在代码里、进 git、有 commit 历史与作者**。一条 jsonl 记录可以被覆盖，一次 git 提交不能被静默改掉。**用日志去追溯一个已经在版本控制里的事实，是降级不是升级。**

**语义层面的理由**：既有 `AuditEvent(scenario, action, evaluator, automation_level, decision, data_sources, content_hash)` 是为「**AI 每一次决策**」设计的流水（一天可能几千条）；而**签认是人的一次性动作**（全项目 18 条判据、一年十几次）。塞进同一条 jsonl 会让审计日志的语义变糊 —— 查「AI 做过哪些决策」时混进「某人某天签了个字」。

#### 🔴 反向依赖方案（本包只写方案、**不接线**；实施归 A4，见 `tasks.md` 4.7）

**依赖方向**：**审计日志指向判据版本**，**不是**判据模块去写审计日志。

- **谁改**：五个场景各自的**引擎**（A4 段落地），**不是** `criteria_signoff`，也**不是** `zhuopin_platform.audit`；
- **怎么改**：引擎在调 `AuditLogger.record(AuditEvent(...))` 时，把**当时生效的** `RULE_VERSION` 写进 `AuditEvent.decision`（如 `decision={..., "rule_version": RULE_VERSION}`），成本约一行；
- **为什么这样就够**：`RULE_VERSION` 在全部判据签认完成前**自带 `unsigned` 标记**（`CriteriaRegistry.assert_rule_version()` 双向校验），所以每条 AI 决策的日志里天然记着「这次用的是哪一版口径、当时签完没有」——**「每条 AI 决策可回溯到当时用的哪版口径」这个诉求被完整满足**；
- **🔴 底座侧净变化 ＝ 零**：`criteria_signoff` 不 import `audit`，不新增任何字段、任何钩子。零依赖自律（D3）不被破坏。

- **风险 · 迁移时顺手补数**：A4 迁移最可能的翻车形态是「反正在改 config，把几个明显的阈值先填上」。治法＝A4 验收条件写死「**迁移前后未签认判据数量必须相等**」，已进 `tasks.md` 4.3。🔴 **该数已由 17 改为 18**（`G-3 = (a)` 把 `SLOW_MOVING_CRITERIA` 归进注册表所致）—— **18 条进、18 条出**。⚠️ 这正是那条验收条件在起作用的证明，不是它的缺陷：一条判据的归属变了，验收数必须跟着变，否则 A4 会按「迁移失败」退回。

- **已否决 C · 判据可变（`criterion.sign(...)` 就地改）**：写起来短一行，但会让"谁在哪一行签的"从代码里消失、变成某次运行期赋值。⇒ 否决，改为 frozen ＋ `signed()` 返回新对象。
