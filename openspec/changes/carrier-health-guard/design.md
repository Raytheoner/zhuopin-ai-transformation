## Goals / Non-Goals

**Goals**

- 让「必载载体陈旧」这件事**产生机器信号**，且信号类型是**常驻状态**（出现→告警、回落→自动解除），不是事件提示。
- 把 `§四 #68` 那三个坑从一段叙述**变成可执行流程**，使下一次对齐不依赖「有没有读到那段话」。
- 守卫自己**每天证明它读到了正确对象**（即使不告警）。

**Non-Goals**

- **不自动对齐、不自动重启生产服务。** sweep 无权也不该去动生产（既有 `_announce_resident_service_deployment_hint` 的注释已确立这条边界，本包沿用）。
- **不改孤儿 worktree 扫描的任何删除判定**（纯增列，预授权④）。
- **不调阈值**（首月只攒样本，预授权①）。
- 不替代既有事件型部署提示（proposal 已论证两者不可互相取代）。

## 决策点 1（超出五项预授权，已获答复）：子项 B 的信号出口做到哪一档

**问题**：`#338` 字面只要求「扫描报告新增一列」。但实测 `git grep` ＋ 全盘遍历双向确认——**`工具-孤儿worktree扫描.py` 没有任何调度器调用它**，唯一调用点是值周巡检 skill `zhuopin-queue-audit` SKILL.md 第 39 行的一句人手跑的命令。

⇒ 只加列，信号仍落在一份**要靠人记得去跑**的周报里，而 `#338` 的共同命题正是「全靠人事后发现」。**加列本身不产生机器信号。**

**选项**：(a) 只加列 ／ (b) 加列 ＋ sweep 第 5 类常驻告警 ／ (c) (b) ＋ 人工触发的对齐重启脚本。

**✅ Shao Peishen 2026-08-23 先拍板 (c)，同日又亲自推翻 (c)、改为「分两级持续同步」**（补进队列 §一 `#338` 行首，明写「优先级高于下方派单说明」）。

🔴 **推翻的理由，比这三个选项本身更重要**：**(a)(b)(c) 三个选项其实是同一件事的三种包装** —— 它们都把「对齐」当成一次性动作，只在**触发人**上做文章（自己想起来 / 被周报提醒 / 被机器提醒）。而根因是 **「落后是持续过程，约 70 提交/天」**。

> **一次性动作治不了持续过程，无论触发人是谁。**

`#68` 就是实证：08-19 五项验收全过、四天后落后 305。**我当时给的 (c) 档只会让这段历史原样重演，只是重演时会有一条告警在旁边响。** 这一层是提问方（我）没看穿、由他当场补上的——**我把「谁来按按钮」当成了问题，而问题是「这件事根本不该由按按钮来完成」。**

**⇒ 改定方案（本包按此实现）：**

| | 做什么 | 频率 | 风险 |
|---|---|---|---|
| **① ff** | `--ff-only` 对齐执行体 worktree | **每轮 sweep 自动做** | 低——sweep 每小时本来就在 `_reconcile_with_origin_and_push` 对齐 master，这是同类操作 |
| **② 重启** | 停服→启动→验重启→验活 | **按需**：只在本轮 ff 真的动了常驻服务代码路径时 | 高——故须可一键关闭，且**缺省走人工确认** |

**为什么 sweep 是正确的挂载点（架构理由，不是就近）**：实测四个计划任务里，**只有 `ZhuopinCommitSweep` 的 Action 指向主工作区**，其余三个都指向那个落后 305 的 worktree。⇒ 挂进 sweep 的守卫**合入即生效**；挂进那三个中的任何一个，都会撞上「新代码部署不到执行体」——**即用来检测落后的东西自己因为落后而没被部署**。这不是假想，它就是本包要解决的那个问题的自指形态。

## 决策点 2（超出五项预授权，已获答复）：「常驻执行体」名单从哪来

**选项**：(a) 从 Windows 计划任务反查 ／ (b) 白名单配置文件 ／ (c) 硬编码。

**✅ Shao Peishen 2026-08-23 拍板 (a)。**

**判据**：枚举计划任务，取其 Action 的 `Execute` ＋ `Arguments`，**凡路径落在 `<repo_root>/.claude/worktrees/<name>/` 之下者，该 `<name>` 即为常驻执行体**。

**为什么优于白名单**：新增一个指向 worktree 的常驻任务会被**自动纳入**，不需要有人记得去登记。白名单本身就是一个新的人守点——而本包的整个立意是减少人守点，不是换个地方增加。

🔴 **但 (a) 有一个必须显式处理的失败模式**：sweep 若不在本机 Windows 跑（CI、别的机器、权限不足），`Get-ScheduledTask` 拿不到东西。**此时绝不能返回空名单然后静默判「零执行体、一切正常」**——那正是 CLAUDE.md §5「工具静默回退」记的那一族：*当一个只读命令返回了「太干净」的结果，先问它是不是根本没读到我以为的那个对象*。

**⇒ 三态显式区分，不合并**：

| 情形 | 行为 |
|---|---|
| 查询成功，有执行体 | 正常判落后并告警 |
| 查询成功，零执行体 | 日志明写「计划任务查询成功，无任务指向 worktree」 |
| **查询失败/不可用** | 日志与告警明写「**执行体名单未取到**（原因）」，**不推断为零** |

⚠️ 既有 `RESIDENT_SERVICE_*` 那组常量的注释里写着「③ 只能写成常量，没有任何仓库内文件可读——**计划任务的真实设置不在仓库里**（#199 的核心教训）」。本决策点**不推翻那句**：那组常量服务于「本批路径是否命中服务目录」这个**静态判据**，本包新增的是**运行时反查**，两者并存。**本包不改那组常量。**

## 决策点 3：尺寸判据量什么、量哪一份

- **量字节数**（`len(bytes)`），不是字符数、不是行数——阈值 90 KB / 50 KB 是按字节给的。
- **量 sweep 自己 `repo_root` 下的那一份**，即主工作区真身。**不遍历 `.claude/worktrees/**` 下的 13 份副本**：那些副本的尺寸是历史版本的尺寸，对它们告警既无意义又会天天响。
- **批次日期跨度判据只对根文件**——预授权①的原文就是这样分的（「根 `CLAUDE.md` >90KB **或**顶部进度段跨 >1 个批次日期；场景与底座 `CLAUDE.md` >50KB」）。这一分法恰好也绕开了场景文件顶部段**结构不统一**的问题（`工具-CLAUDE进度段lint.py` 实测：SC8 型 3 份、其余 5 份结构各不相同），不必为此新造结构判定。

## 决策点 4：顶部段解析复用 lint，还是另写

**复用 `工具-CLAUDE进度段lint.py`**（`parse_structure_a` ＋ `ENTRY_DATE_RE`），sweep 侧不另写一套。

理由是本项目已经吃过的亏：`工具-CLAUDE进度段lint.py` 自己的模块注释记着，**同一个「顶部段条目」判据，用裸正则数出 4 条、用区间判据数出 2 条**，且那个错误的判据「看起来很确定」。⇒ 再写第二套解析，等于再造一次同样的漂移，而且两套的分歧不会有任何报错。

**实现约束**：lint 脚本文件名含中文且以「工具-」开头，不是合法 Python 标识符 ⇒ 走 `importlib.util.spec_from_file_location` 动态导入（sweep 内已有同类先例，`editlock` 即以此法被 lint 反向导入）。**导入失败必须如实报「顶部段判据不可用」并跳过该半条，不得静默把它当作「未超限」。**

## 决策点 5：第 5 类告警的触发判据用哪个「落后数」

预授权④只锁定一件事：**用 git 提交计数，不用 mtime**（A9 教训）。它没有锁定用哪一个计数。

- **加列那一列**（子项 B 的原文要求）：`CLAUDE.md` 触碰提交数 —— **照 #338 字面，不改**。
- **第 5 类告警的触发判据**：**HEAD 落后 master 的总提交数**。

**为什么告警不用 `CLAUDE.md` 触碰数**：执行体每天跑的是**代码**。实测这份 worktree 落后 305 个提交，其中触碰 `CLAUDE.md` 的只有 26 个——**用 26 去衡量一个跑代码的载体，会把严重程度低估一个数量级**。而 `CLAUDE.md` 触碰数对**开发用 worktree** 是合适的（那里关心的是「我这个 session 载入的规则有多旧」）。

**⇒ 两个数都报，不二选一**：扫描报告那一列与告警正文都同时回显「HEAD 落后 N / 其中触碰 `CLAUDE.md` M」。读者不必知道我们内部用哪个数做的判据，他看到的是两个事实。

### ~~阈值 `RESIDENT_CARRIER_LAG_ALERT_THRESHOLD = 100`~~ —— 🔴 **随改版整条作废**

初版曾要为「落后多少算该管」定一个数（拟 100，理由是 `>0 即告警` 会天天响、必被无视）。**改版后这个问题不存在了**：自动 ff 之后落后恒为 0，没有「多少算该管」可言。

🔑 **这是本次改版的一个附带收益，值得单独记一笔**：**一个本来要靠经验拍板、且拍完还要攒一个月样本去复核的数字，被一个结构性做法直接取消掉了，而不是被另一个数字取代。** 凡是发现自己在为一个阈值找理由时，先问一句：**这个量能不能干脆不让它涨起来？**

告警语义随之从「落后了」改为**「有例外」**——ahead>0 停手／工作区脏／ff 失败／需重启但开关关着／自动重启失败。这五种都是**人必须介入**的状态，而不是一个连续量的某一段。

## 决策点 6：告警节流与解除语义

沿用 `_track_and_alert_standing_state` 既有形状，**不做 schema 迁移**：

- 单时间戳状态形状（`{key: last_alerted_iso}`），与既有 `SCENARIO_SPEC_GAP_STATE_REL` / `STALE_CHANGE_STATE_REL` 兼容。
- 再提醒间隔 **24 小时**（与既有两类一致）。
- **key 的选取决定了解除语义**，这里有一个必须想清楚的点：
  - 子项 A 的 key ＝ **文件相对路径**（如 `CLAUDE.md`）⇒ 尺寸回落到阈值内即解除。**不把尺寸值放进 key**，否则每涨 1 字节就是一个新 key、天天当成新问题告警。
  - 子项 B 的 key ＝ **worktree 名**（如 `wecom-service-home`）⇒ 落后归零即解除。同理**不把落后数放进 key**。
- ⇒ 告警正文里的**数值会变，但 key 不变**：这正是「常驻状态」与「事件」的分界线。

## 两级同步：① ff 每轮做（sweep）／② 重启按需（`工具-执行体对齐重启.ps1`）

🔴 **这一节是本包相对 `#338` 原文的主要增量。** `#338` 只定义了「怎么检测落后」；行首改版进一步定死了「检测到之后怎么办」——**不是提醒人去做，而是每轮自己做掉低风险那一半。**

### ① ff：sweep 每轮做

- **挂载点**：`_reconcile_with_origin_and_push` 之后——sweep 刚把主工作区对齐到 origin，此刻的 `master` 就是最新的。
- **三道停手闸，任一命中即不 ff 并告警**：`ahead > 0`（执行体上有本地提交）／已跟踪文件脏／`--ff-only` 自身失败。**绝不 rebase、reset、revert、cherry-pick**——那会在生产载体上造出第三种代码状态。
- 🔴 **刻意不做每轮备份**：`--ff-only` 若会覆盖某个未跟踪文件，**git 自己就会拒绝并非零退出**，据此告警即可。每轮复制 26 个 `reports/` 文件既无必要，又会自己制造一堆需要清理的目录。`#267` 那次事故的动作是 `worktree remove`（真删），与 ff 的风险面不同，不该套同一套防护。

### ② 重启：按需，且缺省走人工

- **判据复用 `_touches_resident_service`（`#87` ⑶⑷ 白名单），不另写一套**——`#338` 明写这一条。输入 ＝ 本轮 ff 实际前进的提交所触碰的路径（`git diff --name-only <ff前>..<ff后>`）。
- **开关 `CARRIER_AUTO_RESTART_ENABLED`，缺省 OFF**（`.env` 无键/读不到/值不认识一律 OFF）。首月只 ff，重启走人工确认，攒够样本再放开（`#257` 先攒样本纪律）。
- **开关 ON 时，sweep 调用 `工具-执行体对齐重启.ps1 -RestartOnly`，而不是自己实现一遍**。这是「勿另写一套」真正的兑现方式：**人工执行与机器执行走同一份代码，两套实现迟早分叉，而分叉不会有任何报错。**

### 🔴 实跑当场又抓出两个，`#68` 的「三个坑」实为五个

**两个都是 2026-08-24 首次真实运行时撞到的，不是设想。共同点：判据/文档说的和命令做的是两回事，而两者都「看起来很确定」。**

**第 4 个坑 · 脏判据把未跟踪件也算进去了。** `_carrier_tracked_dirty` 的文档字符串明写「未跟踪／被 ignore 的内容不在此判」，用的却是 `git status --porcelain=v1` —— 它**缺省连未跟踪件一起报**（`??` 行）。执行体里那个唯一的未跟踪 wrapper `run-followup-dispatch-check.ps1` 于是把整个 ff 挡住了，第一次真 sweep 报的是「已跟踪文件有未提交改动 …… 已停手不 ff」。修法＝显式 `--untracked-files=no`，配两条反例单测（未跟踪件不算脏、ignored 内容不算脏，且 ff 后两者都还在）。
⚠️ **所幸失败方向是保守的**（该动手时没动手）；**若判反了就是「该停手时动了手」**——同一个疏忽，代价差一个量级。

**第 5 个坑 · 「重启」把一次性日任务也计划外拉起来了。** 三个关联计划任务里**只有 `ZhuopinAibotDevListener` 是常驻的**，另两个是每日一次性任务。初版对 `$tasks` 全量 `Start-ScheduledTask` ⇒ 实测启动后出现 **9 个进程**（3×wscript/powershell/python），两个日任务各被计划外跑了一遍。
**本次实测它们没对外发出任何东西**（`dispatch_batch_summary` 的 `sent: 0`，两个提醒 state 只更新了 seen 集合）——**但那是运气不是设计**：这一族脚本普遍是「报告上次以来的新增项并记下已见」，**计划外跑一遍有可能把新增项消耗掉却不通知任何人**。
修法＝停服前采集各任务 `State`，**只重启 `Running` 的**，其余显式跳过并说明；一个都不在跑时以退出码 **17** 停手——那时想做的是「启动」而不是「重启」，交人工判断。

🔑 **这两个坑合起来说明一件事**：`#68` 那三个坑是**上一次实操**踩出来的，本次实操又踩出两个。**「把已知的坑固化成脚本」本身不会让脚本变得可靠，只有真的跑一遍才会。** 这正是决策点 7（同批实跑）的价值所在——若按「先上线、下次再跑」，这两个缺陷会以「首次使用时」的形态出现在某个更糟的时刻。

### 那五个坑（脚本内建，两条路径共用）

**九关，每关都有一条「不这样做会怎样」**（`-RestartOnly` 模式跳过 2/3/5 三关）

| # | 步骤 | 为什么必须这样 |
|---|---|---|
| 1 | **身份校验**：该目录内 `.git` 条目存在 **且** 在 `git worktree list --porcelain` 注册项内 | 🔴 `#98` 实测：对**非注册**目录跑 `git -C`，git 会**静默向上找到主工作区的 `.git`**，返回主工作区的状态。照抄就会把一个空壳记成「干净、无需处理」。**判 worktree 身份不看 `git -C` 的输出。** |
| 2 | **可 ff 校验**：`merge-base --is-ancestor HEAD master` 且 ahead ＝ 0 | 不满足即**停，不做任何事**。绝不 revert、不挑拣提交——`#68` 的原话是「未在生产载体上造出第三种代码状态」 |
| 3 | **固化备份到仓库外**：未跟踪 ＋ ignored 内容全量复制，**回显清单与件数** | `#267` 真实事故：两份签字审计报告落在某 worktree 的 `reports/`（gitignore 命中），被判「干净可删」后随 `worktree remove` **真实丢失** |

### 退出码纪律（本项目已两次栽在这里）

**脚本自身 `exit <code>`，调用方读 `$LASTEXITCODE`。**

🔴 **禁止**用 `cmd /c ... && echo %ERRORLEVEL%` 之类取码：`%ERRORLEVEL%` 在 cmd **解析期**就被展开，读到的是命令**还没跑时**的值（`OP-0819-F` 实测读到 0、真值是 2）。同族第一形态是管道——报的是 `tail` 的码。**两者都表现为「拿到一个看起来很正常的 0」。**

### 刻意不做的三件事

1. **不默认自动跑。** 缺省 OFF 时脚本只在人工触发时执行，sweep 只告警并给出命令；开关显式打开后，sweep 才调用它的 `-RestartOnly` 模式。**ff 不受此开关约束——它是低风险那一半，每轮都做。**
2. **不修 `#355`**（`run-decision-reminder-check.ps1` 的孤立 CR）。它已单独立行，本包按范围红线不碰。⚠️ **实测补充一条 `#68` 未记的事实**：那三个 `run-*.ps1` wrapper **不在 git 跟踪范围内**（`run-decision-reminder-check.ps1` 与 `start-aibot-service-dev.ps1` 被 ignore，`run-followup-dispatch-check.ps1` 未跟踪）⇒ **ff 不会碰它们，也永远修不了 `#355`**；`run-*.vbs` 三份则是跟踪的。**这意味着「执行体落后 N 提交」这个判据从定义上就覆盖不到那三个 wrapper**，本包如实登记为未覆盖缺口，不假装闭合。
3. **不改 `.51` 部署链。** 本包只管本机 worktree 执行体；`.51` 是另一条链（既有事件型提示管那边）。

## 已知边界（不得表述为质量保证）

0. **重启会给 Shao Peishen 发一条 1:1 `gap_alert`。** 实测每次重启后服务都会因检出连接间隔而发一条私信（本次三轮重启共发 3 条）。这是既有行为、不是本包引入，但**「自动重启开关打开」意味着这条私信会变成自动发生的**——首月只 ff 的安排把这件事也一并压住了。
1. **计划任务反查只在本机 Windows 有效。** 别处跑 sweep ⇒ 报「名单未取到」，不是「零执行体」。
2. **加列只覆盖「经工具走」的路径**——手敲 `git worktree remove` 仍无拦截。沿用 `#267` 已确立的边界披露，本包不扩大也不假装闭合。
3. **重启仍需人动手（首月）。** ff 已是机器每轮处置；重启缺省走人工确认，开关打开后才自动。**「靠人发现」→「机器每轮对齐 ＋ 只在真需要重启时叫人」**。
3b. **sweep 会写生产载体。** 这是本包与本项目既有告警最大的行为差别——既有告警只读，本包的 ff 会改 `wecom-service-home` 的工作区。三道停手闸与「绝不强推」是这条差别的全部防护，配了真 git 仓库的单测（`ResidentCarrierFfTests`，含「ahead>0 时 HEAD 一个字节都没动」的反例断言）。
4. **两个尺寸阈值与落后阈值都是未经验证的经验值**，首月只攒样本。
5. **`run-*.ps1` wrapper 不在版本控制内**（见上），落后判据对它们恒为不可见。
6. **sweep 提前 abort 时本轮两类检查都不会跑。** 它们挂在 `main()` 的正常路径末段（与 #298 那两类同位置）；若本轮因脏文件、非 master 分支、推送非快进等原因走 `SweepAbort`，检查被跳过。**这是与既有告警一致的既有形状，不是本包新引入的缺口**，但须如实登记：sweep 连续 abort 的日子里，这两个守卫是静默的。
7. **本包上线当天预计零告警**（所有实测值都在阈值内）⇒ **「没响」不等于「有效」**。这正是强制每轮回显「当前值/阈值/差多少」的原因：那行日志是这个守卫每天唯一的存在证明。
