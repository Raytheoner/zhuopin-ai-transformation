# carrier-health-guard Proposal

## Why

**共同命题（队列 §一 #338）：必载载体的健康度目前没有任何机器守卫，全靠人事后发现。**

「必载载体」指两类每次新会话都会被读进去、读错就一路错下去的东西：

1. **`CLAUDE.md`**（根 ＋ 各场景／底座）—— 会话开场注入的规则本体。它只会长不会短，2026-08-16 实测：根文件 08-09 瘦身到 84,399 B 后 **7 天回涨到 106,353 B（＋26%），全程无人察觉**。
2. **常驻服务的执行体 worktree** —— 三个每日计划任务真正跑的那份代码。它只会越落越远，2026-08-23 实测：`wecom-service-home` **落后 master 305 个提交**。

### 🔴 这一条把问题的形状说清楚了，也决定了解法只能是「持续同步」

`§四 #68` 已于 **2026-08-19 完整做过一次对齐**——五项验收全过、ff 到 `6994fd4`、进程链 `CreationTime` 真刷新、心跳真实建连。**四天后又落后 305 个**（同期 master 前进 281）。

⇒ 问题从来不是「那次没做好」。做完当天归零，此后以约 70 提交/天的速度重新拉开，**而全程没有任何机器信号**。今天是 Shao Peishen 顺口问了一句「机制会自动接过跑掉？」才被翻出来的。

🔴 **而这句话还有下半截，是本包第一版没看穿的**：既然落后是持续过程，那么**「检测＋提醒＋人工对齐」也治不了它**——它只是把触发人从「自己想起来」换成「被机器提醒」，**对齐本身仍是一次性动作**，`#68` 的历史会原样重演，只是重演时旁边会有一条告警在响。

> **一次性动作治不了持续过程，无论触发人是谁。**

⇒ 本包的解法是**分两级持续同步**：**ff 每轮做**（低风险，sweep 每小时本来就在对齐 master，顺带把执行体一并 `--ff-only` 是同类操作），**重启按需**（高风险，只在真动了服务代码路径时才需要，且缺省走人工确认）。

### 🔴 本次取证推翻了 #338 里「零信号」那句的字面表述，并因此改变了本包的形状

**sweep 里其实已经有一个常驻服务提示**（`_announce_resident_service_deployment_hint`，队列 #198(c)／§四 #87⑶⑷），它的正文甚至点名了正确的载体：「同步 `ops/wecom-service-home` 后重启 `ZhuopinAibotDevListener` 才在生产生效」。所以「零信号」不准确。**但实测把它为什么不管用量了出来**：

```
$ git rev-list --count 33c5d18..master                                    → 305
$ git rev-list --count 33c5d18..master -- 5-平台底座/wecom-aibot-service \
                                          5-平台底座/zhuopin_platform     →   6
```

**305 个提交里只有 6 个触碰常驻服务运行体**⇒ 那条提示在四天里最多响过 6 次，**另外 299 个提交零信号**。而那 299 个里有 **161 个触碰队列文件**——正是这三个任务每天读的东西。

**⇒ 两条结论，直接决定本包做什么：**

- **⑴ 事件型提示无法承担常驻状态的职责。** 它每次只说「这一批需要同步」，说完就随日志滚走；**六句各自都对的「你该同步了」，加起来也不会变成一句「你现在欠了 305」**。⚠️ 但这条结论只走到一半——**「换成常驻状态型告警」仍然只是把提醒做得更好，而提醒治不了持续过程**（见上）。改版后的答案是：**每轮自己把它 ff 掉，只在真需要重启时才叫人。**
- **⑵ 判据的覆盖面错了。** 既有提示按「本批是否触碰服务目录」判，而执行体是**整个仓库的一份 checkout**，它落后与否跟本批碰了哪个目录无关。本包的判据改为**直接量这份 checkout 落后多少**，与批次内容无关。

这也是本项目反复记的那一族问题的又一个实例：**错误不产生任何信号**（同「工具静默回退」「判据恒真、零信息量」）。区别只在于，这次不是没有信号，而是**信号的类型与问题的类型不匹配**。

### 本次退休哪一个既有守卫（协议〇.9 措施 B，机制类变更包强制）

**退休对象：根 `CLAUDE.md` §5 文档治理 R5 中「顶部进度段只留最近一批／季度迁档」这条约束的「尺寸」那半条人守。**

该半条此后由 sweep 第 4 类常驻告警承接（本包新增），R5 正文相应**降为一行指针**，人守条目净减一。沿用 #206 已确立的范式（机制化后正文保留指针属防御性冗余、非机制必需）。这一项是队列 §一 #338 预授权⑤明写的既定方案，不是本包自选。

⚠️ **退休的边界必须写明，不得扩大**：退休的只有**尺寸**半条。R5 里的「条目数上限」「单条长度上限」早已由 `工具-CLAUDE进度段lint.py` 的 J2/J3/J5 在 CI 里守着（`--enforce`），**那部分不是本包退的**；R5 里「接力件定长交接卡」「季度迁档的执行动作」等仍是人守，本包不碰。

### 不退休的一项，写明为何不能退

**既有的 `_announce_resident_service_deployment_hint`（事件型部署提示）不退休。**

理由不是「留着也没坏处」，而是**它和本包新增的第 5 类告警判的是两件不同的事，互相取代任何一个方向都会漏**：

| | 既有事件型提示 | 本包新增常驻状态告警 |
|---|---|---|
| 问的问题 | **这一批**改动需不需要部署才生效 | **此刻**执行体欠了多少没对齐 |
| 触发时机 | commit 落库那一刻 | 每轮 sweep，与批次内容无关 |
| 能回答 | 「刚才这个改动为什么线上没生效」 | 「我现在离对齐还有多远」 |
| 漏什么 | 不碰服务目录的 299 个提交 | 「本批具体哪几个文件需要重跑注册脚本」这类逐条处置 |

**用新的取代旧的**⇒ 丢掉「本批命中了哪个文件、该同步还是该重跑注册脚本」这层逐条处置（`RESIDENT_SERVICE_REMEDY_BY_SOURCE` 四种处置措辞各不相同，#199 的教训就挂在「任务注册脚本」那一条上）。**用旧的取代新的**⇒ 就是现状，已实测失败。

### 伴生文件的 .gitignore 覆盖

本变更**新增两种此前不存在的自动生成文件形态**（两个常驻告警的状态文件，形状与既有 `sweep-*-state.json` 同族）。实测覆盖情况：

```
$ git check-ignore -v reports/sweep-claude-md-size-state.json reports/sweep-carrier-lag-state.json
.gitignore:28:**/reports/	reports/sweep-claude-md-size-state.json
.gitignore:28:**/reports/	reports/sweep-carrier-lag-state.json
$ echo $?
0
```

两者均被 `.gitignore:28` 的 `**/reports/` 覆盖，**退出码 0（实跑结果，非推断）**。

新增的 `工具-执行体对齐重启.ps1` 不自动生成任何文件：备份落到仓库外的用户指定目录（`--BackupDir`，默认 `%TEMP%` 下带时间戳的目录），**刻意不落在仓库内**——避免重演 #328②「新造的文件形态没人回头看忽略规则、被 sweep 判为孤儿脏文件连响 17 小时」。

## What Changes

**子项 A —— `CLAUDE.md` 尺寸/批次跨度守卫（sweep 第 4 类常驻告警）**

- 新增判据：根 `CLAUDE.md` **> 90 KB**，或顶部进度段**跨 > 1 个批次日期**；`4-数字员工/**/CLAUDE.md` 与 `5-平台底座/*/CLAUDE.md` **> 50 KB**。
- 走 `_track_and_alert_standing_state` 既有骨架与既有出口，**不新增通道**（预授权②）。
- **首月只告警、不调参**（守 #257 先攒样本纪律）。
- 解析**复用 `工具-CLAUDE进度段lint.py`**，不另写一套顶部段解析。

**子项 B —— 常驻执行体持续同步**（🔴 2026-08-23 由 Shao Peishen 改版：不是「守卫＋提醒」，是**持续同步**）

- `工具-孤儿worktree扫描.py` **新增一列**「落后 master N 提交」（**纯增列**，不改任何删除判定、不新增桶、不新增删除能力）。
- sweep **每轮自动 `--ff-only` 对齐**常驻执行体。执行体名单**从 Windows 计划任务反查**（Action 路径落在 `.claude/worktrees/` 下者即执行体）。三道停手闸：`ahead > 0`／已跟踪文件脏／ff 自身失败——**绝不强推**。
- **重启按需**：只在本轮 ff 真的动了常驻服务代码路径时才需要，判据**复用 `#87` ⑶⑷ 的既有白名单**（`_touches_resident_service`），不另写一套。由 `CARRIER_AUTO_RESTART_ENABLED` 控制，**缺省 OFF**（首月只 ff、重启走人工确认）。
- 新增 `工具-执行体对齐重启.ps1`：停服→重启→验活的**唯一实现**，人工与 sweep 走同一份（`-RestartOnly` 模式）。把 `§四 #68` 实测的三个坑内建成流程。
- **第 5 类常驻告警的语义是「有例外」，不是「落后了」**：正常对齐路径零推送。

**⑤ R5 尺寸半条降指针**（根 `CLAUDE.md` §5，与 apply 同批）。

### 分期：首月只告警、不调参（理由须原样保留）

本包上线当天**预计零告警**——实测根 `CLAUDE.md` 56,002 B、场景最大 40,867 B（FI2），全部低于阈值；顶部段只有一个批次日期 `2026-08-19`。

🔴 **「零告警」正是这类守卫最危险的状态**——`OP-0819-F` 那条教训的原话是「一个告警机制建成 9 天、每天在跑，却从来没有真正发出过一条消息」。故本包强制：**即使不告警，每轮也必须在 sweep 日志回显「当前值 / 阈值 / 还差多少」**。这不是调试信息，是**这个守卫每天证明自己读到了正确对象**的唯一手段。阈值本身首月不动（预授权①）。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

**⑴ 本流程哪些判断是人脑默会经验？**

- **「载体多大算超限」**：90 KB / 50 KB 两个阈值来自 2026-08-16 那次审核的经验判断，**没有实测依据说明为什么是 90 而不是 80**。
- ~~**「落后多少算该管」**~~ —— 🔴 **这条默会经验被改版直接取消了，不是被显性化**：自动 ff 之后落后恒为 0，不再需要一个警戒线。**凡是发现自己在为一个阈值找理由时，先问一句：这个量能不能干脆不让它涨起来。**
- **「对齐之后怎么确认真的生效了」**：三条判据（先杀父后杀子并复查零残留 / 比对进程链 `CreationTime` / 验心跳时间戳真刷新）是 2026-08-19 一次实操里踩出来的，**目前只活在队列 `§四 #68` 的一段叙述里**——换个人做，得先读到那段话才知道。
- **例外/尺度**：哪些 worktree 属「常驻执行体」（要管）、哪些属「开发中的临时台面」（不管）——本包改为**从计划任务反查**，这一条默会经验已被结构性判据取代。
- **「重启放开的时机」**：自动重启开关何时可从 OFF 打到 ON，目前只有「首月攒样本」这一条，**攒到什么样算够，尚无判据**。

**⑵ 由谁显性化？**

- 持有人：**Shao Peishen**（阈值与警戒线的拍板人；三坑的原始实操记录人）。
- backup：**陈承（IT，男）**——`.51` 与本机计划任务侧的第二双眼睛。
- ⚠️ 本包只完成「把三坑从叙述变成可执行脚本」这一半；**两个阈值仍是待验证的经验值**，首月攒样本后再由持有人复核。

**⑶ 用什么方法提取？**

**历史案例反推**为主：`§四 #68`（2026-08-19 实操全记录）＋ 2026-08-16 memory 审核报告 §二 F3/F4/F5 ＋ 本次 2026-08-23 实测取证。三份都是**已经发生过的真实事件**，不是设想。首月样本积累后转为 **L2 改判判例累积**（每次告警是真问题还是噪音，逐条记回队列行）。

## 验收与晋档条件（强制，四档口径）

**本变更包交付后所处档位：档 3（内部服务）。**

- 判据：两类告警挂在**已在生产运行**的 sweep（`ZhuopinCommitSweep` 计划任务）上，走既有企微出口推到**采购内部工作群**（内部收件人，非对客）；对齐脚本为内部运维工具。不涉任何对客外发 ⇒ 不触档 4。

**晋下一档（档 4 对客交付）的条件：** **不适用，本包永不晋档 4。** 它是内部机制守卫，不产生任何对客交付物。写在这里是为了让「未晋档」不被误读成「欠着一步没做」。

**晋「阈值可信」的条件（本包真正的下一步，逐条）：**

1. 首月（上线日 → 2026-09-23）积累告警样本，**每条告警逐条判真/噪音并记回队列 §一 #338**；
2. 样本 ≥ 5 条后，由 Shao Peishen 复核两个尺寸阈值，并决定自动重启开关是否可打到 ON；
3. 复核结论落回本包 spec，**不得由实现方自行调参**（预授权①明写「首月只告警、不调参」）。

**价值指标：**

- **风险型（主）**：执行体**处于落后状态的时长**。基线 ＝ **持续存在**（2026-08-19 对齐 → 08-23 落后 305，且此前每一轮都是如此）。目标 ＝ **≤ 1 小时**（sweep 每轮自动 ff）。⚠️ 改版把这个指标从「多久被发现」改成了「多久处于落后」——**前者衡量的是提醒的灵敏度，后者才是这件事真正的危害**。
- **风险型（辅）**：根 `CLAUDE.md` 从瘦身后到超阈值被发现的时长。基线 ＝ **7 天且靠人工审核偶然发现**（2026-08-16 实测）。
- **工时型**：一次执行体对齐的实操耗时。基线 ＝ 2026-08-19 那次**约半个工作日**（含踩三个坑、手工核进程链与心跳）。目标 ＝ 脚本化后 ≤ 15 分钟。
- ⚠️ **基线由本包作者取自实测记录，须由业务 Champion（Shao Peishen）确认**——尤其「半个工作日」是从 `§四 #68` 的叙述反推的，不是计时得来的。
