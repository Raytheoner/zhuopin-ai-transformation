# plan-backpressure-scanner Proposal

> 来源：队列 §一 `#462`（2026-09-02 立，Shao Peishen 当日答 (a)）｜核心逻辑取证件＝`1-转型规划/0-全景路线图/取证件-2026-09-02-规划与执行覆盖差集.md` §三｜**机制/环境类变更包**
> 本次范围＝**propose ＋ design 起草**，不建脚本、不改 `工具-落库sweep.py`（`#462` 行内明定）。
> 🔴 **本件的实测数全部取自 2026-09-07 propose 期复跑**，不是搬取证件 2026-09-02 的旧数——两者差异很大，且差异本身是本包最重要的输入（见「Why」②）。

## Why（为什么做）

**一句话**：规划里有 35 个场景，队列只装「已经有人立过行」的任务——**规划里有、但没人立行的场景，对所有现役机制（可 Open 池／拆件巡逻／值周巡检／泳道看护）完全不可见，且不产生任何信号**。本包补上「规划 → 队列」这一棒，并把它做成常驻的，不是一次性的。

### ① 根因（取证件 §二，2026-09-02 已定，本节不重复论证）

现有全部机制只扫队列 §一。**「看不见」正是这个问题的症状**——它不会报错、不会超时、不会有人抱怨，只会在某个场景的排期月到了以后才被人发现从来没人接。这是本项目那个老病（**只落文档、无承接载体、于是消亡**）的第三个也是最大的一个实例；前两个（`决策点:` frontmatter 覆盖率 70%→0%、口径点无台账）已分别由 `#447`／`#439` 治理。

### ② 五天内 14 → 2，而这个数字下降**不是**好消息（2026-09-07 复跑实测）

取证件 2026-09-02 判「三处皆无」14 个。本次用**同一份代码、同一套别名**复跑：

| | 2026-09-02 | 2026-09-07 | 差异来源 |
|---|:---:|:---:|---|
| 🔴 三处皆无 | 14 | **2**（R2／S4） | `#463` 手工立行 ＋ 8 个新场景 openspec 包（`sc4`/`sc10`/`sc11`/`fi5`/`fi6`/`fi8`/`fi9`/`fi10`）落地 |
| 🟡 队列提及、无工程无包 | 11 | **15** | 判据太松，灰区反而变大 |
| 🔵 *参照：修好判据后的同日实测* | — | **13** | 见下 ⑸——**"2" 这个数本身就是缺陷的产物** |

🔴 **但复跑同时坐实：今天这 2 个里没有一个是"真信号"，而消失的那 12 个里有一半也不是"真解决"。** 逐条如下（每条都是本次实测、可复现）：

**⑴ 自我否定的假阴性——宣布问题存在的那一行，被判据当成了问题已解决的证据。**
销售域 `S1`／`S2`／`S3`／`S5`／`S6` 五个场景，在 §一 151 个数据行里**只被一行命中，就是 `#463` 本身**——而 `#463` 的任务列写的正是「规划里有、执行侧完全没有的 14 个场景：立行与排期」。判据看到"队列里提到了 S1"，于是判它已承接；实际那句话的意思是"S1 没人接"。**同域的 `S4 技术文档` 之所以今天仍报 🔴，唯一原因是它在 `#463` 里的写法是「S4 技术文档」而别名表写的是「技术文档生成」——一个字面差异，决定了同一批同一状态的六个场景里五个静默、一个报警。**

**⑵ 命名空间正面对撞——本项目有两套独立的 `R1`-`R5` 编号，字面完全相同。**
工程研发域场景是 `R1` 需求分析／`R2` AUTOSAR／`R3` 代码审查／`R4` 测试用例／`R5` 技术文档生成；需求侧改进项**也**是 R1-R5（`#439`「**R1 · 口径点台账**」、`#440`「**R4 · 纪律 eval 套件**」、R3 ＝ `followup_readme_bridge`）。判据据此把 `R1`／`R4` 判为「已承接」。`R5` 更乱，命中的 7 行里有跟进信稿次（「补件…**R5** 分母请签认」）、FI2 对账规则（「**R5** 门禁在真实数据上几乎从不触发」）、memory 审核报告条目（「场景级 **R5**」）——**没有一条是工程研发域 R5 场景。**

**⑶ 右边界缺失——取证件代码注释里那句自我保证不成立。**
取证件 §三 的 `hit()` 注释写「前置断言避免 O1 命中 O10、S1 命中 SC1 一类误匹配」。实测：`(?<![A-Za-z0-9])` **只守左边界**，右边界没有任何断言 ⇒

```
'O1'  in 'O10 设备'                  -> True   ← 注释声称避免了，实际没有
'FI1' in 'FI10-存货跌价智能分析'      -> True
'SC1' in 'SC10-BOM评审与物料库管控'   -> True
'S1'  in 'SC1 供应商风险'            -> False  ← 注释里唯一说对的那半
```

今天没出事，只因为 `FI1`／`SC1`／`O1` 各自也有自己的工程目录、结果碰巧一致。**`FI1` 现状是「条件复启暂缓」——它的目录一旦按暂缓清理，判据会立刻静默地继续报"已承接"（因为 `FI10` 还在）。** 🔑 **一个"注释声称有守卫、实际没有"的判据，比一个明说没守卫的判据更危险**——它让下一个读代码的人不再去查。

**⑷ 宽紧两档都不对。** 全行 grep 太松（灰区 15 个）；`#463` 建议的收紧口径「首列编号所在行的**任务列**是否点名该场景」也不够——它照样把 `#439`「R1 · 口径点台账」判成 R1 场景的承接行（因为"R1"确实在任务列里）。**⇒ 收紧不是换一列扫，是要给场景码一个不与别的编号体系重名的判据。**

**⑸ 修好之后的真实数字是 13，不是 2。** 按 design D2 定的口径（任务列 ＋ **标的段** ＋ 双侧边界）在同一份真实数据上重跑：**「三处皆无」＝ 13 个**（O3／O4／Q4／FI4／FI7／R2／R3／R4／S2／S3／S4／S5／S6），逐条人工核对**全部为真**；剩余灰区收敛到 4 个，且其中 3 个恰好就是 ⑵ 那族命名空间对撞（R1←`#202`／R5←`#337`,`#391`／S1←`#259`）。**⇒ 现役判据把 13 个真实的不可见场景报成了 2 个，漏报率 85%。** 这个数字才是本包要修的东西的大小。

### ③ 为什么必须是常驻机制，而不是"再跑一次那个脚本"

`#463` 那次是**人工的、一次性的**：一个人读取证件、判 14 个、手工立 8 行、销售 6 个按他明令不立。这次做对了，但它不产生任何"下次也会做"的保证。全景规划的排期表还会改（v6／v7／v8 三次结构级重排都在最近三个月内），每改一次就重新产生一批"规划里有、队列里没有"的场景，**而没有任何机制会在改完的那一刻告诉任何人**。

### ④ 退休哪一个既有守卫（协议〇.9 措施 B，机制类强制回答）

**能退，且必须退：取证件 `取证件-2026-09-02-规划与执行覆盖差集.md` §三 那段内嵌的一次性扫描脚本，其"可执行判据"身份随本包上线终止。**

- 判据不能有两份。本包上线后若取证件 §三 的代码块仍原样躺着，任何人复制粘贴跑出来的都是**带上述四个缺陷的旧结果**，且它写在一份标题为「取证已完成」的权威件里，读者没有理由怀疑它。
- 退休动作（写进 tasks，可检验）：取证件 §三 代码块替换为一行指向本包实现的指针，frontmatter `status` 由 `取证已完成，待落成常驻扫描器` 改为 `已落成常驻扫描器（<包名>），本件转历史件`；**正文其余部分一字不改**（原文原样，守「历史记录不追改」）。
- ⚠️ **除此之外本包不退休任何守卫，理由如实登记**：本包填的是一个**从来没有守卫的空位**（取证件 §二 的原话是"现有全部机制只扫队列 §一"），没有前任可退。这不是"以无搪塞"——上面那条取证件脚本就是本包必须退掉的那一个，只是它的形态是"文档里的可执行代码块"而非"守卫模块"。

### ⑤ 伴生文件的 `.gitignore` 覆盖（协议〇 强制项，实测非推断）

本包**会**新增一种此前不存在的自动生成文件形态：陈化抑制／指纹状态文件（同 `open_pool_reminder` 的 `#312` 指纹状态文件与 sweep 各类 `reports/sweep-*-state.json` 同族）。实测：

```
$ git check-ignore -v reports/sweep-plan-backpressure-state.json
.gitignore:41:**/reports/	reports/sweep-plan-backpressure-state.json     (exit 0)
$ git check-ignore -v reports/sweep-fork-state.json          # 对照组，同族既有文件
.gitignore:41:**/reports/	reports/sweep-fork-state.json                  (exit 0)
```

⇒ **已被 `.gitignore:41 `**/reports/`` 覆盖，无需新增规则**，前提是状态文件必须落在 `reports/` 下（写进 design D6 与 spec，不是口头约定）。**扫描器产出的"未承接清单"报告件同理落 `reports/`（不入库）；唯一入库的产出是队列行本身。**

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

🔴 **本包属机制/环境类，非业务场景**——但三问照答，且本包确有一处真实的默会判断（同 `#454` 已开的先例：机制类条目可以进 §一.2 知识资产台账）。

1. **本流程哪些判断是人脑默会经验？**
   - **⒜「这个场景算不算已经有人接了」的尺度**（本包核心）。当前只在做过 `#463` 那次判定的人脑子里，且**已被证明容易错两次**：其一，`#463` 自己写下的收紧口径「任务列点名」，实测仍会把 `#439`「R1 · 口径点台账」判成 R1 场景的承接行；其二，**本包 design 起草期自己也错了一次**——初稿定的"元任务行阈值 3"判据经逐行核对不成立、已撤回并在 design D2 留痕（那条规则会误杀 FI3 与 SC4 的真承接行）。**⇒ 这条尺度连本包的起草方都两次没拿准，它必须成文、必须有反向对照组，不能留在任何人的脑子里。** 规则／阈值／例外三档目前一条都没有成文。
   - **⒝「前置依赖算不算已解除」的尺度**。判据源《跨场景前置数据与知识库任务总表》的「状态」列是自由文本 ＋ emoji，而 emoji **不表示 ready/not-ready**——图例写的是「🔴 关键前置（卡场景上线）｜🟡 已在某文档排期、需拉齐｜⚪ 后置场景、提前提醒」。**🔴 是"这条重要"，不是"这条没就绪"**，直接按 emoji 判会得到与语义相反的结果。且 35 个场景里只有约 13 个在该表有行，"无行"如何解释（＝无已知前置 ⇒ 可开）也是一条未成文的默会规则。
   - **⒞「哪些域现在根本不该被倒逼」**。他 2026-09-02 明令「研发和销售域场景依然暂缓等我通知再排序」（`#463` 行内），⇒ 今天扫出的 R2／S4 的正确处置是**登记不立行**。这条例外只在他和 `#463` 那行里，任何机器判据都推不出来。
2. **由谁显性化？**
   - ⒜⒞ **持有人＝Shao Peishen**（"什么算可开工"与"哪些域暂缓"的唯一权威）；**backup ＝孙涛**（缺席代理，范围见 `.claude/rules/场景建造与合规.md`）。
   - ⒝ **持有人＝Shao Peishen**；**backup ＝值周巡检当值 session**（该表的日常维护方）。
   - 三条均按 `#454` 既例登记进《跨场景前置数据与知识库任务总表》§一.2 知识资产台账（写进 tasks）。
3. **用什么方法提取？**
   - **历史案例反推（主）**：本 proposal「Why ②」的四个误判形态全部由**真实队列数据**反推得出（`#463`／`#439`／`#440`／`#391`／`#337` 五行原话，均可复现），不是假想题——这正是"AI 起草·专家批改"里的"起草"那一步，草案即 design.md D2/D3 的判据表。
   - **L2 改判判例累积（辅）**：扫描器上线后，每一次"它报了未承接、而人判定不该立行"都是一条负例（如今天的 R2／S4），进 `#462` 行内留痕；**满 5 条即回头收紧判据**（同 `#454` 的负例累积口径，不另造机制）。
   - **不设工作坊**——判例随每小时告警自然累积，满 5 条负例时才占用他一次时间。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：🔴 **本包是机制/环境类，四档口径（档1 mock／档2 真实数据／档3 内部服务／档4 对客交付）为业务场景而设，对本包不直接适用**。按既有机制类包惯例映射如下，如实标注、不套用不适用的档位：
  - **交付后位置 ＝「档2 等价」**：判据在**真实队列/仓库数据**上跑通（151 行 §一 数据行、35 个场景、`4-数字员工` 真实目录树、`openspec/changes` 含 archive 真实包名），非 mock。
  - **「档3 等价」＝ 接进 sweep 每小时常驻轮次并连续 7 天零误报**（误报定义见下）。**本包交付即到此为止的前一步；接入是 tasks 内的一项，连续 7 天的观察窗在 apply 之后。**
- **晋下一档的条件**（逐条，缺一不晋）：
  1. 四个已知误判形态（自指行／命名空间对撞／右边界／宽紧两档）各有一条**在真实数据上跑的**断言测试，且**每条都有反向对照组**（去掉守卫后测试必须失败——防"守卫本身没生效也能通过"，同 `coverage-point-ledger` D3/D5/D8 既有做法）。
  2. 全 35 个场景的判定结果与一次**人工逐个复核**逐格一致，差异逐条写明是判据错还是人错。
  3. 接进 sweep 第 13 类后**连续 7 天零误报**；误报 ＝「报了未承接、而实际三处之一有真实承接」。**"报了未承接、而人决定不立行"（如 R2／S4）不算误报，算负例**——两者必须分开计，混计会让判据被错误地收紧。
  4. 陈化抑制生效实测：同一批未承接场景不得在 24 小时内推送两次。
- **价值指标**（三类模板取 2）：
  - **风险型（主）**：**"规划已排期、但三处皆无"的场景数**，目标恒为 0；**基线 ＝ 2026-09-02 的 14**（有据可查、已被 `#463` 处置至今日的 2）。**基线由 Shao Peishen 确认**（本包上线前）。
  - **风险型（辅）· 发现时延**：从"全景规划权威排期表新增/改动一个场景"到"该场景被判定为未承接并推送"之间的小时数，目标 ≤ 一个 sweep 轮次（约 1 小时）。**基线 ＝ 当前无穷大**（无任何机制会发现），这条是本包价值的真正落点。
  - ❌ **不设工时型指标**：本包节省的不是工时，是"没人发现"这件事本身；硬凑工时基线会造出一个无法核算的数。
- **LLM 判据黄金集**：🔴 **不适用——本包全部判据为结构化字符串/表格匹配，零 LLM 运行时判断**（写死进 spec：判定路径 MUST NOT 调用模型推理，同 `queue-status-machine-field` 的 Non-Goals 既例）。

**红线核对**：

- **mock 先行**：🔴 **不适用且不应适用**——本包的判定对象就是本仓库自身的真实结构（队列/目录/包名），mock 一份假仓库只能测到解析器、测不到判据。**改为"只读先行"**：扫描器的第一个可运行版本 MUST 为纯只读（只出清单、不写队列行），写侧在 design D5 拍板后才实现。
- **audit 留痕**：本包不是业务 AI 决策，但"机器写队列行"这一动作 MUST 走 `audit`（append-only），与 `open_pool_reminder` 的推送动作同一套；只读扫描不强制。
- **OEM 隔离**：不适用——本包不接触任何 OEM 技术数据，判定输入全部是仓库内的编号、目录名与包名。
- **L2 门禁**：不适用——本包不产生任何采购/交付/对客动作。
- **ISO 26262 / ASIL**：不适用——本包不生成安全相关代码，不进安全证据链。
- 🔴 **本包自己的门禁（新，须 design 审确认）**：**"机器自动向 §一 追加业务场景行"是本项目此前从未有过的动作**，它同时触碰三条现行边界——⑴ 协议〇.10 的**并入审核**（取号前必须先判"能不能并进已有行"，这是一次人/LLM 判断，机器绕不过去）；⑵ **环境保障线边界**（`#463` 明写"产出业务场景行属项目构建、交业务总线派发，机制线只出取证与扫描器"）；⑶ **他的域级暂缓明令**（研发/销售域"根本不立"）。**⇒ 「产出队列行、不只报告」这条 `#462` 的硬要求，与上面三条的兼容方式必须由 design 审拍板，不在 propose 阶段自行决定。** 见 design.md D5。
