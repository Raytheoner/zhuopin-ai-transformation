# editlock-hold-scope-and-wip-block Proposal

## Why

本变更包同车处理 `工具-共享文档编辑锁.py` `release` 咽喉上的**两处已实测失效**——两者同文件、同函数（`_validate_release_structure`）、触碰区完全重叠，按协议〇.10「并入优先」合为一包，不拆两包各审一次 design。

### 缺陷一：校验⑥ 把「整个单元格」当成「当前结论」（队列 #324）

⑥（跟进信暂缓一致性，队列 #258）的判据是「状态列／事项列含暂缓关键词（`暂不发`／`暂缓`／`压着`／`不发`）**＋** 行内出现反引号包裹的 `.md` 文件名」。**问题在于队列单元格按「历史记录不追改」会长期沉积多轮登记**，而判据把整格一视同仁地当作"这一行此刻的结论"。

**2026-08-10 真实误报**（业务总线实测，队列 §四 #52）：「压着」二字来自 08-05／08-07 两段历史原文（当时说的是 07-29 判例包被压着），反引号文件名来自 08-10 新起草的 采购部#13（当日已获批准转 `🆕 待发`）——⑥ 把「历史里的暂缓」与「今天这封已批准待发的信」错误配对，拒绝放行。当次处置＝**去掉该行文件名的反引号绕开配对**，而这个绕法本身会削弱 ⑥ 未来的真实拦截力（一旦成为惯用手法，⑥ 想拦的 #150 真实误发场景也会一并拦不住）。

**本次取证把"结构性缺陷"量化了**（对现网两份队列文件全量只读跑，非推断）：

- §四 #52 那格**总长 4062 字符、按 `━━━` 切出 11 段，头段仅 447 字符**；四个暂缓关键词**全部出现在历史段，头段一个都没有**——即被扫描的文本面是语义相关文本面的 **9 倍**，且该倍数只随沉积单调上升。
- 把当时被去掉的反引号在内存里补回后复现：**现判据命中、头段判据不命中**，误报机理坐实。

**⑥ 自 #258 落地（2026-08-07）以来是否真拦下过一次真实的暂缓不一致？——查得的答案是「没有」**，且这不是查不到，是**曾被记错、当时就已更正**：队列 #285 行 2026-08-07 引用「#225 的列数校验、#258 的 release⑥ 两天内各拦下业务总线一次」作为"弱校验有效"的论据，**同一行同日的『顺带核实』段已把归属更正为「两次拦截均命中校验①（列数／裸竖线）」**。⇒ ⑥ 在岗 10 天，**真阳性 0 次、假阳性 1 次**。**故本包不只是"修"，同时按规则退休制评估了"退"**（结论见下方退休问答与 design 决策点 1）。

> ⚠️ **本段一处 propose 期断言已于 apply 期证伪，如实更正（2026-08-17）**：propose 时写的「⑥ **至今没有任何单测覆盖**（`test_工具-共享文档编辑锁.py` 全文 0 命中）」**不成立**。实测该文件内有一整个 `HoldConsistencyValidationTests` 类、**9 个用例**覆盖 ⑥（正向拒绝／README 已非待发放行／判不出放行／反向告警／仅关键词无文件名／仅文件名无关键词／§四 事项列／#150 真实事故重现等）。**误判成因**：propose 期的 grep 应是按函数名 `_row_hold_language_status` 之类的**实现符号**去搜，而这些用例全部走 `cmd_release` 端到端、正文里不出现该符号 ⇒ 0 命中被读成了"0 覆盖"。**这正是本包自己要治的那类错误的同形**——**判据的扫描面与要判的对象不一致**（⑥ 扫的是整格、要判的是当前结论；那次 grep 搜的是实现符号、要判的是行为覆盖）。⇒ 本包 apply 期的动作相应调整：不是"从零补齐"，而是**收窄相关的增量补测 ＋ 把两个反向告警用例改写为退休后的断言**（见 tasks 2.4）。

### 缺陷二：⑨ 机制类可动 WIP 的非阻断提示已被连续 6 次越过（§四 #58 第⑶条）

⑨ 在本次持锁期间新增 `[D:机]` 的 §一 行时重算 WIP，超上限则 `print` 提示、**不阻断**。2026-08-16 口径冻结观察期满复评（Shao Peishen 2026-08-17 答《本周计划-2026-08-17》B-1 选 (a)）实测：

- 可动 WIP 由 2026-08-10 的 **17／16** 升至 2026-08-17 的 **24／16**；
- 观察周内新立机制类行 **6 条**（#324／#326／#327／#328／#337／#338），**无一伴随关行**；
- 🔑 **已白盒核实（非推测）**：`工具-共享文档编辑锁.py` L1753 的提示**只在 `new_mechanism_row_added` 为真时触发**，即只在「正要新建机制行」那一刻响。**⇒ 不是提示没响——它这 6 次每次都响了、每次都被越过。一个非阻断提示在连续 6 次被无视后，信息量已经是零。**

⇒ 2026-08-10 那次留下的反向留痕（「(c) 的代价＝提示很快沦为背景噪音，等于措施 C 自动失效」）已如期兑现，故 `release` 由非阻断提示改为**阻断**，带 `--force` 逃生阀；🔴 **逃生阀的理由必须落进队列行、不能只落日志，否则等于没有约束**。

## What Changes

- **⑥ 扫描范围收窄到「当前结论段」**：暂缓关键词的扫描面由整个状态列／事项列，收窄为该单元格按 `━━━` 切出的**首段**；§四 的文件名提取同步收窄到该首段，§一 的文件名来源（`cells[3]` 输入指针／`cells[6]` 触碰区）不变（依据见 design 决策点 3 的实测）。判定命中后与 README 的交叉核对规则、拒绝/放行语义均不变。
- **⑥ 的「反向告警」半边退休**：README 已是"已推送"类终态而队列行仍称暂缓时打印告警的那个分支整体删除（一进一出，理由见下节）。
- **⑨ 由非阻断提示改为阻断**：新增 `[D:机]` 的 §一 行且重算后可动 WIP 超上限时，`release` MUST 拒绝（计入 `violations`），锁保持占用；新增 `--force-mechanism-wip` 逃生阀，且**该逃生阀只在本次新增的那条机制行的状态列内写明 `WIP豁免：<理由>` 时才生效**——理由因此天然落在队列行里、进 git、被 `工具-队列结构lint.py` 与值周巡检看得见，工具自身不新增任何写盘路径。
- **上限值不动**（16，`--mechanism-wip-cap` 仍可覆盖）：§四 #58 ⑴ 明确"第三次为迁就现状改口径即等于废掉措施 C"。
- **BREAKING**：是。`release` 在"新增机制行且已超限"这一输入下由**放行**变为**拒绝**——这正是本次要的改变；存量 24／16 的清理由 §四 #58 ⑵（A 节收口后复核、仍超限则强制关行至 16）承接，**不由本包代做**。

## 本次退休哪一个既有守卫（强制，协议〇.9 措施 B）

**退休：⑥ 的「反向告警」半边**——即 `_validate_followup_hold_consistency` 中 `elif status not in FOLLOWUP_NON_TERMINAL_STATUSES:` 那个 `print` 分支（对应 spec 中「README 已终态推送而队列行仍称暂缓，告警放行」这条 Requirement），本包整条删除、不降级保留。三条理由均有实测支撑：

1. **它设计上就会对自己承认合法的写法报警**。它今天在现网队列上唯一的命中是 §一 #150，而 #150 恰恰是 spec 自己的 Scenario 明文列为合法的那一种——"队列行的文本是在事故发生后新增、用于如实记录『本应暂缓但已被机制误发』这一经过"。**一条只会在合法写法上响的规则，产出的不是约束，是噪音。**
2. **它正是 §四 #58 刚判定"信息量为零"的那一类非阻断提示**。本包同批把 ⑨ 从这一类里拿掉；若一边承认这种形态无效、一边继续留着同形态的存量，退休制在同一个变更包里就自相矛盾了。
3. **风险不对称，不值得占一条守卫**。⑥ 正向拦的是"照发一封已决定暂缓的信"（对外、不可撤回、有 2026-08-06 01:30 UTC 真实事故）；反向管的是"队列文本滞后于 README"（纯内部、可事后改、无外部后果）。

**为何不整体退休 ⑥（只退反向半边）**：⑥ 正向拦的那个失效模式（#150）是**真实发生过且不可撤回**的对外事故，而本包的收窄已用现网全量数据验证不损失正向拦截力（design 决策点 1 的对照表）——**在"从未拦到"与"拦不到就会真出事"之间，退休制要求的是先修判据、再看它在修好之后是否仍然从不命中**，而不是把唯一一层针对不可逆对外动作的结构性校验直接拆掉。本包因此把 ⑥ 的**真阳性观察窗口重置**（见「验收与晋档条件」的晋档条件③）。

## 伴生文件的 .gitignore 覆盖（强制）

**不适用——本变更不新增任何自动生成的文件名形态**：⑥ 的收窄是纯判据改动、无产物；⑨ 的阻断只影响 `release` 的返回码与 stdout，逃生阀的理由写在**既有队列文件的既有单元格**内（复用 `串行豁免：` 已有的"标记写在行里"范式），**刻意不引入任何 CLI 参数携带的理由落盘、不写状态文件、不写日志文件**（这一点本身即是 design 决策点 5 的选择依据之一，见该决策点对 #322 `*.editlock.mutex.stale` 教训的引用）。已核实：本包不改动 `.gitignore`，`git status --porcelain` 在本包 apply 后不应出现任何新形态未跟踪文件。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？** 两处：① **「单元格里哪一段是这一行此刻的结论」**——本项目的书写惯例是"新结论写在头部、历史用 `━━━ 以下为…原文 ━━━` 往下压"，这条惯例此前完全在人脑里，没有任何工具认得它，⑥ 正是因此把历史当成了现状；本包把它显性化为一条机器判据（按 `━━━` 切段、取首段）。② **「WIP 超限时到底该不该让这条行立起来」**——此前靠人读一行提示自己拿捏，观察周实测 6/6 越过；本包把它显性化为"要么先关一条、要么在行内写明 `WIP豁免：<理由>`"，使判断本身留痕可审。
2. **由谁显性化？** 决策人 Shao Peishen（决策点拍板与 design 审）＋ CC 建造车间（判据实现、单测、现网全量历史兼容核对）；backup＝下一位领取 #324／§四 #58 的 session 可凭 design.md 与本包附的实测对照表独立复核，不需要重跑取证即可判断结论是否成立。
3. **用什么方法提取？** 历史真实案例反推 ＋ 现网全量实测对照：⑥ 用 2026-08-10 §四 #52 那次真实误报做复现（内存内补回反引号，不落盘），并对现网两份队列文件 **170 行 §一/§四 全量**跑新旧两套判据比对命中集；⑨ 用 2026-08-10→08-16 观察周的 6 条真实新立行与 17→24 的 WIP 实测轨迹。不涉及 LLM 判断。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：本变更为**跨项目治理机制**（编辑锁是全项目共用的队列写入咽喉），非独立业务场景，不适用四档"对客交付"口径；套用最接近的描述＝**档1 mock 验证**——design 审通过、代码与单测完成，且已用现网真实队列文件做过只读全量对照，但尚未经历一次**真实的** `release` 被 ⑨ 阻断、也尚未真实用过一次 `WIP豁免：` 逃生阀。
- **晋下一档（档2 真实数据跑通）的条件**，逐条：
  1. 真实发生一次「新增机制行 ＋ WIP 超限」的 `release`，确认被**真的拒绝**（不是单测里的构造），且提示文案足以让操作者知道下一步该做什么；
  2. 真实用一次 `WIP豁免：<理由>`，事后核实该理由**确实留在队列行里并进了 git**（`git log -p` 可查），而不是只出现在当次终端输出里；
  3. 🔴 **⑥ 的真阳性观察窗口重置**——本包交付后，⑥ 若再经过一个完整观察周（建议同样以值周巡检为节拍）仍是"真阳性 0 次"，则按规则退休制**重新评估整体退休**，且届时不得再以"它防的是不可逆对外动作"为由无限期续期；本条须在下一次 §四 #58 类复评时被显式回答，不得默认续期。
  4. 🔴 **观察窗口有效性判据（Shao Peishen 2026-08-17 审 design 时附加，design 原文没有，随 apply 一并落地，见队列 §一 #324 行 2026-08-17 段）**——**上条那个窗口，须至少覆盖 N＝3 段「README 确有 `🆕 待发` 数据行」的时期，其"真阳性 0 次"才算有效样本**；**若整个窗口内待发行恒为 0，该窗口判为无效——既不得据此判 ⑥ 无用、也不得判它有用**，须延长窗口或另设判据。
     - **为什么必须加这一条**：⑥ 的"真阳性 0 次"这个数字**被一个混淆变量污染了**——⑥ 只有在 README 存在 `🆕 待发` 行时才**可能**拒绝任何东西，而 2026-08-17 实测待发行 ＝ **0**。**一个守卫在其前置条件从未出现时没响过，不能证明它没用，只能证明它没被检验过。** 这与 #308 子项 F1、§一 #122 同形，是同一天内第三次遇到该形态。
     - **N＝3 的依据（实测，非拍脑袋）**：对 README 全部 78 个历史版本逐个还原表格、按「发送状态」列统计，2026-07-04→08-17 共 45 天内出现过 **7 段**「确有待发行」的时期（`2026-07-06→07-11`／`07-26→07-27`／`07-28`／`07-29→08-06`／`08-07`／`08-11`／`08-13`），**均值约 6.4 天一段**；其中 **3/7 段只持续单个快照日**。⇒ **N＝1 不够**——单段（很可能只有一天）落在窗口内几乎不构成检验；**N＝3 对应约 19 天、约 3 个值周巡检节拍**，与本项目既有"口径冻结观察期"的量级一致，且能让"3 段里一次都没轮到 ⑥"这句话真正带有信息量。复算方法：遍历 `git log -- <README>` 各版本，用 `_followup_readme_rows()` 切表取「发送状态」列计数（**不得整文件 grep**，见下）。
     - ⚠️ **本判据是必要条件、不是充分条件，如实写明**：⑥ 真正被检验还需**同时**发生"某个队列行点名了那封待发信、且该行在持锁窗口内被改动"这一合取。N＝3 只保证前一半条件出现过足够次数；**若 3 段窗口内确实一次真阳性也没有，正确表述是"⑥ 在 N＝3 段有效时期内未拦下任何东西"，而不是"⑥ 已被充分检验且无效"**。本包**刻意不为此加运行时埋点**（那会新增写盘路径，与决策点 5 拒绝 `--force` 自动写盘同一理由）。
- 🔴 **计数纪律（同批落地，两桌通用）**：**凡引用 README 状态计数，一律按表格块切分取「发送状态」列，不得整文件 `grep`。** 2026-08-17 实测同一份 README：直接 `grep "🆕 待发"` 得 **13**，但那 13 处**全部在讲解状态语义的正文里**，**表格数据行是 0**（数据行共 42 行，全处于终态）。**若拿 13 当依据，会推出「待发行不少、⑥ 却从没拦下过 ⇒ 它没用」这个完全反过来的结论——同一个数字两种读法、结论相反。** 本包所有 README 计数（含上条 N 的取证）均已按表格块口径取数，复算请用 `工具-共享文档编辑锁.py::_followup_readme_rows()`。
- **价值指标**（风险型）：① ⑥ 的误报——基线＝2026-08-10 一次（且该次的绕开手法削弱了守卫本身），目标＝对"关键词只出现在历史段"的形态零误报，本包用现网全量对照给出证据，对"暂缓结论只写在 `➕ 并入` 段而不在头段"这一形态**如实不覆盖**（design 决策点 2 的已知残余风险），不假装能覆盖。② ⑨ 的越过率——基线＝观察周 6/6 被越过，目标＝越过必须留下可审的书面理由（越过率本身不设目标，逃生阀存在的意义就是允许越过）。
- **LLM 判据黄金集**：不适用（纯字符串/结构化匹配，无 LLM 运行时判断）。
