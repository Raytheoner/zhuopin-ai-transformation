# opener-batch-archive-precheck Proposal（队列 #397，#395 已并入）

> 出件日期 2026-08-25（本机 `Get-Date` 当场取值）。**本包只到 propose＋design 待审为止，未 apply、未改任何 runner 源码。**
> 门槛判定：命中 §5 机制/工具类 openspec 门槛第 ③ 条「改变既有模块对外语义」——同一份计划、同一批参数，脚本此后会自行跳过某些 opener。故必须走 propose ＋ design 审，不得当纯 bugfix 直改。

## Why（为什么做）

**一件三天前就已完成的活，被脚本原样又派出去一次，烧掉一整个 session 才被人发现。**

2026-08-24 夜 opener 批处理（run `20260824-165657`，A1–A14）中，**A4「质量域场景清单重审」对应队列 §一 `#368`**。该行 2026-08-22 已整行销号、2026-08-24 值周清扫已迁入 `跨桌任务队列-归档-202608.md`。批处理器对此一无所知，照常派出；执行 session 直到读完全部输入、开始动手时才发现是重做。**连带发现** `派单件-*.md` frontmatter `status` 普遍失真（21 份中 9 份仍为 `待执行`，已坐实至少 2 份实际已执行完毕，其中一份「下一批还会再派一次」）。

🔑 **这一族缺陷的判别特征：错误不产生任何信号。** 脚本退出码 0、日志正常、`OPENER_DONE` 哨兵照常打出——从机器视角这是一次完美成功的执行。与本项目已登记的「工具静默回退」「判据恒真、零信息量」同族：**没有人会去追查一个看起来成功了的结果。** 现有双指标（退出码 ＋ 哨兵）只能回答「这个 session 跑完了吗」，**完全无法回答「这个 session 本来就不该被启动」**。

批处理器把「派出」的边际成本压到了近乎零，这正是它的价值；但同时也把**误派**的边际成本压到了零，而误派的代价（一整个 session ＋ 一次人工识别）一分没降。派出量越大，本缺陷造成的损失越线性增长。

## What Changes（改什么）

**新增能力**

1. **派出前队列态校验**——每个 opener 派出前，解析其标题中声明的 §一 队列行号，跨「两份在办队列 ＋ 全部归档件」解析后合并查询，判定该行是否已完成；已完成则**跳过并告警**，不启动 session。
2. **`SKIPPED` 成为第一等执行状态**——与 `OK`/`PARTIAL`/`NO-SENTINEL`/`FAIL` 并列，进汇总表与 `summary.txt`；跳过**不触发** fail-loud 中断（v1 不 `break`、v2 不停泳道）。
3. **`工具-队列查询.py` 新增归档检索能力**——`--include-archive` 与 `--format json` 两个**新增可选开关**；不传时默认行为与退出码逐字不变（见 design 决策点 5，避免本次自身成为一次"改变对外语义"）。
4. **v1/v2 共用一个挂点**——新增 `0-学习与工具/工具-opener派出前校验.ps1`，两个 runner 各 dot-source 一次；判据只有一份实现。

**移除能力**

5. **删除 v1 第 130 行的失败提示原文**（#395 并入项）——该提示给出的 `-Only A0,A1,...` 在 `-File` 调用方式下**必然跑不起来**（PowerShell 不拆逗号 ⇒ 整串绑成单元素 ⇒ 零命中 ⇒ `exit 12`），改为输出 `-Command` 形态的完整可粘贴命令。

## 本次退休哪一个既有守卫（强制，协议〇.9 措施 B / 队列 #308）

**如实回答：本包净增守卫 ＋1，未能一比一退休，理由如下；但确有两项实质删减。**

- **实质删减一（删的是一个会主动误导人的旧物）**：v1 第 130 行提示被**整段删除重写**。它不是"没用"，而是**把人导向一条死路**——照抄必得 `exit 12`，且错误文案（"`-Only` 过滤后为空"）信息量不足以让人想到根因。删除一个反向工作的守卫，价值高于删除一个闲置守卫。
- **实质删减二（消灭一条人守，而非新增人守）**：#396 的治标是"9 份派单件逐份人工核实"。本包落地后，**"派出前人工核一遍队列行状态"这件事此后不再需要由人承担**——它从未被写成明文规则，但事实上一直是靠人记得。本包把它移进机器咽喉，属"机制化优于人守"（协议〇 规则退休制路径 ①）。
- **为何不能一比一退休**：现存守卫中**没有任何一条在做本包要做的事**——全库无"派出前校验"这一环节，退无可退。硬凑一条无关守卫来抵扣，等于用一次真实的能力削减去换一个账面平衡，与措施 B 的立意（遏制只增不减）背道而驰。**代价如实登记：机制/工具类守卫代码净增一处挂点、一个 PS helper、一个 Python 可选开关。**

## 伴生文件的 .gitignore 覆盖（强制，队列 #328 子项②）

**本变更不新增任何此前不存在的文件名形态。** 校验结论只写入既有的 `reports/opener-batch/<时间戳>/` 目录（`summary.txt` 与既有 `<泳道>-<编号>.log`），不新建缓存、锁、快照、状态文件或备份副本。

**核实方式＝实际执行结果，非推断**：

```
$ git check-ignore -v reports/opener-batch/20260824-165657/A1.log
.gitignore:28:**/reports/    reports/opener-batch/20260824-165657/A1.log      (rc=0)
$ git check-ignore -v reports/opener-batch/20260824-165657/summary.txt
.gitignore:28:**/reports/    reports/opener-batch/20260824-165657/summary.txt (rc=0)
```

两者均由 `.gitignore:28` 的 `**/reports/` 命中，rc=0（确实被忽略）。⚠️ design 决策点 4 中若 Shao Peishen 选 (b)（落一份跨批次校验缓存），**该选项会凭空造出一种新文件名形态**，届时须回头补 `.gitignore` 并重跑 `git check-ignore` 取证——已在 design 该决策点内显式标注为选 (b) 的附带义务。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？**
   - **规则**：「一个 opener 标题里的 `——队列 #NNN` 就是它对应的队列行」——这条对应关系从未被写成机器可读契约，纯靠写计划的人与读计划的人心照不宣。
   - **阈值**：「派出前要不要回头看一眼这行是不是已经做完了」——无人定义何时该看、看哪里，事实上从来没人看。
   - **例外**：`§四 #N` 与 `§一 #N` 是**两套独立编号**（archive 中 `§四 #88` 与 `§一 #368` 同时存在且互不相干）；`协议〇.8` 这类非编号引用不指向任何行。这三类的区分只存在于长期参与者的直觉里。
   - **尺度**：一个 opener 引用多行（如本 A27 引用 `#397／#396`）时，"部分已完成"算不算已完成——从无定论。
   - **当前只在谁脑子里**：值周巡检与写波次计划的人（环境总线侧），无成文记载。
2. **由谁显性化？**——**持有人 ＝ Shao Peishen（环境总线口径拍板）**；**backup ＝ 陈承（IT，本机工具链侧）**。本包 design 决策点 1/2 即为显性化产物，待其签认后落为 spec。
3. **用什么方法提取？**——**历史案例反推**。样本已现成且为真实生产数据：`#368` 白跑（run `20260824-165657`）＋ `#396` 普查出的 9 份 `待执行` 派单件（其中 2 份已坐实失真）。本包 design 的全部判据均由这批真实样本反推得出，**未凭空设计任何一条**（这正是 #397 排在 #396 之后的排期依据）。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：**档 3（内部服务）**。本机制的"生产环境"就是本仓库的批处理运行本身；apply 后随下一次真实波次批处理即进入日常使用，无 mock 与真实数据之分。（本包属机制/工具类，四档口径按内部工具映射：档 1 ＝ 单测绿、档 2 ＝ 用历史真实计划文件回放、档 3 ＝ 真实波次在用、档 4 不适用——本机制不对客。）
- **晋下一档的条件**：
  1. 单测覆盖 design 决策点 1 全部四态（A 派出／B live-done 跳过／C 归档命中跳过／D 无法解析→告警但仍派出），含 `#368`（归档）、`#395`（live 且 done）、`#397`（live 且 open）三个**真实行号**的回放用例；
  2. 用 `本周计划-2026-08-24.md` 原文回放，**必须复现出 A4 被跳过**，其余 13 项一个不少地照常派出（防"判据过宽把活都跳掉"）；
  3. v1 与 v2 各跑一次 `-DryRun`，跳过标记与原因在两处输出一致；
  4. 无 `.51` 依赖、无真实库依赖 ⇒ **本包不含 LAN 留步项**。
- **价值指标（风险型 ＋ 工时型）**：
  - **风险型（主）**：误派 session 数 / 批次。基线 ＝ **1/14（run `20260824-165657` 实测，A4）**；目标 ＝ 0，且**每次跳过都必须留下一条可读告警**（不允许静默跳过——静默跳过会变成本缺陷的镜像形态）。
  - **工时型（次）**：单次误派的沉没成本 ＝ 1 个 CC session ＋ 一次人工识别。基线由 run `20260824-165657` 的 A4 日志时长实测取值，**apply 时从日志读出真值填入，不在此处估算**。
  - 基线确认人 ＝ Shao Peishen（本机制无业务 Champion，环境总线自持）。
- **LLM 判据黄金集**：**不适用**。本包全部判据为结构化字符串与表格单元格匹配，零 LLM 运行时判断（见 design 决策点 1 末「不引入 LLM」）。

- **audit 留痕** ✅ 每次跳过写入 `summary.txt` 与批次日志，含行号、命中载体、判定理由；**跳过必留痕**是硬要求。
- **OEM 隔离** ✅ 不涉及任何 OEM 技术数据。

- **ISO 26262** ✅ 不涉及安全相关代码。
- **IATF 可追溯** ✅ 本变更**增强**可追溯性：此前"某 opener 为何被派出"无任何记录，此后每次派出/跳过均有判定依据落盘。

**风险与反向风险（design 决策点 1 详述）**

- 🔴 **主风险 ＝ 误跳过**（判据过宽 ⇒ 该做的活被静默跳掉）。这比误派更危险：**误派会被人发现（有人在读那个 session），误跳过不会有任何人在场**。故本包一切模糊地带**一律 fail-open（照常派出 ＋ 告警）**，绝不 fail-closed。
- **次风险 ＝ 告警疲劳**：无法解析行号的 opener 会告警但仍派出；若计划文件普遍不写行号，将产生大量噪音。design 决策点 2 给出计数与收敛口径。
