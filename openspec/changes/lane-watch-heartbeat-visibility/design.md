## 〇、先钉死三条自我约束（否则本件会修错地方）

1. 🔴 **读侧的 `REPO_ROOT` 今天是对的，不要"顺手修"它。** 实测：在 linked worktree 内按文件路径加载 `工具-共享文档编辑锁.py`，`REPO_ROOT` 解出 `C:\Dev\zhuopin-ai`（主 checkout），完全符合其 docstring 承诺。`#504` 行内提醒的「防 `REPO_ROOT` 解析偏移（同 `#488` 形态）」在本包的正确落法是**写侧复用同一个常量并加一条断言两侧同锚的单测**，**不是**去改那个函数。改它会同时打断编辑锁——那是本仓库最不能碰的一处共享设施。
2. 🔴 **本包不新增任何"告警/检查器"。** `#504` 行内原文：「看门狗本身就是守，问题是它读的位置和写的位置不是同一个 —— 修的是口径不统一，不是再加一层告警。」实现期若冒出「顺手加一个心跳格式校验」这类好意，**当场退回**。
3. 🔴 **两半必须同批修。** 读写同锚（半 ⑴）与已 DONE 豁免（半 ⑵）是同一个误判的两个来源；只修一半的结果是误报率从 100% 降到某个非零值，而**非零的误报率仍然会训练出「🐕 出现就当误报」这个习惯**——那正是本包要保的东西。

## 一、决策点

### 决策点 1 · 读写怎么同锚：加写侧工具入口，还是让泳道自己写绝对路径？

- **(a) 新增 `heartbeat` 写侧子命令，路径由工具按 `REPO_ROOT` 解析〔推荐 · 默认〕**
  泳道不再自己拼路径，改跑 `python 0-学习与工具/工具-泳道看护状态机.py heartbeat --lane <泳道> --text "<一句话>"`（收工加 `--done`）。函数内 `path = REPO_ROOT / "reports" / "lane-heartbeat" / f"{lane}.md"`，**与读侧同一个 `REPO_ROOT` 常量、同一处表达式**；目录不存在时自建；追加写、自动带本机时刻前缀。
  **收益**：读写共用一个锚的**同一处表达式** ⇒ 漂移的物理可能性被消除，不是"两边都记得改"。路径从此是工具实现细节，**不再是每份 opener／看护件／SKILL 都要复述一遍的口径**（退休 proposal 里那条手抄形态的人守）。手法与本工具既有的 `criteria`（D1 判据现取而非手抄）完全同源，该手法在本仓库已运行且被 SKILL.md 顶部明文钉为单一可信源。
  **代价**：① 每写一行心跳多一次 Python 启动（约 0.3 s）——对 30 分钟粒度的看门狗可忽略；② 工具坏了心跳就写不出——但读侧本来就依赖同一个模块，模块坏了看门狗一样失效，**不新增单点**；③ 已派发但未跑完的 opener 正文仍写着旧约定 ⇒ 须有向后兼容，见决策点 2。
- **(b) 保留散文约定，改成让泳道写绝对路径 `C:\Dev\zhuopin-ai\reports\lane-heartbeat\<泳道>.md`**
  **代价**：那个绝对路径要么写死在每一份 opener 里（＝`#345` 35 份路径引导手抄的同族，本项目已栽过），要么由泳道自己算（＝把锚的解析交给被锚的人）。且 `#504` 行内那句「心跳统一写主 checkout 的**绝对路径**」描述的是**目标**，(a) 正是达成该目标而不落入手抄的做法——**绝对路径由工具算出来，不由人抄下来**。
- **(c) 读侧改为扫描全部 worktree，取该泳道最新的一份心跳**
  **代价**：把一个锚变成一次搜索。**实测直接否掉**：`491-general-collections-readonly.md` 同时存在于三个不同 worktree，「最新那份」在多次重试／同名泳道并存时**不等于**「当前这条泳道那份」；且陈旧副本会被当成新鲜心跳读出来——**那比误报更危险，误报只是吵，读错副本是把真失联判成健康**。另：本机 worktree 目录当前 **82 个**，每次看门狗轮询都要遍历一遍。
- **(d) 把 `reports/lane-heartbeat/` 从 `.gitignore` 放出来，让心跳随 git 流转**
  **代价**：心跳一入库，泳道每写一行就脏一次索引 ⇒ 与「看护者自己不 commit」「撞 `.git/index.lock` 不重试」（队列 `#487`／P4）正面冲突，且心跳会污染每一个批次的 commit。**心跳是运行期信号，不是版本化产物**——这条边界不动。

**推荐 (a)。默认项 ＝ (a)。**

### 决策点 2 · 向后兼容：已按旧约定直接写文件的泳道怎么办？

本批九条泳道正在旧行为下运行，且看护件模板／opener 模板库里的旧措辞不会瞬间全部更新。

- **(a) 读侧不变、双源认账：`--heartbeat-file` 仍受支持且仍锚 `REPO_ROOT`；写侧新增命令成为推荐路径〔推荐 · 默认〕**
  即：`check_heartbeat` 一行不改其路径解析（本来就对），新命令只是让写侧落到同一个地方。旧泳道若仍在自己 worktree 里写文件，行为与今天完全一致（该误报还是误报）——**但这不是"兼容"，是"未迁移"**，须靠 SKILL/opener 模板同批改口（`tasks.md` §4）＋ 下一批次全面切换来收敛。
  **收益**：读侧零改动 ⇒ 既有 5 例单测零漂移；迁移是文本层的事，不是代码层的兼容分支。
  **代价**：迁移期内新旧混跑，误报不会在 apply 当天归零——**如实写在验收条件里**（proposal 晋档条件 1 要求的是「下一个看护批」而非「apply 当天」）。
- **(b) 读侧加一条兜底：主 checkout 没有该文件时，去调用方 CWD 再找一次**
  **代价**：这就是「两侧各试一遍」——`工具-共享文档编辑锁.py` 第 1612 行的注释已经把这条路明文禁掉过（🔴 不得改成「CWD 与 `REPO_ROOT` 两侧各试一遍」）。同一个坑不踩第二次。
- **(c) 加一个一次性迁移脚本，把各 worktree 现存心跳复制进主 checkout**
  **代价**：为一次性的迁移期造一个永久存在的工具；且复制之后主 checkout 里同时存在真心跳与复制品，mtime 语义被破坏（复制时刻 ≠ 心跳时刻）——**看门狗读的正是 mtime**。

**推荐 (a)。默认项 ＝ (a)。**

### 决策点 3 · 「已 DONE」怎么判——终态的判定来源与优先级

这是本包唯一一处需要**新造判据**的地方，也是最容易造出第二份可信源的地方。

- **(a) 双源 ＋ 明确优先级：状态文件 `status == "done"` 为权威；仅当状态非 `done` 时，才回落读心跳文件末行哨兵〔推荐 · 默认〕**
  ⑴ **权威源**：`heartbeat --done` 把泳道状态置 `done`（新增终态），`check_heartbeat` 见 `done` 直接返回 `stale=False, skipped_reason="lane_done"`；
  ⑵ **回落源**：状态非 `done` 时，读心跳文件**最后一个非空行**，命中既有约定的收工哨兵（`DONE ｜` / `STOPPED ｜`，见决策点 4）即同样豁免，并**不**改写状态文件（只读推断，不冒充权威）。
  **收益**：⑴ 覆盖新口径下的泳道，⑵ 覆盖**所有按旧散文约定写了 `DONE ｜ 产出落点` 的存量泳道**——这正是决策点 2 迁移期里唯一能立刻见效的一半。哨兵格式不是本包新造的，是 SKILL.md 步骤 4 已运行的既有约定（「收工写 `DONE ｜ 产出落点`」），**本包只是第一次让机器去读它**。
  **代价**：一个事实两个来源 ⇒ 有漂移风险。**缓解＝优先级写死且两者都是只读派生**：状态文件由 `--done` 唯一写入；哨兵只被读、不被任何代码写。**没有"两处都能改"的载体，就没有漂移的对象。**
- **(b) 只认状态文件 `done`**
  **代价**：apply 当天起，**所有存量 opener 正文里的「收工写 `DONE ｜ ...`」全部不算数**——那些泳道不会去调新命令。修好的分支在真实批次里长期够不着，等于把半 ⑵ 推迟到"所有模板都换完"那一天。
- **(c) 只认心跳末行哨兵**
  **代价**：依赖泳道确实写了那一行。一条真挂掉的泳道**恰好**在最后一次心跳里写了 `DONE`（例如写完 DONE 再去跑收尾却卡死），会被永久豁免——**把真失联判成健康**。故哨兵**只能作回落**，不能作唯一源；(a) 的优先级设计正是为此。
- **(d) 引入「泳道注销」——收工时把泳道从活跃集合里删掉**
  **代价**：删掉之后 `summary` 就报不出这条泳道了，D6「本批停 N 次」那一列会缺项。**终态是要被汇总报出来的，不是要被消失的。**

**推荐 (a)。默认项 ＝ (a)。**

### 决策点 4 · `STOPPED ｜`（泳道自己停下等人）是否与 `DONE ｜` 同等豁免？

既有约定里收工哨兵有两个：`DONE ｜ <产出落点>` 与 `STOPPED ｜ <停在哪一步、为什么>`（看护件 0828 批原文，沿用至今）。二者语义不同：前者是干完了，后者是**停在决策点等人**。

- **(a) 两者同等豁免，但 `skipped_reason` 分别标 `lane_done` / `lane_stopped`〔推荐 · 默认〕**
  **理由**：看门狗要答的问题是「还有没有信号」，而 `STOPPED` 恰恰**是一个明确的信号**——它已经说清了在等什么。此时再推一条「分不清是长回归还是挂了」的告警，是拿一个含糊的问题去覆盖一个明确的答案。且 `check_heartbeat` 今天已经跳过 `paused` 泳道（「那种没心跳是预期状态」），`STOPPED` 与 `paused` 是同一件事在两个载体上的表达——**同因同果**。
  **代价**：一条泳道写了 `STOPPED` 之后**真的**挂了，看门狗不再管它。缓解：它已经落在「待人裁」清单里，收工汇总必报（既有 D6 列），**不会消失，只是不再由看门狗催**。
- **(b) 只豁免 `DONE`，`STOPPED` 仍判失联**
  **代价**：泳道按约定老老实实写了「我停在这里、在等 X」，30 分钟后被推一条「失联了，分不清在跑长回归还是挂了」——**机制在惩罚遵守约定的行为**。
- **(c) `STOPPED` 豁免但设更长的二级阈值（如 4 小时）**
  **代价**：新造一个阈值 ＝ 新造一条要审的判据，而既有 `check-timeout`（`DEFAULT_TIMEOUT_HOURS = 4.0`，待答超时自动收工）**已经在管这件事**。重复实现。

**推荐 (a)。默认项 ＝ (a)。**

### 决策点 5 · 看门狗对已终态泳道的返回值：静默 OK，还是可区分的"已终态"？

- **(a) 返回可区分字段 `skipped_reason`，CLI 打印「泳道 X 已终态（DONE/STOPPED），本次不判失联」〔推荐 · 默认〕**
  **理由**：CLAUDE.md 常驻纪律原句——🔴 **只读命令结果「太干净」先怀疑没读到对象**。若「健康」与「已完工」返回得一模一样，看护者就分不清「它还在跑」和「它早跑完了」；而这两种状态下**下一步动作完全不同**（等 vs 收工）。今天已经有一个同族先例：`already_paused` 就是一个可区分的返回字段。
  **代价**：CLI 输出多一种分支，`summary` 多一列。
- **(b) 静默返回 `stale=False`，与健康泳道无差别**
  **代价**：见上。**一个把两种不同事实压成同一个输出的接口，就是在制造下一个误判。**

**推荐 (a)。默认项 ＝ (a)。**

### 决策点 6 · 本包的 spec MODIFIED 块以谁为基线？

`openspec/specs/` 下**尚无** `lane-watch/`（现取：只有 `lane-clearpool/`）——`lane-watch` capability 的 spec 目前只以 delta 形态存在于**未归档**的 `lane-watch-mode` 变更包里。

- **(a) 以 `openspec/changes/lane-watch-mode/specs/lane-watch/spec.md` 的对应 requirement 为基线出 MODIFIED 块，并在本包 spec 顶部注明该前置依赖〔推荐 · 默认〕**
  **收益**：requirement 文本有唯一出处，不凭空重写；`lane-watch-mode` 归档时两包的 delta 依序合并，语义连续。
  **代价**：本包的归档顺序被约束在 `lane-watch-mode` 之后——须在 tasks 里显式写明（`tasks.md` §6.2），否则先归档本包会得到一份"修改了不存在的 requirement"的 spec。
- **(b) 在本包里写 ADDED，新起一条独立 requirement**
  **代价**：「什么算失联」会有两条 requirement 并存且互相矛盾（老的说超时必 pause，新的说已 DONE 不 pause）。**这是 proposal 里点名要避免的"靠新增一份 spec 绕过真实改写"。**
- **(c) 先推动 `lane-watch-mode` 归档，再基于正式 spec 出本包**
  **代价**：把本包的进度绑在另一个包的归档节奏上，而那个包的归档条件与本缺陷无关。**如实登记为可选路径，不作推荐。**

**推荐 (a)。默认项 ＝ (a)。**
