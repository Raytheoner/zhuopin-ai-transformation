# open-pool-reminder-dual-file-and-staleness Proposal

## Why

队列 `#312`「可 Open 池事件驱动提醒」在 2026-08-10 落地并持续在跑（计划任务 `ZhuopinDecisionReminderDaily` Ready，2026-08-19 07:36 本地刚写过状态文件），**但对 Shao Peishen 真正要的那件事——「提醒我加快」——结构性失效**。2026-08-19 零时巡检（`1-转型规划/0-全景路线图/零时巡检报告-2026-08-19.md` §一）实测查清两个叠加的缺口，本包一次修掉两个。

### 缺口一（决定性）：读侧只跟了一份队列文件，业务场景那份从来没被扫过

`aibot_service/repo_paths.py::DEFAULT_QUEUE_RELATIVE_PATH` 是**单文件常量**，只指向 `跨桌任务队列-机制环境.md`；`scripts/decision_reminder_check.py` 用它读出唯一一份 `queue_text` 后交 `build_pool_items(queue_text, repo_root)`。

**而 `#315` 双文件拆分（2026-08-11）之后，采购／财务／质量三域的构建任务全部住在 `跨桌任务队列-业务场景.md` 里。**

实测坐实（非推断）——生产状态文件 `reports/open_pool_reminder_state.json` 当前内容：

```json
{ "known_open_ids": ["240", "337", "338", "341", "98"] }
```

**五个全部是机制环境行。采购 `#334`／`#344` 一个都不在池里。** 采购 `#334` 的两个排队前置（`#266` 穿透改造、`#118` 优先级补全）已于 2026-08-18 全部完成、`#266` 还经姚祖怡本人抽查验收通过，**但没有任何机制会去重算它** —— 它就这样静静地待在一个没人扫的文件里。

⚠️ 这一条**在拆分时就被知道了**：该常量上方注释自陈是「迁移期妥协（决策点 3）」。但 `#341` 承接的那笔欠账治的是**写侧路由**（新行该写进哪一份），**读侧漏了一份不在 `#341` 的范围里**，于是它成了没人管的第三块。

🔑 **形态 ＝「一份拆成两份，下游只跟了一份」**——与 `#345`（35 份手抄副本漂成 4 种语义）、README「下一个可用号」段（改了下表没改上段）同属一族：**副本增加时，没有任何机制保证所有消费者都跟上。**

### 缺口二：设计上「只在新增时推一次」，对「一直有活、没人开」结构性沉默

现指纹定义＝当前可 Open 行号集合，**集合不出现新行号即静默**（`compute_new_ids`）。`#341` 是 2026-08-17 立的，此后机制侧没有新 open 行 ⇒ **即使修好缺口一，只要 `#334` 已经在池子里待了几天，它也不会再响第二次。**

**而「提醒我加快」要的恰恰就是这一半**：他要的不是「有新活了通知我」，是「**有活一直没开，催我一下**」。这两件事在现有实现里是同一个判据，而它只覆盖了前者。

### 本次退休哪一个既有守卫（协议〇.9 措施 B，机制类变更包强制）

**退休对象：`DEFAULT_QUEUE_RELATIVE_PATH` 作为「可 Open 池读取范围」这一角色。**

本包之后，可 Open 池的取数范围由 `queue_table.iter_queue_paths()`（双文件权威枚举）唯一决定，**该常量不再参与决定"池子扫哪些文件"**——它此后只剩「仓库根解析锚点」与「写侧默认落点」两个职责（后者是 `#341` 的范围，本包不动）。

这是一次**真实的收敛而非新增**：`iter_queue_paths()` 是 `#315` 已经建好、专门为「需要读取全部队列内容的消费者」准备的入口（其 docstring 原话：「替代此前假设『只有一份队列文件』的遍历逻辑」）。本包不新造第三份枚举，而是**把一个漏跟的消费者接回那个既有入口**——每接回一个，「拆成两份而下游只跟一份」这个家族就少一个可能的实例。

⚠️ **不退休的一项，写明为何不能退**：既有的「新增即推」指纹判据（`compute_new_ids`）**不退休、不被陈化催办取代**。两者判的是不同的事——前者判"池里出现了以前没有的活"（低延迟、事件驱动），后者判"某条活一直没被领走"（周期性、存量催办）；用后者取代前者会让新活最多迟 7 天才被提醒，用前者取代后者就是今天这个缺口。**故两条判据各自独立计指纹、互不覆盖**（design 决策点 4）。

### 伴生文件的 .gitignore 覆盖（队列 #328 子项②，强制）

**本变更不新增任何新文件名形态。** 陈化催办的状态写入**既有**状态文件 `5-平台底座/wecom-aibot-service/reports/open_pool_reminder_state.json`（新增一个 JSON 键，文件名不变）。

核实方式与实测结果（`git check-ignore -v`，不是推断）——apply 期真实执行，原样贴回：

```
$ git check-ignore -v "5-平台底座/wecom-aibot-service/reports/open_pool_reminder_state.json"
.gitignore:28:**/reports/	5-平台底座/wecom-aibot-service/reports/open_pool_reminder_state.json
```

⇒ 已被 `.gitignore` 第 28 行的 `**/reports/` 覆盖，退出码 0（命中）。本变更不改变该文件的落点目录，故覆盖情况不变。

## What Changes

- `aibot_service/open_pool_reminder.py`
  - 新增「可 Open 池专用的双文件取数」——按 `queue_table.iter_queue_paths()` 读两份物理队列文件后合并成池；**`DEFAULT_QUEUE_RELATIVE_PATH` 本身不动**（它还被 `queue_appender` 等写侧消费，动它会牵到 `#341` 的范围）。
  - 新增「陈化催办」判据：某可 Open 行在池中停留 > 7 天且期间该行无任何改动，每周推一次；与既有「新增即推」并存、分别计指纹。
  - 「该行无任何改动」的判据**用 git**（该行所在文件上该行的末次触碰提交时间），**不用 mtime**（`#338`④ 已记过 A9 教训：文件 mtime 与"这一行有没有被改过"是两回事）。
  - 状态文件 schema 增加一个键承载陈化催办的"上次催办时间"，与 `known_open_ids` 并列、互不覆盖。
- `scripts/decision_reminder_check.py`：可 Open 池段改用双文件取数；陈化催办消息作为**独立一条**推送，审计 action 名单独区分。
- 新增能力 spec `aibot-open-pool-reminder`——`#312` 落地时未走 openspec（当时机制类门槛尚未覆盖到它），本包首次把它的行为契约写成 spec，既有行为一并纳入。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

**本流程哪些判断是人脑默会经验？**

1. **「这条活该不该催他」的尺度**——现由 Shao Peishen 每次靠自己回想。本包把它显性化为两条可机读规则：① 新出现在可 Open 池即推一次；② 在池中停留 > 7 天且期间无改动，每周催一次。
2. **「这条活到底动没动」的判据**——人的默会做法是"我记得上周好像动过"。本包显性化为 git 上该行的末次触碰提交时间，**排除了 mtime 这个看起来等价、实际不等价的替身**。
3. **例外/尺度**：`open` 以外的状态（`partial`／`hold`／`blocked`／`timed=`／`done`）不进池——这是 `#308` 机器字段已固化的既有口径，本包沿用不改；`partial` 行"主体已完成而子项待领"这一已知边界仍不处理（`#312` 行内已如实登记，需要一个可机读的二次判据才能纳入，不靠正则猜中文）。

**由谁显性化？** 持有人 ＝ Shao Peishen（判据尺度的唯一决策人，2026-08-19 已就阈值 N＝7 与形态答定夺 1 选 (a)）；backup ＝ 值周巡检线（每周《本周计划》固定列出可 Open 池计数，是该判据在人侧的第二双眼睛）。

**用什么方法提取？** **AI 起草·专家批改**——由 2026-08-19 零时巡检报告 §五 以三选一（(a) 陈化催办／(b) 只修缺口一／(c) 每次非空就推）带默认项的形式提出，Shao Peishen 当日答 (a)、N＝7。

## 验收与晋档条件（强制，四档口径）

**本变更包交付后所处档位：档 2（真实数据跑通）。**

判据：本包的验收**不接受只跑单测**——必须对**生产队列真身**跑出可 Open 池、并**真实推送到企微**、由 Shao Peishen 在手机上看到，且**必须验证业务场景文件里的行能被推出来**（`#334` 或 `#344` 即现成样本）。这正是缺口一的直接反面：只在 mock 上跑通，恰恰是本包要修的那个缺陷当初能存活下来的原因。

**晋下一档（档 3 内部服务）的条件：**

1. 陈化催办在生产上**完整跑过一个 7 天周期**——即观察到「某行满 7 天 → 推一次 → 一周内不重复推 → 满 14 天再推一次」这条完整轨迹；本包交付时**只能验证前两步**，后两步须等自然发生，如实登记不假装闭合。
2. 观察期内**未出现狼来了效应**（同 `#147` 教训）：若 Shao Peishen 反馈"这条催办已经开始被我忽略"，须回 §五 重议阈值而不是继续加判据。
3. 已在生产上确认：一条行被领走／转 `partial` 后，其陈化记录被清掉，**不会在它重新回到池里时立刻误催**。

**价值指标（风险型）**：**「排队条件已满足但无人重算」的行的最长滞留天数**。基线 ＝ 采购 `#334`——2026-08-17 定级、2026-08-18 前置全部解除、**2026-08-19 由人（Shao Peishen 主动问一句）而非机制发现**，滞留 ≥ 1 天且当时无任何上界。目标 ＝ 该指标此后有上界（≤ 7 天首次提醒 + 每周复催）。业务 Champion ＝ Shao Peishen 本人（本机制的唯一使用者与唯一受益人）。
