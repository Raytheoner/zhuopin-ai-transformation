# open-pool-reminder-dual-file-and-staleness Design

## Context

`#312` 可 Open 池提醒的两个缺口（读侧只跟一份队列文件／只在新增时推），完整取证见 `1-转型规划/0-全景路线图/零时巡检报告-2026-08-19.md` §一，不在此重复。

**范围红线（派单件 OP-0819-A ⑵ 明写，本包严格遵守）**：
- 🔴 **不并进 `#341`**——`#341` 承接的是**写侧按域路由**的欠账，读侧漏一份不在其范围内，也不要假设它会顺带解决。
- 🔴 **`DEFAULT_QUEUE_RELATIVE_PATH` 本身不动**——它还被 `queue_appender` 等写侧消费，动它会牵到 `#341` 的范围。加一个「可 Open 池专用的双文件取数」，**而不是改那个共享常量**。

## Goals / Non-Goals

**Goals**
- 可 Open 池覆盖两份物理队列文件，业务场景域（采购／财务／质量）的 `open` 行能被推出来。
- 存量催办：某可 Open 行久无进展时周期性提醒，而不是只在它首次出现时响一次。

**Non-Goals**
- 不处理 `partial` 行的"仍有待领子项"边界（`#312` 已登记的已知边界，需可机读的二次判据）。
- 不改写侧路由（`#341`）、不改 `decision_reminder` 链路、不碰编辑锁/sweep/lint。
- 不做「池非空即推」（定夺 1 的 (c)，已被否决——每天一条会很快被忽略，同 `#147`「狼来了」教训）。

## 决策点

### 决策点 1：双文件取数的落点——新增函数，还是让 `build_pool_items` 自己去读文件？

- **(a) 新增 `build_pool_items_from_repo(repo_root)`，内部按 `queue_table.iter_queue_paths()` 逐份读、逐份解析、合并成一个池；`build_pool_items(queue_text, repo_root)` 原样保留（推荐）**
  - 代价：模块里出现两个语义相近的入口，需靠 docstring 说清各自职责。
  - 收益：`build_pool_items` 是**纯函数**（给文本、给根，返回池），31 个既有单测全部建立在这个形状上；改成"自己去读文件"会让它从纯函数变成有 I/O 的函数，既有测试要么改造要么加 monkeypatch，**为了少一个函数名而牺牲一整套测试的简洁性，不划算**。
  - 且新入口正是「退休 `DEFAULT_QUEUE_RELATIVE_PATH` 作为读取范围」这件事的落点——它把"扫哪些文件"这个决定收在一处，而不是散在调用方。
- (b) 改造 `build_pool_items` 让它自己按 `iter_queue_paths()` 读文件——代价见上。
- (c) 让调用方 `decision_reminder_check.py` 自己拼接两份文本再传给 `build_pool_items`——**代价：把"扫哪些文件"这个决定留在调用方**，下一个消费者出现时又要各拼一次，正是本包要退休的那个形态本身。
- **默认项：不答按 (a) 执行。**

> ⚠️ **(c) 还有一个不明显的技术障碍**：两份文件的文本直接拼接会产生两个 `## 一、` 标题，而 `_parse_table_rows` 用 `text.find(heading)` **只取第一个**——拼接后第二份文件的 §一 会被静默丢弃，**症状与今天这个缺口一模一样、且更难发现**。故 (a)/(b) 必须是"逐份解析后合并结果"，不是"拼接文本后解析一次"。

### 决策点 2：陈化阈值与推送频率

**已由 Shao Peishen 2026-08-19 答《零时巡检报告-2026-08-19》§五 定夺 1 选 (a)、N＝7 定死**：某可 Open 行在池中停留 **> 7 天**且期间该行无任何改动，**每周推一次**。本包不重议，只记录落地口径：

- 「停留 > 7 天」的计时起点 ＝ **该行在其所属队列文件上的末次触碰提交时间**（见决策点 3），不是它进入池的时间——后者需要另一份状态记录，且行被改过之后"进池时间"这个概念本身就模糊了。
- 「每周推一次」＝ 距上次对该行发出陈化催办 ≥ 7 天才再推。

### 决策点 3：「该行无任何改动」的 git 判据用哪种查法

派单件明写**用 git、不用 mtime**（`#338`④ A9 教训：文件 mtime 反映的是"这个文件被写过"，队列文件几乎每天都被写，**用它判"这一行动没动"恒为假**）。git 侧仍有两种查法：

- **(a) `git log -1 --format=%cI -G'^\| *<行号> *\|' -- <文件>`（推荐）**
  - `-G` 匹配"diff 的增删行中有匹配该正则的行"。编辑一行 ＝ 删旧行 + 加新行，两侧都以 `| <行号> |` 起首 ⇒ **任何对该行正文的改动都会命中**。
  - 代价：该行号若在同文件别处被以 `| 349 |` 形态提及会误命中——实测队列文件里行首 `| <数字> |` 只可能是 §一 数据行本身，误命中概率极低；且**误命中的方向是"以为它动过、于是不催"**，属保守失败（宁可少催一次，不可乱催）。
- (b) `git log -1 --format=%cI -L<n>,<n>:<文件>`——按行范围追溯。**代价：`-L` 追的是"当前第 n 行"的历史，而队列行的物理行号随上方增删不断漂移**，追出来的很可能是另一行的历史，是一个会静默给出错误答案的判据。
- (c) `git blame -L<n>,<n>`——同 (b) 的行号漂移问题，且 blame 只给"最后一次修改该行的 commit"，对被整体重排的行同样失真。
- **默认项：不答按 (a) 执行。**

🔴 **取不到时间怎么办（必须显式规定，否则会静默走进某个方向）**：新立的行在 commit 之前 git 上查不到 ⇒ 返回 `None`。**`None` MUST 被当作「刚触碰、不催」**（保守失败），并**MUST NOT 静默**——记一条 audit。理由：一条还没进 git 的行必然是刚写的，催它是纯噪音；而反过来把 `None` 当"很久没动"会让每一条新行在下一次运行时立刻被催，直接把机制变成 (c) 方案。

### 决策点 4：陈化催办与「新增即推」是两条消息还是合并一条

- **(a) 两条独立消息、两套独立指纹、两个独立 audit action 名（推荐）**
  - 收益：两者的抑制条件完全不同（新增＝行号首次出现；陈化＝距上次催办 ≥ 7 天），**合并会让其中一条的抑制条件覆盖另一条**——派单件原文「两条判据分别计指纹，不要互相覆盖」。
  - 且 audit action 分开才符合 `open_pool_reminder.py` 既有那句「IATF 可追溯性要求动作可精确归因到具体机制，不是『反正都是提醒就共用一个标签』」。
  - 代价：极端情形下同一次运行可能连发两条推送（一条新增、一条陈化）。可接受——两条各自都自带下一步动作，不是重复内容。
- (b) 合并为一条消息、分两段——代价见上。
- **默认项：不答按 (a) 执行。**

### 决策点 5：冷启动——首次带上陈化判据运行时，把当前所有已陈化的行一次性推出来吗？

现状状态文件里没有 `stale_notified_at` 键 ⇒ 第一次运行时，池中每一条满足"> 7 天无改动"的行都会被判为"从未催过"。

- **(a) 一次性全推（推荐）**
  - 收益：**这正是他要的**——`#334` 这类"排队条件已满足但没人重算"的行，今天就该被催出来，而不是再等一个周期。
  - 代价：首次可能是一条较长的消息（当前实测量级：可 Open 行共 9 条左右，其中满 7 天的更少），一次性噪音，此后即回归每周节奏。
- (b) 冷启动时静默、只把当前时间写进状态，从下一轮开始催——**代价：把本包要解决的那件事又推迟 7 天**，且"修好了但今天还看不到效果"会让验收无法在本包内完成（验收要求真实推送）。
- **默认项：不答按 (a) 执行。**

### 决策点 6：行离开池后，它的陈化记录怎么处理

- **(a) 每轮把 `stale_notified_at` 裁剪为"仅保留当前池中还在的行号"（推荐）**——与 `new_known_state` 已确立的"替换而非并集累加"语义一致（该函数 docstring 明写选择了 sweep 那版"出现→消失→再出现即再报"语义）。一条行被领走后又退回 `open`，它会重新按 7 天起算，**而不是带着三个月前的催办记录立刻被催**。
- (b) 只增不减——代价：状态文件无界增长，且上述"重新入池立刻被催"的误报。
- **默认项：不答按 (a) 执行。**

## Risks / Trade-offs

- **两份文件读取的失败模式**：某一份文件读取失败（不存在/权限）时，**MUST NOT 静默把池算成"另一份的内容"**——那正是缺口一的形态。处理：缺失的文件跳过并发 `RuntimeWarning`（同本模块 `parse_open_pool_rows` 对字段缺失的"非静默降级"既有惯例），不中断另一份的处理。
- **每行一次 git 子进程**：当前可 Open 行量级个位数，成本可忽略；若未来池子上到几十行需重新评估（可改为一次 `git log --format` 全量扫描后在内存里配对）。**本包不预先优化**，但在实现里把 git 查询独立成单个函数，便于将来整体替换。
- **误命中方向的选择**：决策点 3 的 `-G` 判据宁可"以为动过而不催"，不可"以为没动而乱催"——`#147` 狼来了教训指向后者的代价更高。

## Migration Plan

状态文件向后兼容：旧文件只有 `known_open_ids` 键，`load_state` 现有实现按 `default_state()` 的键做过滤合并，**新增键会自动取默认值（空 dict）**，不需要迁移脚本、不需要手工改状态文件。冷启动行为见决策点 5。
