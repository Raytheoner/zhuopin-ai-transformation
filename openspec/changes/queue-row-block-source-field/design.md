## Goals / Non-Goals

**Goals：**
- `_suggest_status_reclassification` 的判据来源从"匹配七个中文短语的自由文本正则"改为"读一个结构化字段"，把黄金集一致率从 2/9 提到可验证、可回归的水平。
- `_count_mechanism_wip` 与建议器共享同一个 `[B:]` 字段来源，消灭"配对与开闸各用一把尺"同族问题（`#366` 教训）。
- `[B:split]`（一行两半）获得显式的机器识别与"建议拆行"提示，替代"改判 or 不改判"这个在混合态行上无论怎么选都错的二选一。
- 吸取 `[D:]` 字段"从未设 CI 门禁、静默少算"的真实教训，让 `[B:]` 门禁上线时点比 `[D:]` 更早、更明确（决策点 7）。

**Non-Goals：**
- **不改 `[S:]`／`[D:]` 既有语法与取值集合**——`[B:]` 是在其后新增的第三段，不重新论证前两段。
- **不改变 `#308`（`queue-status-machine-field`）自身的归档状态或范围**——该变更仍未归档，本变更与其并行存在，proposal.md 已说明为何暂不对其能力写 `MODIFIED` delta。
- **不代行拆行动作**——`[B:split]` 只产出"建议拆行"提示，实际把一行拆成两行是行所有者的人工动作，机器不自动改写队列正文的行结构（同 `_suggest_status_reclassification` 现有"只建议不代改"的边界，理由相同：状态是行所有者对自己工作的判断，机器越权翻转会制造比它想解决的问题更难查的问题）。
- **不引入 LLM 判断**——五态归类与拆行判断均由人工在补标/建行时给出，机器只做字段查表。
- **不新增字段所在物理列**——沿用 `[S:]`/`[D:]` 的前缀方案，追加进同一个状态列字符串，不改 `SECTION_COLUMN_COUNTS`。

## Decisions

### 决策点 1：`[B:]` 字段语法、取值集合与位置

**语法**：§一 状态列 `[S:<value>][D:<value>]` 之后，紧跟第三段 `[B:<value>]`，三段之间无分隔符，各自方括号自成边界；`[D:]` 可省略（向后兼容既有降级路径）时 `[B:]` 仍可独立出现在 `[S:]` 之后（即 `[S:<value>][B:<value>]` 也是合法形态，覆盖"域字段暂缺但阻塞源已补"的中间态）。正则收敛为：

```
^\[S:(?P<status>done|open|partial|hold|blocked|timed=\d{4}-\d{2}-\d{2})\]
  (?:\[D:(?P<domain>机|业)\])?
  (?:\[B:(?P<block>none|person|env|external|split)\])?
```

**取值集合**（5 个，直接采纳设计正本 §3.1 表，未作改动——该表已是"一次失败实验＋两处真实误判根因"倒推出的结果，重新发明不会更好）：

| 取值 | 含义 | 计入可动 WIP | 建议器动作 |
|---|---|---|---|
| `none` | 无阻塞，现在就有人能动手 | ✅ 计入 | 不建议改判 |
| `person` | 等具体某人拍板／签认 | ❌ 不计入 | 确认 `blocked` |
| `env` | 等环境条件（回内网、设备、窗口期） | ❌ 不计入 | 确认 `blocked` |
| `external` | 等外部方（专员回件、供应商、OEM） | ❌ 不计入 | 确认 `blocked` |
| `split` | 一行两半：有可动半边，也有阻塞半边 | 见决策点 5 | 建议拆行，不建议改判 |

**向后兼容降级（不得静默，沿用 `[S:]`/`[D:]` 既有范式）**：任一消费者读到 `[S:]` 可解析但 `[B:]` 缺失的行，MUST 记一条"阻塞源字段缺失，回退既有判据"的降级日志——回退判据即本变更要退休的 `STALE_STATUS_PHRASES` 匹配逻辑本身在**补标完成前的过渡期**内继续可用（不是立刻删代码，是"读到新字段就用新字段、读不到就用旧判据且留痕"，与 `[S:]` 先例的过渡期处理完全一致）。补标 ＋ 消费者切换全部完成后（决策点 7），`STALE_STATUS_PHRASES` 与其匹配循环整体删除，届时不再存在"缺 `[B:]` 字段"的稳态行，回退分支成为死代码路径、随之一并删除。

**被否候选**：
- **候选：五态之外再加一个"待定/未分类"占位值** → 否决：这会重新制造一个"字段存在但不解决问题"的中间态，且设计正本 §2 的教训正是"引入新的模糊态会在下一次措辞变化时静默失效"；缺字段本身已经是"待补标"的显式信号（非静默降级日志会指出来），不需要再造一个同义的取值。
- **候选：`[B:]` 放在 `[S:]` 之前** → 否决：与 `[D:]` 的既有位置约定（紧随 `[S:]` 之后）保持"先状态、后修饰字段"的统一顺序；且现有五处解析实现的正则锚点均以 `^\[S:` 开头，若 `[B:]` 插到最前会让所有既有实现在"字段是否存在"判断上全部失真，代价与收益不成比例。

**默认项**：若不答，按上表 5 值集合 ＋ `[S:][D:][B:]` 顺序前缀语法 ＋ 非静默降级执行。

### 决策点 2：`_suggest_status_reclassification` 判据来源退休方案

**现状**：函数遍历 §一 `open`/`partial` 行，对状态字段之后的自然语言正文 `rest` 做 `STALE_STATUS_PHRASES` 七元组子串匹配，命中即产出改判候选。

**改法**：判据源从"匹配 `rest`"改为"读 `[B:]` 取值"——

```python
def _suggest_status_reclassification(section_one_text):
    candidates = []
    for _line, cells in _table_data_rows(section_one_text):
        if len(cells) <= 5:
            continue
        row_id = cells[0].strip() if cells and cells[0] else "?"
        status_value, _domain, block_value, _rest = _parse_status_domain_block_fields(cells[5])
        if status_value not in ("open", "partial"):
            continue
        if block_value is None:
            candidates.append((row_id, status_value, "[B:] 缺失", "回退旧判据（补标未完成）"))
            # 过渡期内此处继续调用旧的 STALE_STATUS_PHRASES 匹配作为回退分支
            continue
        if block_value == "none":
            continue
        if block_value == "split":
            candidates.append((row_id, status_value, "建议拆行", "[B:split]"))
            continue
        candidates.append((row_id, status_value, "blocked", f"[B:{block_value}]"))
    return candidates
```

`STALE_STATUS_PHRASES` 常量与其匹配逻辑在过渡期结束后（决策点 7）整体删除——这就是 proposal.md「Why」段承诺的"本次退休哪一个既有守卫"。

**回归验收**：`#142` 9 行黄金集补标后逐条核对，`[B:]` 推出的建议须与人工判定结论一致（`#312`／`#422` 应仍建议 `blocked`，其余 7 行应仍不建议改判为 `blocked`，且当中的混合态行应落 `[B:split]` 并给出"建议拆行"而非静默放过）。`OP-0901-D` §2 的 v1/v2 实验数据（领取方列匹配的成败案例）作为反例集一并纳入回归——补标结果不得复现"改一个坏一个"的模式。

### 决策点 3：`_count_mechanism_wip` 消费契约

现有排除条件：`status_value in (done, blocked, timed=...)` 或正文以 `🛑` 开头。**新增一条**：`block_value in (person, env, external)` 时同样排除（即便 `status_value` 是 `open`/`partial`/`hold`）。`block_value in (none, split, None)` 不触发本条排除（`split` 是否计入见决策点 5；`None` 即字段缺失，走既有"非静默降级"路径，不静默计入也不静默排除，只记降级日志、按原有域字段判据兜底）。

这与建议器共享同一个 `_parse_status_domain_block_fields` 调用与同一份 `[B:]` 取值语义——两处消费者读的是同一个字段、同一套五态定义，不会出现"WIP 计数说这行不算数、建议器却说这行该建议改判"的口径分裂（`#366` 教训：口径分裂比单一口径出错更难查，因为两处各自看起来都"没错"）。

### 决策点 4：`[B:split]` 拆行语义与操作流程

机器动作范围：`_suggest_status_reclassification` 对 `split` 行输出"建议拆行"文案（复用 `_render_reclassification_candidates` 既有渲染框架，追加一个候选类型分支）。**机器不做**：不自动把一行拆成两行、不自动决定拆分点在哪、不自动改写触碰区/领取方等其余列。

人工流程（值周巡检或行所有者执行，写入 tasks.md 作为操作手册，不写进代码逻辑）：
1. 读该行自然语言正文，识别"可动半边"与"阻塞半边"两段描述。
2. 用 `append-row` 新建一行承载可动半边（继承原行触碰区中与可动部分相关的子集，状态置 `[S:open][D:<原域>][B:none]` 或视实际进度置 `partial`），并在新行「输入（指针）」列点名原行编号（"承接 #N 拆行"）。
3. 原行状态改为 `[S:blocked][D:<原域>][B:<person|env|external，按阻塞半边实际原因定>]`，正文保留阻塞半边描述，删除已拆出的可动半边描述（历史记录不追改——若拆分前的完整正文有留痕价值，先落 `1-转型规划/0-全景路线图/队列行日志/#N.md` 再精简，同队列与落库规则的"行内日志外置口径"）。
4. 两行落库后，`_count_mechanism_wip` 与建议器均按各自新字段独立判定，不再需要人工每次重新分诊。

### 决策点 5（收敛设计正本 §5 开放点 1）：`[B:split]` 是否计入可动 WIP

**推荐：计入**，与设计正本 §3.1 表的建议一致，附加一条落地期限制：拆行完成前最长保留期为**下一次值周巡检**（当前每周一 10:00），超期未拆的 `split` 行由值周巡检的候选清单再次点名，不静默无限期占着可动 WIP 名额。

**理由**：
1. `split` 行确有可动半边——不计入会重演"藏活"这个设计正本 §1 明确指出比 WIP 虚高更危险的反向失真。
2. 现有 `🛑` 前缀已经证明"显式标出但仍需要人为动作清理"的中间态是本项目已经在正常运作的一种模式（`#439`／`#440`／`#447` 均以 `🛑` 起首且不计入 WIP，`#448` 本行本身立行时也用过这条豁免）——`split` 计入 WIP 但被建议器持续点名，性质上更接近"透明地占着位置、有人盯着"，而非"消失不见"。
3. 不计入的反方案（靠"建议拆行"提示驱动）在**建议器本身还没有强制阅读机制**的现状下，等价于"指望有人主动去看候选清单"——而候选清单目前的消费方式正是本变更要修的"靠人逐行读"，用同一个尚未验证生效的机制去兜底自己的排除条件，论证上是循环的。

**尚未做、且本设计明确承认的局限**：设计正本 §5 原文写"需实测存量 `split` 行数才能定"——本变更止步于起草，不做存量补标（那是 tasks.md 落地阶段的工作），故此刻仍不知道存量 `split` 行的真实数量。**推荐"计入 ＋ 限期"这套方案本身对存量行数不敏感**（不论 `split` 行是 3 行还是 30 行，"计入但被点名、超期继续点名"这条规则都成立），这是特意选择一个不依赖未知数字的方案，而不是绕开设计正本指出的这条局限。若补标后 `split` 行数远超预期（如超过在办总量的 20%），值周巡检应把这个事实登记回 `#448` 行，届时再重新评估是否要改为"不计入"。

### 决策点 6（收敛设计正本 §5 开放点 2）：存量补标由谁做、一次性还是渐进

**推荐：值周巡检一次性补标**，不采用"各行所有者下次触碰时顺带补"的渐进方案。

**理由（直接对照 `[S:]`/`[D:]` 先例的真实结果）**：
1. `queue-status-machine-field` 的 106 行状态字段回填就是一次性做完的（该变更 tasks.md 3.1-3.4），且该次一次性回填已产出"新旧判据分歧清单"这一有价值的副产品（17 处分歧，逐条复核后确认均为合理细化）——一次性补标能在同一个时间窗口内做交叉核对，渐进补标做不到这一点，因为不存在"同一时刻的整体视图"。
2. **渐进方案在这个项目里已有一次实测的反面教材，就是 `[D:]` 字段本身**：`[D:]` 字段从 `#308` 落地至今从未补上 CI 门禁（tasks.md 7.3 实测记录），长期停留在"部分行有、部分行没有、没有门禁去发现谁没有"的状态，代价是 `_count_mechanism_wip` 按 `[D:机]` 取数时**静默少算**——这正是"两套并存"的具体后果，不是一个假设的风险。`[B:]` 若采用渐进补标，会在结构上复制同一条路径。
3. 45+23＝68 行的量级与 `[S:]`/`[D:]` 先例的 106 行同一数量级，先例证明这个量级"一次性做"是可行的，不需要用渐进方案分摊成本。

**代价（如实登记，不回避）**：一次性补标需要值周巡检在同一次巡检窗口内逐行读懂 68 行正文并给出五态归类，工作量集中在一次巡检——但这与"该成本躲不掉，只是一次性付还是每次分诊都付"的设计正本 §4 既有结论一致（"今日本会话即第 3 次" 付的正是分散支付的成本）。

**默认项**：若不答，按"值周巡检一次性补标，纳入下一次值周巡检窗口"执行；渐进补标不作为默认。

### 决策点 7：CI 门禁上线时机（吸取 `[D:]` 字段教训，不是重复 `[S:]` 或 `[D:]` 任一先例）

三条路径的比较：

| 方案 | 做法 | 对应先例 | 问题 |
|---|---|---|---|
| A：append-row 必填即拒 | 缺字段的新增行直接拒绝写入 | 设计正本 §4 原设想（本设计已修正其对现状的描述，见 Context） | 补标完成前，存量行的"编辑既有行"操作（`edit-row`）若原样保留旧行会不会触发同一校验？若触发则在补标完成前所有编辑都会被拒；若只对 `append-row` 生效则治标不治本（存量行仍长期缺字段，`_count_mechanism_wip` 仍要走非静默降级分支） |

**推荐 C**，具体落点：`工具-队列结构lint.py::_lint_one_file` 现有 `[S:` 门禁分支（L493-504）旁新增一个同构分支——`status_value is not None`（即 `[S:]` 已可解析）但 `block_value is None` 即判违规，文案指向本行、指向 `#448`。**上线前置条件**（同 `[S:]` 先例的既有纪律，不新造）：仅当决策点 6 的一次性补标 ＋ 决策点 2/3 的两处核心消费者切换均已完成时才合并这段代码，避免对未补标的历史行段误报——但"完成"到"合并"之间不留时间差，一次 commit 内同批交付，不给"以后再补门禁"留出可以被遗忘的窗口。

tasks.md 第 8 节（收工验证）须把"lint 门禁已合入且对当前队列文件跑绿"列为不可勾选省略的一项，不能像 `[D:]` 那样被默认为"暂不做"。

### 决策点 8：五处独立实现的消费者切换范围与顺序

沿用 `queue-status-machine-field` 决策点 4 的既有排序原则（先权威实现、再各独立副本、最后 CI 门禁），本次范围收窄为只涉及"阻塞源"读取的位置：

1. `工具-共享文档编辑锁.py`（权威）：`STATUS_FIELD_RE` 扩展、`_parse_status_domain_fields` → `_parse_status_domain_block_fields`（新函数名，返回 4 元组；保留旧函数名作为对旧 3 元组调用点的兼容包装，内部委托新函数并丢弃第三个新增返回值，避免一次性改光全部调用点导致的大范围连锁改动——同批仍需把 `_suggest_status_reclassification`／`_count_mechanism_wip` 两个真正消费 `[B:]` 的调用点显式切到新函数，其余只消费 status/domain 的调用点可以继续用旧函数名，不强制全部迁移）、`STALE_STATUS_PHRASES` 退休。
2. `工具-落库sweep.py`：独立实现的 `_parse_status_domain_fields` 是否需要感知 `[B:]`——核实其消费点（L2823/L3386，均只取 `status_value`，`_`/`_domain`/`_rest` 均丢弃）**不需要改动**，只需确认新增的 `[B:]` 段不会打断其现有正则匹配（新增可选分组，向后兼容，不需要）。
3. `工具-队列查询.py`：展示层需要能把 `[B:]` 取值显示给人看（`--field all` 输出），属于本次范围内的必要改动，供值周巡检读取用。
4. `decision_reminder.py`／`open_pool_reminder.py`：核实其消费点是否读取 `rest`／`domain_value` 做进一步判断（若只取 `status_value` 则同 sweep，无需改动；若有用到 `rest` 做二次匹配则需要确认 `[B:]` 前缀不会被其误当作自然语言正文的一部分）——本设计不预判结论，列为 tasks.md 的核实项，不在此处断言。
5. `工具-队列结构lint.py`（经 import 复用权威实现）：决策点 7 的门禁分支。

## Risks / Trade-offs

- **五处独立实现意味着五处都可能遗漏**——这是本项目状态字段解析从 `[S:]` 落地起就存在的结构性代价（`#306` 曾提议收拢、至今未做），本变更选择沿用而非借机收拢，风险敞口与 `[S:]`/`[D:]` 持平、未扩大也未缩小。
- **决策点 5（`split` 计入 WIP）的推荐建立在"限期＋值周巡检持续点名"这套配套机制真正被执行**的前提上——若值周巡检本身出现遗漏（同"建议清单靠人主动看"的老问题），`split` 行可能长期滞留占位。缓解：候选清单的"建议拆行"文案与既有改判候选共用同一处渲染，不是一个需要额外去看的独立入口。
- **补标窗口内的判断质量**——68 行一次性补标由值周巡检人工判断五态归属，存在误判可能（同 `queue-status-machine-field` 106 行回填时"新旧判据分歧清单"性质相同）；缓解：回归验收明确要求补标结果与 `#142` 黄金集逐条核对，不满足清零标准的行须逐条给出人工结论，不能整体标记"完成"了事。
