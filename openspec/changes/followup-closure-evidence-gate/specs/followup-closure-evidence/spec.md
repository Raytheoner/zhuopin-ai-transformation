## ADDED Requirements

### Requirement: 闭环终态 SHALL 携带机器可核的回灌引用
跟进信 README「发送状态」列写入闭环终态 `📥 已回件并回灌 <日期>` 时，MUST 在同一单元格内声明**被回灌的队列行引用**（形如 `§一 #427`，可多值）与**依据的归档件**。

判据模块 SHALL 提供一个**与 `is_closed_status` 并列、不改其语义**的判定：某个 `📥` 状态是否**带合格引用**。合格 MUST 同时满足四条：

1. 状态以 `📥 已回件并回灌` 开头；
2. 可解析出至少一个队列行引用与至少一个归档件标识；
3. 每个被引用行确实存在于两份队列真身之一 —— 解析 MUST 逐份进行后合并，MUST NOT 先拼接文本再解析（同名分区标题会让后写覆盖先写，静默丢掉第二份的 §一）；
4. 🔴 每个被引用行的状态列，在剥掉全部机器字段（`[S:…]`／`[D:…]`／`[R:…]`）与空白之后，**仍非空**。

第 4 条 MUST NOT 被削弱为「行存在即可」：入信行由企微机器人按固定模板建立，该模板在状态列只写机器字段、不写正文；「这一格有正文」正是「机器人之外的某个主体往这里写过东西」的唯一非平凡证据。

判定 MUST NOT 依赖 git 历史 —— 回灌与转态发生在同一个未提交窗口内，判定时刻这些改动尚未进入任何 commit。

#### Scenario: 带合格引用的终态被认可
- **WHEN** 某信状态为 `📥 已回件并回灌 2026-08-28（回灌去向：§一 #427；回件：`7-外部文档/…md`）`，且 `§一 #427` 存在、其状态列剥掉机器字段后含拆件结论正文
- **THEN** 判定为「带合格引用」

#### Scenario: 无引用的终态不被认可
- **WHEN** 某信状态为 `📥 已回件并回灌 2026-08-29`，括注中无任何队列行引用
- **THEN** 判定为「不带合格引用」

#### Scenario: 引用的行只有机器字段则不被认可
- **WHEN** 终态引用了 `§一 #500`，而该行状态列剥掉 `[S:…][D:…]` 后为空
- **THEN** 判定为「不带合格引用」

#### Scenario: 引用的行不存在则不被认可
- **WHEN** 终态引用的行号在两份队列中均不存在
- **THEN** 判定为「不带合格引用」，且输出 MUST 指名是哪一个引用落空

#### Scenario: 第二份队列里的行同样能被找到
- **WHEN** 被引用行位于 `跨桌任务队列-业务场景.md` 的 §一
- **THEN** 判定成立（两份队列逐份解析后合并，不因解析次序而丢失）

### Requirement: 串行闸 SHALL 由两态改为四态
跟进闸的对外结论 MUST 由布尔量改为四值：`🔒 在途`（已发出、未收到回件）／`🔴 待拆件`（回件已到、尚未拆件回灌）／`✅ 开`（已拆且回灌有证据）／`⏸ 暂缓`（主动压着）。

只有 `✅ 开` SHALL 放行下一封信的起草与登记。

`🔴 待拆件` MUST 与 `🔒 在途` 严格区分：两者都不放行，但催办对象与处置动作完全不同（前者催拆件，后者等专员）。原有 `gate_open` 布尔字段 SHALL 保留为 `gate_state == "✅ 开"` 的派生字段，使既有 JSON 消费方零改动。

退出码语义 SHALL 不变：四态全部返回 0（闸锁不是错误，是一个正常答案）；解析失败或收信人不存在返回 2。

#### Scenario: 回件已到未拆件显示第四态
- **WHEN** 某收信人最近一封信的状态为 `📨 回件已到，待拆件 <UTC>`
- **THEN** `gate_state` 为 `🔴 待拆件`，`gate_open` 为 false，退出码 0

#### Scenario: 信还没发与回件没人拆不再同态
- **WHEN** 甲收信人最近一封为 `✅ 已推送 …`、乙收信人最近一封为 `📨 回件已到，待拆件 …`
- **THEN** 两者的 `gate_state` 不同（`🔒 在途` 与 `🔴 待拆件`）

#### Scenario: 终态但引用不合格不得放行
- **WHEN** 某信状态为 `📥`、日期在截止日期之后、且不带合格引用
- **THEN** `gate_state` 为 `🔴 待拆件`，`gate_open` 为 false

#### Scenario: 既有布尔字段保持可用
- **WHEN** 以 `--json` 调用
- **THEN** 输出同时含 `gate_state` 与 `gate_open`，且 `gate_open` 恒等于 `gate_state == "✅ 开"`

### Requirement: 截止日期之前的终态 SHALL 按旧口径放行并显式标注
状态日期早于截止日期、或**完全不带日期**的 `📥` 行，MUST 按旧口径视为已闭环并放行，MUST NOT 追改。

同时，闸的**输出**中 MUST 显式标注该结论的依据为旧口径（无回灌引用），MUST NOT 呈现为一个不带保留的 `✅ 开`。标注仅写在文档里而不出现在输出里，视为未满足本 Requirement。

🔴 本 Requirement 的含义 MUST 被如实说出：本机制对截止日期之前的行**零保证**。任何「跟进信闭环状态已全部可核」的表述都是错的；正确表述是「截止日期之后新增的闭环可核」。

#### Scenario: 无日期的历史终态按旧口径放行
- **WHEN** 某信状态为 `📥 已回件并回灌`（无日期、无引用）
- **THEN** `gate_state` 为 `✅ 开`，且输出含「旧口径（无回灌引用）」字样

#### Scenario: 截止日期之后的无引用终态不享受豁免
- **WHEN** 某信状态为 `📥 已回件并回灌 <截止日期之后的日期>`、无引用
- **THEN** `gate_state` 为 `🔴 待拆件`

### Requirement: 机器代写的存量终态 SHALL NOT 享受历史豁免
状态列含「未经人工逐字确认」字样的行，MUST NOT 因日期落在截止日期之前而被豁免。它们是被本变更判定为不可信的那一类的**产物本身**，MUST 逐条处置：经人工核实的补写引用转正，未经核实的降回第九态 `📨 回件已到，待拆件`。

降回第九态 MUST 被理解为「把状态改回它当时真实的样子」，MUST NOT 被当作惩罚性动作；其重新锁闸的后果 MUST 在处置前如实告知决策人。

#### Scenario: 机器代写行不因日期而豁免
- **WHEN** 某信状态为 `📥 已回件并回灌 2026-08-24（… 未经人工逐字确认 …）`
- **THEN** 不适用历史豁免，`gate_state` 为 `🔴 待拆件`

#### Scenario: 补写引用后转正
- **WHEN** 该行被人工核实并补写了合格引用、「未经人工逐字确认」字样被删去
- **THEN** `gate_state` 为 `✅ 开`

### Requirement: 判据模块既有对外符号 SHALL NOT 改名或改语义
`CLOSED_STATUS_PREFIXES`／`is_closed_status`／`find_unsynced_letters`／`reply_matches_letter` 四个符号 MUST 保持存在且语义不变；新判据 MUST 以新增函数的形式并列存在。

理由：`工具-队列结构lint.py` 有一条 CI 断言专盯这四个符号的存在性，而编辑锁对该模块 import 失败有一条**静默降级**路径（S4 校验整条跳过、只打一行 ⚠）——该断言存在的唯一目的就是让那条静默降级变红。改名会让断言红得名不副实，改语义会同时改掉全部既有消费者的行为而不产生任何信号。

新增符号 MUST 同批加入该条 CI 断言的名单。

#### Scenario: 既有符号仍可 import 且行为不变
- **WHEN** 本变更实现后运行 `工具-队列结构lint.py`
- **THEN** 四个既有符号断言通过，且新增符号一并被断言存在

#### Scenario: 旧判据行为逐字不变
- **WHEN** 对本变更前的 README 样本调用 `is_closed_status`
- **THEN** 返回值与本变更前逐条相同
