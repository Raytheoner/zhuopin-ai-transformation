## Context

见 proposal.md「Why」——完整故障时间线、commit 级证据（`c852883`→第一班 09:19 写盘→`4907dd7` 09:25:55）与真实代码路径复现用例均在那里，本节不重复，只展开候选方案的取舍推导。

现有 `append_task_and_sync_to_git` 冲突重算分支（`queue_git_sync.py:203-213`）：

```python
if attempt == max_retries:
    exhausted_conflict = True
    break

_run_git(resolved_repo_root, "fetch", remote)
_run_git(resolved_repo_root, "reset", "--mixed", f"{remote}/{branch}")
_run_git(resolved_repo_root, "checkout", "--", relative_path)
_sleep(backoff_seconds)
```

关键点：`_commit`（本函数上方）已经在这之前执行过 `git add relative_path` + `git commit`——`git add` 会把**当次磁盘上的全部内容**暂存进本地 commit，无论这些内容是不是本函数自己算出来的。协议〇.7/〇.8 明确允许"锁已释放、内容仍未提交"作为这份文件的合法常态（sweep 按 §二 批次统一提交前，工作区脏是预期状态，可持续数分钟到数小时）——这意味着 `git add` 暂存的内容里，随时可能混入与本次追加完全无关的第三方合法成果。一旦推送因非快进被拒（几乎必然，见 proposal.md 引用的 2026-08-06 实测），`reset --mixed` + `checkout --` 会把这个"混合本地 commit"连根拔起，工作区回退到 origin 版本——第三方成果随之从工作区与可达历史里一并消失。

## Goals / Non-Goals

**Goals:**
- 冲突重算命中"磁盘上存在与本次追加无关的外来未提交内容"这一情形时，绝不执行会覆盖工作区文件内容的操作（`reset`/`checkout`），改为安全退避。
- 退避后要有留痕（audit 事件 + 暂存记录），不能像本次一样"零告警、零痕迹"。
- 不引入新的、需要人类记住的手工纪律（本项目「规则退休制」的反面教训——机制化优先于人守）。
- 护栏未命中（磁盘内容确实只是本次追加自己产生的差异）时，行为与现状完全一致，不改变正常路径的性能与语义。

**Non-Goals:**
- 不试图让机器人自动"融合"外来内容与自己的追加（队列文件的合并语义只有编号计算这一处是机器可判定的，其余交人工/sweep）。
- 不改变 `append_task_and_sync_to_git` 三类既有失败语义的对外契约（非快进重算/网络失败保留本地 commit/重试耗尽 `reset --hard`）——只在"非快进重算"分支内新增一个前置检查点。
- 不解决"人类会话编辑窗口本身应该多长""sweep 多久跑一轮"这类节奏问题——那是协议〇.7/〇.8 与 sweep 调度频率的范畴，本变更只管机器人这一侧不能因为撞上这个窗口就销毁内容。

## Decisions

### 决策点 1：护栏放在哪一层——选定"预期差异校验"（候选 A），否掉"全程持锁"（候选 B）与"纯 git 对象级重写"（候选 C，登记为未来可选的更彻底方案）

**候选 B（机器人在整个 `append_task_and_sync_to_git` 调用期间持有编辑锁）否决**——已用真实场景验证锁语义解决不了本问题：协议〇.7/〇.8 的既有设计允许人类 `acquire`→写盘→`release` 后立即释放锁，内容却仍未提交、合法地脏着数分钟到数小时。机器人即便在自己的操作期间全程持锁，锁在它拿到的那一刻本就是空的（人类早已释放）——磁盘上人类的成果依然原样在那儿，持锁不会让它消失，也不会让机器人"看见"它是别人的合法成果而不是垃圾。持锁能防止的是"两个写手同时写"，防不了"前一个写手已经合法地写完并放手，但还没来得及提交"。

**候选 C（彻底改为 git 对象级操作——基线读 `git show HEAD:path`、经 `hash-object`/`update-index`/`commit-tree` 直接更新分支引用，全程不碰工作区文件）**——这是更彻底的根治方案，从架构上完全消除"git add 会暂存磁盘上任意内容"这一风险来源，但改动面显著更大：需要重写 `append_task_and_sync_to_git` 的核心实现、处理"push 成功后工作区是否要 checkout 追上"这一新问题（追上本身在工作区仍有其它脏内容时同样危险，很可能还是需要候选 A 的护栏），且与 `append_pending_task`（供人工/其它调用方直接使用的独立入口，语义是"读改写磁盘文件"）在语义上要么重复实现、要么强行复用出跨层耦合。**登记为候选、不在本次采纳**——本次事故的直接诱因（非快进冲突后的销毁性 reset/checkout）用候选 A 就能根治，候选 C 的额外收益（彻底消灭"git add 暂存任意磁盘内容"这条路径本身）值得作为独立的后续加固，但不应绑定在本次止血修复里扩大改动面与审查负担。

**选定候选 A（预期差异校验护栏）**：在即将执行 `reset --mixed` + `checkout --` 之前，比较"本次追加预期产生的差异"与"磁盘相对本函数已提交内容的实际差异"——预期差异的形状是固定且可枚举的：`append_pending_task` 每次调用**恰好**新增一行（新任务行）＋**至多**修改一行（高水位线标注行的数字自增），即"新增行数 ≤ 2 且删除行数 ≤ 1"。用 `git diff --numstat HEAD -- relative_path`（此刻 HEAD 就是我们自己刚 `_commit` 出来的那个本地提交，尚未被 reset）与"上一次已知的干净基线"比较行数量级即可判定，不需要理解语义、不需要解析队列表格结构，复杂度低、误判面窄。

### 决策点 2：护栏命中时的降级路径——复用 #286 统一后的暂存通道，不新增第三个暂存文件

护栏命中（判定磁盘有外来内容）时，本函数：
1. **不执行** `reset`/`checkout`（工作区原样保留，外来内容不受影响）。
2. 也**不**保留自己那个已经"污染"了外来内容的本地 commit（`git reset --soft HEAD~1` 撤销这个 commit 但不touch工作区——工作区此刻仍是"外来内容 + 我们插入的行"混合状态，commit 被撤销后这个混合内容变回未提交状态，与它进入本函数之前的磁盘状态完全一致，只是多了我们刚才插入的那一行，这一行本来就该留在磁盘上等人工/sweep 处理）。
3. 记录降级 audit 事件（复用 `queue_sync_degraded` 事件形状，新增 `reason="foreign_dirty_content_detected"` 区分于其它降级原因）+ 写入 #286 统一后的暂存文件（供人工核对："这条追加因磁盘有其它未提交内容而跳过了自动 git 同步，行本身已经在磁盘上，需要人工确认后续由谁提交"）。
4. 私信降级告警——文案说明"检测到队列文件有其它未提交内容，为避免覆盖已跳过自动同步，该行已在磁盘、需人工核对"，不同于现有"网络/冲突失败"文案，避免人工误判成同一类问题去重试推送（重试推送不会解决"磁盘有外来内容"这个问题，只有人工确认后手工处理才行）。

不新增独立的第三个暂存文件——直接并入 #286 已经在做的"统一 flush 通道"改造（`pending_queue_appends.jsonl` 覆盖两类失败），护栏命中算作这类失败里的一个新 `reason`，复用同一份 schema 与同一条 flush 逻辑，避免重蹈 #286 本身的覆辙（"同一种失败从两个不同层抛出，只有一层的暂存会被补录"）。

### 决策点 3：阈值怎么定——"新增行数 ≤ 2 且删除行数 ≤ 1"，超出即判定异常，不做更精细的语义解析

考虑过更"聪明"的做法（解析队列表格结构，比对"预期插入的具体那一行"是否精确等于 diff 里唯一新增的行）——否决，理由：
- 语义解析引入了新的失败面（表格格式漂移、`_bump_section_one_high_water_mark` 未来若变化都要求这里的校验逻辑同步跟进），而单纯的行数量级判断天然对格式变化免疫。
- 本场景要防的是"大规模外来内容混入"（人类一次编辑锁窗口通常涉及多行新增/修改，如本次事故的"8 行修改＋4 行新增"），量级判断的区分度已经足够；不追求对"人类同一时刻恰好也只改了 1-2 行"这种边界情况的精确识别——design 认为这种边界情况即便偶尔护栏误判为"正常"而走了旧逻辑，也不改变现状（现状本来就是无护栏），不构成回退。
- 阈值写成模块级常量（如 `MAX_EXPECTED_DIFF_LINES = 2`），不做成可配置项——可配置项本身是未来又一个"没人记得调"的人守面，且本场景没有合理的多套阈值需求。

### 决策点 4：与 #286「归档件数↔队列行数对账」判据的关系——互补，不是同一层

#286 的对账判据（归档 `.md` 文件数 vs 队列可见行数）是**事后审计**——发现"应该有但没有"的行，但发现时数据可能已经丢了分钟到小时级。本变更的护栏是**事前拦截**——在销毁性操作真正执行前挡住它，护栏命中时数据从未离开磁盘。两者不是二选一，是纵深防御的两层：护栏挡住本次事故这一类"机器人自己动手抹掉"的路径；对账判据继续兜底护栏覆盖不到的其它丢失模式（如磁盘本身故障、其它未预见的并发写手）。

## Risks / Trade-offs

- **[风险] 护栏基于行数量级判断，理论上存在"人类恰好也只改了 1-2 行"时护栏误判为安全从而仍执行 reset/checkout** → 影响有限：这与现状（完全无护栏）相比不是回退，只是护栏没有 100% 覆盖率；`append_pending_task` 本身的乐观并发重试机制（写入前重读比对）仍是另一层独立保护，覆盖的是"机器人自己内部" append 的并发安全，与本护栏针对的"外部第三方内容"是两个不同的保护对象，互不替代但也互不冲突。
- **[风险] 护栏命中后本地 commit 被 `reset --soft` 撤销，若这一步本身失败（极小概率的 git 异常）** → 缓解：外层 `sync_after_archive` 已有通用 `except Exception` 兜底（记 `queue_sync_degraded`+暂存+告警），本护栏的异常路径不需要另建一套兜底，天然被现有异常处理覆盖。
- **[权衡] 护栏命中时这次追加的"自动同步"能力被放弃，退化为需要人工确认** → 可接受：这正是"止血优先于自动化"的取舍——参照 #288 决策点 2"对少数真实冲突情形不强求自动打破循环，退化为止血也不劣于现状"的同一哲学，本变更命中护栏的场景在协议〇.7/〇.8 常态下本就应当是低频事件（编辑锁窗口与机器人处理消息的时间窗口重叠、且恰好这条消息还撞上非快进冲突，三个条件同时满足）。

## Migration Plan

不涉及数据迁移或状态 schema 变化（暂存文件 schema 变化交由 #286 的实现处理，本变更只新增一个 `reason` 字段值）。部署方式：代码合入 `master` 后，`ops/wecom-service-home` 常驻服务下次重启（或按既有惯例的下一次同步+重启流程）生效，无需数据迁移。

回滚：`git revert` 即可，护栏是纯新增的前置检查，回滚不影响任何已推送的历史内容。
