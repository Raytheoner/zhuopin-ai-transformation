# queue-status-machine-field Proposal

## Why

`跨桌任务队列.md` §一（任务看板）的状态语义**完全靠自然语言承载**——状态列动辄 800-2000 字富文本，"当前结论到底是什么"只能靠正则猜中文。2026-08-08 环境总线实测四组数据坐实这不是感觉，是事实：

- §一 现存 **机制/环境类 : 业务场景类 ＝ 86 : 20（81%）**，未收口 **19 : 9** 倒挂；
- **2026-08-07／08-08 两天新建行 机制 12 ／ 业务 0**；
- 守护这一个 Markdown 表格的工具代码合计 **4822 行**（sweep 2292＋编辑锁 1479＋队列查询 203＋台账 242＋载体扫描 169＋worktree扫描 169＋安全同步 130＋定时备份 138），且只增不减；
- 队列 #248（开头片段锚定）、#302（commit scope 主判据＋触碰区路径副判据）、#304（首标记冒领）、#306（队列表格七份各自独立的解析实现）以及 2026-08-08 CLI 首跑暴露的第四个误报源（commit scope 带行号 ≠ 该行已完成）**全部是同一个源头的衍生物**——以往每次只能局部修，是因为每次都在修某一个衍生物，源头（状态语义靠自然语言承载）从未被动过。

同一根问题还派生出三类相邻缺口，Shao Peishen 2026-08-08 已拍板将其一并纳入本次治理（"措施 A＋B＋C 全采纳"）：

1. **守卫代码本身没有退休制**——CLAUDE.md §5 规则退休制只管人守规则，4822 行守卫代码只增不减不可持续（措施 B）。
2. **机制类未收口 WIP 上限（协议〇.9 措施 C，＝8）的分母目前部分靠人工核定**——排除类别②"依赖外部方"刻意未造关键词判据，协议正文明写"改为并入 #308 的字段设计"（措施 C）。
3. **告警只报出现、不报解除**——sweep 现有 8 类 webhook 告警中只有"孤儿脏文件"一类（#301）有"✅ 已解除"通知，2026-08-08 两个实证（分叉早已解除但连发两轮告警；`fi2-recon-mvp`/`wecom-aibot-channel` 已被 #299 逐项判定为真实未完工却仍每 24 小时重复告警"疑似遗忘归档"）证明这是同族缺陷，不是单点（子项 D）。

此外，2026-08-08 承载性核查第三批发现两处"规则已入法、载体未跟上"的具体缺口，均落在同一把编辑锁咽喉上，一并并入本行（协议〇.10 并入优先，不另立行）：

4. **子项 F**：§二 批次行状态列缺少"新增即终态"式的结构性拦截——2026-07-28 两批（`B-0728财务专线核实`/`B-0728队列#125回填`）曾因登记时直接写 `✅` 被 sweep 判为已处理、内容石沉大海；2026-08-03 一次性抓出 6 行"行尾写完成、开头仍待领"的头尾不一致。
5. **子项 G**：跟进信串行原则（Shao Peishen 2026-08-03 定，优先于一切触发点规则）此前完全靠人记"回件消化完记得把 README 该行改为 `📥 已回件并回灌 <日期>`"——2026-08-08 承载性核查指出这正是本次治理反复批评的形态（判据存在但只能靠人记），不应自己再制造一个同类缺口。

## What Changes

- **状态机器字段（措施 A，主体）**：§一 状态列**开头**新增定长机器字段 `[S:<value>]`，取值集合 `done`／`open`／`partial`／`hold`／`blocked`（受外部阻塞）／`timed=YYYY-MM-DD`；字段之后的自然语言正文**一字不改，完全自由**。全部判据改为只读该字段，不再解析中文。存量 106 行（现存 §一 全部行）随本变更一次性回填。
- **域字段（同批增设，design 决策点定案）**：状态字段旁并列新增 `[D:机]`／`[D:业]` 域字段，在 `acquire --reserve` 取号时随并入审核门禁一并声明；供协议〇.9 措施 C 的"机制类可动 WIP"计数与看板按域独立统计使用，替代当前的关键词猜测判据。域字段本身不预设"是否分双队列文件"（P4，见 design.md 支撑论证三），本次只交付可逆的字段层。
- **措施 B（守卫 one-in-one-out）**：`openspec/config.yaml` 的 `rules.proposal` 新增一条：新增机制类变更包 MUST 回答"本次退休哪一个既有守卫；若不能退，写明为何不能"。不写成人守条目。
- **措施 C（机制类未收口 WIP 上限提示）**：`工具-共享文档编辑锁.py::release` 在新增 §一 机制类行导致可动 WIP 计数超过上限（8）时打印提示，不阻断释放。
- **子项 D（告警生命周期通用化）**：抽取 `_track_and_alert_orphan_paths`（#301）已验证的"出现→告警／消失→解除通知"骨架为通用函数，retrofit 到分叉告警（#171）、场景 spec 缺口告警（#298 M1）、在途变更包滞留告警（#298 M2）；对"疑似遗忘归档"一类判断型（非事实型）告警新增指纹抑制（记录判定时的未完成项数＋最后改动时间，指纹未变即静默，变了才重新告警）。
- **子项 E**：E1（"被标红的行其实不是 open 态"这一误报源）由状态机器字段落地自动消解，不需任何额外代码；E2（"真 `[S:open]` 行被 commit scope 顺带提及"这一误报源）**缺真实数据支撑，本次不做**，留 Open Questions，待观察几轮真实标红数据后再决定。
- **子项 F（编辑锁 release 结构校验新增两项）**：F1——§二 新增批次行状态列不得以 `✅` 开头（只拦新增行，既有行合法转 `✅` 不受影响）；F2——状态列含 `✅` 但不在开头片段即报（§一／§二 均适用，直接复用既有 `_leading_status_segment()`）。
- **子项 G（跟进信串行原则挪入编辑锁咽喉）**：`_validate_followup_readme_release` 新增校验——本次持锁窗口内新增某收信人的跟进信登记行时，回查该收信人此前最近一行的发送状态；若仍属非闭环态（`⏳ 待你审`／`🆕 待发`／`⏸ 暂缓`／`✅ 已推送 …`）即拒绝 release，除非新行内显式写明 `串行豁免：〈理由〉`（逃生阀，放行并留痕）。
- **同批收口/缩范围**：#304（首标记冒领）随措施 A 落地自动消解，不再单独处置；#306（队列表格七份解析实现）范围收窄为"读一份定长字段"，降 P3，其 design 审并入本变更（不再单独占一次 design 审）；#307 并入 #306，不单独立行。**⇒ 4 行 → 2 行（本行 ＋ #305），且省下 #306 原本需要的一次 design 审。**
- **BREAKING**：无——状态字段是新增的前缀，既有消费者在切换前仍按旧的自然语言关键词解析全文（字段本身不影响正文可读性）；`_validate_release_structure`/`_validate_followup_readme_release` 新增校验只对本次持锁期间新增/修改的行生效，历史行不追溯。

## Capabilities

### New Capabilities

- `queue-row-status-field`：跨桌任务队列 §一 状态列机器可读字段的语法、取值集合、位置约束、向后兼容降级规则。
- `queue-row-domain-field`：§一 行"域"（机制/业务/受外部阻塞）字段的语法、声明时机（`acquire --reserve`）、与协议〇.9 措施 C 可动 WIP 计数的消费契约。
- `editlock-mechanism-wip-guard`：编辑锁 release 时对新增 §一 机制类行做可动 WIP 上限提示（不阻断）的行为契约。
- `editlock-section-leading-status-guard`：编辑锁 release 对 §一/§二 状态列"✅ 是否在开头片段"及"§二 新增批次行是否以 ✅ 开头"的结构性拦截契约（子项 F1/F2）。
- `sweep-alert-lifecycle-guard`：sweep 8 类 webhook 告警中"标准长期存在状态类"告警（分叉/孤儿脏文件/场景 spec 缺口/在途变更包滞留）的出现→告警/消失→解除通用骨架，以及判断型告警的指纹抑制机制。

### Modified Capabilities

- `wecom-followup-review-state`：新增一条 Requirement——结构性拦截违反跟进信串行原则的新增登记行（子项 G），带 `串行豁免：〈理由〉` 逃生阀。既有六条 Requirement（两态语义、批准路径、冷却窗口、硬截止排除、authorship-agnostic）不变。

（`sweep-batch-status-classification`／`editlock-assertion-gate-scope`：本变更不改变这两个既有 capability 描述的判定结果——§二 的"待/✅"二元判据与 ④ 断言门槛的引号剔除逻辑均维持不变，只是编辑锁在其基础上新增 F1/F2 两项独立校验（见 `editlock-section-leading-status-guard`），故不在此处列为 Modified。措施 B 落点是 `openspec/config.yaml` 的 `rules.proposal` 字段——工具链/机制配置，非产品 capability，同 2026-08-02 `openspec-config-proposal-rules` 变更的既有处理惯例，不单独建 capability。）

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？**
   - "一条 §一 行当前到底是 open／done／partial／hold／blocked 哪个状态"此前完全是人脑默会——写行的人心里清楚，但从未被要求显式声明，所有下游判据（sweep/编辑锁/队列查询/台账/看板）都在用正则猜测这个默会判断。
   - "这条行是机制类还是业务类"同理：建行的人当下就知道，当前的 86:20 分类靠事后关键词计数近似。
   - "一次告警是否已经不再成立"——目前只有孤儿脏文件一类沉淀了"何时该说已解除"的默会经验（#301），其余 7 类告警的"何时该闭嘴"仍在人脑里，靠人主动去查证。
   - "跟进信是否已回件并回灌、可以起草下一封"——2026-08-03 立规到本次之前，完全靠人记住去查 README 再动笔，没有任何强制。
   - "字段回填时新旧判断不一致该信谁"——采用一次性迁移的通用经验（启发式初筛 ＋ 人工复核兜底可接受，长期运行的判据用启发式则是本变更要根治的病，design.md 已明确写出这条区分）。
2. **由谁显性化？** 持有人：**Shao Peishen**（本变更所有 Decisions 的拍板人，已就措施 A/B/C 明确"全部按默认"，域字段决策点见 design.md 待其审核）；backup：**Claude Code（CC）**——负责字段语法落地、106 行回填脚本化＋人工复核抽样、七处消费者切换与各自回归、以及后续接手本变更 design.md 的任何一位 CC session（design.md 记录完整取舍依据，无需重新论证已否决的候选）。
3. **用什么方法提取？** **历史案例反推**——字段取值集合与校验形态均来自 #248/#302/#304/#306/#301/#150/#248(F 前身)/#294 等一系列真实事故的共同根因倒推，不是预先设计；106 行存量回填**同时用历史案例反推校准初筛判据**（回填时对照现存行的人工既有判断，逐条核对分歧）。不涉及 LLM 判断、L2 改判判例累积（本变更是纯结构化字段与规则匹配，不含运行时 LLM 推理）。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：本变更是跨项目治理机制（编辑锁/sweep/队列文件是全项目共用的写入与判读咽喉），非独立业务场景，四档口径不直接套用产品语义。近似映射：**档1 mock 验证**（design 审通过、字段语法定案、106 行回填完成、七处消费者中优先级最高的若干处已切换并通过回归，尚未经过至少一次真实并发写入场景+至少一次真实告警解除通知的端到端观察）。
- **晋下一档的条件**（晋**档2 真实数据跑通**）：① 106 行回填后，`--check-*` 一类只读核验工具对新旧判据的分歧行清零或逐条有人工结论；② 七处消费者全部切换完成且各自既有回归套件零漂移；③ 至少观察到一次真实的"机制类新增行超过 WIP 上限"提示与一次真实的"跟进信串行豁免"或"跟进信串行拦截"事件；④ 至少一类被 retrofit 的告警（分叉/spec 缺口/在途包滞留）真实经历一次"出现→解除"全周期并收到"✅ 已解除"通知。
- **价值指标**（风险型为主）：⑴ 消除"状态语义靠正则猜中文"导致的系统性误报——基线＝#248/#302/#304/#306 四个已知衍生 bug 家族＋2026-08-08 CLI 首跑第四个误报源，目标＝本变更范围内四个家族全部关闭或降级为"读一个定长字段"；⑵ 跟进信串行原则违规发送——基线＝2026-08-06 01:30 UTC 一次真实误发（#150），目标＝新增行 100% 经过结构性校验，无法再绕开锁直接产出违规行；⑶ 告警"狼来了"信任损耗——基线＝分叉/在途包滞留两类告警 2026-08-08 均出现"早已解除仍在告警"的真实实例，目标＝这两类纳入 D1 骨架后具备解除通知能力。
- **LLM 判据黄金集**：不适用（本变更不含 LLM 运行时判断，纯字符串/结构化字段匹配与状态机逻辑）。
