# 齐料日期按答交数量累计取值（SC8 保供看板 · 队列 #344）

## Why

姚祖怡（采购部 AI 专员）2026-08-12 采购部#13 回件举证：`F02N.0224` 看板显示齐料 **2026-11-18**，他核定的正确值是 **2026-12-25**，瓶颈物料 `R01I.0622`。#266/#118 建造 session 按派单要求（「同根因就一并修，不同根因就单独登记，不许含糊带过」）做了实测定性，结论是**不同根因**，故 2026-08-18 单独立队列行 `#344`。

**缺陷一句话**：看板上方的**齐料日期**与**瓶颈物料**，取的是该物料**最早的那一笔答交日期**，**完全不看那一笔答交了多少数量——连答交数量为 0 的记录也照用**。

**取证（2026-08-18 当日真实取数，非推断）**：`R01I.0622` 的逐笔看板承诺是 `2026-08-20 qty=0` ／ `09-20 qty=0` ／ `10-20 qty=0` ／ `11-20 qty=0` ／ `12-20 qty=0` ／ `2027-01-20 qty=0` ／ `02-20 qty=0` ／ **`2027-05-20 qty=10000`** ／ `06-20 qty=0`——**唯一有数量的一笔在 2027-05-20，而引擎实际采用的是 2026-08-20 那笔数量为 0 的记录**。

**根因两处同源，都在「只问日期不问数量」**：

1. `sc8/sources.py::load_srm_deliveries` 合并时 `committed = min(auth_dates)` 取最早，且构造 `SrmDeliveryOrder(qty_committed=0)`——**数量在这条链路上根本没被带出来**。
2. `sc8/forecast.py::estimate_material_arrivals` 的 `srm_index` 同样只留最早日期（`committed < srm_index[...]` 即覆盖）。

⇒ 齐料日 `kit_date = max(arrivals)`、瓶颈物料、四色缺口天数**全部**建立在「最早日期、不问数量」之上。

**为什么他一直感觉「下面的清单是对的、上面的汇总数不对」**：看板下方 BOM 缺口物料清单走 `_cumulative_confirmed_batches`（**按数量累计至覆盖缺口**，即他 2026-07-28 亲自定的 #18-a 口径，**是对的**），而上方齐料日期/瓶颈**不走它**。这是 #262／#296 那一族「汇总数与明细清单口径不一致」的又一处落点。

**与 #266 的分层区别（不可混为一谈）**：#266 在 **BOM 展开深度**那一层（只看第一层子件，已于 2026-08-18 修复上线）；本变更在 **答交数量匹配**那一层。两者可各自独立复现。

- **`_cumulative_confirmed_batches` 由 `sc8/baoguan.py` 下沉到 `sc8/forecast.py`**，`baoguan.py` 改为 `from .forecast import _cumulative_confirmed_batches` 再导出。**一份实现、两处使用**——上方齐料日与下方缺口清单从此不可能漂移。`sc8/material_board.py` 与既有单测的 `from .baoguan import _cumulative_confirmed_batches` 导入路径**保持可用、零改动**。
- **`sc8/baoguan.py::assess_supply_risk`**：把 `gross = _gross_need(...)` 提到 `estimate_material_arrivals` 之前，算出**逐料累计目标数量** `required_qty`（净额开关 ON 且有 inventory ⇒ 缺口数量 `gross − 现货`；否则 ⇒ 毛需求 `gross`，与 `_component_supply_status` 的 #211 v2 口径逐字一致），连同 `material_commitments` 一并传入。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？** 三处：① **「齐料」到底指哪一天**——采购员心里的答案从来是「够用的那批货到的那天」，而不是「供应商第一次回话的那天」；这条从未被写下来过，因为对人来说它太显然了。② **累计目标数量取哪一个**——毛需求还是扣掉现货后的缺口；姚祖怡 2026-08-03（#211 v2）口头给过「累计至满足**缺口数量**」，但当时只约束了下方清单。③ **答交数量为 0 意味着什么**——是「供应商说了这批给 0」还是「等于没说」；他 2026-08-19 才第一次书面给出答案（等同没说、走规则 2）。
2. **由谁显性化？** 持有人 ＝ **姚祖怡**（采购部 AI 专员，判定权威单点）；backup ＝ **解植雅 ＋ 汤易水**（采购域一线标注层，已确认在位，可先批量初标）。
3. **用什么方法提取？** **L2 改判判例累积**——判例批改法（≤10 条真实案例「现状判定 vs 拟改判定」对照，专员只做 ✅/❌/✏️），规则条文由专线从判例反推、回发一行请其确认。本次 3 条判例已全部签认，规则条文即上表四条。🔴 **已知瑕疵留痕**：判例 2 的需求量与判例 3 整条是假设数（违反「判例包不得使用虚构数据」），Shao Peishen 已答 (c) 认定签认有效、补事后佐证而不重问——佐证即本变更包的 `scripts/find_cumulative_evidence.py` 产物。
