## 决策点 1：路由判据 —— 来源群优先，还是发送人部门优先？

**已定（Shao Peishen 2026-08-24 当场确认，非本 session 自拟）**：**来源群优先。**

原话：「「回执按来源群回」才是主修法：陈承那条 @ 发在财务部群，就算 IT 群配好了，回执还是会跑到 IT 群去。两件都要做。」

**判据形式化**：

```
if chattype == "group" and chatid:   → 回 chatid（route=source_group）
else:                                 → 回 发送人部门群（route=sender_department，判据一字未改）
```

**为什么是这个方向**：来源群是入站帧给出的**事实**；「发送人属哪个部门 → 那个部门的群在哪」是**推断链**。#387 正是那条推断链给出了一个语法上完全合法、语义上完全错误的目的地——而它不报错。**事实可用时不退回推断链**，这是本包的中心取舍。

## 决策点 2：群消息路径要不要仍受 `matched` 门槛约束？

**取 (b) 不受约束**（本 session 判定，待审）。

- **(a) 仍受约束**：未命中部门的发送人在群里发言 ⇒ 照旧 `sender_unmatched` 跳过。代价＝**保留一处「事实可用却仍被推断结论否掉」的矛盾**；且 `ShaoPeiShen` 本人在群里采集 chatid 时收不到任何回执，而队列 `#387` ⑵ 明确要求「发第一条回执时对着群里看一眼」来反查那个 chatid——(a) 会让那次反查没有凭据。
- **(b) 不受约束**（选定）：群消息一律回原群。代价＝**一处行为扩面**，`ShaoPeiShen` 在群里发的测试消息此后会收到「已归档」回执。

**选 (b) 的理由**：`sender_unmatched` 跳过的原始理由是「没有对应的真实部门群可发，也不该猜」——**这条理由在回原群路径上不成立**。让一条不成立的理由继续拦着，就是把当初的措辞当成了判据本身。

⚠️ **扩面已用专门用例锁住**（`test_group_message_from_unmatched_sender_still_replies`），不是悄悄发生的。

## 决策点 3：哪些跳过发告警？

**取 (b) 只对「配置缺口」类告警**（本 session 判定，待审）。

- **(a) 全部跳过都告警**：代价＝`sender_unmatched` 每次都响。而它本就是设计内的 fail-closed 常态，响多了整条告警通道贬值——**本包另一半正是在治「告警太少」，一起做过头会把它做回噪音**。
- **(b) 只 `group_not_configured` / `group_webhook_not_configured` 告警**（选定）：这两类的共同特征是**本该配却没配、且除审计里一行谁也不看的记录之外没有任何外部信号**。
- **(c) 不告警、改为启动时校验映射表完整性**：代价＝「完整」需要一份「应该有哪些部门」的清单，而那份清单本身就是要维护的第二真源；且销售部**故意**不配，清单会把有意的空缺报成缺陷。

**判据可复用**：`ALERTABLE_SKIP_REASONS` 是模块级常量，新增 reason 时**必须显式决定它属不属于这一类**，而不是默认继承。

## 决策点 4：告警走哪条通道？

**复用既有独立 webhook 兜底通道**（`WECOM_WEBHOOK_URL`，`build_connector` 新增 `group_notify_alert_fallback_send`），与 `gap_alert` / `disconnect` / `queue_edit_lock` 三处同一范式。

**为什么不用机器人自身长连接发**：与 `gap_alert.py` 2026-07-19 事故同一教训——告警的通道不该与被告警的通道是同一条。虽然本条告警的触发条件与连接健康无关，但**范式一致比逐条论证更不容易出错**。

未配置时 `alert_send=None`，功能整体关闭、只留审计，行为与改动前一致。

## 决策点 5：`IT` 的队列 owner 取什么值？

**取 `业务总线`**（本 session 判定，待审）。

- **(a) `IT专线`**：❌ 本项目**没有这个角色**。`whitelist.py` 顶部原文即「不臆造一个不存在的『IT专线』角色」。造一个会让队列里出现一个永远没人认领的 owner。
- **(b) 保持 `Paul` 回落**：❌ 就是 `#387` ⑷ 要修的缺陷本身——与「完全未命中」共用同一个值，两种完全不同的状态在队列里长得一模一样。
- **(c) `业务总线`**（选定）：陈承两次来件（`#385`／`#386`）**实际就是由业务总线拆件派发的**，且 `业务总线` 是队列里既有的合法 owner 取值。**取一个与事实相符的既有值，不新造。**

⚠️ **本决策点范围外、如实登记**：机器人追加的队列行**一律 `[域未标注]`**（`queue_appender` 刻意不写 `[D:...]`，原注释：「机器人无法判定机制/业务归属，交人工事后补」）。`#387` ⑷ 把「owner 落 Paul」与「域未标注」并列描述，但**后者不是 IT 特有的**，是所有机器人追加行的共同属性，且「按什么判机制/业务」是一条跨场景口径——不在本包范围内，未动。

## 决策点 6：`queue_append_skipped` 为什么不复用 `queue_append_deferred`？

**取 (a) 新增独立字段**（本 session 判定，待审）。

- **(a) 新增 `queue_append_skipped`**（选定）：语义是「这一行**本就不该存在**」。
- **(b) 复用 `queue_append_deferred=True`**：❌ 那个字段的语义是「这一行**还欠着，等下次补录**」。复用会让 `flush_pending_queue_appends` 这条补录链路去补一条永远不该补的行——**而补录链路是不看理由的，它只看有没有欠账**。

两个字段在 `connection.py` 里都导致「跳过 git 同步」，但**同一个后果不等于同一个原因**，合并会在下一次有人读这段代码时把两种状态弄混。

## 决策点 7：补录幂等按什么字段判重？

**取 `input_pointer`**（本 session 判定，待审）。

- **(a) `input_pointer`**（选定）：归档文件的仓库相对路径，含 msgid 消歧后缀（`intake._build_filename`）⇒ **对每一条来件唯一**。
- **(b) 按行编号**：❌ 补录时编号本来就要重算，重算前没有编号可比。
- **(c) 按 description 文本**：❌ 同一发送人同类消息的描述文本完全相同，会把两条真实不同的来件判成重复。

🔴 **扫描范围＝全部物理队列文件**（`queue_table.iter_queue_paths()`），不只扫写入侧那一份：`#315` 拆成两份后，行可能被人工挪进另一份；只扫一份会把「已挪走的行」误判为不存在，于是补出第二条——**正是「一份拆成两份、下游只跟了一份」那个家族的又一个入口**（`#312` 缺口一同形）。

⚠️ **读不到文件时 fail-open**（当作没找到、照常补录）：本函数只是一道去重网，不能因为一个读不到的文件把整条补录链路卡死。**这一侧与本包其余部分的 fail-closed 取向相反，是刻意的**——去重网 fail-closed 的代价是丢行，比补重行严重。
