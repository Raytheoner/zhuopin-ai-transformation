# env-anchor-collapse Design

> 🔴 **本文件是待审件。本次只 propose，不 apply。**
> 六个决策点。**决策点 1 与 4 无默认项**（见各自末尾说明）；其余四点给出推荐与默认项（不答即按默认执行）。

## Context

事实基础见 proposal.md。一句话：**「仓库根在哪」本仓库已有三套答案，读凭据的那一套用的是最差的一套，而这个 bug 类已经被解决过两次、结论没有传过来。**

已确认的生产缺陷（`run_baoguan_dashboard.py` 在 `.51` 上从未可用）**不在本包范围**，已于 2026-08-24 单独修完并真机验证（commit `b7bc8bc`）。

### 三种布局，各自的正确答案并不相同

| | 开发机主工作区 | 开发机 linked worktree | `.51` 扁平部署 |
|---|---|---|---|
| 脚本位置 | `<repo>/4-数字员工/<域>/<场景>/scripts/` | `<repo>/.claude/worktrees/<n>/4-数字员工/…` | `C:/<svc>/app/scripts/` |
| marker `5-平台底座/zhuopin_platform` | ✅ 在 `<repo>` | 🔴 **✅ 也在 `<n>`（实测）** | ❌ 不存在 |
| 该读哪份 `.env` | `<repo>/.env` | **`<repo>/.env`**（凭据唯一） | `C:/<svc>/.env` |
| 有 git 吗 | ✅ | ✅ | ❌ **没有** |

🔑 **第二列那个 ✅ 是本设计最反直觉的一格**，也是 #354 行内建议（「向上找仓库根标记再取其 `.env`」）**按字面实现会失效**的原因：worktree 是完整 checkout，marker 在里面。

🔑 **第四列那个 ❌ 同样要紧**：`.51` 上没有 git，所以任何依赖 `git rev-parse` 的方案**必须能在无 git 时优雅退化**，不能把生产入口钉死在一个开发机才有的工具上。

### 代码要就近，凭据要唯一 —— 两者方向相反，这是本设计的主轴

`ensure_paths()`（#345）刻意取**最内层** marker：每份 worktree 必须测自己的代码（#300 原语义）。
`.env` 恰恰相反：**同时只该有一份权威凭据**，worktree 里那份陈旧副本就是 #354 的病灶。

**⇒ 不能把 `.env` 解析塞进 `ensure_paths()` 复用它的查找逻辑**——看起来像复用，语义正好相反。这也是 #345 design 决策点 5 把 `.env` 列为 Non-Goal 的原因；本包接手的正是那一半。

## Goals / Non-Goals

**Goals**
- 一处定义、一处修复；新入口不可能再手抄出第 10 种语义
- 三种布局由同一实现覆盖，且 **worktree 与主工作区解出同一份凭据**
- 「本次用了哪份 `.env`」可被回报、可被审计（当前 9 个入口里只有 1 个会说）
- 无 git 环境（`.51`）下正常工作，不引入新的硬依赖

**Non-Goals**
- 不改 `ensure_paths()` 的 `sys.path` 语义（#300/#345 既定，就近优先，不动）
- 不合并 `5-平台底座/.env` 到仓库根（服务级作用域是刻意的，见决策点 1）
- 不碰 `0-学习与工具/` 下的工具族（`工具-引导样板lint.py` docstring 明写「刻意不覆盖」，范围克制照旧）
- 不做凭据加密/Vault 化（独立 backlog，与本包无关）
- 不修改任何 `.env` 文件本身（见文末「顺带发现」）

## 决策点

### 决策点 1 · `.env` 有没有"作用域"这回事？

这是本包的**前置问题**，其余决策点都建立在它的答案上。主工作区现存三份真实 `.env`（实测，只比键名未读值）：

| 文件 | 键数 | 性质 |
|---|---|---|
| `<repo>/.env` | 19 | 全项目凭据（XKY／FO／U9C／STOCK／两个企微 webhook） |
| `5-平台底座/.env` | 6 | 企微机器人服务专属，**7 个脚本显式 `load_dotenv(SERVICE_DIR.parent/".env")` 指名要它** |
| `4-数字员工/采购部/SC1-供应商风险初筛/.env` | 6 | 🔴 **性质未明**——含 `DEEPSEEK_API_KEY`（根 `.env` 没有）＋ **5 个 `XKY_*` 与根 `.env` 同名** |

- **(a) 承认作用域**：`.env` 分「服务级」与「仓库级」，解析时**先找作用域根、找不到再找仓库根**，两层合并（近的优先）。
  - *得*：`5-平台底座/.env` 与 SC1 的用法都被正当化，不必搬动任何现存文件。
  - *失*：**"作用域根"要怎么判定？** 一旦答不出，就退化成"最近的那份"，即今天的病本身。
- **(b) 否认作用域，统一到部署根**：只认一份，`5-平台底座/.env` 的 6 个键并入仓库根，SC1 的并入或删除。
  - *得*：语义最简单，`#354` 的病根除得最干净。
  - *失*：**要动 3 个 gitignore 凭据文件与 7 个在跑的脚本**，其中 `wecom-aibot-service` 是常驻服务；改错即企微机器人停摆（07-16 已有 24h49m 停摆前科）。
- **(c) 承认作用域但把它显式化**：作用域**不靠目录距离猜**，由调用方在代码里**指名**（如 `load_env(scope="platform")` / 默认 `scope=None` ＝ 仓库根）。
  - *得*：`5-平台底座/.env` 的用法从"碰巧最近"变成"显式声明"；**"最近的那份"这个隐式规则被彻底删掉**，SC1 那份除非被指名、否则永远不会被误命中。
  - *失*：每个入口要多写一个参数（但那正是让它可被 lint 检查的东西）。

**推荐 (c)。**

> 🔴 **本项无默认项。** 判据（CLAUDE.md §5「默认项两前提」）：② 这一项若不答，代价不是"停在原地"——**SC1 那份 `.env` 与根 `.env` 的 5 个 `XKY_*` 同名键会继续处于"谁先被找到谁生效"的状态**，属正在出血的口子，不得用默认项背书。且本项依赖一个**只有 Shao Peishen 能回答的事实**：**SC1 那份 `.env` 是刻意的服务级配置，还是早期遗留的历史副本？** 答案决定 (a)/(b)/(c) 的取舍，`git log` 查不出意图。

### 决策点 2 · worktree 里跑，凭据取谁的？

前提：marker 搜索**解决不了**这个问题（worktree 里有 marker）。三个选项：

- **(a) 沿用 C 家族已验证的 `--git-common-dir` 规范化（推荐 ✅ 默认项）**：`git -C <anchor> rev-parse --path-format=absolute --git-common-dir` → 取其父目录 ＝ 所有 linked worktree 共享的那个主工作区根。**这是 `repo_paths.py::resolve_default_queue_anchor`（#269）与 `工具-共享文档编辑锁.py::_resolve_repo_root`（2026-07-23）已经跑了两个多月的同一段逻辑。**
  - *得*：不发明新东西；worktree 与主工作区**必然**解出同一份凭据；普通 clone（非 worktree）下 `--git-common-dir` 的父目录就是 clone 自己，**行为不变**。
  - *失*：要起一个 `git` 子进程。`.51` 没有 git ⇒ **必须配无 git 的退化路径**（决策点 3 承接）。启动开销约几十毫秒，对 CLI 与常驻服务启动均可忽略。
- **(b) 取"最外层含 marker 的祖先"**：从脚本向上收集所有含 marker 的目录，取最高的那个。因为 `.claude/worktrees/<n>/` 物理上在主工作区内，最外层就是主工作区。
  - *得*：纯路径运算，零依赖，`.51` 上也能跑。
  - *失*：**只在"worktree 恰好放在主工作区内部"时成立**。`git worktree add` 允许放在任何地方，这条假设一旦被破坏就静默失效——**又是一个"错误不产生任何信号"的判据**，正是本包要根除的形态。**不推荐。**
- **(c) 强制显式环境变量 `ZP_ENV_FILE`，不做任何自动解析**：
  - *得*：绝对确定。*失*：**忘了设就退化回今天的状态**，而"忘了设"没有任何信号。作为**覆盖入口**很好（推荐保留），作为**唯一入口**不行。

**推荐 (a)，并保留 (c) 作为显式覆盖（`ZP_ENV_FILE` 优先级最高）。默认项：(a)+(c)。**

### 决策点 3 · 无 git、无 marker 时怎么退化？

`.51` 上两者都没有（扁平布局 `C:/<svc>/{app,zhuopin_platform,.env}`）。

- **(a) 第二锚点：找"含 `zhuopin_platform` 子目录"的祖先（推荐 ✅ 默认项）**：即扁平部署根 `C:/<svc>/`，其下就是 `.env`。**实测确认该布局属实**：`.51` 上 `C:/baoguan/` 含 `.env`／`app`／`zhuopin_platform`／`.venv`／`deploy-tools`（2026-08-24 ssh 实跑 `Get-ChildItem`）。
  - *得*：锚点仍然是"部署根"这个**结构性事实**，不是"哪儿有 `.env` 就用哪儿"这个巧合。
  - *失*：多一条分支要维护。
- **(b) 退化回"最近的 `.env`"**：*失*：把病根留了一个后门；且这个后门**恰好在最难验证的生产环境上生效**。**不推荐。**
- **(c) 无 git 无 marker 即 fail-loud**：*失*：`.51` 上直接起不来，等于 #345 A 形态重演。**不可行。**

**推荐 (a)。默认项：(a)。**

### 决策点 4 · 找不到任何 `.env` 时，报错还是静默？

现存三种态度，无一处写明理由：8 份静默 `return`、`build_golden_real.py` `SystemExit`、`verify_material_board_real.py` 打印后继续。

- **(a) 一律静默**：*得*：兼容"凭据由服务环境/计划任务直接注入"的情形（`.51` 常驻服务确有此可能）。*失*：**保留今天的失败形态**。
- **(b) 一律 fail-loud**：*得*：最诚实。*失*：**会打挂那些本来就靠环境变量注入凭据的入口**——而"哪些入口是这样"目前无人能列全。
- **(c) 默认静默 + 调用方可声明 `required=("XKY_APP_KEY", ...)`**：读完后检查这些键是否真的到位（不论来自 `.env` 还是进程环境），缺则 fail-loud 并写明缺哪个键、找过哪些路径。
  - *得*：把判断从"文件在不在"移到"**我要的键到手没有**"——那才是调用方真正关心的事，且**对两种凭据来源都成立**。
  - *失*：每个入口要列出自己依赖的键（一次性工作，且这份清单本身就是有价值的文档）。

**推荐 (c)。**

> 🔴 **本项无默认项。** 判据：① 若不答，谁去执行？本 session 已收工，**回合制无法自我唤醒**，"按默认"实为停摆；且本项与决策点 1 耦合——(c) 的键清单怎么写，取决于 1 的作用域结论。**须明确答复。**

### 决策点 5 · CI 门禁挂在哪、怎么上线？

- **(a) 扩 `工具-引导样板lint.py`（推荐 ✅ 默认项）**：该脚本已在 CI 里、已有豁免机制、已有 `--enforce` 过渡开关，且它守的正是本病的另一半（`sys.path` 引导）。新增判据：已跟踪 `.py` 中出现"向上逐级找 `.env`"形态（`for d in (…parents…)` 内含 `/ ".env"`）即违规。
  - *得*：零新载体（协议〇.9：机制化优于新增守卫）；**one-in-one-out 的"退休"与"新增"落在同一个文件里，账最清楚**。
  - *失*：该脚本的名字（"引导样板"）会略微名不副实——建议同批把模块 docstring 的适用范围改写清楚，**不改文件名**（改名会打断 CI 配置与全库引用）。
- **(b) 新起一支 lint**：*失*：又多一个守卫，与协议〇.9 措施 B 的方向相反。**不推荐。**

**上线节奏（两个选项都适用）**：先 `--enforce` 关、只告警，**存量清零后再关门**——#345 的原话是「否则门禁上线第一天就是红的，只会被习惯性忽略」。

**推荐 (a)。默认项：(a)。**

### 决策点 6 · 分几批改、先改谁？

12 处（A 家族 9 ＋ B 家族 3）里有 4 个是 `.51` 常驻服务的入口，改错即停摆。

- **(a) 三批，按"改错的代价"从小到大（推荐 ✅ 默认项）**：
  - **批一（低危，可先行）**：一次性 CLI —— `build_golden_real.py`／`verify_material_board_real.py`／`ingest_tax_export.py`／`probe_u9c.py`。改错当场可见，无常驻影响。
  - **批二（中危）**：定时任务 —— `scan_tax_export_scheduled.py`。改错会静默不响（#82 的老毛病），**须构造真实触发条件验一次**，不接受"跑了没报错"。
  - **批三（高危，最后且逐个）**：4 个常驻服务入口 —— `run_baoguan_web.py`（8091）／`run_qd_b_web.py`（8093）／`run_fi2_web.py`／`serve.py`（8092）＋ `run_sc2.py`。**每个都必须单独部署 `.51` 并冒烟（`/api/ping`／关键页 200／一次全量重算）后再动下一个**，不许一批推四个。
  - *得*：任何一批出事，回滚面都只有一个服务。
  - *失*：跨三个 session，周期长。
- **(b) 一批全改 + 一次全量部署**：*失*：**四个服务同时上线新的凭据解析路径**，一旦语义有偏差就是四个一起挂，且归因困难。**不推荐**（#345 那次两个服务分别挂掉、各自修一遍，已经演示过同时出事的排查成本）。

**推荐 (a)。默认项：(a)。**

## 顺带发现（不属本包范围，登记备查，**未动手**）

**根 `.env` 第 3 行是一条孤立的裸 URL**，无键名——`https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=…`。它会被现存全部 9 份 `load_env()` 按 `split("=", 1)` 解析成「键名＝那段 URL、值＝`key` 之后的 36 字符」，`setdefault` 进 `os.environ`。**不影响任何现有功能**（第 2 行 `WECOM_WEBHOOK_URL` 的值完整，89 字符），但它意味着 `.env` 里躺着一个**没有名字的第三个 webhook 地址**。

🔴 **本 session 未修改 `.env`**——它是 gitignore 的凭据文件，删哪一行属于 Shao Peishen 的判断，且删错会静默改变某个群的收信去向。**建议由他确认第 3 行是误粘贴还是有意留存后再处置。**
