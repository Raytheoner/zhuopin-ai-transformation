## ADDED Requirements

### Requirement: 回件配对 SHALL 走两级通道
一条入站回件与跟进信的配对 SHALL 走两级通道，第一级命中即止：

1. **stem 精确匹配** —— 归一化后的原信文件名 stem 逐字相等（既有判据）。命中即配那封信，MUST NOT 再进第二级。
2. **后备：该收信人最新一封已发出的信** —— MUST NOT 看文件名、MUST NOT 看正文；文件类回件与纯文字回件 MUST 同等对待。

配对判据 MUST 只有一份，落在权威判据模块内；消费者侧 MUST NOT 另写一份。

本 Requirement 取代前序变更包中的「匹配不上 SHALL 不动 README 且 fail-loud」——「配不上就不动」这条整体退休，其 fail-loud 部分由下方「未命中 SHALL 分因处置」承接。

#### Scenario: stem 命中即止
- **WHEN** 一条文件类回件的 stem 与某封信的 `目标文件：` 标注逐字相等，而该收信人另有一封更新的已发出信
- **THEN** 配到 stem 对上的那封，更新的那封状态列逐字未变

#### Scenario: 纯文字回件走后备通道
- **WHEN** 归档文件名主题段为 `文本反馈`，无法与任何信 stem 匹配
- **THEN** 配到该收信人最新一封已发出且未闭环的信，并被标为第九态

### Requirement: 「已发出」SHALL 排除尚未送达专员的三态
判定「最新一封已发出的信」时，状态列以 `⏳ 待你审`／`🆕 待发`／`⏸ 暂缓` 开头的行 MUST 被排除——这三者的共同事实是专员尚未收到该信，不可能是任何回件的目标。

本模块未见过的状态写法 MUST 按「已发出」处理（保守方向）：误判为未发出会使该行在排序中被跳过、回件被配到更早的信上，且不产生任何信号。

#### Scenario: 最新一封是待审草稿则取次新
- **WHEN** 某收信人最新一封为 `⏳ 待你审`、次新一封为 `✅ 已推送` 且未闭环
- **THEN** 配到次新那封，草稿行状态列逐字未变

#### Scenario: 一封已发出的信都没有
- **WHEN** 该收信人名下只有草稿／待发／暂缓
- **THEN** README 逐字未变，记审计并打印 WARN

### Requirement: 「最新」SHALL 按日期、编号、表内行序三者排序
取「最新一封」MUST 按（日期, 编号序号, 表内物理行序）的三元组比较，MUST NOT 只按表内行序，也 MUST NOT 只按日期。README 的物理行序不是时间序；同一天可以有多封信。

收信人所属部门 MUST 在比较前归一化（剥除尾字「部」），因为发送人→部门映射与 README 收信人列对同一部门的写法不一致。

#### Scenario: 表内排在最后的不是最新的
- **WHEN** 一封 2026-07-21 的信在表格中排在一封 2026-08-20 的信之后
- **THEN** 取到的是 2026-08-20 那封

#### Scenario: 部门名带不带「部」都认得
- **WHEN** 发送人映射给出 `IT`，README 收信人列写的是 `IT部 · 陈承`
- **THEN** 两者判为同一部门，配对正常进行

### Requirement: 未命中 SHALL 分因处置，MUST NOT 合并为一种
未命中的原因 MUST 至少区分三类，各自记独立的审计 action：

- **最新一封已闭环** —— 🔴 预期内常态（闭环后到达的补充说明必然走到它）。MUST 只记审计 ＋ 低噪提示，MUST NOT 打印警告前缀，MUST NOT 触发告警通道。
- **该收信人无任何已发出的信** —— MUST 记审计 ＋ 打印 WARN。
- **收信人部门解析不出** —— MUST 记审计 ＋ 打印 WARN，MUST NOT 猜测。

把这三类合并成一个 `unmatched`，会让「预期内常态」与「真的出问题了」在审计里长得一模一样。

#### Scenario: 闭环后的补充说明不制造假警报
- **WHEN** 某收信人最新一封已发出的信已处于闭环态，此时又到达一条回件
- **THEN** README 逐字未变、闸未重新锁、未调用告警通道，输出前缀为低噪符号

#### Scenario: 收信人解析不出即不动
- **WHEN** 发送人未命中部门映射（fail-closed 归「待分拣」）
- **THEN** README 逐字未变，记审计并打印 WARN，且不尝试取锁

### Requirement: 审计事件 SHALL 记录命中的通道
每一次配对的审计事件 MUST 记录本次命中的是哪条通道（stem／后备），未命中时 MUST 记录落在哪个分支。日后复盘误配时，第一个要回答的问题是「这条是逐字对上的，还是按位置推的」。

#### Scenario: 通道写进审计
- **WHEN** 一条纯文字回件经后备通道被标为第九态
- **THEN** 审计事件的决策字段中通道标识为后备通道

### Requirement: 历史未闭环信 SHALL 只报数，MUST NOT 阻塞配对
「某收信人有 N 封已发出且未闭环的信」SHALL 作为独立健康检查输出，MUST NOT 参与任何转态判定，MUST NOT 阻塞配对。

以「未闭环恰好一封」为配对前提的实现方式 MUST NOT 被采用——实测生产数据上各收信人分别有 7／7／4／4 封历史未闭环信，该前提恒不成立，会使机制上线即失效；且它引入的「在途」定义与串行闸的判据不一致。

#### Scenario: 堆积的历史信不影响配对
- **WHEN** 某收信人名下有 6 封历史未闭环信，外加一封最新的已发出未闭环信
- **THEN** 回件被配到最新那封，6 封历史信状态列逐字未变，健康检查另行报出总数
