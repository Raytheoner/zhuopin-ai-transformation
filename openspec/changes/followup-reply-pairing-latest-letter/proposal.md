# 回件转态改判：stem 优先 ＋ 最新一封后备，桥二由拦截改为机器代写

> 承接队列 §一 `#366`（S4 桥一／桥二）；派单件
> `1-转型规划/0-全景路线图/派单件-【CC】回件转态只配最新跟进信-2026-08-23.md`（`OP-0823-D`）。

## Why

**一句话**：跟进信 README 的「发送状态」列是串行闸的唯一权威源，而**它没有任何机制会自己变**——机器只写队列，改那一格的一直是人。

改造前的两座桥都只认一条判据：**归档文件名 stem 与 README 行的 `目标文件：` 标注逐字相等**。该取舍当初的理由成立（「一条文本回件无法确定地指向哪一封信，硬配会造出比漏配更难发现的错误」），但它的后果已被实测量化：

- 2026-08-23 实测，README 中 12 封信的状态列停在「✅ 已推送」，最久积压 20 天以上；
- 后果有两个，第二个此前没被点破：**⑴ 串行闸误锁**（该发的信发不出，只能编 `串行豁免：` 去绕）；**⑵ 度量失真**——「未转态」与「回得慢」在数据上长得一模一样，我们在一份自己没维护好的账上做度量决策。

Shao Peishen 的解法是**换掉前提，不是改进猜法**：不按内容配，**按位置配**——回件属于该收信人最新那封已发出的信。位置的确定性来自本项目既有硬约束「跟进信串行原则：同一收信人同时只能有一封在途」。

### 本次退休了哪一个既有守卫（协议〇.9 措施 B，机制类变更包强制回答）

**退休两条，不是零退休**：

1. **桥一的硬约束「匹配不上就不动 README」**（`followup_readme_bridge.py` 模块 docstring 三条硬约束第 1 条）——**整条退休**。它的替代不是"放宽"，而是换了一个确定性更强的来源（收信人 ＋ 串行原则），且 stem 仍保留为第一优先。
2. **桥二的「拒绝 release 逼人手改」**（`_validate_followup_reply_state_sync`）——**退休为机器代写**。人只需把 §一 入信行改成 `[S:done]`（那本来就是「我回灌完了」这句声明），README 那一格由机器写。**写不成时仍然拦**——退的是"让人干机器能干的活"，不是"失败时假装没事"。

⇒ 本包**净减一条人守规则、净减一条人工步骤**，未新增任何需要人记住的语法（刻意不发明 `回灌完成：` 标记：那等于让人多记一条规则去说一件他已经说过的事）。

### 伴生文件的 .gitignore 覆盖（队列 #328 子项②，强制回答）

**本变更不新增任何此前不存在的文件名形态。** 桥二新增的机器写入会占用跟进信 README 的编辑锁，产生 `README-跟进机制与命名约定.md.editlock` / `.editlock.lastknown` / `.editlock.mutex` —— 这三种形态**在本变更之前就已存在**（任何人对该 README 跑一次 `acquire` 都会产生），本次只是多了一个产生它们的调用方。

核实方式（`git check-ignore -v` 实测结果，非推断）：

```
6-人才与组织/部门AI专员跟进/README-跟进机制与命名约定.md.editlock
  -> .gitignore:62:*.editlock*
6-人才与组织/部门AI专员跟进/README-跟进机制与命名约定.md.editlock.lastknown
  -> .gitignore:62:*.editlock*
6-人才与组织/部门AI专员跟进/README-跟进机制与命名约定.md.editlock.mutex
  -> .gitignore:62:*.editlock*
```

三条全部命中 `.gitignore` 第 62 行 `*.editlock*`。

## What Changes

### 桥一（`aibot_service/followup_readme_bridge.py`）——两级配对

- **① stem 精确匹配**命中即止（保留既有行为，**去掉它就是净回归**）；
- **② 未命中时**：配「该收信人**最新一封已发出**的信」。不看文件名、不看正文，**docx 与纯文字一视同仁**。
- 「已发出」＝ 排除 `⏳ 待你审` / `🆕 待发` / `⏸ 暂缓`；「最新」＝ 按（日期, 编号, 表内行序）取最大。
- 未命中的三种原因**分开记 action**：`latest_closed`（🔴 预期内常态，低噪）／`no_dispatched_letter`（WARN）／`no_department`（WARN）。

### 桥二（`0-学习与工具/工具-共享文档编辑锁.py`）——由拦截改为机器代写

- §一 入信行转 `[S:done]` ⇒ 机器在 `release` 时把该信写为 `📥 已回件并回灌 <本地日期>`，**一次走完「转态 → 闭环 → 开闸」**。
- 配对只走**两条确定通道**：stem 逐字相等，与**桥一写在第九态单元格里的溯源回指**。
- 🔴 **桥二刻意不跑桥一那条通道②**——它扫的是全部历史入信行，**没有时间上下文**（论证见 design.md D2）。
- 写入经跟进信 README 自己的编辑锁；锁被占／写盘失败 ⇒ 返回违规、拒绝 release。

### 判据模块（`zhuopin_platform/shared_tools/followup_gate.py`）

新增 `NOT_YET_SENT_STATUS_PREFIXES`／`is_dispatched`／`normalize_department`／`recipient_department`／`LetterRow`／`latest_dispatched_letter`／`pair_reply_to_letter`／`unclosed_dispatched_by_department`／`reply_arrived_cites`。**判据只此一份，消费者侧不得另写。**

### 健康检查（§3.1bis）

「某收信人有 N 封已发出未闭环的信」降级为**只报数的健康检查**，🔴 **不参与转态判定、不阻塞配对**。

## Impact

- **受影响能力**：`wecom-followup-readme-reply-bridge`（桥一）、`editlock-followup-reply-state-sync`（桥二）。
- **受影响代码**：`followup_gate.py`、`followup_readme_bridge.py`、`connection.py`（透传 `department`）、`工具-共享文档编辑锁.py`、三处测试、新增 `scripts/smoke_followup_pairing.py`（只读冒烟）。
- **不受影响**：两态语义与人工批准流程、`delivery.py` 门禁②、`工具-跟进闸查询.py` 读侧判据、L2 门禁、OEM 隔离（本服务不涉技术数据）。
- **合规**：桥二的机器写入是 L1 自动化，全程写 `audit`；写入文案显式声明「本次由机器代写，未经人工逐字确认」，保留原状态原文，可追溯。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

**本流程哪些判断是人脑默会经验？**

1. **「这条回件是回哪封信的」** —— 拆件的人一眼就知道，靠的是「这位专员手头只有那一封信没了结」这个默会前提（即串行原则），而不是读文件名。
2. **「什么状态算这封信还在等回复」** —— 人能一眼分辨 `⏳ 待你审`（我还没发）与 `✅ 已推送`（发了在等），机器此前没有这条判据（`IN_FLIGHT_STATUS_PREFIXES` 把两者混在一起）。
3. **「哪些历史信其实已经不作数了」** —— 20 封 2026-07-31 编号体系建立前的信，人知道它们早已过去，账上却仍是「在途」。这一条**本次未显性化**，作为取证清单交 Shao Peishen 处置。
4. **例外/尺度**：闭环之后专员再补一条说明是常态，不是异常——这条尺度此前只在人脑里，机器会把它当成配对失败去告警。

**由谁显性化？** 持有人 **Shao Peishen**（口径来源，2026-08-23 三次调整定稿）；backup **孙涛**（决策代理，可代 design 审）。

**用什么方法提取？** **L2 改判判例累积 ＋ 历史案例反推**：判据 1／2／4 均由 2026-08-23 对生产 README 的实测反推而来（四位收信人的在途封数、`财务部#14` 与 `财务部#15` 同日的反例、32 份文本反馈件的首行格式统计 12%），不是设问得来的。

## 验收与晋档条件（强制，四档口径）

**本变更包交付后场景所处档位**：**档 3（内部服务）**。桥二在本机开发环境真实运行（编辑锁 `release` 每次触发）；桥一的执行体是常驻服务，本包合入 master **不等于**桥一在跑（其载体 worktree 落后 master，见 §四 #68 未解）。

**晋下一档（档 4 对客交付）的条件**：不适用——本机制服务内部专员协同，永不对客。

**桥一真实生效的前置条件（逐条）**：

1. 常驻服务执行体 worktree 与 master 对齐（§四 #68，本包范围外）；
2. 服务重启后收到第一条真实纯文字回件，审计中出现 `followup_readme_bridge_marked` 且 `channel=latest`；
3. 该次转态经人核对确为正确的那封信。

**价值指标（风险型 ＋ 质量型）**：

- **风险型**：「README 状态列滞后天数」的最大值。基线 ＝ **20 天**（2026-08-23 实测积压最久的那封）；目标 ＝ **≤1 天**（回件到达即打第九态、拆件当次即闭环）。
- **质量型**：「靠 `串行豁免：` 绕闸的次数」。基线待 Cowork 从 git 历史统计；目标 ＝ 趋零（闸锁着的原因应当是真的有信在途，而不是账没维护）。
- **基线由业务 Champion 确认**：Shao Peishen。

## 已知边界（必须随交付一起说出去）

1. **桥一没跑成的纯文字回件，桥二配不上** —— 两条确定通道都对不上，仍需人手工转态。这不是回归（改造前同样配不上），但也不是全覆盖。
2. **20 封历史未闭环信本包不动** —— 它们没有回件归档件作硬证据，闭环与否只能由 Shao Peishen 判定。本包只出取证清单。
3. **本包与前序变更包 `followup-letter-state-single-source` 的关系见 design.md D5** —— 那个包尚未归档，两者的 delta 落在同一批能力上，归档时须先对齐。
