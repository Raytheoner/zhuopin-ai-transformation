# Design — 回件转态改判（`OP-0823-D`，队列 §一 #366）

## D1：为什么后备通道是「最新一封已发出的信」，而不是「唯一在途的信」

当天先后出现过三个方案，取舍如下：

| 方案 | 状态 |
|---|---|
| **A. stem 精确匹配** | ✅ **保留为第一优先**。问题从来不在它本身，而在「匹配不上就不动」 |
| **B. 唯一在途（所有未闭环恰好一封）** | 🔴 **不进配对判据**，降级为健康检查 |
| **C. 最新一封已发出的信** | ✅ **采用为后备通道** |

**B 被否掉有两条独立理由，任一条都足够**：

**⑴ 它在生产数据上恒不成立。** 2026-08-23 对真身 README 实测（CC 与 Cowork 双方独立跑、结论一致）：

| 收信人 | 已发出且未闭环 | 按 C：最新一封 |
|---|---|---|
| 采购部 · 姚祖怡 | 7 封 | `采购部#17` 已闭环 ⇒ 闸开 |
| 财务部 · 唐燕萍 | 7 封 | `财务部#15`（08-23 08:26 发）⇒ 闸锁 |
| 质量部 · 陈忱 | 4 封 | `质量部#8` 已闭环 ⇒ 闸开 |
| IT部 · 陈承 | 4 封 | `IT部#9`（08-18 发）⇒ 闸锁 |

按 B 实现，四位收信人**一次都不会命中**（全部撞「≥2 拒绝」），**机制上线当天就是哑的**——同本项目已记的「`#82` 建成 9 天、每天在跑，却从来没真正发出过一条消息」。

**⑵ 比「恒不命中」更根本：它与闸不是同一把尺子。** 跟进闸判的是「**该收信人最近一封是否已闭环**」——只看最新一封。B 引入的是**第三种「在途」定义** ⇒ 配对和开闸各用一把尺子，必然出现「配上了但闸没开」或反过来。**C 与闸同尺，这才是它真正的优势，不只是更简单。**

## D2：🔴 桥二为什么不能也跑通道②

桥一在**回件到达那一刻**配对，那时才有「这条刚到的回件属于该收信人当前那封信」这个时间上下文。
桥二在**每次 `release`** 时扫**全部历史入信行**，没有任何时间上下文。

**反例（取自 2026-08-23 真身，不是构造的）**：`财务部#14` 的回件与 `财务部#15` 的发出**同为 2026-08-23**。若桥二按「该部门最新一封已发出的信」去配，一条 7 月的 `[S:done]` 入信行会把今天刚发出、根本还没人回的 `财务部#15` 自动闭环并开闸——**错得悄无声息，且连按日期加护栏都挡不住**（日粒度不够）。

⇒ **桥二只认两条确定通道**：

1. `reply_matches_letter`（stem 逐字相等）；
2. `reply_arrived_cites`（该信当前是第九态，且单元格里的溯源归档文件名正是这一份）。

第 2 条是**桥一 → 桥二的确定性回指**：桥一把配对结论写进单元格，桥二读回来。**它让纯文字回件第一次进入桥二的覆盖面**——此前这类回件既配不上 stem、README 行也多半没有 `目标文件：` 标注。

**代价**（如实登记）：桥一没跑成（服务停摆／锁忙三次用尽）的纯文字回件，桥二配不上，仍需人手工转态。这不是回归——改造前同样配不上——但两座桥从「冗余」变成了「桥二在这一类上依赖桥一」，原 docstring 里「两座桥是冗余而非串联」那句对**纯文字回件**不再成立，已在代码注释里改掉。

## D3：「已发出」为什么要单独定义，而不是复用 `IN_FLIGHT_STATUS_PREFIXES`

原有的「在途」一直混着两件事：**已经发出去等着回**，与**还没发出去**（`⏳ 待你审` / `🆕 待发` / `⏸ 暂缓`）。判「回件该配哪封信」时只有前者算数——一封草稿不可能收到回件。

派单件只点名了 `⏳ 待你审`，本实现一并纳入另两个：**三者的共同事实是「专员那边还没看到这封信」**，漏掉任何一个都会让机器去配一封对方根本没收到的信。

`is_dispatched` 定义为 `not is_not_yet_sent`（**未知写法算已发出**），因为两个方向的代价不对称：误判成「没发出」会让它在排序里被跳过，回件被配到更早的另一封信上，**错得悄无声息**；反过来最坏是配到一封没人收到的信，人拆件时一眼看得出。

## D4：「最新」的排序键为什么是三元组

`(日期, 编号序号, 表内行序)`，三个都需要：

- **不能只按表内行序**——实测 `采购部#4`（07-21）在真身 README 里排在 `采购部#17`（08-20）**之后**，README 的物理行序不是时间序；
- **不能只按日期**——`采购部#15`／`#16` 同为 2026-08-18；
- **行序兜底**无编号行（`采购部（未发，不编号）`）与前两者都相同的情形。

另有一处**不对齐**必须归一化：`department_mapping.yaml` 里陈承那行的取值是 `IT`（不带「部」），README 收信人列写的是 `IT部 · 陈承`。直接字符串比对会让 IT 域的回件**一封都配不上，且不报任何错**。

## D5：与前序变更包 `followup-letter-state-single-source` 的关系

那个包引入了本次要改的两项能力（`wecom-followup-readme-reply-bridge` / `editlock-followup-reply-state-sync`），**尚未归档**（其 `tasks.md` §0 两项未决，文件明写「本包不得归档」），因此这两项能力**只存在于它的 delta 里、尚未 sync 进 `openspec/specs/`**。

本包因此用 `## ADDED Requirements` 而非 `MODIFIED`——没有主 spec 可 MODIFY。**归档时须先对齐**，本包被以下前序 Requirement 取代的部分逐条列明：

| 前序包中的 Requirement | 本包如何取代 |
|---|---|
| 桥一「匹配不上 SHALL 不动 README 且 fail-loud」 | 整条退休，由「回件配对 SHALL 走两级通道」取代；fail-loud 的部分保留在新 Requirement 里 |
| 桥二「拆件完成 SHALL 强制 README 转闭环态」 | 由「拆件完成 SHALL 由机器代写闭环态」取代（拦截 → 代写，写不成仍拦） |
| 桥二「配对 SHALL 确定，判不出即不拦」 | 扩为两条确定通道（新增第九态溯源回指），「判不出即不拦」不变 |

⚠️ **这是一个已知的账**，不是遗漏：两包同时活着期间，同一能力下会并存两组措辞相近的 Requirement。归档任一包之前必须先解决，已写进 `tasks.md`。

## D6：机器写 README 为什么要自己占一次锁

桥二挂在**队列系统**目标的 `release` 上，此刻持有的是队列那把锁；README 是另一个目标、另一把锁。不占就写正是协议〇.7 要禁的裸改，而且下一次有人 `acquire` README 时，#200 绕锁检测会如实把它报成「被直接改写过」——**等于我们自己制造了一条假警报**。故：

- 用 `_acquire_mutex` 保护「读判定 → 写锁」整段（同 `cmd_acquire` #197 的既有做法）；
- 锁被别人占用时**不抢、不等**，返回原因 ⇒ 转成一条 release 违规（fail-loud）；
- 写后回读校验（#197「不信写成功了」）；
- **同步 `lastknown` 基准**，否则下一次 acquire 误报绕锁——已配单测锁死。

## D7：写入时机——即便本次 release 因别的原因被拒，转态也已落盘

桥二的写入发生在其它结构校验之后、release 决定之前。若同一次持锁里另有一处格式问题导致 release 被拒，**这次转态已经落盘**。

这是有意的：「拆件回灌完成」是既成事实，不该因为同一次持锁里另有一处格式问题就退回去；且重跑幂等（已闭环的信不会被再写一次），已配单测。

## D8：为什么不发明一个「回灌完成」声明标记

派单件 §3.2 写「人在编辑锁 release 时声明本次已完成回灌」。**这个声明动作已经存在**：把 §一 入信行的状态字段改成 `[S:done]`，本来就是「我回灌完了」这句话本身。

另造一个 `回灌完成：` 标记，等于让人多记一条规则去说一件他已经说过的事——与本项目「规则退休制」的方向相反。⇒ **零新增语法。**

## D9：告警级别——为什么「最新一封已闭环」必须是低噪

§3.3 定案：闭环后到达的补充／更改照常落档，**但 README 状态列一字不改、闸不重新锁、不重开在途**。

⇒ 「最新一封已闭环」这个分支是**预期内常态**，闭环后的每一条补充说明都必然走到它。把它按告警报出去，等于**每条补充说明制造一次假警报**——那正是 §四 `#87` ⑶ 记的「误报训练人忽略告警」。

实现上表现为三处：`ACTION_SUPPLEMENT` 独立成一个 action（不与真正的失败混在 `unmatched` 里）、日志前缀是 `·` 而非 `⚠`、**不调 `alert_send`**。三处都配了单测。

## Non-Goals

- 不动那 20 封历史未闭环信（无硬证据，判定权在 Shao Peishen，本包只出取证清单）。
- 不改两态语义、批准流程、`delivery.py` 门禁②。
- 不做「读回件正文首行提取标题」那条通道——实测 32 份文本反馈件里只有 4 份（12%）具备该格式，且四份全部出自同一人，样本同源，不成立。
- 不加等待期、不加可重入态（§3.3 硬边界）。
