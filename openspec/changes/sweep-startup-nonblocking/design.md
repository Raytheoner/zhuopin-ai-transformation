## 2. 通则一：起跑段全部中止位点逐一判定（交付条件⑵）

**判据（本次立的通则，一句话）**：
> **一处起跑段检查是否该中止整轮，取决于「它挡住的那些本地工作，是否真的依赖它所检查的那个前提」。依赖 ⇒ 拦；不依赖 ⇒ 记录后继续，把该前提的职责交给真正需要它的那一段。**

推论：**「仓库物理状态不可用」必须拦**（本地工作真做不了或做了有害），**「外部依赖暂时不可用」应降级**（本地工作与它无关）。

### 现存九个位点的逐一结论

| # | 位点 | 现退出码 | 判定 | 理由 |
|---|---|---|---|---|
| 1 | `_heal_stale_index_lock:598` 新鲜 `.git/index.lock` | 0 | **维持拦截** | 另有 git 进程在跑，继续则后续每个 `_run_git(check=True)` 都会抛 `CalledProcessError`（正是 #121(b) 的症状）。本地 git 本身不可用 ⇒ 依赖成立。 |
| 2 | `_assert_not_a_linked_worktree:572` `.git` 非目录 | 1 | **维持拦截** | 运行位置错误。继续会在一次性建造分支上提交，该分支可能被 `git worktree remove` 连同提交一起丢弃（协议〇.5）⇒ 真实数据丢失风险。 |
| 3 | `_check_preconditions:612` repo_root≠主工作区 | 1 | **维持拦截** | 同 #2，计划任务配置误指的兜底。 |
| 4 | `_check_preconditions:621` 分支非 master | 0 | **维持拦截** | 落库目标是 master；在别的分支上提交即制造分叉，比不落库更糟。 |
| 5 | `_check_preconditions:625` 未完成 git 操作（`MERGE_HEAD` 等） | 0 | **维持拦截** | 仓库处于半完成状态，任何写动作后果不可预期。 |
| 6 | `_check_preconditions:629` 未合并冲突路径 | 0 | **维持拦截** | 同 #5。 |
| 7 | `_abort_if_edit_lock_held:2268` 编辑锁被占用 | 0 | **维持拦截** | 协议〇.7。继续即与他人并发写队列；#198(b) 立行理由原文即「锁占用时连第一个 `git add` 都不该发生」。 |
| 8 | `_fetch:635`（**起跑段**调用） | 0 | 🔴 **降级** | **本行主体。** 挡住的是批次本地提交／台账重跑／flush 暂存／孤儿告警／openspec 检测——**没有一项需要网络**。 |
| 9 | `_push_any_unpushed_commits:683` 补推失败 | 2 | 🔴 **降级** | **通则扫出来的「第四例」，不在派单件字面范围内。** 与 #8 同因（网络/鉴权），同样不影响本地工作；本地提交本就不会被撤销，推送交收尾段重试，收尾段推送失败仍以 `exit_code=2` 收尾 ⇒ **对外语义不丢，只是判定时机后移**，与 #309-F 当初「起跑段一律拦 → 收尾段确认真不行才拦」的收窄完全同构。 |

**结论：7 处维持、2 处降级。** #9 正是这条通则存在的意义——**它不在任何人"撞见"的路径上，只有逐位点扫一遍才会发现**。

### 可扫描判据（把通则从人守变机制守）

新增单测 `test_起跑段中止位点须与冻结清单一致`：用 `ast` 静态解析 `工具-落库sweep.py`，收集起跑段六个函数（`_heal_stale_index_lock`／`_assert_not_a_linked_worktree`／`_check_preconditions`／`_abort_if_edit_lock_held`／`_push_any_unpushed_commits`／`_fetch`）内的全部 `raise SweepAbort` 位点，与测试内冻结的清单（含每项一行判定理由）逐项比对；**新增、删除或改动任一位点即失败**，强制作者按上表判据显式分类。

为何用 AST 而非正则：本项目「用正则猜代码/中文」已是被 #308 点名要收敛的家族（`工具静默回退` 同族），正则会被注释、字符串、跨行调用骗过；AST 对这三者天然免疫。为何不做成运行时守卫：它要约束的是**改代码的人**，不是**跑代码的机器**，运行时拦不到"下一个人新写了一个 abort"。
