## Why

### 这不是一条新规则，是一个从未被显性化过的判据缺口

`工具-共享文档编辑锁.py` 的 `release` 校验 ①～⑩ 已经把"一行队列行长什么样才算合法"这件事讲得很细（列数、裸竖线、跨行、关键格哨兵……），但那一整套判据只在 **`release` 释放锁时**跑一次。`edit-row`／`append-row` 本身在**写入那一刻**做的校验明显更薄——薄的具体形态是三件事，且三件事是**同一根因的三面**（#455 原话）：

1. **竖线守卫非反引号感知**（#324 未闭合⑵）：`queue_table.has_bare_pipe` 按其自身 docstring 明写"不做反引号感知"，对 `edit-row --set`（整格替换）之外的**存量**内容不构成问题（`validate_row_cells(source="parsed")` 已豁免），但当**整格替换的新值**恰好需要引用一段含合法反引号包裹竖线的文本时（#324 状态格引用"朴素切列函数的代码引用"），该整格替换会被现有 `has_bare_pipe` 拒绝——而 `--append` 只能加尾巴、翻不动 `[S:]` 前缀，**行的状态字段因此锁死，改不动**。
2. **不校验反引号奇偶／写入后是否仍是合法列数**（#454 亲历）：`edit-row` 目前对"待写入新值"只做**朴素竖线子串检测**，不检查这段新值本身的反引号是否能正确闭合。2026-09-02 一次改判把分诊器给出的引文按 60 字硬截断，恰好把一个反引号截在中间——**整格反引号变奇数，未闭合跨度把行尾真正的列分隔符也吞掉了**，`#337`／`#422` 两行由 8 列塌成 7 列。`edit-row` 写入时**没有任何检查能发现这一点**：它对"待写入的新值"只查裸竖线，不查反引号闭合性；对"写完之后这一行还是不是合法队列行"完全没有回读校验。是 `release` 校验①（结构门禁）**事后**才拦下来的。
3. **对已塌列的行拒绝一切操作，含 `--append`**（#454 亲历，鸡生蛋）：`cmd_edit_row` 写盘前会用 `queue_table.validate_row_cells(section, new_cells, source="parsed")` 校验 `new_cells`（即"改动前的旧列表 + 按列名覆盖后的结果"）的列数；一旦这一行**在本次编辑之前就已经**因为① 而塌了列（比如已经是 7 列），这个检查会无差别报"列数为 7，应为 8"并拒绝**任何**改动——**包括本该被允许用来补救的 `--append`**。行一旦被写坏，**唯一还能碰它的入口把自己关上了**，只能在持锁状态下退化成手工改文件（#454 当次即如此）。

**三件事合起来是一句话**：`edit-row`／`append-row` 的写侧校验比 `release` 的读侧解析弱一档——**读侧反引号感知（`split_row_cells`／`_table_data_rows`，队列 #314），写侧不感知**；且写侧对"这一行改之前是否已经是坏的"与"这一行改完之后是不是还是好的"这两件不该混在一起的事，目前挤在同一个 `len(new_cells) != expected` 判断里，两件事都没做对。

### 为什么这三条都该机守而非人工复查

Shao Peishen 2026-09-02 当场给出的元判据（拟建议升进根 `CLAUDE.md` §5，本包不代其升进，仅引用）：**「如果能做，就不要指派手工——会带入失误。」** 完整论证与本包的对应关系见 design.md「决策点 0」；结论先写在这里：**这三件事全部可以被机器精确判定**（反引号能否按 CommonMark 游程规则闭合 / 一行按分隔符重新切出来是几列 / 一行改之前的列数是否已经不对）——不存在"需要人的经验判断"的空间，凡可判定就不该留给"下一次值周巡检的人肉复查"或"操作者自己当心点"。#454 本身就是本判据的反例实证：**这次事故的操作者正是本项目里对这套工具最熟悉的角色之一，仍然中招**——熟练度不是这类失误的解药，机器判据才是。

## What Changes

- **新增写侧校验 A「反引号跨度可闭合性校验」**：对 `edit-row --set`／`--append`／`--changes-json`／`--stdin-json` 传入的**每一个新值**，在写入前用与读侧 `split_row_cells` 同一套 CommonMark 游程配对算法（`_mask_backtick_spans`）逐个扫描，确认值内部**不存在未闭合的反引号游程**。存在即拒绝写入，提示具体哪个字段、哪一段反引号未闭合。**不是简单的 `count('`') % 2` 奇偶计数**——决策点 1 论证为何简单奇偶计数不充分（游程长度必须两两匹配，而非总数为偶）。
- **新增写侧校验 B「写入后列数回读校验」**：写入磁盘后，**立即从磁盘重新读回**该行文本、用 `queue_table.split_row_cells` 重新切列，确认列数仍等于该分区预期列数。**不符即自动回滚**——把文件内容还原为写入前的字节，本次改动视为未发生，并如实提示"已回滚"。这是防止校验 A 之外仍存在的、跨字段边界的反引号交互（如某新值虽自身闭合、但与相邻既有格内容组合后仍产生非预期切列结果）的最后一道防线（design 决策点 2）。
- **新增逃生入口「已塌列行的 `--repair`」**：`edit-row` 新增 `--repair` 开关。目标行在**编辑前**列数已不等于预期列数（即已经塌列）时，现状是**无差别拒绝一切操作**；`--repair` 放开这一前置门，但代价是收紧输入形态——**必须一次性提供该行全部列的值**（而非按列名 `--set`／`--append` 部分覆盖，因为已塌列行的现有列位与列名的对应关系本身已不可信），并且**仍然完整过一遍校验 A 与校验 B**——`--repair` 只豁免"改之前列数是否合法"这一个前置检查，不豁免"改完之后是否合法"。
- **BREAKING**：是。`edit-row` 在"新值含未闭合反引号跨度"这一输入下由**当场写入（写坏）**变为**当场拒绝**；在"目标行已塌列"这一输入下，不传 `--repair` 时行为不变（仍拒绝），传 `--repair` 且提供全量列值时由**恒定拒绝**变为**有条件放行**。存量已经写入的合法行不受影响。

## 本次退休哪一个既有守卫（强制，协议〇.9 措施 B）

**退休对象**：`cmd_edit_row` 现有的 `queue_table.validate_row_cells(section, new_cells, source="parsed")` 列数分支——它目前**一身兼两职**：① 判"这一行在本次编辑之前是否已经损坏"，② 顺带被误用来当作"这一行编辑之后是否仍然合法"的唯一信号。**这两件事的判定对象根本不同**（① 判的是 `new_cells` 这个 Python 列表的长度，一个由"旧列表复制 + 按下标覆盖"构造出来的值，长度在构造时就已恒定，**不会因为新值里藏了未闭合反引号而改变**；② 应该判的是"把 `new_cells` 拼成字符串、写盘、再按真实解析规则切一次列，数出来是几列"）——**现状用①的信号去回答②的问题，两者都没答对**：本该拦的（校验 A/B 要拦的"这次编辑把行写坏了"）拦不住，不该拦的（已经坏掉的历史行想用 `--append` 挽救）却被无差别拦死。

本包**整体退休**这个合一分支，拆成三件边界清楚的判据：**前置门**（对应旧分支①的职责，显式命名，`--repair` 可豁免）＋**校验 A／B**（对应旧分支②本该做却没做的职责）。旧分支的报错文案（"列数为 N，应为 M"）与判断逻辑不再在 `cmd_edit_row` 里被当作唯一的写入前列数校验使用；`validate_row_cells(source="parsed")` 本身（供其它调用方复用的通用函数）不改动语义，只是 `cmd_edit_row` 不再单独依赖它的列数分支来同时回答两个问题。

## 伴生文件的 .gitignore 覆盖（强制）

**不适用——本变更不新增任何自动生成的文件名形态。** 校验 A／B／`--repair` 只影响 `edit-row` 的返回码、stdout 提示与（校验 B 触发回滚时）目标队列文件本身的字节内容（回滚到写入前状态，不产生任何新文件）。apply 后 `git status --porcelain` MUST NOT 出现任何新形态未跟踪文件。

## Capabilities

### New Capabilities

- `editlock-write-backtick-span-guard`：`edit-row` 写入前对每个新值做反引号游程闭合性校验，未闭合即拒绝。
- `editlock-write-postwrite-column-readback`：写入磁盘后重新读回并按真实解析规则复核列数，不符即自动回滚。
- `editlock-row-repair-escape-hatch`：`edit-row --repair`——对已塌列的行放开前置门，但要求全量列值输入，且仍受校验 A／B 约束。

### Modified Capabilities

（无——三条均为独立新增判据，互不改写彼此语义；`cmd_edit_row` 内部实现结构调整见「本次退休哪一个既有守卫」，但不构成对外能力语义的修改。）

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？** 三处：① **"这段我正要写进去的文本，反引号收得住吗"**——此前完全靠人在改动前"看一眼"，且 #454 的操作者正是本项目最熟悉编辑锁工具的角色之一仍然中招，证明这不是"看一眼"能稳定发现的问题（60 字截断点落在哪里是运气）；② **"这一行改完之后还是不是一条合法的队列行"**——此前唯一的信号来源是**下一次 `release`** 才跑的结构门禁，中间这段"写完但还没 release"的窗口完全靠人不出错；③ **"这一行已经坏了，我还能不能碰它"**——此前的答案是"不能，除非脱离工具用脚本手改"，本质是把判断丢给了人（且是**持锁状态下的手改**，本身就是本项目一贯要消灭的绕过路径）。
2. **由谁显性化？** 决策人 Shao Peishen（design 审对决策点 0/1/2/3 拍板）＋ CC 建造车间（判据实现、单测、对现网两份队列历史行的现网只读全量核对）；backup ＝ 下一位领取 #455 的 session 可凭本包与 design.md 独立复核，且 #454／#324 两行本身已留有完整的事故重现路径可复算。
3. **用什么方法提取？** 历史真实案例反推（#454 的 2026-09-02 亲历事故、#324 的状态字段锁死）＋ **对现网两份队列文件的全量实测**（apply 期 tasks 1.x：对所有既有行的所有格跑一遍新的反引号游程闭合性判据与列数回读判据，确认新判据不会把现网**已经合法**的历史行误判为不合法——`#324`／`#326` 两行是已知的"格内含反引号保护竖线"正例，必须继续通过）。不涉及 LLM 判断，纯字符串/游程扫描与列数比较。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：跨项目治理机制，非独立业务场景，套用最接近的描述 ＝ **档1 mock 验证**（design 审通过、代码与单测完成、现网两份队列全量只读对照跑过，但尚未真实拦下过一次"新值反引号未闭合"或真实用过一次 `--repair`）。
- **晋下一档（档2 真实数据跑通）的条件**，逐条：
  1. 真实发生一次校验 A 拒绝（新值含未闭合反引号跨度），确认提示文案足以让操作者定位到具体是哪个字段、哪一段反引号出的问题。
  2. 真实发生一次校验 B 触发（写入后回读列数不符、自动回滚），确认文件确实被还原到写入前字节（`git diff` 为空或与预期一致），且提示如实说明"已回滚"而非"写入失败但文件已变"这种半吊子状态。
  3. 真实用一次 `--repair` 修复一行已塌列的行，且修复后该行通过 `release` 结构门禁①。
  4. 🔴 **误报观察窗口**：交付后至少覆盖 3 个值周巡检节拍，期间校验 A／B 的每一次拒绝都要被逐条判定真阳性还是误报；若误报数 > 真阳性数，须重评判据实现（尤其决策点 1 的游程配对算法）而非简单放宽。
  5. 🔴 **零命中不得读成"问题已解决"**（同项目已有 §四 #58／#122 等同形教训）——若窗口内校验 A／B 一次都没响过，正确表述是"未被检验"，不得表述为"反引号写坏行的问题已解决"。
- **价值指标**（风险型）：队列行被写坏的发现方式——基线 ＝ **`release` 事后拦截 + 手工改文件挽救**（#454 实测：`release` 校验① 拦下，随后在持锁状态下用脚本改文件，未走任何正规入口）；目标 ＝ **写入当刻即被拒绝，且已塌列行有正规入口可修**。误报率不设硬指标，按上条第 4 项逐次判定。
- **LLM 判据黄金集**：不适用（纯字符串扫描与列数比较，无 LLM 运行时判断）。

## 已知残余风险（如实写明，不粉饰）

1. **本包不修复 #324 未闭合⑵本身**（"竖线守卫非反引号感知"这一条，即 `has_bare_pipe`／`validate_row_cells(source="write")` 对**合法**的反引号包裹竖线仍然一律拒绝、不做豁免）。#455 的期望产出原话只列了"反引号奇偶校验 ＋ 写入后列数回读校验 ＋ `--repair` 逃生入口"三项，不含"让竖线守卫具备反引号感知"；2026-09-04 附记显示该触发条件当前因内容外置而**偶然缓解、非根治**。design.md 决策点 3 就"是否顺手在本包内一并解决"给出分析与不建议同车的理由，**不假装本包覆盖了 #324 的全部未闭合项**。
2. **校验 A 只能判定"这一段新值自身的反引号是否闭合"，不能判定"这段新值与既有格内容拼接后是否仍然闭合"**——理论上存在"新值本身闭合、但与相邻列的既有内容产生跨列反引号交互"的边界情形（可能性极低，因为反引号跨度不跨"|"分隔符去匹配相邻格，但**本包不假装已经用现网数据验证穷尽了这一点**）；这正是校验 B（写入后回读）作为最后一道防线存在的理由，而不是把全部信心押在校验 A 上。
3. **`--repair` 仍然是一个需要人手动判断"该不该修、修成什么"的入口**——它只解决"入口被锁死、只能脱离工具手改"这一个问题，不解决"怎么修才是对的"这个语义问题（那仍然需要操作者读懂损坏前的行原意）。design.md 决策点 4 讨论了是否要求 `--repair` 附带"你为什么确认这样修是对的"的留痕字段。
