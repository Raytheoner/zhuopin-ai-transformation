## Why

队列 §一 #416 ⑶：**企微机器人的 `release` 被拒 ⇒ 队列锁死 30 分钟**，已三次（2026-08-24 18:00／2026-08-26 08:16／2026-08-26 13:19），**每次都紧跟专员回件到达**，锁一直挂到 30 分钟自动陈旧才被接管，期间所有人类会话无法写队列。

**真因已由受控复现坐实**（不是相关性推断）：在玩具 git 仓库里让 `who=企微机器人` 持锁、只追加一行自己的收件登记行、同时让工作区存在一个**属于别的会话**的脏文件，`release` 当场被拒，文案为：

```
⑹ 登记完整性：2 个脏文件不属于任何待处理 §二 批次的文件清单
  【本次持锁期间新出现】    - queue.md
  【acquire 之前就已经脏（可能来自并发 session）】    - 某个别的会话正在改的方案件.md
  两条出路：⑴ 为它们登记 §二 批次；⑵ …在本次 note 或本次触碰的队列行内写「登记豁免：<理由>」
```

**⇒ 缺陷的准确表述**：`_registration_completeness_violations`（校验⑹）只豁免 `SWEEP_LOCK_WHO`，**不豁免 `AIBOT_LOCK_WHO`**；而它度量的是 `_local_git_status_paths(repo_root)` ——**整个仓库的脏文件，不是持锁者自己碰过的文件**。于是：

1. **机器人被别人制造的脏文件挡住**。它能否释放锁，取决于**此刻是否恰好有另一个会话在改别的文件**——这解释了为什么三次被拒都发生在有人在办的时刻，而 13:55:38 同一条链路工作区干净时**没有**被拒。
2. **机器人不会写「登记豁免」**，也无法判断别人的脏文件该不该登记（那是别人的活）。两条出路它一条都走不了。
3. **机器人自己的那一行也算"未覆盖"**——因为它**从不登记 §二 批次**：它走 `append_task_and_sync_to_git` **自己 commit 自己 push**（审计事件 `queue_sync_pushed`），失败另有降级路径（`queue_sync_degraded` ＋ pending 补录 ＋ `_mark_row_unsynced_safely`）。

🔑 **判据**：**校验⑹ 的适用对象是"要靠别人来提交自己改动的那种持锁者"。** `SWEEP_LOCK_WHO` 已因"它就是来提交的那个人"被豁免；**机器人同样是自己提交自己的，只是这一点当初没被识别**——与 #333② 一模一样的疏漏形态：一条既有的合法路径，校验从未认得它。

⚠️ **同族第二形态（比本条更值得记住）**：一个把**全局状态**当作**本次动作的责任范围**来度量的校验，必然在并发环境里错怪无辜者。校验⑹ 想问的是"你改的东西有没有人管"，实现成的却是"仓库里还有没有没人管的东西"。

## What Changes

（拟议，**本次不实现**）

- `工具-共享文档编辑锁.py::_registration_completeness_violations` 的豁免分支由"仅 `SWEEP_LOCK_WHO`"扩为"`SWEEP_LOCK_WHO` 或 `AIBOT_LOCK_WHO`"，理由取自二者共同的性质——**都自己提交自己的改动**，校验⑹ 的适用前提对它们不成立。
- 豁免 SHALL 仅作用于校验⑹；机器人仍须通过其余各项 release 校验（列数、关键格、组内编号重复、归档号重复、称呼判据等）。
- **BREAKING**：`release` 在 `who=企微机器人` 且存在未覆盖脏文件时，返回由"拒绝"变为"放行"。这正是本变更的目的，但它确实改变了既有对外行为，故必须走本流程。

**备选方案（design.md 决策点 2 展开）**：把校验⑹ 的度量范围从"仓库全部脏文件"收窄为"本次持锁期间该持锁者实际改动的文件"。**更治本，但影响面大得多**（改变所有持锁者的判定口径，含人类会话），且 `dirty_at_acquire` 快照当初被明确记为"**不再用于过滤**、只用于归因"（其差集判据已被取证推翻）。⇒ 建议本次取窄修法，把宽修法登记为独立候选。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？** 「这个持锁者的改动，是不是要靠别人来提交」——`SWEEP_LOCK_WHO` 豁免时这条判断已被使用，但**只落在那一个身份上，没有被表述成一条可复用的判据**，于是机器人这条同类路径无人识别。本变更把它显性化为"自行提交自身改动的持锁者"这一类。
2. **由谁显性化？** #416 ⑶ 取证（2026-08-26 环境总线三次事故记录）＋ 本次受控复现；持有人＝环境保障线，仲裁人＝Shao Peishen。
3. **用什么方法提取？** **受控复现**——静态定位出可疑分支后，在玩具 git 仓库里构造"机器人持锁 ＋ 他人脏文件"场景直接触发拒绝，并与 `SWEEP_LOCK_WHO` 对照。**这比派单件原定的"先用 ⑵ 修好的 stderr 复核真因"更强**：stderr 只能告诉我们哪条文案，复现能证明因果。
