## ADDED Requirements

### Requirement: 修复既有破损行不得被预留归属校验判为新增
release 时的③预留归属校验 SHALL NOT 把"修复一条此前行头损坏、因而在 acquire 快照中解析不出编号的既有行"判定为"本次凭空新增、未经预留的行"。系统 MUST 以一条不依赖人工声明的机器判据识别这一情形——该编号若已存在于版本库 HEAD 中同一分区，则该行不是新增行，本项校验不适用。该机器判据无法取数时（不在 git 工作树内、HEAD 中读不到该文件、git 调用失败），系统 MUST NOT 静默放行，而 SHALL 退回原有拒绝逻辑并在拒绝文案中指明可用的显式逃生阀。

本豁免 SHALL 仅作用于"预留归属"这一项判定，MUST NOT 削弱同一行仍需通过的组内编号重复与已归档编号重复两项独立校验。

#### Scenario: 修好行头断裂的既有行后可正常释放锁
- **WHEN** acquire 时某行行头断裂（快照解析不出其编号），持锁期间该行被修复，且该编号已存在于 HEAD 同一分区
- **THEN** release 不因"不属于本次预留集合"拒绝，锁正常释放

#### Scenario: HEAD 中不存在的新编号且未预留仍被拒绝
- **WHEN** 本次新增一条编号在 HEAD 同一分区中不存在、且未经预留的行
- **THEN** release 仍因"不属于本次预留集合"被拒绝

#### Scenario: 取不到 HEAD 基线时不静默放行
- **WHEN** 仓库根不在 git 工作树内，本次存在未预留的新编号且行内无逃生阀标记
- **THEN** release 仍被拒绝，拒绝文案指明可在行内写逃生阀标记放行

#### Scenario: 行内逃生阀标记放行并留痕
- **WHEN** 本次新增/修改的行任一单元格内含预留豁免标记及理由
- **THEN** release 不因"不属于本次预留集合"拒绝；该标记随行留存，可被 grep 计数
