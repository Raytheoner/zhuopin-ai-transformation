# queue-write-root-fix-414 Design

## 决策点 1：竖线校验的写侧 / 读侧口径分离

**问题**：`has_bare_pipe` 既有语义是"反引号包裹不豁免"，其 docstring 给出的理由是"本项目现有表格解析对整行做原样 `split('|')`，不具备反引号感知能力"。**该理由自队列 #314 起已不成立**——`split_row_cells` 已是反引号感知的，生产队列 §一 #324／#326 两行正文里就带着被反引号保护的竖线，且两行都正确解析为 8 列。

**实测**：把 `validate_row_cells` 不加区分地用于读侧（对已解析的行做 lint），当前生产队列**5 行误报**，其中 2 行正是 #324／#326。

**决策**：**不动 `has_bare_pipe` 的既有语义**（改它属改变全项目口径，且写侧从严是刻意的），改为给 `validate_row_cells` 加 `source` 参数：
- `"write"` —— 待写入的字段值，竖线一律拒绝（沿用 `append-row` 既有行为，零放宽）。
- `"parsed"` —— 已被 `split_row_cells` 切好的单元格，跳过竖线检查。

**为何不合并成一个口径**：两侧问的不是同一个问题。写侧问"这个值能不能安全写进一个格"，读侧问"这一行现在是不是坏的"。合并必然二选一：从严则读侧误报两条结构完全正常的行，从宽则写侧放开一条已知会撑列的入口。

**弃案**：让 `has_bare_pipe` 变成反引号感知 —— 改变既有模块对外语义（门槛③），且写侧从严本身有价值（写入那一刻拒绝，比事后发现撑列便宜），不为省一个参数去换。

## 决策点 2：🔴 「按字样识别 shell 污染」实测否决

`#414` 行内建议 ⑶ 原文要求：「疑似被 shell 污染的痕迹（如整格为空、含 `Is a directory`／`command not found`、或含多行路径列表）即告警」。

**照此实现后对当前生产队列实测：5 行全部误报**——
- §一 **#414 自己的「任务」格与「期望产出」格**，因为**它正是描述这个 bug 的那一行**，正文里就写着 `Is a directory`；
- §一 #98「状态」格合法地讨论 `Permission denied`；
- §二 一条批次行的「文件清单」格同理。

🔑 **判据**：**这类判据把「格子里被污染成了报错文本」与「格子里在谈论报错文本」当成同一件事，而它们在字面上无法区分**——一个负责记录事故的载体，必然会大量引用事故的原文。**判据越贴近事故原文，越必然打到记录事故的那一行。**

**决策**：**不实现字样判据**，只保留**结构性**信号（格内换行、关键格为空/非数字、列数、格位哨兵）——它们不依赖正文措辞，不会因为"有人在写关于它的文档"而误报。

**为何这条比它拦下的 bug 更值得记住**：**误报会把调用方推去绕过守卫**，而"绕过"正是修复面 B 要消灭的东西。一道误报的守卫，比没有守卫更糟。代码内已按此写下长注释，防止后人再照 #414 行内建议 ⑶ 的字面重做一遍。

## 决策点 3：🔴 更正派单件 A3 的一条判断（「13 列而 lint 报通过」复现不出来）

**派单件原文**：「实测 `#414` 一度为 **13 列**（`awk -F'|'` 数得出），而 `工具-队列结构lint.py` **报通过**。请复现并修。」

**实测结论：该形态复现不出来。** 构造一条真正 13 列的 §一 行，现有列数校验**当场就报**（`§一 行列数为 13（应为 8…）`），已配对照单测 `test_genuine_column_count_violation_was_already_caught` 锁死这一事实，防止后人再把它当待修缺陷重开一轮。

**原报告的成因**：`awk -F'|'` **不认反引号保护**。对当前生产队列跑同一条 awk 命令，§一 #324 数出 12 列、#326 数出 9 列，而两行实际都是正确的 8 列——差额全部来自被反引号正当包裹的竖线。**#414 行内那次 12 格的记录，与本次 13 列的说法，极可能都是同一个测量工具误差。**

**真盲区是另外两种**（均已复现并修）：
- **C · 编号格被清空** —— `_table_data_rows` 把「首格为空」当表头/分隔行跳过（`_TABLE_HEADER_FIRST_CELLS` 含空串），该行**连列数校验都跑不到**。这正是 #414 行内记录的事故形态「列位错置 → 编号格 → 行头断裂，grep 与队列查询双双找不到该行」。
- **D · 行首竖线丢失** —— `split_row_cells` 返回 `None`，整条被丢弃。

🔑 **元判据**：**一行「坏到连解析器都不认它是一行」的数据，会从所有按行校验的判据里彻底消失，于是 lint 报「通过」——通过的意思是「我检查过的都没问题」，不是「没问题」。** 同族＝「工具静默回退」（取证知识库 §二）：坏消息让人追根因，而"太干净"的结果不会。

**判据收窄以保 0 误报**：C 要求"其余格确有内容且不是分隔行"；D 要求"行尾是 `|` 且竖线 ≥3"（正文里偶然出现的竖线不命中）。两条对当前生产队列实测 0 误报，并配回归护栏单测 `test_real_queue_files_have_no_broken_row_heads`。

## 决策点 4：release 自愈出口选 HEAD 存在性，而非纯逃生阀

**死锁形态（2026-08-26 实测）**：`acquire` 取快照那一刻某行行头是断的 ⇒ **快照解析不出它的编号** ⇒ 它不在 `old_numbers` 里；持锁期间把它修好之后，release 看到一个"快照里没有、现在有"的编号 ⇒ 判为**凭空新增、未经 `--reserve` 预留** ⇒ 拒绝释放；而此时 `acquire` 又被自己那把锁挡住 ⇒ **只能等 30 分钟自动陈旧**。

🔑 **判据**：**一个只认「快照里有没有」的校验，会把「修好一行」和「凭空造一行」当成同一件事**——因为坏行在快照里本来就是不可见的。⇒ 凡以"解析结果"为基线的差分校验，都要问一句：**基线本身解析失败时，它把什么误判成了新增？**

**选型**（派单件给了两条，取前者为主、后者兜底）：
- ✅ **主：HEAD 存在性豁免** —— 该编号若已存在于 git HEAD 同一分区，它就不是新行。**机器可判，不需要任何人记得做什么**，符合 CLAUDE.md §5「机制化优于人守」。
- ➕ **兜底：行内 `预留豁免：<理由>`** —— 只覆盖 HEAD 也读不到的残余情形（破损在 HEAD 里就已存在／不在 git 工作树内）。完全复用 `WIP豁免：`／`串行豁免：` 既有范式：写在行内、随行留痕、可 grep 计数，**不新增写盘路径**。

**fail-safe 方向**：`_head_row_numbers` 取不到时返回 `None` 而**非空集合**——空集合会被当成"HEAD 里一个编号都没有"，从而把每一行都判成新增，那是静默回退到一个看起来合理的错误答案。返回 `None` 时该豁免不生效，退回原有拒绝逻辑（但拒绝文案会提示逃生阀），**从宽的方向留给显式留痕，不留给静默**。

**刻意不做**：不豁免"组内编号重复"与"与已归档编号重复"两项——那两项抓的是真正的撞号，与本次死锁无关。配套反例单测 `test_genuinely_new_unreserved_row_still_blocked_in_git_repo` 锁死这一边界：**没有它，"豁免生效"与"整项校验被改废了"无法区分。**

## 决策点 5：多入口并用一律拒绝，不做静默取舍

`--cell`／`--set`／`--cells-json`／`--stdin-json` 四选一，给多个即 fail-loud。**不实现"以某个为准、其余忽略"**——静默取舍正是本变更包要消灭的那一族失效（内容落错位置而不报错）。同理 `build_row_cells` 对缺列 fail-loud、不补空串；`--set` 里再写编号列亦拒绝（两个来源就有两个真相）。
