## 决策点 1 · 判据放在哪一层：`zhuopin_platform.shared_tools`，不放消费者侧

**问题**：闭环判据有三个消费者——`工具-跟进闸查询.py`（新）、`工具-共享文档编辑锁.py`、`aibot_service`。而本仓库既有惯例是「**判据独立实现、不跨 `0-学习与工具/*.py` 互相 import**」（`工具-队列查询.py` 文件头原话），编辑锁的 `_followup_readme_rows` 还专门写了「本工具不 import aibot_service 包」。

**决策**：**判据一份、解析各自。**

- **判据**（什么算闭环、哪份回件对哪封信）⇒ 收进 `zhuopin_platform.shared_tools.followup_gate`，三处共用。理由：`queue_table` 已经为「表格切分/列数」立过同样的先例（#306/#307/#313），位置、引导方式、兜底桩、CI 可 import 断言四件套全部现成。
- **解析**（怎么从 md 里把行切出来）⇒ 保持各自实现不变。理由：那是几行纯文本切分，两处各自维护成本极低，而强行统一会把编辑锁拖进对 `aibot_service` 的包依赖。

**⇒ `followup_gate` 的公开函数一律只收「已经切好的单元格文本」，不碰文件、不解析表格。** 这条边界写进了模块 docstring，防止下一棒顺手把解析也塞进来。

## 决策点 2 · 编辑锁的串行闸改认四态（**改的是既有对外语义，本包最需要被审的一条**）

**现状**：`_validate_followup_readme_release` 只认 `📥 已回件并回灌`。
**README 正文（2026-08-18 起）**：闭环四态。
**⇒ 判据分裂已存在 3 天，且已产生一次真实绕行**（质量部#7 走 `串行豁免：`）。

**决策：改机器侧，对齐书面纪律。** 判据分裂时该改的是偏离纪律的那一侧，不是反过来把纪律迁就机器。

**⚠️ 这是放宽还是收紧？——是放宽，且必须说清楚。** 改后有三种状态（`✅ 无需回复`／`📨 已确认闭环`／`❌ 已作废`）从「拦」变成「放」。**但这三种状态本来就该放**：它们是 README 明文列出的闭环形态，此前之所以被拦，是机器没跟上文档。**放宽的边界是精确的**：`✅ 已推送`／`✅ 已发`／`⏳ 待你审`／`🆕 待发`／`⏸ 暂缓` 五种在途态一个都没放。

**没有一并做的一件事**：`❌ 已作废` 判为闭环，意味着「把上一封作废」可以开闸。这在语义上正确（作废的信不再等回件），但**它同时也是一条可被滥用的捷径**——不想等回件就把前信标作废。本包**不加防滥用判据**（那需要「作废须带理由 ＋ 谁批准」这一整套，属 S5 范围），只在此记录该风险，留给 S5。

## 决策点 3 · 桥二挂在**队列** release 上，不挂 README release 上

拆件回灌这个动作发生在队列这一侧（人把 §一 入信行改成 `[S:done]`）。**把校验放在动作发生的那一刻，才谈得上「拆件的人不可能忘」。**

挂 README release 上会怎样：一个只是去改 README 别的行的人，被一条与他无关的存量不同步拦住——**惩罚了错误的人**，而真正忘了转态的那个人当时早已 release 走了。

## 决策点 4 · 逃生阀只认「本次持锁触碰过的行」，不认队列全文

**首版实现按队列全文匹配 `转态豁免：`，写完立刻自我推翻。**

两份队列文件合计 1.9 MB。全文匹配意味着：`转态豁免：` 一旦写进任何一处（哪怕是一条 2026-07 的历史行、哪怕只是在正文里**引用**了这个词），这道门禁就被**永久关掉**，而且此后不会有任何人发现——因为它的失效形态是「一直放行」，与「本来就没有违规」长得一模一样。

**决策**：取材面 ＝ 本次持锁的 `note` ＋ `_diff_touched_rows` 算出的本次触碰行。**逃生阀必须一次一用。** 已配反例单测把这个陷阱锁死（`test_豁免只认本次持锁触碰过的行不认文件里的陈年旧字`）。

同一族教训在本仓库已有先例：`串行豁免：` 只看新增行自身的单元格，不看全文。

## 决策点 5 · 桥一放在 `connection.py`，不放 `intake.py`

派单件原文写的是「在企微机器人自动追队列 §一 入信行的**同一次动作里**」。字面读会放进 `intake.archive_inbound_message`。

**不放那里**，两条理由：
1. `intake.py` 文件头的**门禁①是一句结构性保证**：「代码路径只允许三类动作——写文件归档／追加队列行／调用 connector 发确认收讫回执」。往里加第四类写盘动作，那句保证就不再成立，而它是 spec `wecom-feedback-intake` 的门禁依据。
2. `sync_after_archive`（同族的旁路增强）本来就挂在 `connection.py::on_message` 这一层。

**⇒「同一次动作」指的是同一条消息的同一次处理，不是同一个函数体。**

## 决策点 6 · 桥一拿不到锁时**不**建暂存补录路径

队列侧有 `queue_lock_pending.py`（锁忙则暂存、下次补录），因为**队列行丢了等于这条回件在调度视野里从未发生**（#286/#315 实测过的代价）。

README 这一格不同：即使本次没打上第九态，**桥二仍会在拆件 release 时把人拦下来**。**两座桥是冗余而非串联**，缺一座不会漏。

⇒ 只做有限重试（3 次指数退避）＋ 告警，**不新增第三个暂存文件**。少一个自动生成文件形态，就少一次 #328②（`*.editlock.mutex.stale` 未被 gitignore、企微群连响 17.1 小时）那样的事故机会。

## 决策点 7 · 第九态**不**覆盖原状态

`build_reply_arrived_status` 把新前缀放最前、**原状态原样接在后面**（`　━━━　原状态 ━━━　`）。

覆盖式写入会丢掉「这封信何时推送」——而**这一格没有任何别处的副本**，转闭环态时还要引用它。前缀在最前是因为闭环判据一律按前缀比对。

## 决策点 8 · S2 一期只 `--warn`，与 `claude-progress-section-lint` 同策略

上线时存量非零（实测 3 处活行）。一期就硬拦会立刻挡住所有人的 push，而「队列不得复述信状态」这条规则**如果第一天就被绕过，绕过的将是 lint 本身**。

**⚠️ 与 `bootstrap-stub-lint` 的区别要说清**：那道门禁上线前存量已实测清零、首次运行即为绿，故直接 `--enforce`；本道不是。**判据是「存量是不是真的 0」，不是「我觉得该不该严」。**

## 被实测推翻的规格假设（三条，逐条列出，不藏）

### ⑴ 派单件说「5 处存量里 4 处在 §二 历史批次行」——**实测 §二 一处都没有**

派单件 §三：「全库仅 5 处，其中 4 处在 §二 历史批次行（按「历史记录不追改」豁免），真正需要改的只有 §四 #65 一处。⇒ 判据须跳过 §二 批次行。」

**实测**（前后各 8 字窗口，命中数恰为 5，与派单件的计数一致）：

| 位置 | 分区 | 片段 |
|---|---|---|
| 机制环境 #65 | **§四** | `等采购部#15 闭环` |
| 业务场景 #249 | **§一** `[S:done]` | `待定，须排在财务部#11 回件` |
| 业务场景 #150 | **§一** `[S:done]` | `待采购部#10 回件` |
| 业务场景 #264 | **§一** `[S:partial]` | `待领（P2；须排在财务部#11 回件` |
| 业务场景 #361 | **§一** `[S:open]` | `等姚祖怡采购部#16 闭环` |

⇒ **「跳过 §二」这条豁免规则本身是对的（§二 确实是历史记录），但它一处都豁免不到**——真正需要豁免的是 §一 里 `[S:done]` 的行。若照派单件原文只跳过 §二，会对 2 条已完成的历史行**持续误报**，正是派单件想避免的那个后果。

**修法**：跳过 §二（保留，语义正确）**＋** §一 `[S:done]` 行按「历史记录不追改」豁免。**两类豁免都必须把数打印出来**——静默豁免与本判据要治的毛病同族。

⇒ **活行违规 3 处**（#65／#264／#361），非派单件预期的 1 处。派单件写「若远大于 1 说明判据过宽」，3 不属于「远大于」，且逐条核过都是真违规。

### ⑵ 派单件 §一 说 CLI 判据须「与既有 `_validate_followup_readme_release` 保持同源」，同时又要求认闭环四态——**这两条当时是互斥的**

既有实现只认 `📥`。要同时满足，只能改既有实现。⇒ 见决策点 2。**派单件没写这一层，是因为写它的人当时不知道两处已经分裂了。**

### ⑶ 派单件 §六 给的验收真值「姚祖怡 🔒 锁」——**执行时已不成立**

派单件写「当日真值：姚祖怡 🔒 锁（采购部#17 在途）；陈忱 ✅ 开」。实际跑 `--to 姚祖怡` 得 **✅ 开**：主工作区 README 在派单之后、本 session 之前，已由「Cowork 拆件巡逻第二班」把 采购部#17 转为 `📥 已回件并回灌`（该改动当时尚未 commit，只在主工作区工作树里）。

**⇒ 这不是工具算错，恰恰是工具算对了**：它读的是**主工作区的权威真身**（`REPO_ROOT` 经 `git rev-parse --git-common-dir` 解析，队列 #314① 的既定口径），而不是本 worktree 那份创建时的旧快照。**派单件写下的那个「真值」本身就是一个会过时的快照——这正是本包要消灭的东西。**

陈忱 ✅ 开则与派单件一致。

## 已知边界（必须随文案一起说出去，不得让人以为「零违规＝全同步」）

1. **配对覆盖率有限**。桥一/桥二的配对只走「归一化后 stem 逐字相等」，两类天然在覆盖面之外：
   - **纯文本回件**（归档文件名主题段恒为 `文本反馈`）——无从确定指向哪一封信。实测 37 条入信行里 **23 条**属此类。
   - **README 行未带 `目标文件：` 标注**（队列 #241 之前的历史行）——实测 49 行里只有 **14 行**有。

   **这是设计取舍，不是缺陷**：硬配会造出比漏配更难发现的错误（配错了，会把 A 信的状态改成 B 信的回件结论）。派单件 §二 原文「匹配不上时不要猜」。

2. **入信行归属粒度是部门，不是人**。入信行只带归档路径，路径里只有部门段。当前五个部门各只有一位在册收信人（`department_mapping.yaml`），故部门级等价于人级；**哪天某部门有了第二位收信人，`最近入信` 那一行会把两人的混在一起**。代码里已留路标注释。

3. **`IT部` vs `IT`**：README 写 `IT部 · 陈承`，`department_mapping.yaml` 把陈承映射到 `IT` ⇒ 归档目录是 `7-外部文档/IT/`。只按 README 写法找目录会对陈承**恒返回零条入信行、且不报错**（教科书式的「工具静默回退」）。已按别名表处理并配单测。

4. **S5 未做**：README 状态列仍可被人手改。S3 只把「读」收敛到一个出口；只要那一格还能被手写，它就还会与队列里的 506 处引用打架。这是拍板 (b) 的既定范围，不是遗漏。
