## ADDED Requirements

### Requirement: 闭环判据 SHALL 有唯一权威实现
「一封跟进信的发送状态算不算闭环」SHALL 只有一处实现（`zhuopin_platform.shared_tools.followup_gate`）；闸查询 CLI、编辑锁 `release` 校验、企微机器人入信桥三处消费者 MUST 委托同一实现，MUST NOT 各自持有一套状态字面量。

闭环态 SHALL 为四者之一：`📥 已回件并回灌`／`✅ 无需回复`／`📨 已确认闭环`／`❌ 已作废`。判定 MUST 在剥除 markdown 强调星号与首尾空白（含全角空格）后按**整串前缀**比对，MUST NOT 只比对首个 emoji。

归一化后仍不属任何已知形态的状态 MUST 被归入独立的「未知」类并向调用方显式暴露，MUST NOT 被静默归入在途或闭环。判闸时未知类 MUST 按在途（闸锁）保守处理。

#### Scenario: 四种闭环写法全部认得
- **WHEN** 状态列取值为 `✅ **无需回复**（起草时即判定）` 这类带 markdown 强调的闭环写法
- **THEN** 判定为闭环、闸放行

#### Scenario: 在途写法一律不放行
- **WHEN** 状态列取值以 `✅ 已推送`／`✅ 已发`／`⏳ 待你审`／`🆕 待发`／`⏸ 暂缓` 之一开头
- **THEN** 判定为在途、闸锁

#### Scenario: 未知写法暴露而非静默归类
- **WHEN** 状态列出现权威实现未收录的写法
- **THEN** 分类结果为「未知」，闸按锁处理，且调用方输出中含可见告警

### Requirement: 只读闸查询 CLI
SHALL 提供 `0-学习与工具/工具-跟进闸查询.py`，支持 `--to <收信人>`（按收信人算闸）、`--all`（全部收信人）、`--json`（机器消费）。该工具 MUST 只读、零写盘。

「最近一封」SHALL 按 README 表格顺序取该收信人的最后一行，MUST NOT 按日期列排序（日期列存在补记情形）。

「下一个可用号」SHALL 只按下表实际出现的 `<部门>#<N>` 最大值推算，MUST NOT 读 README 顶部那段自由文本的「当前各部门下一个可用号」。

README 表格解析 MUST 复用 `aibot_service.readme_table.iter_rows`，MUST NOT 另写一套正则拆表。

#### Scenario: 最近一封已闭环则闸开
- **WHEN** 某收信人在 README 中最后一行的发送状态属闭环四态之一
- **THEN** 输出闸开

#### Scenario: 表格顺序优先于日期
- **WHEN** 表格最后一行的日期早于其上方某一行
- **THEN** 仍以表格最后一行为「最近一封」

### Requirement: 闸锁不是错误
闸开与闸锁 SHALL 同为退出码 `0`。退出码 `2` SHALL 仅用于 README 解析失败或收信人不存在。收信人不存在时 MUST 一并列出已知收信人。

#### Scenario: 闸锁仍返回 0
- **WHEN** 查询对象的最近一封仍在途
- **THEN** 进程退出码为 0

#### Scenario: 收信人不存在返回 2 并给出已知名单
- **WHEN** `--to` 指定的收信人不在 README 清单里
- **THEN** 退出码为 2，且输出含已知收信人列表

### Requirement: 人读格式与 JSON 由同一份数据渲染
两条渲染路径 MUST 消费同一个报告对象，MUST NOT 各自实现一套取数逻辑。

#### Scenario: 两侧字段一致
- **WHEN** 对同一收信人分别取人读输出与 `--json` 输出
- **THEN** 闸状态、依据信编号、告警列表三者逐一对应一致

### Requirement: 编号列括注 SHALL 被容忍且矛盾 SHALL 被告警
编号列解析 MUST 容忍 `（待发，暂不占号）` 这类括注，仍能取到 `<部门>#<N>`。

当编号列自称「未发／待发／暂不占号」而状态列表明该信实际已发出（已推送态，或除「已作废」外的闭环态）时，SHALL 输出告警——README 顶部「下一个可用号」段与下表编号列是同一事实的两份副本，已连续失真四次。

#### Scenario: 括注行仍被正确取到并告警
- **WHEN** 某收信人最近一行编号列为 `IT部#7（待发，暂不占号）`、状态列为 `📥 已回件并回灌`
- **THEN** 该行被取为「最近一封」、闸判开，且输出含编号与状态矛盾的告警

### Requirement: 入信行 SHALL 逐份解析后合并
扫描队列入信行 MUST 遍历全部物理队列文件、**逐份解析后合并**，MUST NOT 先把多份文本拼接再解析一次。某份队列文件缺失时 MUST 发出可见提示，MUST NOT 静默当作「没有入信行」。

部门目录名与 README 部门写法不一致时（如 README 写 `IT部`、归档目录为 `IT`）MUST 仍能找到入信行。

#### Scenario: 归档目录名与 README 部门写法不一致
- **WHEN** 收信人所属部门在 README 中写作 `IT部`，而归档路径为 `7-外部文档/IT/...`
- **THEN** 该入信行仍被计入

#### Scenario: 队列文件缺失时可见
- **WHEN** 某份物理队列文件不存在
- **THEN** 结果中出现指明该文件缺失的条目，而非静默少一批行

### Requirement: 入信已到而 README 未转态 SHALL 告警
闸锁且存在该部门未拆件（非 `[S:done]`）的入信行时，SHALL 输出「入信已到但 README 未转态」告警。

闸未开且存在**已拆件**且**确定配对到该信**的入信行时，SHALL 输出更强的一条告警，指明该行已拆件、README 仍未转闭环态（即 `release` 侧会拒绝的同一形态）。

#### Scenario: 已拆件而未转态给出强告警
- **WHEN** 某封信的入信行状态为 `[S:done]`、且其归档文件名确定配对到该信，而 README 该行仍为在途态
- **THEN** 输出含「已拆件」与「请先转闭环态」的告警
