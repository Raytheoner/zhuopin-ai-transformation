# followup-letter-state-single-source Proposal

## Why

**串行闸永远不会自己开。**

「一封跟进信此刻是什么状态」，唯一权威源是 `6-人才与组织/部门AI专员跟进/README-跟进机制与命名约定.md` 的「发送状态」列（S1，Shao Peishen 2026-08-21 答队列 §四 #85 选 (b) 确立）。而**机器只写队列**：

- 回件到达 ⇒ 企微机器人自动追 §一 入信行 ✅ 做到了
- 拆件回灌 ⇒ 人写队列行 ✅ 做到了
- **README 那一格 ⇒ 没有任何东西去改它** ❌

闸只读 README，中间那一步一直是人。**2026-08-21 一天之内咬了两次**：

| 事故 | 形态 |
|---|---|
| 质量部#8 | 回件已拆件、已原样回灌 `§一 #340`、还派生了 `§四 #83`——README 那格仍是 `✅ 已推送`，**闸锁着**，直到 Shao Peishen 追问才由人转态 |
| 采购部#17 | 回件 13:13:24 落盘、队列 13:15 自动追行——README 仍 `✅ 已推送` |

### 为什么不是「合并成一个文件」

他的原议是把队列与 README 合并成一处唯一读写。架构设计件（`1-转型规划/0-全景路线图/跟进信状态单一可信源-架构设计-2026-08-21.md`）实测否掉了：两个载体**存的不是同一份状态**（一个存「信」、一个存「任务」），真正发生的是**双向交叉引用 506 处**。合并之后这 506 处一处都不会消失，只是都搬进同一个文件里——**引用只要是「人写的文字」就会过时，与它写在哪个文件无关**。

⇒ 正解是**写侧单一化 ＋ 读侧派生化**。本包做 S2/S3/S4（S1 是纯文档、已落地；S5「状态列机器专有」按拍板 (b) 留作下一步）。

### 🔴 顺带修一处真实的判据分裂（不是本包新造的口子）

README 串行原则段 2026-08-18 起写的是**闭环四态**（`📥 已回件并回灌`／`✅ 无需回复`／`📨 已确认闭环`／`❌ 已作废`），而 `工具-共享文档编辑锁.py::_validate_followup_readme_release` 一直**只认第一个前缀**。代价是实测过的：质量部#7 形态为 `✅ 无需回复`、按纪律闸早已打开，机器却不认，起草下一封时只能编一条 `串行豁免：` 去绕过它——**拿逃生阀去绕它本来要拦的那件事**；根 CLAUDE.md §5 把这条边界原样记了下来。

本包把该判据收归**一份权威实现**（`zhuopin_platform.shared_tools.followup_gate`），三处消费者共用。**判据分裂时该改的是偏离书面纪律的那一侧**，故编辑锁改为认四态。这是修分裂，不是放宽门禁。

## 本次退休哪一个既有守卫（协议〇.9 措施 B，机制类变更包强制）

**退休对象：`FOLLOWUP_SERIAL_CLOSED_PREFIX` 这个单前缀判据本身。**

它被 `FOLLOWUP_SERIAL_CLOSED_PREFIXES`（权威模块提供的四态）整体取代；单数名保留**仅供提示文案取首项**，不再是任何判定路径上的取值。**这是一进一出的实质退休，不是改名**——退休之后，「什么算闭环」在整个仓库只有一个可改的地方。

**同批退休的第二项：「起草下一封前先人工查 README 该收信人最近一行」这条人守步骤。** 根 CLAUDE.md §5 场景固定流程第 8 步与「跟进信串行原则」两处都写着这个查法，2026-08-20 §四 #74 还为它专门改过一次措辞。本包之后它由 `工具-跟进闸查询.py --to <收信人>` 一条命令回答，**正文降级为一行指针**（沿用 #206 范式，正文不删）。

**不退休、也不能退的一项**：`_validate_followup_hold_consistency`（⑥ 暂缓一致性）**不被本包取代**。⑥ 判的是「队列行说暂缓、而 README 已是可发送态」（发信前），桥二判的是「回件已拆件、而 README 未转闭环」（回件后）——**同一条信生命周期的两头，互不覆盖**。用桥二取代 ⑥ 会把发信前那一头重新敞开。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？**
   - **「这个状态算不算闭环」**——四态口径此前只活在 README 正文与几个人的记忆里，机器侧只认一态。⇒ 本包已显性化为 `CLOSED_STATUS_PREFIXES`。
   - **「这份回件是回哪封信的」**——此前完全靠拆件人看文件名认。⇒ 显性化为 `reply_matches_letter`（含「专员常附 `-回复` 尾缀」这条只有做过拆件的人才知道的经验）。
   - **「编号列的括注还算不算数」**——`IT部#7（待发，暂不占号）` 这类写法此前无任何判据覆盖。⇒ 显性化为 `number_status_mismatch`。
   - **仍是默会、本包未显性化**：「一封信在什么条件下可判 `📨 已确认闭环` 而非 `📥 已回件并回灌`」——两者的选择目前仍是拆件人的判断。
2. **由谁显性化？** 持有人 **Shao Peishen**（口径权威）；backup **孙涛**（决策代理，根 CLAUDE.md §5）。拆件侧实操经验持有人＝历次拆件巡逻线。
3. **用什么方法提取？** **历史案例反推**——四态口径、`-回复` 尾缀、编号括注三条全部由 2026-08-21 对 49 行真实 README ＋ 37 行真实入信行的逐条比对反推得出，非凭空设计。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：**档 2（真实数据跑通）**。三项均已对**生产真身**跑通：`--all` 覆盖全部 5 位收信人并当场照出一条真实漂移（唐燕萍 §一 #369/#370 入信已到、README 未转态）；S2 判据在真实两份队列文件上给出 3 处活行 ＋ 2 处历史豁免；桥二全量扫描在真实数据上找出 2 封不同步的信。
- **晋档 3（内部服务）的条件**：⑴ 桥二的 2 处存量清完；⑵ 桥一在生产常驻服务上真实触发过至少一次（**「探针通了」不等于「机制通了」**——OP-0819-F 那条教训：`#82` 建成 9 天、每天在跑，却从未真实发出过一条消息）；⑶ S2 由 `--warn` 切 `--enforce`。
- **价值指标**（风险型）：**基线** ＝ 2026-08-21 当天「回灌完成到 README 转态」的人工延迟，实测两例分别为 **约 4 小时**（质量部#8，靠 Shao Peishen 追问才触发）与 **≥2 小时且当日未完成**（采购部#17）；**目标** ＝ 桥二上线后该延迟结构性归零（不转态就 release 不掉）。基线由 Shao Peishen 确认。
- **LLM 判据黄金集**：**不适用**——本包零 LLM 运行时判断，全部为确定性字符串判据。
