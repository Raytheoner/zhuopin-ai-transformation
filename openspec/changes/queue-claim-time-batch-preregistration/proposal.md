# queue-claim-time-batch-preregistration Proposal

## Why

跨桌任务队列.md 协议〇.1 已要求"认领先于动手"，但落地方式只把状态改成"在办"+登记触碰区，§二"待 commit 批次"是收工时才补登记的——这在 session 顺利收工时没问题，但一旦 session 中途失联（Claude Desktop 重启、被中断、或任何其它原因），它已经做完的实质改动就完全没有任何留痕：没有批次行、没有文件清单、没有 commit message，队列里既不知道谁在改、也不知道改了什么。2026-08-04 值周巡检取证（队列 #236）实测：一条 session 已完成对 SC8 场景 CLAUDE.md、姚祖怡跟进信 md/docx、session接力文件共 4 个真实文件的改动，因 Claude Desktop 同日被重启而永久失联，这 4 个文件变成无主孤儿——不仅没人能声明它们，还因为与 sweep 工具彼时的"unaccounted 全局门"耦合，连带挡住了 20 个本已正确声明、彼此毫无关系的批次跨天无法落库（该全局门问题已由队列 #238 批次隔离机制解决，但"孤儿从何而来"这一根因仍未解决）。

根因不是"忘了登记"，而是"回合制 session 没有回合可用来收工"——session 只能在被给到一个回合（用户消息/工具调用轮次）时才能执行动作，一旦人转去开下一个任务或客户端被关闭/重启，那条 session 永远不会再有机会主动执行"收工登记"这个动作。协议〇.1"认领先于动手"与协议〇.3"收工必写"两条纪律的时序设计里，唯一能保证一定会被执行的只有"认领"这一步——它发生在实质工作开始之前，此时 session 一定还活着、一定还有回合。故把批次登记的可靠锚点从"收工"移到"认领"。

## What Changes

- 协议〇.1（"认领先于动手"）新增：认领一个任务、准备开始实质工作之前，须在跨桌任务队列.md §二"待 commit 批次"登记一行**预登记批次**——batch_id 用任务编号或域+日期，文件清单先写"预期会改动的文件/目录前缀集合"（保守估计，收工时精确化），commit message 可留占位文案，状态标"在办（预登记，收工时精确化）"。
- 协议〇.3（"收工必写"）新增：收工时不再是"从零开始登记"，而是回到这一行**预登记批次**，把文件清单精确化为实际改动的文件、把 commit message 写成真实描述、状态改回可被 sweep 处理的"待处理"——若 session 从未收工（失联/中断），这行预登记记录本身就是可供后续核实的留痕，不再是"完全没有任何痕迹"。
- 新增：预登记批次若长期停留在"在办（预登记，收工时精确化）"状态超过阈值（对应失联/长期未完成的 session），需要被发现——具体检测机制、阈值、处理路径见 design.md 决策点 2。
- 新增：预登记这一步骤的执行方式——纯人工协议约定，还是工具化（如编辑锁工具 `工具-共享文档编辑锁.py` 的 `acquire` 顺带支持登记）——见 design.md 决策点 3。
- `专线opener模板库.md` 同步补一句"认领即预登记"的口令引用（不改其定稿的措辞体系，只加指针）。
- **BREAKING**：无——纯新增协议步骤与可选工具能力，不改变 sweep 现有对 §二 批次的解析/处理逻辑（§二表格结构、`_parse_section_two`/`_resolve_batch_files` 均不变），预登记批次在"收工前"状态列不含"待"字样，天然不会被 sweep 当作可处理的待处理批次误动。

## Capabilities

### New Capabilities

- `queue-claim-time-preregistration`：跨桌任务队列 §二"预登记批次"这一新状态形态的行为契约——何时必须登记、登记内容的最低要求、如何从预登记态收敛为可处理的"待处理"态、长期滞留预登记态时的检测与处理路径。

### Modified Capabilities

（无——跨桌任务队列.md 本身的协议文本此前未建立为 openspec capability，sweep 相关的既有 capability `sweep-startup-resilience`/`sweep-fork-alert` 均不涉及"批次何时被登记"这一前置环节，本变更不修改它们的 REQUIREMENTS。）

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？** 三处：① "预期文件集合"该保守到什么粒度才既有用又不至于认领时就要求预判全部改动——目前完全靠执行者的经验判断，无固定规则（design.md 决策点 1 给出推荐粒度，但"这次改动算探索性强还是范围明确"仍是人的判断）；② "陈旧预登记批次"的处理路径里，"重新认领 vs 转人工核实"该如何选择——取决于该预登记行的文件清单是否已经足够具体到可以直接被别人接手核实，这是个案判断，非算法可决；③ 预登记与协议〇.7 编辑锁的交互强度（认领这一步是否值得为了登记一行队列而抢锁、抢不到锁时是否允许降级为"先记进域接力文件待补"）——目前是根据"认领"动作的紧迫性做的权衡拍板，非从第一性原理推导。
2. **由谁显性化？** 本变更为跨项目治理机制（协议〇.1/〇.3 + 队列文件使用惯例），非对客业务场景，无部门专员对口；持有人＝环境保障线（Cowork，负责取证、判据设计与协议文本改写）+ CC 建造车间（负责工具化部分的实现，若采纳决策点 3 的工具化方案）；backup／仲裁＝Shao Peishen 本人（本项目技术决策人，本变更包 design.md 须经其审核批准方可 apply）。
3. **用什么方法提取？** 历史案例反推——本变更直接源自 2026-08-04 队列 #236 的真实故障复盘（4 个孤儿文件挡住 20 个批次），判据设计参照同族已落地机制（#171 分叉告警的 webhook 点名范式、#236(2) 孤儿脏文件告警的阈值+去重设计、#163 编辑锁 `--reserve` 取号"把加法从人手里拿走"的工具化思路）；不新增 L2 改判判例累积或 AI 起草·专家批改工作坊类方法，因本变更不涉及业务判断黄金集。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：本变更为**跨项目治理协议机制**，非独立业务场景，不适用四档"对客交付"口径；套用最接近的档位描述＝**档1 mock 验证**（design 审通过、协议文本与可能的工具化代码已实现并通过单测，但尚未经过至少一次真实失联场景的端到端验证——即"预登记记录真的在 session 失联后被后续 session 正确核实并收敛"这一完整闭环，受限于失联场景难以主动构造，初期只能靠自然发生的真实案例验证）。
- **晋下一档的条件**：晋**档2 真实数据跑通**——① 协议〇.1/〇.3 文本改写完成并同步两份 skill 源码（`zhuopin-queue-audit`/`zhuopin-kickoff-prompt`，按既有惯例，已安装版待 Cowork `save_skill` 同步）；② 若采纳工具化方案，编辑锁工具新增能力通过单测+一次真实 CLI 调用验证；③ 至少一次真实认领场景验证"预登记→收工精确化"全流程无阻塞（不要求真实失联，先验证正常收敛路径）；④ 值周巡检对账审计（skill `zhuopin-queue-audit`）纳入"陈旧预登记批次"检测项。晋**档3 内部服务**（全项目强制执行）的条件——上述验证完成后，Shao Peishen 确认无重大摩擦（如认领动作因登记步骤变得过重、锁冲突频发等），正式写入协议正文（去掉"试行"标注，若有）。
- **价值指标**（风险型）：消除"session 失联后已完成的实质工作完全无留痕、且拖累其它无关批次"的窗口——基线＝2026-08-04 队列 #236 真实故障（4 孤儿文件挡住 20 批次跨天），目标＝同类失联场景发生后，后续核实方可凭预登记记录在合理时间内定位到"谁在改、大致改了什么"，不再是"完全查无此人"。
- **LLM 判据黄金集**：不适用（本变更不含 LLM 运行时判断）。
