# Codex intent→deploy 阶段接力设计（已批准）

日期：2026-09-25。承接队列 §一 #648 与本变更包 `intent.md`；本文件是追加的架构设计，不改写已验收的三消费者结论。Shao Peishen 已选定“1a”：在现有接力入口上自动推进机器可验阶段，设计、ff、生产部署、真实发送保留逐项人工闸。Shao Peishen 随后明确回复“批准书面设计，写实施计划”；实施仍以该计划审阅为下一闸。

## 意图与完成判据

目标是把原 Claude Agent 已工作的任务驱动建造流程迁到 Codex：从真实队列任务和批准 intent 出发，产出 OpenSpec、隔离工作树内实现、逐项目测试、独立 review 与发布准备；能自动跨越已获授权且有机器证据的阶段，遇决策、不可逆动作、证据缺失立即停，并能从落盘状态恢复。Claude 只作流程来源，不作执行或回退。用户当前 Off LAN，`.51` 真实部署不得作为离线验收步骤。机制完整通过以前不启动业务场景开发。

完成不是脚本返回 0：必须有原生 Codex thread/turn/tool/hook、明确的阶段输入与产物哈希、目标 CI、独立 review、调度或人工唤醒路径、拒绝路径及重启恢复证据；最终报告分别给出“本地建造链已验收”“ff 已逐项授权并验收”“`.51` 待回 LAN”三种状态，不把离线等待写成已部署。

## 已有行为正本及复用边界

| 能力 | 既有正本/入口 | Codex 适配职责 |
|---|---|---|
| 队列身份、锁、落库 | `工具-队列查询.py`、`工具-共享文档编辑锁.py`、`工具-落库sweep.py` | 只调用专用入口；不用队列原文扫描或另建任务池 |
| 四档动作、停/续、心跳、转出及部署授权记录 | `工具-泳道看护状态机.py` 和 `zhuopin-lane-watch` 正本 | 复用 `classify/pause/resume/transfer-out/deploy-authorize`；不复制字典或创建第二套动作判据 |
| 看护件、opener、隔离批处理 | `工具-opener生成.py`、`工具-opener块lint.py`、`工具-opener批处理执行v2.ps1` | 生成 `Codex` opener、先 DryRun 对泳道/依赖，再经已迁移 provider 启动；不得静默从 guardian 改为无头 |
| 单任务上下文及模型证据 | `codex-handoff/handoff.py`、`model_provider.py` | 复用 `prepare` 的队列/HEAD 锚和 provider 原生审计；补跨阶段判定与恢复，不把 `output_needs_review` 当交付 |
| 完成、ff 与部署 | 既有完成探针、获授权的 `工具-待合分支巡检.ps1`、`zhuopin-lan-closeout` | 调用既有检查/授权入口；`.51` 只转出和指向正本，不复制快照/部署/冒烟/回滚程序 |

源端 `Task/Agent`、`claude -p`、Claude transcript、`save_skill`、`set_session_title`、Cowork 定时任务均不是 Codex 接口。新链只使用本机已验证的 Codex provider、当前工具和明确存在的调度器。中英文 last30days 及其他无关项目技能保持原状。

## 架构与状态所有权

采用薄适配器连接现有接口，不新建并行的泳道守护系统。单任务阶段状态存于 `handoff.py` 既有运行目录，含 task id、队列行、intent/设计批准引用及哈希、source HEAD、worktree、phase、attempt、原生 thread id、证据路径、评审结论与下一可行动作。泳道级暂停、答复、心跳、转出及部署授权仍只写现有 `lane-watch-state.json`；两者通过 batch/lane/task id 与证据引用关联，不互相镜像状态。重启时先读两个权威状态和实际 git/产物，再计算下一步，不信任仅有的进程退出码或旧哨兵。

入口分两种，互不偷换：

1. 单任务 `intent→release-ready`：`handoff.py prepare` 绑定真实队列行和批准 intent；适配器按阶段调度现有 provider/生成器/批处理/校验工具，适合单个任务。
2. “开启泳道看护”：保留源工作流的 LAN 探针、候选过滤、触碰区排波、看护件、默认批量上限与并发/错峰、心跳和四档处理。Codex guardian 接口先实现并验收，才能把这个口令标为可用；明确要求无头时才走现有批处理入口。若当前 Codex 会话无法持续持有看护循环，必须以真实 Windows 任务或 Codex automation 作为具名触发器且经单消费者验收；否则该模式停在“需人工重新唤醒”，不得声称后台自动看护。

批量任务与单任务共享阶段判定器，但批量的依赖 DAG 由既有排波结果提供。每泳道内串行、泳道间按现有限额错峰；一项失败只停它和依赖项，独立泳道继续。锁工具类排最后一波。看护会话发现工具缺陷按源规则登记派单，只有规则允许的当批极小修复例外。

## 阶段与证据闸

| 阶段 | 自动推进的充分证据 | 停点 |
|---|---|---|
| `intent` | 队列查询成功、任务可领、触碰区无冲突、批准 intent、HEAD/规则版本固化 | 来源缺失或冻结行停；不由模型补造授权 |
| `proposal/tasks` | OpenSpec 结构及内容机器校验，产物落盘、哈希和人可读摘要 | `design` 审归 🟡，需该任务明确审阅记录 |
| `implement` | 设计授权绑定当前文件哈希；干净隔离 worktree；项目/hooks 正常信任；实际 tool/hook 事件；改动仅在声明触碰区 | 未信任、HEAD 漂移、权限失败或主树泄漏即停并留证 |
| `test` | 按 CI 矩阵逐项目运行受影响测试，保存命令、退出码、报告及版本；必要时比较 master 基线 | 失败、漏跑、环境阻断分开记，不让模型文字覆写结果 |
| `review` | 独立于实施轮次的 Codex review，针对 implementation HEAD、diff、测试和规则；机器复核 review 所指 HEAD 与产物 | 结论不清、需修复则回到有界实施循环；次数上限后停等人 |
| `release-ready` | opener/产物/证据/队列回写齐备，报告剩余风险和可执行的下一授权项 | ff 属 🟡；无逐项授权不得合 master |
| `deploy` | 先 ⏭️ `transfer-out`；当次 LAN 实测 on、未绑定转出记录及逐项授权原文经既有 `deploy-authorize` 记录 | 由 `zhuopin-lan-closeout` 串行执行并登记冒烟/回滚证据；off/unknown LAN 均停 |

动作档位以 `工具-泳道看护状态机.py` 运行时结果为准：🟢 已授权可逆动作可自动；🟡 停等用户决策并持久化；⏭️ 转交 LAN 正本；🔴 对外发送、L2 签字、合规红线和 ASIL C/D 不代办。未知动作自动按 🟡，不能靠配置默默放宽。ff 的内容已在 master 时可用既有 patch-id 预检记录跳过；真需合入仍要原授权及六关。

## 失败、恢复与授权语义

- 状态写入用原有单任务互斥和原子文件更新；每次 attempt 有独立 ID。启动前核对状态与当前 HEAD、worktree、授权证据哈希，避免重复触发双跑或拿旧授权执行新内容。崩溃后保留 lock/attempt/原生证据，由恢复命令读证据判定；不能自动删除不明 stale lock 或把未知运行判成功。
- 当前原生上下文计量缺失、模型失败/超时、hook 未运行、工具事件缺失、无产物、未通过测试均 fail closed。`OPENER_DONE`、`turn.completed`、exit 0 和 §二登记只能分别作过程证据，不能单独触发下阶段。
- 🟡 回答须与当前 batch/lane/任务和等待项绑定，单次消费；沿现有 `pause/resume` 留痕。四小时超时按源状态机复位，不隐式批准。对于设计审或 ff，须保存用户实际答复的可审阅原文；不能把已有会话的“继续”泛化为新设计/新 ff 授权。
- 外发无自动执行路径。通知如果需真实企微发送，须区分已授权既有运维通知和新业务对外发送；新通道上线前不得因模板存在而发送。
- 恢复手段是停止本链自动消费、保留信号/证据/工作树和已存在的业务服务；绝不启动 Claude 或撤销他人资产。

## 实施切片与验收

本设计获审后才写实施计划，切片按依赖顺序：先阶段判定与证据契约；再把既有 opener/批处理、测试、review 接入；再接 guardian 的候选/排波/心跳/暂停恢复；最后接 ff 发布准备及 LAN 转出。每片用现有接口契约测试和针对性实测，不把三消费者已有通过项无故重跑。

验收用脱敏、无真实发送的隔离任务跑完一条可逆建造链：真实队列/intent→OpenSpec→设计停点→该项批准→Codex 原生隔离建造→目标 CI→独立 review→release-ready；同时跑 design 未批准、未知动作、hook 未信任、HEAD 漂移、测试失败、重复触发、崩溃恢复、旧哨兵、off/unknown LAN 和越权 ff/发送负例。批量验收另证依赖停链/独立泳道继续、并发错峰与心跳。实际 `.51` 部署只在用户 On LAN、逐项授权、既有收口正本就绪后验；离线夹具只证明正确拒绝和转出，不证明生产部署成功。启用任何常驻调度器前证明单消费者、触发器、账户、停止开关和端到端产物；未启用则报告“需人工唤醒”。

## 未闭合的设计核点

实现计划须核对 `handoff.py` 与现有 batch runner 的任务/阶段 ID 映射，防止同一模型轮次被两边重复调度；确认当前 Codex 是否有可持久看护的具名机器触发器。若不存在，guardian 先交付前台会话模式及清晰停点，后台自动看护单列 blocked，不以“已写循环”伪称自动化。该核点不影响先完成离线单任务阶段链，但影响“整套机制已迁移”的最终宣称。
