# batch-registration-precheck Design

> **本件为补件式记录，非事前 design 审**——四个子项的方案与取舍已在 `构建环境瘦身第二轮-方案-2026-09-04.md` §一 B1 由 Shao Peishen 一次性批准（「都按建议推进」）。本文件只记录**实现期发现的、方案原文未覆盖到的细节判断**，供归档与未来复核；不再逐点征求拍板。

---

## 判断点 1（ⓘ1）：git 归属校验对哪个仓库生效

方案原文只说"须在 git 脏集∨未跟踪∨最近 3 commit 内"，未明说对**哪个仓库**判断。§二 批次登记的对象是"主仓（`C:\Dev\zhuopin-ai`）里其他 session/worktree 已经改完、待落库的文件"，登记这个动作本身通常发生在某个独立 worktree 内——若对**登记发生的那个 worktree**判断 git 状态，会系统性地判断不到主仓里的真实脏集。

**取舍**：复用 acquire/release 已有的"主仓根目录"定位逻辑（`_is_inside_git_work_tree`／`_local_git_status_paths`／`REPO_ROOT`／`_resolve_repo_root()`），git 归属校验固定针对主仓，不针对调用方所在的 worktree。写进「已知残余风险」第 1 条：从其它 worktree 登记、尚未同步回主仓的改动会被误判为不合格。

## 判断点 2（ⓘ1）：git 状态完全不可得时怎么办

若目标目录根本不是 git 工作区，或 git 调用本身失败（罕见，如仓库损坏），git 归属校验**无法得出任何结论**。选 fail-closed（一律拒绝）会让整个批次登记功能在任何 git 异常时全面瘫痪，与「机制优先」原则冲突（机制本身的可用性不应比它防护的问题更脆弱）。

**取舍**：git 状态不可得时，fail-open**仅限 git 归属这一半**——形态校验与"同上/同名"速记校验仍然生效、仍会拒绝明显不合格的输入。

## 判断点 3（ⓘ2）：「未被任何待取活批次覆盖」在实现中如何判定

方案原文：「主仓若存在未被任何待取活批次覆盖的两份队列文件改动，先单独 commit」。字面实现方式是按每个待处理批次登记的文件清单，逐路径比对"这份队列文件的路径是否出现在某个清单里"——但**批次清单几乎从不会把队列文件自己的路径写进清单**（批次登记的是这一批业务改动涉及的文件，不是队列文件本身），字面实现会导致**几乎所有队列文件改动都被判定为"未覆盖"**，包括一个仍在途、因自身内容歧义而暂缓（blocked）的批次所在的那次登记改动——提前把它 commit 掉会冲掉暂缓状态本该保留的"未决"语义（回归测试 `BatchIsolationIntegrationTests::test_all_batches_blocked_logs_no_batch_processable_without_crashing` 实测复现了这个问题）。

**取舍**：改为按**该队列文件当前是否还有任何"待处理"状态的 §二 行**判断——零待处理行 ⇒ 判定为"此刻没有批次在盯着这份文件"，可以即刻兜底 commit；有任何待处理行（无论是否被字面清单覆盖）⇒ 暂不动，留给批次处理主循环。写进「已知残余风险」第 2 条：这不是"未被覆盖"的严格子集，同一文件内"已在途批次的改动"与"锁流程自身改动"混在一起时，当前判据按整份文件整体放行，尚未实现更细粒度的分段判断。

## 判断点 4（ⓘ2）：commit message 是否携带 `Co-Authored-By`

沿用现网 `git log` 实测：sweep 既有的自动化 commit（straggler backfill、ledger rerun 等）均不带 `Co-Authored-By` 尾行，只有真人／CC session 直接书写的 commit 才带。`docs(队列): 锁流程自带改动即刻落库` 属于 sweep 自动产生的兜底 commit，与既有惯例保持一致，不带尾行。

## 判断点 5（ⓘ3）：stash 覆盖范围为什么必须按路径而非整体

若用整体 `git stash -u`（不带路径参数），会把**即将被批次处理 commit 的文件也一并收走**，rebase 完成后再 pop 回来虽然文件内容不丢，但批次处理主循环若在 stash 期间读取工作区状态（判断哪些文件"脏"），会读到一个不完整的视图，产生竞态。

**取舍**：`git stash push -u -- <files...>` 按路径列表精确 stash，只收"不在本轮批次清单集合内"的文件；清单内的脏文件保留在工作区、只发告警（因为它们理应很快被批次处理 commit 掉，不需要也不应该被挪走）。

## 判断点 6（ⓘ4）：日志轮转按什么单位切分

`sweep-commit.log` 是连续追加的运行日志，若按行数或字节数硬切，会把一次"sweep 运行"的起止记录切成两半，破坏"看一眼末几行确认真落库"这条既有取证习惯（`.claude/rules/队列与落库.md`）。

**取舍**：按 `=== sweep 运行 ... ===` 起始标记切分为"运行块"，保留最近 4 周的完整运行块；`hooks-audit.jsonl` 是逐行 JSON，按每行的 `ts` 字段直接过滤即可，无需分块。两者的轮转逻辑相互独立（一个解析失败不影响另一个），且都遵循"解析不出就保留、不猜测丢弃"。
