## 决策 1：档三三条走 `cross_module_items`，**不进 82 条结果集**

**继承档一档二的架构约束**（`scoring.py::score()` 只遍历 registry 82 条），故总分与档位
在数学上不可能被档三影响。

## 决策 2：C05 的匹配次序 —— 豁免优先于一切匹配

```
空 → 漏填 ┃ 豁免词 → 不参与匹配 ┃ 严格相等 → 通过 ┃ 互为子串 → 通过
        ┃ 映射表白名单命中且目标阶段已填 → 通过 ┃ 其余 → 错误
```

**豁免必须排在最前**：`全项目周期` 若先进匹配环节，2-gram 可能给它配上某个阶段，
于是"豁免"就永远轮不到——护栏⑴ 会被护栏⑵ 之前的相似度悄悄架空。

**为什么严格相等与包含匹配不需要过白名单**：这两者是自证的（`立项` ⊂ `立项评审` 无歧义），
陈忱对判例 4–6 也判 ✅。需要白名单的只有"看起来像但不一定是"的那一类。

## 决策 3：相似度只写进证据，**永不作为通过依据**

陈忱对第 8 条判 ❌ 的正是「`软硬件开发设计` 仅因共有『设计』二字被配到 `概念设计`」。
但**把相似度整个丢掉也不对**——那样报告只会说"对不上"，看不出引擎其实注意到了这个近似。
故：判错误，同时在证据里写明「相似度指向 X，但映射表未确认此对应，按白名单校验不予采信」。

**⚠️ 本决策处理了一处真实歧义，须在 design 审时确认**：陈忱对第 8 条的 ❌ 有两种读法——
(a)「不该判通过」；(b)「不该配到 G1，应配到 G2/G3 后通过」。信里那句「软硬件开发实际对应 G2/G3」
**是我方在信中的说明、不是他的裁定**。本实现取 (a)（判错误），理由：
① 它与他把此条与「不要只靠字符串相似度」并提的语境一致；② 它与判例 7/10 同为"对不上→错误"，口径自洽；
③ **代价不对称**——C05 不进扣分，判错误只是报告上多一行待核，而误判通过会让一个错映射被当成已核过。
映射表里**刻意不含**这一条，并配了单测锁死（`test_c05_mapping_table_must_not_whitelist_the_case_8_mismapping`），
防止后人"顺手补全"把它补进去从而反转他的 ❌。

## 决策 4：档三三条**不接入扣分**（对 2026-08-18 归档件预期的显式改判）

2026-08-18 的 spec 写着「C05/C06/C07 的阻断效力待其判定口径裁定并实现时一并落到规则侧」。
**本次不这么做**，理由是实测：EQ17 的 C05 判**错误**（4 条风险里 3 条对不上），
而 EQ17 是评审委员会判**合格**的那一份 —— 接进扣分即当场把它打成不合格，
与黄金基准正面冲突。

⇒ 档三仍只作**呈现**。「这三条该不该阻断」是一个**新的口径问题**，须陈忱另行裁定，
不由实现方顺手决定。spec 已同步改写该 Scenario，不留"代码与 spec 不一致"的暗礁。

## 决策 5：两份 C05 表落 JSON，不硬编码

陈忱要确认的是**表的内容**，不是 Python 代码。落 `data/rules/cross_module_c05.json`
（与 `registry.json` 同目录），每条附 `_逐条取证` 说明该条来自哪个判例、哪几条是无判例的对称草拟。

**未确认状态是可见的**：`_确认状态` 字段在表里，且每条 C05 结论的证据末尾都带
「⚠ …待陈忱确认」。**判据类永不默认生效**（IATF 显式签认红线）——所以不能只在文件里写一句
就当他知道了，得让每一份报告都带着这句。

## 决策 6：同义词集只有一份（`rules/vocab.py`）

规则 12 与 C06 用**同一个 frozenset**，`AS_NOT_FILLED_SYNONYMS` 是它的别名而非副本。
「无」这个字此前正是被两套口径分别处置的典型：规则 12 判待改进、C06 若另立表就会判出第二个结论。
**在 `deterministic.py` 里再抄一遍字面量，就等于把刚合上的两处又拆开。**

`is_na_synonym()` 对空值**一律返回 False**——空的语义是「漏填」（Q2 后半句），
由调用方各自处置：规则 12 判不合格并计分，C06 判转人工并写明扣分归规则 12，不重复否决。

## 决策 7：黄金基准的移动必须留一道会响的闸

不改 manifest、不改 `GOLDEN`，改用 `xfail(strict=True)`：
- 闸未开 → 该断言按旧基准失败 → xfail 吸收，**套件仍绿，但"有一条 xfail"本身是可见的**；
- 闸开后有人改了 `GOLDEN` 却忘了摘标记 → **XPASS → strict 判红**，标记不会烂在代码里。

另配 `test_pending_baseline_equals_what_the_engine_actually_produces_now`，
断言《基准变更说明》里给他签的那个 100.00 **就是引擎真实重跑值**——防止签认一个凭空写的数。

## 决策 8：`data/rules/*.json` 必须入库（.gitignore 负例）

场景 `.gitignore` 有一条 `*.json`（本意是挡运行期 JSON 产物）。`registry.json` 早年是被
force-add 进来的，所以这个洞从未暴露。新增 `cross_module_c05.json` 时被它吞掉，
**后果不是报错而是静默判错**：文件缺失时 `_c05_tables()` 退化为空表，
豁免与白名单同时失效，华丰/邦奇的 C05 从「通过」翻成「错误」，**且本地永远复现不出来**。

与 `run_qd_b_web.py` 那颗潜伏 10 天的引导雷同族（本地绿 ≠ 生产对）。
双层守：`.gitignore` 加 `!data/rules/*.json`；加单测断言表文件存在且非空。
