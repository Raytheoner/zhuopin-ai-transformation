# 队列写侧按域精确路由 ＋ 跨文件高水位线同步语义补齐（承接 `queue-dual-file-split` 归档遗留）

> `#341` 行内原文明写"停下等审"。

## Why

`queue-dual-file-split`（2026-08-17 归档）把跨桌任务队列拆成机制环境／业务场景两份物理文件，
但归档时**明确带着两条欠账**（tasks.md 3.7、归档表脚注 2）：

1. **写侧未按 `[D:机/业]` 精确路由**——编辑锁 `append-row`/`acquire` 与企微机器人
   `queue_appender` 在"域未声明"或"从不声明域"时，统一落**机制环境**文件（design 决策点 3
   的"迁移期妥协"）；两份主 spec（`queue-dual-file-topology`／`editlock-dual-queue-routing`）
   写的却是"未声明即拒绝"——**目标态与实现从归档那天起就是分叉的，且已如实标注**。
2. **跨文件高水位线同步的完整语义未做**——高水位线只存在机制环境文件，design 决策点 7 当年
   对"两份文件各自独立锁"提出唯一顾虑："改高水位线时业务场景文件的写入者感知不到"。

真实实例，非假想：§一 `#336`（`[D:业]`）自 2026-08-15 起就位于机制环境文件，是机器人
`queue_appender` 盲写所致；2026-08-17 拆件巡逻对它是"就地销行、未搬家"。**该行不能充当
"机器人来件按域路由已通"的证据，本欠账未清前，同类错位会持续产生。**

**本次起草过程中另发现一处此前未被登记的分叉**（见 design 决策点 3）：`editlock-dual-queue-
routing` spec 现有"锁粒度——每份队列文件各持一把独立锁"这条 Requirement，其依据是
`queue-dual-file-split` 归档 tasks.md 6.5 的结论"独立锁已是既成实现"；但当前代码
（`0-学习与工具/工具-共享文档编辑锁.py::QUEUE_LOCK_ANCHOR`，含 2026-08-28 队列 `#420` 止血时
重申的显式不变式"两份物理队列文件共用同一把锁"）实际走的是**共享锁**，且这正是当年决策点 7
顾虑的"跨文件高水位线竞态"的既有解法——**归档分析在当时就看漏了一处代码分支，spec 从归档那天
起就描述了一个不存在的行为，而非"此后才drift"**。这把本包要处理的"实现差异"标注从两处变成
事实上的三处，一并纳入本包范围（触碰区仍是 `#341` 原定的两份 spec 文件，未越界）。

## What Changes

- **能力增量**：新增 `aibot-queue-domain-routing` capability，定义企微机器人写队列行时的域路由
  规则（现状：恒定写机制环境文件，止血性质；目标：恢复方案件 §6.5 建议 4／design 决策点 4 项 6
  已采纳但从未真正落地的"机器人 100% 盲写业务场景队列"）。
- **能力修改**：
  - `queue-dual-file-topology`——"§二 域路由" Requirement 由"未声明即拒绝"改为如实描述现状
    （默认落机制环境文件）并入目标态，移除"实现差异"临时标注。
  - `editlock-dual-queue-routing`——"acquire/append-row 按域路由" Requirement 同上；"锁粒度"
    Requirement 由"每份队列文件各持一把独立锁"改为如实描述"两份物理队列文件共用一把协作锁，
    锚点恒为机制环境文件"，作为跨文件高水位线同步的实现机制正式收编进目标态。
- **不改动**：`0-学习与工具/工具-共享文档编辑锁.py`／`queue_appender.py` 本次**只在 design
  阶段读，不动一行代码**（触碰区改动留给本包获批后的 apply 阶段，`tasks.md` 已列出）；`#313`
  （路径常量收拢，与本行"写入哪份文件"不重叠）不在本包范围内，未触碰。
