## Context

见 proposal.md - Why。补充 design 层面需要的技术底细：

1. **`.51` 上无任何现成反向代理设施**——没有 nginx/IIS ARR/Docker，现有四个服务（8091 Flask/8092 stdlib `http.server`/8093 Flask/8094 Flask）均各自独立 `python xxx.py` + Windows 计划任务（`SYSTEM + AtStartup`，见 CLAUDE.md §5"部署即收口纪律"沉淀下来的既有惯例）。引入网关不改变这一运维模式，只是新增一个同样方式部署的 Python 进程。
2. **`simple_gate.py`（#160）已提供一套经过实战检验的 Cookie 签名范式**（HMAC-SHA256、无服务端 session 存储、`Path=/` 跨端口共享）——本次网关的会话机制延续同一思路，但语义不同：`zp_gate` 只回答"知道口令与否"，SSO 场景需要回答"这是谁"，故新增独立 cookie，不复用/不修改 `zp_gate` 本身（proposal.md 已声明本次不修改 `platform-service-auth-gate` 现有 spec）。
3. **企微机器人（`wecom-aibot-service`）用的是"智能机器人"BotID + WebSocket 长连接体系**（`connection.py` 读取 `BOTID_KEY`），这与本次需要的"网页授权登录"（企微自建应用 `CorpID`/`AgentID`/`Secret`）是企微后台两套不同的应用注册——**两者共享同一个企业（同一批 userid），但 OAuth 网页授权所需的自建应用凭据是否已经在企微管理后台注册，目前未经证实**（见 Open Questions）。
4. **`zhuopin_platform` 核心依赖已含 `requests`**（`pyproject.toml`），但不含 Flask——三个 Flask 场景（SC8/QD-B/FI2）各自在自己的 `requirements.txt`/环境里装 Flask，不通过平台底座引入。网关若选 Flask 实现，同样应作为独立服务自带依赖，不污染平台底座核心依赖。

## Goals / Non-Goals

**Goals：**
- 交付网关的四项能力本身：反向代理路由、企微 OAuth SSO、三层权限判定、访问日志（对应 proposal.md 的四个新 capability）。
- 提供至少一个真实可验证的收编试点（见决策 3），端到端证明"登录一次→按权限访问→留痕"链路可用，而不仅是四份 spec 文档。
- 网关自身具备进程守护、健康检查、应急直连通道。
- 给出程序化访问清点方法论与验证清单，供收编时套用（不代替各服务收编时刻各自重新执行）。

**Non-Goals：**
- 不引入 nginx / IIS ARR / Docker 等新基础设施类别——保持与现有"Python 脚本 + Windows 计划任务"运维模式一致，避免为 100 人规模的内部工具新增一整类运维技能要求。
- 不做字段级细粒度权限、跨域审批矩阵（proposal.md 与 spec 已声明起步边界）。
- 不做企微通讯录自动同步（决策件已拍板手工映射表）。
- 不把四个后端服务合并进网关进程（决策件 §五决策2 已收回该早期建议）。
- 不在本次把 8091（保供看板）/8093（QD-B）/8094（FI2）正式收编进统一路由——决策件线③明确"条件触发、最后做、顺序财务→质量→采购、8091 最后动"，本次只交付网关能力，实际收编是后续独立任务（各自开工前需再走一次程序化访问清点，本设计只提供方法论）。

## Decisions

### 决策 1：网关实现技术选型 —— Flask + `requests` 反向代理，不选 nginx/IIS ARR

**做法**：网关是一个新的独立 Python 服务（Flask app），用 `requests` 转发请求到后端服务并流式返回响应；路由表是一份显式白名单（域/场景 → 后端 base URL），不做通用透明代理。

**为什么不用 nginx/IIS ARR**：
- `.51` 目前没有装 nginx，IIS ARR 需要额外安装 IIS 模块并学习一套新的配置语言（`web.config`/URL Rewrite 规则），而这支团队目前对 Python 的掌控力远高于 IIS 配置——用团队已经熟练的技术栈实现，出问题时排查成本更低。
- 用 Python 实现，网关本身也能天然复用 `zhuopin_platform` 的 `audit`（审计留痕）与既有 Cookie 签名代码风格，不需要在两套技术栈之间搭桥。
- 代价：需要自己处理流式转发、大文件上传（QD-B/FI2 均有 xlsx 上传）、超时与连接池——但这些用 `requests` + Flask 的 `stream=True` 与分块转发即可覆盖，复杂度可控。

**为什么路由表用白名单而非通用代理**：通用透明代理（任意路径转发到任意上游）是常见的 SSRF 攻击面；本网关只需要转发到四个（未来更多个）已知的内部服务，白名单式路由表从设计上就排除了"代理请求被诱导访问非预期内网地址"的风险类别。

### 决策 2：网关监听独立新端口 8090，四个既有端口保留作应急直连

**做法**：网关绑定 `0.0.0.0:8090`，作为门户新的对外唯一入口；8091/8092/8093/8094 四个端口保留监听（不因本次改动强制收窄绑定网段或下线），供运维应急直连排障用（决策件 §八风险1 已要求"保留后端直连能力"）。

**为什么是 8090 而不是 80/443**：内部工具无需标准端口，避免要求在 `.51` 上以管理员权限绑定特权端口；沿用现有 809x 序列，与团队已熟悉的端口命名习惯一致，降低认知负担。

**已知代价**：在 8091/93/94 完成"线③存量收编"之前，知道旧端口地址、且持有 `simple_gate` 口令的人仍可绕过 SSO 直接访问——这是决策件已经接受的过渡期风险（§八风险2 已单独设定止血口令的复审死线 2026-10-31），本设计不重复解决，只如实沿用。

### 决策 3：首个真实收编试点选 8092（命令中心 / 门户首页），不是任何一个业务服务

**做法**：本变更包落地时，网关至少真实代理一条路由——门户首页 `/`（即命令中心 8092 的静态内容）——完整走通"企微登录→权限判定（公开只读即可访问首页）→访问日志留痕"链路，作为验收依据；8091/8093/8094 三个业务服务在本次不接入网关路由表，继续维持现状（`simple_gate` 口令直连）。

**为什么不选某个业务服务做首个试点**：
- 决策件线③已明确顺序"财务→质量→采购，8091 最后动"，且触发条件是"各域业务数据对准 + 专员验收通过"——这个条件本身与网关能力是否就绪无关，用业务服务当试点会把两条本该独立的进度线（网关工程 vs 业务数据口径）意外耦合。
- 8092 命令中心本身就是"门户本体"，数据敏感度最低（销售域数据已脱敏），复杂度最低（静态内容，无上传/无重算），是验证"网关能否正确转发+鉴权+留痕"这一纯工程问题的最干净场地，不会被业务口径的不确定性干扰验收判断。

**代价**：交付时网关能力"看起来"还没有覆盖真正有价值的业务场景——这是刻意的，决策件本就要求网关"立即启动、与业务开发并行"而不是等业务数据对齐，先证明地基本身可靠，再按线③节奏收编。

### 决策 4：会话机制 —— 延续 `simple_gate` 的 HMAC 签名 Cookie 范式，新增独立 Cookie，不复用/不修改 `zp_gate`

**做法**：新增 `zp_portal_sso` Cookie（区别于 `zp_gate`），值格式 `{userid}.{exp_ts}.{HMAC-SHA256(secret, f"{userid}.{exp_ts}")}"`，服务端凭同一份密钥重新计算签名校验，无服务端 session 存储（无状态，与 `simple_gate` 保持同一哲学）。

**为什么不复用 `zp_gate`**：`zp_gate` 语义是"知道共享口令"，不携带身份信息；把身份塞进同一个 Cookie 会让 `platform-service-auth-gate` 现有 spec（proposal.md 已声明本次不修改）的行为发生变化，違反"新增能力、不改旧能力"的边界。两套 Cookie 可以短期并存（网关会话 Cookie 用于走网关路由的服务，`zp_gate` 继续保护尚未收编的三个业务服务）。

**为什么不引入 JWT/第三方 session 库**：HMAC 签名值已经是 `hmac`（标准库）就能实现的等价方案，与 `simple_gate` 保持技术风格一致，不为此新增第三方依赖（`PyJWT` 等）或运维一个 session 存储（Redis 等）——100 人规模、单机部署，无状态签名 Cookie 已经足够。

### 决策 5：部门映射表 —— 独立手工表，未登记 userid 一律 fail-closed 为公开只读

**做法**：新增一份手工维护的映射文件（格式沿用 `wecom-aibot-service` 现有 `department_group_mapping.yaml` 范式），记录 `userid → 域 → 层级（域成员/域管理员）`；网关在权限判定时查此表，查不到即视为公开只读（不默认授予任何域权限），与决策件 §五决策3 附表初始人员（姚祖怡/唐燕萍/陈忱 + 解植雅/汤易水/朱映桦/李姣龙 等）对齐。

### 决策 6：网关代理仍启用 `simple_gate` 的后端时，注入 `X-Auth-Token`，避免双重拦截

**做法**：当网关代理一个自身仍配置了 `ZP_GATE_PASSWORD` 的后端服务时（如收编初期新旧机制并存），网关在转发请求时附加 `X-Auth-Token: <该服务口令>` 请求头，命中 `simple_gate` 的"程序化访问"通过路径，避免员工在网关侧已经用企微 SSO 登录、却又被后端自己的 `simple_gate` 拦截要求再输一次口令。

**代价/边界**：这要求网关持有各已收编后端的 `ZP_GATE_PASSWORD`（配置在网关自己的 `.env`，不入库，同现有惯例）；未来该后端"正式收编"完成、下线自己的 `simple_gate` 后，这份配置随之失效清理，不需要额外机制。

### 决策 7：进程守护 —— 复用 Windows 计划任务既有惯例，不引入新工具

**做法**：网关注册为 Windows 计划任务，`SYSTEM` 账户 + `AtStartup` 触发器 + 失败重启配置，与 SC8/QD-B/命令中心现有三个服务完全同款（CLAUDE.md §5 已记录 `AtLogOn` 在会话断开场景下不可靠、`SYSTEM+AtStartup` 是已验证可靠的模式）。健康检查端点 `/api/ping`（与既有惯例一致，供 `deploy-server.ps1` 与外部监控探活，豁免鉴权）。

**为什么不引入 supervisor/pm2/systemd 等专用进程管理工具**：`.51` 是 Windows Server，Windows 计划任务已是团队验证过的可靠方案，引入额外工具会带来新的学习成本与运维面，收益不明确。

## Risks / Trade-offs

- **[风险] 企微自建应用（网页授权）凭据可能尚未在企微管理后台注册** → 这是外部前置依赖，不由本变更包控制；已列入 Open Questions，需 Shao Peishen/IT 在 apply 开工前确认，若未注册则需先申请（同 CLAUDE.md 记录的 U9C MCP 7/1 申请先例），届时会阻塞"决策 3 试点验收"里 OAuth 登录这一环，但不阻塞路由/权限/日志三项能力的独立开发与用 mock userid 的先行验证。
- **[风险] 网关成为单点** → 决策 7 的进程守护 + 健康检查 + 决策 2 的应急直连通道；应急通道的存在本身不解决"网关挂了大家看不到门户"，只是给运维一个排障后门，不是自动降级方案——**门户不可用期间业务服务仍可通过旧端口直连访问**，止损但不是无感知容灾。
- **[风险] 白名单路由表遗漏或误配可能导致某条路径被静默拦截或误转发** → 决策 1 已选白名单式而非通用代理排除 SSRF 类风险；配置错误本身仍可能发生，缓解：路由表变更须走 §二 批次登记 + 部署后冒烟验证（同现有"部署即收口纪律"），不额外发明新流程。
- **[风险] `X-Auth-Token` 注入机制（决策 6）要求网关持有多个后端的口令** → 这些口令本身已是各服务 `.env` 里的既有秘密（非新增秘密），网关侧新增一份汇总配置增加了"泄露面从 4 处变成 5 处"的量级，但均为同一司内网、同一止血机制下的口令，风险量级不变，只是集中存放；随收编完成逐个失效。
- **[已知不解决] 8091/8093/8094 收编前，知道旧端口地址的人仍可绕过 SSO** → 决策件已知悉并接受，止血口令通道复审死线 2026-10-31 是既有机制，本设计不重复处理。

## Open Questions

- **企微自建应用（网页授权）的 `CorpID`/`AgentID`/`Secret` 是否已在企微管理后台注册？** 现有企微机器人走的是 BotID + WebSocket 体系，与网页授权是两套独立注册；若未注册，需 Shao Peishen/IT 走申请流程（参考 CLAUDE.md 记录的 U9C MCP 申请先例）。此项不改变本设计的技术路线（仍是企微 OAuth SSO），只影响 apply 阶段决策 3 试点里"真实登录验证"这一步能多快开始，不阻塞路由/权限/日志三项能力的开发与基于 mock userid 的先行联调。
- **网关端口选 8090 是否与 `.51` 上其他既有或规划中的服务冲突？** 本 design 基于当前已知的四个端口（8091-8094）做出选择，apply 开工前需 CC 再核对一次 `.51` 上的实际端口占用表，确保无冲突。
