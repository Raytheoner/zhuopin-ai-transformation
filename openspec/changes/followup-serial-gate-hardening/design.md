## D1. 身份键 ＝（归一化部门, 姓名）二元组，**不是**只取姓名

### 决策

```
RecipientIdentity = tuple[str, str]     # (归一化部门, 姓名)，两段均非空
recipient_identity(cell) -> RecipientIdentity | None
same_recipient(a: str, b: str) -> bool  # 两侧都解析成功且二元组相等
```

### 为什么不只取姓名

生产里**三处已有实现各取一半**，正是本包要收敛的对象：

| 现有实现 | 取的是 | 位置 |
|---|---|---|
| `split_department_and_name` | `(部门, 姓名)`，**部门不归一化**（`IT部` 原样） | `readme_table.py` |
| `recipient_department` | **只有部门**，且归一化（剥尾字「部」） | `followup_gate.py` |
| `_assert_gate_open`／`build_report`／`draft_gap_detection` | **只有姓名** | 三个消费方各自 `_, name = split(...)` |

只取姓名的代价是**跨部门同名会被合并成一个人** —— 现网五个部门各只有一位在册收信人，所以今天不会命中；但 `_collect_intake_rows` 的注释里已经埋着同一族路标（「哪天某部门有了第二位收信人，这一行就会把两人的入信混在一起」）。**同一个坑不该修一半。**

### 🔴 辨析：「往严的一边统一」的方向性只适用于一类

`#124` 的裁决判据是「误拦会被看见，误放不会 ⇒ 往严的一边统一」。**这句话有一个隐含的适用范围，必须写死，否则会被误用：**

- ✅ **适用**：「本该是同一个人，却因写法差异被判成两个人」⇒ 该合并（合并 ⇒ 找得到前一封 ⇒ 闸更容易锁 ⇒ 更严）。
- 🔴 **不适用**：「本是两个人，却被判成同一个人」。它表面上也「更严」（更容易找到前一封、更容易锁），**但那是错误的严** —— 它制造的是误拦，而误拦会把一封合规的信永久染成豁免行（`质量部#10` 的实际后果）。

**⇒ 「往严」是**在同一人的写法差异上**往严，不是无原则地扩大匹配面。** 二元组正是这条辨析的落点。

### 部门段的归一化沿用既有 `normalize_department`

剥尾字「部」。这不是洁癖：`department_mapping.yaml` 里陈承那一行是 `IT`（不带「部」），README 写 `IT部 · 陈承`，直接比对会让 IT 域一封都配不上且不报错（该函数 docstring 已记）。

## D2. 归一化规则：MUST 剥什么、MUST NOT 剥什么、解析失败怎么办

### 规则

| | 动作 | 依据 |
|---|---|---|
| 分隔 | 以**第一个** `·` 切分为「部门段」「姓名段」 | 既有 `split_department_and_name` 口径，44 行主表 ＋ 19 行归档件**解析失败 0 行** |
| 装饰 | 两段均剥 markdown 强调星号与首尾空白／全角空格 | 复用 `_DECORATION_CHARS`（状态列实测存在 `✅ **无需回复**` 这类写法，收信人列今天没有但成本为零） |
| **姓名段括注** | 🔴 **MUST 剥除**：从**第一个**全角 `（` 或半角 `(` 起到姓名段末尾，全部丢弃 | `#482` ⑵；`#124` 已裁决「后括号注记不算闸道标识」 |
| 部门段括注 | MUST NOT 特殊处理（现网无此写法；一旦出现应当报出来，而不是被静默剥掉） | 保守方向 |
| 尾字「部」 | 部门段剥，姓名段**不剥** | D1 |

### 🔴 解析失败：`None` MUST NOT 与 `None` 相等，且 MUST 出声

`recipient_identity` 在下列情形返回 `None`：无 `·`／部门段为空／姓名段剥完括注后为空。

- **匹配侧**：`same_recipient(a, b)` 在任一侧为 `None` 时 **MUST 返回 False**。🔴 **两个解析不出来的收信人不是同一个人** —— 若让 `None == None` 成立，一次表格损坏会把整张表压成「同一个人」，闸会对全表逐行乱锁，**且看起来像是在正常工作**。
- **出声侧**：三个消费方当前的处置各不相同，本包统一为**一律出声**：

| 消费方 | 现状 | 本包要求 |
|---|---|---|
| `_assert_gate_open`（append 前置） | `if not name: return` —— **静默放行** | MUST 打印一条指名该行的告警；是否阻断见下 |
| `_validate_followup_readme_release`（release 后置） | 逐字比对，解析概念不存在 | 改调后：解析失败 MUST 记一条 violation（**阻断**） |
| `build_report`（读侧派生） | 抛 `GateQueryError` ⇒ 退出码 2 | 不变 |

**append 前置那一处 SHOULD 出声但 SHOULD NOT 阻断**（它是前置便利检查，真正的咽喉在 release），理由与 `_followup_readme_rows_advisory` 已确立的口径同源：「**『不阻断』是有意的取舍，『不出声』不是。**」

### ⚠ 如实登记：括注剥除的一个新增静默误判面

`（可分担朱映桦）`／`（转汤易水第④项）`／`（可请朱映桦先初标）` 三种括注里**都出现了另一个真实人名**。归一化把它们剥掉后，行仍归属 `·` 之后那个人 —— 这是**既有口径**（`recipient_department` docstring：「括注标的是『谁可以分担』，不改变这封信是写给谁的」），本包沿用。

**但它意味着：若哪天有人用括注表达「本封改由朱映桦回复」，机器会把它算成陈忱的信，且不报错。** ⇒ 配套要求（写进 delta spec，落 README 正本）：**变更收信人 MUST 改 `·` 之后的那个名字，MUST NOT 用括注表达。**

## D3. 🔴 「最近一封」用哪把尺子 —— **须拍板**

### 问题

`#124` 只裁决了「收信人怎么匹配」。实测发现「最近一封怎么取」在生产里也有两份实现，且**此刻正对陈忱给出相反答案**（proposal 实测二）：物理行序取到 `质量部#12`（closed ⇒ 闸开），日期排序键取到 `质量部#13`（2026-09-04 `✅ 已推送` ⇒ 闸锁）。

而 `_letter_sort_key` 的 docstring 里已经写着 **「⚠️ 不能只按表内行序」**，并给出实测反例（`采购部#4` 07-21 排在 `采购部#17` 08-20 之后）。**闸侧用的正是那个 docstring 说了不该用的东西。**

### 三个候选

| | 尺子 | 优点 | 代价 |
|---|---|---|---|
| **(a) ✅ 推荐** | **日期 → 编号序号 → 表内行序**（＝既有 `_letter_sort_key`） | 已在生产（配对侧）跑了半个月；三段决胜有实测支撑（同日多封靠编号、无编号靠行序）；**消掉自称与实际的不一致** | 日期列若空或非 ISO 形态会退化为按编号；**上线即改变陈忱的闸状态** |
| (b) | 维持物理行序，改 `latest_dispatched_letter` 的 docstring 承认两把尺子 | 零行为变更、零风险 | 🔴 **把一处已知不一致合法化**。README 的物理行序不是时间序是实测事实，闸会继续按位置判时间 |
| (c) | 新造第三把（如「日期为唯一键，同日一律判锁」） | 最保守 | 又多一份实现；且同日多封是常态（实测 `采购部#15`／`#16` 同为 2026-08-18），会把正常路径大面积拦死 |

### 推荐 (a)，以及为什么它「上线即锁陈忱」不是反对理由

`质量部#13` 的状态列是 `✅ 已推送 2026-09-04 06:24 UTC`，**按闭环四态它确实不是闭环态** ⇒ 闸锁是**判据的正确输出**。

它「本应」闭环（交期要点写「知会性质，不用回复」，本应是 `✅ 无需回复`），被发送脚本回填覆盖 —— **那是 `质量部#7` 行内已经记了整整 20 天的另一个已知漏洞**（「起草时判定了、发送时被机器抹掉了」），有自己的成因、自己的修法（发送脚本回填时须保留闭环形态判定）和自己的触碰区。

🔴 **不得为了让本包上线不影响质量线，而把闸的尺子留在错的那一把上。** 处置建议（写进 tasks 0.x，不在本包实现）：上线**前**先把 `质量部#13` 据实改为 `✅ 无需回复`（一次单元格改写，属既有合法转态，不需要新机制），闸即恢复 ✅ 开；同时把「回填覆盖闭环态」另立队列行。

### 若拍板选 (b)

则 `latest_dispatched_letter` 的 docstring 里那句「**与跟进闸同一把尺子**」MUST 当批改掉 —— **一句已知为假的自陈留在权威模块里，比两把尺子本身更危险**（下一个人会照着它写第三处实现）。

## D4. `❌ 已作废` 防滥用判据 —— 按**转态前状态**分档

### 判据源：acquire 快照

`_validate_followup_readme_release(current_text, snapshot_text)` **已经拿着 acquire 快照**，但现在只用它算行身份集合、没用它比对状态。本项**完全在既有数据流内**，不新增任何输入、不读 git（同 `followup-closure-evidence-gate` D2 已确立：回灌与转态在同一未提交窗口内，git 判据恒为假）。

### 分档

对既有行（身份在快照中可找到）且当前状态为 `❌ 已作废` 的，取**快照中同一行的状态**判档：

| 快照中的状态 | 档 | 要求 |
|---|---|---|
| 已是 `❌ 已作废`（未变） | — | 不校验（不回溯既有行，同「历史行不追溯」惯例） |
| `NOT_YET_SENT_STATUS_PREFIXES` 之一（`⏳ 待你审`／`🆕 待发`／`⏸ 暂缓`） | **低** | 仅要求 **R1 写明理由** |
| 其余（＝已发出：`✅ 已推送`／`✅ 已发`／`📨 回件已到，待拆件`／未知写法） | 🔴 **高** | **R1 ＋ R2 ＋ R3** |
| 新增行直接写 `❌ 已作废` | 🔴 **高** | **R1 ＋ R2 ＋ R3**（新增行没有「前状态」，但它同样能开闸 ⇒ 从严） |

### 三条要求

- **R1 · 写明理由（结构性）**：`❌ 已作废` 之后 MUST 有正文。判法 ＝ `normalize_status(cell)` 去掉前缀 `❌ 已作废` 后，剥净装饰字符与括号符号，**剩余实义字符 ≥ 8 个全角字**。
  🔴 **门槛取 8 不是拍脑袋**：归档件里那唯一一行真实作废的理由是「`· 9 月重写`（2026-08-04，队列 #137，Shao Peishen 选 (a) 线下当面说）——信中三件事已全部随销售域推迟失效……」，远超门槛；而一句「已作废」「不需要了」在门槛之下。**实现期须用该行做一次正例断言。**
- **R2 · 不得命中开闸措辞（黑名单）**：理由文本命中下列任一即拒 —— `为了开闸`／`为开闸`／`开闸`／`解闸`／`打开串行闸`／`绕过串行`／`不想等回件`／`不等回件`／`腾闸`／`让闸开`。
- **R3 · 可核凭据**：理由中 MUST 含至少一个可核引用 —— 队列行引用（`§一 #N`／`§四 #N`，形态复用 `followup-closure-evidence-gate` 已定义的解析）或 `Shao Peishen <ISO 日期> 答` 形态之一。**MUST NOT 只校验存在性以外的语义**（本判据不判「这个行号说的对不对」）。

### 🔴 黑名单的诚实局限，以及为什么还要有 R3

**R2 防手滑，不防蓄意** —— 想绕过它的人换个措辞即可，成本近乎为零。

**R3 才是有约束力的那一条**：它要求作废理由**指向一个仓库里查得到的东西**。伪造一句措辞不留痕迹；伪造一个队列行号会在值周巡检对账（skill `zhuopin-queue-audit`，既有职责）时被查出来。这与本项目 IATF 可追溯纪律同源 —— **不是让机器判断动机，是让动机留下可查的痕迹。**

⇒ **R2 单独存在意义不大，但与 R3 同在时它免费**：它把「顺手写一句实话」的那一类当场拦下并给出提示，而那一类恰恰是最可能发生的（`#90` 描述的正是「不想等回件」这个念头本身）。

### 逃生阀

高风险档给一条与既有范式一致的逃生阀：行内写 `作废豁免：〈理由〉`，放行但**打印留痕**（同 `串行豁免：` 的既有形态，零新增写盘路径）。
🔴 **本包不为它设自动到期** —— 那需要一个承接方，而本包没有为它建承接方（同「写下需要动作、却没有承接方」那条已被点破的形态，不再犯一次）。

### 现网命中面（如实登记）

主表 `❌ 已作废` **0 行**；归档件 1 行（低风险档，R1 满足，R3 满足——含 `队列 #137`）。**⇒ 本判据上线当天命中数为 0，它是预防性的。**

## D5. 🔴 停止机器制造豁免 —— 两个方案，**须拍板**

### 问题复述

`工具-跟进信README行长外置.py` 压缩「主要事项」列 ⇒ `_followup_row_identity`（＝除状态列外全部单元格）改变 ⇒ 串行闸判该行为「新增行」⇒ 拒绝 release ⇒ 工具自动写 `串行豁免：D3 行长外置压缩摘要，非新起草跟进信` 绕过。现网 **5 行**，随每次外置**单调增长**。

**它是一条被机器踩出来的路，不是一次人的疏忽。** 该工具自己的 docstring 已如实登记这是「design.md 撰写时未预见」的交互缺口。

### (a) 🔴 推荐：行身份改用**编号列主键**

```
_followup_row_identity(cells) -> str      # ＝ 编号列的归一化取值
新增行 ⇔ 该编号在 acquire 快照中不存在
```

- **根治面最大**：一次消掉整类「改了任一非状态列 ⇒ 被判成新增行」的误报。行长外置只是第一个撞上的，**手工改日期／改交期要点／修错别字全都会撞**（proposal 已知边界 5）。
- **编号是 README 的天然主键**：`parse_letter_number` 已在生产解析它；`_next_available_number` 已按它推算占号；归档件已按它保证「编号不复用」。
- **归一化取值**：先跑既有 `strip_unnumbered_annotation` 剥掉 `（待你审，暂不占号）` 这类括注，再取 `parse_letter_number` 的 `<部门>#<数字>`。
- **回落**：无 `<部门>#<数字>` 的行（实测：归档件里 `销售部（未发，不编号）`，主表 0 行）**回落到既有的「全单元格」身份**，并出声说明该行走的是回落路径。
- **代价（如实登记）**：① 「改编号列」会被判成「删一行 ＋ 增一行」—— 但那本来就该被当成新增行看待（编号是身份）。② 两态语义检查（新增行不得直接写终态 `🆕 待发`）的判据面随之改变：改动**已有编号**的行、把状态写成 `🆕 待发` 将不再被拦。🔴 **这是一处实实在在的削弱，必须在 design 审上被看见** —— 缓解 ＝ 两态语义检查改为**同时**看身份与状态迁移（快照中该编号的状态不是 `⏳ 待你审` ⇒ 拒），成本约十行。

### (b) 备选：专用标记 `行长外置：`

新增一个**只服务于这一种形态**的标记，判据可机器验证：把当前行的「主要事项」列换成快照中同编号行的原文后，其余单元格 MUST 与快照逐字相等 —— 满足即放行，不满足即当普通新增行处理。

- **优点**：改动面最小，不动两态语义检查。
- **代价**：① 又多一条要记的规则（本项目已明确「一个词只表达一个含义」并否掉过同义标记）；② **只修行长外置这一条路**，手工改其它列仍会撞闸、仍需要人写豁免 ⇒ 那一类没有承接方；③ 新标记若被误用为通用逃生阀，等于把今天的问题换个名字再来一遍。

### (c) 不推荐：维持现状，只改 `SERIAL_WAIVER_REASON` 的文案

**明确否掉**。文案再怎么写，它在机器眼里仍是一个无条件开闸口令，且仍会增长。**改文案 ＝ 把一个机器问题伪装成一个可读性问题。**

### 两案共同要求（无论拍哪个）

1. **退休 `_find_serial_gate_conflicts` 这份复刻实现**，改为调用权威判据（它复刻的是有缺陷的那一份，是本包实测四里的第 4 处分叉）。
2. **`串行豁免：` 的判据 SHOULD 收窄**：现状是「**任一单元格**含标记即放行」。收窄为「标记后 MUST 跟非空理由」——**不做语义判断**（那会重演 R2 的局限），只拦「有标记没理由」这一种。理由：一个只有标记没有理由的豁免，读者无从判断它是不是真豁免，而这正是 `#124` 那句「后续读者据 README 扫豁免会误判串行原则被跳过」说的事。

## D6. 🔴 存量 5 行怎么清 —— **须拍板**

### 张力

- 一边是本项目硬纪律：**历史记录不追改**。
- 另一边是事实：**这 5 行携带的不是历史记录，是活的开闸口令** —— 只要其中任何一行日后被编辑（身份改变 ⇒ 判成新增行），那条豁免立刻生效并静默放行。

### 辨析：它们不属于「历史记录」

「历史记录不追改」保护的是**对已发生的事的叙述**。这 5 行里的 `串行豁免：D3 行长外置压缩摘要，非新起草跟进信` **不是对任何事的叙述** —— 它是 2026-09-06 一次自动化操作为了绕过一处工具缺陷而写入的**控制指令**，其内容既不描述这封信、也不描述串行原则。

**⇒ 判别一句：删掉它，会不会让任何一件已发生的事变得读不出来？** 不会 —— 那次外置动作本身有 git 提交、有行日志文件、有工具 docstring 的登记，三处留痕一处不少。

### 推荐处置

| 对象 | 处置 |
|---|---|
| 5 行 README 单元格里机器写入的 `串行豁免：D3 …` | **删除**，并在同批 commit message 里写明依据（`#482` ④ ＋ 本 design D6） |
| `跟进信行日志/质量部#10.md` 里**人写**的那段「🔴 串行豁免：本行不是真的豁免，闸本来就是开的……」 | 🔴 **原样保留，一个字不动**。它是对 `#124` 那次实撞的第一手记述，正是「历史记录不追改」保护的对象；且它已随行长外置迁出 README 行内，**不构成开闸口令** |
| `质量部#10` 主要事项列残留的「……起草前复核＝✅ 开、下一可用号 质量部#10，**无需豁免**）」 | **保留**。它是事实陈述，且与删豁免这个动作方向一致 |

### 次序硬约束

🔴 **必须先做 D5（停产），再做 D6（清存量）。** 反过来做，下一次行长外置会把 5 行原样写回来，而清理动作会被记成「已完成」——**一次看起来成功的、什么都没改变的操作**。

## D7. 双向回归用例（`#482` ①「双向各一条」）

🔴 **取材于本轮实测的真实行，不构造理想样本** —— `#124` 的整个成因就是「误放不会有人看见」，用构造样本写这两条测试等于放弃了唯一一次把真实误放钉进断言的机会。

| # | 方向 | 取材 | WHEN | THEN |
|---|---|---|---|---|
| **T1** | 🔴 **误放**（本包核心） | `质量部#7` 实况 | 表内已有 `质量部 · 陈忱`（状态 `✅ 已推送`，在途）；新增一行收信人写 `质量部 · 陈忱（可分担朱映桦）` | release **MUST 拒绝**；拒绝文案 MUST 指名前一封的编号。🔴 **改造前这条必然失败**（现状放行）——这条测试的价值就在这里 |
| **T2** | ⚠ **误拦** | `质量部#10` 实况 | 表内已有 `质量部 · 陈忱（可请朱映桦先初标）`（状态 `📥 已回件并回灌`，闭环）；新增一行收信人写 `质量部 · 陈忱` | release **MUST 放行**，且**不需要任何豁免标记** |
| **T3** | 反向（少写注记） | `采购部#21` 实况 | 表内最后一行是 `采购部 · 姚祖怡（采购域 AI 专员）`（在途）；新增一行写 `采购部 · 姚祖怡` | MUST 拒绝（T1 的镜像：多写与少写必须同判） |
| **T4** | 身份解析失败不匹配 | 构造 | 两行收信人列均无 `·`（如 `销售部`） | MUST NOT 判为同一人；MUST 出声 |
| **T5** | 跨部门同名不合并 | 构造 | `质量部 · 张三` 与 `采购部 · 张三` | MUST NOT 判为同一人（D1 二元组） |
| **T6** | 两端同判（append ＋ release） | `质量部#7` 实况 | 同 T1 | `工具-跟进信README登记.py` 的 append 前置与 release 后置 **MUST 给出同一结论**。🔴 现状二者相反 |
| **T7** | `❌ 已作废` 反例（`#482` ③） | 构造 | 已发出未闭环的信改为 `❌ 已作废（为了开闸，先把这封作废）` | MUST 拒绝，且拒绝文案指出命中的是哪一条（R2） |
| **T8** | `❌ 已作废` 反例二 | 构造 | 已发出未闭环的信改为 `❌ 已作废（不需要了）` | MUST 拒绝（R1 理由过短 ＋ R3 无凭据） |

## D8. 消费方迁移盘点与兼容

### 必须改调的四处（＋两处外围）

| 位置 | 现状 | 改后 |
|---|---|---|
| `_validate_followup_readme_release` | 整格逐字 | `same_recipient` |
| `工具-跟进信README行长外置.py::_find_serial_gate_conflicts` | 复刻上者 | **整个函数退休**，改调权威判据 |
| `工具-跟进闸查询.py::build_report`／`all_recipients`／`_collect_intake_rows` | 归一化姓名 | `recipient_identity`；`_collect_intake_rows` 的部门粒度**本包不改**（它的路标另有承接） |
| `工具-跟进信README登记.py::_assert_gate_open` | 归一化姓名 ＋ 静默回退 | `recipient_identity` ＋ 出声（D2） |
| `readme_table.split_department_and_name` | 独立实现 | 改为权威函数的**薄封装**（保留符号名——`dispatch.py`／`draft_gap_detection.py`／`工具-跟进信README查询.py` 三个现役消费方按名取值） |
| `followup_gate.recipient_department` | 独立实现 | 改为 `recipient_identity(...)[0]`，**对外签名与语义不变** |

### 不改的

- `latest_dispatched_letter` 的**排序逻辑**不动（除非 D3 拍 (a)，那时是闸侧改调它，不是它改）。
- `followup_gate` 既有函数的对外签名一律不变 —— `工具-队列结构lint.py` 盯着符号存在性，且 `find_unsynced_letters` 有两个现役消费方。**新增函数，不改旧函数**（同 `followup-closure-evidence-gate` 已确立的口径）。
- 隔离环境兜底桩：`工具-共享文档编辑锁.py` 在无平台包时会回落到本地字面量（`_followup_status_is_closed` 的既有形态）。新增的归一化同样 MUST 有回落实现，且**回落实现与权威实现须由同一份单测双跑**，否则回落分支会静默漂移。

### 迁移次序（tasks 的排法依据）

```
1. followup_gate 新增函数 ＋ 单测（不动任何消费方）
2. D7 的 T1/T3/T6 先写、先跑、先红        ← 🔴 顺序不能反
3. 四处消费方逐处改调，每处改完全量回归
4. D5 拍板方案落地（停产）
5. D6 清存量 5 行
6. README 正本口径段同批改（含 D2 的「变更收信人不得用括注」）
7. #124 截止段那条人守删除（proposal 退休项 4）
```

## 附：本 design 主动扩了范围的两处，须在 design 审上被明确同意或推翻

1. **D3（「最近一封」的第二把尺子）** —— `#124`／`#482` 都没提到它。扩范围的理由：它与 ⑴ 是**同一个病**（同一条串行原则有多份不一致的实现），且此刻正在生产上对陈忱给出相反答案；只修 ⑴ 不修它，本包的验收条件 3（「四把尺子给出同一答案」）从一开始就不可能满足。
2. **D5(a)（行身份改用编号列主键）** —— `#482` ④ 字面只要求「删掉那段豁免」。扩范围的理由见 D6 次序硬约束：**只删不停产 ＝ 一次看起来成功的、什么都没改变的操作。**
