## ADDED Requirements

### Requirement: 收信人身份 SHALL 由单一权威判据归一化后得出
跟进信 README「收信人」列的身份判定 MUST 收敛为 `zhuopin_platform.shared_tools.followup_gate` 的**一份**实现，返回 `(归一化部门, 姓名)` 二元组；任一消费方 MUST NOT 自留匹配逻辑。

归一化 MUST 按下列规则进行：

1. 以**第一个** `·` 切分为部门段与姓名段；
2. 两段均剥除 markdown 强调星号与首尾空白／全角空格；
3. 🔴 **姓名段自第一个全角 `（` 或半角 `(` 起至末尾的括注 MUST 剥除，不参与匹配**；
4. 部门段剥除尾字「部」（`IT部` 与 `IT` MUST 视为同一部门）；
5. 部门段的括注 MUST NOT 被特殊处理。

身份键 MUST 是二元组而非仅姓名：本该是两个人却被判成同一人所制造的是误拦，而误拦会把一封合规的信永久染成豁免行；「往严的一边统一」这条判据只适用于「本该是同一人却被判成两人」这一类，MUST NOT 被用来无原则地扩大匹配面。

#### Scenario: 后括号注记不同仍是同一人
- **WHEN** 比对 `质量部 · 陈忱` 与 `质量部 · 陈忱（可请朱映桦先初标）`
- **THEN** 判为同一收信人

#### Scenario: 括注里出现另一个人名不改变归属
- **WHEN** 比对 `采购部 · 姚祖怡` 与 `采购部 · 姚祖怡（转汤易水第④项）`
- **THEN** 判为同一收信人（括注表达的是分担／转办，不是收信人变更）

#### Scenario: 部门带不带「部」字视为同一部门
- **WHEN** 比对 `IT部 · 陈承` 与 `IT · 陈承`
- **THEN** 判为同一收信人

#### Scenario: 跨部门同名不得合并
- **WHEN** 比对 `质量部 · 张三` 与 `采购部 · 张三`
- **THEN** 判为**不同**收信人

### Requirement: 收信人解析失败 SHALL NOT 匹配，且 SHALL 出声
`recipient_identity` 在无 `·`、部门段为空、或姓名段剥净括注后为空时 MUST 返回 `None`。

🔴 两侧任一为 `None` 时，`same_recipient` MUST 返回 `False`：**两个解析不出来的收信人不是同一个人**。若令 `None == None` 成立，一次表格损坏会把整张表压成同一个人，闸会对全表逐行乱锁且看起来像在正常工作。

解析失败 MUST NOT 被静默吞掉：

- release 侧结构校验 MUST 记为一条 violation（阻断）并指名该行；
- append 前置检查 SHOULD 打印指名该行的告警但 SHOULD NOT 阻断（真正的咽喉在 release）——「不阻断」是有意的取舍，「不出声」不是；
- 读侧派生查询保持既有 fail-loud 语义（退出码 2）。

#### Scenario: 无分隔符的两行不得互相匹配
- **WHEN** 两行收信人列均为 `销售部`（无 `·`）
- **THEN** MUST NOT 判为同一人，且输出中出现指名该行的告警

#### Scenario: append 前置解析失败不静默放行
- **WHEN** 新增行收信人列解析失败
- **THEN** append 前置检查打印告警后继续，MUST NOT 无任何输出地放行

### Requirement: 串行闸的「前一封」SHALL 由单一定义得出
「该收信人最近一封」的取法 MUST 在 release 后置校验、append 前置检查、读侧派生查询与回件配对四处**一致**。任一处的文档字符串 MUST NOT 声称与其它处同源而实际不同源。

README 的物理行序不是时间序（实测：`采购部#4`（2026-07-21）排在 `采购部#17`（2026-08-20）之后）；若采用日期排序键，其决胜次序 MUST 为「日期 → 编号序号 → 表内行序」，三段缺一不可。

#### Scenario: 四处对同一收信人给出同一答案
- **WHEN** 对生产 README 主表逐位收信人分别用四处实现取「最近一封」
- **THEN** 四者返回同一封信

#### Scenario: 日期晚于表内位置的信不被跳过
- **WHEN** 某收信人在表内物理最后一行的日期早于其上方某一行
- **THEN** 「最近一封」取日期较晚的那一封

### Requirement: 变更收信人 SHALL 改姓名本身而非用括注表达
跟进信 README 中，把一封信改发给另一个人 MUST 通过改写 `·` 之后的姓名实现，MUST NOT 通过括注（如 `（改由某某回复）`）表达。

理由：括注在身份归一化中被剥除且不报错，用括注表达收信人变更会让该行仍被归属到原收信人名下，且无任何信号。该约束 MUST 写入 README 串行原则段的口径正本。

#### Scenario: 括注写变更不改变归属
- **WHEN** 某行收信人列写 `质量部 · 陈忱（改由朱映桦回复）`
- **THEN** 该行仍归属陈忱（本要求即为防止此写法被使用而立）

### Requirement: 串行豁免标记 SHALL 携带非空理由
`串行豁免：` 逃生阀 MUST 在标记之后跟随非空理由文本；只有标记没有理由的行 MUST 被拒绝。

判据 MUST NOT 对理由做语义判断——那既做不到也会重演黑名单的局限；本要求只拦「有标记没理由」这一种可机器判定的形态。

#### Scenario: 空理由的豁免不被接受
- **WHEN** 新增行某单元格含 `串行豁免：` 且其后无任何文本
- **THEN** release 被拒绝

#### Scenario: 带理由的豁免照常放行并留痕
- **WHEN** 新增行含 `串行豁免：业务方要求两条并行跟进`
- **THEN** release 放行，且打印检测到豁免声明的提示

### Requirement: 机器 SHALL NOT 自动写入串行豁免标记
任何工具 MUST NOT 为了让自身的写入通过串行闸而自动向 README 行内写入 `串行豁免：`。

成因（实测，2026-09-07）：行长外置工具压缩「主要事项」列会改变行身份，串行闸因此把一次纯历史内容压缩判成「新起草的跟进信」，工具遂自动写入 `串行豁免：D3 行长外置压缩摘要，非新起草跟进信`——现网已 5 行（`采购部#12`／`IT部#8`／`质量部#7`／`质量部#10`／`质量部#12`），且随每次外置单调增长。这些标记既不描述这封信、也不描述串行原则，却在机器眼里构成永久、无条件的开闸口令。

修法 MUST 作用于成因（行身份判定），MUST NOT 只改自动写入的理由文案——文案再怎么写，它在机器眼里仍是一个无条件开闸口令且仍会增长。

存量标记的清理 MUST 在停产之后进行；反序执行会让下一次外置把它们原样写回，而清理动作被记成已完成。

#### Scenario: 行长外置后不产生新的豁免标记
- **WHEN** 对含长行的 README 副本执行一次行长外置
- **THEN** 产物中 `串行豁免：` 计数为 0，且 release 通过

#### Scenario: 纯内容压缩不被判为新增行
- **WHEN** 某既有行仅「主要事项」列被压缩、其余列逐字不变
- **THEN** 串行闸 MUST NOT 把该行判为新增行
