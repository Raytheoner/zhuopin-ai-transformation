## 决策点 ①：收紧用哪种实现形态（🔴 本项**无默认**，须你明确答复）

**先把现状钉死**（propose 期 AST 全量扫描，非阅读印象）：sweep 全文 **6 处 `git add` 全部带 `--` pathspec**，**5 处 `git commit` 全部是裸 `git commit -m <msg>`**。`git commit` 不带 pathspec ＝ 提交**整个 index**。index 是工作区级共享状态。⇒ **stage 是按清单的，commit 不是；决定提交内容的是后者。**

**受控复现结论**（`git commit --dry-run --short`，proposal §Why 可一分钟重放）：

| 场景 | 无 pathspec | 带 pathspec |
|---|---|---|
| index 里有别人暂存的孤儿 | 🔴 孤儿**进**提交 | 孤儿**不进**提交 |
| 声明件在 add 之后又被并发改写 | `AM` ⇒ 提交 **add 那一刻的 index 快照** | `A` ⇒ 提交 **工作树当前内容** |

### 四个选项

| 选项 | 做法 | 差异 | 代价 |
|---|---|---|---|
| **⒜ pathspec commit** | `git commit -m <msg> -- <resolved ＋ 队列文件>` | 改动最小（每处 commit 加一段 pathspec），与 add 天然对齐 | 🔴 **隐含 `--only` 语义 ⇒ 提交的是工作树当前值，不是 add 时的快照**（见上表第二行）。并发 session 在 add→commit 窗口里改了声明件，sweep 会提交它更新后的内容。窗口极短但非零。次要：路径若无任何改动，`git commit -- <path>` 会以「没有可提交的改动」报错，须处理 |
| ⒝ 提交前清扫 index | commit 前对"清单外但已暂存"的路径跑 `git restore --staged`，再裸 commit | 保留 index 快照语义（不受窗口影响） | 🔴 **它会改掉别人的暂存状态**——把并发 session／人工暂存的内容从 index 里踢出去。虽然那些内容本就不该在 sweep 的提交里，但"替别人 unstage"是一个**对共享状态的写动作**，与 sweep「只碰账面对得上的东西」这条自我约束正面冲突 |
| ⒞ 临时 index（`GIT_INDEX_FILE`） | `read-tree HEAD` → 在临时 index 里 add 清单路径 → `write-tree`／`commit-tree`／`update-ref` | 语义最干净：不碰共享 index、精确控制内容、不受窗口影响 | 🔴 **走 git 底层管道命令，绕开 `git commit` 的全部常规行为**（hooks、`commit.gpgsign`、`Co-Authored-By` 之类的 message 处理、`git commit` 自身的安全检查）。`_run_git` 还需新增 env 透传。**改动面与理解成本远大于另外三个**，且新造一个文件名形态（临时 index，须硬性落在 `.git/` 下，见 proposal §.gitignore 段） |
| ⒟ 只断言不修 | 保持裸 commit，但提交**前**核对 index 与清单，不一致即整批跳过＋告警 | 零行为改动，最保守 | 🔴 **它不产出正确的提交，只是拒绝产出错误的提交**。在 `OP-0827-A` 那个真实场景里（并发 session 持续改写两份文件），结果会是**该批次每一轮都被跳过、直到并发方收工**——即用"停摆"换"不夹带"。与 `#238` 修掉的"批次跨天积压"同形 |

### 🔑 起草方推荐 ⒜（pathspec commit）＋ 决策点④ 的提交后校验，三条理由

1. **⒜ 是唯一"改动面与问题面相称"的选项**。问题就是「commit 少了一段 pathspec」，⒜ 就是「把那段 pathspec 加上」。⒝／⒞ 都在引入一套新机制来绕过这个缺口，⒟ 干脆不修。
2. **⒜ 的那条代价（工作树当前值 vs index 快照）实际影响小于它听起来的样子**。sweep 的 `git add` 与 `git commit` 之间只隔一次 `_strike_off_rows`（改队列文件＋加解锁），窗口是**秒级**；而窗口内被改的必须**恰好是本批声明的文件**——按纪律那正是本批产出方自己的文件，产出方此刻应已收工。⚠️ **不粉饰**：这条论证依赖"纪律被遵守"，而本包存在的理由恰恰是"纪律被遵守时仍出了错"。所以推荐 ⒜ **必须配决策点④ 的提交后校验**——校验看的是"提交实际含了哪些路径"，对这条风险不构成覆盖，但至少让内容异常有一道事后眼睛。
3. **⒝ 被否的理由是边界，不是难度**：sweep 的自我约束一直是「账面之外的任何东西都交给人工判断，不猜」（文件头"非 clean"定义那一段）。**替别人 unstage 恰恰是在替人做判断**——而且是不可见地做。⒞ 被否的理由是**代价不对称**：它解决的是 ⒜ 那条秒级窗口风险，付出的是绕开 `git commit` 全部常规行为的代价。

🔴 **本项为什么无默认**：四个选项的**失败方向各不相同**——⒜ 有窗口风险、⒝ 动别人的 index、⒞ 绕开 git 常规行为、⒟ 换来停摆。**不答不会停在原地**：现状（裸 commit）会持续产生夹带的提交，而这正是 `#127` 已裁定要改的。⇒ 须你明确答一个字母。

## 决策点 ②：收紧的作用面

sweep 全文 5 处自动提交：

| # | 函数 | 提交什么 | 现状风险 |
|---|---|---|---|
| 1 | `_process_normal_batch`（主路径） | 批次清单 ＋ 队列文件 | 🔴 `OP-0827-A` 实撞的就是这一处 |
| 2 | `_commit_uncovered_queue_changes` | 队列文件（无待处理行时） | 同形：add 是 pathspec 的、commit 不是 |
| 3 | `main()` 补销遗留尾巴 | 队列文件 | 同形 |
| 4 | `_rerun_ledger` | 台账文件 | 同形 |
| 5 | `_run_scheduled_task_mirror_sync` | 定时任务镜像目录 | 同形 |

| 选项 | 差异 | 代价 |
|---|---|---|
| ⒜ 只改主路径 | 改动最小，只堵住实撞过的那一处 | 🔴 **留四个同形洞**。2–5 每一处都会用**它自己的固定标题**提交整个 index——`docs(队列): 收工重跑文档台账（sweep 自动）` 这种标题夹带别人的收工内容，比批次标题更难被事后发现（它看起来天经地义） |
| **⒝ 全部 5 处** | 五处 commit 与它们各自的 add 对齐 | 改动点从 1 处变 5 处，但每处形态**完全相同**（同一段 pathspec 拼装），单测可参数化覆盖 |

**起草方推荐 ⒝**。理由：这五处的缺陷是**同一个**（commit 不带 pathspec），不是五个。只修一个等于知道另外四个有病还留着——而它们的 add 早就是 pathspec 的，收紧只是让 commit 追上 add，不引入任何新判断。

## 决策点 ③：撞上清单外 index 内容时怎么处置

收紧之后，"清单外但已暂存"的内容会留在工作区。**它会不会被人看见**是一个独立的问题。

| 选项 | 差异 | 代价 |
|---|---|---|
| ⒜ 静默不带走 | 交给既有 `_track_and_alert_orphan_paths`（#238 孤儿告警） | 🔴 **孤儿告警的判据是"脏路径未被任何待处理批次声明"**，而本场景里那些文件确实未被声明 ⇒ 理论上会被它接住。但**没有任何东西保证这一点**——两道机制的判据来源不同（一个看 index，一个看 status），静默依赖等于把"承接是否闭合"留成假设 |
| **⒝ 点名告警但照常落库** | 该批照常提交（内容已收紧），同时在本轮日志里点名"以下已暂存路径不属于本批清单、未被带入，留在工作区" | 多一条日志。⚠️ 噪音风险：若 index 常态含清单外内容，这条会每轮都响——但那本身就是应该被看见的状态 |
| ⒞ 整批跳过不落库 | 最严 | 🔴 用"停摆"换"干净"，同决策点① ⒟ 的代价：并发方不收工，该批次永远落不了库。且**它把别人的暂存状态变成了本批次的阻塞条件**，责任错配 |

**起草方推荐 ⒝**。两条理由：
1. **本包要治的病是"失败无声"**（release ✓、sweep ✓、结果错）。⒜ 修好了结果却仍然无声，等于只治了一半——**下一次没人知道 sweep 挡下过什么**。
2. **⒝ 与既有孤儿告警不重复，是互补**：孤儿告警说"工作区里有没人管的文件"，本条说"本轮 sweep 主动没带走哪些"。两句话的读者动作不同（前者去登记，后者去确认是不是自己忘了 commit）。

## 决策点 ④：提交后校验（post-condition）做不做、多严

**这条是本包的"非恒真自证"锚点**：没有它，「已收紧」与「碰巧这一轮没人暂存过东西」在日志上**外观完全相同**——正是本项目反复付学费的那个形态（建成而没接线，与没建成外观相同）。

做法：提交完成后跑 `git show --name-only --format= <新 sha>`，与预期路径集合比对。

| 选项 | 差异 | 代价 |
|---|---|---|
| ⒜ 不做 | 零成本 | 🔴 收紧是否真的生效，只能靠单测；生产上一旦因为某个未预料的 git 行为（如 pathspec 匹配到目录、大小写、`core.autocrlf` 造成的空提交）而失效，**没有任何东西会说话** |
| **⒝ 做，不一致即告警** | 一次只读 `git show`，比对集合，不一致写日志＋企微 | 每次提交多一次 git 调用（可忽略）。**不阻断**——提交已经产生，abort 也撤不回 |
| ⒞ 做，不一致即整轮 abort | 最严 | 🔴 **提交已经发生，abort 不能撤销它**，只能让本轮后续步骤（对齐、推送）不做——结果是"错误的提交留在本地、且没推上去"，比 ⒝ 更难收拾。且它会连带把已正确落库的其它批次的推送一起拖掉，正是 `#398` ⑺ 要治的形态 |

**起草方推荐 ⒝**。⚠️ **如实标注**：⒝ 是**事后**校验，它证明不了"没夹带"，只能在夹带发生时喊出来。真正的拦截来自决策点① 的实现本身。两者分工不同，不可互相替代。

## 决策点 ⑤：「关键路径」清单收多大

**先把现状钉死**（propose 期 AST 扫描，按函数归属统计 66 个 except 分支）：

| 函数 | 该函数体内 except 分支数 | 备注 |
|---|---|---|
| `_reconcile_with_origin_and_push` | **0** | `#126` 点名的那个函数，今天是干净的 |
| `_push_any_unpushed_commits` | **0** | |
| `_pop_reconcile_autostash` | **0** | |
| `_commit_uncovered_queue_changes` | **0** | |
| `_strike_off_rows` | **0** | |
| `_process_normal_batch` | **0** | |
| `_rerun_ledger` | **0** | |
| `_run_scheduled_task_mirror_sync` | 3（宽） | **都不罩着它的 `git add`／`git commit`**：L1927 只罩子进程调用且在 except 内 `return`；L1952／L1970 罩 webhook |
| `main()` | 5 | L6427 `except SweepAbort`（专用）／L6438 通用兜底（**已 fail-loud**）／L6463·L6467 在兜底内部／L6242 ＝ `#136` 裁定原文要的 fail-open |

🔴 **⇒ 今天关键路径上零宽 except。本决策点定的是「以后不许在哪些函数里加」，不是「现在要拆掉哪些」。**

| 选项 | 清单内容 | 代价 |
|---|---|---|
| **⒜ 窄** | 4 个直接 `git commit`／`git push`／`git rebase`／`git merge` 的函数：`_process_normal_batch`／`_commit_uncovered_queue_changes`／`_rerun_ledger`／`_reconcile_with_origin_and_push`（＋`_push_any_unpushed_commits`／`_pop_reconcile_autostash` 作为同族） | 清单外的函数出问题仍可能被吞。**缓解＝配一条反向检查**：全文中调用了写动词（`commit`／`push`／`rebase`／`merge`／`reset`）的函数若**不在**清单里即报出，让清单漏项自己暴露 |
| ⒝ 宽 | 再加 `_strike_off_rows`（销行）、`_run_scheduled_task_mirror_sync`、`main()` | 🔴 `main()` **必须**有宽兜底（`#198(a)` 的整个价值就在于此）⇒ 宽清单会立刻与既有裁定冲突，得为 `main()` 开例外；`_run_scheduled_task_mirror_sync` 的 3 个宽 except 是"告警／子进程失败不得带崩 sweep"的既有取向，也得开例外。**两个例外一开，这份清单就从判据退化成了名单** |

**起草方推荐 ⒜ ＋ 反向检查**。理由：**判据要能自洽地一句话说清**——「会自己写 git 历史的函数，不许在里面宽捕获」。`main()` 与镜像同步不满足这句话的前提（前者是兜底本身，后者的写段落不在 try 里），把它们塞进来只能靠开例外维持，而**靠例外维持的判据就不是判据**。

## 决策点 ⑥：⑵ 的守卫形态

| 选项 | 差异 | 代价 |
|---|---|---|
| **⒜ 单测 AST 守卫** | 在 `test_工具-落库sweep.py` 新增一组，按源码文本切片 ＋ `ast.parse`／`ast.walk` 断言 | **本文件已有逐字同款先例**：`LocalOnlyCommitGuardTests::test_本类不做任何git写动作`（L6827）就是用这套锁"本组函数体内不得出现写动词"。⇒ 零新造机制、零新增运行时开销、随全量测试自动跑 |
| ⒝ 独立 CI lint 脚本 | 新写一个 `工具-*lint.py`，挂 CI job | 🔴 本项目已有实测教训：**CI job 红了两个多月没人看**（§四 `#118` 原文）。多一个 job 就多一处需要人去看的地方 |
| ⒞ 运行时自检 | sweep 启动时反射自查 | 🔴 把静态性质放到运行时查，**发现得太晚**（错误代码已经在跑），且给生产路径增加了一个可能自己出错的环节 |

**起草方推荐 ⒜**。⚠️ **如实标注守卫的边界**（proposal §残余风险 3 已列，此处复述以免被当作细节略过）：AST 断言锁的是**形状**——它拦不住「把关键逻辑挪进清单外的小函数再宽捕获」，也拦不住 `except OSError` 这类**窄但同样吞掉真问题**的捕获。⇒ 交付措辞只能是「清单内函数不会出现宽捕获」，**不得**写成「关键路径此后不会被静默吞掉」。

## 现存 31 处宽 except 分诊表（🔴 本包**一处不改**，只登记，防止"止了血就没人再想根治"）

propose 期 AST 全量扫描：全文 66 个 except 分支，其中 **31 个宽捕获**（`except Exception` 29 ＋ `except BaseException` 2）。按用途分四类：
