## Context

见 `proposal.md · Why`。本设计要处理的现状约束：

- 4 处独立实现（`工具-共享文档编辑锁.py::_table_data_rows`／`工具-队列查询.py::_table_data_rows`／`工具-落库sweep.py::_parse_section_one`/`_parse_section_two`）各自朴素 `str.split("|")`，且各自对"切不出合法行时怎么办"有不同的既有策略——编辑锁"原样返回交调用方判"（其 docstring 明文承诺）、sweep"静默跳过、不崩溃、不误判"（其 docstring 同样明文承诺，是刻意的设计取舍，非 bug）。
- 队列 #314① 已先行修复了一个相邻但不同的缺口：`_table_data_rows` 此前误要求"行首行尾都必须是 `|`"，导致结尾被外部工具吞掉的行（#313）连列数校验都进不去；该修复已把行首要求放宽为"只需以 `|` 开头"，本变更在此基础上继续推进"反引号感知"这一步，两者是同一族问题的相邻子问题，不是同一处代码的重复改动。
- `queue_table.has_bare_pipe` 现有 Requirement 明文"反引号包裹不豁免"——这是"该不该拒绝写入"层面的判断，与本变更"该不该把反引号内的竖线当列分隔符"是两个不同问题，本设计不改前者。

## Goals / Non-Goals

**Goals:**
- 反引号内的竖线不再被 4 处消费者的切列逻辑当作列分隔符。
- "一行应有几列"这一校验，从"消费者各自记得调用 `column_count_ok`"收进 `queue_table.parse_section_rows` 这一权威入口，新增消费者默认就会拿到列数校验结果，不需要重新发现这件事要做。
- 4 处消费者各自既有的"切不出合法行时怎么办"策略保持不变（原样返回 vs 静默跳过），本变更不强行统一。

**Non-Goals:**
- 不改变 `has_bare_pipe`/`escape_bare_pipe` 的既有语义。
- 不处理反引号本身不闭合（如正文里出现单个孤立反引号）以外的 Markdown 转义规则（如 `` \| `` 反斜杠转义竖线）——本项目现有正文从未使用过反斜杠转义竖线这一写法（grep 全量生产队列文件 0 命中 `` \| ``），不为假想场景增加复杂度，真出现时按"反引号包裹"这一种转义手法引导写作（sweep/编辑锁均已有"改用全角『／』或反引号包裹"的既有提示文案）。
- 不在本变更里决定是否放宽 `append-row` 的裸竖线拒绝范围（见 Open Questions）。
- 不处理 §二/§四 分区可能出现的同类问题以外的分区结构变化——列数常量沿用既有 `SECTION_COLUMN_COUNTS`，不新增分区。

## Decisions

### 决策点 1：反引号跨度识别算法——正则 vs 状态机

**推荐：正则 `` `[^`]*` `` 逐个非重叠匹配，复用 `工具-共享文档编辑锁.py::BACKTICK_SPAN_RE` 已确立的同一模式**（该正则已在生产代码里用于⑩因果断言证伪命令校验，队列 #285 落地并跑过真实生产队列文件，不是本变更首次引入的新写法）。

切列算法：先用该正则找出行内全部反引号跨度的字符区间，切列时如果某个 `|` 落在任一区间内，则不作为分隔符（等价于：把每个反引号跨度整体当成一个不可分割的字符序列，再对"反引号跨度之外的部分"做正常的 `|` 分隔）。

**备选方案（状态机，逐字符扫描并维护"当前是否在反引号内"的布尔状态）**：能额外处理"反引号未闭合"这种正则天然处理不了的情形（正则 `` `[^`]*` `` 要求成对出现，落单的反引号会被当成普通字符，不产生跨度）——**本设计判断这正是期望行为，不是缺陷**：一个未闭合的反引号本就不构成"反引号跨度"，其后的竖线仍应按列分隔符处理，这与 Markdown 渲染器对未闭合反引号的处理方式（不生成 code span）一致，状态机方案在此处不比正则更正确，只是更复杂，故不采用。

### 决策点 2：`parse_section_rows` 返回结构——三元组 vs 具名结构

**推荐：`(原始行文本, 单元格列表, 列数是否符合布尔值)` 三元组**，与既有 `_table_data_rows` 的 `(line, cells)` 二元组返回习惯保持形状上的连续性（调用方原有的 `for line, cells in _table_data_rows(...)` 解构写法只需加一个变量，不需要理解新的具名类型）。

**备选方案（`dataclass RowParseResult`）**：类型更自解释，但本项目现有 4 处消费者均未使用 dataclass 表达表格行（`工具-落库sweep.py::_parse_section_one` 用的是 `dict`），引入新的返回类型形态会制造第三种表达同一概念的方式，与"消费者各自决定要不要用" 相悖；且元组已能满足调用方直接解构的需求，不引入额外类型定义。

### 决策点 3：4 处消费者的迁移方式——保留函数名与签名 vs 直接改调用点

**推荐：保留 `_table_data_rows`/`_parse_section_one`/`_parse_section_two` 现有函数名与调用方签名，只替换函数体内部实现为委托 `queue_table.split_row_cells`/`parse_section_rows`**——这样调用方（release 校验的 10 项检查、lint.py 的两项检查、sweep 的批次处理与stale-row检测等）零改动，回归测试可以只验证"输出结果不变（对既有合法行）＋输出结果变好（对反引号内竖线的行）"，不需要同时改造调用方逻辑，缩小本次改动半径。

## Risks / Trade-offs

- **[风险] 反引号跨度识别可能误伤"反引号本身就是内容的一部分"的边界情形**（如正文讨论"反引号"这个符号本身、出现奇数个反引号）→ **缓解**：沿用 `BACKTICK_SPAN_RE` 这一已在生产环境跑过的既有实现，不是新写的正则；task.md 要求对当前生产队列文件全量跑一次新旧切列结果 diff，任何"单元格数量因本变更而变化"的行都需人工过目确认是修复还是误伤，不允许静默上线。
- **[风险] `工具-队列结构lint.py`/`_validate_release_structure`①对历史行的判定结果会改变**（proposal.md 已标注为 BREAKING）→ **缓解**：这属于预期内的行为修正（消除误报），但仍需在 tasks.md 里显式核对"迁移前后，生产队列文件里所有行的列数校验结果"这份 diff，凡出现从"校验通过"变为"校验失败"的行（真实列偏移此前被反引号意外掩盖，理论上不应发生，因为反引号感知只会让切列更精确、不会让原本正确切出的列数变多或变少），须先查清楚原因再上线。
- **[风险] sweep 的"静默跳过"策略与新解析入口的"原样返回列数校验结果"存在语义落差**——sweep 若不假思索地全量切换到 `parse_section_rows`，可能需要额外一行判断"列数校验为 False 时是否仍要跳过该行"，否则会改变 sweep 现有的静默容错行为 → **缓解**：决策点 3 已锁定"只替换切列内部实现，不改各消费者既有的行为策略"，sweep 侧的调用点需要显式加一行"若列数校验为 False，按其既有'静默跳过'策略处理"，tasks.md 需把这一行为保持验证列为独立任务项，不能假设它自动成立。

## Open Questions
