## Context

见 `proposal.md`「Why」——README 主表 177.7 KB、12 个读取方共用一份真身，登记走 Edit 直改逼迫每次登记吞 178 KB 上下文。四个 spec（`followup-readme-registry`／`followup-readme-archive`／`followup-readme-row-length-guard`／`followup-readme-read-guard`）分别对应派单件四件；本节按四件逐一给出实现取舍。约束条件：不改表头/列序、不动 `.51`、不发企微、rules/SKILL 正文改字交 Cowork（本包只交付建议文本）。

## Goals / Non-Goals

**Goals:**
- 登记与状态更新全部经 CLI 完成，人不再需要 Read 全文。
- 已闭环历史行迁出主表且 12 个读取方零回归。
- 超长行外置，行长有机器判据兜底、不再反弹。
- README 与两份队列真身享有同款读侧禁通读门禁。

**Non-Goals:**
- 不改变跟进信「串行闸」「判例批改法」「发送硬前置三条」等已有业务纪律本身（那些在 `.claude/rules/跟进信与专员.md`，本包不动正文）。
- 不实现自动发信或自动批准——CLI 只是登记/改状态的执行工具，`wecom-followup-review-state` 既有的人工批准链路不变。
- 不做「12 个读取方」之外的其它 README 消费方改造（若后续发现遗漏读取方，走新的 queue 行，不在本包补）。

## Decisions

### D1（对应派单件①）登记 CLI：单文件锁 + 写前列数校验 + 写后回读，不引入新的持久化状态
- **决策**：CLI 不自建数据库或缓存层，每次调用都是「取锁 → 读表格快照 → 按表格已有解析器（`followup_gate._readme_rows` / `readme_table` 权威实现之一，与 `工具-跟进信README查询.py` 复用同一份解析逻辑，不新造第二份解析器）定位/追加行 → 写回 → 回读校验 → 释放锁」的无状态流程。
- **理由**：README 表格解析已有至少两份「权威实现」（sweep 注释里明确点名 `followup_gate`/`readme_table`），新增 CLI 若再造第三份解析器会重演「同一逻辑多处实现、互相漂移」的问题；复用现有解析器是本包内部的 one-in-one-out（不新增解析口径，只新增写入入口）。
- **备选方案**：CLI 自带正则直接拼字符串写入——放弃，因为无法保证与既有查询工具对表格结构变化（如未来加列）的假设一致，写后回读也更难做结构化比对。

### D2（对应派单件②）已闭环归档：先做「9 个具名读取方」的代码走查结论，而非假设需要瀑布查询
- **决策**（本次走查结论，见下表）：`工具-跟进闸查询.py`／`工具-跟进信README查询.py`（默认路径）／`工具-共享文档编辑锁.py`（G 闸）／`工具-落库sweep.py`／`followup_readme_bridge.py`／`approve_followup_letter.py`／`dispatch_followup_letters.py`／`draft_gap_check.py`／`push_followup_letter.py` 共 9 个具名读取方，**全部属于「活行读取方」**——它们的判定逻辑本质上是「该收信人最新一封」或「当前非终态行」，而归档判据（终态 + >30 天）保证这两类查询的目标恒在主表中，归档动作不改变其结果。**真正存在跨归档查找需求的只有登记 CLI 自身的 `set-status`**：当调用方按编号定位一个已被归档的编号时，需要能报出「该编号已归档、不可再用登记 CLI 改状态」而不是笼统的「编号不存在」——这是登记 CLI 内部的一处「主表未命中再查归档」两段式查找，不涉及上述 9 个既有读取方的代码改动。

  | 读取方 | 判定语义 | 归档后是否需要改造 |
  |---|---|---|
  | `工具-跟进闸查询.py` | 该收信人最新一封（`build_report` 遍历主表取 `latest`） | 否；主表内该收信人无任何行时视为「无在途」，语义不变 |
  | `工具-跟进信README查询.py` | digest/grep，默认只读传入的 `--file`（默认主表） | 否（默认行为不变）；**新增**同队列查询工具先例的显式 `--file <归档件>` 用法，供人工核对历史 |
  | `工具-共享文档编辑锁.py`（G 闸） | 持锁窗口内 acquire/release 快照 diff | 否；只关心当次窗口内的表格变化 |
  | `工具-落库sweep.py`（待发信盘点） | 委托②README查询 `--digest --json` 取非终态计数 | 否；归档行恒为终态，天然不计入 |
  | `followup_readme_bridge.py` | 该收信人最新一封已发出的信（stem 精确匹配优先，`latest` 兜底） | 否；同①，最新一封恒在主表 |
  | `approve_followup_letter.py` | 定位 `⏳ 待你审` 的目标行并转 `🆕 待发` | 否；非终态行恒在主表 |
  | `dispatch_followup_letters.py` | 处理 `🆕 待发` 的行 | 否；非终态行恒在主表 |
  | `draft_gap_check.py` | 近 `--window-days`（默认远小于 30）窗口内的缺口检测 | 否；窗口远小于归档阈值，不会触及已归档行 |
  | `push_followup_letter.py` | 人工触发指定编号发送 | 否；可发送的编号必是非终态、恒在主表 |

  **须 Shao Peishen 书面确认**（proposal 知识资产三问 ⑵）：上表「归档后是否需要改造」列的判定基于本次源码走查（`OP-0906-A`），非该 9 个工具作者原始设计文档；确认后方可 apply，若确认后发现遗漏的第 10-12 个读取方（各工具自身单测不计入独立读取方，随其宿主工具的改造同步跑），按新 queue 行补，不阻塞本包其余三件。
- **理由**：先走查代码而非直接假设「全量读取方需要瀑布查询」，避免在没有真实需求的地方引入不必要的两段式查找复杂度（对应「不新增不必要的抽象」的项目工程纪律）。
- **备选方案**：不做代码走查、给全部 9 个读取方无差别加「主表未命中再查归档」——放弃，因为对语义本就是「只看活行」的读取方（如闸查询）而言，加一层归档回退查找是死代码，且会制造「闸查询是否应该在收信人所有信都归档后仍返回最后一次归档状态」这种未被业务要求过的新歧义。

### D3（对应派单件③）行长口径：复用队列 K2 外置手法 + 编辑锁行长判据分级生效
- **决策**：外置格式（原文原样迁 `跟进信行日志/<部门#N>.md`，行内留首段＋末段＋指针）与阈值判定逻辑直接复用队列「行内日志外置口径」（K2）与「行长校验⑪首周告警、一周后阻断」的既成代码路径，只是把保护目标从两份队列真身扩展到 README；不为 README 另写一套独立的行长判断代码。
- **理由**：K2/⑪ 已经过队列场景验证（`.claude/rules/队列与落库.md`），README 的行长问题在结构上与队列行日志问题同构（都是「历史回写段单调增长撑大单行」），复用现成机制是本包能保持小范围改动的关键。
- **备选方案**：为 README 单独实现一套阈值/外置逻辑——放弃，制造重复代码与未来两处口径漂移的风险。

### D4（对应派单件④）门禁：扩展既有 hook 目标清单，不新建门禁机制
- **决策**：`hooks-pretooluse-queue-read-guard.ps1` 的 `$script:ProtectedExactPaths`／`$script:ProtectedArchiveNameRegex` 两个既有变量分别追加 README 主表精确路径与 `README-归档-.+\.md` 的正则，机制工具白名单同步加入登记 CLI 与 `工具-跟进信README查询.py`；不新建第二个 PowerShell 门禁脚本。
- **理由**：README 场景与队列场景的读侧问题同构（单行可达数 KB～数十 KB，Read/Grep 整文件即灌爆上下文），复用同一个已验活的 hook 比新建一个平行门禁更省维护面，且天然共享同一份 `reports/hooks-audit.jsonl` 审计流。
- **rules/SKILL 改句**：本包只产出建议文本（登记只用 CLI、判状态只用查询）交 Cowork，在 CLI 验活（D1 单测全绿）后落字到 `.claude/rules/跟进信与专员.md` 与 `zhuopin-followup-letter`／`zhuopin-send-followup` SKILL——先机制后降指针，避免规则文本先于工具落地造成「文档说能用、工具还没有」的空窗。

## Risks / Trade-offs

- [风险] D2 的「9 个读取方全部活行」结论若有遗漏（例如某单测里藏着一个跨历史统计的隐藏用途未被走查覆盖）→ **缓解**：验收条款要求归档迁移前后对全部 12 个读取方（含单测）跑基线对比，任何输出差异视为分类错误、退回本决策重判，不允许「先上线再观察」。
- [风险] 编辑锁行长判据「一周后阻断」窗口内，若仍有历史长行未及外置 → **缓解**：D3 复用的 K2/⑪ 机制本身已有「首周告警」缓冲期，且逃生阀 `行长豁免：` 可对已知例外显式放行，不会硬性卡死既有登记流程。
- [风险] hook 目标清单扩展（D4）如果遗漏归档件的正则匹配边界（如文件名含非常规字符）→ **缓解**：复用队列归档件同款正则形式（`^前缀-.+\.md$`），沿用已验证过的匹配方式而非重新设计。
- [权衡] D1 选择不新造解析器、复用既有 `followup_gate`/`readme_table` 实现，意味着 CLI 的行为边界受制于这两份实现的既有假设（如表格必须是标准 Markdown 表格）——接受此权衡，因为独立维护第三份解析器的成本更高。

## Migration Plan

1. D1 落地：登记 CLI + 单测，验收 append/set-status 正常路径与拒绝路径。
2. D2 落地：先产出「12 读取方基线输出」（改前快照），拿着 D2 决策表找 Shao Peishen 书面确认分类结论，确认后再执行归档迁移脚本，逐一 diff 基线。
3. D3 落地：>5KB 行外置 + 编辑锁行长判据（先告警模式验活，观察一周行为符合预期后再由值周巡检切换为阻断模式，与队列⑪的两阶段上线节奏一致）。
4. D4 落地：hook 目标清单扩展，跑一次真实 Read README 主表验证拦截与审计留痕；产出 rules/SKILL 改句建议文本交 Cowork。
5. 全量测试：`test_工具-跟进闸查询.py`／`test_工具-跟进信README查询.py`／`test_工具-共享文档编辑锁.py`／aibot 相关单测全绿后，队列 §一 `#490` 回写销号。

**回滚**：D1-D4 均为纯代码/文档改动，无数据库迁移；若归档迁移（D2）后发现分类错误，回滚手段是把归档件对应行整行迁回主表原位置（编号不变，因编号本就不复用，迁回不产生冲突），随后修正分类结论重新迁移。
