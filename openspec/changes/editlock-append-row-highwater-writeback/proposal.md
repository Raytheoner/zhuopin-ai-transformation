## Why

**病灶（可当场复核的代码事实，非推断）**：编号高水位线这个计数器在 `0-学习与工具/工具-共享文档编辑锁.py` 里**只有一个写入方** —— `_reserve_ids()`（`acquire --reserve` / `--reserve-multi` 走的那条路）。`cmd_append_row()` 从 `_resolve_append_cells` 一路到 `target_path.write_text(new_text)` 再 `return 0`，**没有任何一行触碰高水位线**。

复核方式（本会话实测，master ＠ `d987d31`）：

```
$ grep -n "HIGH_WATER\|高水位" 0-学习与工具/工具-共享文档编辑锁.py
… 1672 _read_high_water_mark  ／ 1880-1955 _reserve_ids（唯一写入方）
… 5956-6006 cmd_acquire 的预留分支  ／ 6013 acquire 的只读回显
（cmd_append_row 所在的 2929-3053 区间：零命中）
```

于是同一个计数器有**两个写入编号的入口、只有一个会回写**，而错的那一半**不报错**：

- 走 `--reserve` ⇒ 取号、写行、推线，三件事齐。
- 走 `append-row --number N`（N 是个新号）⇒ 行落盘、**线不动**，命令返回 `0`、打印 `✓ 已追加一行`。

**后果不落在写的人身上，落在下一个人身上**：线一旦滞后于文件，下一次 `--reserve` 算出的 `current+1` 必然撞上已经存在的可见行 ⇒ 命中 `_reserve_ids` 的碰撞前置校验 ⇒ **整体拒绝并回滚该次 acquire**，该分区对**全线**取不到新号，直到有人手工订正那一行。

**判据（一句话）**：**一个共享计数器如果有两个写入方，两个都必须推它；只让其中一个推，等于把「谁走了哪条路」变成一条无人守护的口头纪律，而违约的代价由下一个人支付。**

### 实证：两天之内两次，不是设想

2. **2026-09-08（`OP-0908-B`，`#505` 立行的那一次）** —— CC `OP-0908-I` 当日**走锁**写入 §四 `#174`（`reports/queue_edit_lock_bypass.jsonl` 当日无记录 ⇒ 排除绕锁），高水位线仍停在 `§四 #173`；下一个会话 `append-row --number 174` 撞号、改 175 又被「未预留」拦、再 `--reserve` 被整体回滚，**三次才走通**。已按 Shao Peishen 当日答 `1a` 手工把线订正为 `§四 #174` 解冻（**治标**）。

### 为什么「release 的③预留归属校验」没有兜住

`_validate_release_structure` 的③校验确实会拒绝「本次新增、却不属于本次 `--reserve` 预留集合」的编号行 —— 但它有**三个既有豁免口**，每一个都是一条「编号落盘而线不动」的合法通路：

| 豁免 | 代码位置 | 适用面 |
|---|---|---|
| 企微机器人收件登记（协议〇.10 ⑶，队列 `#333`②） | `is_aibot_intake_row` | 仅 §一 |
| 修复既有破损行（编号已在 git HEAD 中，队列 `#414` A3-2） | `is_repair_of_existing` | §一/§四 |
| 行内逃生阀 `预留豁免：<理由>` | `has_reserve_waiver` | §一/§四 |

外加：`--file` 显式覆盖到非队列系统目标时，本就不走这套口径。

⇒ **③校验是「拦住不该发生的写入」，不是「保证计数器同步」**。它守的是纪律，守不了状态一致性 —— 每开一个豁免口，就多一条让线滞后的路。本包补的正是它守不到的那一半。

（`预留豁免：` 目前在两份队列真身里只有 1 处命中，说明它不是主要泄漏路径；两次实证具体走的是哪一个豁免口，本包**不臆断**，列为 apply 阶段的取证任务 tasks §0.6。）

### 为什么必须机器守、不能再靠人守

CLAUDE.md §5「规则退休制」判据 —— 人守条目被违反 3 次即机制化。这条口头纪律（「新行编号一律用 `--reserve` 取」，协议〇.7，2026-07-31 立）已有的违反计数：`#200`／`#233`（归因绕锁）、2026-09-07、2026-09-08 —— **四次**，且最近两次是**走锁的、合规的**会话，只是选了不回写的那个入口。违反者不是不守纪律的人，是**读了文档也看不出两个入口有区别**的人 —— 因为命令返回 `0`。

## What Changes

（拟议，**本次不实现**；D1–D4 编号与 design.md「决策点」一一对应）

- **D1 `append-row` 写入带编号的新行后，同步推进该分区高水位线** —— 与 `--reserve` 走**同一条**回写路径（`_reserve_ids` 现有的行定位 ＋ 分区片段替换逻辑抽成共用函数），两个入口对同一计数器行为一致。
- **D2 推线在前、写行在后** —— 推线失败即**整体拒绝、零残留**（不写行）；反序（先写行后推线）会在推线失败时留下「行在、线不在」的半成品，正是本包要消灭的那个状态。
- **D3 单调推进** —— 新值 ＝ `max(当前值, N)`。`N ≤ 当前值`（补写一个空洞号、或修复既有行）时线**不回退、不改动**，与协议〇.8「编号永不复用、允许留空洞」一致。
- **D4 只对队列系统目标生效** —— `--file` 显式覆盖到非队列系统文件时，沿用今日行为（不推线、不报错）。那类目标本就没有高水位线行，一律推线会让全部既有单测的临时文件路径当场报错。

**BREAKING**：`append-row --section 一|四 --number N`（N 大于当前高水位线）在同一输入下的**副作用**由「只改一行」变为「改一行 ＋ 改高水位线声明行」，且推线失败时返回码由 `0` 变为非 `0`。这正是本变更的目的，但它确实改变了既有模块的对外语义，故走本流程。

**受影响的既有 spec 断言**：`editlock-queue-number-reservation` 现有 Requirement 均**不被反转** —— 它们讲的都是 `--reserve` 侧的行为，本包只在同一 capability 下 **ADDED** 两条新 Requirement，不 MODIFIED 任何一条。

## Capabilities

### Modified Capabilities

- `editlock-queue-number-reservation`：**ADDED** 两条 Requirement（① `append-row` 写入新编号后同步推进高水位线：单调、先推后写、fail-loud；② 非队列系统目标不适用本项）。**无 MODIFIED、无 REMOVED。**

### New Capabilities

## 本次退休哪一个既有守卫；若不能退，写明为何不能

**不退休任何既有守卫。** 理由：本包**没有新增任何一道守卫** —— 它补的是一个**缺失的状态写入**，不是加一道判定。守卫面净不变，可绕过面净减少（少一条让计数器滞后的路），与协议〇.9 措施 B 想防的「规则只增不减」同向。

**候选逐一过一遍，登记在此，避免「补上了就没人再想」**：

- **候选一：退休 `_reserve_ids` 的「预留号与可见行冲突 ⇒ 整体拒绝」前置校验**（队列 `#185`）。D1 落地后，「走锁但走了不回写入口」这条成因消失，该校验看似可退。**不取** —— 它还守着**另一条**成因：绕锁直写（`#200`／`#233`，`queue_edit_lock_bypass.jsonl` 有独立记录佐证其真实发生过）。退掉它，绕锁写入造成的滞后就会从「当场拒绝」退化成「静默分配一个已被占用的号」—— 那是比本包要修的缺陷更坏的一种失败。
- **候选二：退休 release ③ 的行内逃生阀 `预留豁免：`**。D1 之后，未预留的新号不再造成状态不一致，逃生阀的必要性下降。**不取，但降级为 apply 后的观察项** —— ③校验守的是**纪律**（「该走 `--reserve` 你没走」），本包治的是**状态**（计数器滞后），两者目标不同；且该逃生阀在真身里只有 1 处命中，退休它收益极小、却要动一条与本包无关的门禁语义。登记为 design 审可讨论、apply **不做**。
- **候选三：退休高水位线声明行第 12 行里那一长串「当场订正」的历史注释**。**不取，不是守卫** —— 那是实证载体，退休制不适用；但 D1 落地后它会**停止增长**，这本身就是本包生效与否的生产信号（见「验收与晋档条件」）。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？**
   - **「我这次写的这个号，需不需要我自己去把线推一下」** —— 这是本次要显性化的**主判据**。今天它完全靠人读源码或撞过一次才知道：`--reserve` 帮你推、`append-row --number` 不帮你推，而**两者的成功输出长得一样**（都是 `✓`、都返回 `0`）。规则 ＝「凡有编号落盘，线必须 ≥ 该号」；**例外** ＝ 非队列系统目标（D4）；**尺度** ＝ 单调，不回退（D3）。
   - **「行落盘了但线没推，算成功还是算失败」** —— 人会说「这是半成品」，机器今天说「成功」。本包把它显性化为 D2 的先后次序 ＋ fail-loud 返回码。
   - **「线可以留空洞吗」** —— 协议〇.8 已明文可以，但该口径此前只写在协议里、没有以代码形式表达在 `append-row` 这一侧；D3 把它落成 `max()`。
2. **由谁显性化？** 持有人 ＝ 本会话（CC `OP-0908-K`，机制/工具线）；backup ＝ Cowork 环境总线 `OP-0907-AL`（`#505` 派出线）；仲裁人 ＝ Shao Peishen。
3. **用什么方法提取？** **历史案例反推** —— ① 本会话对 master ＠ `d987d31` 的只读源码取证（`cmd_append_row` 全程零命中高水位线，`_reserve_ids` 为唯一写入方）；② 高水位线声明行内 `OP-0907-AM` 2026-09-07 留下的订正原话（§一 499→500、§四 168→170）；③ `#505` 行内 `OP-0908-B` 2026-09-08 的「三次才走通」实证。apply 阶段补**受控复现**（真 CLI ＋ 真 git 仓库，见 tasks §2.4）。
