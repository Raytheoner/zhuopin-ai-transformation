# followup-supplement-channel Proposal（队列 §一 #399，含并入的 #400）

> 🔴 **本变更包只到 design 审为止**。出件会话（2026-08-25 CC 无头批处理 A24）**未 apply、未改任何一行生产源码**，开工 opener 明令「只 propose＋design 出件并登记 §四 待审，到 design 审即停」。

## Why（为什么做）

**《补件登记》节里的补件，既批不了、也不会被班次扫到——两端都够不着它。**

补件的发送状态写在跟进信 README《补件登记》节的**列表项**（`- **发送状态**：⏳ 待你审`），而批准与发送两条通道**都只认表格行**：

- `approve_followup_letter.py` 经 `readme_table.locate_row` 定位**《现有跟进信清单》表**的行、改该行的「发送状态」**列**；
- 每工作日 09:30 的 `ZhuopinFollowupDispatchDaily` 经 `readme_table.iter_rows` 扫**同一张表**。

⇒ 列表项形态的补件对这两条通道**完全不可见**。**已实测**：2026-08-25 本机 `python scripts/dispatch_followup_letters.py --dry-run` 输出 `无「🆕 待发」行`，而当时《补件登记》⑶ 恰恰处于待发/已发流程中——**班次没有报错、没有告警、只是什么也没看见。**

🔑 **成因是一个正确修复的副作用。** 2026-08-24（A1）把补件挪进独立小节，是为绕开 `工具-跟进闸查询.py` 的真实缺陷：串行闸取「该收信人在表中的**最后一行**」当作「最近一封信」，补件一旦混进那张表就会被读成一封状态未知的在途信、把闸由开误判成锁。**绕开缺陷的同时也绕出了自动发送通道**，A1 记了前一半、没人注意到后一半。**当日造出、当日咬人**：2026-08-25 06:56 那封合并补件被迫复用 `delivery` 原语走一次性直发脚本（脚本落 Temp 不入库，审计前缀 `supplement_*`），四链路里首跑还崩在 `AuditLogger.record` 签名上——实况见队列 §二 `B-0825_5`。

**本包要解决的不是「让补件也能被发」这一个动作，而是「补件到底住在哪」这个结构问题。** 它现在是本仓库唯一一种**有发送状态、却不在任何机器认得的载体上**的对外件。

**并入 #400**（同一载体、同一批准脚本）：`采购部#18` 一行两格自相矛盾——**编号列** `采购部#18（待你审，暂不占号）` vs **发送状态列** `🆕 待发`。只读编号列的人判「还没批」，只读状态列的人判「已批待发」。`followup_gate.number_status_mismatch` **已经能检出它并给出 warning**（`工具-跟进闸查询.py` 侧），但**没有任何一处会去清除那个后缀**——批准脚本转态时不碰编号列。

## What Changes（改什么）

1. **新增能力 `wecom-followup-supplement`**：把补件确立为一种**有名有份的登记形态**，定义它的载体、定位判据、状态词汇、与串行闸/编号/入信配对的关系。
2. **`readme_table` 增加显式表选择**：由「取文首第一个含『发送状态』的表头」改为**按所属章节标题显式选表**，主表与补件表各有其名。⚠️ 这是本包**唯一改变既有模块对外语义**的地方（见下 §Impact 与 design 决策点 2）。
3. **批准脚本 `approve_followup_letter.py` 兼容补件**：新增 `--table` 选择器；转态时**一并清除编号列的「（待你审／暂不占号）」括注**（#400）。
4. **班次扫描 `dispatch.py`：补件纳入 or 显式人工通道化——二选一，见 design 决策点 4**（本包**不预设**答案，两案都已成型、代价已量化，待签认）。
5. **四处「不该看见补件」的消费者取得结构性免疫**（闸查询／编辑锁串行原则闸／入信配对桥／起草缺口检测）——**靠它们根本读不到那张表，不靠记得加过滤**。
6. **新增守卫：补件表位置断言**（见 design 决策点 3）。

## 本次退休哪一个既有守卫（协议〇.9 措施 B，强制）

**退休 `工具-跟进闸查询.py` 与 `工具-共享文档编辑锁.py` 两处各自持有的「隐式文档顺序判据」。**

这不是一条写下来的规则，而是一条**从未被任何人声明、却被两个独立实现同时依赖**的判据：两处都用「文件里第一个以 `|` 开头且含『发送状态』的行」当表头。它今天正确，**只因为补件表恰好排在主表后面**。把补件表挪到主表之前——一次纯排版编辑——两处会**同时**开始读补件表当主表，**且都不会报错**。

本包用**显式章节选表**替代它，并配一条断言把「谁在前谁在后」从判据里彻底移除。**⇒ 净减一条人守（且是一条无人知道自己在守的人守），不新增人守。**

## 伴生文件的 .gitignore 覆盖（强制）

**本变更不新增任何自动生成的文件名形态。** 逐项核对：

- 批准冷却态文件 `resolve_followup_approval_cooldown_state_path(...)` 是**既有**产物，本包只是让补件行也走进同一条路径，**不产生新形态**（补件行的 `row_identity` 与普通行同构，落进同一个 JSON 的另一个 key）。
- 本包不新增锁文件／快照／备份／改名退路产物。
- **实测（非推断）**：`git check-ignore -v "5-平台底座/wecom-aibot-service/reports/followup_approval_cooldown_state.json"` → 退出码 0，命中规则 `.gitignore:28:**/reports/`。真实落点由 `repo_paths.py:64` 给出。**apply 阶段若实现偏离本条（换了落点或换了文件名形态），须重新跑一次 `git check-ignore -v` 并回改本节，不得沿用此结论。**

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？**
   - **「什么算补件、什么算下一封正式信」** —— 现在只在起草人脑子里。已知尺度：补件是对**已发出信**的补充/更正/解除通知，不引入新议题、不占编号、不占串行闸；一旦引入新议题就该是新一封正式信。**这条尺度此前从未成文，本包 spec 是它第一次被写下来。**
   - **「补件要不要回复」** —— 2026-08-25 那封同时含「通知（不用回）」与「签认（必须回）」两半，说明这不是补件形态的属性、而是逐封的属性，须显式登记。
   - **「补件发出后什么算了结」** —— 主表有闭环四态，补件没有。需回复的补件收到签认后算不算闭环？谁去改那一格？（design 决策点 5）
2. **由谁显性化？** 持有人 **Shao Peishen**（跟进信纪律的拍板人）；backup **孙涛**（决策代理，可代 design 审）。登记进《跨场景前置数据与知识库任务总表》§一.2 知识资产台账。
3. **用什么方法提取？** **历史案例反推** —— 现存补件样本共 3 条（2026-08-24 两封 ⑴⑵ ＋ 2026-08-25 合并件 ⑶），另有 2026-08-19「澄清件」先例一条。样本量太小，故本包 spec 只固化**已被这 4 个样本坐实**的判据，把未被坐实的（如「补件能不能有自己的补件」）显式列为 Out of Scope，不凭空设计。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：**档 3（内部服务）**。本服务已在开发环境用真实凭据跑通对内部专员的真实发送（`wecom-aibot-service` 现状），补件通道是其已有能力的一个形态扩展，不改变档位。
- **晋下一档的条件**：本包**不谋求晋档 4**（对客交付）。补件通道的收信人恒为内部专员，`CUSTOMER_OUTBOUND_ENABLED` 不涉及。
- **本包自身的验收条件（逐条）**：
  1. `dispatch_followup_letters.py --dry-run` 能列出补件表里的 `🆕 待发` 行（或按决策点 4 案 B，显式打印「补件表 N 行，本通道不自动发送」——**沉默不算通过**）；
  2. `approve_followup_letter.py --table 补件` 能把补件行 `⏳ 待你审` → `🆕 待发`，且**同一次转态清掉编号列括注**（#400）；
  3. 🔴 **反例测试**：把补件表**移到主表之前**，四处消费者（闸查询／编辑锁 release／入信桥／起草缺口）**必须全部 fail-loud**，MUST NOT 静默读成主表；
  4. 用 2026-08-25 那封真实合并补件做端到端复现（**LAN 无关，走公网 aibot 通道**）——**须见 `errcode=0` 与审计事件，不得以「命令没报错」代替**。
- **价值指标（风险型）**：*「有发送状态、却不在任何机器认得的载体上」的对外件数量*。基线 **3 条**（2026-08-24 ⑴⑵ ＋ 2026-08-25 ⑶，本包出件当日实测）；目标 **0 条**。基线由业务 Champion（Shao Peishen）确认存档。
- **LLM 判据黄金集**：**不适用** —— 本包全部判据为字符串前缀比对与表格结构定位，无任何 LLM 运行时判断。

## Out of Scope（明确不做）

- **不修 `工具-跟进闸查询.py` 取「最后一行」当最近一封这条判据本身。** 它在主表语境下是对的；本包让补件不再进入那张表，问题在源头消失。若日后某部门有第二位收信人（`_collect_intake_rows` 注释已标出那一天），另立行。
- **不做「补件的补件」。** 无样本，不凭空设计。
- **不并入 `工具-跟进闸查询.py` 与 `编辑锁` 两份 README 解析实现。** 两份独立实现是既有决定（编辑锁 docstring 明写「避免额外的跨包耦合」），本包只要求**两份都显式化选表**，不改变「有两份」这个事实——那是另一件事的范围。
- **不下线 2026-08-25 那份一次性直发脚本**（它本就落 Temp、未入库，随会话消亡）。
