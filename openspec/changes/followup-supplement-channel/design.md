## 〇、先说三句最该被记住的

**⑴ 把补件放回主表，闸会锁——而且是两种状态下都锁，第二种没人预料到。**
A1 当时实测的是「补件以 `⏳ 待你审` 进表 ⇒ 闸由开翻锁」。本轮把**补件已经发出去之后**（`✅ 已推送`）那一态也测了：**闸照样是锁的**。原因很实在——`followup_gate` 的闭环四态里没有一个能描述「一封不需要回复、已经送到的补件」，而 `✅ 已推送` 明明白白属于 `IN_FLIGHT`。⇒ **「等它发完就好了」这条最自然的想法是错的**：补件进主表，闸就从此不再为这个收信人打开，直到有人手工给它编一个闭环态。

**⑵ 补件一旦发出，它会开始截胡本该属于正式信的回件——而配对结果看起来完全正常。**
实测：补件行处于 `⏳ 待你审` 时，入信桥把一封新回件配给 `财务部#15`（正确，因为「还没发出的信不可能收到回件」这条判据把它排除了）；**同一封回件，在补件行转成 `✅ 已推送` 之后，被配给了补件行**（`channel=latest`）。**两次都没有报错、没有 warning、没有低置信标记。** 这正是 `NOT_YET_SENT_STATUS_PREFIXES` 那条判据的边界：它只挡住「还没发出的」，挡不住「发出了但不该参与配对的」。

**⑶ 两个独立实现，同时依赖着一条谁都没写下来的判据：谁排在文件前面。**
`aibot_service.readme_table.iter_rows` 与 `工具-共享文档编辑锁.py::_followup_readme_rows` 是两份刻意独立的实现（编辑锁 docstring 明写「避免额外的跨包耦合」）。**两份都取「文件里第一个以 `|` 开头且含『发送状态』的行」当表头。** 今天正确，只因补件表恰好排在主表后面。**把补件表挪到主表前面——一次纯排版编辑——两份会同时开始把补件表读成主表，且都不报错。** 这就是本包要退休的那个守卫：一条无人知道自己在守的人守。

## 一、取证（全部本机实测，2026-08-25）

**取证脚本**：`scratchpad/probe_399.py`、`probe_399b.py`（只读 ＋ 内存改写，不落盘、不触碰仓库文件）。**基线**：README 主表 54 行、6 列，表头 `['编号','日期','收信人','主要事项','交期要点','发送状态（2026-07-06）']`。

### 1.1 现状：班次对补件完全看不见

```
$ python 5-平台底座/wecom-aibot-service/scripts/dispatch_followup_letters.py --dry-run
[dry-run] 无「🆕 待发」行，本轮不会发送任何消息。
```

🔴 **注意这句输出的形态**：它不是「跳过了 N 行补件」，也不是任何一种告警——**它是一句完全正常的「今天没活」**。同族＝根 CLAUDE.md §5「工具静默回退」：*当一个只读命令返回了「太干净」的结果，先问它是不是根本没读到我以为的那个对象。*

### 1.2 反事实 A：补件作为普通行进入主表 —— 四处下游各自的答案

| 消费者 | 基线 | 补件行 `⏳ 待你审` | 补件行 `✅ 已推送` |
|---|---|---|---|
| `工具-跟进闸查询.py`（唐燕萍） | ✅ **开** / 依据 `财务部#15` | 🔒 **锁** / 依据变成补件行 | 🔒 **锁** / 依据仍是补件行 |
| 入信桥 `pair_reply_to_letter`（一封新回件） | — | 配到 `财务部#15`（**正确**） | 配到**补件行**（**错**，`channel=latest`） |
| 起草缺口 `_drafted_recipient_dates`（唐燕萍） | 15 条，最新 `2026-08-23` | **16 条，最新 `2026-08-25`** | 同左 |
| 编辑锁 `_validate_followup_readme_release` 串行原则闸 | — | **拒绝 release**（「前一封尚未闭环」）；须编 `串行豁免：` 绕过 | 同左 |

**编号列碰撞（第五处，独立实测）**：`followup_readme_bridge._letter_rows` 用 `locations[number] = row` 建索引。补件行若复用父信编号 `财务部#15`：**信行数 55、locations 键数 54 ⇒ 静默覆盖 1 条**。⇒ 补件若进主表，编号列**必须**独立且唯一，而这恰恰与「补件不占号」的纪律直接冲突。

**⇒ 结论：「补件放回主表 ＋ 各处加过滤」需要在 4 处加排除、1 处保证编号唯一，共 5 个必须记得的点，每一个漏掉都不产生任何信号。** 这正是本项目反复记录的那一族缺陷。

### 1.3 反事实 B：补件登记改为 README 内的第二张表

| 消费者 | 基线 | 加了第二张表之后 |
|---|---|---|
| `iter_rows` 数据行数 | 54 | **54**（表头单元格逐字相同） |
| 闸查询（唐燕萍） | ✅ 开 / `财务部#15` / 下一个可用号 `财务部#16` | **完全一致** |
| 入信桥信行数 | 54 | **54** |
| 起草缺口（唐燕萍） | 15 条，最新 `2026-08-23` | **完全一致** |

**⇒ 四处消费者零改动、零过滤、零漂移。** 免疫来自「它们读不到那张表」，不是来自「它们记得跳过补件」。

⚠️ **但这份免疫今天是靠运气拿到的** —— 见 §〇⑶。故本案**必须**同时把两份解析改成显式选表，否则等于把一颗雷从「会响」改成「暂时不会响」。

## 二、方案（三选一，已定案 → **案 C**，理由如下）

| | **案 A：留列表项，两端各加一套列表解析** | **案 B：放回主表 ＋ 各处加排除过滤** | **案 C：README 内独立第二张表 ＋ 显式选表** |
|---|---|---|---|
| 补件定位判据 | 需新写列表项解析＋写回（第 3、第 4 份 README 解析实现） | 复用现有 | 复用现有 `_split_row`/`write_status`，只多一个「选哪张表」的入参 |
| 需要改的下游 | 批准、班次、delivery 各加双形态分支 | **4 处加排除 ＋ 1 处保编号唯一** | 批准、班次各加一个 `--table` 入参 |
| 漏一处的后果 | 补件半通半不通 | **闸锁死／回件配错／缺口被掩盖，全部无信号** | 编译期就传不进去，漏不了 |
| 状态词汇 | 另起一套（列表项自由文本） | 与正式信共用（含不适用的闭环四态） | 与正式信共用词汇，**但闭环语义单列**（决策点 5） |
| 与「补件不占闸」 | 成立（靠不在表里） | **须靠过滤维持**，随时可能被下一个人改回去 | **成立且结构性**（不在那张表里） |
| 与「补件不占号」 | 成立 | **冲突**（须给唯一编号才不撞键） | 成立（第二张表首列叫「承接编号」，不是「编号」） |
| 新增解析实现 | **+2** | 0 | 0 |
| 退休既有守卫 | 无 | 无 | **退休隐式文档顺序判据（两处）** |

**✅ 定案：案 C。** 判据是本项目已成文的那条：**能让错误产生信号的，优先于要靠人记得的。** 案 B 的 5 个排除点全部属于「漏了不报错」；案 A 把 README 解析实现从 2 份变成 4 份，与「一份拆成两份、下游只跟一份」是同一族病的加重版。

🔴 **案 C 有一处必须讲清、免得被当成万灵药**：**它把「补件不占闸」从一条纪律变成一个结构事实，但代价是 README 里从此有两张长得很像的表。** 缓解＝表头首列刻意取不同名（主表 `编号` / 补件表 `承接编号`），且决策点 3 的断言会在两表次序颠倒时 fail-loud。

## 三、决策点（🔴 **本节六项全部无默认项**）

> **为什么无默认**：按根 CLAUDE.md §5「默认项两个前提」自检——**第 ① 问「若他不答，谁去执行？」答不出执行者**：提出方是无人在场的无头批处理会话，收工即结束，「按默认执行」实为停摆。**故一律不设默认项，全部登记 §四 待签认。**

### 决策点 1 —— 补件的载体形态（本包地基，其余五项都依赖它）

- **(a) 案 C**：README 内独立第二张表《补件登记》，与主表同列结构、首列改名「承接编号」。**代价**：README 多一张表；须一次性把现存 3 条补件从列表项转成表行（内容不改写）。**收益**：四处消费者结构性免疫、零过滤、退休两处隐式顺序判据。
- **(b) 案 A**：维持列表项，为它写一套独立的列表解析与写回。**代价**：README 解析实现 2 → 4 份。
- **(c) 案 B**：放回主表加排除过滤。**代价**：5 个「漏了不报错」的必守点，且与「补件不占号」直接冲突。
- **建议：(a)。** 理由见 §二。

### 决策点 2 —— 显式选表怎么选（🔴 **本项即本包「改变对外语义」之所在，§5 门槛③ 的触发点**）

`readme_table.iter_rows(text)` 现在的语义是「取文首第一个含『发送状态』的表」。三种改法：

- **(a) 新增可选入参 `section=` （按其上方最近的 `##` 标题选表），不传时**保持现状**（第一个表）。** **代价**：旧语义仍在，两处独立实现里的隐式顺序判据**只退休了一半**——不传参的调用方照旧靠运气。**收益**：零破坏性，全部既有调用方一字不改。
- **(b) 同上，但不传时**改为强制匹配主表章节标题**，匹配不到即 `raise`。** **代价**：这是**真正的对外语义变更**——若哪天 README 章节标题被改，所有消费者当天集体 fail-loud（而不是静默读错表）。须同批检查两处独立实现 ＋ 8 个消费者。**收益**：隐式顺序判据**彻底退休**，两表次序再也不能影响任何判定。
- **(c) 入参改为必填**，所有调用方显式写明读哪张表。**代价**：8 个调用点全改；`工具-跟进闸查询.py` 与编辑锁两侧同批改，改漏一处即 `TypeError`（**这恰恰是好事——漏了会当场炸，不会静默**）。**收益**：同 (b)，且「读哪张表」在每个调用点都肉眼可见。
- **建议：(b)。** (c) 更彻底但把 8 个调用点全部卷进来、且对 `工具-跟进闸查询.py` 这种「只受益、本无需改动」的消费者也强加改动；(a) 留了一半雷。(b) 在「彻底」与「改动面」之间是唯一的平衡点。
- 🔴 **不论选哪个，`工具-共享文档编辑锁.py::_followup_readme_rows` 必须同批改** —— 它是第二份独立实现，**不改它 ＝ 只修了一半，而修了的那一半会让人以为整件事已经修完了。**

### 决策点 3 —— 补件表位置断言挂在哪

隐式顺序判据退休后，仍需一道守卫防止「有人把补件表挪到前面」这件事悄悄发生：

- **(a) 单测**（`tests/test_readme_table.py` 加反例：构造补件表在前的文本，断言主表消费者 fail-loud 而非静默读错表）。**代价**：只在 CI 跑到时才拦；**而 CI 整体 run 目前长期 failure**（队列 §一 #398 ⑶ 已坐实，红的三条含凭据扫描）⇒ **新增单测的红/绿信号很可能淹没在既有的红里**。
- **(b) 编辑锁 `release` 校验**（README 目标 release 时断言两表次序与章节标题）。**代价**：编辑锁校验函数再长一截。**收益**：挂在**咽喉**上——改 README 必持锁，绕不过去。
- **(c) 落库 sweep 常驻告警**（同 `_check_claude_md_carrier_size` 范式，首月只告警不调参）。**代价**：滞后一轮才发现。
- **建议：(a) ＋ (b) 都要。** (a) 是判据本身的变异验证（**须能对退休前的原实现变红，否则是空转** —— 同 §一 #355 那条「防回归判据的初版自己红了，红得对」的教训）；(b) 是真正拦得住的那一道。**(c) 不做**——三道守同一件事是把告警做回噪音。

### 决策点 4 —— 🔴 班次扫描：纳入 or 显式人工通道化（opener 点名的二选一）

- **(a) 纳入自动班次**：`dispatch.py` 扫完主表后再扫补件表，逐行走同一条 `push_followup`。
  - **收益**：#399 的「发不出去」在 09:30 那一刻自动消失；不再需要一次性直发脚本。
  - **代价 · 须看清**：补件的触发场景恒是「**刚发生了一件需要立刻告知专员的事**」（面板修好了／此前的「不要采信」要解除）。**自动班次意味着最长要等到次日 09:30。** 2026-08-25 那封是 06:56 发的——**走班次会晚 26.5 小时**。⚠️ 更要紧的是：`财务部#14` 曾请唐燕萍「在我方通知前不要采信发票段数字」，**每多等一小时，她就多一小时不敢用那个面板**。
  - **另一处代价**：`has_unmarked_imminent_deadline` 那道「疑似漏标硬截止」判据会对补件生效。补件多为「不设交期」，理论上不触发；**未实测**。
- **(b) 显式人工通道化**：补件表不进自动班次；`push_followup_letter.py` 新增 `--table 补件` 走人工触发。班次每轮**显式打印**「补件表 N 行待发，本通道不自动发送」（🔴 **沉默不算通过** —— 这一句正是 #399 当初能藏住的原因）。
  - **收益**：与补件的时效性匹配（人在场时立刻发）；不引入「补件被自动发出去而没人看过」的风险面。
  - **代价**：仍需一个人动手；#399 只解决了「批不了」，「不会被扫到」变成**有意为之且可见**，而非缺陷。
- **(c) 纳入班次 ＋ 保留人工触发**（两条路都通，谁先谁算）。**代价**：**同一封信有两条发送路径** ⇒ 存在「人工刚发完、班次又发一遍」的重复发送窗口，须靠状态回填的原子性来防（`push_followup` 发完即回填 `✅ 已推送`，理论上第二条路会被门禁②拒——**但那是「发送成功与回填之间」的时间窗，未实测**）。
- **建议：(b)。** 补件按其定义就是「有件急事要立刻说」，把它交给次日班次是**用一个机制解掉另一个机制该有的时效**。**(a) 与 (c) 都要先答一个问题：补件晚一天发，可接受吗？** 从 `财务部#14` 那句「在我方通知前不要采信」看，答案是不。
- 🔴 **本项无论选什么，班次都必须打印一行补件表状态** —— 这一条不进选项，是三案共同的强制项。

### 决策点 5 —— 补件的「了结」怎么表示

主表有闭环四态；补件有两类：**通知型**（不用回）与**签认型**（须回，如 2026-08-25 那封的 R5 分母读法甲/乙）。

- **(a) 补件不设闭环态**：发出即终点，状态停在 `✅ 已推送`。**代价**：签认型补件在等的那个签认，**在任何机器载体上都无迹可寻**——2026-08-25 那封至今在等唐燕萍答甲/乙，**目前只写在 README 散文里**。
- **(b) 补件复用闭环四态**：签认型收到回件后转 `📥 已回件并回灌`，通知型发出即转 `✅ 无需回复`。**代价**：须回答「谁去改那一格」（同 §一 #366 M4 那条「闸永远不会自己开」的老问题，**在补件表上会原样重演**）。
- **(c) 只对签认型设闭环态**，通知型发出即终。**代价**：多一个「这封是哪型」的字段要维护。
- **建议：(b)**，并把「需回复」做成补件表的一个显式列（而不是靠读散文判断）——**通知型起草时即写 `✅ 无需回复` 的预期终态**，发出后由 `push_followup` 回填时一并置终态。这样 (c) 的收益被 (b) 覆盖，不必多一个类型字段。
- ⚠️ **未闭合、如实登记**：**签认型补件的回件谁来配对？** 入信桥现在只认主表（决策点 1(a) 之后更是结构性只认主表）⇒ **唐燕萍答「甲」的那封回件，会被配到 `财务部#15`（正式信）而不是补件行。** 这是案 C 的一个真实缺口，本包**不解决**（无样本——补件回件一次都还没发生过），**但必须写明**，见 §五。

### 决策点 6 —— 审计事件前缀

2026-08-25 那次一次性直发用了 `supplement_delivered` / `supplement_group_cc_delivered` / `supplement_cc_delivered`，「与正式信四链路刻意区分前缀」。

- **(a) 沿用 `supplement_*`**：补件走正式通道后仍记这三个 action。**收益**：查「补件发过几封」一个 grep 搞定。**代价**：审计里同一件事（发一封信）有两套 action 名，查「唐燕萍收到过几封东西」须记得两边都查。
- **(b) 并回正式前缀** `followup_delivered` 等，靠 `decision` 字段里加 `kind="supplement"` 区分。**收益**：一条时间线，不漏查。**代价**：既有那 3 条 `supplement_*` 历史事件留在日志里不追改（同「历史记录不追改」），⇒ 查历史时仍须知道有过这么一段。
- **建议：(b)**。判据：**审计是用来事后复核「这个人收到过什么」的，按「用什么脚本发的」分家会让复核者必须先知道实现细节。** `kind` 字段既保留可筛性，又不分裂时间线。

## 四、#400（并入项）的处置

`采购部#18` 编号列 `采购部#18（待你审，暂不占号）` vs 状态列 `🆕 待发`。

**已有的一半**：`followup_gate.number_status_mismatch` 能检出并 warning（`UNNUMBERED_MARKERS = ("未发","待发","待你审","暂不占号","不编号")`）。
**缺的一半**：没有任何一处会去**清除**那个括注 —— 批准脚本 `write_status` 只改状态列一格。

**修法（本包并入，无独立决策点）**：`approve_followup_letter` 转态成功后，**同一次写入**里把编号列的 `UNNUMBERED_MARKERS` 括注剥掉。
- 🔴 **必须是同一次写入**，不能分两次 —— 分两次就多出一个「状态改了、括注没改」的中间态，而那正是 #400 本身。
- 🔴 **只剥括注、不改编号数值**（不做「落实占号」的号段分配）—— 占号语义归 `_next_available_number`，那是读侧派生值，写侧不该去动它。
- **变异验证要求**：把 `采购部#18` 当前的真实两格喂给新判据，**必须**产生一次修改；剥完再喂一次，**必须**幂等无修改。
