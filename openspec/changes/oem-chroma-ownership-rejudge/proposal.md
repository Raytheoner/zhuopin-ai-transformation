## Why（一段）

`#374` 要重判「OEM 隔离层 Chroma 的归属」。取证后发现真正的问题不是「主人换成谁」，而是**「Chroma 归属」从来不是一件东西，而是三层**——**L1 路由 guard（`OEMRouter`，✅ 已就绪）／L2 唯一入口（`rag.retrieve()`，❌ 未建）／L3 Chroma 本体（❌ 未接）**，三层的主人、就绪度、到期日各不相同。v6（2026-08-18）与 v8（2026-08-22）两次都把它当一件东西挂靠、当一个日期收紧或放宽，这正是这条行「默认沿用比重判更省事」的结构性根因：**一件混成的东西无法被干净地判一次。**

连带查出三处：**⑴** v6 定的 `2027-01` 硬截止，唯一算法是「留出 Q4 前置 2027-02 的余量」，而 v8 删掉了 Q4 的跨客户检索需求后**没有人回头重算**——这个数字的输入已失效；按同一算法重算，最早消费方是 **Q2 8D（场景 2026-10，前置归集 8 月初开工／9 月底完成）**，且隔离规范 §4 门禁写死「**归集时即分库，不允许"先混库后拆"**」⇒ 约束点落在 **2026-09 内**。**⇒ `#374` 行内那句「本行不阻塞任何在建场景」在 v8 之后已不成立，而它正是本行一直被判为"不急"的依据。** **⑵** v6 判词「若 Chroma 停摆，QD-B 那条 IATF 红线就变成写了但底层没有」**在事实上不成立**——QD-B 红线原文要的是 `OEMRouter`（L1，已就绪），不是 Chroma 本体。**⑶** L1 现状有三个可独立收口的缺口（唯一入口未建／默认构造不写审计与隔离规范 §3.2 直接冲突／通用库写入侧校验不存在而读取侧无条件放行），此前被「Chroma 未就绪」整体遮蔽。

### 本次退休哪一个既有守卫（协议〇.9 措施 B）

**退休两条：**
1. 🔴 **退休孤立日期 `2027-01` 本身。** 它是一个**手工反推、无算法留痕、且输入变更后无人重算**的日期常量——v8 改 Q4 之后它已悬空 14 天无人发现，本次是第一次有人回头算。改为**「到期日 ＝ 第一个需检索 OEM 数据的场景的前置开工日」这条可机械重算的规则**（写进 spec）⇒ 以后任何一次场景重排都能自动重算，**不再依赖某个人记得回头算**。这是"用规则换常量"，是净退休。
2. **退休「Chroma 归属」这个混合概念**在权威载体中的单一表述，改为按 L1/L2/L3 三层分别表述。混合概念本身就是一个失效的守卫——它让「隔离层就绪」这句话在四份权威件里指向三个不同的东西。

**不能退的**：隔离规范 §3.3「唯一入口不可绕过」不得退（§5.2 条件① 是单实例方案的全部安全性所在）；§3.1 fail-closed 不得退。

### 伴生文件的 .gitignore 覆盖（队列 #328 子项②）

**不适用**：本变更包**不新增任何自动生成的文件名形态**——交付物为文档改字（既有 `.md`）、spec 文本、以及（若 D2 采纳）`OEMRouter` 构造签名变更。不产生锁文件、快照、状态文件、日志或重命名退路产物。若后续 L2/L3 实施泳道引入 Chroma 持久化目录或索引文件，**须在该泳道的变更包内单独回答本问**，不由本包代答。

## What Changes

1. **口径**：把「OEM 隔离层 Chroma 归属」拆为 L1/L2/L3 三层，各自绑定消费方与到期日规则（不再是一个孤立日期）。
2. **挂靠点重判**：Q4 PPAP 降为**存储侧**合规身份（不再支撑 L2/L3 到期日）；QD-B 红线明确挂 **L1**（已就绪，改述为"不得下线"）；**L2/L3 的主人改为新 Q2 8D**，条件为 **D1**（Q2 生产判定是否需检索历史 8D 语料）。
3. **spec 变更**（`platform-oem-isolation`）：新增「到期日重算规则」「唯一入口不可绕过」「通用库写入侧校验」「运维面隔离（备份/导出/日志）」四条 Requirement；**修改**「跨 OEM 访问拒绝前写审计」一条（D2 裁决后定稿）。
4. **载体改字**：全景规划（§加速启动总览 Chroma 归属条／§8 战略决策清单／Q4 两处日期复述）、`3-治理与合规/OEM数据隔离规范.md`（§4 Q4 行／§4 Q2 行／§5 映射表／新增 §7）、`跨场景前置数据与知识库任务总表.md`（Q4 行／§三.4／Q2 行）——**逐条拟改文本见结论件 §八，本包 tasks 承接、design 审过后执行**。
5. **一处标准更正**：不再以 **ISO 26262** 作为 OEM 隔离的合规依据（26262 管功能安全，不管客户数据保密；本项依据 ＝ 客户 NDA ＋ IATF 16949 §7.5.3 ＋ §8.3，隔离规范 §1 原文如此）。

## Non-Goals

- 不改 OEM 隔离**边界**本身（哪些数据要隔离、哪些不隔离，`5-平台底座/CLAUDE.md` L17-18 与根 `CLAUDE.md` §7 红线 3 一字不动）。
- 不裁决 Q2 场景本身的排期、范围或自动化等级（那是质量线与 88-B 已闭环的地盘）。
- 不部署 `.51`、不触碰生产服务。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

**⑴ 本流程哪些判断是人脑默会经验？**
- **规则**：「一个跨域基础设施的到期日，应取所有消费方中最早的那个前置开工日，减余量」——v6 用过这条规则但**从未把它写下来**，因此 v8 改了输入后无人重算。
- **阈值**：「余量取多少」（v6 取约 1 个月：Q4 前置 2027-02 → 截止 2027-01）。
- **例外**：「消费方只需要存储侧隔离、不需要检索侧隔离时，它不计入到期日推算」——这正是 Q4 在 v8 后的形态，此前无人显式表述过。
- **尺度**：「合规基础设施的'有主人'与'有到期日'是两件事」——L1 有主人（QD-B 红线）但无到期日；L2/L3 的到期日只能来自有排期的消费方。

**⑵ 由谁显性化？（持有人 + backup，实名）**
- 持有人：**Shao Peishen**（口径与排期裁决人，本包 design 审）
- backup：**孙涛**（根 `CLAUDE.md` §5 决策代理条：可代 design 审查；🔴 但「合规红线变更」不可代 ⇒ **D2 若走"收紧"方向，不在代理范围内，须 Shao Peishen 本人**）
- 技术事实持有人：平台底座线（L1/L2/L3 就绪度）；Q2 设计侧（D1）

**⑶ 用什么方法提取？**
**历史案例反推**（本次即是：从 v6 判词与 v8 差异清单反推出那条从未写下的到期日算法），产出物 = spec 里的「到期日重算规则」Requirement。**不用 AI起草·专家批改**——本项的默会经验持有人只有一位且已在审位上。

**价值指标**：
- **风险型（主）**：消除一条「沿用现归属 → 2026-10 撞门 → 为不误场景而'先混库后拆'」的不可逆合规路径。基线 = 隔离规范 §4 Q2 行门禁「不允许先混库后拆」；达成判据 = Q2 归集实际按客户分库、有落盘证据。
- **风险型（副）**：L1 三个缺口由"被遮蔽"转为"已登记且各有承接"。基线 = 隔离规范 §5 映射表现状列（三项 ❌/⚠️）；达成判据 = 三项各有 openspec tasks 行或队列行。
- **质量型**：权威件中「隔离层就绪」一词的指代由 3 种收敛为 1 种（按层显式）。基线 = 本次 grep 到的 4 份权威件表述不一致；达成判据 = grep 零残差。
