## Goals / Non-Goals

**Goals**（设计层，不复述 proposal 的范围）：

- 取数、指标、组装、确认、交付**五层解耦**，使口径变更（必然会发生，O-1/O-4 未定）只落在指标层，不牵动取数与交付。
- 指标层为纯函数，**周报可复算**——这是价值指标「口径一致性」能被证明的前提。
- 路由与鉴权自首版即按目标态书写，**网关落地时只改映射**。

**Non-Goals**：

- 不做统一门户网关本体（D11/D12，独立机制类包）。
- 不做自然语言查询（D3）、不推管理层（D8）、不接质检与物流（D1）。
- **不追求首版指标口径正确**——首版的作用是给姚祖怡一个可批改的实物（D5）；口径正确性由判例包收敛，不由建造方预判。

### 🔴 二之零、apply 阶段的实测修正（2026-08-18，D15/D16 已被推翻并重定）

> **本节是本 design 最重要的一段**：D15 与 D16 都建立在两个我在 propose 阶段**读封装而没读端点**得出的判断上，apply 时一接真实接口即被证伪。原文保留在下方（不删），修正版为 **D15-R / D16-R**。

| 原判断 | 实测结果（2026-08-18） | 
|---|---|
| SRM 看板支持日期区间，是收货侧唯一结构匹配的源 | 🔴 **SRM 看板返回 `300234: 供应计划看板不允许查询当前时间 7 天之前的数据`**——它只能查**未来**区间。周报要的「上周」「四周前」两个历史窗口**结构性取不到**，SRM 在本场景路径上完全不可用 |
| `GR/Query` 只能按 `docNo` 单查，按周取数请求数不可控 | ✅ **错**。该端点支持**无过滤分页整表拉取**（27,785 行、服务端硬顶 500/页 ⇒ 56 次请求），每行自带 `BusinessDate`（真实入库过账日）、`RcvQtyTU`、`SrcDocNo/SrcDocLineNo`。我把底座封装 `get_gr_lines(doc_no)` 的形状当成了端点本身的能力——**读封装不等于读端点** |
| `ZpViewPurOrder` 无制单日可用，下单日只能用交期近似 | ✅ **错**。原始行有 `makeDate`（28,274/28,274 非空），还有 `finallyPriceTC`（价格）与 `makeEmpName`（采购员）——**金额与采购员维度本来就可算**，是我先前误判为不可算 |
| （未预见） | 🔴 **`ZpViewPurOrder` 完全没有交期字段**：`deliveryDate`/`DeliveryDate`/`expectDate`/`planDate`/`demandDate`/`arrivalDate` 六个候选名在 28,274 行中**全部 0 命中** ⇒ 底座的 `expected_date` 与 `supplier_confirmed_date` 实际恒等于制单日 ⇒ **收货准时率算不出来**（见 O-6） |

#### D15-R · 订单侧与收货侧**同属 ERP，单源双端点**；SRM 退出周报路径

**决策**：订单侧 `ZpViewPurOrder/Query`，收货侧 `GR/Query`（整表分页 + 客户端按 `BusinessDate` 落窗口）。**SRM 不参与周报取数。**

**为什么比原 D15 好，而不只是"退而求其次"**：口径反而更硬——「**ERP 已入库过账**」是公司账上的事实，比「供应商在 SRM 上自报的答交」更接近采购经理关心的东西；且原 D15 那条必须一路带到周报上的口径警告（SRM 答交 ≠ ERP 入库）**随之消失**。**代价**：SRM 侧的「供应商承诺 vs 实际」对比在首版没有了，留待 O-6 一并评估。

**⇒ 数据源边界由「ERP + SRM 双源」收敛为「ERP 单源」**，spec `sc2-feed-source` 已同批修正。这是对 grill D1 的**实质性改动**，须请你追认（见「需追认」①）。

#### D16-R · 「上月环比」仍取 W-4 同期周，但**理由已换**

原 D16 的理由（SRM 60 天跨度上限）随 SRM 退出而失效。**结论不变，但现在的理由是**：三窗口同为「一个自然周」，量纲可直接比较；取整月则须除以周数换算，多引入一层口径，而那层口径本身又要问姚祖怡。**这条决策现在完全建立在口径可比性上，与任何接口限制无关。**

#### D21 · 页面走快照优先，全量重算是显式动作

**决策**：网页请求一律渲染当期快照；重算走独立的 `POST /api/refresh`。

**为什么**：实测一次全量真实取数**约 2 分 19 秒**（`GR/Query` 56 次分页 ＋ 窗口内 812 个料号逐个查行级关闭状态，后者无缓存）。把两分钟挂在 HTTP 请求上，用户会以为服务挂了。此外发布收口冒烟本就要求「一次全量重算」是个可触发的动作，二者正好同一个端点。

#### D15 · 收货与交付侧走 SRM 看板，订单侧走 ERP —— **不逐单调 `GR/Query`**

**决策**：周报中「本周收货／交付及时」类指标取自 SRM `get_receive_board`／`get_delivery_orders`（支持日期区间）；「本周下单／在途」类取自 ERP `get_purchase_orders`（按 `makeDate` 客户端切窗）。**`GR/Query` 首版不用于周窗口取数。**

**为什么**：`ZpViewPurOrder` 行内无收货日期、只有累计收货量，**订单侧结构上给不出「本周收到多少」**；而 `GR/Query` 只能 `docNo` 单查——按周取数意味着对该窗口内每张单各发一次请求，请求数随业务量线性增长且无缓存，周报生成时长不可控。SRM 看板天然按日期区间返回，是唯一结构匹配的源。

**代价（如实登记）**：收货口径变成「**供应商在 SRM 上的答交/到货记录**」而非「**ERP 已入库过账**」，两者可能有时间差与口径差。**这一差异必须在周报上显式标注**，并列为判例包 O-1 的一个具体判例问姚祖怡——**这恰好是 D5「拿实物去问」的正例**：抽象地问「收货口径怎么定」他答不了，拿着两个数字差问「这周该按哪个算」他一眼能判。

**备选方案**：(i) 逐单调 `GR/Query`——请求数不可控，且未验证其是否支持批量，否决；(ii) 只报订单侧、不报收货——周报少掉一半价值，否决。

#### D16 · 「上月环比」窗口定义 ＝ **4 周前的同一自然周**，非上月整月

**决策**：三窗口＝本周（W）、上周（W-1）、**四周前同一自然周（W-4）**。

**为什么**：SRM 单次查询跨度硬上限 60 天。若「上月环比」取上月整月，则最早边界到 W-9 左右，合计跨度逼近或超过 60 天，必须拆多次查询且触发 30 秒限流窗口。取 W-4 后合计跨度约 35 天，**一次查询覆盖全部三窗口**，且三窗口同为「一个自然周」、量纲可直接比较（整月 vs 单周需除以周数换算，反而引入一层口径）。

**代价**：W-4 若恰逢长假或月末冲量，环比会失真。**已列为判例包 O-1 的一条判例**——但**不因此改设计**：失真是业务真实波动，标注比换算更诚实。

#### D17 · 在途/未清行的判定必须用 `get_purchase_line_status`，不用数量启发式

**决策**：凡涉「在途」「未清」的指标，MUST 先调 `get_purchase_line_status(item_codes)` 取行级 `LineStatus`（0 开立／1 审核中／2 已审核未交清／3 自然关闭／4 短缺关闭／5 超额关闭），**剔除 3/4/5 三类已关闭行**后再计算。

**为什么**：`qty_received` vs `qty_ordered` 的纯数量启发式，会把**短缺关闭**（收货量长期小于订单量）误判为 `partial`、把**超额关闭**误判异常——SC8 队列 #173 已真实踩过并根治，本场景直接继承结论，不重犯。

**代价**：`get_purchase_line_status` 按料号逐个分页查询（服务端不支持多料号一次查全），料号数多时请求数上升。**缓解**：仅对本窗口内实际出现的料号集合调用，且首版接受该开销；若实测过慢，转为在指标层限定「在途」类指标只覆盖 TOP-N 料号并显式标注。

#### D18 · 分层结构

```
sc2/
  sources.py     取数层：ERP+SRM 双源 → 冻结数据集（含 F14 参数名对照、real fail-loud）
  windows.py     窗口层：基准日期 → (W, W-1, W-4) 三窗口，纯函数、不读当前时刻
  metrics.py     指标层：冻结数据集 + 窗口 → 指标集（纯函数、不触网、不写盘）
  report.py      组装层：指标集 → 周报模型 + 快照读写（reports/ 下）
  review.py      确认层：待确认/已确认状态机 + audit 写入 + 持久化
  webapp.py      交付层：Flask 蓝图（前缀 /procurement/sc2）+ gate + access_log
  notify.py      推送层：企微（采购部群 + 姚祖怡）
```

**为什么这样切**：唯一会被判例包反复改动的是 `metrics.py`（O-1/O-4 全落在它上面）。把它做成不触网、不读时钟、不写盘的纯函数，**口径改一次的成本 ＝ 改一个函数 + 改一组单测**，不牵动其余六层。`windows.py` 单独切出来是因为 D16 那条窗口定义本身也可能被改判。

**备选**：单文件实现——首版更快，但第一次口径批改就会让取数与指标纠缠在一起，否决。

#### D19 · mock → real 在同包内切换的做法

`sources.py` 提供 `mock` / `real` 两种数据源实现，同一接口；`real` 严格 fail-loud（spec `sc2-feed-source` 已定）。**先以 mock 跑通全链路与全部单测，再切 real 做真实数据验证**——红线「先 mock 再真实」由**执行顺序**满足，而非由拆包满足（D4）。真实验证产出的黄金基准落 `reports/`（已 gitignore），不入库。

#### D20 · F14 参数名对照测试的落法

首碰 `ZpViewPurOrder/Query`（本仓库已在用，但本场景首次以周窗口口径消费）与任一新端点时，**对照测试作为一次性取证脚本执行并把结论写入场景 CLAUDE.md**，不作为常驻单测（它需要真实网络，进不了 CI）。结论二选一：过滤可信 ／ 过滤不可信须二次过滤（spec `sc2-feed-source` 已定两种分支行为）。

## Risks / Trade-offs

- **[收货口径 SRM vs ERP 存在真实差异]** → 周报显式标注数据源与口径，并作为 O-1 的具体判例交姚祖怡判定；**不自行选定一个口径当作正确**。
- **[首版指标全量呈现可能让周报过长、专员抓不住重点]** → 异常项标记＋按域分组呈现；且这是 D5 的刻意取舍——**宁可他说「这几个删掉」，也不要他看不见被我们预先删掉的那些**。
- **[`get_purchase_line_status` 逐料号查询可能慢]** → 见 D17 缓解；首版接受，实测后再调。
- **[SRM 30 秒限流与 90 秒缓存]** → 周报为低频生成（周级），限流风险低；但**开发调试期极易触发**，调试须走 mock，real 验证集中一次跑完。
- **[过渡期第 5 个端口]** → 显式豁免已获认可；**风险不在技术而在遗忘**——注销条件（网关落地后收编）已写进 spec `sc2-report-delivery` 与场景 CLAUDE.md 留痕项，使其不会静默长期化。
- **[价值指标基线未证实]** → 3 人天/月 尚待 O-2 核实；**在核实前不得对外把该数字当作已证实成果引用**（proposal 已写死）。
