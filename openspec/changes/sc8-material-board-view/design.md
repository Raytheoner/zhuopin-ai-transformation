# 设计 · 物料看板视图（队列 #334）

## Context

动机与需求原文见 `proposal.md`。这里只写约束现状：

- 现有保供看板是**成品行粒度**（`BaoguanRow`），每行的 `component_status` 里挂着该成品的 BOM 缺口物料清单，物料相关的八个字段（料号/品名/状态/未交量/现货/缺口/答交批次/替代料角色）已经算好了。**物料看板要的绝大部分数据，已经在快照里，只是被"按成品切"了。**
- 快照重算一次约 **15 分钟**（携客云 SRM 1 req/30s 限流是瓶颈，180→365 天窗口后更长）。因此物料看板**绝不能**触发独立取数，只能派生。
- `.51:8091` 上跑的是 `BaoguanWebServer` 计划任务（SYSTEM + AtStartup），`SC8_NET_INVENTORY=on`、`SC8_PO_TRANSIT=on` 均已生效——这是缺口数量 `gap_qty` 存在的前提。
- CLAUDE.md §5 硬约束：新场景/新视图不得新起端口。

**2026-08-19 真实探测已坐实的三件事**（生产凭据只读，非推断——SC2 2026-08-18「读封装 ≠ 读端点」教训的直接应用）：

| 探测 | 结果 |
|---|---|
| 携客云 OpenAPI 是否有「请购需求池-采购订单协同」端点 | 8 个候选路径**全部 HTTP 404**，与故意乱写的对照路径返回完全相同的 404；同批对照组 `/receiveBoard/queryList.json` 返回 200 带数据 ⇒ 探测方法有效，**该端点在 OpenAPI 上不存在或未开放** |
| 品牌字段是否在任何已通端点里 | ERP 物料档案 `ZpViewItemMaster`（13,818 行，10 个字段）**无品牌**、`spec` 为空；ERP `ZpViewPurOrder`（28,298 行，23 个字段）**无品牌**；SRM 供应计划看板 `prodFeature`／`productFeature` 921 条**全为 null** |
| ERP `makeEmpName` 能否充当「负责采购」 | **证伪**。用姚祖怡自己截图里的 `R01B.0115` 反查：SRM 页负责采购＝沈潇敏，而该料 7 张未交 PO 的制单人是尤胤栋(4)／沈潇敏(2)／汤易水(1) |
| ERP `supplyName` 能否充当「供应商」 | **可用代理**。同一 `R01B.0115` 未交 PO 供应商 6/7 为 `ZA0114 厦门信和达电子有限公司`，与他截图红框内的值一致；`R01B.0105` 未交 PO 44 张全为 `上海森和创电气有限公司`，与 SRM 供应计划看板 `innerVendorName` 亦一致 |
| 品名 | ERP `itemName` ＝ `RPK-50V471MI5D#Q-F52`，**与他给的样例行逐字一致** |

## Goals / Non-Goals

**Goals**
- 物料看板是**同一份快照的第二种切法**——单一可信源，一次计算两处消费。
- 三个月窗口**随快照日期滚动**，不写死月份（他写的 8/9/10 是回件当月的实例，不是常量）。
- 取不到的列**看得见是取不到**，不用近似字段顶替（IATF：假数比没数更贵）。

**Non-Goals**
- 不改任何既有判定口径。**齐料日期已知缺陷（#344）不在本范围**——判例包已作为采购部#16 发出等回件，本视图若展示相关数据沿用现状口径并在页面标注「该口径正在确认中」。
- 不做全量物料台账（只覆盖有缺口的物料）。
- 不碰携客云 SRM 的请求量（本变更新增的取数全部走 ERP 已缓存端点）。
- 不做服务端 Excel 生成（见 D8）。

### D1（默认执行）派生位置＝`compute_snapshot` 末尾一步，结果落进 `Snapshot.materials`
新增纯函数 `sc8/material_board.py::build_material_board(rows, *, today, commitments, supply_by_material)`，在 `compute_snapshot` 算完 `rows` 之后调用一次，结果存入 `Snapshot` 新增字段 `materials: list[dict]`（带缺省 `[]`）。

- **为什么不在前端 JS 里聚合**：聚合口径（月份归属、累计截断、状态分歧）是**业务判据**，放前端等于把判据写两遍（同 #308 要根治的「第二实现」）；且导出与页面必须同源。
- **为什么不在路由里现算**：路由每次请求都算一遍，且拿不到 `material_commitments`（那是 `compute_snapshot` 局部变量）。
- **向后兼容**：`Snapshot(**raw)` 反序列化旧缓存时缺该键 → 取缺省 `[]`，页面显示空态而非报错；下一次重算即填满。

### D2（默认执行）三个月窗口＝以快照 `today` 所在月为首的连续三个自然月，列标题显示真实月份
`2026-08-19` 的快照 → 列为「8月/9月/10月/8-10月合计」；跨到 9 月自动变「9月/10月/11月」。

- **备选（未采纳）**：固定 8/9/10。他写的是「8月/9月/10月」，但他是在 8 月写的，且第 4 列写作「8-10月总缺口＝三者相加」——是相对表述而非常量。写死会在 9 月产生一张永远指着过去的表。
- **窗口外缺口**：不计入任何列，页面写明窗口范围（否则「合计」会被误读为「该物料全部缺口」）。

### D3（默认执行）答交明细取**物料级**承诺全量，按物料三月合计缺口累计
**不复用行级 `cst[].cb`**——那是按**单个成品行的毛需求**累计截断出来的，多行取并集会既重复又缺漏。改为直接消费 `material_commitments`（`{料号: [(日期,数量),...]}` 全量），按物料的三月合计缺口重新跑一次既有的 `_cumulative_confirmed_batches`。

- 这样物料看板与成品卡片在同一物料上的答交列**可能显示不同的批次条数**——这是**正确的**（累计目标不同：一个是这张单要的量，一个是三个月要的总量），但会被误读为矛盾，故页面须写明累计口径。⇒ 归入 D7 的标注范围。

### D8（默认执行）Excel 导出沿用既有前端零依赖 `.xls` Blob
现有看板已上线同款导出（`_HTML_JS` 里的 `xlsx` 按钮，HTML-table + `application/vnd.ms-excel` Blob），姚祖怡已在用。
- **备选（未采纳）** 服务端 `openpyxl` 生成真 `.xlsx`：能力更强（列宽/冻结行/数字格式），但要新增依赖、新增一条会落盘的服务端路径，且与既有导出体验不一致。**先与既有一致，有具体不满足再升级。**

### D9（默认执行）路由挂现服务：页面 `GET /materials`，数据 `GET /api/materials`
`/api/materials` 直接吐 `Snapshot.materials`，与 `/api/baoguan` 同一门禁、同一进程、同一端口 8091。导航栏加一个入口。**不新起端口**（CLAUDE.md §5 硬约束）；SC2 那次的教训（部署当天才发现健康检查被门禁挡在外面）在此不适用——本视图复用既有服务，`/api/ping` 豁免已在位。

### D10（默认执行）状态列：物料级四态；不一致时如实标示分歧
四态取自既有 `ComponentSupplyStatus.status`。同一物料的状态在各成品行下**理论上应一致**（它派生自物料级的未交 PO 与物料级答交记录，与成品无关），但这是推断而非验证——**apply 阶段须用真实全量快照实测**：若全部一致则直接取；若发现不一致，按 spec 要求显式标示分歧，并把该现象单独登记为一行待查，不顺手改既有判定（同 #266 建造时对 `F02N.0224` 的处置——那次正确地单独立了 #344）。

### D11（默认执行）替代料行的处理：只计主料，替代料展示行不单独成行
`component_status` 里 `role == "substitute"` 的是**沿用主料需求量**的展示行（#297），若也聚合成物料行会**把同一份缺口数重复计一次**。故 `build_material_board` 只吃 `role != "substitute"` 的记录；替代料关系在物料行上以标注形式体现（有替代料的主料行标「含替代料」）。

## Risks / Trade-offs

- **[三列取数缺口被读作「没认真做」]** → 缺口原因、已做的探测、下一步（问 IT／问他本人）全部写在页面与随后的判例包里；且这三列的缺口是**真实的系统边界**，不是实现偷懒——探测证据可复核。
- **[月度缺口与他心算结果对不上]** → 根因多半在「窗口外缺口不计入」与「只含有缺口的物料」两条边界。apply 阶段必须做**逐物料人工对账**（至少 3 个真实物料，把各成品卡片的缺口抄出来相加，与物料看板的数字逐位比对），且把对账底稿落进 `docs/`。
- **[`Snapshot` 变大]** → 物料行数量级与料号数同阶（百级），远小于既有 `rows[].cst`；`reports/baoguan_snapshot.json` 已 gitignored，无入库风险。
- **[答交列条数与成品卡片不同被当成 bug]** → D3 已说明，D7 页面标注兜住；这是设计选择不是缺陷。
- **[快照缓存跨版本]** → 服务升级后首次读到的是**旧格式缓存**（无 `materials` 键），页面会短暂显示空态直到下一次重算。部署脚本里在冒烟阶段主动打一次 `POST /api/refresh`（既有流程本就如此），风险自然消解。

## Migration Plan

1. 合入 master（ff-only）→ `sync-to-server.ps1` 推送 `.51`。
2. 重启 `BaoguanWebServer`，**核对进程 CreationDate 真实刷新**（不只信脚本打印"已重启"——SC8 2026-07-14 教训）。
3. `POST /api/refresh` 触发一次全量重算（约 15 分钟），使快照带上 `materials`。
4. 冒烟：`/api/ping` 200 ／ `/materials` 页 200 ／ `/api/materials` 有数据 ／ 匿名访问被门禁 302 ／ **从笔记本外部**实测可达（根 CLAUDE.md 坑 5：只在 `.51` 本机冒烟 200 是假象）。
5. **回滚**：本变更是纯新增（新路由 + 新字段 + 新模块），回滚＝`git revert` 后重推重启；既有页面与判定在回滚前后均不受影响，**无数据迁移、无不可逆动作**。
