# editlock-section-append-and-followup-consistency-guard Proposal

## Why

`工具-共享文档编辑锁.py` 是跨桌任务队列.md 写入的唯一咽喉，但两类真实事故证明它还有两处结构性缺口：

1. **插入位置无保证**：人工/自动化定位"§一 末尾"时用"全文最后一个 `# 数字` 形态的行"这一启发式，而 §四 用同样的行格式——2026-08-05 单 session 内两次（#248、#254）把新行插进了错的分区，且**不报错**，只有逐行核对分区归属才能发现。
2. **决定与载体分离**：2026-08-06 01:30 UTC 真实误发——队列 #150 行明写"按串行原则暂不发、README 对应行状态维持 `🆕 待发` 不动"，但 `🆕 待发` 正是 `ZhuopinFollowupDispatchDaily` 每日批处理唯一认可的可发送标记，机制照发、信不可撤回。决定写在队列行、机制只读 README 状态列，两者从未有过一致性校验。

队列 #294 已建"⏸ 暂缓"状态本体（README 侧），但#294 明确指出"只做⑴不做⑵，仍会有人把决定写进队列却忘了改 README"——语义要闭合，必须有一层结构性校验在队列文件 release 时把关。本变更包承接 #258（已扩容并接管 #294 修法⑵，升 P2）。

## What Changes

- **新增 `append-row` 子命令**：为 `工具-共享文档编辑锁.py` 新增"追加行到指定分区"能力——调用方以结构化字段（而非预拼好的整行 Markdown 字符串）传入内容，工具负责：① 定位该分区表格的真实末行并插入 ② 按分区规则（§一 8 列／§二 4 列／§四 4 列）拼装并校验列数 ③ 检出字段内容含未转义竖线 `|` 时拒绝写入并指出具体字段（而非事后靠 #225 release 校验才发现）。
- **release 新增队列↔跟进信一致性校验**：锁定目标为默认队列文件时，`_validate_release_structure` 新增第⑥项——本次持锁窗口内新增/修改的 §一/§四 行，若状态列命中"暂不发/暂缓/压着/不发"任一字样，且该行内可提取出一个跟进信 `.md` 文件名引用（反引号包裹、与 README「主要事项」列 #241 目标文件标注同名匹配），而该文件名在 README 现有跟进信清单中对应行的「发送状态」列当前值仍是终态标记 `🆕 待发`，MUST 拒绝 release；反向（README 已是终态"✅ 已推送…"而队列行新文本仍称"暂不发/暂缓"）打印告警但不拒绝（详见 design.md 决策点 4）。
- **BREAKING**：无。`append-row` 是新增能力，不影响既有 `acquire`/`release`/`status` 三个子命令的现有调用方；新增校验⑥只在新增/修改行触发指定关键词组合时生效，不改变既有五项校验的判定结果。

## Capabilities

### New Capabilities

- `editlock-section-append-guard`：`工具-共享文档编辑锁.py` 新增 `append-row` 子命令的行为契约——结构化字段输入、按分区规则拼装、插入到该分区真实末行、列数与竖线合法性在写入前校验。
- `editlock-followup-hold-consistency-guard`：`工具-共享文档编辑锁.py` release 时对队列文件与跟进信 README 两处状态做交叉一致性校验的行为契约——队列行暂缓类结论与 README 发送状态互斥时的拦截/告警规则。

### Modified Capabilities

（无——`editlock-assertion-gate-scope` 覆盖的是既有④断言门槛的检测范围，本变更新增的是独立的第⑥项校验，不改动④的既定行为；`wecom-followup-review-state` 覆盖的是 README 自身 release 时的两态语义拦截（`_validate_followup_readme_release`），本变更新增的校验运行在队列文件 release 路径、读取 README 内容做只读交叉核对，不修改 README 文件也不改动 `_validate_followup_readme_release` 的既有行为，两者是同一问题域下互补但独立的两条校验路径，故不作为其 Modified 列出。）

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？** 三处：① "全文最后一个 `# 数字` 形态的行＝§一末尾"这一定位启发式本身就是错的默会经验，本变更改为显式复用已有的 `_split_live_sections`/`_table_data_rows` 结构化解析，不再靠人眼数行；② "队列行说暂缓，README 也要跟着改"这条一致性要求此前完全在人脑里，没有任何工具校验；③ "点名了某封信"如何从自由文本行判定——本变更收窄为"存在反引号包裹的 `.md` 文件名且与 README #241 目标文件标注同名"这一结构化判据，不尝试理解自然语言语义（见 design.md 决策点 3 的取舍）。
2. **由谁显性化？** 业务总线（Shao Peishen，负责决策点拍板与 design.md 审核）+ CC 建造车间（负责子命令与校验的代码实现、单测、历史兼容核对）；backup：下一位领取本行的 CC session 可凭 design.md 独立复核决策依据。
3. **用什么方法提取？** 历史真实案例反推——#248/#254 是插入位置错误的两次真实事故；2026-08-06 01:30 UTC #150 误发是决定-载体分离的真实事故（有审计与 README 回填时间戳为证）。判据设计延续 #225 已建立的"release 时结构校验、只对本次持锁期间新增/修改行生效、历史行不追溯"范式。不涉及 LLM 判断，不适用"AI 起草·专家批改"类方法。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：本变更为**跨项目治理机制**（编辑锁是全项目共用的队列写入咽喉），非独立业务场景，不适用四档"对客交付"口径；套用最接近的档位描述＝**档1 mock 验证**（design 审通过、代码与单测完成，尚未经过至少一次真实 `append-row` 调用链路 + 至少一次真实触发一致性校验拒绝 release 的端到端验证）。
- **晋下一档的条件**：晋**档2 真实数据跑通**——① 用 `append-row` 真实追加一行到 §一/§四/§二 任一分区，确认插入位置正确、列数正确；② 构造一个"状态列含暂缓字样 + 点名 README 仍为 `🆕 待发` 的信"的测试队列行，走一次真实 `release`，确认被拒绝；③ 用现存生产队列文件全部 §一/§四 行跑一次历史兼容核对（本 propose 阶段先做分析性核对，apply 阶段固化为可重复运行单测）。
- **价值指标**（风险型）：消除"分区插入错误"（基线＝#248/#254 两次真实事故）与"决定未同步到可执行状态、机制误发"（基线＝2026-08-06 01:30 UTC 一次真实误发，信不可撤回）两类失效；目标＝两类失效各自的检测覆盖率在本变更范围内（结构化引用可判定的场景）达到 100%，对无法结构化判定的场景（如信件引用是纯自然语言描述、无反引号文件名）如实不覆盖，不假装能覆盖。
- **LLM 判据黄金集**：不适用（本变更不含 LLM 运行时判断，纯字符串/结构化字段匹配逻辑）。

## Impact

- 受影响代码：`0-学习与工具/工具-共享文档编辑锁.py`（新增 `cmd_append_row` 及其解析/拼装/校验辅助函数；`_validate_release_structure` 新增第⑥项校验）。
- 受影响测试：`0-学习与工具/test_工具-共享文档编辑锁.py`。
- 受影响文档：本变更包归档后，`工具-共享文档编辑锁.py` 文件头部说明段需补充本次两项加固的背景（沿用文件既有"头部记录设计决策历史"惯例）；`1-转型规划/0-全景路线图/专线opener模板库.md` 需补充 `append-row` 用法说明（若决策点 1 采用结构化字段调用形式）；根 `CLAUDE.md` 队列 #258/#294 行回填。
- 红线核对：mock 先行——不适用（无新数据源接入）；audit 留痕——不适用（纯字符串/结构化匹配逻辑修法，不涉及新增 audit 事件）；OEM 隔离——不适用；L2 人工确认门禁——不适用（编辑锁是内部机制工具，本身不触发对客/采购金额相关自动执行，但其守护的正是"避免机制误发对外通知"这一间接合规风险）；ISO 26262——不适用（非车规安全相关代码）。
