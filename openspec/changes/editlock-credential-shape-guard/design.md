## 决策点 ①：判据范围取多大（🔴 本项**无默认**，须你明确答复）

`工具-密钥扫描lint.py` 里其实有**两族**判据，而它对 `.md` 文件**只用了第一族**：

| 族 | 内容 | lint 本体对 `.md` 的处理 |
|---|---|---|
| 结构化 `CREDENTIAL_PATTERNS` | AWS Access Key（`AKIA…`）／私钥文件头（`-----BEGIN … PRIVATE KEY-----`）／Anthropic API Key（`sk-ant-…`）／企微 webhook 真实 key 参数（`qyapi.weixin.qq.com/...?key=<hex>`） | **生效** |
| 通用启发式 `GENERIC_ASSIGNMENT_RE` | `XXX_SECRET`／`XXX_KEY`／`XXX_TOKEN`／`XXX_PASSWORD` ＝ 带引号字符串字面量，且右值不是占位符、不是纯大写标识符、长度 ≥8 | **不生效**（只对代码/配置类扩展名生效） |

lint 排除 `.md` 的**原文理由**：「本仓库文档大量以『环境变量 `XKY_APP_KEY=<value>`』这类叙述句提及变量名，与真实赋值在文本形状上无法用正则可靠区分」。

| 选项 | 差异 | 代价 |
|---|---|---|
| **(a) 只取结构化四条** | 与 lint 对 `.md` 的既有口径**逐字一致**，不产生任何新的范围判断 | **漏网面明确存在**：`WECOM_WEBHOOK_SECRET = "真实值"` 这种写法粘进队列格**不会被拦**——而队列行里粘一段配置片段是**真实发生过的行文习惯** |
| **(b) 结构化 ＋ 通用启发式** | 覆盖面严格大于 (a)，把「粘一段带赋值的配置片段」这条真实路径也堵上 | 引入一个**与 lint 对 `.md` 的既有决定不同的范围判断**——须论证这个不同是有依据的，而不是随手扩面 |

🔑 **起草方推荐 (b)，理由是 lint 排除 `.md` 的那条理由在写入侧不成立**：

1. **作用对象不同**：lint 扫的是**整份文档全文**（1465 个 `.md`，含大量解释性 prose）；本闸只看**本次这一次写入的那几个单元格值**。「大量叙述句造成假阳性」这个成本，在"全文扫描"里是成立的，在"单次新值"上要小得多。
2. **失败代价不对称**：lint 假阳性 ⇒ CI 全红、阻塞所有人、且是**事后**发现；本闸假阳性 ⇒ **这一次写入被拒，当场看到文案，改写后重试**，代价是一次重试。而漏网的代价两边一样：不可逆地进 git 历史。
3. **🔴 实测证据（propose 期实跑，非推断）**：对 `git ls-files` 全部 **1465 个已跟踪 `.md`** 各跑两遍——**结构化四条命中 0 处，通用启发式（含 lint 同款占位符/标识符/长度过滤）也命中 0 处**。⇒ **(b) 相对 (a) 的额外误伤面，在现网内容上实测为零**。
   - lint 自陈担心的 `XKY_APP_KEY=<value>` 这类叙述句为什么不会命中：该正则**要求右值是带匹配引号的字符串字面量**，且占位符（`<...>`）会被 `PLACEHOLDER_VALUE_RE` 滤掉——两道都不满足。
4. ⚠️ **(b) 的诚实代价**：「今天零命中」只支持「今天不误伤」，**不支持**「永远不误伤」。若日后真出现合法误伤，那时的正确动作是回到本决策点、或按决策点② 加逃生阀，**不是当场删判据**。

🔴 **本项为什么无默认**：默认项只在「不答＝停在原地」时才成立。这里两个选项的**错误方向相反**——按 (a) 落地就持续存在一个已知漏网面，按 (b) 落地就持续承担一个（实测为零但理论存在的）误伤面。**不答不会停在原地，会有一个方向持续发生**。⇒ 须你明确答 (a) 或 (b)。

## 决策点 ②：命中后给不给逃生阀

本项目既有的逃生阀范式：`WIP豁免：`／`日期豁免：`／`登记豁免：`／`opener豁免：`——都是「我知道我在越过一条规则，写明理由，理由随行进 git」。

| 选项 | 差异 | 代价 |
|---|---|---|
| **(a) 硬拒，无豁免** | 命中即拒，任何理由都不放行 | 若真出现「必须把一个**已失效的**旧 key 逐字记进队列做取证」这类需求，只能改写成非凭据形状（如中间插全角字符）或落到别处 |
| (b) 提供 `凭据豁免：<理由>` | 与既有四个豁免同形，操作者可自证 | 🔴 **逃生阀会让豁免变廉价**——`opener豁免` 的 design D5 已给过同款论证：「写一行理由的成本已经低于补一行 title 的成本，加开关只会让豁免变廉价」。而凭据这一项与 opener 不同：**豁免用错一次是不可逆的**（进了历史就只剩轮换） |

**起草方推荐 (a)**，两条理由：

1. **不存在正当理由把真凭据写进队列**——出路（落 `.env`、队列写指针）成本极低且随拒绝文案一起给出；「记一个已失效的旧 key 做取证」这种边缘需求，`#118` 的实际处置已经给了范式：**写 `<REDACTED-见§四#118>` ＋ 行号指针**，不需要逃生阀。
2. **取严的代价可逆，取松的代价不可逆**——不设逃生阀，日后真需要可以加；设了逃生阀被用错一次，凭据已进历史，而历史已裁定不清洗。

## 决策点 ③：拒绝文案回显多少命中内容

派单件要求「点名具体命中了哪条规则」。规则名必须回显，无争议。**命中串本身**回显多少是判断题。

| 选项 | 差异 | 代价 |
|---|---|---|
| (a) 一字不回显 | 只说「命中『企微 webhook 真实 key 参数』，在「状态」列」 | 假阳性时**排障困难**——操作者不知道是值里的哪一段触发的 |
| **(b) 前 8 字符 ＋ 截断标记** | 例：`命中前缀 qyapi.we…（已截断，不回显完整值）` | 8 字符对四条结构化规则都只暴露**公共前缀**（`qyapi.we`／`AKIA`＋4／`sk-ant-`＋1／`-----BEG`），不泄露密钥主体 |
| (c) 同 lint 的前 24 字符 | 与 `工具-密钥扫描lint.py` 的 `m.group(0)[:24]` 一致 | 🔴 lint 的输出落在 **CI 日志**（本就已进 git 的内容的复述）；本闸的输出落在**操作者终端**，而拒绝正是为了让这串东西**不要被传播**。24 字符对一个 32-40 位 hex key 会暴露过半 |

**起草方推荐 (b)**。⚠️ **如实标注一处不一致**：这会让本闸与 lint 的回显位数不同（8 vs 24）。这是**刻意的**，理由如上（两者输出落点的传播面不同），apply 期须在代码注释里写明，避免后人当作漂移去"对齐"。

## 决策点 ④：作用面边界

| 选项 | 差异 | 代价 |
|---|---|---|
| **(a) 只两个写入子命令，但对**全部**写入目标生效**（队列两份 ＋ 跟进信 README ＋ 任何 `--file` 目标） | 与 `#480` 触碰区一致（「`工具-共享文档编辑锁.py` 写入侧」） | `acquire`／`release --note` 通道不覆盖 |
| (b) 再加 `--note` | 覆盖面更大 | 超出 `#480` 触碰区；且 note 的落点风险面**实测低一档**（见下） |

**起草方推荐 (a)**，依据是**实测**而非推断：note 落进 `<目标文件名>.editlock` 锁文件，`git check-ignore -v` 实跑结果 `.gitignore:69:*.editlock*` ⇒ **note 不进 git**，不会重演 `#118`「已进 git 历史且不清洗」那条不可逆路径。
⚠️ **但不得据此说 note 是安全的**：note 会被 `acquire`／`status` 回显，回显内容可能被人再粘进队列行——不过**那一次粘贴本身走的是 `edit-row`／`append-row`，仍会被本闸拦下**。⇒ (a) 的覆盖是**闭合**的，不是留了个洞。若你仍要覆盖 note，请答 (b)，apply 期另立行处置。

## 决策点 ⑤：校验对象＝本次新值 还是 改动后整行

| 选项 | 差异 | 代价 |
|---|---|---|
| **(a) 只校验本次新值**（`edit-row` 的 `changed_values`；`append-row` 的各内容格） | 只对"这次写进去的东西"负责 | 若某历史行**已经**含凭据形状，本闸不会在编辑该行其它列时报出来 |
| (b) 校验改动后的整行 | 顺带体检历史行 | 🔴 **会把含凭据形状的历史行彻底锁死**——连"把它改成 REDACTED"这个动作本身都会被拒（改动后整行仍含旧内容的其它部分…甚至改到一半就拒）。这正是 `#324` 付过学费的形态：**唯一能修复它的入口把自己也关上了**，`#455` 为此专门造了 `--repair` |

**起草方推荐 (a)**，理由即 `#324`／`#454` 的既有教训，不重复付学费。
补充：(a) 的"漏网"其实由 CI `凭据扫描` 兜住——它扫全文，历史行里的凭据形状它看得见。**两道闸的分工在这里正好互补**：本闸管"别让新的进来"，CI 管"已经在里面的有没有"。
