# sweep-startup-fork-defer-to-reconcile Design

## 背景

队列 #309 子项 F 明确指出：`_push_any_unpushed_commits`（起跑段②）与 #288 新增的 `_reconcile_with_origin_and_push`（收尾段）在"发现分叉时该怎么办"这一问题上给出了两个不同答案——前者仍是旧的"整轮放弃"，后者是新的"尝试 rebase、真失败才放弃"。两者共存于同一个 `main()` 调用链里，且前者排在批次处理之前、后者排在之后，导致前者的"整轮放弃"必然生效，后者的"尝试 rebase"永远没有机会执行到——这不是两个函数之间的冲突，是同一个 `main()` 里存在一条永远不会被走到的死路径。

## 决策点：如何处理 `_push_any_unpushed_commits` 发现分叉的情形

**候选 A（采纳）：检测到分叉时不再 `SweepAbort`，记录日志后 `return`，把判定与告警职责完全移交给收尾段。**

**候选 B（否）：在起跑段就直接尝试 rebase（把 `_reconcile_with_origin_and_push` 的 rebase 逻辑提前搬到这里跑一次）。**
否决理由：此时工作区可能仍有未提交的批次改动（§二 待 commit 批次的存在本身就意味着工作区必然脏，同 #288 proposal.md 的既有论证）——在这个时间点跑 `git rebase` 需要工作区干净，会重新踩回 #288 已经踩过的坑（`_sync_master_if_behind_origin` 当初就是因为在脏工作区尝试 `git merge --ff-only` 而失败）。收尾段之所以能安全 rebase，恰恰是因为它排在"批次已提交、工作区已干净"之后——把 rebase 提前到这里等于放弃这个前提。

**候选 C（否）：保留起跑段的 `SweepAbort`，但把它排到批次处理之后（相当于在 main() 里手动调整调用顺序，而不改函数本身）。**
否决理由：即便调整调用顺序，起跑段这次检查看到的仍是"批次提交之前"的 ahead/behind 关系，判定出的"已分叉"结论会在批次提交之后过时（批次提交会让本地进一步领先），需要重新 fetch+判定一次——这正是收尾段 `_reconcile_with_origin_and_push` 已经在做的事。与其在两处维护两套"判定分叉"的逻辑，不如让起跑段这次检查只做它真正该做的事（补推"纯粹领先、可快进"的历史遗留提交），把"是否已分叉、如何对齐"这个判断完全交给收尾段一次性做完。

**结论**：采纳候选 A。`_push_any_unpushed_commits` 收窄为只负责一件事——"存在遗留的、可快进推送的历史提交时，尽早把它推上去，减少悬空窗口"；"是否已分叉、如何对齐、真无法自动解决时如何告警"完全下放给收尾段的单一职责。这与候选 C 的否决理由是同一个道理：一个判断只应该有一个权威的判定点，不应该分散在两处、用两套时机不同的 ahead/behind 快照分别做决定。

## 与 #288「决策点 2」结论的关系

#288 design.md「决策点 2」的结论是："是打破了自锁循环，还是只是让它不再阻塞批次？——两者都是，取决于是否发生真实冲突。" 本次修法不引入新的权衡，只是把这个已经拍板过的结论，应用到 `_push_any_unpushed_commits` 这第二个此前未覆盖到的分叉判定点上——使"发现分叉后先尝试自动解决、真失败才要求人工介入"这一策略在 `main()` 的两个分叉判定点上保持一致，不再是"起跑段悲观放弃、收尾段乐观尝试"的不一致状态。

## 范围边界（Non-Goals）

- 不改变 `_push_any_unpushed_commits` 处理"可快进"这条既有分支的行为——这条分支与本次修复的场景（已分叉）无关。
- 不合并 `_push_any_unpushed_commits` 与 `_reconcile_with_origin_and_push` 为一个函数——两者的职责边界（"起跑段尽早补推历史遗留"vs"批次提交后统一对齐"）在 #288 design.md「决策点 4」已有明确论证（"是两个不同的时序点，不合并、不重写"），本次不重新打开这一讨论。
- 不为"识别一个前置检查是否存在同类死路径风险"建立机械化检测——这需要理解调用图与业务语义，目前判定为超出本次修复范围，如复发第三次可能触发 CLAUDE.md §5「规则退休制」评估是否值得机制化。
