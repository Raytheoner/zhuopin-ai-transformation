## ADDED Requirements

### Requirement: 结构性拦截跟进信串行原则违规
共享文档编辑锁工具在 `release` 时，若锁定目标为跟进信 README 文件，SHALL 对本次持锁窗口内**新增**的跟进信登记行（识别方式与"结构性拦截『新建即终态』反模式"一致：该行的"非状态列身份"在 `acquire` 快照中不存在）逐一核查——取其"收信人"列值，在表格中该收信人此前最靠近的一行（"前一封"）；若该收信人历史上首次出现（无前一封），本项不适用，直接通过。若存在前一封，SHALL 判定其"发送状态"是否已闭环（值以 `📥 已回件并回灌` 开头即闭环，其余任意取值均视为非闭环）；非闭环时，MUST 拒绝 release，除非新增行内任一单元格显式包含子串 `串行豁免：`（逃生阀，放行但 SHALL 在 release 输出中打印留痕提示）。

#### Scenario: 前一封未闭环，无豁免声明，拒绝 release
- **WHEN** 持锁窗口内新增一条跟进信登记行，其收信人此前最近一行"发送状态"为 `🆕 待发`（非闭环），且新增行内无 `串行豁免：` 字样
- **THEN** release 被拒绝，提示"前一封尚未闭环……请先据实把它改为 `📥 已回件并回灌 <日期>`，或写明串行豁免理由"

#### Scenario: 前一封已闭环，正常放行
- **WHEN** 持锁窗口内新增一条跟进信登记行，其收信人此前最近一行"发送状态"为 `📥 已回件并回灌 2026-08-08`
- **THEN** release 正常放行，本项不拦截

#### Scenario: 前一封未闭环，但新增行显式声明串行豁免
- **WHEN** 持锁窗口内新增一条跟进信登记行，其收信人前一封状态为非闭环，但新增行内含 `串行豁免：业务方要求并行跟进两条独立事项`
- **THEN** release 正常放行，并在输出中打印一条留痕提示，摘录豁免理由

#### Scenario: 该收信人历史上首次出现，不受约束
- **WHEN** 持锁窗口内新增一条跟进信登记行，该收信人此前在 README 表格中从未出现过
- **THEN** release 正常放行，本项不适用（无"前一封"可比对）

#### Scenario: 既有行的状态转换不受本项约束
- **WHEN** 持锁窗口内的变化是某个已存在跟进信行（在 acquire 快照中已存在）的发送状态发生转换（如经批准脚本从 `⏳ 待你审` 转为 `🆕 待发`）
- **THEN** release 正常放行，本项不检查既有行的状态转换，只检查新增行是否违反串行原则
