## Goals / Non-Goals

**Goals：**
- §一 状态列开头获得一个所有判据都能直接读取的定长机器字段，消灭"正则猜中文"这一整族误报源头。

- 守卫代码本身获得"新增必须论证退休"的约束（措施 B），遏制 4822 行只增不减的趋势。
- 告警的"解除"与"出现"同等重要——标准长期存在状态类告警补齐解除通知；判断型告警补齐"已判定则不再重复打扰，直到状态真的变化"的能力。
- 队列文件写入侧（编辑锁）补齐两处结构性拦截缺口（F：§二 新增即终态防写；G：跟进信串行原则挪入咽喉）。

**Non-Goals：**
- **不改 §二/§四 的状态语义**——§二 继续用既有"待/✅"二元判据（F1/F2 加固，不替换其判定逻辑本身）；§四 无独立状态列，本身体量小（个位数量级），不纳入机器字段范围。
- **不在本变更内决定是否拆分双队列文件**（P4）——本变更只交付域字段这一"可逆"层，阶段 3（机械切分成两份文件）是否做、何时做，留给至少 2 周观察期后的独立判断（见「支撑论证三」）。
- **不改变任何一行状态列的自然语言正文**——机器字段只作为开头前缀新增，正文一字不改；这既是范围红线，也是本次 106 行回填能够低风险进行的前提（回填是纯前缀插入，不是内容重写）。
- **不引入 LLM 判断**——所有新增校验均为结构化字符串/状态机匹配，不调用模型推理。
- **不追求消灭子项 D 的"少数需人工介入"情形**（如真实内容冲突、真实新增未判断过的滞留包）——延续本项目 sweep 一贯的"止血不硬解"哲学（同 `sweep-ff-sync-batch-reorder` design.md 决策点 2 的既有立场）。

## Decisions

### 决策点 1：状态机器字段语法、取值集合与向后兼容降级

**语法**：§一 状态列**开头**（去除前导 `*`/空白后的第一个字符起）写入 `[S:<value>]`，与既有域字段（决策点 2）并列时顺序固定为 `[S:<value>][D:<value>]`（先状态、后域，二者之间无分隔符，各自方括号自成边界，正则可用 `^\[S:(?P<status>[a-z=0-9-]+)\](?:\[D:(?P<domain>[^\]]+)\])?`），字段之后原样跟自然语言正文（可含前导空格，不强制）。

**取值集合**（6 个，覆盖协议〇.9 措施 C 已定的三类排除 ＋ 常规四态）：

| 取值 | 语义 | 对应既有约定 |
|---|---|---|
| `done` | 已完成/已收口 | 现状"✅"开头 |
| `open` | 待领/待处理，无特殊时限或依赖 | 现状"待"开头且无其它修饰 |
| `partial` | 在办中（已认领、正在推进，未完工） | 现状"在办"类表述 |
| `hold` | 搁置/暂缓（我方主动决定暂不推进，非依赖外部） | 现状"暂缓"类表述 |
| `blocked` | 受外部阻塞（等专员签认／等 IT／等供应商数据——等人不等我们） | 协议〇.9 措施 C 排除类②，此前刻意未造判据 |
| `timed=YYYY-MM-DD` | 定时触发型，指定日期前不建议开工 | 协议〇.9 措施 C 排除类①，`[S:timed=2026-08-25]` |

`🛑`（永久关闭·仅手动唤醒，措施 C 排除类③，如 #220）**不纳入取值集合**，维持现状——它是行首独立的自然语言标记，不是状态语义的一部分（一个 `🛑` 行仍可能是 `done`/`open` 中的任一实质状态，只是"不主动催办"），机器字段与 `🛑` 标记正交，判据各自独立生效，互不覆盖。

**向后兼容降级（不得静默）**：本变更同批完成 106 行全部回填，理论上合入 master 后不存在"§一有行缺字段"的稳态。但要防的是**未来**某行绕过编辑锁咽喉产生（如仓库外定时任务/机器人直接追行，见 #305），或回填有遗漏：
- **消费者侧**：任一判据读到 §一 行状态列不匹配 `^\[S:` 前缀，MUST 不静默回退猜测，而是显式记一条"字段缺失，回退旧关键词判据"的日志/告警（沿用队列 #302/#308 反复强调的"工具静默回退"反模式教训，见根 CLAUDE.md §5"同族第三条"）——回退判据本身即为现有的关键词逻辑，不是新造一套。
- **CI 侧（`工具-队列结构lint.py`）**：本变更全量回填完成、七处消费者切换完成后，MUST 新增一项硬性检查——§一 任意数据行状态列不以 `[S:` 开头即判 lint 违规（阻断 CI），把"未来新行必须带字段"从约定升级为可执行门禁。该检查在回填与消费者切换均完成之前**不得**上线（否则会在迁移期间对存量未回填行报错）。

**被否候选**：
- **候选：字段值用中文枚举**（如 `[状态:已完成]`）→ 否决：与自然语言正文视觉上难以区分，正是要消灭的"靠肉眼/正则从中文里抠语义"问题的翻版；英文短 token 与正文有清晰的字符集边界（`[a-z=0-9-]`），扫描零歧义。
- **候选：不设 `blocked`，继续人工核定协议〇.9 排除类②** → 否决：协议〇.9 措施 C 正文已明确"改为并入 #308 的字段设计"，本变更若不做等于留一个已承诺的缺口未兑现。
- **候选：字段做成独立列而非前缀** → 否决：跨桌任务队列.md 是全项目共享的 Markdown 表格，改列结构意味着全部 7 处消费者的解析函数与既有 106 行全部要做"插列"而非"追加前缀"的更大改动，且与既有 `SECTION_COLUMN_COUNTS` 硬编码列数校验（编辑锁①）直接冲突（会被判定为"列数不对"），代价远高于前缀方案。

**默认项**：若不答，按上表 6 值集合 ＋ `[S:...]` 前缀语法 ＋ 非静默降级执行。

### 决策点 2：状态机器字段是否同批增设「域」字段（机制／业务），以及该字段的语义边界

> 本节内容与 `构建环境基建方案-CI基线与业务环境双队列-2026-08-08.md` §4.5.1 一致（该节明确要求原样搬入本 design 的 Decisions，不放 Open Questions），仅将"本决策点"措辞与本文件其余决策点编号对齐，技术结论未作任何改动。

**背景**：队列 §一 现存行 机制/环境类 : 业务场景类 ＝ **86 : 20（81%）**，2026-08-07／08-08 两天新建 机制 12 ／ 业务 0。协议〇.9 措施 C 因此设了「机制类可动 WIP 上限 8」，但其分类当前靠关键词猜（机制词数 > 业务词数），协议正文自陈"判据的已知模糊处……出现争议时以值周巡检的人工判断为准"。此外协议〇.9 措施 C 的三类排除中，②"依赖外部方"刻意未造关键词判据，协议明写"改为并入 #308 的字段设计（机器状态字段增加一个『受外部阻塞』态），落地后自动排除"（本变更已在决策点 1 用 `blocked` 值兑现）。

**⇒ 本决策点要定的不是"双队列做不做"（那是 P4 的事），而是：本次字段设计的取值集合里，是否一并容纳"域"信息。**

**推荐：是，同批增设 `[D:机]`／`[D:业]`。** 三条理由：

1. **"域"在建行那一刻就已知，从来不需要猜。** 建行的人清楚自己在建什么；当前之所以要猜，纯粹是因为建行时没被要求说。落点已现成：协议〇.10 已把"并入审核"挂在 `工具-共享文档编辑锁.py` 的 `acquire --reserve` 上，同一咽喉、同一次交互顺带要求声明域即可（`--reserve 1 --section 一 --domain 机`），与决策点 6（措施 C 的 release 超限提示）同文件同批，边际成本近零。
2. **不增设的代价是另造一套判据。** 双队列（P4）落地时若无域字段，必须另建归属判据——等于在本变更消灭一族"用正则猜中文"的同一时刻新增一族，方向相反。
3. **存量回填零额外成本**：本变更本就要回填现存 §一 全部行的状态字段（决策点 3），域字段随同一次遍历写入，不多开一轮。

回填时的域判定可以用现有关键词判据做初筛 ＋ 人工复核（复核抽样比例并入决策点 3）。🔑 **此处有一个必须写明的区分，否则与本变更的立意自相矛盾**：一次性迁移用启发式 ＋ 人工复核兜底 ＝ 可接受；长期运行的判据用启发式 ＝ 本变更要根治的病。差别在于前者有终点且有人看过，后者会在无人注意时持续产出错误答案。

**被否候选**（各附理由，避免后续重新论证）：

- **候选：域信息编进行号前缀**（如 `#M-101`／`#B-205`）→ 否决，两条硬理由：⑴ `B-` 已被 §二 批次号占用（`B-0808_xxx`），再用作业务队列前缀直接违反《专线opener模板库》§〇.2"已有专属含义的词不得表达第二种含义"；⑵ 现存 7 份解析实现与 `--reserve` 取号工具全部假定"行首＝分隔符＋纯数字＋分隔符"，加前缀要全改一遍。
- **候选：不设字段，双队列时靠"行在哪个文件里"承载域** → 否决：分文件是不可逆动作，而字段是可逆的；且行在两份文件间迁移的过程中，文件位置恰恰是最不可信的那个依据，此时字段是唯一可靠来源。分文件后字段与位置冗余，但该冗余有用——"行在业务文件里却标机制域"可一行判出，供交叉校验。
- **候选：把双队列拆分一并纳入本变更** → 否决：见「支撑论证三」，双队列应分三阶段推进且第三阶段可能不做，纳入本变更会把一个可逆改动与一个不可逆改动绑在一起。

**默认项：若不答，按"同批增设域字段 ＋ `blocked` 态"执行。**

**支撑论证一 · 跨队列引用不需要新语法，因为不该分两套编号**：双队列的原方案曾把"取号空间独立"列为收益之一。实测该项收益最小、代价最大：取号串行的真实代价是编辑锁窗口内一次毫秒级读写（迄今无任何事故记录），而两套编号空间的代价是——全部历史引用（队列内 ＋ 九份规划文档 ＋ 归档件 ＋ 根 `CLAUDE.md`）需回填或永久歧义，且 `--reserve` 的竞态防护（已修三次：#146／#163／#185）要重来一遍。⇒ 维持单一编号、只分文件时，跨队列引用写法与现状一字不差（`#205`），根本不需要发明前缀语法。另需修正一处对实况的描述：原方案称"机制任务大多是业务问题的残渣，两边必然互引"——该实况成立，但方向被描述错了。其自举三例（#22 源于业务可见性需求／#129 源于业务反馈／#282 挂业务专员通道）全是机制行指向业务出处，无一反向。⇒ 真实需求是单向溯源，不是跨命名空间寻址。

**支撑论证二 · 读取侧的真实前置比原方案所写的多一条**（并入本设计决策点 4，见下）。

**支撑论证三 · 双队列应分三阶段，且第三阶段可能不做**：

| 阶段 | 动作 | 收益 | 可逆性 |
|---|---|---|---|
| 阶段 1（＝**本变更范围**） | 加域字段 ＋ 存量回填 ＋ 建行时声明域，仍单文件 | 拿到"WIP 与注意力"这一项的绝大部分：看板与值周巡检可按域独立统计，措施 C 的分母不再靠猜 | ✅ 完全可逆 |
| 阶段 2（观察期 ≥2 周） | 域字段在真实使用中跑一段，统计争议行与改域次数 | 用可逆方式验证判据，再决定要不要做不可逆那一步 | ✅ 可逆 |
| 阶段 3（＝原 P4，视阶段 2 结果决定做不做） | 按域字段机械切分成两份文件 | 文件锁／批次流两项解耦 | 🔴 不可逆 |

⇒ 阶段 1 就能拿到四项收益里价值最高的那项，全部不可逆成本都在阶段 3。故明确保留"阶段 3 可以不做"这个出口：若阶段 2 观察下来注意力失衡已被域字段解决，不做阶段 3 也是合格结局，不是半途而废。

### 决策点 3：106 行存量回填策略

**范围**：§一 现存全部数据行（2026-08-08 计数 106＝机制 86＋业务 20，回填时以实跑 `_table_data_rows` 的行数为准，允许与本数字有小幅出入）。

**流程**：
1. 脚本对每一行跑初筛：状态维度沿用既有关键词启发式（cells[5] 开头片段含"待"→倾向 `open`，含"✅"→倾向 `done`，含"暂缓"→`hold`，能提取出明确 `YYYY-MM-DD` 且行文明示"触发日"/"启动"字样→`timed=`，能提取出"等专员/等IT/等供应商/依赖…签字"类措辞→`blocked`，其余→`partial` 作为需要人工判断的默认桶而非强行归入 `open`/`done`）；域维度沿用现行"机制词数 > 业务词数"启发式。
2. 脚本产出一份**分组预览表**（按初筛的 (S,D) 组合分组，每组列出行号＋任务列前 40 字），供人工复核——**采用批量表格复核，不是逐行 1/N 抽样**：106 行体量小，逐行过一遍的边际成本低于"抽样 X% 后仍需为遗漏的 (100-X)% 承担分类错误进入权威字段的风险"（域字段一旦落地即成为协议〇.9 措施 C 的计数依据，错误分类会直接扭曲 WIP 计数，不是无关痛痒的元数据）。
3. 复核人（Shao Peishen 或其显式委托的 CC 会话）对预览表逐组确认或改判，改判只需在预览表标注、不逐行手改源文件——脚本据最终确认表批量生成 106 处前缀插入，一次性提交。
4. 提交前跑一次"新旧判据分歧清单"（新字段 vs 现行关键词判据在 done/open 二元及机制/业务二元两个维度上的分歧行），逐条列入复核记录，不静默采用（同 `editlock-assertion-gate-scope` capability 已确立的"历史兼容核对"范式）。

**默认项**：若无进一步指示，按"批量表格 100% 过目 ＋ 分歧清单强制列出"执行，不做百分比抽样。

### 决策点 7：子项 D——告警生命周期通用化（D1 通用骨架 ＋ D2 判断型告警指纹抑制）

**D1 · 通用骨架**：`_track_and_alert_orphan_paths`（#301）已验证"出现→告警／消失→解除通知"的完整模式（`first_seen`/`last_alerted` 按 key 持久化，阈值/再提醒间隔可配置，消失且曾告警过才补发解除通知）。抽取为通用函数（签名形态：`repo_root, current_keys: dict[str, metadata], state_rel_path, threshold_hours, realert_interval_hours, render_alert(to_alert)->str, render_resolved(resolved)->str`），retrofit 到：

- **分叉告警**（#171，`_handle_fork_detected`/`_read_fork_state`/`_write_fork_state`/`_reset_fork_state`）——2026-08-08 实证：分叉已解除（`_reconcile_with_origin_and_push` 成功、`_reset_fork_state` 已执行）但此前发出的告警消息无解除通知，读者只能凭空猜测是否仍成立。retrofit 后：`_reset_fork_state` 被调用时，若重置前状态文件存在（即此前确实告警过），补发一条"✅ 分叉已解除"通知。阈值维持现状（0，检测到即告警，不设最低存续时长——分叉的严重性不适合像孤儿文件那样延后 3 小时）。
- **场景 spec 缺口告警**（#298 M1，`_announce_scenario_spec_coverage_gaps`）——现状已有 24 小时再提醒节流与按 key 的 `_read_json_state`/`_write_json_state`，但 key 从 `state` 消失时只静默 `del state[key]`，retrofit 后补发解除通知。
- **在途变更包滞留告警**（#298 M2，`_announce_stale_in_flight_changes`）——同上模式，retrofit 后补发解除通知；**但本类告警同时命中 D2（见下），解除通知不是本类的主要问题，指纹抑制才是**。

**明确不 retrofit 的类别（事件型，非标准长期存在状态型，无"解除"语义）**：
- **定时任务镜像差异告警**／**凭据拦截告警**（`_run_scheduled_task_mirror_sync` 内两条）——描述的是"本轮检测到一次差异/一次拦截事实"，不是一个持续存在、需要被"解除"的状态；下一轮若无差异/无拦截，本身就是沉默，不需要额外的"解除通知"语义。
- **部署留痕提示**（#229，`_announce_missing_deployment_trace`）——同上，描述"本批改动"这一事实，非标准状态；且已是纯提示、非阻断，队列文本上文已把它排除在措施 C 的"标准长期存在状态类告警"清单之外（原始 8 类枚举里，只有分叉/孤儿脏文件/场景spec缺口/在途包滞留 四类具备"一个状态持续存在，直到被处理才消失"的性质，其余四类是一次性事件判定）。
- **未预期异常告警**——本质是"本轮运行崩了"，不存在"解除"概念（下一轮跑通就是最好的解除信号，无需额外通知）。

**D2 · 判断型告警的指纹抑制**：现状 `STALE_CHANGE_DEFER_MARKER`（一个声明"以后长期不归档"语义的四字静态文本标记，`_change_package_has_defer_marker`；⚠️ **本节此后刻意不逐字引述该标记的字面文本本身**——逐字引述会被同一检测函数在扫描本文档（`design.md` 亦在其扫描范围内）时字面命中，导致本包被误判为"已自行声明该标记"从而被永久排除出"疑似遗忘归档"检测，2026-08-10 已实测坐实并订正措辞，详见文末"补记"）功能上等价于一次性永久白名单——一旦文档内出现该文本，此后无论完成率/滞留天数如何变化都不再告警，这正是队列正文点名的"白名单会永久失明"反模式，也是 2026-08-08 两个真实案例（`fi2-recon-mvp`/`wecom-aibot-channel`，均已被 #299 逐项判定但仍每 24 小时重复告警）暴露的缺口——注意这两个案例里**连静态白名单标记都还没补上**，问题比"标记会失明"更前一步："判定过但从未有任何机制承接这个判定结果"。

**方案**：新增一个独立的 ack 记录通道（不是扩展 `STALE_CHANGE_DEFER_MARKER` 本身的语义，二者并存、职责不同）——

- 新增 CLI：`python 0-学习与工具/工具-落库sweep.py --ack-stale-change <change-name> --note "<判定依据摘录>"`，只读当前该 change 的完成度指纹（`done`/`total`，来自既有 `_parse_tasks_completion`）与当前时间，写入 `reports/sweep-stale-change-ack.json`（`{change_name: {fingerprint: [done, total], acked_at, note}}`）。
- `_find_stale_in_flight_changes`（或其 `_announce_*` 调用方）对每个候选 hit，额外读取 ack 文件：若存在该 change 的 ack 记录**且**当前指纹（`done`/`total`）与 ack 时完全相等 → 该 hit **完全静默**（不进日志、不进 webhook，"指纹未变即静默"）；若指纹不同（意味着自 ack 后 tasks.md 又有勾选变化）→ ack 视为过期，恢复正常告警流程（含 D1 的节流/解除逻辑）。
- **仍保留 `STALE_CHANGE_DEFER_MARKER`**：二者语义不同——该静态标记是变更作者对**未来**的声明（"我知道完成率高但故意不归档，长期如此"），ack 指纹是复核者对**过去某一刻状态**的确认（"我在 X 指纹下判定过这是合理的，指纹变了要重新看"）。两者不冲突，检查顺序：先查静态 marker（存在即完全跳过，不计算指纹），marker 不存在时再查指纹 ack。

**默认项**：若不答，按上述"新增 `--ack-stale-change` CLI ＋ 指纹文件"方案执行；`fi2-recon-mvp`/`wecom-aibot-channel` 两个现存候选在本变更 apply 时**顺带**补一次 ack（复用 #299 已做过的判定依据，不重新判断），验证机制本身工作。

### 决策点 9：子项 F——编辑锁 release 新增两项结构校验（F1／F2）

**F1（仅 §二）**：新增批次行状态列（cells[3]）不得以 `✅` 开头。

- 判别"新增"：§二 无编号，identity 取批次名本身（cells[0]）——比对当前 `_table_data_rows(new_section_text)` 的 cells[0] 集合与快照 `_table_data_rows(old_section_text)` 的 cells[0] 集合，不在旧集合内即为新增（复用决策点 4 前已确立的"识别新增行"范式，与 §一/§四 现有的"编号不在 old_numbers"同构，只是 identity 换成字符串而非数字）。
- 判别"以 ✅ 开头"：复用既有 `_leading_status_segment(cells[3])`，其结果以 `✅` 起始即违规。
- **不得误拦既有行**：既有批次由 sweep 或 CC 收工改为 `✅` 是协议〇.3 的合法动作（本检查只看 identity 是否为本次新增，不看内容变化本身），历史行状态列从"待"变"✅"不受影响。

**F2（§一／§二 均适用）**：状态列含 `✅` 但不在开头片段即报——即 `"✅" in cells[status_index]` 但 `"✅" not in _leading_status_segment(cells[status_index])`。

- §一：`status_index = 5`；§二：`status_index = 3`。
- 该检测独立于决策点 1 的机器字段——即便 §一 已有 `[S:done]` 前缀，其后的自然语言正文仍可能含"✅"字样（如引用历史/描述子项完成情况），本检查捕捉的是"正文内 ✅ 出现在非开头位置、可能与开头片段实际结论不一致"这一头尾不一致的风险信号，与机器字段是否存在正交（机器字段解决"判据该读哪"，F2 解决"人写的自然语言内部前后是否打架"）。
- 覆盖场景：2026-08-03 六行"行尾写完成、开头仍待领"的真实事故。

两项均只对**本次持锁期间新增/修改的行**生效，历史行不追溯（同既有 ①-⑥ 校验的一贯范式）。

### 决策点 10：子项 G——跟进信串行原则挪入编辑锁咽喉（带逃生阀）

**落点**：`_validate_followup_readme_release`（README 文件自身 release 时的校验分支，与队列文件 release 的 `_validate_release_structure` 各自独立，互不干扰，同 #258 既有惯例）。

**逻辑**：
1. 复用既有 `_followup_row_identity`（除状态列外全部单元格）与快照比对，识别本次持锁窗口内**新增**的跟进信登记行（与 F1/F2 同一识别范式）。
2. 对每个新增行，取其"收信人"列值（列索引沿用 `_followup_readme_rows` 的动态表头定位思路，新增一个"收信人"列索引探测，与既有"发送状态"列探测同一手法：表头行按"收信人"字样定位列）。
3. 在**同一收信人值**（精确字符串匹配，不做部门/姓名拆分归一化——见「Risks」已知限制）的其它行中，取表格顺序上**排在新增行之前、最靠近**的一行，作为"前一封"。找不到（该收信人历史上第一次出现）则不受本检查约束，直接通过。
4. 判"前一封"是否已闭环：其"发送状态"值若以 `📥 已回件并回灌` 开头（日期后缀不参与匹配）即视为闭环；`⏳ 待你审`／`🆕 待发`／`⏸ 暂缓`／`✅ 已推送 …`（或任何不以 `📥 已回件并回灌` 开头的值）均视为非闭环。
5. 非闭环时，检查新增行任一单元格是否含子串 `串行豁免：`——含即放行，但仍在 release 输出中打印一条提示（"✓ 检测到串行豁免声明，已放行：<摘录>"，供留痕与后续人工审计追溯，非静默通过）；不含即拒绝 release，提示："前一封尚未闭环（当前「<收信人>」最近一封『<前一封主要事项摘录>』发送状态为『<当前值>』），请先据实把它改为 `📥 已回件并回灌 <日期>`，或在本行内写明 `串行豁免：〈理由〉`"。

**判别法复用**：与决策点 9（F1/F2）共用"identity 不在 acquire 快照 ⇒ 本次新增"这一范式，历史行不追溯——即本检查只在**新增**跟进信登记行时触发，编辑既有行（如批准脚本把状态从待审转为待发）不受影响。

**🔴 刻意不在 sweep 侧新增第 9 类告警**：本次承载性核查已坐实 sweep 现有 8 类 webhook 告警而协议正文只承载 1 项（不算本身即为讨论对象的）——本决策点是把一个此前完全靠人记的动作挪到既有编辑锁咽喉，**不新增守卫、不新增告警通道**，与决策点 5（措施 B，守卫 one-in-one-out）方向一致，本身也是一次决策点 5 精神的践行示范。

**被否候选**：
- **候选：日期解析判"前一封"**（用"日期"列排序取最新一条，而非表格顺序）→ 否决：README 表格本身是按登记顺序追加的（同队列 §一/§二 的既定惯例），表格顺序与日期顺序在绝大多数情况下一致，改用日期解析徒增一个"日期格式是否规范"的新失败面，收益有限。
- **候选：收信人做部门/姓名拆分归一化匹配**（如复用 `split_department_and_name` 的判断精神，剥离"（+团队）"等后缀）→ 否决（本次不做，非永久否决）：编辑锁一贯不 import `aibot_service` 包（跨包耦合与多 worktree editable install 劫持风险，见文件头部既有说明），若要归一化需独立重实现一份，而本项目历史上收信人措辞在同一人身上高度稳定（同"支撑论证"精神——不为尚未观察到的形态提前造判据）；一旦真实观察到因收信人措辞漂移导致误判（漏拦或错拦），再按需补一份轻量归一化规则，登记为已知限制而非阻塞项。

## Risks / Trade-offs

- **[风险] 106 行回填是一次性大批量写入，若初筛判据在某些行上系统性出错（如同一表述习惯被反复误判），复核环节可能因"看起来都差不多"而集体忽略** → 缓解：决策点 3 的分组预览表按 (S,D) 组合聚类展示，同一模式的误判会成组出现、比逐行审阅更容易被肉眼识别为"一整组都不对"；分歧清单强制列出（相对旧关键词判据）作为交叉校验。
- **[风险] 决策点 10（G）的收信人精确字符串匹配可能因措辞漂移漏拦或错拦** → 已在决策点 10「被否候选」中登记为已知限制，不阻塞本变更；真实发生时按"历史案例反推"惯例再补判据。
- **[风险] 决策点 6（措施 C）的 WIP 计数依赖决策点 2（域字段）已正确回填** → 两者在同一变更内同批交付，不存在"WIP 提示先于域字段上线"的时序风险；若拆批交付需注意此依赖。
- **[风险] 决策点 7（D2）新增的 ack 指纹机制若被滥用**（如反复 `--ack-stale-change` 而不真正处理）→ 可接受：ack 需要显式调用+摘录判定依据（同 `approve_followup_letter.py` 的 `--quote` 强制留痕范式），且每次 tasks.md 有真实变化 ack 即失效，不构成可无限续期的静默通道；与决策点 7 明确否决的"永久白名单"有本质区别。
- **[权衡] 七处消费者切换耗时较长（决策点 4 的影子模式要求真实触发周期观察），本变更验收档位因此定为"档1 mock 验证"而非更高档** → 接受，proposal.md「验收与晋档条件」已如实登记，不假装一次性切换完成。
- **[权衡] JS 第二实现（决策点 4）被接受而非消除**——本仓库 CC 会话对其零直接控制力 → 接受，已提供简化后的正则片段供 Cowork 侧手工同步，长期风险登记为后续候选（不在本变更内解决）。

## Migration Plan

1. **代码先行，字段后填**：先落地决策点 1（字段语法/降级规则）与决策点 9/10（F1/F2/G，写侧咽喉）的代码与单测，此时队列文件尚未回填，新增校验对"缺字段的存量行"不生效（只对新增/修改行生效，符合既有校验一贯范式），不会阻塞任何人当前的正常操作。
2. **106 行回填**（决策点 3）：脚本初筛 → 人工批量复核 → 一次性提交，提交本身走 §二 批次流程（协议〇.7/〇.8），不绕过编辑锁。
3. **七处消费者按决策点 4 顺序逐一切换**，每处影子模式观察一个真实触发周期后转正。
4. **`工具-队列结构lint.py` 的"未来行必须带字段"硬门禁**在 2/3 完成后才上线（避免过渡期误报，决策点 1 已述）。
5. **协议〇.9/〇.10 正文与 README-跟进机制与命名约定.md 措辞同步**（proposal.md「Impact」已列受影响文档），随代码同批更新，不滞后。
6. **回滚策略**：机器字段是纯前缀新增，不改变自然语言正文本身，`git revert` 代码改动即可完全回退到"判据继续解析纯自然语言"的旧行为（队列文件里多出的 `[S:...][D:...]` 前缀文本对旧判据是良性噪声——旧判据本就在扫描整个状态列字符串，不会因多出一段方括号前缀而报错，只是不识别其语义，等价于回到未回填前的状态）；无持久化 schema 破坏性变更（ack 指纹文件、状态字段本身均为新增文件/新增前缀，删除即可复原）。
