# 编辑锁咽喉六修（队列 §一 #351 ⑴～⑹）

## Why

`0-学习与工具/工具-共享文档编辑锁.py` 是本项目「队列写入」这道咽喉的唯一实现。队列 §一 #351 在其上累计发现 **六处守卫缺位**，六项全部落在同一个文件、同一批单测、同一次回归上，故同车。行内已明令「不得只做 ⑴」。

| 子项 | 缺口 | 真实事故 |
|---|---|---|
| ⑴ | `append-row` 不校验锁归属（`acquire`／`release` 两侧都校验，唯独中间真正写盘的这个不校验） | 2026-08-18：`acquire`／`append-row`／`release` 被打包成一条命令，acquire 已被正确拒绝、脚本照跑照写，**在他人持锁期间写入两次** |
| ⑵ | 裸竖线诊断被 arity 检查遮蔽 | 裸竖线同族第 6 次复发（2026-08-19），Shao Peishen 明令「必须根治」 |
| ⑶ | §二「文件清单」路径格式全靠人写对 | 写错的代价是批次行转 ✅ 而文件静默没进 commit，只能事后读 sweep 日志发现 |
| ⑷ | 人的属性（性别代词）写错不产生任何信号 | 人守规则被违反 ≥5 次；实测追改 244 处把姚祖怡写成「她」 |
| ⑸ | §二 批次号不预留、不查重 | **本次实测：现存 174 个批次号前缀中 27 个是撞号**，远超立行时以为的「同族第三次」 |
| ⑹ | `release` 把 `acquire` 的 note（意图）当成事实放行 | `OP-0822-E` 2026-08-22 12:26 UTC acquire、note 写「三份接力件定长化 分三批登记」，那三条批次行**从未出现在任何一个提交里** |

### 🔴 本次退休哪一个既有守卫（协议〇.9 措施 B，one-in-one-out）

**退休 `_validate_release_structure` 校验 ②「§二 新增批次行的文件清单列须含队列文件自身路径」。**

**理由**：② 是一个**代理判据**——它真正想保证的是「你改了队列文件，队列文件就得进某个批次、别掉在地上」，但它只能表达成「每一条新批次行都必须把队列文件写进自己的清单」。⑹ 落地后直接度量那件事本身：release 时若队列文件（或任何脏文件）不被任何待处理批次覆盖，即拒绝。**⑹ 严格覆盖 ② 想防的失效形态，且覆盖面更大**（② 只管新批次行的清单写法，⑹ 管全部脏文件是否有归属）。

**② 残余的那点额外严格性没有用途**：② 会拒绝「本次新增的批次行只列代码文件，而队列文件已被另一条既有待处理批次覆盖」这种情形——但那种情形下队列文件确实会被提交，② 拦的是一个不存在的问题。

**⚠️ 退休的代价，如实写明**：② 当前**没有逃生阀**，⑹ 有（`登记豁免：`）。退休后，一个写了 `登记豁免：` 的 session 同时也就不再受 ② 约束。这是一次实质放松，接受它的理由是：⑹ 的逃生阀要求把理由写进队列行（进 git、可被值周巡检看见），而 ② 的绝对性此前从未被验证是必要的。

**另一个候选被否掉，记录理由**：曾考虑退休 sweep 的孤儿告警（既然 ⑹ 阻断更强）。**不退**——⑹ 只对「acquire 过锁的 session」生效，完全不 acquire 的 session 抓不到，那一层正由 sweep 孤儿告警兜住，两者是不同的覆盖面而非重复。

### 伴生文件的 .gitignore 覆盖（队列 #328②）

**本变更不新增任何自动生成的文件名形态。** ⑹ 需要的「acquire 时刻工作区脏文件快照」**存入既有锁文件 `*.editlock` 的 JSON 载荷**（新增 `dirty_at_acquire` 字段），与既有 `reserved`／`domains`／`history` 同一载体，不另建 sidecar。

实测核实（不是推断）：

```
$ git check-ignore -v "1-转型规划/0-全景路线图/跨桌任务队列-机制环境.md.editlock"
.gitignore:62:*.editlock*    1-转型规划/0-全景路线图/跨桌任务队列-机制环境.md.editlock
```

## What Changes

- **⑴** `append-row` 新增 `--who`；目标存在**有效锁**（未释放、未陈旧）且 `--who` 缺失或与持锁人不符时**拒绝写入**。无有效锁时只告警不阻断（协议〇.7 一贯是协作性质，手写整行仍允许，见 opener §〇.7 边界）。
- **⑵-a** arity 校验失败时**顺带扫全部 cell**，任一含裸竖线即把两条诊断合并；并**打印一条修正后的完整命令行供复制**（Shao Peishen 2026-08-23 答 ⑵-b 选 (b)：否决 `--row-md`，走退而求其次）。
- **⑵-b** **不实现**。`--row-md` 与模块 docstring L116「不接受预拼好的整行字符串」正面冲突，Shao Peishen 拍板否决——理由是第二条写入路径正是 #164／#225／#258 那一族缺陷的滋生地。
- **⑶** §二「文件清单」列的反引号片段中，**形如路径者必须是仓库根相对完整路径**；绝对路径／反斜杠分隔符／`./`・`../` 前缀／仓库根下不存在的裸文件名一律拒绝。**预登记批次行豁免**（`queue-claim-time-preregistration` 明文允许其文件清单为目录前缀或范围性描述）。
- **⑷** 队列行内**人名与性别代词邻近矛盾**即 lint 违规，配 `性别豁免：` 逃生阀。名录抽为单一常量 + 一条**与根 `CLAUDE.md` §1 对表的单测**，名录再扩时回归当场变红。
- **⑸** `append-row --section 二` 与 release 校验双侧**批次号前缀查重**，命中即拒绝并提示下一个可用序号。
- **⑹** `acquire` 记录工作区脏文件快照；`release` 时**全部脏文件必须被某个待处理 §二 批次的文件清单覆盖**，未覆盖即拒绝、锁保持占用、逐个列出未覆盖路径。逃生阀 `登记豁免：<理由>`。
- **退休** `_validate_release_structure` 校验 ②（见上）。
- **配套** 更新两份 SKILL.md 源码副本与其**已安装副本**（`C:\Users\Paul Shao\Claude\Scheduled\{huijian-chaijian-patrol,weekly-status-update}\SKILL.md`）——它们当前调用 `append-row` **不带 `--who`**，⑴ 上线后会被拒绝，属真实生产影响，同批修掉。

## 🔴 与 #351 原文的一处偏离（取证推翻，必须先看这一条）

#351 ⑹ 的原文判据是「**本次持锁窗口内新增的脏文件**」（快照差集）。**本次取证证明该判据抓不住它自己的立项实证。**

`reports/sweep-commit.log` 逐行取证：

```
=== sweep 运行 2026-08-22 12:20 UTC ===
⚠ 非 clean：以下脏路径不属于任何待 commit 批次声明，跳过本轮：
    - 1-转型规划/session接力-财务域-归档-202608.md
    - 1-转型规划/session接力-财务域场景落地.md
    - 1-转型规划/session接力-质量域-归档-202608.md
    - 1-转型规划/session接力-质量域场景落地.md
    - 1-转型规划/session接力-采购域-归档-202608.md
    - 1-转型规划/session接力-采购域场景落地.md
```

**12:20 UTC 六个孤儿已全部脏；`OP-0822-E` 12:26:16 UTC 才 acquire——晚 6 分钟。** ⇒ 按「快照差集」口径，这六个文件在 acquire 那一刻**已在基线里**，release 时差集为空，**E 照样放行，缺陷原样复发**。

**⇒ 判据改为「release 时**全部**脏文件都须被某个待处理 §二 批次覆盖」**，acquire 快照**保留但改变用途**：不再用于过滤，而用于**归因**（提示里区分「这条是你 acquire 之前就脏的，可能不是你造成的」）与并发场景单测。

**这不是新造判据**——它逐字就是 sweep 孤儿检测已在用的那一条（`_status_paths` ∖ 各待处理批次片段），本次只是把它从「只进日志的事后告警」前移到「有阻断力的 release 时点」。#351 ⑹ 自己写的设计意图正是这句：「sweep 的孤儿告警只进日志与运维群、没有阻断力，而 release 是唯一一个 session 还活着、且必然会被调用的时点」。**原文的判据与它自己的设计意图不一致，本次以设计意图为准。**

**代价**：并发 session 在**同一工作区**造的脏文件会算到持锁人头上（#351 边界一原想靠差集排除）。**缓解**：⑴ 不同 worktree 天然互不可见，本项目「一任务一 worktree」纪律下这是少数情形；⑵ 提示里用 acquire 快照标出「acquire 前就脏」的那些；⑶ `登记豁免：` 逃生阀。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

**本流程哪些判断是人脑默会经验？**

1. **「这个脏文件该不该登记进批次」**——现由每个 session 各自默会判断，无成文规则；判错不产生任何信号（⑹ 的立项根因）。
2. **「§二 文件清单里的路径写到什么精度才算够」**——现状是「sweep 能用后缀匹配对上就行」，而后缀匹配在同名文件并存时会判 `ambiguous` 并连带跳过批次（#234(1) 实证）。精度的默会尺度从未写下来。
3. **「批次号第二段到底是流水号还是队列行号」**——实测两种写法并存（`B-0818_18_…` 是流水号、`B-0808_309_…` 是队列行号），撞号判据因此含糊。
4. **人员性别与职务**——CLAUDE.md §1 已明文「能从字面猜出来、且猜错了不会当场报错」，是本项目认定的一整族默会知识。

**由谁显性化？**
- 判断 1／2／3：**持有人＝Shao Peishen（环境总线口径）**，**backup＝值周巡检**（每周实际执行批次登记与 sweep 对账的那一方，对失效形态有一手观察）。
- 判断 4：**持有人＝Shao Peishen**（名录唯一权威源，根 `CLAUDE.md` §1），**backup＝IT 陈承**（全员企微名录的汇总方）。

**用什么方法提取？**
- 判断 1／2／3：**历史案例反推**——本变更包的判据全部由实测数据定标，不由设想定标（⑶ 的 1371 个片段／220 个违规、⑸ 的 174 个前缀／27 个撞号、⑹ 的 sweep 日志时间线、⑷ 的 65→18 收窄对比）。
- 判断 4：**已完成的显性化**——名录已在 2026-08-20／08-21／08-22 三次由 Shao Peishen 口述落档；本变更只做「把已显性化的知识挂到机器咽喉上」这一步，不重新提取。
