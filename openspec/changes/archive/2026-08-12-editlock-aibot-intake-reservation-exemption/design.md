## Context

`工具-共享文档编辑锁.py::_validate_release_structure` 的③编号校验（队列 #225 引入，#308 扩展预留归属子句）对持锁期间"真正新增"的 §一/§四 行做两件事：① 不得与现役/归档编号重复；② 必须属于本次持锁期间 `--reserve`/`--reserve-multi` 预留到的编号集合。②这一子句的立法背景是协议〇.7"此后新行编号一律用 --reserve 取"——但企微机器人的收件登记路径（`queue_appender.py::_next_task_id`）从设计之初就没有走 `--reserve`，它是一条独立取号路径，直接从"§一 可见最大号 / 顶部高水位线"取较大值 +1。

这条独立取号路径不是疏漏——协议〇.10 ⑶（2026-08-08 定稿）明文承认它并豁免它接受"并入审核"（"收件登记≠建任务，且机器无法判断并入"）。但③预留归属校验是 2026-08-08 之后（#308）落地的，落地时没有对照协议〇.10 ⑶ 已经承认的这条豁免路径，导致机器人无论何时 `release`，只要它新增了行，必被③拒绝。2026-08-12 真实发生：机器人为姚祖怡 1.6MB docx 正确补上队列行 `#332`，`release` 却被拒绝，锁保持占用直到 30 分钟陈旧接管——期间人类会话被卡住无法正常读改写队列文件。

## Goals / Non-Goals

**Goals：**
- 让③预留归属校验识别并放行协议〇.10 ⑶ 已经承认的机器人收件登记路径，消除 #333 描述的锁卡死复发。
- 不削弱③校验对其它场景的既有保护：人类新增行仍必须走 `--reserve`；机器人若新增非收件登记内容的行（理论上不应发生，但代码不应假设"机器人身份 = 一定安全"），仍须走正常校验。
- 判据与协议〇.10 ⑶ 正文、`queue_appender.py` 实际写入格式三者保持字面一致，不引入协议之外的新规则。

**Non-Goals：**
- 不改变机器人取号本身的实现（`queue_appender.py::_next_task_id` 不动）——本变更只改 release 侧如何"认"这条已存在的取号路径，不改它怎么取号。
- 不扩大豁免范围到"机器人的任何新增行"——只豁免"预留归属"这一项判定，且要求任务列前缀严格匹配；组内重复、归档号重复两项独立校验不受影响，仍能拦住真正的编号冲突（即便冲突来自机器人）。
- 不处理"跨文件移动一行被同一条校验误判为新增"这一衍生发现（见下「相关但不在本次范围内的发现」）——这是队列双队列拆分（#315）自身的载体设计缺口，不是"企微机器人收件登记豁免"这个决策所能覆盖的场景（移动行的一方通常是人类会话，不满足 who=企微机器人 这一前提），已如实登记进 #315，不在本次勉强扩范围。

## Decisions

### 决策点 1：豁免判据的具体实现

**推荐：选项 (a)——`lock_data.get("who") == AIBOT_LOCK_WHO` 且新增行任务列（cells[1]）以 `AIBOT_INTAKE_TASK_PREFIX` 开头，两者同时成立才豁免。**

- **(a) who + 前缀双重判据（推荐，已实现）**——与协议〇.10 ⑶ 原文"who 为企微机器人 且 新增行任务列以「企微反馈自动归档：」开头"逐字对应；`AIBOT_LOCK_WHO`/`AIBOT_INTAKE_TASK_PREFIX` 两个常量的取值分别与 `queue_edit_lock.py::AIBOT_LOCK_WHO`（"企微机器人"）和 `intake.py` 第 213 行实际拼接的描述前缀（"企微反馈自动归档：{sender_label} 发来..."）逐字一致，已用现存代码交叉核对（两处常量物理上分处两个文件、不跨文件 import——与 P0/P1 判据等既有惯例一致，避免多 worktree 共享 editable install 的静默劫持风险，见 `工具-共享文档编辑锁.py` 文件头部既有说明）。**代价**：两处字符串常量分处两个文件，若未来任一处的措辞发生变化（如企微收件描述文案改版），需要同步改另一处，否则豁免会静默失效（退化为③校验拒绝、锁卡死，不会误放行）——这一风险的失效方向是安全的（宁可拒绝也不误放）。
- **(b) 仅按 who 豁免（不检查任务列前缀）**——更简单，但会把豁免面扩大到"机器人身份持锁期间新增的任何行"，包括理论上不应由机器人产生、但若未来代码演化出的其它新增路径也会被一并放行，直接违背协议〇.10 ⑶"须防它变成绕过口"的明文要求，**不采纳**。
- **(c) 新增独立的显式豁免标记（如行内追加一个机器专用字段）**——需要改 `queue_appender.py` 的写入格式与③校验的解析逻辑两处，且与"仅豁免预留归属这一项判定"的最小改动原则不符，代价明显高于 (a)，**不采纳**。

**默认项**：若无人回应本决策点，按 (a) 执行——判据已直接取自协议〇.10 ⑶ 定稿文本，无需另行拍板（见 proposal.md「审批记录」，队列 #333 派单件已将 (a) 列为②的确定实现方案）。

### 决策点 2：豁免的适用范围（§一 vs §一+§四）

**推荐：仅 §一。**

`queue_appender.py::TABLE_HEADER_MARKER = "## 一、任务看板"`——机器人自动追行的唯一写入目标就是 §一，从未、也不会写 §四（§四"需 Shao Peishen 的动作"是人工登记的例外与拍板事项，机器人无权代为登记）。豁免判据在 `_validate_release_structure` 的分区循环内实现，天然只在 `label == "一"` 分支生效；即便未来 §四 出现一行"企微反馈自动归档："开头的文本（人为构造），因为 who 大概率不是机器人（人类没有理由伪装 who），仍会被③正常拦下。

**默认项**：若无人回应本决策点，按仅 §一 生效执行——与机器人实际写入路径完全对应，不引入未使用的扩大面。

## 相关但不在本次范围内的发现：跨文件移动行被同一条校验误判为新增

派单件同时要求核实"跨文件移动一行（把 §一 某行从机制环境.md 挪到业务场景.md）是否与②同源同一处代码"。已用白盒复现确认：**是同一处代码**（`_validate_release_structure` 的③预留归属校验分支），但**不是同一个可修的决策**——本次豁免的判据是"身份(who) + 内容前缀"，而跨文件移动的场景通常由**人类**会话执行（如 2026-08-12 环境总线把 `#332` 从机制环境件挪入业务场景件），既不满足 `who == 企微机器人`，也不涉及"企微反馈自动归档："前缀，本次决策点 1 选定的判据完全不覆盖这一场景。

要正确处理"跨文件移动"，需要在校验一份文件时同时感知**另一份**队列文件的旧快照/新内容（判断"这个编号是不是从另一份文件搬过来的，而不是凭空冒出的重复"）——这是一个结构性不同的问题：现有 `_validate_release_structure` 按单文件独立校验（`cmd_release` 对 `_iter_queue_paths()` 逐份调用），要支持跨文件关联判断，需要额外设计"如何界定合法搬移 vs 巧合撞号 vs 真实错误"，这本身就是一个决策点，且与 #315（双队列拆分自身的载体设计）主题更贴合，不属于"协议〇.10 ⑶ 机器人豁免"这一决策的自然延伸。**已如实登记进队列 #315 行内，不在本变更包内处理**（详见队列 §一 #315 行内新增段）。

## Risks / Trade-offs

- **[风险] who 是调用方自报字段，不是加密身份认证——理论上任何持锁者都可以传 `--who 企微机器人` 冒用豁免** → 这正是协议〇.10 ⑶ 原文自带的已知风险条款："若日后出现「为绕开并入审核而故意走机器人通道建任务」的用法，本豁免立即失效，如实登记为已知风险，由值周巡检在对账审计时留意"——本变更不新增这一风险（豁免本身早已被协议承认并接受这一残余风险），也不试图在代码层解决身份认证问题（超出编辑锁工具的定位，编辑锁全文从未做过身份认证，一贯以"自报 + 事后可追溯"为模型）；监测责任按协议原文归值周巡检，不在本变更包内新增监测机制。
- **[风险] 两处字符串常量（`AIBOT_LOCK_WHO`/`AIBOT_INTAKE_TASK_PREFIX` vs `queue_edit_lock.py`/`intake.py` 的对应值）分处两个文件、无导入关联，未来任一处改动措辞会导致静默不同步** → 失效方向安全（不同步只会导致豁免失效、回退到"拒绝+锁卡死"，不会误放行本不该放行的编号）；不采用跨文件 import 是刻意选择，与 P0/P1 判据等既有惯例一致（见决策点 1 论证），避免多 worktree 共享 editable install 的静默劫持风险。
