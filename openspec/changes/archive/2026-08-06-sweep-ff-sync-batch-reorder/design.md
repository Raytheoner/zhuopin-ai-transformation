## Context

见 proposal.md「Why」——故障链、决定性取证（20/20 提交触碰同一文件）、当日两次人工介入记录均在那里，本节不重复。

现有 `main()` 相关调用顺序（详见 `0-学习与工具/工具-落库sweep.py`）：

```
_heal_stale_index_lock
_check_preconditions
_abort_if_edit_lock_held
_push_any_unpushed_commits        ← #194，起跑段无条件补推遗留的本地提交
_flush_pending_lock_appends       ← #192-A
_run_decision_reminder_second_carrier  ← #219
_sync_master_if_behind_origin     ← 🔴 本次故障点：ff-only merge，此时工作区必脏
_verify_fast_forward(refetch=False, is_fork=True)  ← 分叉早检
_reset_fork_state
dirty_paths / 解析队列 / 批次隔离 / 孤儿追踪         ← #238/#236(2)
批次处理循环：每个批次各自 add → 改队列状态列 → commit → verify-ff → push
遗留尾巴批次：改队列状态列 → commit → verify-ff → push
台账重跑：生成 → commit → verify-ff → push
```

`_sync_master_if_behind_origin` 只处理"本地是 origin/master 祖先（纯落后）"这一种情形，且要求工作区干净（`git merge --ff-only` 需要更新工作区文件，遇到未提交改动会被 git 拒绝）。但按文件头部注释的设计假设，"§二 待 commit 批次的存在本身就意味着主工作区必然有未提交改动"——这个假设与 `_sync_master_if_behind_origin` 对"工作区干净"的隐含要求直接冲突，且该函数排在所有批次处理之前，冲突一旦发生，后面的一切（包括真正有意义的分叉早检、批次处理、告警）全部走不到。

## Goals / Non-Goals

**Goals:**
- 让"工作区处于待提交状态"（sweep 的正常工作前提）不再阻塞它与 `origin/master` 的对齐。
- 对"本地新提交与 origin 新提交分叉但内容不冲突"（队列文件的常见并发编辑形态）做到自动化解决，无需人工介入。
- 对"真实内容冲突"这一少数情形，安全退化到现状同等水平（不丢数据、有告警），不追求自动解冲突。

**Non-Goals:**
- 不改变 `_push_any_unpushed_commits`（#194）的行为与调用位置——它解决的是另一个时序点的问题（见「决策点 4」）。
- 不改变批次识别/状态列判据（#238/#248 既有逻辑）——本变更只动"批次已判定可提交之后、推送之前"这一段。
- 不引入任何自动解决 git 冲突的逻辑——冲突时的动作永远是"回滚 + 告警 + 交人工"，不新增自动合并策略。
- 不追求消灭"主工作区偶尔落后 origin"这件事本身——只消灭"因为落后/分叉而导致批次完全无法处理"这个后果。

## Decisions

### 决策点 1：选定"先提交再同步（含 rebase）"（候选 A 的加强版），否掉候选 B 与候选 C

三个候选见 proposal.md「Why」引用的队列 #288 分析。取舍：

- **候选 B（stash 保护式 ff）否决**——如 #288 分析所述，挡住 ff 的常常正是"已被批次声明、不能 stash"的那个文件（本次故障的典型场景正是：队列文件的某一段落已被某个批次的文件清单声明，是即将要提交的内容，不能被 stash 挪开）。stash 只能保护"未声明的脏文件"，而这恰恰不是本故障的主要矛盾。
- **候选 C（失败降级为告警但继续）单独使用不够彻底，但其"止血不丢数据"的精神被保留**——单独的 C 只解决"不整轮跳过"，不解决"本地提交持续堆积、最终还是要人工 rebase"。本设计把 C 的止血精神吸收进"rebase 失败时的回滚+告警"分支：真实冲突时确实止血于"本地提交安全存在、告警等人工"，但**非冲突场景下不满足于止血，而是自动 rebase 推送到底**——这是"根治大多数情形、止血少数情形"的组合，比单选 C 更彻底。
- **选定候选 A 并加强**：不是简单把"批次处理"整体挪到"同步"之前再挪回来，而是把批次处理拆成"提交"和"推送"两个阶段，提交阶段在同步之前，推送阶段在同步（含可能的 rebase）之后统一执行一次。对齐策略从"只会 ff-only"升级为"能 ff 则 ff，不能则 rebase"——因为提交阶段完成后，本地几乎必然领先或分叉（而非纯落后），只有 ff-only 是不够用的。

### 决策点 2：★ 这是打破自锁循环，还是只是让它不再阻塞批次？——两者都是，取决于是否发生真实冲突

proposal.md 与队列 #288 都明确要求正面回答这个问题，此处给出精确答案：

- **对"本地脏 + origin 改动同一文件但不冲突"这一绝大多数情形（队列文件是追加型文件，不同会话通常编辑不同行/不同批次）——这是真正打破了自锁循环**：过去"越需要同步越同步不了"，现在"提交→rebase→推送"一次跑完，本地与 origin 重新统一，循环被切断，不会自我延续、不会越拖越大。
- **对少数真实内容冲突的情形（同一行被双方修改）——这不是打破循环，是让循环不再阻塞批次，但仍然存在**：rebase 失败后本地提交安全保留、告警发出，但本地领先/分叉的状态本身还在，需要人工 rebase 才能真正解除。这与候选 C 的止血效果相同，且复用现有 #171 告警机制，人工能第一时间知道（不是像现在这样"安静地每小时空转"）。
- **为什么不能对少数情形也做到"打破循环"**：queue 文件的真实冲突意味着两个会话对同一行/同一段落有不同的最终意图，自动选择任一方都可能丢失对方的真实决策内容（这正是 sweep 全文"不强推、不自动解冲突"的一贯设计哲学——见文件头部 `_verify_fast_forward` 的注释"不是快进时绝不强推，交人工处理"）。本变更沿用这一哲学，没有理由在这里破例。
- **诚实的结论**：本变更不是"消灭一切需要人工介入的情形"，而是"把需要人工介入的情形从『20/20 的必然』收窄到『真实内容冲突的少数概率事件』"，且这少数情形下的体验从"安静空转、要主动翻日志才发现"改善为"主动 webhook 告警"。

### 决策点 3：移除批次处理前的第二次分叉早检（`_verify_fast_forward(refetch=False, is_fork=True)`），因为它在现有调用顺序下已是死代码

推导：`_push_any_unpushed_commits`（#194）在 `main()` 起跑段最先运行，其内部逻辑是：若本地领先 origin 且不可 ff（已分叉）→ 立即抛出携带 `is_fork=True` 的 `SweepAbort`；若可 ff → 补推后 `ahead` 归零。也就是说，**执行到 `_sync_master_if_behind_origin` 这一步时，`ahead`（本地领先 origin 的提交数）必然已经是 0**——要么从一开始就是 0，要么已被 #194 补推为 0，要么在补推失败的分支里 `main()` 早已经 raise 退出。而在批次处理开始之前，没有任何代码会产生新的本地提交（批次的 `git commit` 全部在批次处理循环内，即这两次检查之后）。

`ahead == 0` 时，本地相对 origin 只可能是"落后"或"相等"，不可能是"分叉"（分叉的定义要求双方都有对方没有的提交，即 `ahead > 0`）。因此 `_sync_master_if_behind_origin` 之后的 `_verify_fast_forward(refetch=False, is_fork=True)` 想要捕捉的"分叉"场景，在当前调用顺序下**不可能被触发**——它要么被前一步的 `SweepAbort`挡住根本执行不到（`_sync_master_if_behind_origin` 落后场景 ff 失败时已经 raise），要么在能执行到的时候必然是 ancestor 关系（无论落后、相等还是 ff 成功后相等），check 必然通过。这是一段防御性但已经失去实际作用的代码。

本变更把分叉判定与告警职责整体交给末尾新增的对齐步骤（此时 `ahead` 可能真的 `> 0`，因为提交阶段已经产生了新的本地提交，"分叉"在这个位置才是一个会真实发生的场景）——语义不倒退（`is_fork`/`FORK_EXIT_CODE`/webhook 文案/连续轮次持久化全部复用不变），只是移到了它真正该起作用的位置。

### 决策点 4：不改动 `_push_any_unpushed_commits`（#194）

考虑过是否让 #194 也复用本次新增的"能 ff 则 ff，不能则 rebase"逻辑（统一两处对齐代码，减少重复）。否决理由：

- #194 解决的是"上一轮已经 commit 但 push 失败，遗留到这一轮"的问题——发生在**本轮任何新工作开始之前**，此时如果遗留的提交已经与 origin 分叉，直接尝试 rebase 有一个额外风险：这个提交是**上一轮**的产物，rebase 冲突时人工要理解的上下文是"上一轮做了什么、现在又要 rebase 到哪"，比"这一轮刚完成的批次冲突了"更绕。#194 现有"分叉即立即停下告警、不尝试 rebase"的保守策略，对付"陈年遗留提交"这类场景更合适。
- #194 已有独立的 spec（`sweep-startup-resilience`）与既有测试覆盖，本次不动它可以把改动面严格限制在"故障链涉及的那一段"，降低回归风险。
- 两处逻辑虽然相似（都是"ahead>0 时判断能否 ff，不能则如何处理"），但触发时机与需要处理的历史包袱不同，重复几行判断逻辑换来"各自独立、互不影响"的隔离性，本项目其它同类场景（如 #238 与 #248 两处状态列判据"原理相同、实现不同"）也是同一取舍。

### 决策点 5：末尾统一推送一次，而不是保留"每个批次各自推送"

批次提交阶段全部只 commit 不 push，是为了让"对齐 origin/master"这一步只需要处理一次（而不是每个批次各自面对一次"此刻 origin 是否又变了"的竞态）。这也顺带解决了一个次要问题：现状下如果一轮处理 3 个批次，会产生 3 次独立的 push（外加可能的台账重跑 1 次），origin 上会看到 4 次 fetch+ff-check+push 的往返；改为 1 次统一推送后，往返次数从 O(批次数) 降到 O(1)，副作用是网络请求更少、被并发提交插队的窗口更短（間接降低分叉概率，但不是本次改动的主要目的，只是自然收益）。

## Risks / Trade-offs

- **[风险] rebase 会改写本轮批次提交的 commit hash** → 可接受：sweep 的批次提交在推送前本来就只存在于本地，rebase 重写 hash 不影响任何已经推送/被外部引用的历史；队列文件里没有任何地方记录"commit hash"作为可信引用（`_process_normal_batch` 记录的 `sha` 只用于当轮日志文案）。
- **[风险] rebase 冲突时人工需要理解"这一轮到底提交了什么、卡在哪个文件"** → 缓解：`git rebase --abort` 之后本地历史干净（只有本轮的批次提交，未被 rebase 污染），告警文案沿用现有 `_handle_fork_detected` 格式（本地 HEAD 短哈希 + origin HEAD 短哈希），人工可直接 `git log`/`git diff` 查看本轮提交内容；后续处置路径与"手工解卡"（本次故障 A 会话的做法）完全一致，不需要新学一套流程。
- **[风险] 批次提交阶段全部改为"只 commit 不 push"，若这一阶段中途因未预期异常退出，本地会遗留多个未推送的批次提交** → 缓解：这正是 #194（`_push_any_unpushed_commits`）存在的意义——下一轮起跑会自动检测并补推（可 ff 时）或告警（分叉时），不是新增风险，是复用已有兜底。
- **[权衡] 从"每个批次独立成败"改为"批次提交独立、但推送成败共享"** → 如果本轮 3 个批次都成功 commit，但统一推送失败（网络问题，而非分叉），3 个批次的 commit 全部停留本地——这与现状下"第 1 个批次 push 失败就直接 SweepAbort，第 2、3 个批次连提交机会都没有"相比，**是净改善**（现状下失败的批次多，新设计下失败的批次通常更少：至少都完成了本地提交，只是没推送，而 #194 会在下一轮自动兜底）。
- **[权衡] 台账重跑不再有独立的"内容有无变化才 commit"提前短路机会与独立失败隔离** → 影响很小：台账重跑仍然按原逻辑判断"内容是否变化"再决定要不要 commit（这部分逻辑不变，只是去掉它自己的 verify-ff+push，改为汇入末尾统一推送）；若台账重跑本身失败（如生成脚本报错），原逻辑就是"记日志、不影响已落库批次"，这个语义不变。

## Migration Plan

不涉及数据迁移（sweep 是无状态 CLI 脚本，唯一的持久化状态是 `reports/sweep-fork-state.json`/`reports/sweep-orphan-state.json`，两者的读写逻辑本次都不改）。部署方式与既有惯例相同：代码合入 `master` 后，下一次 `ZhuopinCommitSweep` 计划任务触发时自动生效，无需手工重启（sweep 本身就是"每次全新进程执行"的定时任务，不是常驻服务）。

回滚策略：若上线后发现新逻辑有未预期问题，直接 `git revert` 本次改动的提交即可回到"批次处理前同步"的旧逻辑；由于本次改动不涉及任何持久化状态的 schema 变化，回滚无需数据迁移。
