# queue-table-shared-parser-consolidation Proposal

## Why

队列 #306 取证：跨桌任务队列表格的"按竖线切列＋取某一列语义"这一解析逻辑，历史上曾在至少 7 处各自独立实现，且 `工具-队列查询.py` 文件头把这种重复正当化为"本项目一贯做法"（理由是"本目录多个 `.py` 文件名含中文/连字符，不是标准可 import 的模块路径"——该理由已被证伪：`zhuopin_platform` 本就是 `pip install -e` 的可安装包，各场景已在 import 它）。

队列 #308（状态机器字段，2026-08-09 已 apply 落地）从根本上消解了这七份实现里最重的两件事——① 列语义解析、③ 开头片段提取——消费者此后只需读一个定长的 `[S:...][D:...]` 前缀字段，不再需要理解 8 列各是什么语义。**Shao Peishen 2026-08-08 已拍板措施 A**：#306 原定需要独立 design 审的"权威解析器"大工程降级为 P3、缩范围为"#308 落地后，把仅存的转义（②）与列数校验（④）两件小事合并进 `zhuopin_platform/shared_tools/`"，**原本要为 #306 单独走的 design 审取消，相关决策并入 #308 的 design**（详见 `openspec/changes/queue-status-machine-field/design.md` 决策点 4）。#307（撤掉"独立实现是本项目一贯做法"这段文件头表述）已由 Shao Peishen 拍板并入 #306，不再单独占行。

本变更即落地这一已拍板的缩窄方案：只交付②转义与④列数校验两件事的权威模块，不重建"权威解析器"这一原始大工程，也不重开设计讨论。

## What Changes

- **新增 `5-平台底座/zhuopin_platform/zhuopin_platform/shared_tools/queue_table.py`**，承载两件事：
  - `SECTION_COLUMN_COUNTS`：跨桌任务队列.md 各分区（§一/§二/§四）的标准列数常量（8/4/4），供各消费者引用而非各自硬编码。
  - `has_bare_pipe(cell)` / `column_count_ok(section, cells)` 等校验函数：判定单元格是否含未转义的半角竖线、判定一行的实际列数是否符合该分区预期。
  - `escape_bare_pipe(text)`：写侧半角竖线 `|` → 全角 `／` 的转义函数（与 #164 已确立的人工修复口径一致：`工具-共享文档编辑锁.py::append-row` 现行为是"含竖线一律拒绝写入并提示改用全角『｜』"——本函数供**非 append-row 路径**的写入方/校验方需要程序化转义时复用，两种"全角替代字符"约定并存的历史成因见 design.md）。
- **消费者切换**（六处，`5-平台底座/wecom-aibot-service` 经 `repo_paths.py` 集中的多个消费者算一处）：`工具-落库sweep.py`／`工具-共享文档编辑锁.py`／`工具-队列查询.py`／`工具-文档台账生成.py`／`工具-队列结构lint.py`／`wecom-aibot-service`（`decision_reminder.py`/`draft_gap_detection.py`，若涉及）——各自把本地硬编码的列数常量/裸竖线检测切换为 import 本模块；**不含 #305 的写侧 `queue_appender.py`**（明确排除，见队列 #306 行文）。切换后逐处跑各自既有回归套件，不新增测试覆盖缺口。
- **#307**：`工具-队列查询.py` 文件头"独立实现是本项目一贯做法"段改写为指向本权威模块的一行指针。
- **Cowork artifact `zhuopin-project-status`（JS）如实登记为不可消除的第二实现**——本仓库 CC 会话无法直接改动该文件，不纳入本次消费者切换范围（与 #308 design.md 决策点 4 的处置结论一致）。
- **BREAKING**：无——本模块是新增的纯函数工具集，消费者切换只替换内部实现，不改变各工具对外的 CLI 行为/输出格式。

## Capabilities

### New Capabilities

- `queue-table-shared-parser`：跨桌任务队列表格解析中"转义（半角竖线↔全角替代）"与"列数校验"两类判据的权威实现契约，供项目内多个消费者复用。

### Modified Capabilities

（无——本变更消费者切换的是各工具内部实现细节，不改变 `editlock-assertion-gate-scope`／`sweep-batch-status-classification`／`editlock-section-append-guard` 等既有 capability 已描述的对外判定行为，故不在此处列为 Modified。）

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？** "队列表格有几列、哪一列是状态列"此前是每个消费者作者各自的默会假设（写代码时凭记忆填的硬编码常量），从未有一处集中声明；"裸竖线该不该拒绝还是该转义"目前存在两种并存惯例（#164 的"改全角／" vs `append-row` 的"拒绝并提示改全角｜"），本变更如实记录而非强行统一（见 design.md）。
2. **由谁显性化？** 持有人：**Claude Code**（本变更的直接建造方，落地已拍板的缩窄方案）；决策拍板人：**Shao Peishen**（2026-08-08 措施 A 拍板，见队列 #306/#308）；backup：任何后续接手队列文件解析相关工作的 CC session，`queue_table.py` 模块 docstring 与本 design.md 是首选参考。
3. **用什么方法提取？** **历史案例反推**——七处独立实现的取证清单、#164 转义口径、`append-row` 拒绝口径，均来自现存代码逐一 grep 核实，非预先设计。不涉及 LLM 判断。

## 本次退休哪一个既有守卫；若不能退，写明为何不能

**本次不退休任何既有守卫**——`SECTION_COLUMN_COUNTS`/裸竖线检测此前分散在多处，本身不构成"独立守卫"（它们是各工具内部实现细节，不是对外可绕过/可命中的独立校验点），本变更是"消除重复实现"而非"替换某个校验行为"。真正对外可见的校验点（编辑锁①列数校验、`append-row` 裸竖线拒绝）**保持行为不变**，只是其内部实现改为调用共享模块——不存在退休对象。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：跨项目治理机制，非独立业务场景；近似映射＝**档1 mock 验证**（模块与单测完成，六处消费者切换完成且各自既有回归零漂移，尚未经过至少一次真实生产队列文件的写入/校验场景对新实现的端到端观察——但因本变更不改变对外行为，此项风险显著低于新增行为类变更）。
- **晋下一档的条件**：晋**档2 真实数据跑通**——① 六处消费者切换后各自既有测试套件零漂移；② 对当前生产队列文件（真实 106+ 行）跑一次六处消费者的实际调用，确认输出与切换前一致（回归验证，非新场景验证）。
- **价值指标**（质量型）：消除"同一份判据在 N 处独立实现、无机制发现何时开始不一致"的结构性风险——基线＝7 处独立实现（本变更缩窄后实际消费 2 处判据：转义/列数），目标＝新增第 8 处消费者时默认 import 本模块，不再新写一份本地实现。
- **LLM 判据黄金集**：不适用。
