## Goals / Non-Goals

**Goals：**
- `append-row` 子命令消除"插入位置靠启发式猜"这一类失效（#248/#254 同族），子命令本身不引入新的猜测环节——插入位置、列数、竖线合法性均由工具结构化保证，不依赖调用方手工数行/数列。
- release 新增的一致性校验只对"能被结构化判定"的场景生效（暂缓关键词 + 反引号 `.md` 文件名引用，且文件名与 README 目标文件标注同名），不尝试理解自由文本语义——判不出就不拦，不假装能覆盖所有表达方式（同 `ReserveFailedError` 一贯的 fail-loud、不猜测的哲学）。
- 两项加固都能用现存生产队列文件全部 §一/§四 行 + README 现有跟进信清单做历史兼容核对，结果与人工判断一致。
- 两项加固各自独立可单测验证，不互相依赖对方的实现细节；均不改变 `_validate_release_structure` 既有五项校验（①-⑤）的判定结果。

**Non-Goals：**
- 不尝试对队列行做自然语言理解或主题相似度匹配来判定"点名了哪封信"——只认结构化的反引号 `.md` 文件名引用，这是本次唯一决策点里明确收窄的边界（决策点 3）。
- 不改变 §二 批次行的既有校验（①-⑤ 均维持不变）；`append-row` 支持 §二 时同样只负责插入位置+列数+竖线合法性，不新增 §二 专属语义。
- 不追溯改写队列 #150 行或 README 对应行的既有文本——事故已发生且信不可撤回（见 #294），本变更只保证"下一次类似场景被结构化校验拦下"，不处理已发生的事故本身。
- 不在 `append-row` 内实现编号预留逻辑——编号预留仍是 `acquire --reserve`/`--reserve-multi` 的职责（#163/#185），`append-row` 的 `--cell` 参数里数字编号一列由调用方显式传入（通常是刚从 acquire 拿到的预留号），`append-row` 只负责把这个值连同其它字段拼装进正确位置，不做编号分配决策；编号是否合法仍由既有校验③在 release 时把关。
- 不改变 `ZhuopinFollowupDispatchDaily`/`delivery.py`/`dispatch.py` 的既有发送判据本身——那是 #294 的范围，本变更只在队列文件 release 路径新增一层只读交叉核对，不修改 README 文件、不触碰发送门禁代码。

## Decisions

### 决策点 1：`append-row` 输入形式——结构化字段 vs 整行 Markdown 字符串

**推荐：选项 (a) 结构化字段（按分区列序重复传入 `--cell "内容"`，不含首列编号；编号单独用 `--number N` 传入，§二 除外）。**

- **(a) 结构化字段（推荐）**——调用方按该分区除首列编号外的列序依次传 `--cell`（§一需 7 个、§四需 3 个、§二需 4 个含批次列本身），工具内部用 `"| " + " | ".join(...) + " |"` 拼装成表格行，天然保证列数与预期一致（拼装本身就是按固定分隔符 join，不存在"数错列"的可能）。**代价**：调用方需要把长文本拆成多个命令行参数（对多行长文本略繁琐，需配合 shell 的多行 quoting）。**优点**：从源头消除 #164 那类"裸竖线致列偏移"问题的另一半——不只是"检测到就拒绝"，而是拼装路径本身不给裸竖线可乘之机（下面决策点 2 处理"某个字段内容本身含 `|` 字符"这一残余场景）。
- **(b) 整行 Markdown 字符串**——调用方传入已经拼好的 `--row "| 299 | ... | ... |"`，工具只负责校验列数并插入。**不推荐**：这仍然要求调用方自己数对竖线数量，与现状（人工在编辑器里拼一整行）本质相同，只是把"贴进文件"这一步替换成"贴进命令行参数"，没有消除#248/#254 那类"人眼数错"的根因——真正的根因是拼装环节，不是插入环节。

**默认项**：若无人回应本决策点，按 (a) 执行。

### 决策点 2：字段内容含裸竖线 `|` 的处理——硬拒绝 vs 自动转全角

**推荐：选项 (a) 硬拒绝，报错指出具体是第几个 `--cell` 参数含裸竖线，附上建议改法（改用全角 `｜`）。**

**⚠️ apply 阶段修正（非重新决策，见文末「apply 阶段的实现细节修正」）**：propose 阶段本条原文一度建议"反引号包裹的裸竖线可豁免"，写代码时发现与 `_validate_release_structure` ①列数校验的既有口径矛盾——已改为**不论是否反引号包裹，任何裸竖线一律拒绝**，建议改法也相应去掉"或反引号包裹该片段"这一条（它对本项目的表格解析器不起作用）。

- **(a) 硬拒绝（推荐）**——与本文件一贯的 fail-loud 哲学一致（`_reserve_ids`/`ReserveFailedError` 已确立"宁可让调用方明确知道，也不可返回一个看似正常、实则可能有问题的结果"这一原则）。**代价**：调用方需要手工改一次措辞再重试。
- **(b) 自动转全角 `｜`**——工具自动把字段内的半角 `|` 替换成全角 `｜` 后静默继续。**不推荐**：静默改写调用方的原文内容，本项目已有"工具静默回退"这一专门被点名警惕的失效模式（CLAUDE.md §5）——自动改写字符本身没有恶意，但调用方可能没意识到内容被改过，且全角替换在极少数情况下可能改变原意（如果调用方是想在字段里放一个代码片段，代码片段里的半角 `|` 有语义时不应被静默替换）。

**默认项**：若无人回应本决策点，按 (a) 执行。

### 决策点 3：一致性校验"点名了某封信"的判定范围——结构化引用 vs 自然语言匹配

**推荐：选项 (a) 仅认反引号包裹的 `.md` 文件名引用（basename 匹配 README「主要事项」列 `readme_table._TARGET_FILE_RE` 同款正则提取出的目标文件标注），不做任何形式的自由文本/主题相似度匹配。**

- **(a) 结构化引用（推荐）**——只在队列行（§一：cells[3]"输入指针"+cells[6]"触碰区"两列；§四：cells[1]"事项"列）中查找反引号包裹且以 `.md` 结尾的片段，取其 `Path(...).name`（basename，兼容队列行常写完整相对路径、README 标注常写裸文件名两种形式），与 README 表中各行「主要事项」列用同一正则提取出的目标文件名做精确字符串相等比较。**代价**：只有"点名"方式恰好是反引号 `.md` 文件名、且 README 侧该行已有 #241 目标文件标注时才能被结构化识别；用"部门#N 编号"、纯主题描述等方式点名的行不会被本校验覆盖。**已用 2026-08-06 #150 真实事故重放验证**：该行确实以此形式点名（见 Context 节），本设计能正确识别。**为何仍然推荐，尽管覆盖面不是 100%**：本项目反复出现"用启发式/自然语言判据导致误判"的同族事故（#221、#248 均是子串扫描误伤案例），比起用更宽的匹配换取更高覆盖率、同时引入新的误判风险，收窄到"结构化引用才生效、判不出就不拦"更符合本文件一贯的保守取舍——一次新增的校验若自己成为下一次误判来源，代价比"覆盖不全但从不误判"更高。
- **(b) 更宽的自然语言/主题匹配**——尝试用队列行文本与 README「主要事项」列做子串/关键词重叠度匹配（类似决策点 1 前身"用主题一次性判定 dispatch 目标"的旧路径，见 #241 proposal 提到的"歧义就是因为主题匹配不可靠"）。**不推荐**：#241 本身的存在就是"主题级匹配会产生歧义"的前车之鉴，本变更没有理由重蹈——尤其本次是**拦截/拒绝 release** 这一比"跳过发送"后果更直接的动作，误判成本更高（错误阻塞会逼调用方在结构校验和真实需求之间找变通写法，形成新的规避压力）。

**默认项**：若无人回应本决策点，按 (a) 执行。

### 决策点 4：反向检查（README 状态与队列行结论互斥）的处理力度——告警 vs 阻断

**推荐：选项 (a) 仅打印告警，不拒绝 release。**

- **(a) 告警不阻断（推荐）**——当匹配到的 README 行「发送状态」已是终态"已推送"类值（不等于 `⏳ 待你审` 也不等于 `🆕 待发`），而队列行新增/修改的文本仍含"暂不发/暂缓/压着/不发"字样时，判定为可能的表述滞后（如事故发生后仍在队列行补写"暂不发"说明，属于对已发生事实的追述而非真实的当前决策），打印告警但放行 release。**代价**：不能强制阻断这类滞后表述。**为何不阻断**：这一方向的语义天然比正向（"决定暂缓但载体未同步"）更模糊——队列行事后追述一次已发生的误发经过（如 #150 行本身现在的文本）完全合法且必要，若硬性阻断会让"事故后如实记录"这一必要动作被误伤，与规则退休制"不能把机制立在会误伤正当行为的位置"的既有教训（#225 dogfooding 案例）一致。
- **(b) 同样阻断**——与正向同等对待，一律拒绝 release。**不推荐**：正如上面分析，反向场景包含"如实记录已发生事故"这一合法且高频（本变更包自身的 proposal/design 文本就在做这件事）的写法，阻断会造成大量误伤。

**默认项**：若无人回应本决策点，按 (a) 执行。

### 决策点 5：暂缓关键词集合

**推荐：沿用派单件原文给出的四词——"暂不发"、"暂缓"、"压着"、"不发"，不扩大也不缩小。**

- 这四词是从队列 #294 派单件原文直接摘录（该行本身即由业务总线基于 #150 真实事故拟定），未新增词汇的理由与决策点 3 一致：本变更倾向"收窄、不猜"，若未来发现遗漏场景应作为新的真实案例驱动扩词，而非本次预防性地扩大猜测范围。
- 需注意"不发"是"暂不发"的子串，两词在代码里只需保留"不发"一词即可覆盖两种写法（"暂不发"天然包含"不发"子串），保留全部四词书写是为了让代码可读性上与派单件原文一一对应，不影响判定结果。

## Risks / Trade-offs

- **[风险] 决策点 3 的收窄意味着大量"点名但不用反引号 `.md` 文件名"的历史写法不会被本校验覆盖** → 缓解：这是有意识的取舍（宁可漏判、不可误判），且 #241 已经在推动"起草新行时标注目标文件"成为标准写法，本变更的校验反过来会给"按规范标注"提供额外的价值（能被结构化保护），形成正向激励；不覆盖的场景不会比"完全没有这层校验"的现状更差。
- **[风险] `append-row` 决策点 1 的结构化字段调用形式与现状"直接在编辑器里手写整行"差异较大，存在被现有习惯忽略、大家继续手写整行导致 #248/#254 同族问题复发的风险** → 缓解：本变更不强制要求所有新行都必须走 `append-row`（不改变现有 acquire/release 流程，`append-row` 是可选的增强通道）；若后续发现"手写整行"仍是高频真实事故来源，可在 `专线opener模板库.md` 等载体里把 `append-row` 提升为推荐/强制通道，但那属于改变既有模块对外语义的更大决策，本变更不预先决定。

## apply 阶段的实现细节修正（决策点 2，非新增决策，如实登记）

`/opsx:apply` 实现决策点 2（字段含裸竖线拒绝）时，propose 阶段的原文一度建议"反引号包裹的裸竖线可豁免不拒绝"（参照 §二"文件清单"声明解析用 `re.findall` 提取反引号片段这一先例，误以为反引号在本项目里普遍具有"豁免结构解析"的语义）。写代码时对照 `_validate_release_structure` ①列数校验的既有文档注释重新核实，发现这一假设是错的：①列数校验的原文明确写着"含反引号内裸竖线致列数偏移的情形——本函数按原样切分列，不做任何'容错'，**这正是要抓的失效形态**"——也就是说，现有的 release 校验本就把"反引号内的裸竖线"当作违规来拦截，从未豁免过。

`§二`的反引号提取（`re.findall(r"\`([^\`]+)\`", cell)`）解决的是一个不同的问题（从文件清单文本里识别出哪些片段是文件路径），与"这一行按 `|` 切分后列数对不对"是两条独立的判断——前者对反引号内容做语义提取，后者是对整行字符做naive 分隔符切分，两者互不影响、不能把前者的"反引号有特殊含义"套用到后者。若 `append-row` 放行反引号内的裸竖线，会制造一个"当场写入成功、但下一次任何人编辑该行触发 release ①校验时又会被拒绝"的自相矛盾状态——`append-row` 存在的目的正是要在写入时就替代之后的事后校验，这样的豁免完全违背设计初衷。

**修正**：`_cell_has_bare_pipe` 检测口径改为不做任何反引号剥离，任何 `|` 字符（不论是否被反引号包裹）一律触发拒绝，与 `_validate_release_structure` ①保持完全一致的口径。已同步修正 `specs/editlock-section-append-guard/spec.md` 与本文件决策点 2 的建议改法（去掉"或反引号包裹该片段"）。这不是对决策点 2 选项 (a)"硬拒绝"的推翻——硬拒绝的精神不变，只是把"拒绝的范围"从一开始就设想错误的"排除反引号"改正为与既有校验一致的"不排除任何情形"，是同一决策方向下的实现修正，不需要重新征询决策。
