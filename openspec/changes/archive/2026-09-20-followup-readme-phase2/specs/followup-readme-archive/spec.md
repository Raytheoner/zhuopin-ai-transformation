## Purpose

跟进信 README 主表中已进入终态且长期不再变化的行 SHALL 定期迁出到按月归档件，在不丢失任何读取方既有语义的前提下把主表体积控制在可人工阅读的规模。

## ADDED Requirements

### Requirement: 归档判据
一行 SHALL 被判定为可归档，当且仅当其「发送状态」列以 `📥 已回件并回灌` 或 `❌ 已作废` 开头，且该行「日期」列（即派单件原文「发送日」——信最初登记/发出的日期，MUST NOT 与状态列内自由文本中出现的任何日期混淆）距归档执行时刻已超过 30 天。不满足任一条件的行 MUST NOT 被迁移。**判据只读「日期」列这一个结构化字段，不解析状态列自由文本里的任何时间戳**——避免依赖一个大量历史行并不具备、且格式不统一的隐性字段。

#### Scenario: 满足归档判据的行被迁移
- **WHEN** 一行「发送状态」以 `📥 已回件并回灌` 开头，且其「日期」列距今已超过 30 天
- **THEN** 该行被整行迁移到对应月份的归档件

#### Scenario: 未满 30 天的终态行不迁移
- **WHEN** 一行「发送状态」已是终态标记，但其「日期」列距今不足 30 天
- **THEN** 该行保留在主表，不被迁移

#### Scenario: 非终态行不迁移
- **WHEN** 一行「发送状态」不以任一终态标记开头（如仍是 `⏳ 待你审`／`✅ 已推送…`）
- **THEN** 该行保留在主表，不被迁移，无论其时间跨度多长

### Requirement: 归档件表头与内容原文原样
归档目标文件 `README-归档-YYYYMM.md` SHALL 使用与主表相同的表头与列序；被迁移行的内容 MUST 原文原样写入归档件，不得在迁移过程中改写、压缩或省略任何字段。

#### Scenario: 迁移后内容与迁移前逐字节一致
- **WHEN** 一行被迁移到归档件
- **THEN** 归档件中该行的六个字段值与迁移前主表中的值逐字节一致

### Requirement: 归档编号不复用
一个编号（如 `财务部#3`）一旦被写入主表，无论该行后续是否被迁移到归档件，该编号 MUST NOT 被后续任何新增行复用。**取号算法 MUST 同时扫描主表与全部归档件**，取两者中该部门出现过的最大序号——只扫主表 MUST NOT 被视为满足本要求：一个部门若长期无新信，其主表在途行序号可能均低于其已归档的历史序号，只扫主表会把「下一个可用号」算低，与刚归档的编号相撞。

#### Scenario: 已归档编号不被复用
- **WHEN** `财务部#3` 已被迁移到归档件，此后为财务部新增一封跟进信
- **THEN** 新行编号为该部门计数器下一个未使用过的编号，不为 `财务部#3`

#### Scenario: 部门历史高编号已归档、主表仅剩低编号在途信时取号仍不回退
- **WHEN** 某部门在主表中现存的信编号均低于该部门已归档的历史信编号（如主表仅剩 `#5`，而 `#6`～`#11` 均已归档）
- **THEN** 取号算法返回的下一个可用号基于归档件中的最大编号（如 `#12`），不基于主表现存的较低编号

### Requirement: 活行读取方语义不变
仅依赖「该收信人最新一封信」判定结果的读取方（如跟进闸查询）SHALL 在归档实施后得到与实施前一致的判定结果，无论该收信人的历史信件是否已被归档——判定范围恒定为主表当前存在的行。

#### Scenario: 最新一封已归档，闸判定仍正确
- **WHEN** 某收信人当前在主表中最新的一封信已满足归档条件并已被迁移，但主表仍保留其更早的非终态历史行（若存在）或该收信人当前无主表在途行
- **THEN** 跟进闸查询对该收信人的判定结果（闸开/闸锁）与归档前的既有语义一致，不因归档动作本身产生误判

### Requirement: 全量读取方改为主表未命中再查归档
需要跨历史匹配的读取方（如按编号回填历史统计）SHALL 改造为「先查主表，主表未命中该编号时再查归档件」的两段式查找，且该改造后的输出结果 MUST 与改造前对相同输入的输出结果一致。

#### Scenario: 编号仍在主表，改造后行为不变
- **WHEN** 全量读取方查询一个仍存在于主表的编号
- **THEN** 查找在主表阶段命中并返回，不触发对归档件的查询

#### Scenario: 编号已归档，改造后仍可查到
- **WHEN** 全量读取方查询一个已被迁移到归档件的编号
- **THEN** 主表未命中后自动查询归档件并返回该编号对应的行内容，结果与归档前直接从主表查得的结果一致

### Requirement: 入信桥的 stem 匹配须覆盖归档件（Shao Peishen 2026-09-06 对读取方分类的唯一补充）
`followup_readme_bridge.py` 的 stem 精确匹配 SHALL 在活表未命中时查询归档件；归档件 stem 命中 SHALL 视为「回件命中一封已归档的旧信」——MUST NOT 写入 README 任何单元格（该信已不在活表），MUST NOT 落入「该收信人最新一封已发出的信」这一兜底通道，SHALL 按低噪（不告警）路径记录审计与可见输出，语义等同于「闭环后补充说明」。**理由**：归档判据保证被归档的信恒为终态，但其 `target_filename` 会随行一起迁出活表；若 stem 未命中即直接落入兜底通道，一条回给旧信的回件会被误配给该部门**当前**最新一封活信——这是归档动作本身引入的误配，不是任何人的操作失误，故必须由本能力在归档前一并解决，不能留给使用方逐个发现。

#### Scenario: 活表未命中、归档件 stem 命中
- **WHEN** 一条回件的文件名与活表中任何信的目标文件均不匹配，但与某个归档件中某封已归档信的目标文件匹配
- **THEN** 该回件被判定为命中该归档信，不写入 README，不落入「最新一封」兜底通道，按低噪路径记录

#### Scenario: 活表命中时不查归档
- **WHEN** 一条回件的文件名已在活表中通过 stem 精确匹配命中
- **THEN** 不再查询归档件，直接按活表命中结果处理（活表优先级不变）

#### Scenario: 归档件与活表均未命中
- **WHEN** 一条回件的文件名在活表与全部归档件中均无 stem 匹配
- **THEN** 按既有通道②「该收信人最新一封已发出的信」兜底，行为与归档能力上线前一致
