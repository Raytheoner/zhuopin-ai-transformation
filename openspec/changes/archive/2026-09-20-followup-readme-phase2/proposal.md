> **队列指针**：§一 `#490`（OP-0906-A，`[D:机]`）。
> **openspec 门槛核对**（`.claude/rules/场景建造与合规.md` 三条）：①改变全项目口径（README 登记/状态写入路径、归档编号语义）✅／②涉鉴权与数据可见性（编辑锁、读侧门禁）✅／③改变既有模块对外语义（12 个读取方的读取路径）✅——三条全中，走 openspec 含 design 审。
> **执行环境判别**：本包对象是「跟进信 README 的登记机制、编辑锁行长判据、读侧门禁」——构建环境与自动化机制本身，属**环境保障线**范畴（`.claude/rules/环境保障线.md`「环境保障线边界」——2026-09-13 `OP-0913-E` 由 `队列与落库.md` 拆出），不是业务场景建造。

## Why

`6-人才与组织/部门AI专员跟进/README-跟进机制与命名约定.md` 现状 177.7 KB（主表 102 行，`主要事项`列 75 KB／`发送状态`列 34 KB，37 行已闭环），机器读它（12 个读取方）不费，**人读它费**：跟进信 skill 登记 `⏳ 待你审` 走 Edit 直改，Edit 前按工具约束必须先 Read，每登记一封信就吞 178 KB 上下文。二期把「人碰表」全部换成 CLI，把已闭环的历史行迁出主表，再把超长行外置，目标表 ≤60 KB。

## What Changes

- **新增登记 CLI** `0-学习与工具/工具-跟进信README登记.py`：子命令 `append`（自动按部门取号、未发出不占号）与 `set-status`（发送状态枚举校验），走 `工具-共享文档编辑锁.py --file <README>` 单文件锁，写前列数校验、写后回读，`主要事项` ≤600 B／`交期要点` ≤400 B 超限拒并提示外置。
- **新增已闭环归档**：`📥 已回件并回灌`／`❌ 已作废` 且发送日 >30 天的行整行迁 `README-归档-YYYYMM.md`（表头同、原文原样），归档编号不复用；12 个读取方逐个核实读取语义后分两类改造——只读「最新一封」的（跟进闸查询等）不变，需全量历史的改为「主表未命中再查归档件」。
- **新增行长口径与外置**：现存 12 行 >5 KB 的 `发送状态` 历史段外置 `跟进信行日志/<部门#N>.md`（原文原样，同队列 K2 精神），行内留首段＋末段＋指针；`主要事项` 超 600 B 的行压成摘要、原文进同一日志件；编辑锁 release 校验族对 README 加同款行长判据（首周告警、一周后阻断，逃生阀 `行长豁免：`）。
- **新增门禁**：`hooks-pretooluse-queue-read-guard.ps1` 保护目标清单加 README 主表与归档件（Read 全文即拦，提示改用 `--digest`／闸查询／登记 CLI）；对 rules/跟进信与专员.md 与 `zhuopin-followup-letter`／`zhuopin-send-followup` SKILL 只交付**改句建议文本**（登记只用 CLI、判状态只用查询），由 Cowork 在 CLI 验活后落字——本包不改这两类载体正文。

## Capabilities

### New Capabilities
- `followup-readme-registry`：README 登记 CLI 的 append/set-status 语义、字段长度上限、编辑锁集成、写后回读校验。
- `followup-readme-archive`：已闭环行迁移归档的判据（>30 天、终态标记）、归档编号不复用、读取方按「活行读取方 vs 全量读取方」分类改造的行为约束。
- `followup-readme-row-length-guard`：README 超长行（`发送状态`>5KB／`主要事项`>600B）外置行日志的判据，以及编辑锁 release 校验族对 README 的行长阻断（首周告警、一周后阻断、逃生阀）。
- `followup-readme-read-guard`：`hooks-pretooluse-queue-read-guard.ps1` 保护目标扩展到 README 主表与归档件，拦截直击 Read/Grep/Bash、引导改用查询工具链。

### Modified Capabilities
（无）——`wecom-followup-review-state`（起草只能写入待审草稿态／批准转换路径等既有 Requirement）不改变：新登记 CLI 的 `append` 子命令新建行时仍只能写入 `⏳ 待你审`，遵循该 capability 第 7 条「authorship-agnostic」约束，复用既有写入路径与结构性拦截，不新开一条绕开它的通道，故不构成 Requirement 变更、无需 delta spec。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

**⑴ 本流程哪些判断是人脑默会经验？**
- **规则**：「哪些读取方只需要该收信人最新一封信、哪些需要跨历史全量匹配」——这条判断此前从未显式写下，只存在于各读取方各自的实现逻辑里（如闸查询按语义只看最新一封，而某些回填/统计类脚本可能遍历全表）。
- **阈值**：「已闭环行超过 30 天即可归档」「单行 `发送状态` 超 5 KB／`主要事项` 超 600 B 即需外置」——这两个阈值已由派单件（Shao Peishen 经 Cowork 环境总线拍板）显性化，写入本 proposal 与派单件正文，不再是默会经验。
- **例外**：「哪些读取方即便改造后仍需保留全量读（如需要跨编号回填历史统计的场景）」——本包要求逐个核实、而非一刀切改造，例外名单需在 design.md 中逐一列出并注明理由。
- **尺度**：「归档 ≠ 删除，编号不复用」——防止历史编号在归档后被误认为可复用，这条尺度此前依赖人工记忆，本包起将其写入 spec 成为机器可校验的约束。

**⑵ 由谁显性化？（持有人 + backup，实名）**
- 持有人：**CC 建造会话**（本次 `OP-0906-A`）——逐个走查 12 个读取方源码确定其读取语义、判定「活行 vs 全量」分类。
- backup：**Shao Peishen**——因误判某读取方为「只需最新一封」而实际需要全量历史会导致数据静默丢失（读取方看不到已归档的历史行却不报错），后果不可逆，须由决策人书面确认 design.md 中的分类结论后方可 apply。

**⑶ 用什么方法提取？**
**历史案例反推**：逐个读取方源码走查 + 现有单测断言反推其真实依赖的读取范围（同队列 `#446` 回件形态识别一致的提取方法：先跑通既有单测作行为基线，再核对代码路径）。不用 AI 起草·专家批改——本项判断对象是既有代码行为而非新知识起草。

## 验收与晋档条件（强制，四档口径）

**本变更包交付后场景所处档位**：**不适用四档场景口径**——本包是**工具/机制类变更包**（README 登记与治理基础设施），不交付任何可运行的业务场景功能，无 mock/真实数据/内部服务/对客交付之分。按项目惯例（同 `oem-chroma-ownership-rejudge` 先例）自评为「**档外（工具类）**」，请 design 审核实此自评。

**晋下一档的条件（此处解为「本包可判完工的条件」，逐条）**：
1. 登记 CLI（append/set-status）单测全绿，`--dry-run` 或真实追加测试行后删除均可复现、审计可查；
2. 12 个读取方分类结论（活行 vs 全量）经 Shao Peishen 书面确认后写入 design.md，且对应改造单测全绿；
3. 归档迁移前后 `工具-跟进闸查询.py --to <任一收信人>`／`README查询 --digest` 输出与改前基线逐字节一致（改前先留基线文件）；
4. 编辑锁行长判据（首周告警）已验活，`行长豁免：` 逃生阀单测覆盖；
5. hook 保护目标清单扩展后，一次真实 Read README 主表被拦截且审计行留痕（`reports/hooks-audit.jsonl`）；
6. 队列 §一 `#490` 已回写销号，rules/SKILL 改句建议已移交 Cowork（本包不自改）。

**价值指标**：
- **工时型（主）**：单次登记从「Read 178 KB 全文 + Edit」降为「CLI 一次调用」；主表体积从 177.7 KB 降至 ≤60 KB。基线 = 本次实测 177.7 KB／102 行；达成判据 = 改造后主表实际字节数。
- **质量型**：12 个读取方改前/改后输出零回归（逐一 diff 基线）；README 无单行 >5 KB 残留（行长判据阻断生效）。基线 = 现存 12 行 >5 KB；达成判据 = grep 行长扫描零命中（豁免行除外）。
- ⚠️ 无风险型指标——本包不改变任何合规红线或数据可见性边界。

## 协议〇.9 措施 B：本次退休哪一个既有守卫

**退休对象**：「登记/改状态跟进信 README 必须靠人工 `Edit` 直改（且工具约束下 Edit 前必先 `Read` 全文）」这一**现存但从未被禁止的默认写入路径**。CLI 上线且 hook 保护目标清单纳入 README 后，裸手 `Edit` 登记路径被结构性拦截（同队列 K3 精神对新目标的复用），只能经登记 CLI 完成——这是「用规则换路径」的一进一出：新增的是 README 读侧门禁（`followup-readme-read-guard`），退休的是「裸手 Edit 直改 README」这条一直存在但缺乏门禁约束的隐性路径。

**不能退的**：`wecom-followup-review-state` 既有的「起草只能写入待审草稿态」「唯一合法批准转换路径」等 Requirement 不退——CLI 只是新增一条同样受这些约束的写入路径，不改变、不绕过既有状态机语义（理由见上「Modified Capabilities」）。
