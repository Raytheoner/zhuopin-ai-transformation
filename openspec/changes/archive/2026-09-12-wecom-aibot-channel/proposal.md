# 企微智能机器人双向通道服务（v1）Proposal

## Why

现有企微通道（`0-学习与工具/发企微.py` + 平台 `wecom.py`）只发不收，跟进信送达确认与专员回复归档（R6 纪律）全靠 Paul 人肉转存，是当前最易丢件的环节。Paul 2026-07-11 拍板建「智能机器人」双向通道（WebSocket 长连接，off-LAN 可用、免公网回调），补齐"发得出、收得回、自动归档"的闭环。

## What Changes

- 新增企微智能机器人连接层：WebSocket 长连接客户端（订阅/心跳/断线重连），凭据复用平台 `SecretsProvider`，全部收发动作写平台 `AuditLogger`。
- 新增场景①：推送跟进信（md 正文 + docx 附件），发送成功后回填跟进信 README 状态列。
- 新增场景②：接收专员消息/文件，按 R6 规则自动归档至 `7-外部文档/<部门>/`，并向跨桌任务队列追加"待领"行。
- 新增两道硬门禁（写死进代码，非配置项）：① 收消息只做归档/登记/通知，不自动执行任何业务动作；② 发送侧仅限 README 已登记为定稿的跟进信，草稿不外发。
- 现有 webhook 群机器人通道（`wecom.py`）不变、并存，不做替代。

## Capabilities

### New Capabilities
- `wecom-aibot-connector`：企微智能机器人长连接客户端——订阅（aibot_subscribe）/心跳保活/断线重连退避/单连接看门狗、`aibot_send_msg` 发送、临时素材上传（初始化/分片/结束）、多媒体资源解密下载；凭据经 `SecretsProvider` 注入，全量收发经 `AuditLogger` 留痕。
- `wecom-followup-delivery`：场景①送达通道——推送已定稿跟进信（md+docx）到项目群，发送成功回填 README 状态列；内置门禁②（仅定稿可发，草稿拒绝）。
- `wecom-feedback-intake`：场景②反馈归档——接收专员消息/文件，发送人→部门映射，按 R6 命名规范落 `7-外部文档/<部门>/`，登记 + 向跨桌任务队列追加待领行；内置门禁①（只归档/登记/通知，不触发任何业务动作，fail-closed：映射不明时归入"待分拣"而非猜测部门）。

### Modified Capabilities
（无——本变更不改动 `platform-notification-channels`/`secrets-provider`/`audit-hash-chain` 既有需求，仅作为新增独立通道复用其接口。）

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？**
   - 发送人→部门映射的例外情况（专员离职/临时代理人发消息、非四域实名专员的消息如何分拣）——当前完全在 Paul 脑子里，靠人肉转存时凭经验判断。
   - R6 归档命名中"主要事项"摘要提炼——当前由 Cowork/CC 人工读文件内容拟定，非机械规则。
   - 门禁①"是否构成业务动作"的边界判断（如专员回复里附带的口径确认算不算需要人工升级）——v1 用**保守规则兜底**（只要不是纯"收到/确认"类文本、且不匹配到白名单的定稿跟进信，一律归档+登记，不做语义判断，不引入 LLM 分类），暂不显性化，留 backlog。
2. **由谁显性化？**
   - 部门映射表（企微 userid/姓名 → 部门）持有人 = Paul，backup = **孙涛**（Paul 2026-07-11 确认，随 §5 决策代理纪律）；配置进本变更的 `department_mapping.yaml`（design 给出格式），非代码硬编码。
   - R6 归档命名摘要：v1 不做 AI 摘要，直接用"发送人+收到时间+原始文件名"落档（保守、可追溯），摘要提炼留给专线人工事后补充文件名（不阻塞归档），此项不进本次知识资产提取范围。
3. **用什么方法提取？**
   - 部门映射表：**AI 起草·专家批改**——CC 依据《部门AI专员协同一页纸》起草初版映射，Paul 一次性批改确认即可（非持续性知识提取任务，无需工作坊）。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：**档2（真实数据跑通）**——B/C/D 段验收用真实企微测试群+真实凭据跑通两场景；档3（内部服务，即"接入真实项目群灰度"）留给 F 段（本变更包不含 F，F 单独验收）。
- **晋下一档的条件**（档2→档3，对应任务分段 F）：
  1. Paul 完成前置动作（企微后台建智能机器人+BotID/Secret 交接+拉进真实项目群）。
  2. 测试群验收全通过（echo 收发、断网重连自愈、两场景各一次成功案例、门禁单测全绿）。
  3. 真实群跑一周无事故（无误归档、无漏推送、audit 全程留痕可查）。
  4. Paul 签字批准转常驻。
- **价值指标**（风险型为主）：
  - 风险型：R6 归档丢件率（人肉转存基线=当前无量化数据，事故驱动；目标=自动化后归档动作 100% 落地，零遗漏）。
  - 工时型：跟进信送达确认与专员反馈转存的人工操作时间（基线由 Paul 启动前一句话估算，如"每封信+每次回复约 3-5 分钟人工操作"）。
- **LLM 判据黄金集**：不适用——v1 不含任何 LLM 运行时判断（部门映射用静态配置表、归档命名用确定性规则），无需黄金集。

## Impact（影响面）

- **新增代码**：`5-平台底座/zhuopin_platform/zhuopin_platform/shared_tools/notifiers/wecom_aibot.py`（连接器 SDK 薄封装）+ 新服务目录（位置由 design 定，候选 `5-平台底座/wecom-aibot-service/`）。
- **新增依赖**：WebSocket 客户端库（官方 SDK 或 `websockets`，design 选型），当前全仓库无此类依赖。
- **触碰既有文件（仅追加，不改既有语义）**：跟进信 README 状态列（机器回填行）、跨桌任务队列 §一（追加待领行）。
- **不触碰**：`wecom.py` webhook 通道（并存不改）、任何规划文档正文（CC 分工红线）、ERP/SRM/生产系统。
- **红线核对**：先 mock/脱敏跑通（B 段用测试群+假凭据）再切真实（§7-1）；全量收发写 `AuditLogger`（§7-2）；OEM 隔离不适用（本服务不涉及研发/OEM 技术数据）；L2 门禁不适用（专员均内部人员，`CUSTOMER_OUTBOUND_ENABLED` 不涉及）；ISO 26262 不适用（非嵌入式安全代码）。
