# sweep-commit-message-extraction Design

> 🔴 **本文件是 design 审材料，待 Shao Peishen 拍板**（场景固定流程第 3 步）。审过之前不 apply。
> 决策点共 5 个，每个都给了推荐项与「选它会发生什么」。

## 现状与病灶

```python
# 0-学习与工具/工具-落库sweep.py:2437-2439
def _extract_commit_message(message_cell: str) -> str:
    match = re.search(r"`([^`]+)`", message_cell)
    return match.group(1) if match else message_cell.strip()
```

调用点两处：`_process_normal_batch()` 的 `--dry-run` 打印（5013 行）与真实 `git commit -m`（5023-5024 行）。

**病灶不在正则写错，而在"约定"与"实现"从来没对上过**：实现假设「整格就是一个反引号跨度」，而真实写法有三种，且占多数的那种（94%）压根不写反引号、只是碰巧落进 `else` 分支才对。

## 取证基线（设计依据，已实测）

扫 2026-08-01 以来 `跨桌任务队列-机制环境.md` 的 745 个 commit 历史版本，去重得 357 个 §二 message 格：

| 形态 | 判别 | 条数 | 现行结果 |
|---|---|---|---|
| 无反引号 | `cell.count("\`") == 0` | 335 | ✅ 走 `else`，正确 |
| A | 恰好 2 个反引号且首尾各一 | 15 | ✅ 正确 |
| C | 反引号在正文中间 | 7 | ❌ 静默截断 |
| B | 起首是跨度、其后另有说明 | **0** | —— |

🔑 **形态 B 为零，是本设计能成立的关键**：若历史上存在「\`信息\` ← 一句尾注」的写法，"整格即信息"会把尾注也提交进去；实测它一条都不存在，故该风险不存在。

## 决策点 1：提取语义取哪一种？（**核心**）

| 选项 | 语义 | 对 335/15/7 的效果 | 代价 |
|---|---|---|---|
| **(a) 整格即信息，仅剥一层完全包裹的反引号**（推荐） | 见下伪码 | 335 ✅ / 15 ✅ / 7 ✅ | 形态 C 的信息里会保留字面反引号（git log 里显示为 `` ` `` 字符，不影响可读） |
| (b) 贪婪取首个到末个反引号之间 | `re.search(r"\`(.*)\`")` | 335 ❌（无反引号则回退，同 (a)）/ 15 ✅ / 7 ❌ 仍截掉首尾的散文 | 仍会丢字，只是丢得少一点——**换了个位置继续静默** |
| (c) 只在写入侧 fail-loud，提取逻辑不动 | 编辑锁拒绝非规范 message 格 | 存量 7 条不修；今后作者被迫遵守 4% 那种写法 | **等于把人守写成机器守**，而 94% 的现存写法一夜之间全部违规 |
| (d) 提取时判定歧义即跳过该批次 | 形态 C ⇒ 不提交、留待处理 | 7 ✅（不再损坏）/ 但批次会卡住 | 把静默损坏换成静默停滞，仍需人来捞 |

**推荐 (a)**。理由：它是唯一一个**在任何输入下都不可能丢字**的选项；(b)(d) 只是把失败换个形状，(c) 让 94% 的历史写法变违规。

伪码：

```python
def _extract_commit_message(message_cell: str) -> str:
    text = message_cell.strip()
    if text.count("`") == 2 and text.startswith("`") and text.endswith("`"):
        text = text[1:-1].strip()          # 规则 1：剥去完全包裹的一层
    return text                             # 规则 2：其余一律整格原文
```

⚠️ **`text.count("\`") == 2` 这一条不能省**：只判首尾是反引号会让 `` `a` 和 `b` `` 这种（首尾恰好都是反引号、中间还有两个）被误剥成 `a\` 和 \`b`。

## 决策点 2：提取结果为空时怎么办？

- **(a) fail-loud：拒绝提交该批次，保留其待处理态，日志写明批次号与原因**（推荐）
- (b) 回退到一个固定兜底信息（如 `docs(队列): 批次 <id> 落库`）
- (c) 照常 `git commit -m ""`

**推荐 (a)**。`git commit -m ""` 本就会被 git 拒绝（空信息），(c) 等于让整轮 sweep 抛异常；(b) 会造出一条"看起来正常但不含任何信息"的 commit——**那正是本变更要根除的失败形态，不能亲手再造一个**。(a) 让批次留在待处理态，下一轮仍会被捞起，人补完 message 即自愈。

## 决策点 3：要不要同时在写入侧加一道形态守卫？

- **(a) 不加**（推荐）
- (b) 加：`append-row`/`edit-row` 写 §二 时校验 message 格形态

**推荐 (a)**。决策点 1(a) 生效后，**任何写法都能正确提取** ⇒ 再加一道"必须怎么写"的守卫，是在没有失败面的地方立新规矩，与 one-in-one-out 的方向相反（本包本来就是要**退休**一条人守，不是换一条）。且写入侧已有 `batch-registration-precheck` 在守文件清单列，职责边界清楚。

## 决策点 4：历史那 11 条被截断的 commit 要不要追改？

- **(a) 不追改，只登记**（推荐）
- (b) `git rebase`/`filter-repo` 重写历史信息

**推荐 (a)**。那些 commit 已在 `master` 且已 push；重写历史与本项目「PR 一律 ff-only、不强 push、不 rebase 已推送历史」的既定纪律直接冲突，且会让所有 worktree 与他人本地副本一起失效。**可追溯性的补法是补一份书面留痕，不是伪造一段更好看的历史**——存量清单已落在队列 `#398` ⑹ 与 `1-转型规划/0-全景路线图/CI长期红-逐job根因取证-2026-09-06.md`。

## 决策点 5：退休那条人守时，SKILL.md 那行怎么改？

- **(a) 只把「不得裸反引号」缩到 message 列之外，改写为一行指针**（推荐）
- (b) 整行三条禁令一起删

**推荐 (a)**。同一行的另两条（路径不得速记「同上」、清单内不得裸竖线）守的是**文件清单列**，与本变更无关且仍然有效；(b) 会顺手退休两条没被证伪的守卫——**规则退休制退的是"被违反 3 次的那一条"，不是它的邻居**。

## 影响面与回归边界

- **只改一个纯函数的返回值语义**，不碰批次取活顺序、销行、push/对齐。
- 现存单测里没有任何一条针对 `_extract_commit_message`（已 grep 确认 0 命中）⇒ 本包新增的用例是该函数的**首套**测试，不存在"改语义打挂旧断言"的面。
- `_resolve_batch_files()`（文件清单列）同样用反引号，但语义完全不同（那是**多个**路径片段，本来就该逐个取）——**刻意不合并、不共用工具函数**，两者对"反引号意味着什么"的答案相反，共享代码会诱导后来者把逻辑也合并掉（同 `env_anchor` 与 `bootstrap` 刻意不共享常量的先例）。

## 不做的事（Non-Goals）

- 不改 message 该写什么内容的尺度（那是人的判断，不是机制的事）。
- 不追改历史 commit（决策点 4）。
- 不在写入侧加形态守卫（决策点 3）。
- 不动 `#398` 第 ⑸ 处（`_strike_off_rows()` 不检查 `release` 返回码）——那是另一件事，另行立项。
