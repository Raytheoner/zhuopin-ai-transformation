## Purpose

跨桌任务队列 §二"待 commit 批次"新增"预登记"状态形态，把批次登记的可靠锚点从"收工时补登记"移到"认领时"，使 session 中途失联时已完成的工作仍留有可追溯记录，不再是无主孤儿，也不再连带阻塞与之无关的其它批次。

## ADDED Requirements

### Requirement: 认领即预登记
任何 Cowork/CC session 在认领跨桌任务队列.md §一"任务看板"中的一项任务、且即将开始改动代码或文档等实质工作之前，SHALL 在 §二"待 commit 批次"登记一行预登记批次，先于任何实质改动发生。

#### Scenario: 认领后立即预登记
- **WHEN** 一个 session 把 §一 某任务行的状态从"待领"改为"在办"并登记触碰区
- **THEN** 同一动作序列内（实质改动开始之前），该 session 在 §二 新增一行预登记批次，batch_id 关联该任务编号或"域+日期"

#### Scenario: 未预登记不得开始实质改动
- **WHEN** 一个 session 已将任务状态改为"在办"，但尚未在 §二 登记预登记批次行
- **THEN** 该 session 不 SHALL 开始任何文件的实质改动（读取、探索、只读取证不受此约束）

### Requirement: 预登记批次的内容与状态标识
预登记批次行 SHALL 包含 batch_id、预期改动的文件或目录前缀集合（允许保守估计，不要求认领时即精确到具体文件）、可为占位文案的 commit message，其状态列 SHALL 使用不含"待"字样的标识文本（如"在办（预登记，收工时精确化）"），以确保它在被精确化之前不会被自动化处理机制误当作可处理的待处理批次。

#### Scenario: 预登记批次状态不触发自动处理
- **WHEN** 一个预登记批次行的状态列为"在办（预登记，收工时精确化）"
- **THEN** 依赖"状态列含待字样"判据的批次处理机制（如落库 sweep）SHALL NOT 将该行纳入可处理批次范围

#### Scenario: 文件清单允许保守估计
- **WHEN** 一个 session 在任务探索阶段尚无法精确预判会改动哪些具体文件，只能确定大致的场景目录或功能范围
- **THEN** 该 session 可以在预登记批次的文件清单中填写目录前缀或范围性描述，不因"无法精确列出文件"而放弃预登记

### Requirement: 收工时精确化
session 收工时，SHALL 回到其预登记批次行，将文件清单精确化为实际发生改动的文件、将 commit message 替换为真实描述改动内容的文案、并将状态列改为不再含"预登记"标识、可被批次处理机制正常识别为待处理的状态。

#### Scenario: 正常收工精确化
- **WHEN** 一个 session 完成实质工作准备收工，且其预登记批次行仍处于"在办（预登记，收工时精确化）"状态
- **THEN** 该 session SHALL 将该行的文件清单更新为实际改动文件、commit message 更新为真实描述、状态列更新为批次处理机制可识别的待处理状态

#### Scenario: 精确化后不产生重复批次行
- **WHEN** 一个 session 对其预登记批次行执行精确化
- **THEN** 精确化 SHALL 是对同一行的原地更新，不 SHALL 在 §二 新增第二行来描述同一次任务的改动

### Requirement: 陈旧预登记批次的可发现性
预登记批次行若在超过约定阈值的时长内仍未被精确化（对应 session 失联、中断或长期未完成），SHALL 被某种机制检测并使人可见，不 SHALL 保持"存在于队列文件但无人知晓其陈旧状态"这一沉默失效形态。

#### Scenario: 超过阈值的预登记批次被检测
- **WHEN** 一行预登记批次行自登记起经过的时长超过约定的陈旧阈值，且状态仍为"在办（预登记，收工时精确化）"
- **THEN** 检测机制 SHALL 产生一条对人可见的提示（如队列对账审计报告、webhook 告警或等价的可见留痕），指出该行 batch_id、登记时长、原认领方

#### Scenario: 陈旧预登记批次不被静默复用或覆盖
- **WHEN** 一行预登记批次被检测为陈旧
- **THEN** 处理该陈旧批次（重新认领、转人工核实、或其它处置）SHALL 是显式动作，不 SHALL 被后续 session 静默覆盖或删除该行而不留处置记录
