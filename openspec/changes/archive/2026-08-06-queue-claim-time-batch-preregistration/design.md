## Context

跨桌任务队列.md 是 Cowork 总线/域专线与 CC 建造两侧任务流转的唯一载体（协议〇全文）。协议〇.1 要求"认领先于动手"，协议〇.3 要求"收工必写"，但两者之间存在一段"实质工作期间"完全不落任何 §二 批次记录——批次登记是收工时才发生的动作。session 是回合制的：只有在被给到一个回合（用户消息/工具调用轮次）时才能执行动作；一旦人转去开下一个任务、或客户端被重启/中断，该 session 不会再拿到任何回合，"收工登记"这个本该发生的动作就永远不会发生。

2026-08-04 队列 #236 的真实取证：一条 session 已完成对 4 个真实文件的改动，因 Claude Desktop 同日重启而失联，这 4 个文件此后没有任何批次行认领它们，成为"孤儿"；更严重的是，当时的 sweep 实现里"任一脏文件不属于任何批次声明即整轮 return 0"（已由同批次 #238 修复为按批次隔离），这 4 个孤儿连带挡住了 20 个本已正确声明、彼此毫无关系的批次。#238 解决的是"孤儿存在时不应伤及无辜"，本变更解决的是"孤儿从何而来"——把批次登记的可靠锚点从"收工"（不保证发生）移到"认领"（发生在实质工作之前，此时 session 一定还活着、一定还有回合）。

详见 proposal.md - Why。

## Goals / Non-Goals

**Goals：**
- 把"批次登记"从"收工时的单次动作"改为"认领时登记预期集合 + 收工时精确化"的两阶段动作，使中途失联的 session 也留下可追溯记录。
- 让"预登记但未精确化"这一中间状态本身可被发现（不新增一个新的沉默失效点）。
- 不改变 sweep 现有批次解析/处理逻辑（`_parse_section_two`/`_resolve_batch_files`/`_classify_section_two_rows` 均不变）——预登记批次靠状态列不含"待"字样天然被现有判据排除在处理范围之外，零代码改动即可与 #238 的批次隔离共存。

**Non-Goals：**
- 不解决"session 失联后，谁来接手处理陈旧预登记批次"这一具体人力分配问题——本变更只负责让陈旧预登记批次"被看见"，处理方式（重新认领/转人工核实）留给发现者按当时情境判断。
- 不改变 §二 表格本身的列结构（批次/文件清单/建议 message/状态四列不变），预登记只是"状态"列的一种新取值 + 一次两阶段写入流程，不新增列。
- 不追溯性处理本变更生效前已经发生、已经沉默失效的孤儿文件案例（那些由 #236 取证登记的具体行处理，不属本变更范围）。

## Decisions

### 决策点 1：预登记文件清单的粒度

**推荐：选项 (a) 允许目录前缀/范围性描述，不要求精确到具体文件。**

- **(a) 粗粒度（推荐）**——认领时只需写清任务涉及的场景目录、功能范围或"预计触碰"的文件前缀（例如"`4-数字员工/采购部/SC8-.../` 全部改动"），不要求预判每个具体文件。**代价**：sweep 现有的 `_resolve_batch_files` 按反引号片段做后缀/精确匹配，粗粒度声明（如整段目录描述而非反引号包裹的具体路径）在精确化之前本来就不会被 sweep 处理（状态列本就不含"待"），故粗粒度声明不会造成 sweep 误判——**唯一代价是这份粗粒度声明本身不精确，供人核实时信息量较低，但仍远优于"完全没有记录"**。
- **(b) 细粒度**——认领时即要求列出预期改动的具体文件（反引号包裹、供 sweep 未来可解析的格式）。**代价**：探索性任务（如"排查为什么某功能异常"）在认领阶段往往无法预判会改哪些文件，强制细粒度会导致认领动作被拖慢，或者被迫写一个不准确的清单——**这与"陈旧预登记批次核实"的初衷相悖：不准确的清单反而误导核实方**。

**默认项**：若无人回应本决策点，按 (a) 执行——已是本 design 的既定推荐，理由：#236 的真实故障案例里，四个孤儿文件所属 session 的任务本身就是探索性质（跟进信答复+口径梳理），细粒度要求在认领时不可行。

### 决策点 2：陈旧预登记批次的检测与处理路径

**推荐：选项 (a) 纳入既有值周巡检对账审计（skill `zhuopin-queue-audit`），不新建独立 webhook 告警通道。**

- **(a) 纳入既有值周巡检（推荐）**——值周巡检开跑前已执行的 `zhuopin-queue-audit` 对账审计新增一项检查："在办（预登记，收工时精确化）"状态且登记时长超过阈值（建议 **24 小时**——覆盖"跨天但当日应收工"的正常场景，同时不至于让"预登记后几小时内自然收工"的健康路径被误报）的行，列入《本周计划》或独立提示段。**代价**：值周巡检是每周一次，若失联发生在周初，最长可能要接近一周才被巡检发现——**比不上独立 webhook 及时，但零新增基础设施，且与 #236(2) 孤儿脏文件告警（sweep 每小时，已实现）形成互补：孤儿脏文件告警覆盖"文件已经脏了"这一物理层信号，值周巡检覆盖"队列记录本身陈旧"这一逻辑层信号，两者信号来源不同、不重复**。
- **(b) 新建独立 webhook 告警（同 #236(2) 范式，每小时或每日检测一次）**——需要一个新的检测脚本+状态持久化文件+webhook 通道（可复用 `_load_webhook_url`/`_send_wecom_markdown` 现成基础设施，改动量不大）。**代价**：多一个需要维护的独立检测点；且陈旧预登记批次的"处理紧迫性"通常不如孤儿脏文件（后者已经产生真实的未提交改动风险），每小时检测的必要性存疑。

**默认项**：若无人回应本决策点，按 (a) 执行——改动量最小，且已有互补信号来源（#236(2)）覆盖更紧迫的物理层风险。

**🔴 验收硬要求（Shao Peishen 2026-08-05 审批时补充，非建议）**：选 (a) 落地时，`zhuopin-queue-audit` skill 源码与本 design 均须**明确写清**陈旧检测在值周巡检整体流程中的**具体位置**（如"排在对账审计之后、生成《本周计划》之前"）与**触发判据**（如"状态列为『在办（预登记，收工时精确化）』且登记时长 ≥24 小时"的精确匹配逻辑，含状态文案变化时如何仍能识别）——不得只写"新增一项检查"就视为完成。理由：#219／#204 的病灶正是"规则成文但缺具体挂载点/触发条件，实际无载体执行"，本次验收明确排除同类失败。此要求同步写入 tasks.md 任务 4.1。

### 决策点 3：预登记步骤的执行方式——纯协议约定 vs 工具化

**推荐：选项 (a) 先纯协议约定（改协议〇.1/〇.3 文本），暂不工具化编辑锁工具，待观察一段时间后视摩擦程度再评估是否补工具化。**

- **(a) 纯协议约定（推荐，先行）**——只改协议文本，要求 CC/Cowork 在认领时手动登记预登记批次行（沿用现有编辑锁 `acquire`/`release` 流程改队列文件）。**代价**：依赖执行者自觉遵守，CLAUDE.md 已明确记录"人守规则"历史失败率较高（"规则退休制"专门讨论此问题）——**但本决策点的默认项设计已考虑这一点：若本条纪律在观察期内被违反达到 CLAUDE.md"规则退休制"的阈值（3 次），则触发升级为选项 (b) 工具化，不需要重新走一次 design 审**（该升级路径已写入 tasks.md 的验收标准）。
- **(b) 工具化（编辑锁 `acquire` 新增预登记能力）**——`工具-共享文档编辑锁.py` 的 `acquire` 命令新增可选参数（如 `--preregister-batch <batch_id> <预期文件集合>`），在获取锁的同一原子操作内顺带写入预登记批次行，不依赖执行者额外记住"改队列文件"这一步。**代价**：改动范围更大（编辑锁工具本身的功能扩展+对应单测），且"认领"这个动作会变重——决策点 4 讨论的锁竞争问题在 (b) 下影响更直接（认领本身就要抢锁，抢不到会直接阻塞认领，而非只阻塞登记）。

**默认项**：若无人回应本决策点，按 (a) 执行——遵循"先跑通最小验证，再规模化"节奏（全局偏好），且已内置"3 次违反即升级工具化"的退出路径，不会无限期停留在人守状态。

### 决策点 4：预登记与协议〇.7 编辑锁的交互

**推荐：选项 (a) 预登记步骤经过编辑锁保护，抢不到锁时降级为"先记入域接力文件⏳队列更新待补节，回补时再精确登记"（与协议〇.7 现有降级路径完全一致，不新增另一套语义）。**

- **(a) 经编辑锁保护、抢不到锁时按既有降级路径处理（推荐）**——预登记本质上也是"改队列文件"的一种，天然应遵守协议〇.7；抢不到锁时的降级路径已经存在（协议〇.7 原文："返回非 0（占用中）不得继续改本文件，把要登记的内容先写进自己的域接力文件、注明'队列更新待补'"），**不需要为预登记再发明一套新语义，只需明确"预登记内容"也适用这条既有降级路径**。**代价**：若锁被长时间占用，认领后的一段时间内该任务确实"暂时没有预登记记录"（记在域接力文件里而非队列里）——但协议〇.7 本身对本地文件锁的陈旧判定是 30 分钟自动可接管，且 #197 已用互斥标记文件堵住了"两边都读到无锁"的竞态，实际抢锁失败的窗口很窄。
- **(b) 不经编辑锁保护，直接尝试写入，冲突时靠人工事后修复**——绕开锁保护写队列文件，正是协议〇.7 建立之初要根治的"静默覆盖"问题（2026-07-23 两次撞号事故的直接成因）。**明确不推荐**：这会让预登记机制本身重新引入它试图解决的同一类风险（认领记录被并发写入覆盖）。

**默认项**：若无人回应本决策点，按 (a) 执行——与协议〇.7 现有降级路径完全一致，零新增复杂度，且是四个决策点里风险最明确的一个（(b) 明确不推荐）。

## Risks / Trade-offs

- **[风险] 预登记增加认领动作的步骤数，可能被执行者视为"多此一举"而跳过** → 缓解：决策点 3 选 (a) 时先观察真实违反频率，达到"规则退休制"阈值（3 次）才升级为工具化强制；不预先假设人一定会跳过。
- **[风险] 粗粒度文件清单（决策点 1 选 a）在精确化前信息量有限，陈旧检测发现时可能仍难以判断具体改了什么** → 缓解：这是"有总比没有好"的权衡——粗粒度清单至少能定位到"谁认领了、大致范围是什么"，比 #236 故障案例里"完全没有任何记录"已经是质的提升；后续若观察到粗粒度清单确实不够用，可在协议文本里补充"建议至少写明场景目录"这类软性指引，不必现在就锁定细粒度。
- **[风险] 值周巡检（决策点 2 选 a）检测周期为一周，失联发生在周初时发现延迟较长** → 缓解：与已实现的 #236(2) 孤儿脏文件告警（每小时，物理层信号）形成互补——多数真实场景里，失联 session 已产生的实际文件改动会先触发孤儿脏文件告警（3 小时阈值），值周巡检的"逻辑层记录陈旧"检测是第二道网，不是唯一防线。
- **[风险] 协议文本改写后，两份 skill 源码（`zhuopin-queue-audit`/`zhuopin-kickoff-prompt`）与已安装版之间可能出现"仓库内已更新、已安装版未同步"的滞后窗口** → 缓解：沿用队列 #185 已建立的既有惯例（仓库源码更新+已安装版待 Cowork `save_skill` 同步，两者滞后已知且有登记机制），不是本变更独有的新风险。
