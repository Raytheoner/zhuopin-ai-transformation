# sweep-editlock-status-keyword-anchoring Proposal

## Why

`工具-落库sweep.py::_classify_section_two_rows` 与 `工具-共享文档编辑锁.py::_validate_release_structure`（④断言门槛）都用"关键词是否出现在状态列文本任意位置"来做判定——前者判"待处理" vs "已完成"，后者判"P0/P1 定级 + 未核实字样是否同时出现"。这类子串扫描把"状态列描述判据本身"（引用、复述、讨论这条规则）与"状态列正在断言的当前结论"混为一谈。

2026-08-05 真实事故（队列 #248 自身取证）：§二 批次 `B-0805_124propose设计交付` 的状态列回填 `✅ 已完成` 时，说明文字里引用了 sweep 判据原文（那句"既不含 ✅ 也不含〔表示尚未处理的单字〕"），该单字落在状态列内即被判为可取活——sweep 取活该批、执行一次提交（`a4f6ba3`）、把状态列覆写为标准回写句，原核实说明连同 commit hash 一并丢失（已复原，零业务影响）。这是同族第三次：⑴ #164 裸竖线致列数偏离；⑵ #225 校验④初版按整行扫描 P0/P1＋"未核"字样，把两条正在讨论这条规则的行自己拦下，当日已收窄为只查状态列；⑶ 本次证明"只查状态列"仍不够——按 CLAUDE.md §5 规则退休制，同一"人守"条目被违反 3 次即须机制化或删除。

本变更包起草期间的历史行核对（见 design.md「历史兼容核对」）额外发现：队列 §一 #221 行的状态列**当前就带着**未加引号保护的 `P1` 定级标记与被引号包裹的"未做的核实"字样（该行讲述的是它自己如何被"未做的核实如实登记"这条纪律救回的正面案例）——若这一行在编辑锁 ④ 断言门槛的现行代码生效后被再次编辑，会被误判为违规而拒绝 release。这不是假设风险，是已经存在于生产队列文件里、只等下一次编辑触发的真实定时炸弹，进一步佐证"两处判据必须同批修，且不能只满足于'查状态列'这一层收窄"。

## What Changes

- **sweep `_classify_section_two_rows`**：判据从"状态列整体是否含'✅'/'待'子串"改为"状态列去除前导 `*`、空白后的**开头片段**是什么"——开头为 `✅` 判已完成（跳过）；开头为"待"判待处理；两者皆非判模糊状态（记日志，不纳入本轮处理）。不再扫描开头之后的任何文本。
- **编辑锁 `_validate_release_structure` ④ 断言门槛**：扫描状态列前先剔除被中文引号（`「...」`/`『...』`）包裹的片段，只对剩余（未加引号保护）的文本做 P0/P1 定级 token + "未核"/"未做的核实"字样的共现检测。
- 两处修法**原理相同、实现不同**——都遵循"只依据代表'当前生效判断'的文本做匹配，排除引用/复述/历史存档类文本"这一原则，但两个检测点的文本形状不同（sweep 状态列是短符号前缀 + 简短标签，编辑锁状态列是多分句长叙述），导致"只看开头"这个具体规则对 sweep 成立、对编辑锁不成立（编辑锁的真实断言可能出现在长文本的任何分句里，不止开头）；design.md「决策点 2」完整记录了为什么不能把 sweep 的修法原样复制到编辑锁。
- **BREAKING**：无。两处修法都只收窄误判范围，不改变"真正待处理的批次仍被取活""真正未核实的 P0/P1 断言仍被拦截"这两条核心行为——已用当前生产队列文件的全部现存行验证（§二 12 行、§一 61 行），新旧判据结果仅 1 处分歧（#221，且新判据结果与人工判断一致，详见 design.md）。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？** 两处：① "引号包裹＝引用/讨论，非引号＝当前断言"这一区分，依赖本项目既有的中文引号书写惯例（「」/『』在队列文件里 339/9 次均衡出现，是稳定惯例，但不是任何文档正式约定的规范），不是从第一性原理推导；② "状态列开头片段代表当前结论"同样是靠现存行**实测**（§二 12 行 100% 以 `✅`/`待处理` 开头）反推出的惯例，非成文规范——若未来书写习惯漂移（如开头不再是符号/关键字），"模糊状态"分支会兜底记日志，但不会自动纠正书写习惯本身。
2. **由谁显性化？** 环境保障线（Cowork，负责取证、判据设计与本变更包 design.md）+ CC 建造车间（负责两处代码实现与单测）；仲裁人＝Shao Peishen（本变更包 design.md 须经其审核批准方可 `/opsx:apply`，且本次触碰的是提交与队列写入两处咽喉件，须独立 session、不得与任何批同车，见派单件 `1-转型规划/0-全景路线图/开场prompt-【CC】C批-248-判据锚定状态列开头-交接.md` §〇）。
3. **用什么方法提取？** 历史真实案例反推——#248 是 sweep 侧的真实已发生事故（有 commit hash `a4f6ba3` 为证）；#221 是本变更包起草期间**新发现**的编辑锁侧潜在同族案例（尚未真实触发，因该行内容写于编辑锁 ④ 检查代码落地之前，属"历史行不追溯"的窗口内，但下一次编辑即会触发）。判据设计参照同族已落地的收窄先例（#225 从"整行扫描"收窄到"只查状态列"），本次是该收窄路径的下一步。不涉及 LLM 判断，不适用"AI 起草·专家批改"类方法。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：本变更为**跨项目治理机制**（sweep + 编辑锁均是全项目共用的工具类模块），非独立业务场景，不适用四档"对客交付"口径；套用最接近的档位描述＝**档1 mock 验证**（design 审通过、代码与单测完成，但尚未经过至少一次真实 sweep 取活链路 + 至少一次真实编辑锁 release 链路的端到端验证）。
- **晋下一档的条件**：晋**档2 真实数据跑通**——① 登记一个真实测试批次，跑一次真实（非 `--dry-run`）sweep，确认"状态列含判据关键词但不在开头"时不被误取活、"真正待处理"时仍被正常取活；② 构造一个含引号包裹"未做的核实"字样 + 引号外游离 P0/P1 定级的测试 §一 行，走一次真实 `release`，确认不再被误拦截、且真正未加引号保护的共现仍被正确拦截；③ 现存 §一/§二 全部行按新判据重判一遍的核对结果（本 propose 阶段已完成一次分析性核对，apply 阶段需固化为可重复运行的单测）。
- **价值指标**（风险型）：消除"状态列描述性文字提及判据关键词即触发误判"这一类误判——基线＝2026-08-05 #248 真实事故（1 次误取活+内容丢失）+ #221 潜在事故（1 次编辑锁误拦截，尚未真实发生但已确认会发生），目标＝两处判据均只对"状态列自身当前断言"生效，不对引用/复述/历史存档类文本生效。
- **LLM 判据黄金集**：不适用（本变更不含 LLM 运行时判断，纯字符串匹配逻辑）。
