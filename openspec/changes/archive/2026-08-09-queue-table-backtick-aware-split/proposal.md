# queue-table-backtick-aware-split Proposal

## Why

队列 #314① 调查坐实：跨桌任务队列.md 的表格切列在本项目 4 处独立实现（`工具-共享文档编辑锁.py::_table_data_rows`／`工具-队列查询.py::_table_data_rows`／`工具-落库sweep.py::_parse_section_one`/`_parse_section_two`）里一律做朴素 `str.split("|")`，对 Markdown 表格规范允许的"反引号内的竖线视为字面量、不算列分隔符"这一约定完全无感知。#313 行的真实破损（`git grep` 正则交替符 `` `from zhuopin_platform|import zhuopin_platform` `` 里的 `|` 被当作列分隔符，行被撑破、触碰区与日期两列被吞）正是这一类失效的实例——本该被理解为"一个反引号片段里的字面竖线"，却被解析器当成了列边界。

`queue_table.has_bare_pipe`/`column_count_ok` 目前的权威口径是"反引号包裹不豁免"（`queue-table-shared-parser` spec 既有 Requirement，2026-08-09 #306 落地），即刻意要求裸竖线一律被当成撑列的风险，不论是否反引号包裹——这在"检测风险"这一用途上是对的（本项目历史上确实发生过反引号包裹竖线撑列的真实事故），但在"如何切列"这一更基础的问题上，让 4 处消费者继续对反引号视而不见，意味着"叙述中提及一个含竖线的正则/命令片段"这种完全合理的写法，一旦出现就必然撑坏当前这一行——这不是"该被检测拦下的风险"，是"解析器本身的能力缺口"，两者需要区分开：检测裸竖线该不该拒绝写入，是一回事；解析既有正文时该不该把反引号内的竖线当列分隔符，是另一回事。

## What Changes

- **新增反引号感知切列函数** `queue_table.split_row_cells(line: str) -> list[str] | None`：识别反引号跨度（`` `...` ``），反引号内的 `|` 不作为列分隔符；行不以 `|` 开头时返回 `None`（不断言必须以 `|` 结尾——沿用 #314① 已验证的教训：一行的收尾若被截断，仍应进入切列结果交列数校验去发现，而不是在切分这一步就静默丢弃）。
- **列数不变式收进解析入口**：新增 `queue_table.parse_section_rows(section_text: str, section: str) -> list[RowParseResult]`（`RowParseResult` 含原始行文本／切出的单元格／`column_count_ok` 布尔结果），把"每行应有几列"的校验从"消费者各自决定要不要调用 `column_count_ok`"收进解析入口本身——凡经这个新入口读到的行，列数是否正确已经是返回结果的一部分，不再要求每个消费者自己记得去查。
- **`has_bare_pipe` 语义不变**：仍是"反引号包裹不豁免"（继续服务"这个字段值能不能写入"这一判断），本变更只新增切列能力，不改这个函数——两者服务不同问题，不合并。
- **4 处消费者迁移**（`工具-共享文档编辑锁.py`／`工具-队列查询.py`／`工具-落库sweep.py` 的 `_parse_section_one`/`_parse_section_two`）：切列逻辑改为委托 `queue_table.split_row_cells`；`_table_data_rows`/`_parse_section_one` 等函数名与既有调用方签名保持不变，只替换内部实现，不改各消费者对"列数不对/行结构损坏时该静默跳过还是原样返回"这一各自既有策略（`工具-共享文档编辑锁.py` 一贯"原样返回、留给调用方判"；`工具-落库sweep.py` 一贯"静默跳过、不崩溃"——这一行为差异是各自既有的、有文档记录的设计选择，本变更不强行统一，见 design.md）。
- **BREAKING（对外行为，非 API 签名）**：此前会被误判为"列数偏移"的、反引号内含裸竖线的行，迁移后列数校验结果会变化（不再误报）——`工具-队列结构lint.py` 与 `_validate_release_structure`①列数校验对这类历史行的判定结果因此改变，属预期内的行为修正，不是新缺陷。

## Capabilities

### Modified Capabilities

- `queue-table-shared-parser`：新增"反引号感知切列"与"列数不变式收进解析入口"两条 Requirement；既有的 `has_bare_pipe`/`escape_bare_pipe`/`column_count_ok` 三条 Requirement 不变。

## Impact

- **受影响代码**：`5-平台底座/zhuopin_platform/zhuopin_platform/shared_tools/queue_table.py`（新增两个函数）；`0-学习与工具/{工具-共享文档编辑锁.py,工具-队列查询.py,工具-落库sweep.py}`（切列实现改为委托，签名不变）；`0-学习与工具/工具-队列结构lint.py`（复用编辑锁的 `_table_data_rows`，随其自动获得新能力，预期不需改动，需验证）。
- **受影响测试**：上述文件各自既有测试套件（含队列 #314① 新增的、基于 `git show 298c152` 真实历史行的回归用例——那批用例断言"该行会被列数校验命中"，迁移后仍应成立，只是命中原因从"行尾被吞"变为"列数不对"两种子情形都需覆盖）；`zhuopin_platform` 新增 `queue_table.py` 单测覆盖反引号跨度的边界情形（反引号未闭合、反引号内多个竖线、反引号跨越整行等）。
- **受影响文档**：`queue-table-shared-parser` spec 增补两条 Requirement；本变更包 design.md 记录"是否放宽 `append-row` 对反引号包裹竖线的拒绝"这一 Open Question。
- **红线核对**：mock 先行——不适用（纯文本解析工具，非业务场景）；audit 留痕——不适用；OEM 隔离——不适用；L2 人工确认门禁——不适用；ISO 26262——不适用（非车规安全相关代码）。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？** "反引号内的竖线该不该算列分隔符"此前从未被显式定义过——4 处消费者的作者各自默认"不需要考虑这个问题"（朴素 split 是唯一实现过的方式），直到 #313 行的真实事故才把这条隐含假设的边界暴露出来；"列数校验该在解析入口做还是留给调用方各自决定"同样是默会假设（本项目现有 4 处实现里，编辑锁选"原样返回交调用方"、sweep 选"静默跳过"，两种假设长期并存、从未有人显式比较过取舍）。
2. **由谁显性化？** 持有人：**Claude Code**（#314 调查方与本变更起草方）；决策拍板人：**Shao Peishen**（本 design.md 的 Open Questions 待其审阅拍板）；backup：任何后续接手队列表格解析相关工作的 CC session，`queue_table.py` 模块 docstring 与本 design.md 是首选参考。
3. **用什么方法提取？** **历史案例反推**——#313 行的真实破损文本（`git show 298c152` 可复现）、#267 行同批发现的控制字符另一类破损、`queue-table-shared-parser` 既有 spec 的"反引号包裹不豁免"条款，均来自现存代码与真实生产数据逐一核实，非预先设计。不涉及 LLM 判断。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：跨项目治理机制，非独立业务场景；近似映射＝**档1 mock 验证**（模块与单测完成，4 处消费者切换完成且各自既有回归零漂移，尚未经过至少一次真实生产队列文件的完整校验场景对新实现的端到端观察）。
- **晋下一档的条件**：晋**档2 真实数据跑通**——① 4 处消费者切换后各自既有测试套件零漂移；② 对当前生产队列文件（含 #313/#267 两行真实历史破损内容，若彼时仍未修复）跑一次 4 处消费者的实际调用，确认反引号内裸竖线不再被误判为列偏移，且真正的列偏移（如 #313/#267 那种"结尾被吞"）仍被正确捕获（两者都要验证，不能只验证其中一种）。
- **价值指标**（质量型）：消除"反引号内竖线撑列"这一类失效的复发面——基线＝该失效自 #313 行触发起已致其结构损坏并阻塞正常编辑至少 5 个提交（见队列 #313/#314 行记录），目标＝同类正文（含反引号包裹的 grep/命令片段）此后不再需要人工避免在正文中使用竖线字符。
- **LLM 判据黄金集**：不适用。

## 本次退休哪一个既有守卫；若不能退，写明为何不能

**本次不退休任何既有守卫，理由如下**：列数校验（`工具-队列结构lint.py`①／`_validate_release_structure`①）覆盖的失效面是"任何原因导致的列数不对"，本变更只是缩小了该守卫今后会真正命中的来源之一（反引号包裹的裸竖线不再造成列偏移），并不缩小守卫本身需要覆盖的范围——非反引号包裹的裸竖线（真正的输入错误）、#313/#267 那种"结尾内容被外部工具吞掉"的破损，仍然需要同一个列数校验去捕获，守卫不能退。

**可能的顺带缩窄，留作 Open Question、不强制**：`append-row` 子命令当前对"含竖线的字段值一律拒绝写入，不论是否反引号包裹"（`queue-table-shared-parser` spec"反引号包裹不豁免"条款），其原始理由是"现有解析对反引号无感知，口径需与其一致"——本变更落地后这一理由本身不再成立（解析器已能正确处理反引号内的竖线），是否要相应放宽 `append-row` 的拒绝范围（只拒绝真正裸露的竖线），是design.md 的一个决策点，默认建议"暂不放宽"（append-row 的"一律拒绝"是更保守、更不容易踩坑的策略，放宽的收益主要是书写便利性，不放宽不影响本变更的核心目标）。
