## Goals / Non-Goals

**Goals：**
- 给出拆分后两份物理文件各自承载什么、放在哪、如何互相引用的完整拓扑。
- 收拢方案件 §4.4.4 实测发现的"队列文件路径在 5 处 Python + 1 处 JS 各自硬编码"这一隐藏硬前置，且一并纳入 #313/#314 之后仍遗留的 sweep 自身 `QUEUE_REL`（第 4 处）。

## Decisions

### 决策点 0：本设计的产出时点与 apply 执行时点是否应该分离

**背景**：方案件 §4.4.3（三阶段渐进表）与 #308 design.md 决策点 2 支撑论证三均明确：

| 阶段 | 动作 | 可逆性 |
|---|---|---|
| 阶段 1（已完成，2026-08-09） | 域字段单文件 | ✅ 完全可逆 |
| 阶段 2（观察期 ≥2 周） | 域字段真实使用中跑一段，统计争议行与改域次数 | ✅ 可逆 |
| 阶段 3（＝本变更 apply，视阶段 2 结果决定做不做） | 机械切分成两份文件 | 🔴 不可逆 |

方案件原文："阶段 3 就能拿到四项收益里价值最高的那项……全部不可逆成本都在阶段 3……若阶段 2 观察下来注意力失衡已被域字段解决，不做阶段 3 也是合格结局，不是半途而废"。**本变更领取时（2026-08-10）距阶段 1 落地仅 1 天，观察期未满。**

**⇒ 本决策点要回答的不是"拆不拆"（那已经是方案件与 #308 的既有结论：值得做，但阶段 3 可能不做），而是：propose＋design 这份纸面产出本身，是否也要等观察期结束才能开始？**

**推荐：不等，design 现在做；`/opsx:apply` 等观察期结束再做。** 三条理由：

1. **design 是可逆的纸面工作，不消耗方案件想保护的"不可逆成本"**——方案件真正想延后的是"物理切分文件"这一不可逆动作，不是"想清楚切分要怎么做"这一思考过程本身。二者混为一谈会导致观察期结束那天才从零开始设计，反而拖长了从"数据支持切分"到"切分真正落地"之间的窗口。
2. **队列 #315 行本身已由 Shao Peishen 在 2026-08-09 拍板"立项"**——"立项"在本项目惯例中（对照方案件自身"三项决策全批"的措辞、以及 #308 走的"propose+design 先行、apply 待批"两步式）自然读作"可以开始 propose+design"，而非"可以跳过方案件自己写明的观察期直接执行"。**本决策点的价值是把这一区分显式写下来，避免"design 已获批"被误读为"可以 apply"这一常见的阶段混淆**（本项目已有先例：`CLAUDE.md` §5"决策路由"条反复强调"批准了 A 不等于 B 也获批"）。
3. **观察期的真正价值是收集数据判断阶段 3 是否有必要**，而 design 阶段产出的恰恰是"阶段 3 具体怎么做"的方案，两者是正交的工作——design 定稿不会让观察期提前结束，也不会让"阶段 3 可以不做"这个出口失效；design.md 完稿后，若观察期结束时数据显示域字段已经够用，本变更包直接可以标记为"设计完成、不 apply"归档，成本损失有限。

**被否候选**：

- **候选：本变更连 design 都不做，等观察期结束再重新走 propose**→ 否决：会造成"数据支持切分"那一刻起，还要再等一次完整的 propose+design 审核周期才能真正开始切分，延长了本应最短化的"决策→执行"窗口；且 2026-08-10 当日新发现的幽灵副本问题（决策点 5）不应搁置到 2 周后才开始设计。
- **候选：跳过观察期，design 获批后立即 apply**→ 否决：直接违反方案件与 #308 design.md 均已白纸黑字写下的可逆性论证，且没有任何新证据能推翻"域字段单独可能已经够用"这一假设——过早 apply 会让"阶段 3 可以不做"这一方案件明确保留的出口形同虚设。**若 Shao Peishen 判断有紧急理由需要跳过观察期，须在本决策点显式给出理由并覆盖默认项**（见下）。

**默认项**：若不答，按"design 现在定稿，`/opsx:apply` 不早于 2026-08-23（2026-08-09 + 14 天）且须附观察期内收集到的真实数据（WIP 计数准确性、看板/值周巡检按域分列后的实际使用反馈、是否仍观察到注意力被机制类行淹没）"执行。

### 决策点 1：两份物理文件的命名、目录与章节归属

**命名**：`跨桌任务队列-机制环境.md`（承载协议〇、§一"机"域行、§二"机"域批次、§三、§四、编号高水位线声明）／`跨桌任务队列-业务场景.md`（承载 §一"业"域行、§二"业"域批次）。均落 `1-转型规划/0-全景路线图/`（原文件同目录，不新增子目录）。

**命名依据**：符合文档治理 R4 命名四律（主题-对象-日期-事项、不含会变数字）——"机制环境"/"业务场景"对应方案件与协议〇.9 措施 C 已使用的"机制类/业务类"分类措辞，不发明新术语。

**为何协议〇/§三/§四/高水位线归"机制环境"文件、不独立成第三份文件**：

1. 协议〇 本身就是**机制类正文**（管辖锁/取号/清扫等机制行为），归入机制环境文件是语义上最贴切的位置，不是"随便找个地方放"。
2. §三（口径冻结标）、§四（需拍板事项）体量均为个位数至十位数量级（2026-08-10 实测 §四 数据行个位数、§三 近乎空），独立成第三份文件的读取侧改造成本（消费者要多扫一份文件）远高于其体量带来的"注意力拥挤"问题——不符合方案件"值得做的是治理与注意力解耦"这一立论前提（体量小的东西不构成注意力负担，拆它没有收益）。
3. §四 本身混装机制/业务两类拍板事项（如"是否跳过观察期"这类本设计决策点 0 式的问题就可能出现在§四），拆分需要域字段而 §四 从未纳入 #308 域字段范围（#308 design.md Non-Goals 已明确原因：体量太小不值得），维持其单文件形态是对该既有决策的延续，不重新论证。

**跨文件指针**：业务场景文件顶部 frontmatter 后新增一句固定格式指针："协议〇/§三/§四/编号高水位线见《跨桌任务队列-机制环境.md》"，避免读者在业务文件里找不到协议正文时误以为协议不适用于自己。

**被否候选**：

- **候选：三份文件（机制/业务/共享）**→ 否决，理由见上第 2 点；且新增第三份文件会让"两份"这一方案件反复使用的心智模型（如 §4.1 表"两条独立落库流水"）失真，读取侧消费者需要遍历的文件数从 1→2 变成 1→3，改造成本不成比例。
- **候选：按现有文件名加后缀（如 `跨桌任务队列-一.md`/`跨桌任务队列-二.md`）**→ 否决：数字后缀不能自解释内容（读者要额外记住"一"对应机制还是业务），违反 R4"文件名不含会变数字"的精神类比（虽非严格意义上的"会变数字"，但同样是不透明标识符）；且历史上编号"一/二/三/四"已被队列内部章节占用，复用为文件名后缀会造成"文件-一"与"章节一"两层"一"的歧义。

**默认项**：若不答，按上述两文件命名与章节归属执行。

### 决策点 3：§二 批次的域判定——物理文件位置即域，不新增字段

**背景**：方案件 §4.1 表把"批次流"列为"能真解耦的项"之一（"§二 混装两类 → 两条独立落库流水"），但方案件与 #308 design.md 均未展开"§二 批次如何被判定归属哪个域"这一具体机制——#308 design.md Non-Goals 明确排除了"改 §二 状态语义"，但拆分后 §二 本身需要一个归属信号，这是 §308 未覆盖、本变更必须补的空白。

**推荐：不新增字段，物理文件位置本身即域信号。**

- **写侧**：`append-row --section 二` 时新增 `--queue 机制|业务`（或等价的 `--domain` 复用，见决策点 7）参数决定写入哪份物理文件；不显式声明时，MUST 拒绝写入并要求调用方明确（不静默默认某一域，同 #308 决策点 1 已确立的"非静默降级"原则）。
- **读侧**：sweep/值周巡检等消费者读取 §二 批次时，天然只从其正在遍历的那份文件里读到属于该域的批次，无需额外判断字段。
- **理由**：这正是 #308 design.md 决策点 2 已经论证过的"字段与位置冗余，但该冗余有用"的反向应用——对 §二 而言，域字段这一层冗余的**收益低于成本**（§二 批次是短生命周期的，落库后很快被 sweep 处理为 commit，不像 §一 那样需要长期跨文件迁移与交叉校验），故本变更选择只用位置、不加字段，是"够用就好、不为尚未观察到的收益预先造判据"这一项目一贯精神（同 #308 design.md 决策点 8 对 E2 的处理态度）的延续。

**被否候选**：

- **候选：§二 也加 `[D:]` 字段，与物理文件位置双重校验**→ 否决（本次不做，非永久否决）：§二 批次生命周期短（登记→sweep 落库→销行/迁归档，通常数小时至一天内完成），"字段与位置不一致"这一风险窗口远小于 §一（§一 行可能长期存在、跨会话迁移）；若拆分后实测发现 §二 批次确实频繁被错误路由到另一份文件、造成实质困扰，再按"历史案例反推"惯例补字段，不预先造。
- **候选：§二 批次统一只写机制环境文件（不拆）**→ 否决：违反方案件 §4.1 明确把"批次流"列为可解耦项的既有结论，且业务场景批次继续与机制批次混装会让业务线读 §二 时仍然承受同样的注意力问题，与本变更主旨相悖。

**默认项**：若不答，按"物理文件位置即域，写侧显式声明写入哪份文件，不新增 `[D:]` 字段"执行。

### 决策点 4：权威路径解析收拢（接手方案件 §4.4.4 与 #306 遗留缺口）

**背景**：方案件 §4.4.4 实测队列文件路径在 **5 处 Python 硬编码 + 1 处 JS**：`工具-落库sweep.py::QUEUE_REL`／`工具-共享文档编辑锁.py::DEFAULT_TARGET`／`工具-队列查询.py::DEFAULT_TARGET`／`工具-文档台账生成.py::QUEUE_PATH`／`wecom-aibot-service/aibot_service/repo_paths.py::DEFAULT_QUEUE_RELATIVE_PATH`（机器人侧三消费者已通过此处集中，本族唯一做对的一处）／Cowork artifact JS（不可 import Python，登记为不可消除的第二实现）。

**现状更新（2026-08-10 本变更复核）**：#313 已把编辑锁／队列查询／文档台账 3 处 `QUEUE_PATH_REL` 收拢进 `queue_table.py`（见该模块现有 `QUEUE_PATH_REL` 常量与文档字符串"队列 #313"段）；`工具-落库sweep.py` 自身的 `QUEUE_REL` **明确登记为第 4 处、当时刻意未纳入 #313 范围**（该模块文档字符串原话："#313 派单件明确点名的是前 3 处，本次未纳入，如实登记见队列 #313 回写"）；`工具-队列结构lint.py` 经既有 `importlib` 复用编辑锁常量，不在硬编码路径清单内。**⇒ 待收拢的路径解析共 3 类：① sweep 自身 `QUEUE_REL`（唯一遗留的第 4 处 Python 硬编码）；② 双文件扩展本身（现有 `QUEUE_PATH_REL` 是单一路径，需扩展为双路径 + 归属判定）；③ JS 第二实现的双文件读取协同。**

**消费者切换（沿用 #308 design.md 决策点 4 已确立的"影子模式"过渡范式，不重复论证该范式本身的必要性）**：

1. `工具-落库sweep.py`——自身 `QUEUE_REL` 改为 `queue_table.iter_queue_paths()`，起跑段扫描、`_find_stale_pending_rows`、告警生命周期（#308 子项 D）等所有当前"扫描单一队列文件"的逻辑改为对两份文件分别扫描后合并结果（保持告警去重与节流状态按"文件+行"复合 key，不因物理文件增多而重复告警同一逻辑行）。
2. `工具-共享文档编辑锁.py`——`DEFAULT_TARGET` 改为按 `--domain` 参数路由（决策点 3/7），`acquire`/`release`/`append-row` 均需要知道"这次操作的是哪份文件"；不带 `--domain` 且目标不是显式 `--file` 覆盖时，fail-loud 要求调用方明确（同决策点 3 的非静默降级原则）。
3. `工具-队列查询.py`——`--row` 查询时若不确定行在哪份文件，先查机制环境文件、未命中再查业务场景文件（编号唯一，两份文件不会有同编号冲突，见决策点 2）；`--field all` 输出需附带"命中于：<文件名>"，避免歧义。
4. `工具-文档台账生成.py`——遍历 `iter_queue_paths()`，两份文件各自的状态头/列数自检独立跑。
5. `工具-队列结构lint.py`——经既有 `importlib` 复用编辑锁常量的机制不变，只需编辑锁自身切换后自动带出。
6. `wecom-aibot-service/aibot_service/repo_paths.py`／`queue_appender.py`——`DEFAULT_QUEUE_RELATIVE_PATH` 改为双常量 + 域路由；机器人来件默认写业务场景文件（沿用方案件 §6.5 建议 4"机器人 100% 盲写业务队列，机制行只由巡逻升格时创建"这一已被方案件全盘采纳的结论，本变更直接复用不重新论证）。
7. **Cowork artifact `zhuopin-project-status`（JS）**——继续"接受并登记为不可消除的第二实现"（同 #308 design.md 决策点 4 已定的处理原则），本变更在 apply 阶段需给 Cowork 侧一份可直接复制的"读双文件并按 `[D:]` 合并展示"伪代码/正则片段，具体协同时机由 Cowork 侧决定，本仓库 CC 会话无法直接控制该 artifact。

**协议〇/§三/§四正文的"本文件"自称问题**（方案件 §4.4.4 读取侧改造清单第 5 项）：决策点 1 已把这四者固定在机制环境文件内，故协议〇正文的"本文件"可以改为"本文件（机制环境文件）"或保持不变但在业务场景文件顶部指针里说明——**推荐保持协议〇正文不变、只在业务场景文件顶部加指针**（决策点 1 已定），避免协议正文因"支持双重读者"而变得啰嗦，代价是业务场景文件的读者需要多跳转一次，可接受（协议正文本就是低频阅读内容，不是高频扫描对象）。

**被否候选**：

- **候选：本次一并收拢 sweep 的 `QUEUE_REL`（第 4 处）而不等它成为双文件扩展的一部分**→ 不否决，**合并处理**：既然双文件扩展本身就要求 sweep 切换读取逻辑，第 4 处遗留顺带一次性解决，不需要为它单独走一轮 #313 式的"收拢"变更，属本决策点范围内的自然产物，不算额外范围蔓延。
- **候选：JS 侧改为读 Python 产出的静态 JSON 快照**→ 否决，理由与 #308 design.md 决策点 4 完全相同（新增一层构建/同步管线，违反措施 B"能不新建机制就不新建"精神），本变更不重新论证。

**默认项**：若不答，按上述 `resolve_queue_path`/`iter_queue_paths` 方案 + 七类消费者切换清单执行，第 4 处 sweep 遗留路径随双文件扩展一并解决。

### 决策点 5：幽灵副本检测（队列 #315 子项⑥并入项，2026-08-10 当日实证）

**背景**：2026-08-10 #321 那个 CC session 在自身 worktree 内用通用 Edit 工具按本地路径改队列文件，而编辑锁 CLI（`acquire`/`append-row`/`release`）通过 `git rev-parse --git-common-dir` 恒定解析到主工作区的那一份——两者是两个不同的物理文件。该 session 三次 `append-row` 全部写进了主工作区（正确），但它同时**误以为**自己在检查的 worktree 本地副本才是权威、误判写入失败；对 #321 状态字段的第一次编辑落进了 worktree 本地孤立副本，成为一份谁也看不到的幽灵。**队列拆分后，权威物理文件从 1 份变 2 份，同一失效模式的风险面同步翻倍**（每份文件都可能各自产生一份 worktree 本地幽灵副本）。

**⇒ 拆分设计必须回答 #315 原文已提出的三问**：

**⑴ 拆分后两份队列各自的权威物理路径如何解析？**

**推荐：继续 `--git-common-dir` 恒定指主工作区，不允许 worktree 本地。** 理由：这是 2026-07-23 编辑锁已确立、`repo_paths.py`（#126）同源复用过的既有范式，其价值（"所有 worktree 的锁互相可见"）在双文件场景下同样成立且更重要——若允许 worktree 本地解析，两份文件在不同 worktree 里会各自产生互不可见的锁与内容分支，比现状单文件的幽灵副本问题更难排查。

**⑵ 通用编辑工具（Edit）与锁 CLI 必须解析到同一份，否则幽灵副本会在拆分后翻倍——但这一点无法靠代码强制。**

Edit 类通用文件编辑工具由调用它的 session/agent 决定操作哪个路径，不感知 `git-common-dir` 语义，代码层面无法拦截"session 传了一个 worktree 本地路径给 Edit"这一操作本身。**⇒ 本决策点的方案是检测与提示，不是强制拦截**：

- **`acquire` 输出改为打印绝对路径**（当前只回显相对路径/文件名，见 `工具-共享文档编辑锁.py` 现有输出格式），使操作方能一眼核对"我接下来要用 Edit 打开的路径，和 CLI 刚刚告诉我的路径，是不是同一个绝对路径"。
- **新增"本地影子副本漂移检测"**：`acquire`（及 `status`）执行时，额外检查 `<当前 cwd 所在 worktree 根>/<QUEUE_MECHANISM_PATH_REL 或 QUEUE_BUSINESS_PATH_REL>` 这一路径是否存在、且物理上不同于 CLI 解析出的权威路径（`os.path.samefile` 判定，两者路径字符串不同不代表物理不同——需处理"当前就在主工作区，两条路径本就相同"这一正常情形，不误报）；若存在**且内容不一致**（simple 哈希/mtime 比较），打印醒目警告：

  ```
  ⚠️ 检测到本地影子副本：<worktree 本地路径> 与权威文件 <绝对路径> 内容不一致。
     你的编辑器/Edit 工具若正在操作前者，改动不会被本工具看到，也不会被
     release 校验，极可能造成幽灵副本（同 2026-08-10 #321 事故）。
     请改为直接编辑绝对路径指向的文件，或改用 append-row 子命令写入。
  ```

  该检测**只读，不自动删除/覆盖任何一方**——2026-08-10 #321 事故的正确处理方式是"发现→session 自行判断哪份是权威、手工核实后清理"，代码不应替人做这一判断（同本项目一贯的"止血不硬解"哲学，见 `sweep-ff-sync-batch-reorder` design.md 决策点 2 已确立的立场）。

**⑶ 若保留"恒定指主工作区"，须给出让 worktree 内 session 能察觉自己正在改错文件的机制，而非靠人记得——即上述检测本身就是答案，写死为 `acquire`/`status` 的固定输出内容之一，不依赖任何人主动想起去检查。**

**被否候选**：

- **候选：允许 worktree 本地覆盖（新增环境变量如 `WECOM_AIBOT_REPO_ROOT` 同款覆盖口）**→ 否决：`repo_paths.py` 的覆盖口是给"独立 clone/异常环境"兜底的最后手段，不是常规工作流的一部分；若把它包装成"worktree 内可选择本地模式"，等于把 #321 事故的成因（worktree 本地与主工作区两份物理文件并存）从"意外"变成"官方支持的模式"，方向相反。
- **候选：在 Edit 类工具层面强制拦截**→ 不可行，已在本决策点开头说明：通用编辑工具不感知本项目的 git-common-dir 语义，这是工具边界，不是本变更能解决的范围。

**默认项**：若不答，按"`acquire`/`status` 新增绝对路径打印 + 本地影子副本漂移检测（只读警告，不自动处理）"执行。

### 决策点 6：迁移策略——一次性机械切分，双写窗口与回滚点

**继承方案件 §4.4.3 已比较过的结论**："阶段 3 若真做，选'一次性机械切分'而非'存量不动、新行分流'：后者会导致同一个域的行散在两份文件里，读取侧必须两边都读、且无法信任任何一边的完整性——比一次性切分更糟。有了域字段之后，一次性切分是零判断的机械操作。"本决策点不重新论证选择，只补充执行细节。

**执行顺序（apply 阶段，本次不做，仅定方案）**：

1. **代码先行**：决策点 4/5/7 的路径解析、幽灵副本检测、域路由代码与单测先落地，此时队列文件仍是单一物理文件（`跨桌任务队列.md`），新代码对"仍是单文件"的现状保持向后兼容（`resolve_queue_path`/`iter_queue_paths` 在双文件尚未产生前，两个域都指向同一份旧文件，等价于现状）——同 #308 design.md Migration Plan 第 1 步"代码先行，字段后填"的同一范式。
2. **一次性机械切分**：按 `[D:]` 字段把 §一 现存全部数据行、按物理文件位置把 §二 现存全部数据行，一次性拆入两份新文件；协议〇/§三/§四/高水位线声明整体移入机制环境文件；旧文件 `跨桌任务队列.md` **不删除，改为一份纯指针文件**（"本文件已拆分为……，见……"），保留一段时间（决定于决策点 0 的观察期结束后再定具体保留时长，不在本设计预先武断），避免遗留的外部引用（历史归档件/CLAUDE.md 旧链接）404。
3. **消费者逐一切换**（决策点 4 已列七类，顺序沿用 #308 已验证过的"写侧优先→高风险读侧→CI→低风险读侧→跨仓库→仓库外"排序惯例，不重新设计一套新顺序）。
4. **仓库外载体**（值周巡检、拆件巡逻定时任务真身，Cowork artifact JS）——方案件 §4.4.4 已标注"须经 `update_scheduled_task` 改，不可直接 Edit"且"阶段 3 启动时须跑 `python 0-学习与工具/工具-仓库外载体扫描.py`"，本决策点直接复用该既有纪律，不重新设计扫描方式。

**回滚点**：一次性切分是文件系统操作（新建两份文件、旧文件转指针），`git revert` 单个 commit 即可完全回退（旧文件内容仍在 git 历史里，两份新文件若已被后续行追加内容，回滚需要人工把切分后新增的行合并回旧文件——**这是本次机械切分方案唯一的不完全可逆点，须在 apply 阶段的 commit 信息里显著标注"此 commit 之后新增的行，回滚需人工核对"**，不假装"随时可无损回滚"）。

**默认项**：若不答，按上述四步顺序 + git revert 回滚点声明执行。

### 决策点 7：四类消费者兼容性验证方案（本次只定方案，不执行）

**背景**：#315 原文期望产出③"四类消费者兼容性实测——编辑锁 `acquire`／`release`、`工具-落库sweep.py`、值周巡检、拆件巡逻，每类都要在两份队列上各跑一次真实场景，不接受只测新队列"。本决策点把"怎么测"具体化，实测本身留给 apply 阶段。

| 消费者 | 验证场景 | 通过标准 |
|---|---|---|
| 编辑锁 `acquire`/`release` | 分别对机制环境文件与业务场景文件各跑一次真实 `acquire --reserve --domain <对应域> → 编辑 → release` | 两次均返回预期编号、锁文件路径一致（同一把锁保护两份文件还是各自独立锁，见下方待定项）、`release` 校验（①-⑩ 全部既有检查）在两份文件上均正确触发 |
| `工具-落库sweep.py` | 分别在两份文件各造一条"待处理"§二 批次，触发 sweep | 两条批次均被正确落库，起跑段扫描/告警生命周期在两份文件上均正常工作，不因文件数增多而漏扫或重复告警 |
| 值周巡检 | 生成一期《本周计划》 | 报告正确合并展示两份文件的机制类/业务类统计，不遗漏任一文件、不重复计数 |
| 拆件巡逻 | 触发一次真实企微来件升格为正式任务 | 升格结果正确路由到业务场景文件（沿用方案件 §6.5 建议 4"机器人 100% 盲写业务队列"），并入审核仍正常触发 |

**待定项（本决策点不预先拍板，留 apply 阶段实测后再定）**：两份文件是否共用同一把编辑锁（`.editlock` 单一文件保护两份队列，串行化跨域写入）还是各自独立锁（机制/业务可并行写入，收益是方案件 §4.1 表"文件锁"项列出的真实解耦收益）。**推荐倾向独立锁**（否则拆分就拿不到方案件自己列出的"两把独立锁"这项收益），但两份文件间仍有共享内容（协议〇/§三/§四/高水位线只在机制环境文件），独立锁是否会造成"改高水位线时业务场景文件的写入者感知不到"这一新竞态，需要 apply 阶段真实验证后才能下结论，本设计如实标注为待验证项而非假装已解决。

## Risks / Trade-offs

- **[风险] 决策点 0 的观察期约束可能被后续 session 忽略、直接 apply**→ 缓解：本 design.md 与 proposal.md 均已把观察期约束写入 Decisions（而非 Open Questions，遵循 #308 design.md 已确立的"待拍板项放 Decisions 不放 Open Questions"惯例），apply 前须回读本节确认时点条件；队列 #315 状态列本身也会记录本次 design 产出与"待观察期"这一结论。
- **[风险] 决策点 6 的一次性机械切分若在协议〇/§三/§四归属判断（决策点 1）上出现遗漏，读取侧会出现"协议正文在业务文件里找不到"的困惑**→ 缓解：业务场景文件顶部固定指针（决策点 1 已定），且 apply 阶段的验证清单（决策点 7）应加一项"人工核对业务场景文件顶部指针可点击/可定位"。
- **[风险] 决策点 5 的幽灵副本检测依赖"当前 cwd 所在 worktree"这一判断，若 session 从非常规路径（如临时目录、非 `.claude/worktrees/` 结构）运行本工具，检测可能失效**→ 接受：与 `repo_paths.py` 既有覆盖口的边界一致（"解析失败才回落现状"），不追求覆盖所有理论上可能的运行环境，只覆盖本项目实际使用的 worktree 结构。
- **[权衡] 决策点 3 选择"§二 不加域字段、只用物理文件位置"，长期看若发现物理文件位置本身也会被搞错（如误用 `append-row` 未带 `--queue`），会缺少交叉校验手段**→ 接受，已在决策点 3"被否候选"中登记为可能的后续候选，不预先造。
- **[权衡] 决策点 7 的"共用锁 vs 独立锁"待定，意味着 apply 阶段的锁机制改造范围在 design 阶段无法完全锁定**→ 接受并如实登记，proposal.md「验收与晋档条件」已注明 design 审通过≠可以 apply，apply 前还有真实验证工作。
