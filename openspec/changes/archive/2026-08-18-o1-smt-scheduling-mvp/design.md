## Context

动机与 ⓪ 步实测结论见 `proposal.md`「Why」，不重述。此处只列约束设计形状的现状：

1. **可收割的代码是 72 行两函数**，无状态、无 I/O（CSV 读取除外）、无外部依赖，纯确定性算术。**这决定了本变更的技术风险几乎为零，全部风险在口径与数据侧。**
2. **两个输入的可达性不对称**：到货日 ✅ 有真实来源（`ZpViewPurOrder/Query`／`GR/Query`／SRM `get_receive_board`，SC8 已在真实使用）；SMT 工时 🔴 既无端点、也无真实 mock 数据（CSV 46 行全为常数 7）。**「可达」与「有数据」是两件事，本设计必须让二者在结果里可分辨。**
3. **底座已有现成的档位闸**：`ZpConnector._fallback_or_failloud`（`erp_connector/connector.py:909`）已实现「real 未 opt-in → 抛 `RealEndpointNotReadyError`；real 且 opt-in → CSV ＋ 审计标 `CSV_mock` ＋ `UserWarning`；mock → CSV 回退」三态语义，`get_production_plan` 正是其消费方之一。**本场景无需自建同类机制。**
4. **同构先例是 O2**（`4-数字员工/运营部/O2-物料齐套预警/`），其 D1-D4 四条决策与本场景一一对应，可直接沿用而非重新论证。

## Goals / Non-Goals

**Goals**

- 把 supplychain `smt_scheduling` 落位为可运行、可测试、有审计留痕的 O1 场景包，达档 1。
- **让「算出来的完工日有多可信」在返回值里可见**，而不是埋在代码注释或文档里——这是本设计相对原 MVP 的唯一实质增量。
- 为晋档 2 留出零改造的切换点：端点开放后只换数据源，不动引擎。

**Non-Goals**（设计层边界，proposal 已列的范围排除不重复）

- **不做优化求解**。首版是「给定齐料日算完工日」的单向推算，不是「在多工单间分配产能」的求解问题。二者是不同的问题类别，混谈会让首版看起来像半成品的优化器，实际它是一个完整的估算器。
- **不建 Web 呈现层**，因而本变更不触发 §5「不新起端口」约束的任何落地动作（仅在场景 CLAUDE.md 记录未来路由为 `/operations/o1`）。
- **不改底座任何文件**。O1 是排程引擎的消费方 #1，rule-of-three 未触发。

## Decisions

### D1：引擎放哪 —— **场景本地，不进底座**

- **推荐 ＝ 场景本地** `o1_smt_scheduling/schedule_engine.py`。**默认项：不答即按此执行。**
- **理由**：完全复用 O2 的 D1 论证——O1 是排程引擎的**消费方 #1**，rule-of-three 未触发；且此时无第二消费方可用于校准接口形状，过早提底座会把一个 72 行函数的签名冻死在错误的抽象上。O2 当初正是先场景本地、待 SC5 成为消费方 #2 时才提升底座（2026-07-02），该路径已被验证。
- **备选**：直接进 `zhuopin_platform/agents/schedule_engine.py`。**不取**——重复代价仅 72 行，而错误抽象的代价是全项目级。

### D2：收割方式 —— **复制 ＋ 改 import，不包装、不改签名**

- **推荐 ＝ 同 O2 D2。默认项：不答即按此执行。**
- **理由**：`schedule_smt()` / `load_smt_lead_time()` 两个签名已被 supplychain 的 92 行测试覆盖并跑过；保持签名不变意味着**这 92 行测试可以原样带过来当回归网**，收割的可信度不依赖新写的测试。改签名则这层保障归零。
- **备选**：借收割顺手重构（如把 CSV 读取抽成 provider）。**不取**——收割与重构混在一次提交里，一旦回归失败无法归因是收割错了还是重构错了。重构留到有第二消费方时。

### D3 🔴：自动化等级 —— **L1（推荐）还是 L2？此处存在两份权威件的分歧，请裁**

- **分歧事实**：全景规划 §2.1.3 O1 行写 `自动化等级: L2（AI 生成排程方案，计划员审核调整）`；本批 opener B 节写「L1 内部看板、无 L2 门禁」。**两者都是被授权的口径来源，本 session 不自行择一。**
- **推荐 ＝ (a) 首版记 L1，并在场景 CLAUDE.md 显式写明「全景规划所载 L2 定位在场景具备『排程方案下发车间』能力时生效，届时须补人工确认门禁」。默认项：不答即按 (a) 执行。**
- **理由**：§7 红线 4 的 L2 门禁清单是「采购金额>50万／新供应商／交付预测推客户」，均为**有外部后果的动作**；首版产出是一个纯计算返回值，无任何下发、推送、写回动作，**没有可供人工确认的动作对象**——此时标 L2 会造出一个空门禁，属于「写了但底层没有」的形态（同 2026-08-18 OEM 隔离层那条的教训）。
- **(b) 备选：首版即记 L2 并预留空门禁壳**。代价＝多一层当前无实义的确认逻辑，且空门禁长期不触发会退化为无人维护的死码。
- **⚠️ 无论选哪个，都须回写全景规划或 opener 之一使二者一致**——该回写属 Cowork 归口，本变更只输出结论、不改规划件。

### D4 🔴：占位工时表怎么处置 —— **随表声明（推荐）／剔除数据只留料号／不收割**

- **事实**：46 行 `smt_lead_days` 全为常数 7，是占位值不是实测值。
- **推荐 ＝ (a) 收割整表，但在 CSV 文件头加显式声明块**（「本表工时值全为占位常数 7，非真实工时，禁止用于任何对外承诺或产能测算」），且 agent 返回值中携带 `lead_time_is_placeholder=True` 标记。**默认项：不答即按 (a) 执行。**
- **理由**：这正是 O2 的 B6 红线（「无库存快照时不静默、不假装 available=0，而是显式标注 `missing_snapshot=True`」）在本场景的同构应用。**占位数据的危险不在于它是占位的，而在于它看起来不像占位的**——一张有 46 个真实料号的表，读者会默认其工时列同样真实。声明写在文件里而非文档里，是因为文档不会随数据被复制走。
- **(b) 备选：只收割料号列，工时列留空**。代价＝引擎将对全部 46 个料号返回「无法排产」，档 1 连跑通都做不到，mock 验证失去意义。
- **(c) 备选：不收割该表，改用 inline 夹具**（同 O2 D4 的选择）。代价＝丢掉 46 个真实料号，而这恰是该表**唯一**的真实资产。**故本场景与 O2 在此处刻意不同构**——O2 的夹具是自造的三层 BOM，本场景的夹具含真实料号，二者性质不同。

### D5：数据源档位闸 —— **复用底座 `_fallback_or_failloud`，不自建**

- **推荐 ＝ 场景侧只负责传递档位与 opt-in 标志，fail-loud 由底座 `ZpConnector` 抛出。默认项：不答即按此执行。**
- **理由**：底座那三态语义（real 未 opt-in 抛错／real opt-in 走 CSV_mock ＋ warn ＋ 审计标记／mock 直接回退）是 design D2/Q3 已审过的既有设计，且 `get_production_plan` 本身就是其消费方。场景侧另建一套等价机制，等于制造第二实现——**同一语义两处实现必然漂移**，这正是队列 #308 所根治的那类问题。
- **备选**：场景自建档位判断。**不取**，理由同上。

### D6：夹具形态 —— **CSV（工时表）＋ inline dict（到货日）混合**

- **推荐 ＝ 工时表沿用收割来的 CSV（保真实料号，见 D4）；物料到货日用 inline Python dict 夹具（自包含、不依赖外部文件、手工核对结果写注释，同 O2 D4）。默认项：不答即按此执行。**
- **理由**：两个输入的资产性质不同——工时表的价值在真实料号，必须留文件；到货日在原 MVP 里本就由调用方传入、无对应真实文件，造一个 CSV 反而凭空增加一个需要维护的夹具文件。

### D7：测试策略 —— **原 92 行测试原样带过来 ＋ 新增边界用例**

- **推荐**：① supplychain `test_smt_scheduling.py` 的 8 个用例原样迁入（仅改 import 路径），作为收割保真的回归网；② 新增覆盖本变更新增行为的用例——跨周末不顺延、工时表非法行跳过、占位标记透传、real 档位 fail-loud、部分产品无法排产时的分项返回。**默认项：不答即按此执行。**
- **⚠️ 一处须在 apply 时留意**：原测试中 `test_all_products_loaded` 断言 `len(lt) == 46`。该断言绑死了行数，**若 apply 时按 D4(a) 在 CSV 头部加声明块，须确认声明块以注释形式存在且不被 `csv.DictReader` 读成数据行**，否则该断言会以一种看似无关的方式失败。这是「改判据前必须也对照既有测试」那条教训的直接应用。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| **首版看起来像「假 AI」**——一次 `max()` 加一次 `timedelta`，无任何智能成分，与场景名「智能优化」落差极大 | 在场景 CLAUDE.md 与 proposal 中**如实写明首版是完工日估算器而非优化器**，不修饰。落差是真实的，掩饰只会把它推迟到验收时爆发。**这也是 D3 建议记 L1 的旁证——L2 会暗示存在一个值得计划员审核的「方案」，而首版产出只是一个日期。** |
| **占位工时被误当真实工时使用** | D4(a) 三重防护：CSV 文件头声明 ＋ 返回值 `lead_time_is_placeholder` 标记 ＋ 场景 CLAUDE.md 红线段 |
| **端点长期不开放，O1 永久停在档 1** | 已由 Shao Peishen 2026-08-18 拍 Q11(a) 明示接受。**本设计不额外做 CSV 桥接**——若日后改走桥接，必须同批建源头断供检测（FI2 2026-08-17 补丁为范式） |
| **SMT 工时知识资产无人认领**（持有人/backup 均待点名） | proposal 已提出补登 §一.2 台账；本变更交付时输出待登记行交 Cowork。**⚠️ 这是本场景晋档 2 的真实卡点之一，且它卡在「点名」而非「技术」上** |
| **原 92 行测试迁入后掩盖收割缺陷** | 这些测试当初是与实现同批写的，可能与实现同源错误。故 D7 ② 的新增用例**刻意从 spec 反推而非从实现反推**（跨周末不顺延这条即由 spec 而来，原测试只在 docstring 提了一句「不跳周末」却无对应断言） |

## Open Questions

1. **正式版是否需跳周末/节假日、以及节假日日历从哪来**。档 1 用自然日已由业务方确认可接受；正式口径待 PMC 工作坊。届时若改为工作日，`schedule_smt` 增加一个日历参数即可，引擎结构不变。

3. **完工日推算是否需回流校准**（实际完工 vs 推算完工的偏差月度回流，同链 D 的 L5 范式）。属晋档 3 后的话题。
