# o1-smt-scheduling-mvp Proposal

## Why

O1 生产排程智能优化是 S1 筑基期场景（全景规划 §2.1.3 运营部 O1，排期 2026-09），N3 拍板要求 **8/31 前建目录并出 propose**。supplychain 试验田留有一个 MVP 阶段验证过的 `smt_scheduling` 模块，但它是首轮收割中**唯一被跳过**的引擎（收割策略 §7 第 3 项明写「〔O1 生产排程未在本轮收割，待后续〕」，O2/SC3/SC5 当时均已收割），至今既不在平台底座、也不在任何场景包内。本变更把它收割落位，并**如实划定首版能力边界**——O1 的核心输入「生产计划/工单」在 real 模式下取不到，故首版只到档 1。

**⓪ 步实测结论（Shao Peishen 2026-08-18 拍 Q12(c) 要求，不预设结论）**：已通读 `supplychain/src/agents/smt_scheduling.py`（72 行）、`tests/test_smt_scheduling.py`（92 行）、`scripts/spike_mvp_t5_smt.py`（141 行）、`data/mock/smt_lead_time.csv`（46 行）。**判定＝收割，不从零重写**，理由与代价如下：

- **它确实覆盖「到货＋工时→完工日」**：`schedule_smt()` ＝ `max(所有物料到货日) + timedelta(SMT工时天数)`，与 opener 描述逐字相符。
- **但可收割的代码资产极薄**——2 个函数、一次 `max()` 加一次 `timedelta`，无容量约束、无产线/设备分配、无优先级排序、无换线损耗，**它是一个「完工日估算器」，不是「排程优化器」**。真正值得收割的是三样**非代码**资产：① 业务方已确认接受的简化口径（按自然日、不跳周末节假日）；② 46 个真实成品料号清单；③ `spike_mvp_t5_smt.py` 探查坐实的**否定结论**——携客云 SRM 无任何外协/排产/工单端点。这三样从零重写会全部丢失，并把一个已被业务方拍过的简化问题重新打开。
- 收割方式沿用 O2 决策 D2：**复制＋改 import，不包装、不改函数签名**。

🔴 **⓪ 步另发现一处 opener 与前置总表均未记载的事实，直接改变本变更的目标口径**：`smt_lead_time.csv` 的 46 行 `smt_lead_days` **全部等于 7**（已用脚本统计确认，无一例外）。即所谓「SMT 工时对照表」**只有真实料号、没有真实工时**，是一张常数占位表。⇒ **引擎的两个输入里，「到货日」有真实来源，「工时」既无真实端点、也无真实 mock 数据**，它 100% 停留在计划员脑子里。这使得「前置总表无 O1 行 ＝ 无外部知识前置」这一读法**在实质上不成立**——正确的读法是**该前置从未被登记**。本变更据此提出补登 §一.2 知识资产台账（见下）。

## What Changes

- **新建场景工程** `4-数字员工/运营部/O1-生产排程智能优化/`（pyproject + 包 + tests/conftest.py 三件套，conftest 照抄 O2 同款 worktree 路径引导，队列 #300）。
- **收割** `supplychain/src/agents/smt_scheduling.py` → 场景本地 `o1_smt_scheduling/schedule_engine.py`：保留 `schedule_smt()` / `load_smt_lead_time()` 两个签名不变，import 改指平台底座。
- **收割** `smt_lead_time.csv` 为 mock 夹具，**并在文件头显式标注「本表 46 行工时值全为占位常数 7，非真实工时，禁止用于任何对外承诺或产能测算」**——不静默沿用一张看起来像真实数据的占位表（同 O2 B6「不静默、不假装」红线）。
- **新增场景入口** `o1_smt_scheduling/agent.py::run_smt_schedule()`：薄包装，接平台 `AuditLogger`（`scenario="O1"`），`audit_logger` 可选（None ＝ 静默，单测不依赖 sink），同 O2 D3。
- **新增数据源档位闸**：`real` 模式下取生产计划即 **fail-loud**，复用底座 `ZpConnector._fallback_or_failloud` 既有语义，**不新增回退旁路、不静默降级到 mock**。
- **补登前置**：在《跨场景前置数据与知识库任务总表》§一.2 知识资产台账新增 O1 行（SMT 工时与排程约束），四要素（持有人/backup/提取方法/形态）见下。
- **不做**（首版明确排除，避免范围蔓延）：设备状态、人员排班、最优化求解、紧急插单重排、策略模拟、Web 呈现。这五项是全景规划 O1 描述里的能力，**首版一项都不做**，理由见「验收与晋档条件」。

**无 BREAKING**：本变更不修改任何既有模块的对外语义，纯新增场景包。

## Capabilities

### New Capabilities

- `o1-smt-schedule-engine`：SMT 完工日计算引擎——给定物料到货日集合与工时对照表，产出最早完工日；输入不完整时返回 `None` 而非猜测。
- `o1-smt-schedule-agent`：O1 场景入口——编排引擎调用、写平台审计留痕、按数据源档位对 real 模式 fail-loud。

### Modified Capabilities

（无。本变更不改变任何既有 spec 的行为要求。`platform-data-connectors` 的 `get_production_plan` fail-loud 语义是**被复用**，不是被修改。）

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

**1. 本流程哪些判断是人脑默会经验？**

🔴 **本场景的默会程度高于首轮预估**——工时表是常数占位表，等于该知识**一条都没被显性化过**。逐条列出：

| 默会项 | 当前状态 | 现只在谁脑子里 |
|---|---|---|
| **各产品 SMT 实际工时天数** | 🔴 完全默会。CSV 46 行全填 7，无任何真实差异化数据 | 运营部 PMC / SMT 计划员 |
| **是否跳周末/节假日、跳几天** | 🟡 已有一次业务方口头确认「MVP 按自然日可接受」，但未记录是谁、何时确认，亦未确认正式版是否仍可接受 | 同上 |
| **换线/机型切换损耗**（不同产品切换频繁正是 O1 的原始痛点） | 🔴 完全默会，引擎里零体现 | 同上 |
| **紧急插单的优先级尺度**（什么算紧急、插谁的队） | 🔴 完全默会 | PMC + 运营主管 |
| **设备/人员产能上限与排班约束** | 🔴 完全默会，且无数据源 | 车间主管 |

**2. 由谁显性化？**

- **持有人**：运营部 PMC（**待点名**——运营部 AI 专员/PMC 接口人尚未在本项目点名，与销售接口人当初的情形同类）。
- **backup（双人制）**：SMT 车间主管（待点名）。
- 🔴 **本项建议立即登记进《跨场景前置数据与知识库任务总表》§一.2 知识资产台账**并纳入其「owner 单一 ＋ 双人制」纪律。**当前该表无 O1 行，属登记遗漏而非无前置**——遗漏的直接后果就是上面这张表里 4 个 🔴 至今无人认领。

**3. 用什么方法提取？**

**案例反推 ＋ AI 起草·专家批改**（三步法，§一.2 统一口径）：从 U9C/MES 历史工单的「投产日→完工日」实际间隔反推各产品真实工时草案 → PMC 45-90 分钟工作坊批改 → 判例累积升版。**⚠️ 该方法本身依赖历史工单数据，而工单端点当前不可达**（见下），故首轮工作坊排期须与端点开放绑定，不能空排。按 §二纪律「知识型前置启动前 8 周开第一轮工作坊」，若 O1 正式版仍锚 2026-09，工作坊窗口早已过——**这是一个须由 Shao Peishen 知悉的排期事实，不由本变更单方处置**。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：🔴 **档 1（mock 验证）**——mock/CSV 夹具跑通引擎，`real` 模式显式 fail-loud。依据 Shao Peishen 2026-08-18 拍 Q11(a)，**不照抄 SC2 的「首版直达档 2」**。

- **为什么只能到档 1（逐条，非保守取值）**：
  1. **生产计划/工单不可达**——`ZpConnector.get_production_plan()` 无真实端点（`erp_connector/connector.py:927` 已实测确认：「zp 无对应端点。mock→CSV 回退；real→fail-loud」），TODO 指向 U9C MO 实体 `UFIDA.U9.MO.MO.MO`（`CommonEntity/Query`，**外网 404 至今未开放**）。
  2. **工时无真实数据**——见上，CSV 全为常数 7。
  3. **SRM 侧已探明无替代来源**——`spike_mvp_t5_smt.py` 探查携客云 11 个候选外协/排产/工单端点，结论为走 CSV Fallback。

- **晋档 2（真实数据跑通）的条件**（逐条，全部满足方可）：
  1. U9C `CommonEntity/Query` 外网开放或 LAN/VPN 可达，`UFIDA.U9.MO.MO.MO` 实测可取工单（**卡 IT，非本项目可控**）；
  2. SMT 工时表由运营部 PMC 实名确认并签字存档（替换常数 7 占位表）；
  3. 「按自然日、不跳周末节假日」这条简化口径由 PMC 书面复核仍可接受，或给出正式版口径；
  4. §一.2 知识资产台账 O1 行的持有人与 backup 已点名。

- **已知代价并接受**（Shao Peishen 2026-08-18 拍 Q11(a) 时明示）：**O1 年内很可能停在档 1，对「使用线 ≥5 场景达档 3」零贡献**。**未选 CSV 桥接到准真实**，理由＝那会新增一个「人工定期投放」依赖，而 2026-08-10~08-17 刚被同一形态咬过（唐燕萍 5 个工作日零投放、无人察觉）；**若日后改走 CSV 桥接，必须同批建源头断供检测**（FI2 2026-08-17 补丁为现成范式）。

- **价值指标**（D-4 两级验收；基线由业务 Champion 启动前确认存档）：
  - **风险型（首选）**：因排程不合理导致的交付延迟工单数 / 月 —— 🔴 **基线尚不存在**，须由 PMC 在晋档 2 前确认；档 1 阶段**不申报任何价值兑现**（无真实数据即无价值，不做纸面收益）。
  - **工时型（次选）**：计划员每轮排程编制耗时 —— 同样待 PMC 确认基线。
  - 全景规划所载「设备利用率提升 15-20%」**属首版不可达指标**（首版无设备数据、无优化求解），不作为本变更验收标准。

- **LLM 判据黄金集**：**不适用**——本场景为纯确定性算术，无任何 LLM 运行时判断。若后续引入优化求解或紧急插单判定，须另行评估是否需黄金集。
