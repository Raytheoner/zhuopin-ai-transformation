## Purpose

企微智能机器人在协议〇.7 共享编辑锁被人类会话占用期间，仍需把已归档消息对应的跨桌任务队列行登记动作可靠地完成——本能力把因锁占用而无法立即写入的追加请求原样暂存，待锁释放（下一条消息到达时）按序补录，确保"消息已归档但队列行未登记"这一中间态不会永久丢失，也不会与其它类型的失败（如真实 git 推送失败）混淆处置。

## ADDED Requirements

### Requirement: 锁占用时暂存而非丢弃
机器人向跨桌任务队列追加一行时，若协议〇.7 共享编辑锁当前被占用（`QueueLockBusy`），系统 SHALL 将本次追加所需的完整参数原样暂存到独立的 JSONL 文件，MUST NOT 丢弃该请求或静默跳过；此时对应消息本体已完成归档落盘，暂存的只是"登记进队列文件＋对应 git 提交"这一后续步骤。

#### Scenario: 追加时锁被占用
- **WHEN** 机器人尝试追加一条队列行，此时编辑锁被某人类会话持有
- **THEN** 系统将本次追加参数追加写入暂存 JSONL 文件，不抛出未捕获异常，不影响本次消息归档已完成的事实

### Requirement: 按 FIFO 顺序补录，保序停止
下一条消息到达时，系统 SHALL 尝试按暂存记录的原始顺序（先到先补）依次补录；若补录到某条记录时锁仍被占用，系统 MUST 立即停止本轮补录（不跳过该条去尝试后面的记录），保持剩余暂存记录的原始顺序不变，供下次消息到达时从同一位置继续尝试。

#### Scenario: 補录中途再次遇锁忙
- **WHEN** 暂存队列中存在 3 条记录，补录第 1 条成功后，第 2 条补录时锁仍被占用
- **THEN** 系统停止本轮补录，暂存文件中保留第 2、3 条记录（不含已成功补录的第 1 条），且顺序不变

#### Scenario: 全部补录成功
- **WHEN** 补录时锁已释放，暂存队列中全部记录均可成功写入
- **THEN** 系统按原始顺序逐条补录，全部成功后暂存文件被清空（不留一个永远存在的空文件）

### Requirement: 补录成功后复用完整同步与降级路径
每条记录补录（本地追加）成功后，系统 SHALL 继续走一遍与消息刚到达时完全一致的 git 同步流程（含其既有的乐观重试、降级、告警机制），MUST NOT 为补录路径单独实现一套不同的失败处理逻辑。

#### Scenario: 补录后 git 同步失败
- **WHEN** 某条记录本地追加补录成功，但后续 git 推送遇到与消息刚到达时同样会触发降级处理的失败情形
- **THEN** 系统按与非补录路径完全一致的既有降级/告警机制处理，不因"这是补录路径"而表现不同

### Requirement: 每条记录独立获取与释放锁
补录过程中，系统 SHALL 为每条暂存记录独立构造一次锁获取，MUST NOT 在多条记录之间复用同一把已持有的锁；该行为与正常消息到达时"每次追加各自独立 acquire/release"的语义保持一致。

#### Scenario: 多条记录依次独立持锁
- **WHEN** 一轮补录连续处理 2 条暂存记录
- **THEN** 系统为第 1 条记录单独完成一次锁的获取与释放，再为第 2 条记录单独完成一次，不存在跨两条记录持有同一把锁的情形

### Requirement: 锁忙暂存与 git 失败暂存物理隔离
"编辑锁占用导致的推迟"与"git 层真实失败（如非快进冲突重试耗尽、网络错误）导致的推迟"SHALL 被记录到两个独立的物理暂存文件，MUST NOT 混用同一份暂存文件；混用会导致人工排查或自动补录机制无法区分两类失败各自的处置方式与优先级。

#### Scenario: 两类失败分别落盘
- **WHEN** 某次追加因锁占用被推迟、另一次追加因 git 推送真实失败被推迟
- **THEN** 前者记录写入锁忙专用暂存文件，后者记录写入 git 同步失败专用暂存文件，两者互不出现在对方文件中
