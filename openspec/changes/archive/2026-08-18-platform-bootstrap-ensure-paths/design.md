# platform-bootstrap-ensure-paths Design

> 🔴 **本文件是待审件**。五个决策点均已给出推荐与**默认项**（不答即按默认执行）。**本次只 propose，不 apply。**

## Context

事实基础见 proposal.md。一句话：35 份手抄引导漂成 4 种语义，A 形态（无条件 raise）在 `.51` 扁平布局下必然把入口钉死，2026-08-18 一天内两条 session 各自撞上并各自修了一遍。

两种布局是真实且都必须支持的：

| | 开发机（monorepo） | 生产机（`.51` 扁平） |
|---|---|---|
| 布局 | `<repo>/5-平台底座/zhuopin_platform` ＋ `<repo>/4-数字员工/<域>/<场景>/` | `C:/<svc>/zhuopin_platform` ＋ `C:/<svc>/app`（兄弟目录） |
| 平台底座怎么来 | N 个 worktree 平等副本，**全局 editable 指针只有一个、指向谁不确定** | `deploy-server.ps1` `pip install -e` 进该服务专属 venv，**全机唯一一份** |
| 因此引导要做什么 | **必须**前插本 worktree 的路径，压过全局指针 | **不该**做任何事，交给环境解析即可 |
| 找不到 monorepo 标记意味着 | 环境真的错了 | 正常，本就没有那层目录 |

**根因不是某个文件写错了，而是"同一段逻辑靠复制粘贴分发"**：每份副本都可以独立漂移，而没有任何机制会发现它们已经不一致。

## Goals / Non-Goals

**Goals**
- 一处定义、一处修复；新场景不可能再引入 A 形态
- 保留 `tests/conftest.py` 的 fail-loud 语义，但**由显式参数声明，而非碰巧写成 raise**
- 不引入静默失败：两条分支都走完仍不可导入时必须明确报错

**Non-Goals**
- 不改变 #300 在开发机上的既有语义（前插优先级、压过全局 editable 指针）
- 不试图消灭 stub（鸡生蛋问题无法完全消除，只能压缩到最小，见决策点 1）
- 不顺手统一 `conftest.py` 的 fail-loud（#345 行内已写明该判断，见决策点 2）
- 不在本变更包内处理 `.env` 查找逻辑（`_find_env()` 同样各处手抄、同样存在布局认知不一致，但属独立范围，见决策点 5）

## 决策点

### 决策点 1 · 鸡生蛋：`ensure_paths()` 自己怎么被 import？

引导的目的是让 `zhuopin_platform` 可导入，而函数住在 `zhuopin_platform` 里。三个选项：

- **(a) 极小 stub（推荐 ✅ 默认项）**：每个入口保留 3-5 行——向上找标记、找到就前插、然后 `from zhuopin_platform.bootstrap import ensure_paths; ensure_paths(__file__)`。
  - *得*：35 份副本的**可漂移面积**从 10-30 行压到 3-5 行且无分支；所有**判断逻辑**（何时回退、何时 raise、strict 语义）集中一处。
  - *失*：仍有 35 份副本，只是变小了。**诚实地说，这不是"消灭副本"，是"消灭副本里的判断"**——但判断才是漂移的来源，行数不是。
- **(b) 完全消灭 stub，靠 `.pth` / `sitecustomize`**：*得*：入口文件零样板。*失*：把可见的显式引导换成不可见的环境魔法，**与本项目"取证优先、不要静默"的取向冲突**，且 `.pth` 在多 worktree 下是全局的——正是 #300 要躲开的那类全局单点。**不推荐。**
- **(c) 每个场景包 `__init__.py` 里做**：*失*：CLI 入口（如 `main.py`）在包外，覆盖不全；且 `conftest.py` 早于包 import 执行。**不可行。**

**推荐 (a)。默认项：(a)。**

### 决策点 2 · `tests/conftest.py` 保不保留 fail-loud？

- **(a) 保留，用 `ensure_paths(strict=True)` 显式声明（推荐 ✅ 默认项）**：#345 行内已写明"monorepo 内 fail-loud 有价值——测试就该跑在仓库里，找不到标记说明环境真错了，此时静默回退才是隐患"。收拢的收益是**语义变成一个具名参数**，而不是 12 份各自碰巧写对。
- **(b) 统一为非 strict**：*得*：只有一种行为，最简单。*失*：**丢掉一条真实有价值的判断**，且违背 #345 行内明示。**不推荐。**

**推荐 (a)。默认项：(a)。**

### 决策点 3 · 35 处一次性全换，还是分批？

- **(a) 分两批 + 过渡期共存（推荐 ✅ 默认项）**：批一 18 个非测试入口（B/C/D 形态，行为等价，风险最低）→ 验证 → 批二 12 个 `conftest.py`。`ensure_paths()` 与内联块**向后兼容、可共存**，不要求一次性全切。
  - *理由*：一次性改 35 个文件、跨 9 个场景 + 2 个平台组件，**一旦有一处出错，回归定位成本极高**；而分批的代价只是多一次验证轮次。
- **(b) 一次性全换**：*得*：过渡期短，不存在"两种形态并存"的困惑。*失*：见上。**不推荐。**

**推荐 (a)。默认项：(a)。**

### 决策点 4 · 怎么防止新场景再抄回 A 形态？

- **(a) CI lint 硬门禁（推荐 ✅ 默认项）**：在既有 `工具-队列结构lint.py` 同款位置加一条——**新增 `.py` 若含 `for _p in (_HERE, *_HERE.parents)` 且不是 stub 形态，即 lint 违规**。
  - *理由*：**这正是本变更包退休那条人守规则时欠下的对价**——退休制要求"挂到不可绕过的咽喉上"，否则只是把一条人守换成另一条人守。SC2 的存在证明人守在这里无效。
- **(b) 只写进 CLAUDE.md 指针，不加门禁**：*失*：**等于用一条人守替换另一条人守**，SC2 的教训会重演。**不推荐。**
- **(c) 加门禁但只告警不阻断**：折中，适合过渡期；可作为 (a) 的第一阶段。

**推荐 (a)，过渡期先按 (c) 跑一轮。默认项：(a) 且过渡期按 (c)。**

### 决策点 5 · `_find_env()` 是否同批收拢？

各入口另有一段手抄的 `.env` 向上查找逻辑，**同样存在布局认知不一致**（#345 行内点名的"讽刺处"正是它：`_find_env()` 的 docstring 早写明扁平布局，同文件的引导却没照顾到）。

- **(a) 不同批，另立一行（推荐 ✅ 默认项）**：*理由*：`_find_env()` **当前没有已知的生产事故**，而本变更包已覆盖 35 个文件、跨 9 个场景；再叠一个维度会让回归面失控。**范围克制优先。**
- **(b) 同批收拢**：*得*：同族问题一次清完，且两段代码相邻、改动位置重叠。*失*：回归面翻倍，且把一个"已烧过的火"和一个"尚未烧的隐患"绑在一起，任一出问题都拖累对方。

**推荐 (a)。默认项：(a)——并在队列另立一行登记 `_find_env()` 同族收拢，避免"提了但没人接"。**

## Risks

| 风险 | 缓解 |
|---|---|
| stub 与 `ensure_paths()` 过渡期并存造成困惑 | 决策点 3 分批 + stub 形态唯一且有 lint 守（决策点 4） |
| 替换后某入口的 `sys.path` 顺序变化导致 import 到错误副本 | 每个受影响场景全量测试零漂移 + 三个 `.51` 服务真部署冒烟（验收第 4 条） |
| apply 时与 SC2（opener A2）／O1（opener B）建造 session 撞触碰区 | apply 前重新核对两场景在办状态，必要时等其收口 |
| `ensure_paths()` 自身出 bug ⇒ 影响面从 1 个文件放大到 35 个 | 这是收拢的固有代价；以四情形单测 + 分批验证对冲。**明确写在这里，不假装它不存在。** |

## Open Questions

- `zhuopin_platform` 自身的 `tests/conftest.py` 是否也走 `ensure_paths(strict=True)`？（它 import 的就是自己，语义略特殊；倾向是走，但需 apply 时实测确认）
- 是否值得让 `ensure_paths()` 返回它实际插入了哪些路径，供 `--verbose` 或审计留痕使用？（倾向：返回，成本近零，对排查这类"本地看不出来"的问题有直接价值）
