## 一、8D预填脚本设计

### 输入/输出

- **输入**：8D原文档（.docx / .pdf）
- **输出**：JSON（机器可读）+ Markdown（人可读预览）
  - 12字段提取结果（每字段附置信度HIGH/MED/LOW）
  - 脱敏建议：实体→令牌映射表（按就绪包§1.2范式）
  - 改判表：供陈忱对每字段勾选"采纳/改判"（改判原因可记录→反哺标注语料）
- **校准模式**：`--golden golden.csv` 生成字段命中率报告

### 提取策略（无LLM依赖，确定性优先）

| 字段 | 提取方式 | 置信度 |
|------|---------|:------:|
| 案例ID | header/标题正则 `8D[-\s]?\d+`、`案例.{0,4}[：:]\s*\S+` | HIGH |
| 结案日期 | 日期正则 `\d{4}[-./年]\d{1,2}[-./月]\d{1,2}` | HIGH |
| 安全相关 | 关键词：ASIL/安全相关/功能安全/ISO 26262 | HIGH |
| 不良分类 | 分类词表：设计/制程/工艺/物料/来料/使用不当/操作不当 | HIGH |
| 失效现象描述 | D2段落提取 | MED |
| 临时对策(D3) | D3段落提取 | MED |
| 纠正/预防(D5-D7) | D5/D6/D7段落聚合 | MED |
| 根本原因(D4) | D4段落提取 | MED（长文本） |
| 根因验证有效 | D7/D8 "验证有效/confirmed/已验证" 关键词 | LOW（需人工确认） |
| 关联FMEA | FMEA + 编号正则 | LOW（常缺失） |
| 关联物料/供应商 | 料号正则 + supplier关键词 | LOW（多来源） |
| 客户(令牌) | 识别后由用户映射，工具提取原始值 + 提示令牌化 | MED |

**段落检测**：识别 `D\d[:：]`、`第[一二三四五六七八]步`、`\d\.\s`、`Step\s*\d` 等格式，提取区间内容。

### 脱敏建议模块（scrubber.py）

按就绪包§1.2的6类占位范式，依次为候选实体生成令牌建议：
- 机构/客户名 → `OEM-[A/B/C]-序号`（序号按首次出现顺序，级别默认B、可配置）
- 车型/平台代号 → `某车型平台-[A/B/C]`
- 器件/位号/元件 → `电容-A`/`开关-A`/`某软件模块-A`（按类别）
- 供应商 → `供应商-[A/B]`
- 零件编号 → `料号-[A/B/C]`
- 产线/地点 → `工厂-A`/`客户端地点-A`
- 人名 → `质量工程师-A`/`计划工程师-A`

脱敏建议为**建议，不自动替换**——输出映射表（原文→建议令牌），陈忱手动确认后用工具替换。

### 校准报告（calibrate模式）

对比字段 = 12字段，对比方式：
- **精确匹配**：案例ID、结案日期、安全相关（是/否）、根因验证有效、不良分类 → 相等得分1
- **关键词覆盖**：文本字段（D2/D3/D4/D5-D7）→ 人工标注词在AI输出中的覆盖率（≥80%算命中）
- 报告：字段命中率表 + 总体命中率 + 改进建议（哪些字段最需优化）

## 二、doc_parser 架构评估（Paul须审）

### Rule-of-three 现状

| 消费方 | 场景 | 解析对象 | 状态 |
|--------|------|---------|------|
| QD-B 立项门禁 | `qd_b_gate/parser.py` | xlsx 立项书 | ✅ 已存在，场景本地 |
| **QD-A 8D预填** | `qda_prefill/doc_reader.py` | docx/pdf 8D报告 | **本次新建，场景本地** |
| 合同解析 | FI-? 或 SC-? | docx/pdf 合同 | 🔴 尚未开发 |
| RFQ 解析 | 采购部 | docx/pdf RFQ | 🔴 尚未开发 |

**当前：2/4 消费方**，rule-of-three 未触发（需要3个真实消费方才提升）。

### 评估结论（建议Paul批准）

**本次迭代**：QD-A使用场景本地的 `qda_prefill/doc_reader.py`，**不提取到平台底座**。

**接口设计原则**：`doc_reader.py` 的对外接口与预期的平台 `doc_parser` 接口保持同构，具体：
```python
# 本次场景本地（qda_prefill/doc_reader.py）
def read(path: Path) -> DocumentSections: ...

# 未来平台底座（shared_tools/doc_parser.py，触发时同接口）
def read(path: Path) -> DocumentSections: ...
```
当第3个消费方（合同/RFQ解析）出现时，`doc_reader.py` 的实现可**零改动平移**进 `shared_tools/doc_parser.py`，各消费方 `import` 路径更改一行即完成迁移。

**触发提升的判断点**：2026-10 Q2(QD-A/QD-B)启动前，若合同解析或RFQ解析已有开发需求确认 → 达到rule-of-three → 在届时 openspec change 中执行提升（不提前抽象）。

**Paul的行动项**：
- 若同意上述评估结论 → 本变更包直接执行（场景本地，doc_parser预留）
- 若认为应提前提升 → 本变更包中同步新建 `shared_tools/doc_parser.py`（会改动QD-B的import）
