## Why

**两份队列真身（机制环境／业务场景）§一 状态列长期被当"日志"使用——每次回写只追加、从不删旧段，实测最长单格 78 KB（≈3 万 tokens）。** `--digest`（队列 #441）已能"扫全池不通读真身"，但两个高频动作仍未被机制覆盖：

1. **核触碰区**——判断"这次改动会不会撞到别人正在碰的文件/函数"，此前只能对队列文件裸 `grep`/`Read`，一次命中就把 50–78 KB 的单行原文灌进上下文；
2. **行内日志无限增长**——`release` 校验族现有 ①–⑩ 十项判据均不检查单格体量，超限行只会越写越长，直到下一次 `--row`/裸读把它撑爆读者的上下文。

`.claude/rules/队列与落库.md`「读侧禁通读」条目已把这两件事写成项目口径，但落款是**"机器守…待落地，落地前本条人守"**——本包就是把这句话从人守变成机守的那一步，属于队列瘦身方案（`跨桌任务队列瘦身-方案-2026-09-04.md`）K2（行内日志外置口径的机器守）与 K3（读侧禁通读机器守）两刀的落地。

**本包不改变任何业务口径、不碰真实数据、不涉鉴权**——三处产出物的作用对象全部是"本仓库的队列协作机制自身"（查询工具的过滤能力、release 校验族的体量上限、Read/Grep/Bash 三个工具对队列文件的准入）。

## What Changes

### 新增：ⓗ1 `工具-队列查询.py --grep <关键词>`

`--digest` 摘要基础上新增按"任务"列／"触碰区"列关键词过滤（不区分大小写、两列命中都算数），联合两份真身逐份解析后合并、`--file` 可指归档件；仍只输出摘要行，命中触碰区列（任务列摘要看不出命中理由）时附加提示片段。`--grep` 须配合 `--digest` 使用，误用（配 `--row`）或空白关键词均 fail-loud（exit 1），不静默忽略或静默当作"不过滤"。

### 新增：ⓗ3 编辑锁 `release` 校验族第 ⑪ 项——行长上限

`_validate_release_structure` 新增判据：§一 状态列／§四 事项列单格 UTF-8 字节数 >4096（4 KB）即命中，只对本次持锁期间 touched 的行生效（历史超限行不追溯，同⑨ WIP 上限"不能把来关行的 session 也挡在门外"同构）。**2026-09-11 前只告警（打印行号与字节，不阻断 release），此后阻断**；判定用本机本地日期字符串字典序比较，到点自动切换、不需要再改代码。逃生阀：单元格内写明 `行长豁免：<理由>`（理由非空才生效，两种模式下都放行）。

### 新增：ⓗ2 `PreToolUse(Read|Grep|Bash)` 队列读侧门禁

`0-学习与工具/hooks/hooks-pretooluse-queue-read-guard.ps1`：目标命中两份队列真身或 `跨桌任务队列-归档-*.md` 即 `exit 2` 拒绝，提示改用 `--digest`/`--grep`/`--row`。`Read`/`Grep` 只判结构化目标字段（`file_path`/`path`）是否精确命中，不做目录归属之类的模糊启发式；`Bash` 无结构化路径字段，唯一例外对命令文本做正则——须同时命中"读命令名"（`Get-Content`/`cat`/`grep`/`Select-String`）与"目标文件名"两个条件才算。白名单：命令行本身在调用编辑锁／队列查询／sweep／队列结构 lint 四个机制工具之一时整条放行（治本包自身撞车：`--digest --grep <关键词> --file <归档件>` 字面同时含"grep"与归档文件名）。

### 修改：项目 `.claude/settings.json`

新增 `PreToolUse` 数组的第二个条目（matcher `Read|Grep|Bash`），与既有 `Edit|Write|MultiEdit` 条目并列，见 tasks §4 与本文档「不在本包 scope」。🔴 **该文件命中 `~/.claude/protected-paths.json` 的 `*/.claude/settings.json`（`mode: block`）⇒ 必须由 Shao Peishen 或 Cowork 瘦身线人工执行**，与 `cc-hooks-p3`／`project-hooks-write-time-sentinels` 两包完全同形，不绕。

### BREAKING

**是，且仅限 ⓗ2 与 ⓗ3（2026-09-11 起）**：

- ⓗ2：`Read`/`Grep`/`Bash` 在"目标命中两份队列真身或归档件"这一输入组合下，由必然成功变为被拒（`exit 2`）。
- ⓗ3：`release` 在"本次持锁期间新增/编辑的行、§一 状态列或§四 事项列单格 >4 KB"这一输入组合下，**2026-09-11 起**由必然成功变为可能被拒；**2026-09-11 前不 BREAKING**（只告警）。

ⓗ1 不 BREAKING——纯新增 CLI 参数，不传 `--grep` 时行为逐字不变。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

**⑴ 本流程哪些判断是人脑默会经验？**

- **"这段改动会不会撞到别人的触碰区"**：此前完全靠开工时人工对队列文件做一次裸读/裸 grep，凭记忆比对 143 行任务的触碰区列，本包 ⓗ1 之前没有任何工具能做"关键词命中哪几行"这件事。
- **"这一行的状态列是不是已经写成日志、该搬家了"**：此前无任何量化阈值，全靠"看起来很长了"的主观判断，本包 ⓗ3 给出机器可判的 4 KB 数字。
- **"直接读/grep 队列文件会不会撑爆上下文"**：此前完全靠每个 session 自己记得"两份队列真身单行可达 78 KB"这条经验数字，忘记的后果是静默发生（上下文被撑爆，不报错）。

**本变更包交付后所处档位：档 3（内部服务）。** 理由同 `cc-hooks-p3`：三处产出物服务于内部构建流程，真实运行在生产工作区（非 mock），不产出对客交付物、不涉真实业务数据。

**本档验收条件（逐条，全部可机器核）**：

1. `openspec validate --strict` 绿；
2. 三处判据各自的单测覆盖对应 spec 的全部 Scenario，含反例（fail-loud/fail-open、白名单撞车、词边界误判等）；
3. ⓗ1／ⓗ3 已对**真实生产队列文件**跑过至少一次只读/只读校验路径验证（非 mock 夹具），见 tasks §1/§2 验活记录；ⓗ2 依赖人工注册，验活留待 tasks §5（前置条件未满足前不得勾选）；
4. 既有回归测试套件（`test_工具-队列查询.py`／`test_工具-共享文档编辑锁.py`）零漂移通过。

**价值指标（业务 Champion ＝ Shao Peishen 确认基线）**：

- **质量型（主）**：值周巡检/开工核触碰区一次读入量——基线见方案文档实测「50–150 KB（grep 命中 1–3 胖行）」，目标是本包生效后同类核查读入 <2 KB（方案文档 §三"效果估计"表已给出目标值，本包是达成它的机制）。
