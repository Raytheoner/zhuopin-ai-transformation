# queue-read-write-guards Design

## 决策点 1：ⓗ2 `Grep` 的 `path` 用精确匹配，不用目录归属启发式

**问题**：`Grep` 工具的 `path` 参数可选（缺省即从 cwd/repo 根搜索），也可以传一个目录。若目标是"防止一次 grep 把队列文件的内容读进结果"，理论上更彻底的做法是：`path` 未传或 `path` 指向的目录包含两份队列真身/归档件时都拦。

**已否决方案**：目录归属启发式——判断 `path`（含缺省的仓库根）是否是队列真身/归档件所在目录 `1-转型规划/0-全景路线图/` 的祖先或本身。否决理由：① 该目录下还有大量与队列无关的合规文档（方案文档、CHANGELOG 等），一刀切拦会误伤"我只是想 grep 这份方案文档"这类合法调用；② `path` 未传时几乎所有仓库级搜索都会被拦，而"grep 某关键词全库定位"是高频且与队列读侧问题无关的常规操作，误伤面过大；③ 现有同族钩子（`hooks-pretooluse-editlock-guard.ps1`）的既定判据本就是"只判结构化目标字段精确命中"，不做目录/内容层面的模糊猜测——引入启发式会让两枚同族钩子的判据模型出现分叉，违反本项目"两处判据分叉是明确要防的形态"的一贯立场（见 `hooks-pretooluse-editlock-guard.ps1` 文件头注释）。

**采用方案**：`Read` 用 `file_path`、`Grep` 用 `path`，均只判"解析出的目标路径是否精确等于两份队列真身之一，或其父目录等于队列目录且文件名匹配 `跨桌任务队列-归档-*.md` 正则"。`path` 未传（Grep 最常见形态）视为"无结构化目标可判"，不拦，不因此记为"违规"（心跳记 `undetermined`，语义上等价于 SessionStart 心跳的"读不到 XX 时不装作没事"既有原则，见 `Complete-Sentinel` 的 Verdict 说明）。

**已知残余风险，明写不掩饰**：一次不传 `path` 的全库 grep，若命中模式恰好落在队列文件里，其结果**仍会**把命中行（可能是超长单格）打进上下文——本包不堵这个口子。`.claude/rules/队列与落库.md`「读侧禁通读」条目本身的措辞是"两份队列真身与归档件不得 `Read` 全文、不得 `grep`"，本包机制化的是"点名读/grep 这些文件"这个最高频、最容易被机器识别的失效形态，不是"任何可能间接命中队列内容的操作"——后者没有可行的机器判据（`Grep` 工具本身不会把"搜索范围包含哪些文件"作为可预先静态判断的量，需要真正跑一次才知道命中了什么），继续留给人守（K3 规则原文与本条 design 均已如实注明）。

## 决策点 2：ⓗ2 `Bash` 判据——命令文本正则是本钩子唯一的例外，且刻意收窄

**问题**：`Bash` 的 `tool_input` 只有一个不透明的 `command` 字符串，没有结构化路径字段。若要拦住"通过 Bash 间接读队列文件"，除了对命令文本做某种匹配，没有别的信号可用——这与 `hooks-common.ps1` 决策点 2 明确写死的"判定输入一律取 stdin JSON 里解析出的 `file_path`，绝不对 `command` 字段做路径正则"直接冲突（该决策点约束的是**写侧哨兵**族，`sentinel-mojibake.ps1`/`sentinel-pronoun.ps1`，理由是"正文里提到一个路径不等于写入了那个路径"）。

**为何本钩子允许对 `Bash` 做例外**：写侧哨兵判的是"新写入的内容里是否含有问题模式"，`command` 字段与"写入内容"是两个不同维度的东西，对 `command` 做路径正则会产生大量假阳性（提到路径不等于写了它）。但本钩子判的是"这次调用会不会读到队列文件的内容"——对 `Bash` 而言，`command` **就是**唯一描述"读什么、怎么读"的信号，不存在"结构化字段" vs "正文提及"的区分（`Read`/`Grep` 有前者可用，`Bash` 没有）。故本钩子对 `Bash` 的例外处理不是推翻决策点 2 的立场，而是决策点 2 本身"只在有结构化字段时才不猜"这一前提在 `Bash` 上不成立时的必然结果。

**收窄设计**：不对整条命令串做任意匹配，只认定"读命令名"（`Get-Content`/`cat`/`grep`/`Select-String`，四个具名动词、`\b` 词边界匹配，`cat` 不会误中 `concatenate`）与"目标文件名"（两份真身文件名或归档件正则）**同时出现**才判命中。只命中动词或只命中文件名均不算——前者会把 `pytest -k grep` 这类与队列无关的常规操作错杀，后者会把 `git log -- <队列文件>` 这类不读取内容的操作错杀。

## 决策点 3：ⓗ2 白名单——因本包自身新增的 `--grep` 而必须存在，不是防御性调味

**真实撞车实例（建造期现场发现，非假设）**：ⓗ1 新增的合规用法 `python 0-学习与工具/工具-队列查询.py --digest --grep <关键词> --file <归档件路径>` 是文档标注的正确用法（`--grep` 须配合 `--digest`），但这条命令的字面文本**同时**含"grep"子串（来自 `--grep` 标志本身）与一个归档文件名（`--file` 的值）——若 ⓗ2 的判据不做任何豁免，K3 新增的 `--grep` 功能会被 K3 自己的 `Bash` 读守卫反噬，形成"新机制上线当天就把自己的合规用法拦下"的荒谬局面。

**采用方案**：命令行本身在调用编辑锁（`工具-共享文档编辑锁.py`）／队列查询（`工具-队列查询.py`）／sweep（`工具-落库sweep.py`）／队列结构 lint（`工具-队列结构lint.py`）四个机制工具之一（脚本路径子串命中即算，含被这些脚本的同名单测文件如 `test_工具-队列查询.py` 间接命中——测试脚本运行这些工具本身也是被机制信任的合法路径）时，整条命令**无条件放行**，不再检查是否同时命中动词+文件名。这与决策点 2 的"收窄"不矛盾：白名单是在动词+文件名判据**之前**短路，属于"信任来源"层面的豁免，不是放宽判据本身的精度。

**已知边界**：若某条命令同时调用了这四个工具之一**并且**在同一行拼接了一条真正违规的裸读（如 `python 工具-队列查询.py --digest && cat 跨桌任务队列-机制环境.md`），本设计会因白名单命中而整条放行，裸读部分不会被单独抓出。**接受这个残余风险**：这种复合命令行在真实使用中极为罕见（本项目命令习惯是一条命令一件事，见根 `CLAUDE.md` 与两份 rules 文件里大量的单命令示例），且要精确拆分 `&&`/`;`/`|` 复合命令逐段判定的复杂度与收益不成比例，不在本包范围内建造。

## 决策点 4：ⓗ3 行长阈值单位与阻断日期切换机制

**单位**：UTF-8 字节数（`len(cell.encode("utf-8"))`），不用字符数——理由是方案文档 §一 的实测数据本身就是按字节统计（"11.8 KB/行"），且中文字符按字符数统计会让阈值的"物理意义"（灌进上下文的 token 量）失真（中文字符在多数分词器下接近 1–2 token/字，但字节数与"读入这段文本要花多少上下文预算"的相关性更直接、更符合本项目一贯用字节量测的惯例，见方案文档全篇统计单位）。

**阻断日期切换**：不新增配置文件或命令行开关，直接在代码里硬编码 `ROW_LENGTH_BLOCK_FROM = "2026-09-11"` 常量，用 `datetime.now().strftime("%Y-%m-%d") >= ROW_LENGTH_BLOCK_FROM` 的字符串字典序比较判断当前处于哪个模式。**已否决方案**：读取一个外部"模式开关"文件（同 `sentinels-mode.json` 的 warn/block 二态设计）。否决理由：`sentinels-mode.json` 那套设计服务于"人工观察一段时间后手动决定何时切换"的场景（哨兵是新建立的、误报率未知）；本项判据的阻断日期在 `#381`⑸ⓗ3 原文与方案文档里已经**写死为一个具体日期**（2026-09-11，"首周只告警"），不需要人工二次决策，硬编码日期常量反而更符合"到点自动生效、不需要再有人记得去翻开关"的机制化初衷——引入一个本不需要人工介入的开关文件，等于给一个已经写死的日期重新加上"人要记得改"的失效模式。

**逃生阀**：单元格内 `行长豁免：<理由>`，与既有 `WIP豁免：`/`预留豁免：` 同一范式（标记连同理由写在行内、进 git、被值周巡检看得见，不新增写盘路径）。与 ⑨ WIP 上限的逃生阀不同之处：本项逃生阀**不需要配套的命令行开关**（`--force-mechanism-wip` 那种"意图 + 理由两者缺一不可"的设计）——理由是 ⑨ 的阻断对象是"新增一条会让全局计数超限的行"，越过它意味着明知故犯地让系统进入一个受控风险状态，需要双重确认；本项的阻断对象只是"这一格文字还没来得及搬家"，越过它的后果仅仅是"这一格继续变长"，不产生新的系统性风险，单一行内标记已经足够表达"这是有意识的选择、理由已留痕"。

## 决策点 5：ⓗ3 只对本次持锁期间 touched 的行生效，不追溯历史

**直接复用**本文件既有 ①–⑩ 判据的既定原则（`_validate_release_structure` 函数文档"只对本次持锁期间新增/修改的行生效（历史行不追溯）"），不是本包新拟。**必须如此的理由**（与 ⑨ WIP 上限文档里"不能把来关行的 session 也锁在门外"完全同构）：ⓗ3 落地时，两份队列真身**已经存在**大量超限行（方案文档实测 18 行 >20 KB），K2 搬迁工作本身尚未对这些历史行执行完毕。若判据扫描整份文件而非本次改动，2026-09-11 起**任何**触碰队列文件的 `release`（包括来做 K2 搬迁本身的那次 `release`）都会因为文件里还存在其它未搬迁的超限行而被拒——规则会把自己的解法锁死。只判 touched 行，使"专门来修一行"与"顺手改一行、其它超限行原样未动"两种场景都能正确放行，同时保证"新写入或新编辑的一行如果超限，逃不过检查"这一核心诉求成立。

## 决策点 6：ⓗ1 大小写不敏感、按"任务列＋触碰区列"两列过滤，不新增第三列

**大小写不敏感**：本项目关键词常混排中英文/编号（如 `OP-0904`、`P0`、`CC`），实测队列内容里同一编号偶有大小写不一致的笔误（如提交历史里 `op-0904` 与 `OP-0904` 并存的先例，见队列 `#455` 记录的"OP 编号无查重"问题），若严格区分大小写，`--grep OP-0904` 与 `--grep op-0904` 会得到不同结果集，对一个"快速核对触碰区"的工具而言，这种精确性不值得用户去记"到底哪种大小写才对"。

**只判任务列与触碰区列，不含状态列全文**：`--digest` 本身的定位是"扫全池不通读真身"，状态列全文才是真正的大体量来源（方案文档实测 11.8 KB/行均值）；若 `--grep` 也扫描状态列全文，等于让过滤器本身也要读入这份大体量文本，与 `--digest` 从不读入状态列全文（只取 `[S:...][D:...]` 机器字段与截断后的任务列摘要）的既有设计相悖。任务列（改动意图的自然语言描述）与触碰区列（改动涉及的文件/函数）已经覆盖"这次改动是什么、碰了什么"的核心问题，是判断触碰区重叠的最小必要信息。
