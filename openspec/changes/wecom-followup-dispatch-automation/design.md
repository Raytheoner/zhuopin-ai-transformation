## Context

见 proposal.md — Why/What Changes。本节只记支撑设计选择的现状约束：

- 队列 #124 全文（`1-转型规划/0-全景路线图/跨桌任务队列.md` #124 行）是本变更的权威派单依据，本设计逐条回应其列出的三条前置 (a)(b)(c) 与 2026-08-04 拍板追加的三条要求（README 两态语义 / #138 心跳探测取舍已在 §四#48 拍板为 (b) 不做 / #122 用法一并覆盖）。
- 现有 gate②（`5-平台底座/wecom-aibot-service/aibot_service/gates.py::assert_finalized`）已经是"仅当 README 目标行「发送状态」列**严格等于** `🆕 待发` 时才允许发送"的硬断言，`FINALIZED_STATUS_MARKER = "🆕 待发"` 写死代码结构、design.md D8 明确"不得放宽"——本变更**不修改**这个既有断言，只新增"谁、如何、被允许把状态写成这个值"这一维度的约束，是在它"前面"加一层，不是替换它。
- `readme_table.py`（`locate_row`/`write_status`）已是通用的"按含'发送状态'字样的表头定位、原子改写单元格"实现，不与任何具体状态值的语义耦合，可直接复用于本变更的新增状态转换（`⏳ 待你审` → `🆕 待发`）。
- `push_followup_letter.py`（人工触发脚本）与 `delivery.push_followup`（其复用的库函数）不改变——本变更新增的批处理任务复用同一个 `push_followup` 函数，只是触发方式从"人工跑一次带参数的 CLI"变成"定时任务逐行扫描后调用"。
- `工具-共享文档编辑锁.py::_validate_release_structure`（#225 引入）目前的四项结构校验都是**默认目标文件**（跨桌任务队列.md）专属逻辑；工具本身早已支持 `--file` 指向任意共享文件（`acquire`/`release`/`status` 通用），只是结构校验部分尚未泛化到其他文件。本变更需要新增一个校验分支，而非新建一套锁机制。
- `ZhuopinDecisionReminderDaily`（#172）是本变更"发信班次"部署形态的直接先例——同一台笔记本、`LogonType=Interactive`（非 S4U，避免 #189 实测的 Access denied 坑）、`New-ScheduledTaskSettingsSet -StartWhenAvailable`、VBS `run-hidden.vbs` 隐藏窗口（#231 先例）、`WECOM_AIBOT_QUEUE_PATH` 环境变量显式锚定仓库根（规避 worktree 反推坑，同 #172/#127 实测教训）——本变更直接复刻这套已验证范式，不重新设计部署形态。
- `wecom-aibot-channel` 变更包（`openspec/changes/wecom-aibot-channel/`）截至本次仍未 `/opsx:archive`（`tasks.md` 8 项未完成），其 `specs/wecom-followup-delivery/spec.md` 因此尚未同步进 `openspec/specs/` 主目录。本变更依赖的 gate②/`push_followup`/`readme_table` 行为契约实质上就定义在这个尚未落地主目录的 delta spec 里——本变更选择不对它做跨包 delta（避免对一个仍在演进的活跃变更包做脆弱耦合），改为把依赖关系写在本节 + Risks，留给 apply 阶段协调。

## Goals / Non-Goals

**Goals:**
- README「发送状态」列从单态语义改为两态语义：`⏳ 待你审`（草稿，唯一合法起草产物）／`🆕 待发`（终态，唯一合法产生方式=批准脚本）。
- "起草"与"批准"是两次独立、时间上分离的写操作，且这条边界由结构性校验保证，不依赖起草者自觉遵守。
- 批准动作强制留痕批准依据，形成独立于聊天记录、可事后核查的审计证据。
- 新增每日批处理发信任务，消费"🆕 待发"终态行，采用"不承诺准点、只承诺下次开机即发"的可靠性模型。
- 硬截止交付的跟进信可显式排除出自动发送范围，继续走人工触发保证可控时限。
- #122（未来的起草类自动化）复用本变更定义的写入契约，不需要重新设计安全约定。

**Non-Goals:**
- 不做 `--quote` 参数真实性校验（本设计的信任模型与本项目现有"拍板"记录一致：人工转述+事后可审计，非密码学防抵赖）。
- 不在本变更内建造 #122（Dispatch v0.6 起草类任务自动化）——只定死其未来必须遵守的契约。
- 不做"该起草而没起草"的主动检测（发布批次 vs README 新增行的交叉比对）——本变更只保证"起草了就必然留痕"，见 D5，检测本身留作后续独立评估。
- 不做发信频率可配置化——本轮固定"每日一次"，不预先做成多频次可调（保持与 `ZhuopinDecisionReminderDaily` 一致的最简形态，上线观察后再评估是否需要调整）。
- 不对 `wecom-aibot-channel` 变更包的 `wecom-followup-delivery` delta spec 做修改或同步（该包仍未归档，非本变更范围）。

## Decisions

### D1（对应队列 #124 前置 (a)）—— README 两态语义 + 结构性拦截 + 批准脚本

**状态值定义：**
- `⏳ 待你审` —— 草稿态，唯一合法的"起草"产物。CLAUDE.md §5 第8步（场景发布自动起草）、Cowork 域专线手写跟进信、#122 未来的自动化起草，三类起草来源一律只能产出此值。
- `🆕 待发` —— 终态，既有 gate②（`gates.assert_finalized`）唯一认可的可发送标记，本变更不改变这个值本身或消费它的既有逻辑；新增约束的是"谁、如何被允许把状态改写成这个值"。

**批准脚本 `approve_followup_letter.py`（新增，`5-平台底座/wecom-aibot-service/scripts/`）：**
- 参数：`--readme`/`--match-topic`（定位目标行，与 `push_followup_letter.py` 现有参数风格一致）+ `--quote`（**必填**，批准依据摘录，如 Shao Peishen 的放行原话）。
- 前置断言（新增 `assert_draft_pending_review`，风格对齐 `gates.assert_finalized`）：目标行当前「发送状态」列必须严格等于 `⏳ 待你审`，非此值一律拒绝执行，不触碰文件。
- 动作：复用 `readme_table.locate_row`/`write_status` 原子改写状态列为 `🆕 待发`；写入一条 `AuditEvent(action="followup_approved", decision={"quote": <批准依据>, "row_match_topic": <定位关键字>})` 到既有 `wecom_aibot_audit.jsonl`（复用 `AuditLogger`，同 `delivery.py` 现有审计流，不新开一条审计文件）。
- **本脚本不发送任何消息**——只做状态跃迁。发送仍分别由人工路径（`push_followup_letter.py`）或自动路径（新增批处理任务）消费"🆕 待发"这一终态，职责单一。

**结构性拦截"新建即终态"反模式：**
`工具-共享文档编辑锁.py::_validate_release_structure` 新增一个 README 专属分支——当 `--file` 指向跟进信 README 文件时：比对 `acquire` 时读取的表格快照与 `release` 时的表格快照，若某行在 `acquire` 快照中不存在（本次持锁窗口内新增）、且在 `release` 快照中「发送状态」列值为 `🆕 待发`，**拒绝 release**，提示"起草只能写 `⏳ 待你审`，`🆕 待发` 只能由 `approve_followup_letter.py` 写入"，锁保持占用直至该行改回 `⏳ 待你审` 或撤回新增。既有行从 `⏳ 待你审` 转为 `🆕 待发`（批准脚本的合法产物）不受影响，正常放行。

**为何比现状更严（design 要求显式回答）：** 现状（CLAUDE.md §5 第8步 + README L22/L24）里，"起草"与"标终态"是同一会话内、无独立留痕的单一动作——CC/专线自称"已在对话中提交审核并获通过"后直接写 `🆕 待发`，除了这次对话本身的聊天记录（且会话上下文可能被压缩，见"Context management"机制），没有任何机制层面的证据要求或校验。新设计下：① 起草物理上不能一步到位产出终态（结构性拦截，非自觉遵守）；② 终态只能来自一次独立的、强制携带批准依据的脚本调用，产生独立于聊天记录、写入版本化审计流的证据，即使聊天记录被压缩/丢失，这条证据仍可在 `wecom_aibot_audit.jsonl` 里核查；③ 自动化（本变更的直接目的）此后只消费"已经独立留痕过批准依据"的终态行，而非"起草者自称已通过审核"的终态行——门槛从"自陈"升级为"独立记录"。

### D2（对应队列 #124 班次载体二选一）—— 选 (a) 新增独立每日定时任务，不并入巡逻

**结论：** 新增独立每日定时任务 `ZhuopinFollowupDispatchDaily`，工作日固定时刻（**09:30** 本地时间，见"Open Questions"）触发，直接复刻 `ZhuopinDecisionReminderDaily`（#172）已在生产验证过的部署范式。

**理由（三点，逐一对照"并入巡逻 live 收尾"的代价）：**
1. **职责边界**——拆件巡逻当前唯一职责是"回件拆件"（专员回复分流进队列动作），是"进"方向处理；发信班次是"出"方向动作（把已批准内容真正发出去，不可撤回）。#122 自评估时已用"一次只动一个变量"否决在巡逻转正同一窗口内叠加"起草自动化"（影响面更小的动作）；"发送"这种影响面更大、真实触达外部人员的动作更不应该无独立评估地塞进巡逻当前职责范围。
2. **故障归因**——若巡逻班次某次运行既处理了回件拆件、又触发了一封误发的跟进信，无法从单次运行日志干净区分"是拆件逻辑判断错了，还是发信判断错了"；独立任务从一开始就没有这个耦合问题，出错时日志与责任边界清晰，与 #122 自身评估理由②同构。
3. **既有范式复用**——`ZhuopinDecisionReminderDaily` 已提供一套完整、经真实生产验证的"笔记本本地+每日+对外发送"部署范式（`LogonType`/`StartWhenAvailable`/VBS 隐藏/`repo-root` 动态解析四项均已踩坑修正过），新增一个同构的每日任务边际成本很低；把发信塞进巡逻反而要在一个语义不同（拆件 vs 发信）、节奏不同（工作日两次固定时刻 vs 每日一次、且由 Cowork agent 承载而非 Windows 计划任务）的既有流程里做适配，边际成本更高。

**未选 (b) 的代价（design 要求给结论，非只列选项）：** 若选 (b)，等于把"对外发送"这一高风险、不可撤回动作的触发时机与频率绑定给巡逻班次自身的转正/扩容节奏——一旦巡逻因自身问题（如 #106 提到的"零错写"观察期回退 dry-run）被暂停，发信班次会被无关地一并拖累；反之若巡逻运行良好但发信逻辑出问题，也会连累巡逻承担"发错信"的责任，模糊两者本来清晰的问题域边界。

### D3（对应队列 #124 时限承诺，已由 §四#48 拍板选 (b)）—— 不承诺准点 + 硬截止豁免写入规范正文

**时限承诺：** `ZhuopinFollowupDispatchDaily` 采用"不承诺准点，只承诺下次开机即发"——笔记本合盖/关机期间错过的运行窗口，靠 `New-ScheduledTaskSettingsSet -StartWhenAvailable`（复用 #189/#199 已验证生效的设置）在下次开机时自动补跑，不做额外心跳/重试设计（§四#48 已拍板不做 #138 心跳探测，此为其配套取舍的落地）。

**硬截止豁免：** 硬截止交付的跟进信（如 #59 那类）不进入自动发送范围。README 新增行内约定标记 `🔒人工发送`，写在"交期要点"列内、紧跟截止时间之前（例如 `🔒人工发送 · 2026-07-31（本周五）前`）；起草时若已知为硬截止交付，专线/CC **必须**显式标注。`ZhuopinFollowupDispatchDaily` 扫描逻辑对含该标记的行结构性跳过（即使状态已是 `🆕 待发`），只能由人工按现有流程手动跑 `push_followup_letter.py` 发送，以保证可控时限。

**该限制写入规范正文（design 明确要求，非仅设计文档内部约定）：** apply 阶段须在 README-跟进机制与命名约定.md 新增一节，明确 `🔒人工发送` 标记的定义、触发条件（"起草时已知有硬性截止日期、逾期会产生实质后果的跟进信"）与效果（自动化跳过，人工发送不受影响）；CLAUDE.md §5 第8步补一句引用。此点已在 proposal.md「Impact」中列为受影响文件。

### D4（对应队列 #124 与 #122 的同批约定）—— #122 复用同一契约，本轮不建造

#122（Dispatch v0.6 候选：起草类任务自动化）仍处于 2026-08-06 二次评估待办状态，本变更不实现它。本设计的立场：D1 定义的"起草只能产出 `⏳ 待你审`"契约是 **authorship-agnostic** 的——它约束的是"这个状态值如何产生"，不关心产生者是人（Cowork 专线/CC）还是未来的自动化（#122）。因此 #122 将来落地时，只需要让它的输出复用现有 `readme_table` 的行创建路径（无论谁写，新行的状态列只能是 `⏳ 待你审`），不需要（也不应该）为自己重新设计一套"待审/待发"判定逻辑——若 #122 绕过 `readme_table` 公共写入路径直接拼字符串写文件，D1 新增的结构性拦截（`_validate_release_structure` 专属分支）依然会在 release 时挡住任何"新增行+终态"的组合，与幕后写入者是谁无关。

这一决策把 #122 未来评估时的"安全约定"从"需要单独设计"降级为"验收标准里加一句：新增自动化必须复用本变更引入的 README 写入路径与结构校验，不得旁路"，08-06 评估 #122 时无需在这一维度重新讨论——与 #122 原行自身写明的"两者共用同一条安全约定，不得各定各的"完全一致。

### D5（对应队列 #124 追加的第三条前置）—— "该起草而没起草"检测的闭合程度

两态语义生效后，"起草"这个动作被结构性地绑定为"必须产出一行 `⏳ 待你审`"——即凡是发生过的起草，都会在 README 里留下痕迹（区别于现状：起草可能只停留在聊天记录/某个未提交的 `.md` 草稿里，从未写进 README，此时 #124 阶段一"待发信盘点"[只扫描 README 中已存在的行]根本无从察觉）。这**部分闭合**了"该起草而没起草"问题域中的"起草了但没登记"子问题。

**诚实标注未完全闭合的部分（Non-Goal，本变更不做）：** 判断"某个发布收口批次本该触发起草、但连 `⏳ 待你审` 都没有"，仍需要一个独立的比对源——即"近 N 天发布收口批次列表"（类似队列 #229 设想的"命中已部署场景目录却无部署留痕行"式扫描）与"README 近 N 天新增的 `⏳ 待你审` 行"做交叉比对，本变更不实现该比对逻辑。但正因为 D1 保证"起草必留痕 `⏳ 待你审`"，未来要建这个比对时，只需要扩展已交付的"待发信盘点"扫描（阶段一，随巡逻 live prompt 已落地），比对对象从"`🆕 待发` 行"扩展到"`⏳ 待你审` 及以上状态的行"即可，不需要额外的信号源或设计——即"检测能力的地基已经具备，只是本变更不砌这一层楼"。

## Risks / Trade-offs

- [已知限制] D1 的结构性拦截依赖 `--file` 指向跟进信 README 文件、且经由 `工具-共享文档编辑锁.py` 完成编辑——若 CC/Cowork 会话直接用 Edit 工具改文件而不走该锁的 `acquire`/`release` 流程，校验不会被触发（与现状对 `跨桌任务队列.md` 本身的 #225 校验同源限制，是"约定+结构校验"而非"文件系统级强制"）。**缓解**：① apply 阶段更新 CLAUDE.md §5 起草规范时，把"改 README-跟进机制文件前先 `acquire` 该锁"写为强制步骤；② 发送侧的断言（gate②/新增的草稿态断言）是运行时硬断言，不依赖编辑流程被正确遵守——即便有人绕过锁直接手写 `🆕 待发`，最终风险收敛为"审计里少一条 `followup_approved` 留痕"（可事后核查发现异常），而非"发出内容本身失控"。
- [风险，本设计明确接受] `approve_followup_letter.py` 的 `--quote` 参数不做真实性校验（不核实这段文本是否真的是 Shao Peishen 说的）——这是本设计明确接受的边界：本项目现有全部"拍板"记录（队列 §四各行）同样是人工转述、无密码学签名，`--quote` 的价值在于"强制要求必须提供、且永久可查"，不在于"证明其真实性"，与项目既有信任模型一致（人工转述+事后可审计，非防抵赖）。
- [权衡] 选择"每日一次"而非更高频的发信班次扫描——若一封信在 09:30 运行窗口后不久获批，要等到下一个工作日 09:30 才会被自动拾取（除非人工手动 `push_followup_letter.py`）。**可接受**：D3 已明确"不承诺准点"，硬截止信本就走人工快速通道；上线后若观察到延迟造成实际问题，可低成本调整触发时刻/频率（Non-Goal：本变更不预先做成可配置多频次）。
- [依赖风险] `wecom-followup-delivery`（现有 gate②/`push_followup` 契约）位于尚未归档的 `wecom-aibot-channel` 变更包内——本变更新增的两个 capability 在设计上依赖其提供的 `gates.assert_finalized`/`delivery.push_followup`/`readme_table.*`，但不对其 specs 做 delta。若 apply 本变更时 `wecom-aibot-channel` 仍未归档，两者共享的代码文件（`gates.py`/`delivery.py`/`readme_table.py`）会由两个并行变更包共同持有，需要在 apply 阶段先核对 `wecom-aibot-channel` 剩余 8 项未完成任务与本变更是否有文件级交集（如无交集可并行推进）。

### D6（design 审批通过时 Shao Peishen 追加）—— 批准冷却窗口

design 审通过附带两条追加要求，非可选项。第一条：`approve_followup_letter.py` 拒绝在"首次观测到目标行"后 10 分钟内批准（`aibot_service/approval.py::check_cooldown`）。**成因**：D1 的结构性拦截挡的是"一次编辑里既新建又置终态"，**挡不住同一个 actor 连做两步**（起草→release→立刻 approve，`--quote` 填一句自认为对方说过的话）——两步、同一 actor、中间没有真人。**实现取舍**：不追溯真实起草时刻（无可靠信源，README 编辑不经任何脚本），改以"批准脚本第一次调用"为观测时刻——首次调用必然被拒绝并记录时间戳，第二次调用须满冷却时长。这不精确等于真实起草时间，但已达成设计目的：批准动作不能与起草动作在同一次连续操作序列里一步做完，必须至少两次调用、间隔一段刻意等待。**已知局限（design 明确接受）**：对存心等够时间的人无效——"冷却窗口挡不住刻意等待，但把顺手一起做掉变成必须刻意等"，与其自身逻辑一致。

### D7（design 审批通过时 Shao Peishen 追加）—— 疑似漏标硬截止的机器判据兜底

第二条追加要求：`dispatch_followup_letters.py` 在处理每一行前，检查"交期要点"列是否含明确日期（严格 `YYYY-MM-DD`，MUST NOT 识别相对表述）且距今 < 3 天（`aibot_service/dispatch.py::has_unmarked_imminent_deadline`）；命中且未标 `🔒人工发送` 时结构性跳过并私信 Shao Peishen 告警。**成因**：D3 的 `🔒人工发送` 依赖起草者记得标注——**漏标是静默失败**（硬截止信没标即被自动发晚一天、无任何告警），与 #204/#228/#231 同族（"规则成文、无载体"）。**边界（design 明确收窄，非疏漏）**：只识别严格 ISO 日期格式，不做相对表述（"本周五"/"8月初"）的自然语言解析——那类解析的误报/漏报成本过高，本判据定位是"漏标安全网"而非"取代人工标注"，起草者仍须自觉标注 `🔒人工发送`。
