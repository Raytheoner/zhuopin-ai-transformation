## ADDED Requirements

### Requirement: 起草只能写入待审草稿态
起草者（人工专线/CC 建造会话，或未来的自动化如 #122）新增一条跟进信登记行时，「发送状态」列 SHALL 且仅 SHALL 写入草稿标记 `⏳ 待你审`；MUST NOT 在新增该行的同一次编辑中直接写入终态标记 `🆕 待发`。

#### Scenario: 场景发布自动起草跟进信落 README
- **WHEN** CC 按根 CLAUDE.md §5 第8步在场景发布收口后新增一条跟进信登记行
- **THEN** 该行「发送状态」列值为 `⏳ 待你审`，不得为 `🆕 待发` 或其他终态标记

#### Scenario: Cowork 域专线手写跟进信登记
- **WHEN** Cowork 域专线为一封新起草的跟进信在 README 追加登记行
- **THEN** 同上，状态列只能是 `⏳ 待你审`

### Requirement: 唯一合法的批准转换路径
将「发送状态」列从 `⏳ 待你审` 转换为终态标记 `🆕 待发`，SHALL 仅能通过批准脚本（`approve_followup_letter.py`）完成；该脚本 MUST 在执行前断言目标行当前状态严格等于 `⏳ 待你审`，非此值 MUST 拒绝执行、不修改文件。

#### Scenario: 目标行为待审草稿，批准成功
- **WHEN** 调用批准脚本指定的目标行「发送状态」列当前值为 `⏳ 待你审`
- **THEN** 脚本将该值原子改写为 `🆕 待发`，操作成功

#### Scenario: 目标行非待审草稿，批准被拒绝
- **WHEN** 调用批准脚本指定的目标行「发送状态」列当前值不是 `⏳ 待你审`（如已是 `🆕 待发`、`✅ 已推送...`、空值等任意其他值）
- **THEN** 脚本拒绝执行并报错说明当前实际状态，不修改文件

### Requirement: 批准动作强制留痕批准依据
批准脚本 SHALL 要求调用方显式提供批准依据摘录（如 Shao Peishen 的放行原话），缺失该参数 MUST 拒绝执行；批准成功后 SHALL 写入一条独立于聊天记录的审计事件，包含该依据摘录与目标行定位信息。

#### Scenario: 未提供批准依据，拒绝执行
- **WHEN** 调用批准脚本时未提供批准依据摘录参数
- **THEN** 脚本报参数错误并拒绝执行，不触碰 README 文件

#### Scenario: 批准成功写入审计
- **WHEN** 批准脚本成功完成一次状态转换
- **THEN** 审计流新增一条 `action="followup_approved"` 事件，`decision` 字段含批准依据摘录与目标行定位信息

### Requirement: 结构性拦截"新建即终态"反模式
共享文档编辑锁工具在 `release` 时，若锁定目标为跟进信 README 文件，SHALL 比对本次持锁窗口内的表格快照变化；若发现某行在 `acquire` 时的快照中不存在（本次新增）且在 `release` 时状态列值为 `🆕 待发`，MUST 拒绝释放锁并提示违反两态语义，直至该行状态改回 `⏳ 待你审` 或撤回新增。

#### Scenario: 新增行且直接写终态，拒绝 release
- **WHEN** 持锁窗口内新增了一行跟进信登记，且其「发送状态」列在 release 时为 `🆕 待发`
- **THEN** release 被拒绝，锁保持占用，提示该反模式

#### Scenario: 新增行且状态为待审草稿，正常 release
- **WHEN** 持锁窗口内新增的行「发送状态」列为 `⏳ 待你审`
- **THEN** release 正常放行

#### Scenario: 既有行的合法批准转换，正常 release
- **WHEN** 持锁窗口内的变化是某个已存在行（在 acquire 快照中已存在）的状态列从 `⏳ 待你审` 改为 `🆕 待发`
- **THEN** release 正常放行（此为批准脚本的合法产物，不属于"新建即终态"）

### Requirement: 硬截止跟进信排除自动发送
起草者对已知存在硬性截止日期、逾期产生实质后果的跟进信，SHALL 在登记行内显式标注 `🔒人工发送` 标记；标注该标记的行，自动发信任务 MUST 结构性跳过，无论其「发送状态」列取值为何，只能经现有人工触发路径（`push_followup_letter.py`）发送。

#### Scenario: 硬截止信已获批准，自动任务跳过
- **WHEN** 某跟进信登记行标注 `🔒人工发送` 且「发送状态」列为 `🆕 待发`
- **THEN** 自动发信任务跳过该行，不发送；该行仍可被人工触发脚本正常发送

### Requirement: 批准冷却窗口
批准脚本 SHALL 在批准前应用冷却窗口：脚本首次"观测到"目标行时 MUST 记录观测时刻并拒绝本次执行；同一行须距首次观测满冷却窗口时长（默认 10 分钟）后再次调用才 SHALL 被允许批准。本机制 MUST NOT 依赖对"真实起草时刻"的追溯（本项目无可靠信源记录该时刻），仅需保证批准动作与起草动作不能在同一次连续操作序列内一步做完。

#### Scenario: 首次调用被冷却窗口拒绝
- **WHEN** 批准脚本第一次针对某一行被调用（该行此前从未被观测过）
- **THEN** 脚本记录观测时刻、拒绝本次批准，不修改 README 文件

#### Scenario: 冷却窗口内重复调用仍被拒绝
- **WHEN** 距该行首次观测时刻不满冷却窗口时长时再次调用批准脚本
- **THEN** 脚本再次拒绝，不修改 README 文件

#### Scenario: 满冷却窗口后批准成功
- **WHEN** 距该行首次观测时刻已满冷却窗口时长，且该行仍处于待审草稿态时再次调用批准脚本
- **THEN** 脚本正常执行批准转换（同"唯一合法的批准转换路径"其余行为）

### Requirement: 起草写入契约对起草来源保持一致（authorship-agnostic）
本节约束的"起草只能产出待审草稿态"契约 SHALL 对起草来源（人工专线、CC 建造会话、未来的自动化起草能力）一视同仁；任何后续新增的自动化起草能力 MUST 复用本节定义的 README 行创建/状态写入路径，不得另行实现绕开本节约束的写入逻辑。

#### Scenario: 未来自动化起草复用同一写入路径
- **WHEN** 一个新的自动化能力（如未来建造的 Dispatch v0.6 任务发动）新增一条跟进信登记行
- **THEN** 该行遵循与人工起草完全相同的约束——状态列只能是 `⏳ 待你审`，且同样受结构性拦截保护
