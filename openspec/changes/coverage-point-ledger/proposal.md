## Why（为什么做）

**需求管理的单位是「信」，而我们要度量、要串行、要销号的对象是「口径点」——单位错位导致三件事同时失真。**

三条实测证据：

1. **度量拿不到真值。** `6-人才与组织/部门AI专员跟进/度量复盘-判例批改法回退闸到期-2026-08-23.md` §二 自陈：闸原文要的是"开放口径点提出到销点中位天数"，实际算的是"信发出到回件闭环天数"，**"没有逐点台账，就没有精确值"**。中位 2 天这个达标结论建立在代理指标上。
2. **销点动作散在四处**——队列行／README 状态列／design Decisions／代码 commit，没有任何一处能回答"这个口径点现在在哪"。跨引用靠人写的文字维系：README ↔ 队列双向交叉引用 **506 处**，"编号滞后"一族已复发 **6 次**。
3. **一封信 ≤10 条判例，各点不同时销**——信闭环 ≠ 点闭环，而串行闸只看信。

**手册对位**：Anthropic《AI-Native SDLC Playbook》第 1 阶段 intent.md——"每个阶段结束时往版本控制里写一个产物，下一个阶段从读取这个产物开始"。本项目从 `proposal.md` 往后这条链是完整的，**唯独最上游那一节没有产物**。

## What Changes（改什么）

**新增能力：**

- **`口径点台账`**：一点一条，机器可读，**格式＝ `.yaml`**（🔴 **不得用 `.jsonl`** —— 会被 `.gitignore:32:**/*.jsonl` 全局吞掉，实测与成因见下方「伴生文件」节），随代码进版本控制。字段：
  | 字段 | 说明 |
  |---|---|
  | `id` | 稳定标识，形如 `FI2-D19-03`（场景-判例批次-序号）。🔴 **不随队列行增删漂移**，这正是它优于 `§一 #N` 的地方 |
  | `场景` | 归属场景码（FI2／SC8／QD-B…） |
  | `提出人` / `提出日` | 提出人取自人员名录正本，🔴 不推断 |
  | `判例原文` / `拟改判定` | 判例批改法的两栏原样 |
  | `状态` | `待问` → `在途` → `已签认` → `已回灌` → `已落码` ／ `已作废`（单向，回退须留因） |
  | `承接载体` | openspec change 名 ／ 队列行号 ／ commit sha，至少一项 |
  | `载体信` | 该点由哪封信投影出去（`部门#N`），可多封 |
  | `到期` | 可空；非空则进超期扫描 |

- **跟进信改为台账的投影**：起草时从台账取"该收信人状态＝`待问`"的点生成判例包；回件解析后**回写台账**。🔴 **信是视图，点是真身**——这是本变更的设计核心，不是在信之外再加一张表（那只会变成第 507 处会漂移的引用）。

- **度量派生**：`口径点提出 → 销点` 中位天数由台账直接算出，取代现行代理指标。

**不改：**

- 判例批改法本身（格式、≤10 条、判据类不默认生效、不加并行专员）——**只换承载单位，不动方法**。
- 串行闸口径（改按点计属 R2，另立变更包，硬依赖本包）。
- 已闭环的 17 封历史信不追改（同"历史记录不追改"惯例）；**回溯拆点只做未闭环的 15 封**。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

**1. 本流程哪些判断是人脑默会经验？**

| 默会判断 | 现在只在谁脑子里 |
|---|---|
| **"这段回件里有几个口径点"**——一封回件的自由文本要拆成几条，边界在哪 | 拆件巡逻班／值周巡检的执行者，无成文判据 |
| **"这个点算不算已签认"**——专员回了一句"可以"，是签认了整条还是只认了前半句 | 同上；现行只有信级四态，无点级判据 |
| **"这个点的承接载体是谁"**——落 openspec 还是落队列行还是就地改代码 | 无成文规则，逐次判断 |
| **"哪些点必须专员签认、哪些可默认生效"** | 🔴 **这一条已成文**（判据/口径/阈值类永不默认生效，IATF 显式签认红线），是四条里唯一不默会的 |

**2. 由谁显性化？**

- **持有人**：Shao Peishen（OPVP，判定权威单点）
- **backup**：孙涛（决策代理范围内：design 审、批间 Triage、L2 日常审批）
- 登记进《跨场景前置数据与知识库任务总表》§一.2 知识资产台账。
- 🔴 **不含任何部门专员**——拆点判据是我方内部口径，走 grill 不走判例批改法（`zhuopin-requirement-grill` 边界：受访者只有场景发起人）。

**3. 用什么方法提取？**

**历史案例反推为主 ＋ AI 起草·专家批改为辅**：

- 取已闭环的 17 封信作为**训练集**——它们的回件与后续处置都已发生完毕，逐封反推"当时实际拆成了几个点、每个点最终落在哪"，由此归纳拆点边界与承接载体判据；
- 取未闭环的 15 封作为**验证集**——用归纳出的判据实拆一遍，交 Shao Peishen 批改；
- 🔴 **不设并行提取人**（同判例批改法"不加并行专员"）。

## 验收与晋档条件（强制，四档口径）

**本变更包交付后场景所处档位**：**档 2（真实数据跑通）**。
理由：台账建成并回溯拆点后即在真实数据上运行；但"跟进信从台账投影生成"这条链要到 R2/R3 落地后才算内部服务化。

**晋下一档（档 3 内部服务）的条件**（逐条）：

1. 未闭环 15 封的回溯拆点完成，且 Shao Peishen 签认拆点结果；
2. `工具-跟进闸查询.py` 改为从台账取数（不再直读 README 表格），且新旧两路输出对齐一轮；
3. 至少一封新信**完整走通**"台账 → 投影生成判例包 → 发出 → 回件解析 → 回写台账"全链；
4. 度量脚本能直接产出"口径点提出 → 销点"中位数，与现行信级代理指标同期并跑一轮做对照。

**价值指标**（三类取二）：

- **质量型**：口径点"承接载体缺失"数量 —— 基线由本包交付时的首次全量扫描确定，目标归零并保持；
- **风险型**：跟进信编号／状态两份副本互相印证着一起错的复发次数 —— 基线 ＝ **6 次**（README 原文自陈第二至第六次复发，加上 2026-08-10 未编号的首次；日期＝08-10／08-12／08-18／08-21／08-25 两处），目标交付后 **0**。
- 基线由业务 Champion（Shao Peishen）在启动前确认存档。

**LLM 判据黄金集**：
本包**含 LLM 运行时判断**——"回件自由文本 → 拆成几个点 / 每点状态如何"是模型判断。
黄金集计划：以已闭环 17 封信的**冻结回件原文 ＋ 专家认可的拆点结果**为首批黄金集（目标 ≥17 组）。🔴 **无黄金集不晋档 3。**

## 🔴 退休哪一个既有守卫（机制/环境类变更包强制，协议〇.9 措施 B）

**退休对象：README 表格「编号」列作为取号依据的地位，以及本变更覆盖到的"人写的自由文本进了机器要读的位置"那一处。**

具体：

- **可退**：README「下一个可用号」段与下表「编号」列这**两份自由文本副本**——本包落地后取号一律从台账派生（台账 `id` 是稳定标识、由机器分配）。这两处已实测**六次互相印证着一起错**，是本仓库同族复发次数最高的一处。退休方式 ＝ **降为派生视图**（继续显示、但不再是判据来源），不删除。
- 🔴 **不可退，且必须写明为何不能**：
  - **README「发送状态」列**——它是 2026-08-21 你答 §四 #85 选 (b) 确立的"一封信状态的唯一权威源"。本包管的是**点**，不是**信**；两者是不同粒度的两件事，**不得借本包之机把信级权威源也一并改掉**（那会同时动两个口径，出问题时无法定位是哪一个引起的）。信级权威源的调整属 R2，另包处理。
  - **判例批改法本身**——它解决的是"怎么问"，本包解决的是"问出来的东西存在哪"，不同层，不构成替代关系。

### 🔴 格式改判的成因（本节最值钱的一条，写清免得后人再撞）

草案设想台账用 `.jsonl`，并在本节写着「必须进版本控制——它是『受版本控制的产物』这一设计的全部意义所在」。**实跑发现它会被 `.gitignore:32` 的 `**/*.jsonl` 全局规则吞掉。**

那条规则的注释原文是：

```
# 所有运行时审计 JSONL — 含业务数据，绝不入库
**/*.jsonl
```

⇒ **它挡的是「含业务数据的运行时审计」**（现存命中项：`fi2_audit.jsonl`／`connector_access.jsonl`／`sc8_real_validation.jsonl` 等）。**口径点台账是受版本控制的设计产物，性质与之相反——它撞规则纯粹是因为共用了扩展名。**

**三条出路实测对比**（`.yaml`／`.md`／`.json`／`.ndjson` 均实测会入库）：

| 方案 | 判定 |
|---|---|
| **`.yaml`（Shao Peishen 2026-09-02 答 (a) 采用）** | ✅ 会入库、人可读可手改、**diff 友好**（一点一条，改一个字段只动一行）。台账量级几百条，读-改-写整文件无性能问题 |
| 保 `.jsonl` ＋ 加例外 `!**/口径点台账*.jsonl` | ❌ **在一条写着「绝不入库」的规则上凿洞**，后人读 `.gitignore` 会困惑；且例外规则本身是新形态，又要走一遍 #328 核实 |
| `.md` 表格 | ❌ **正是要根治的病**——README 表格 506 处交叉引用、编号滞后复发 6 次；台账要机器读，不该退回 md 表格 |

🔑 **这个问题只有实跑 `git check-ignore` 才会暴露。** 草案里那句「落包时必须补上三行真实输出，缺则 proposal 不完整」当时只是照规矩办事，**没料到真会撞上**。⇒ **#328 那条 MANDATORY 不是形式，它真能拦住东西。**

⚠️ **遗留约束**：本包所有新增受控文件**不得使用 `.jsonl` 扩展名**；运行时派生物一律落 `reports/`。实现期若出现第四种文件形态，**回到本节重新实测**，不得沿用本结论。

**红线核对：**

| 红线 | 核对结论 |
|---|---|
| **mock 先行** | ✅ 回溯拆点先在 17 封已闭环信上跑（结果已知，可对答案），再动未闭环的 15 封 |
