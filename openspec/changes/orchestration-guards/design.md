# orchestration-guards Design

> 方案层面的判据已由 Shao Peishen 在 `构建环境瘦身第三轮-编排层方案-2026-09-05.md`
> 拍板（"全部优化，稳健推进"）与派单件 `OP-0905-Q`（P2/P4/P7① 明标 A 类）敲定；
> 本文件只记录**方案原文未细化到实现层的具体选择**——如后续要改判，回这里找决策点，
> 不必翻代码猜"当初为什么这么写"。

## 决策点 D1 · 撞号查重的扫描范围与短形锚点

**选择**：扫描面固定为 `1-转型规划/` 目录下的 `.md`（不含 `.py`/其它目录），短形只认
`\[Win\](\d{4})([A-Za-z0-9]+)-` 这个结构锚点，不做全文裸数字子串扫描。

**理由**：① `opener骨架.md` 文末既有的人工取号 `grep` 命令本身就是 `grep -rhoE
"OP-?[0-9]{4}-?[A-Za-z0-9]+" 1-转型规划`——本包只是把这条命令的判定逻辑机器化，
扫描面刻意不扩大，保持与既有人工流程同一套范围认知，避免"机器守比人守更严"造成
新的困惑。② 骨架原文明写"短形 `MMDDX` 只用于 session 名"——若不锚定 `[Win]` 前缀，
任何正文里出现的四位数字巧合（日期、金额、行号）都会被误判为"已用编号"，反而制造
假撞号，比不做查重更糟。

## 决策点 D2 · §三泳道解析器的识别判据（只认两个锚点）

**选择**：`parse_section_three_lanes` 只依赖 `### A<N>` 标题 ＋ 代码块内一行
`【设置】` 开头，不检查首行是否符合 `[OP-MMDD-X]【CC】<短名>` 的精确格式（那是
`工具-opener块lint.py::check_block` 的职责），不要求"做什么"/"不做什么"字样。

**理由**：这正是 P2 要验证的东西——3 行精简版与旧长版本的唯一共同点就是这两个
锚点，其余（是否有做什么小节、行数多少）都会因这次精简而改变。若解析器绑定了
更多细节（例如要求首行严格匹配 `[OP-...]` 正则），精简后格式的任何微调都会让
"数泳道条数"这个基础能力跟着碎，把两件独立的事（格式对不对、数量对不对）耦合
在一起——首行格式对不对已经有 `工具-opener块lint.py` 的形态⑤单独守着，本函数
不该重复实现它、更不该把"识别得出"和"写得对"绑成一件事。

## 决策点 D3 · index.lock 撞击是"记录入口"而非"自动侦测"

**选择**：`record_lock_hit` 是一个显式调用点，由撞锁的一方（看护者或子任务）在
真的遭遇 `.git/index.lock` 冲突时主动调用；本包不接 git hook、不做进程级探测。

**理由**：方案原文 P4 的产出物是"summary 统计本批 index.lock 撞击次数"，没有要求
"自动侦测"——先把"记录 + 现取汇总"这个最小闭环做出来，能不能自动侦测是下一层
问题（需要接 pre-commit/post-checkout hook 或轮询 `.git/index.lock` 文件存在性，
后者本身就有假阳性风险：合法持锁 0.1 秒内的正常 git 操作也会被探测到，需要额外
的阈值判断，属于另一个决策点，不在本次范围内一并拍板）。如实标注在 proposal
「已知残余风险」第 2 条，不假装已经解决。

## 决策点 D4 · variant 参数而非新增独立生成函数

**选择**：在既有 `generate_opener()` 上加 `variant` 参数分支，而不是新写
`generate_subtask_lane_opener()`/`generate_guardian_opener()` 两个独立函数。

**理由**：十项必填字段校验（`_require_all_fields`／`_validate_spec` 的大部分规则）
与撞号查重（P7①）对三种变体都适用，只有分支字段格式（guardian 是固定字面量而非
slug）、是否含 `set_session_title`、正文结构三处随变体变化——拆成独立函数会把这
三处共性判据复制三份，正是本项目「同一判据两处各自实现然后漂移」的既定反模式
（`queue_table.py`/`工具-opener块lint.py` 文档里反复点名的坑）。分支集中在一个
函数内，判据只写一份。
