## Why

`OP-0904-A` 会话复盘（见方案文档 §四出处）指出编排层三处摩擦：

1. **P2 · 看护件体积失控**：§三 每条泳道内嵌完整 opener，7 条泳道能把一份看护件撑到
   28 KB；「做什么／不做什么」本就该活在队列行里（任务正本本来就在那），不该在看护件
   里复制一份。收窄前必须先验证：把泳道 opener 精简到 3 行（首行＋【设置】＋读行）后，
   `工具-泳道看护状态机.py` 现有的"数一批有几条泳道"能力还在不在——**它此前根本不存在
   这项能力**（现场取证：该工具此前只做单泳道级别的 pause/resume/summary，没有解析
   看护件 §三 全文、批量数出泳道条数的入口），故 P2 的产出不是"改一个已有解析器"，
   而是"新增一个只依赖两个结构锚点（`### A<N>` 标题 ＋ 【设置】行）、不依赖代码块行数
   的解析器"，并当场验证 3 行版与旧长版本同样能被数对。
2. **P4 · 并行撞锁与合并越界**：七条泳道并行 + sweep + 总线各自 `git commit`，
   `.git/index.lock` 反复撞，逼得总线自己去 commit（越界，违反"总线不 commit"口径）。
   方案给的对策是两句默认口径（并行上限 4、错峰 ≥90 秒；子任务只 push 分支不 ff
   master）——本包让这两句从"人记得写"变成"生成器无条件写入"，并给状态机加一个
   「本批撞了几次锁」的现取计数（`summary` 现有汇总缺这一项，此前只能靠人回忆）。
3. **P7① · 撞号**：`OP-0904-E` 当天两条互不知情的线各自取了同一个编号——取号规则
   写在 `opener骨架.md` 文末，但那是一条 `grep` 命令，人守就会漏跑。本包把它挪进
   `工具-opener生成.py` 的必经咽喉（`generate_opener` 内置校验），撞号直接拒绝生成、
   报出下一个空号。

## What Changes

- **P7①（`工具-opener生成.py`）**：`generate_opener()` 新增当日已用编号查重——扫
  `1-转型规划/` 全树 `.md`，收集全称（`OP-MMDD-X`）与短形（`[Win]MMDDX-`，仅认这个
  锚点，不做裸子串扫描）两种形态的已用后缀；命中当前 `--op-id` 的 mmdd+后缀 ⇒ 拒绝
  生成，错误信息直接给出当日下一个空号。
- **P2（`工具-泳道看护状态机.py`）**：新增 `parse_section_three_lanes()`（只依赖
  `### A<N>` 标题 ＋ 代码块内 `【设置】` 行两个锚点，不依赖行数、不要求"做什么"字样）
  与 CLI 子命令 `dry-run --file <看护件路径>`，报「§三 解出泳道 M／N 条」，逐条列出
  未识别原因。**现场实测结论**：对真实看护件 `看护件-泳道看护批B-0905_C-2026-09-05.md`
  （旧长版本）跑通 4/4；对构造的 3 行精简版样例跑通 2/2——**解析器无需为"识别 3 行版"
  再做改动**（P4 原文条件句「不识别再改解析器」的分支未触发，如实记录，不是"跳过
  未做"）。
- **P4（两处）**：
  1. `工具-opener生成.py` 新增 `variant` 参数（`standard`／`subtask_lane`／
     `guardian`），后两者对应骨架【CC · 子任务泳道】与 §三bis 变体（此前生成器完全
     没有这两种变体的产出能力，只能手写）。`subtask_lane` 变体收尾无条件追加两行
     默认口径（并行上限 4／错峰 ≥90 秒；push 不 ff）；`guardian` 变体正文追加同一条
     口径的看护者视角措辞（指导它怎么用 Task/Agent 起子任务）。
  2. `工具-泳道看护状态机.py` 新增 `record_lock_hit()`／`count_lock_hits()`／CLI
     `record-lock-hit`，`summary` 输出新增第三行「本批 index.lock 撞击 N 次」（现取，
     不手工数，与既有「本批停 N 次」「本批转出 N 项」同一 D6 现取哲学）。
- **不改**：`opener骨架.md` 正文（口径文字仍归 Cowork `OP-0905-P` 改，本包只在代码
  侧默认写入其结论）；`工具-opener块lint.py` 判据本身不变，仅在 `generate_opener`
  自校验调用处按变体传入既有的 `is_subtask_lane` 参数（该参数形态⑥上线时已存在，
  此前从未被 `generate_opener` 使用过——`generate_opener` 只会产标准变体，用不到它）。

## 三处载体是否同改（P4 表述里"机器守：生成器默认写入①②"的落点核对）

只有**一处**载体——`工具-opener生成.py` 本身（生成器代码即口径的唯一权威实现）；
`opener骨架.md`／`skills源码/zhuopin-lane-watch/SKILL.md` 的口径文字改动是 `OP-0905-P`
（Cowork，与本包并行）的范围，本包不越界改 `.md` 正文，只保证代码侧的默认行为与那份
文字最终定稿的方向一致（两句默认口径的措辞取自方案文档原文，如两份最终定稿措辞有
出入，以 `opener骨架.md` 为准，本包代码侧措辞需要跟改，非本次范围内的漂移）。

## Capabilities

### New Capabilities

- `orchestration-guards`：opener 生成器当日撞号拒绝（P7①）＋子任务泳道/看护者变体
  默认写入并行与 push 口径（P4-1）；泳道看护状态机新增 §三泳道 dry-run 解析（P2）与
  index.lock 撞击计数（P4-2）。

### Modified Capabilities

- `工具-opener生成.py::generate_opener`：新增前置校验（撞号查重）与 `variant` 分支；
  同一组标准变体输入（`variant` 省略或 `"standard"`）产出与改动前逐字相同（回归见
  `PositiveGenerationTests`／`ValidationEdgeCaseTests` 全绿，未改一条既有断言）。
- `工具-泳道看护状态机.py::_cmd_summary`：输出新增第三行「本批 index.lock 撞击 N
  次」；既有两行（停 N 次／转出 N 项）措辞与顺序不变。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？** 两处：① **"这个编号今天用过没有"**——此前
   靠人记得跑一条 `grep` 命令、肉眼扫结果，`OP-0904-E` 就是这一步被漏掉；本包把它
   显性化为生成器内置的必经校验，撞号连生成都生成不出来。② **"3 行版会不会把泳道
   数错"**——此前没人验证过，纯凭直觉认为"应该没问题"；本包把它显性化为一次可重跑
   的 `dry-run` 命令，而不是"改完格式后祈祷没坏"。
2. **由谁显性化？** 决策人 Shao Peishen（方案文档拍板"全部优化，稳健推进"，派单件
   `OP-0905-Q` 指定判据已写死无需再问）；CC 建造车间负责实现、单测、对真实看护件的
   现场验证；backup ＝ 下一位改 `工具-opener生成.py`／`工具-泳道看护状态机.py` 的
   session 可凭本包与两份单测独立复核。
3. **用什么方法提取？** ① 真实事故反推——`OP-0904-E` 撞号、七泳道并行撞锁均为真实
   发生过的生产事件（非构造假设）；② 对真实看护件文件（`看护件-泳道看护批
   B-0905_C-2026-09-05.md`）做一次只读 `dry-run` 现场跑通，不是纯单测构造；③ 对真实
   仓库 `1-转型规划/` 树跑一次撞号查重（现场实测：`OP-0905-K` 命中真实存在的短形
   session 标题 `[Win]0905K-看护四泳道C`，`OP-0905-A` 当时未命中，与仓库当日实际内容
   相符，非构造夹具）。不涉及 LLM 判断，纯字符串/结构规则。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后所处档位**：跨项目治理机制，非独立业务场景，套用最接近的描述 ＝
  **档1 mock 验证**（代码与单测完成，已对真实文件与真实仓库树做过一次只读现场验证，
  但尚未在未来一次真实看护件生成流程里被使用过——`variant=subtask_lane/guardian`
  与撞号查重要等下一批看护件真正用这套生成器产出时才算"生产首次命中"）。
- **晋下一档（档2 真实数据跑通）的条件**：
  1. 下一批看护件用本工具的 `variant=subtask_lane`／`guardian` 实际生成至少一条
     泳道 opener 与一条看护者开场词（非本次单测构造）。
  2. 真实发生一次撞号被拒绝（非单测构造）——若长期零命中，正确表述是"未被检验"，
     不得表述为"该失效模式已消除"（同 `editlock-write-guard-hardening` proposal
     已确立的判据）。
  3. `summary --batch <真实批次>` 报出的 index.lock 撞击次数与该批实际发生的撞锁
     次数比对一致（需要看护者在真实撞锁时确实调用了 `record-lock-hit`——**本包只
     提供记录入口，不自动侦测撞锁**，这是本包已知边界，见「不做什么」）。
- **价值指标**（风险型）：编号撞号率——基线 ＝ 人工 grep（`OP-0904-E` 已实证会漏）；
  目标 ＝ 机器拒绝，撞号变成"生成不出来"而非"生成出来了才发现"。
- **LLM 判据黄金集**：不适用（纯字符串/结构规则，无 LLM 运行时判断）。

- 不改变既有标准变体（`variant` 省略或 `"standard"`）的产出格式一个字符——回归测试
  钉住这一点。

## 已知残余风险（如实写明，不粉饰）

1. **撞号查重的扫描面局限于 `1-转型规划/` 且要求 `.md` 已落盘可读**——若某条 opener
   仅存在于聊天记录、尚未写入任何 `.md` 文件，本包查不到它，仍可能撞号（与骨架文末
   人工 `grep` 命令本身的局限一致，本包未扩大也未缩小这个盲区）。
2. **index.lock 撞击计数依赖人／子任务主动调用 `record-lock-hit`**——如实标注为
   "记录入口"而非"自动侦测"，见「不做什么」第 3 条；若未来发现调用率低，需要另立
   变更包评估是否要接一个真正的 git hook 或进程级探测。
3. **`variant="guardian"` 的正文措辞（"你是本批的看护者，不是执行者"等）是本包按
   `opener骨架.md` §三bis 模板固定写死的**——若骨架该节改版，生成器需要跟改，本包
   未建立"骨架改了、生成器自动感知"的机制（现状与标准变体的 `title_call`／
   `_read_line` 等既有拼装逻辑一致，非本包引入的新局限）。
