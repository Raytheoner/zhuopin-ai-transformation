## Why

### 三处缺陷是同一件事的三面：写侧比读侧弱一档

读侧 `queue_table.split_row_cells`（经 `_mask_backtick_spans`）按 CommonMark 反引号游程规则识别跨度，跨度内的竖线不算列分隔符——这是队列表格解析的权威实现（`queue_table.py` 文件头注释：队列 #306/#307「转义与列数校验收归权威模块」）。**写侧完全没有对等能力**：

1. **`#324` 未闭合⑵ · 竖线守卫非反引号感知致状态字段锁死**：`cmd_edit_row` 对 `--set`/`--append` 传入的新值调用 `queue_table.has_bare_pipe(value)`，该函数文档原文自陈"不做反引号感知，即便竖线被反引号包裹也一样会被切列"。于是 §一 #324 行内合法存在的 4 处反引号包裹竖线（引用朴素切列函数的代码片段）导致该行状态字段**整格重写被拒绝、写定即锁死**——`--append` 只能加尾巴，改不了 `[S:]` 前缀，锁死后无法翻转状态。**这一半是"该放行的被拦"**：读侧认为安全（跨度内竖线不算分隔符）的内容，写侧一律当作危险内容拒绝。

2. **`#454` ⑴ · 反引号奇偶未校验致行塌列**：一次改判把分诊器给出的引文片段按 60 字硬截断，恰好在 `#337`/`#422` 两行行内把一个反引号截断，导致该值反引号游程变成奇数（未闭合）。`cmd_edit_row` 写入前只检查了传入值的裸竖线（且如上文，检查本身不区分是否被反引号保护），**从未检查反引号奇偶，也从未在拼装出最终整行字符串后回读切列数**——`validate_row_cells(new_cells, source="parsed")` 校验的是 Python 列表 `new_cells` 的长度，而 `--set`/`--append` 只替换列表中某一列的值、不增删列表元素，**该列表长度在构造上恒等于旧行列数，无论新值把整行写成什么样都不会变**，因此这项校验对"新值让最终整行反引号奇偶被破坏、进而被读侧按跨度规则吞掉一个真分隔符"这条路径**没有任何检测能力**。两行因此由 8 列塌成 7 列，写入照常成功，直到之后 `release` 的事后结构门禁（`_validate_release_structure` ①列数校验）才拦下。**这一半是"该拦的被放行"**——与 #324 互为镜像的同一枚硬币的另一面。

3. **`#454` ⑵ · 已塌列行的 `--repair` 逃生入口缺失**：`#337`/`#422` 被写坏后，`edit-row` 对已塌列的行（列数≠该分区预期列数）拒绝一切操作，含 `--append`，理由正是"列数为 7，应为 8"——**行一旦被写坏，唯一能修复它的入口把自己也关上了**。当次只能在持锁状态下用脚本改文件绕过，锁全程未释放。

**三者共享同一根因**：写侧的裸竖线检测（`has_bare_pipe`）与读侧的反引号感知切列（`split_row_cells`）走的不是同一套判据；且写侧从不对自己"即将真正落盘的那个字符串"做一次回读验证，只验证了一个构造上不可能出错的中间量（Python 列表长度）。**合并处置**：让写侧对新值先做反引号奇偶校验（直接堵住 #454 的破坏源头，同时不再对合法反引号跨度内的竖线一律拒绝，堵住 #324 的误锁），再对拼装后的整行做一次读侧同款切列的回读校验（defense-in-depth，兜住奇偶校验覆盖不到的任何其它路径），最后给已塌列的历史行开一个不绕过持锁、不绕过回读校验、只跳过"旧行列数须先合法"这一项前置检查的 `--repair` 入口。

### 为什么必须机器守，不能继续人工绕过

Shao Peishen 2026-09-02 给出的元判据（升级于本行既有那条「判人守还是机守，看有没有必经的咽喉」）：

> **「如果能做，就不要指派手工——会带入失误。」**——先问「有没有咽喉」（能不能机守）⇒ 再问「既然能，为什么还派给人」（该不该机守）。

`#324`、`#454` 两次实证都不是"没有咽喉"——`edit-row`/`append-row` 本就是队列写入的唯一入口（协议〇.7），能做的判据都能挂在这个咽喉上。真正发生的是"能做却没做"："去掉反引号绕开配对"（#324 当次处置）与"持锁状态下用脚本改文件"（#454 当次处置）都是**人工绕过**，且绕过本身还会**削弱判据未来的真实拦截力**（#324 行内原话："一旦'去掉反引号'成为惯用绕法，⑥ 想拦的那个真实误发场景也会一并拦不住"）。**这正是本条元判据要防的失误**：人工绕过不是解决，是把同一个坑留给下一个撞上它的人（#454 本身就是"下一个人"）。⇒ **三处缺陷都必须机器守，不接受"下次小心点"式的人工纪律**。

## What Changes

- **① 反引号奇偶校验（新增，堵破坏源头）**：`queue_table.py` 新增 `has_unbalanced_backticks(text) -> bool`（或等价具名判据），复用 `_mask_backtick_spans` 已有的反引号游程扫描算法，但语义相反——**扫描到某个反引号游程找不到同长度闭合游程即判定为"未闭合"**（`_mask_backtick_spans` 对这种情形选择"视为普通文本"以贴合 Markdown 渲染器行为，适合**读**已落库的历史内容；**写**新值时，一个未闭合的反引号游程在绝大多数场景下就是一次错误——截断、误敲、复制丢字符——不应被静默接纳）。`cmd_edit_row`/`cmd_append_row` 对每一个新写入的单元格值先跑这项校验，不通过即拒绝写入、报出具体是哪一列。
- **② 写入后列数回读校验，不符即回滚（新增，defense-in-depth）**：`cmd_edit_row`/`cmd_append_row` 在拼装出最终要落盘的整行字符串（`new_line`）之后、真正写文件之前，用**与读侧同一个函数** `queue_table.split_row_cells(new_line)` 回读切列，比对列数是否等于该分区预期列数（`SECTION_COLUMN_COUNTS`）。不符即**拒绝本次写入**（不落盘，等价于"回滚"——因为落盘动作被挪到这项校验之后才发生，从未成功过的写入无需真正撤销）。**`append-row` 现有的"写入前最终校验"（约 L2065-2071，`new_line.strip("|").split("|")`）用的是裸 `split`、非反引号感知，本次一并替换为 `queue_table.split_row_cells`**，与读侧、与 `edit-row` 新增的这项检查口径统一（否则会在 append-row 侧对合法反引号跨度内竖线重犯 #324 同类误判）。
- **③ 已塌列行的 `--repair` 逃生入口（新增）**：`edit-row` 新增 `--repair` 开关。**默认路径不变**——写入前仍先校验目标行的**当前**列数是否合法，不合法即拒绝一切操作（含 `--append`），维持"不假装能安全编辑一个已经不知道结构的行"这一现有立场。传入 `--repair` 时，**只跳过这一项"旧行列数须先合法"的前置检查**，其余判据（本次改动值需过 ①，拼装结果需过 ②）**全部照常执行、不放宽**——`--repair` 能且只能把一行从"不合法"改成"合法"，不能在此过程中引入新的不合法。
- **不改动**：`0-学习与工具/工具-共享文档编辑锁.py` 中与本三项无关的其余校验（①～⑩）、release 结构门禁本身、`_diff_touched_rows` 口径；不追改 `#324`/`#454` 已经手工绕开的那两行历史内容（历史记录不追改，见「不做什么」）。

## 本次替代哪一项既有校验（如实标注，非协议〇.9 的人守规则退休——这是同一层内的判据升级）

`cmd_edit_row`/`cmd_append_row` 现有的 `queue_table.has_bare_pipe(value)` 前置检查（对新值做朴素裸竖线子串扫描，文档已自陈"不做反引号感知"）在 ① ② 上岗后**被功能性替代**：
- 合法反引号跨度内的竖线：`has_bare_pipe` 一律拒绝 → ①（奇偶合法）+ ②（回读列数不变）都放行，不再误锁（修 #324 那一半）。
- 真正会撑列的裸竖线（不在反引号跨度内）：`has_bare_pipe` 拒绝、① ② 也会拒绝（② 回读列数会对不上）——**不放松**这一半。
- 因此 `has_bare_pipe` 这一步检查在 `cmd_edit_row`/`cmd_append_row` 内**冗余**，tasks 中一并移除其调用点（`queue_table.has_bare_pipe` 函数本身保留，其它调用方——如批量清理历史行的场景——不受影响，只移除本次两个命令里这一处过度保守的前置拦截）。

## Capabilities

### New Capabilities

- `editrow-write-guard-triad`：`edit-row`/`append-row` 写入前对新值做反引号奇偶校验，拼装结果对最终整行做读侧同款回读列数校验（不符拒绝写入），并为已塌列的历史行提供 `--repair` 逃生入口（仅跳过旧行合法性前置检查，其余判据不放宽）。

### Modified Capabilities

- `cmd_edit_row` / `cmd_append_row` 的写入前校验语义：由"新值裸竖线子串扫描（不区分反引号保护）"改为"新值反引号奇偶校验 + 拼装结果读侧回读列数校验"。同一输入下行为变化见「What Changes」①②。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？** 两处：① **"这处反引号包裹的竖线安不安全"**——此前完全靠人眼判断"这是合法的代码引用还是真会撑列"，`#324` 当次就是靠人工去掉反引号绕开，判断本身不留痕、下一次遇到同类场景还得重新判断一遍；本包把它显性化为一条与人的记忆无关的机器判据（跨度配对是否闭合 + 回读列数是否对得上）。② **"这一行已经塌列了，还能不能碰"**——此前靠人判断"要不要在持锁状态下用脚本硬改"，`#454` 当次就是这样绕过的；本包把它显性化为 `--repair` 这一条有边界、可审计的正式入口（仍过 ①②，不是"绕过检查直接改文件"）。
2. **由谁显性化？** 决策人 Shao Peishen（design 审拍板 ①②③ 的具体实现细节，本包止步于起草、不代拍板）；CC 建造车间负责判据实现、单测、对 `#324`/`#454` 两行的历史夹具做只读回归核对；backup ＝ 下一位领取 `#455` 的 session 可凭本包与 design.md 独立复核。
3. **用什么方法提取？** 历史真实案例反推（`#324` 的锁死复现、`#454` 的两行塌列复现，均为真实生产队列数据，非构造假设）＋ 对现网两份队列文件全量跑 ① 校验（只读、不落盘），确认现存反引号跨度是否都能通过奇偶校验、是否还有其它已塌列但尚未被发现的历史行需要 `--repair`。不涉及 LLM 判断，纯字符串/结构规则。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：跨项目治理机制，非独立业务场景，套用最接近的描述 ＝ **档1 mock 验证**（design 审通过、代码与单测完成、对现网两份队列全量只读回归跑过，但尚未在生产真实拦下一次"新写入奇偶不合法"或真实用过一次 `--repair`）。
- **晋下一档（档2 真实数据跑通）的条件**：
  1. 真实发生一次"新写入反引号未闭合"被 ① 拒绝（不是单测构造），提示文案足以让操作者知道错在哪一列、该怎么改。
  2. 真实发生一次 ② 回读列数不符被拒绝（同样非单测构造）——若交付后长期零命中，正确表述是"未被检验"，不得表述为"该失效模式已消除"（同 `editlock-write-side-date-guard` proposal 已确立的"零命中不得读成规则已生效"判据，`根 CLAUDE.md` 已有同形教训 §四 #58/#122/⑥）。
  3. 真实用 `--repair` 修复至少一行历史已塌列的行（候选 ＝ `#337`/`#422`，若届时仍未被其它方式修复），事后核实修复结果通过 `release` 的结构门禁。
- **价值指标**（风险型）：队列行被写坏后能否自行修复——基线 ＝ 只能持锁状态下脚本改文件（`#454` 实证）；目标 ＝ `--repair` 走正门、留痕、仍过双重校验。
- **LLM 判据黄金集**：不适用（纯字符串结构规则，无 LLM 运行时判断）。

## 已知残余风险（如实写明，不粉饰）

1. **① 的"未闭合即拒绝"会拒绝一种理论上合法但本项目从未出现过的写法**：故意在单元格内写一个孤立反引号作为标点（不构成任何 code span）。**如实评估**：本项目现网两份队列全量取证（tasks 1.x）尚未发现这种用法；若 apply 期实测发现真实存在，需要回到 design 决策点重新评估是否需要转义逃生阀，而不是本包预先假设不存在。
2. **③ 的 `--repair` 不是万能修复**——它只跳过"旧行列数须先合法"这一前置检查，若目标行除列数外还有其它结构性损坏（如整行编号列非法），`--repair` 后仍会被 ①②或其它既有校验（③～⑩）拦下，需要人工判断如何改写传入的新值，不是"一键自动修复"。
3. **本包不覆盖 `append-row` 现有裸 `split("|")` 之外、`_validate_release_structure` 内其它校验的反引号感知程度**——若那些校验本身也存在类似的读写口径不一致，本包不隐含"已一并修复"，需要另立行处置。
