# queue-domain-strict-routing Proposal

## Why

队列 `#341`（2026-08-17 立行，Shao Peishen 当日拍板 (a) 新建行承接）指出：`queue-dual-file-split` 归档时明列的两条独立后续——**写侧按 `[D:机/业]` 精确路由尚未实现**、**跨文件高水位线同步的完整语义未做**——从未有活载体承接（原挂靠的变更包 3.7 行随归档失效），且两份主 spec（`queue-dual-file-topology`／`editlock-dual-queue-routing`）里各有一处"归档时如实登记的实现差异"标注，写的是目标态而非实现现状，长期分叉不收口。真实实例非假想：§一 `#336`（`[D:业]`）自 2026-08-15 起就位于机制环境文件，系机器人 `queue_appender` 与编辑锁 `append-row` 在未声明域时统一落机制环境文件（design.md 决策点 3 的"迁移期妥协"）所致；2026-08-17 拆件巡逻对它是就地销行、未搬家。

**本次 design 复核过程中另有两处白盒实测发现，`#341` 原文未点名，一并纳入本包**：

1. **锁粒度与 spec 描述不符**——`editlock-dual-queue-routing` spec「锁粒度」Requirement 与其"📌 来源"标注均称"独立锁已是既成实现"，但实测 `0-学习与工具/工具-共享文档编辑锁.py::QUEUE_LOCK_ANCHOR = QUEUE_MECHANISM_PATH_REL`（该模块行 386）——队列系统模式下 `acquire`/`append-row`/`release`/`status` 全部锚定同一把锁（机制环境文件的锁），并非"两份文件各持一把互相独立的锁"。这**不是尚未达成的目标态**，而是 spec 从写入那一刻起就记错了既成事实（design.md 决策点 7 原是"独立锁"倾向 + Open Questions 待验证，2026-08-17 归档时被误记为"已拍板独立锁、已是既成实现"，未察觉真实代码走的是相反方向的保守选择）。
2. **`#341` 期望产出③"跨文件高水位线同步的完整语义"其实已经被①的解法顺带解决**——正因为锁是统一锚点而非独立两把，两个域的队列系统写入从不会同时进入各自独立的临界区，高水位线（唯一跨文件共享的可变状态）不存在需要被"同步"的竞态窗口。design.md 决策点 7 的顾虑本身已被现实现规避，只是从未被如实记录为"已解决"。

## What Changes

- **§二/§一/§四 写侧未声明域时的处置**：两阶段收紧（决策点 1）——不静默默认落机制环境文件，也不一步到位改拒绝（现网 `专线opener模板库.md §〇.7` 明文记载 `--domain` 为可选参数，在途调用规模不明，一步到位会重蹈 2026-08-11 迁移期妥协本身诞生时同样的顾虑）。机器人 `queue_appender`／`repo_paths.py::DEFAULT_QUEUE_RELATIVE_PATH` 一侧不受两阶段约束——直接改默认目标为业务场景文件，恢复方案件 §6.5 建议 4"机器人 100% 盲写业务队列"的原始设计意图（机器人自身产生的行按其性质定义即为业务域，机制域行只应由人工/CC 巡逻升格产生，机器人从未也不应直接产生机制域行——此为改默认值，非收紧为拒绝，不影响任何现网调用方的调用参数）。
- **正式追认"统一锚点锁"为永久设计**（决策点 2），取代 design.md 决策点 7 悬而未决的"独立锁"候选；同步修正 `editlock-dual-queue-routing` spec「锁粒度」Requirement 与其失实的"📌 来源"标注。
- **存量错位行处置口径**（决策点 3）：延续"历史记录不追改／不擅自搬动历史行"纪律，就地留存＋标注，不搬家；同时补齐当前完全未被任何消费者实现的"跨文件一致性交叉校验"（`queue-dual-file-topology` spec 既有 Requirement，2026-08-17 归档至今零实现），使 `#336` 这类错位此后能被值周巡检/`工具-队列结构lint.py` 自动发现，而非仅靠拆件巡逻偶然路过。
- **两份 spec 的"实现差异"标注更新方案**（决策点 4）：`queue-dual-file-topology`「§二 域路由」与 `editlock-dual-queue-routing`「acquire/append-row 按域路由」两处标注保留，补充两阶段收紧的日期指针，阶段 (b) 落地后由后续变更包移除；「锁粒度」标注本次直接更正（描述的是既成事实之误记，不是等待代码补齐）。

## 本次退休哪一个既有守卫（`openspec/config.yaml` 机制类变更包强制问询）

**本次不退休任何既有守卫，理由如下**：本变更是 propose＋design 阶段的方案与文档修订，**不产出任何代码改动**（队列 `#341` 明示"止步于起草不代拍板"，`--domain` 收紧的实际代码落地留待 Shao Peishen 批准 design 后的 apply 阶段变更包）——没有代码改动就没有守卫因本变更被替换或移除。**唯一相关的候选已如实登记供 apply 阶段执行**：决策点 1 阶段 (b)（fail-loud 生效）落地后，`工具-共享文档编辑锁.py` 现有的"未声明 `--domain` 时打印'建议此后显式传 --domain 机|业'"这一软提示分支（模块行 1924／2036）将成为永远不会触发的死代码（届时未声明会被直接拒绝，走不到这条提示），届时应随之删除，本 design.md 已列入 Migration Plan 供后续 apply 包据此退休。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？** 两处：① **"迁移期妥协是否已到期、该不该转正为永久口径"**——此前完全靠人凭印象判断（design.md 原文写"迁移期"却未附退出条件与日期），本包把它显性化为一条附具体日期的两阶段收紧计划（决策点 1）。② **"design 阶段的推荐候选与 apply 阶段的实际实现是否一致"**——`queue-dual-file-split` 归档时把 design.md 决策点 7 的"独立锁倾向、待验证"误记成"已拍板独立锁、已是既成实现"，无人回头用源码核对，本包把"归档时的自我表述"与"白盒读代码得到的事实"做了一次逐字对照（决策点 2），并把这一对照方法本身沉淀为可复用的判据。
2. **由谁显性化？** 持有人 Shao Peishen（design 审拍板）＋ backup CC 建造车间（判据实现、单测、apply 阶段真实场景验证）；下一位领取 apply 任务的 CC session 可凭本 design.md 附的源码行号（`工具-共享文档编辑锁.py` 行 386／1093-1121／1919-1926／2031-2039）与 `repo_paths.py` 行 41-48 独立复核，不需要重新通读全部源码。
3. **用什么方法提取？** 历史案例反推（`#336` 真实错位实例、`#420` 历史锁域分裂旧案、决策点 7 原 Open Questions 措辞）＋ 现网源码白盒核实（非推断——逐行核对 `QUEUE_LOCK_ANCHOR`／`_resolve_append_target`／`DEFAULT_QUEUE_RELATIVE_PATH` 的注释与实际取值，发现 spec 与代码的三处真实落差，两处 `#341` 已点名、一处本次复核新增）。不涉及 LLM 运行时判断。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：本变更为**跨项目治理机制**（队列写入咽喉的域路由与锁语义，全项目共用），非独立业务场景，不适用四档"对客交付"口径；本次交付止步于 **design 审前置**——`openspec validate --strict` 通过、四个决策点均附推荐与默认项，尚未进入档 1（mock/单测验证），代码零改动。
- **晋下一档（档 1，apply 阶段 mock/单测验证）的条件**，逐条：
  1. Shao Peishen 就四个决策点逐条批复（或整体按默认项批准）；
  2. 决策点 1 阶段 (a)（软警告升级 + 模板库 `--domain` 改为必需 + 公布阶段 (b) 生效日期）落地并观察至少一个完整值周巡检节拍（约 7 天），确认无在途调用因阶段 (a) 而失败（阶段 (a) 本身不拒绝写入，理论上不应有失败，此项验证的是"警告是否被看见、模板库改动是否覆盖了实际调用点"）；
  3. 决策点 1 阶段 (b)（fail-loud 生效）到期后，对现网两份队列真身实测"未声明域"的调用是否已归零（`工具-队列查询.py --digest --grep` 抽样，不得整文件通读，见 K3 口径）；
  4. 决策点 2 的 spec 更正落地后，新增单测钉住"队列系统模式下 `acquire`/`append-row` 两个域的锁路径逐字相同（均为机制环境文件的 `.editlock`）"，防止未来有人误读旧「独立锁」表述而"修复"成两把锁、重新引入决策点 7 担心的竞态；
  5. 决策点 3 的一致性交叉校验落地后，对现网两份队列真身跑一次全量核对，确认 `#336`（若仍可查）等历史错位行均被正确识别为"数据完整性告警"而非被误判为正常。
- **价值指标**（风险型）：① 写侧域路由精确率——基线＝现状不可测（未声明域时无从判断"本该进哪份文件"，只能靠事后巡逻偶然发现，`#336` 是唯一已知样本），目标＝阶段 (b) 生效后新产生的错位行数归零（历史错位行不追溯清零，按决策点 3 就地留存）；② spec-实现分叉——基线＝ 3 处已确认落差（`#341` 点名 2 处 ＋ 本次复核新增 1 处），目标＝本包 apply 完成后归零，且新增单测防止回归。
- **LLM 判据黄金集**：不适用（纯路径解析/锁语义/字符串匹配，无 LLM 运行时判断）。
