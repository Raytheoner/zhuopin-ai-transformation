> **本件＝design 审的输入，不是已通过的结论。** 泳道 `436-decision-field-guard`（`OP-0906-R`）已按泳道看护 D1 判据表在 🟡 档 `openspec_design_review` **停住**，不代拍板。

## 背景（一句话）

`决策点:` 字段 2026-07 至 08-10 被自发写了 18 次、覆盖率达 70%，08-11 起归零，根因是**漏写不产生任何信号**。skill v3.8 已补起草侧自检（人守），本包把同一判据挂到 `append` 这个不可绕开的登记咽喉上（机器守）。

---

## D1 · 要不要留逃生阀？🔴 需拍板

**现状实现：不留。** 没有 `--allow-missing-decision` 之类的开关，没有行内 `决策点豁免：` 标注。

- **(a) 不留逃生阀（现状实现，本方推荐）**
  - 依据：同族包留逃生阀的前提是「**合法的违规输入确实存在且常见**」（`editlock-write-side-date-guard` 的合法未来日期确实很多）。本闸的输入空间里**不存在合法的"没有 `决策点:`"**——纯通报信写 `0 项（…无需其决策）` 即可，而 `0 项` 已经是放行值。
  - 代价：真出现"必须马上登记、但信还没写 `决策点:`"的急事时，唯一出路是**回去把那一行补上**（成本约 10 秒）。没有后门。
- **(b) 留一个开关**
  - 代价：**一个不必要的豁免开关，就是这条闸未来失效的入口。** 本项目已有实证——判据一旦误杀真实语料，第一次跑就会被加豁免绕开（`工具-跟进信frontmatter校验.py` S3 的原话）。本闸不误杀真实语料，因此开关只会被用来绕过"我懒得写"。

## D2 · 要不要校验「这封信是不是本次要登记的那封」？🔴 需拍板

**现状实现：不校验。** `--letter-path` 指向哪封信就读哪封；不比对该信 frontmatter 的 `编号:`／`收信人:` 与命令行的 `--department`／`--recipient-cell` 是否一致。

- **(a) 维持不校验（现状实现，本方推荐**，理由见代价栏**）**
  - 风险：指错路径（例如复制上一封信的路径）时，本闸会检查**错的那封信**，闸形同虚设而**不报错**——这正是本项目最忌讳的"错误不产生任何信号"形态。
  - 但：新登记行的 `编号:` 由 CLI 自动取号，**信件起草时往往还不知道自己的编号**（`append` 的整个设计前提就是"未发出不占号"）。按 `编号:` 比对会**恒假**。按 `收信人:` 比对可行，但该字段实测存在**字段名分裂**（`收信人` 28 封 ／ `收件人` 19 封）与**取值格式分裂**（`IT部 · 陈承` ／ `唐燕萍（财务部 AI 专员）`），比对逻辑会立刻变成一堆特例。
- **(b) 现在就加「按 `收信人`／`收件人` 双名比对，取值做宽松包含匹配」**
  - 代价：把一个**已知未收敛的口径**（字段名分裂＋取值格式分裂，`工具-跟进信frontmatter校验.py` S2 判为 violation 而非改名建议、尚未治理）提前绑进本闸；口径一旦收敛（另一条在办线），本闸要跟着改第二次。
- **(c) 登记为一条追行，待 `收信人/收件人` 字段名与取值形态收敛后再加**
  - 代价：在此期间 D2 的风险（指错路径不报错）一直在，只靠人守。

## D3 · 存量 67 封信要不要豁免期？🔴 需拍板

**现状实现：不需要豁免期，因为本闸只作用于"新登记"。** 已在主表里的行不会再走 `append`，本闸碰不到它们；根 `CLAUDE.md` §1「历史记录不追改」自动满足。

- **(a) 确认无需豁免期（现状实现，本方推荐）**
  - 代价：无。但**若将来要给某封历史信补登记**（如归档件回迁），那封信也要现补 `决策点:`。
- **(b) 比照 `436-intent-gate`（泳道 A3）给一个到 2026-10-31 的存量豁免名单**
  - 代价：本闸没有"存量"可豁免，名单会是空的；空豁免名单是纯噪音，且**会给读者"这条闸有后门"的错误印象**。

## D4 · 本包与 `followup-readme-phase2` 的排序 🔴 需拍板

`followup-readme-registry` 这个能力的 spec **还在 `followup-readme-phase2` 变更包里、尚未 sync 进 `openspec/specs/`**（该包 tasks 5.4／5.5 未打勾）。本包对同一能力再出一份 `ADDED Requirements` delta。

- **(a) 先收尾 `followup-readme-phase2`（打完 5.4／5.5 并 archive／sync），再 apply 本包（本方推荐）**
  - 代价：本包的合入要等一步。
- **(b) 两包并行，apply 时人工确保 delta 不冲突**
  - 代价：同一能力两份在途 delta，`openspec sync` 的顺序会决定最终 spec 内容，**出错时不报错、只是内容悄悄少一段**。

## D5 · 判据放在哪一层（已落定，供复核）

放在 `append` 而**不是**放在 `工具-跟进信frontmatter校验.py --enforce`（后者是全量扫描器，跑在 CI/巡检节拍上，**发现时信已经登记了**）。`append` 是**写入前**的咽喉——同 `_assert_gate_open` 在 2026-09-06 从 release 事后拦截前移到写入前拦截的既有教训（避免"文件已改、release 被拒、锁未释放"的中间态）。

## D6 · 校验顺序（已落定，供复核）

`_assert_field_lengths` → `_assert_decision_points` → 读 README → `_assert_gate_open` → 取号 → 取锁 → 写。本闸排在**读 README 之前**：拒绝时连主表都不必读，更不取锁，零副作用。

## D7 · 复用而非重造（已落定，供复核）

importlib 复用 `工具-跟进信frontmatter校验.py::parse_frontmatter`／`RE_DECISION`（同目录既定手法，与已有的 `editlock`／`gate_query` 两处复用同形）。**不新造第二份 frontmatter 解析器、不自持第二份正则**——两处判据各自漂移正是同族病因。副作用检查：该模块的 argparse 全在 `main()` 内、模块级只有常量与正则，import 安全（已实测）。
