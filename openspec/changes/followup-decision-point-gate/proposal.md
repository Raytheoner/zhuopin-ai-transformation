## Why

### 一个被验证过、达到过 70% 覆盖率、然后无声死掉的实践

`决策点:` 是跟进信 frontmatter 里的一个字段，取值形如 `3 项（关闭触发 / 关闭权限 / 部分关闭审计）`。它**不是新设计的字段**——它在 2026-07 到 2026-08-10 之间被起草者自发写了 **18 次**，覆盖率一度达 **70%**；`design审前置-口径点台账三开放点收敛-2026-09-01.md` §2.2 ⑵ 的原话是：这条实践「**在成熟到 70% 时被无声掐断**」，断点精确落在 2026-08-10 与 08-13 之间，此后 **27 封信无一封写**，覆盖率 **70% → 0%**。

**根因不是人忘了写。** `工具-跟进信frontmatter校验.py` 的 docstring 已把它钉死：起草侧唯一的字段清单（`skills源码/zhuopin-followup-letter/SKILL.md:163`）当时**根本没列这个字段**；起草一旦走 skill，写出来的 frontmatter 自然只有三个字段。而**漏写不报错、不阻塞、不产生任何信号**——与本项目已反复吃过亏的「工具静默回退」「转态漏做不报错」完全同族：**错误不产生任何信号，所以永远不会被察觉。**

### 为什么"skill 里补一句"不够，必须落到咽喉

skill v3.8（2026-09-06，Cowork 已落）已在 §5 补入步骤 1bis 与 §6 红线，把「必写 `决策点:`」写进了起草侧自检。**但它自己在括号里写着「（登记 CLI `append` 校验为机器守，建成前人守）」** —— 起草侧自检是**人守**，而这个字段第一次死，死因正是"只有人守、无机器守"。`工具-跟进信frontmatter校验.py` 的 docstring 说得更直白：

> **「只加一条必写 `决策点:`」治不住**：该字段当初消亡的根因就是**无机器守**，只加一条必写而不配可执行校验，等于再造一个没人守的字段。

⇒ 本包补的就是那个机器守：**把判据挂到「一封信要进 README 主表，必须经过 `append`」这个已存在、不可绕开的咽喉上。**

### 为什么不是新建工具、不是新建判据

- **咽喉是现成的**：`工具-跟进信README登记.py append` 已经是 README 主表的**唯一登记入口**（`followup-readme-phase2` D1，且 `hooks-pretooluse-queue-read-guard.ps1` 已在门禁层把裸手 Edit 主表拦死）。不需要任何人额外记住一条新规则。
- **判据是现成的**：`工具-跟进信frontmatter校验.py` 已持有 `parse_frontmatter` 与 `RE_DECISION`（S3 判据，前缀锚定 `^\d+\s*项`）。本包 **importlib 复用它**，不新造第二份 frontmatter 解析器、不自持第二份 `决策点:` 正则——否则两处判据各自漂移，正是同族病因。
- **口径是现成的**：拆点判据 P1–P4 已在 `design审前置-口径点台账三开放点收敛-2026-09-01.md` §2.3 成文。

## What Changes

- **`append` 新增必填参数 `--letter-path`**：指向本次待登记信件的 `.md`（仓库根相对路径或绝对路径）。
- **`append` 新增前置校验 `_assert_decision_points`**，排在**读 README 之前**（拒绝时连主表都不必读，更不取锁）。四种拒绝形态，退出码 1，**都给同一句出路**（skill v3.8 §5 步骤 1bis 的写法 ＋ B 类通报信的 `0 项（…）` 形态）：
  1. 信件读不到（路径写错／文件不存在）；
  2. 信件不以 frontmatter（首行 `---`）开头；
  3. frontmatter 缺 `决策点:` 或其值为空；
  4. 取值形态不合 `letter_fm.RE_DECISION`（须以「数字＋项」开头）。
- **形态校验刻意只做前缀锚定、不校验括号内容**。全串锚定会误杀真实语料 `IT部#5` 的 `2 项（FO…／PO…），或告知已有的替代查询方式`；**一条把真实合法语料判成违规的判据，第一次跑就会被人加豁免绕开，等于没有**（理由原文在 `工具-跟进信frontmatter校验.py` docstring S3，本包复用即继承，不复述第二份）。
- **成功路径也回显守到的取值**：`[PLAN]` 行追加 `｜ 决策点=<取值>`。理由——**一条闸如果只在失败时说话，它自己就是下一个"不产生任何信号"的机制**（同族教训：`.51` 假零、skill 假零，2026-08-24 体检）。
- **`0 项` 必须放行**：通报类信的真实形态（实测语料存在），硬拦会**逼出假数据**——比字段缺失更坏。
- **本包只守「写没写」与「形态对不对」，不判点数对不对**：拆点是起草侧按 P1 做的专家判断，机器守不了。
- **不改 `set-status`**：本闸只挂 `append`（新登记），已登记行的状态流转不受影响。
- **不回溯已发信、不改 README 主表一个字节、不改 skill 源码**（skill v3.8 由 Cowork 已落）。
- **BREAKING**：是。改前可用的 `append` 命令行（六个参数）在改后报 argparse 错误。**存量 README 行不受影响**（只对新登记生效）。

## 伴生文件的 .gitignore 覆盖（强制）

**不适用——本变更不新增任何自动生成的文件名形态。** 本闸只读一个既已存在的信件 `.md`，**不写盘、不落状态文件、不落日志、不落快照**；逃生阀也不存在（见下）。核实方式：apply 后 `git status --porcelain` MUST NOT 出现任何新形态未跟踪文件（tasks 5.2 逐条核）。

## 🔴 本包刻意不设逃生阀

同族包（`editlock-write-side-date-guard` 的 `日期豁免：`、`editlock-hold-scope-and-wip-block` 的 `WIP豁免：`）都配了行内留痕式逃生阀。**本包刻意不配**，理由：

- 那些逃生阀存在的前提是「**合法的违规输入确实存在且常见**」（合法的未来日期确实很多）。本闸的输入空间里**不存在合法的"没有 `决策点:`"**——B 类纯通报信写 `0 项（…无需其决策）` 即可，`0 项` 已经是放行值。
- 一个不必要的豁免开关，就是这条闸未来失效的入口。**判据一句：能用 `0 项` 表达的情形不需要豁免；不能用 `0 项` 表达的情形，说明它该被停下来。**

⇒ **这是本包的第一个 design 决策点**（见 design.md D1，需 Shao Peishen 拍板）。

## 已知残余风险（如实写明，不粉饰）

1. **本闸拦不住"写了但写错点数"**。写 `1 项` 而实际有 3 个待定判断，机器分辨不了 —— 这是有意的取舍（拆点是 P1 专家判断），**不假装覆盖**。对策只有 design 审与值周巡检的人工抽验。
2. **本闸拦不住"为过闸而编"**。见验收条第 3 项的观察窗口。
3. **本闸只覆盖"进 README 主表"这一条路径**。信件**转 docx**、**直接发送**两条路径仍是人守（skill §6 红线）。🔴 **改 skill 那半句文字时 MUST 写明"机器守的只是登记这一条路径"**，不得让读者以为三条路径都被守住 —— 否则这次机制化本身就制造了一个"看起来有覆盖、实际只有三分之一"的假象，与 2026-08-24 体检抓出的 `.51` 假零同形。
4. **`--letter-path` 指错文件时，本闸会检查错的那封信**。它只验"这个路径下的 `.md` 有没有合格的 `决策点:`"，不验"这封信是不是本次要登记的那封"。可加的强化（比对 frontmatter `编号:`／`收信人:` 与命令行参数是否一致）**本包刻意未做**，列为 design 决策点 D2。
