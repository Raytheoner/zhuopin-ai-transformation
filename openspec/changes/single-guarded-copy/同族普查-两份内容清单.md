# 同族普查清单（`#503` 期望产出 ②）

## 判据（逐字取自队列 §一 `#503`）

> 内容 X 同时存在于「落库件」与「给人的即时产物」，且**只有前者过 lint／hook**。

🔴 **本普查刻意把判据放宽了一档**：`#503` 原文的「给人的即时产物」限于**对话输出**，但扫描过程中
发现同一根因的第二种形态——「落库件」与**仓库外的活载体**（已安装版 skill／已复制的 hook／计划任务
真身／docx）之间同样是「两份、只有库内那份有守」，且**这一档里人消费的往往是库外那份**。两档共享
同一句判据（能被机器守住的那一份必须是唯一被消费的那一份），故一并列出并分档标注。

- **档 A ＝ 对话面**：第二份存在于会话输出里，落不了盘 ⇒ **任何 CI 都够不着**（`#503` 称之为「本题最硬的地方」）。
- **档 B ＝ 库外活载体面**：第二份落盘了，但落在 git 之外 ⇒ 全库 grep 与 CI 结构性扫不到（`工具-仓库外载体扫描.py` 文件头已记同一成因）。

## 三条从普查里读出来的结论（供 design 审）

1. **本项目已经解决过这个问题两次，用的都是同一招：让消费端指向唯一那份（清单 4⒜、10⑵）**，而不是给第二份加守。加守的两次（清单 5 的单向回镜、清单 8 的假零检测）都只做到「副本追真身」或「知道自己扫不到」，**没有一次消灭第二份**。
2. **档 A 里，唯一真正落不了盘的是清单 1／2**——它们的第二份存在于对话与 Task prompt 参数里。这不是「还没建守卫」，是**结构上不存在可挂守卫的咽喉**：CI 扫 git、release 守卫扫本次触碰的 `.md`，两者都够不到会话输出。⇒ 只能靠「**不产生第二份**」，不能靠「**检查第二份**」。
3. 🔴 **清单 2 暴露了一个比 `#503` 立行时所写更严重的形态**：落库件与执行件不仅**内容不同**，而且**互相矛盾**（`worktree：☑ 新建` vs 「不要再建 worktree」），**而落库件那份是通过了全部七个形态检查的**。⇒ **形态①–⑦ 守的是「字段在不在」，守不了「字段说的是不是真的」**——这条不该被读成「lint 没用」，该被读成「**lint 的射程边界必须被写下来，否则它提供的是虚假安全感**」（同 `#503` 行内那句「守卫每次都在报告射程之外有东西，却没有任何载体承接这句话」）。
