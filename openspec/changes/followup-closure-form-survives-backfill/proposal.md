# 跟进信「闭环形态判定」在回填后仍然存在

> 队列 §一 `#353`（P2，2026-08-19 由 OP-0819-A ⑶ 补立）。执行环境＝CC。
> 🔴 **本包只到 propose ＋ design 出件为止，未 apply、未改任何一行生产码。**
> 属根 `CLAUDE.md` §5 门槛③（改变既有模块对外语义）⇒ 须走 openspec 含 design 审。

## Why

### 现象

跟进信 README 的「发送状态」列，由 `delivery.py::push_followup` 在推送成功后自动回填成
`✅ 已推送 <UTC>`。回填走的是 `readme_table.write_status()`，而它**把整格替换掉**：

```python
def write_status(text, loc, new_status):
    cells[loc.status_col_index] = new_status      # ← 整格覆盖，格内原有内容一律消失
```

于是「这封信要收到什么才算闭环」这条**起草时就已经做出的判定**，在发送那一刻被机器抹掉。

### 为什么这不只是格式问题

闭环形态判定正是**跟进信串行闸的判据来源**——根 `CLAUDE.md` §5 与 README S1 段都写死了：
判闸看该收信人**最近一封**的发送状态是否已到闭环四态。判定被抹掉之后，下一个 session 只能
靠读正文猜「这封算不算闭环」，**而串行闸恰恰是本项目明令优先于一切触发点规则的那条**。

### 它已经真实咬过一次（实测，非推断）

`质量部#7`（2026-08-18 06:53 UTC 推送）。起草时判定为 `✅ 无需回复`、发出即闭环。发送脚本
回填后，README 该行现在长这样（原文，`|` 为人工手打的并列分隔）：

```
✅ **无需回复**（起草时即判定：…**发出即闭环、不占串行闸**…）｜ ✅ 已推送 2026-08-18 06:53 UTC
　🔴 **两态并列是有意的，勿删任一**：发送脚本自动回填的 `✅ 已推送 <UTC>` 会覆盖起草时的
闭环形态判定，**这是 2026-08-18 闭环三态设计的一个真实漏洞——起草时判定了、发送时被机器
抹掉了**；在代码侧修好之前（…属 §5 门槛③须走 openspec），本行以人工两态并列留痕。
```

代价当场兑现：起草 `质量部#8` 时 `release` 仍被 `_validate_followup_readme_release` 拦下，
只能写一条 `串行豁免：前信质量部#7 为 ✅ 无需回复 形态、发出即闭环` 才过得去——
**拿逃生阀去绕它本来要拦的那件事**（`followup_gate.py` 模块文档里已经记过一次同形教训）。

### 🔴 前置取证推翻了队列行里的第一个建议（本包最重要的一条发现）

队列 `#353` 行给的建议做法是「**回填只写入状态列中约定的那一段**（如以分隔符切分的首段），
闭环形态判定另占一段」。**这条按现状做不成**——因为**闭环形态从来就没能待在状态列里**：

| # | 位置 | 比较方式 | 后果 |
|---|------|---------|------|
| 1 | `readme_table.assert_draft_pending_review` | `.strip() != "⏳ 待你审"` | 起草期状态格里多一个字都过不了批准脚本 |
| 2 | `gates.assert_finalized`（**门禁②，D8 红线**） | `.strip() != "🆕 待发"` | 待发期状态格里多一个字即拒发 |
| 3 | `dispatch.py:213` | `status_value != FINALIZED_STATUS_MARKER` | 批量投递轮巡直接跳过该行 |
| 4 | `dispatch.py:203` | `status_value == PAUSED_STATUS` | `⏸ 暂缓` 同样按等值识别 |
| 5 | `scripts/dispatch_followup_letters.py:71` | `.strip() == FINALIZED_STATUS_MARKER` | 候选行筛选漏掉该行 |
| 6 | `工具-共享文档编辑锁.py:1717` | `status_value != FOLLOWUP_FINALIZED_STATUS` | 两态语义反模式拦截判空 |
| 7 | `工具-共享文档编辑锁.py:1891` | `status == FOLLOWUP_FINALIZED_STATUS` | 发布收口 gap 检查判空 |

⇒ **一封信从起草到发出的整段生命周期里，状态格被七处等值比较钉成「只能是那一个字串」。**
闭环形态判定物理上无处可写——`质量部#7` 那种「两态并列」只能在**发出之后**由人手工补上，
而那时机器早已把它抹掉一次了。**它不是"被覆盖"，是"从来没有落脚点"。**

### 而它其实早就有落脚点，只是机器读不到

`质量部#7` 的**「主要事项」列**末尾原文写着：

> 🔑 **闭环形态＝起草时即判定为 `✅ 无需回复`**（正文三要素表明写「做什么＝不用做任何事」
> 「什么时候交＝不用回」），**批准发出后直接记 `✅ 无需回复`、不占串行闸**，判例包可紧接着发。

**起草人已经把判定写在那里了**——写成了自由散文，所以机器一个字也读不到，于是同一条判定
又被抄进状态列一次以求"至少人能看见"，然后被回填抹掉。全表 54 行里 `闭环形态` 只出现这
1 处（实测 `grep -c` ＝ 1）。

⇒ 本包要做的不是发明一个新位置，而是**把起草人已经在写的那句话，改写到机器认得的形态上**。
这与队列行里的第二个建议（「把闭环形态提升为独立字段」）同向，且本项目已有一模一样的先例：
队列 `#241` 的 `目标文件：\`xxx.md\`` 标注——同样落在「主要事项」列、同样是**只在既有单元格内
追加文本、不新增列**（`readme_table.build_target_file_annotation` docstring 原话：
「不改变表格结构，`_validate_release_structure`（编辑锁的列数/身份校验）因此不受影响」）。

### 本次退休哪一个既有守卫（协议〇.9 措施 B，强制回答）

**不退休任何守卫代码；退休一条人守约定，净变化＝人守 −1、机制守 +1。**

- **退休的人守约定**＝`质量部#7` 行内那条「🔴 **两态并列是有意的，勿删任一**」的人工留痕
  规矩。它是一条只活在**一个单元格里**的规则——没有第二个人会读到它，下一封信的起草人
  除非恰好翻到那一行，否则不会知道要这么写。本包落地后该行改写为标准标注，那条留痕即撤。
- **为什么不能退掉一条守卫代码**：本包扫过 followup 链路现有五道守卫——门禁①（intake 无
  业务系统依赖）／门禁②（`assert_finalized`）／两态语义反模式拦截／串行闸（
  `_validate_followup_readme_release`）／S4 桥一桥二——**没有任何一道能被本判据覆盖**：
  它们各自拦的是"越权访问""未定稿即发""起草即写终态""前信未闭环就起草下一封""回件到了
  README 却不动"，而本判据管的是"判定别被机器抹掉"。硬凑一个来退等于为了满足格式而削掉
  一道真在用的网（同 `queue-lint-appellation-guard` 包对同一条规则的处理）。
- **反向也核实过**：本包**刻意不新增任何一道会拒绝写入的门禁**（见 design 决策点 5 的
  「防滥用判据挂在哪」），故不构成"又加了一道网"。

### 伴生文件的 .gitignore 覆盖（强制回答）

**不适用——本变更不新增任何自动生成文件形态。**

- 本包（propose ＋ design 阶段）**零生成物**：只新增 `openspec/changes/…` 下四份 `.md`
  ＋ 一份 `.openspec.yaml`，全部为入库产物。
- 规划中的实现同样不新增文件形态：所有改动都落在**既有文件的既有单元格**里
  （README 表格的「主要事项」列与「发送状态」列），不产生锁文件／快照／暂存／状态文件／
  日志／退路副本中的任何一种。
- 实测（非推断）：`git check-ignore -v openspec/changes/followup-closure-form-survives-backfill/proposal.md`
  → **无输出、退出码 1（未被任何规则忽略）**，符合预期（变更包必须入库）。

## Impact

- **受影响**：四域专员跟进信全链路（起草 → 审 → 批准 → 投递 → 回填 → 闸），
  以及所有依赖串行闸判断"能不能起草下一封"的 session（Cowork 各专线 ＋ CC 发布收口第 8 步）。
- **现有行为的兼容方向**：无标注的行 MUST 与今天逐字同行为（54 行历史行里 53 行无标注）。
  这条是硬要求，写进 spec，不是"尽量"。
- **风险面最大的一条**＝决策点 2：若同意「回填时按闭环形态直接写闭环态」，等于**让机器
  自动开串行闸**。本包**不默认它**——判据/口径类永不默认生效（IATF 显式签认红线）。
- **本包不部署、不发信、不触碰 `.51`**（本服务按 2026-08-13 拍板永不部署 `.51`）。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

**⑴ 本流程哪些判断是人脑默会经验？**

- **「这封信要收到什么才算闭环？」**——起草人在写正文三要素表那一刻就已经知道答案
  （`质量部#7` 的正文明写「做什么＝不用做任何事」「什么时候交＝不用回」），但这条判断
  此前只以散文形式留在「主要事项」列，**没有任何规则、阈值或格式约束它怎么写**。
- **「什么样的信可以判成 `✅ 无需回复`？」**——尺度全在人脑里。现有唯一成文线索是
  `质量部#7` 行内那句「符合防滥用约束——**起草时判定、非事后追认**」，而这条约束
  **没有任何机器在执行**（本包决策点 5 即为它补判据）。
- **「闸开了没有？」**——今天靠人读状态格 + 读正文 + 记得串行原则，三者合起来才能答。

**⑵ 由谁显性化？** 持有人 **Shao Peishen**（串行原则与闭环四态的定立人，`#353` 的定夺人）；
backup **孙涛**（决策代理，可代 design 审，见根 `CLAUDE.md` §5）。
🔴 **本条不可由 AI 专员代**——它是串行闸的判据来源，属"判据/口径类"，IATF 显式签认红线。

**⑶ 用什么方法提取？** **历史案例反推**——不设问、不猜规则。语料＝README 现有 **54 行**
跟进信的状态格与主要事项格全量实测：`闭环形态` 字样命中 **1 行**（`质量部#7`）、
`✅ 无需回复` 形态命中 **3 行**（`IT部#8`／`采购部#14`／`质量部#7`，均为 2026-08-13～18
按「新增闭环三态」补标）、其余各行的闭环依据一律写在状态格的 `　━━━　` 之后。
标注格式与合法取值集合均从这批真实语料标定，不另设问。

## 验收与晋档条件（强制，四档口径）

**本变更包交付后所处档位：档 3（内部服务）。**
判据跑在真实 README 与真实 `release` 门禁上，对真实的四域专员通信生效，不是 mock 验证。
（🔴 **本包当前尚未 apply ⇒ 实际档位为「档 0 · 仅方案」**，档 3 是 apply 后的目标态。）

**晋下一档（档 4 对客交付）的条件**：不适用——跟进信链路只服务内部专员，无对客交付路径。
**真正要观察的是「它是不是只在纸面上绿」，故列三条可核验的下一步**：

1. **首次真实生效**：至少有一封**新起草**的信带上闭环形态标注、走完「起草 → 批准 → 投递 →
   回填」全程，且回填后标注**仍然读得出来**。观察口径＝`工具-跟进闸查询.py --to <收信人>`
   的输出里能看到该标注。
   🔴 **同族反面教材＝队列 `#82`：告警建成 9 天、每天在跑、一次都没真响过**；
   「单测绿」不算数，必须是一封真信走完真链路。
2. **首次真实开闸**：至少有一次「前信为 `✅ 无需回复` 形态 ⇒ 起草下一封时 `release`
   直接放行」，且**没有用 `串行豁免：`**。观察口径＝该次 `release` 的输出里不含
   `检测到串行豁免声明`。这一条正面回答 `质量部#7 → #8` 那次的失败。
3. **逃生阀不失控**：`串行豁免：` 在 README 表格**数据行内**的出现次数不升。
   🔴 **取数位置必须写死**：在 **README「现有跟进信清单」表的数据行**里取，**不是全文
   `grep`**——队列 §四 `#58` 已实测踩过一次同族陷阱（整文件 grep 得 10、按状态列取数得 1、
   真实 0），一条不写明「在哪个结构位置取数」的监测指令迟早会被在讲解它自己的散文上执行一次。

**价值指标（风险型）**：本判据要消掉的不是工时，而是**「一条起草时已经做出的判定，被机器
静默抹掉，且抹掉时不产生任何信号」**这个结构。
基线＝上线前该判定的机器覆盖率 **0%**（零解析、零校验、零告警，唯一留痕方式是人在单元格里
手打一条给下一个人看的中文提示）；交付后＝**新起草的信 100% 覆盖**，历史 53 行**仍为 0%**
（不追改），如实登记、不含糊。基线由业务 Champion **Shao Peishen** 确认——本项待其追认，
见 tasks §0。
