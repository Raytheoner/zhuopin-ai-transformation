# Design — 跟进信「闭环形态判定」在回填后仍然存在

> 🔴 **本文件是 design 审的对象，六个决策点全部「须签认」、全部无默认项。**
> 依据根 `CLAUDE.md` §5「默认项只在两个前提下成立」：提出本包的 session 是**无人在场的
> 无头批处理会话，收工即结束** ⇒ 第一问「他若不答，谁去执行」答不出执行者 ⇒ 不得设默认项。
> 另：决策点 1／2／4／5 属**判据/口径类**，按专员跟进纪律**永不默认生效**（IATF 显式签认红线）。

---

## 前置：问题的形状不是队列行写的那个形状

队列 `#353` 行的建议是「回填只写入状态列中约定的那一段」。取证之后这条**做不成**——
不是难做，是前提不成立：**闭环形态判定从来就没能待在状态列里**。

一封信从起草到发出，状态格被**七处等值比较**钉成「只能是那一个字串」
（清单见 proposal「前置取证」表）。其中 `gates.assert_finalized` 是 design.md D8 记着
「Paul 拍板不得放宽」的**门禁②红线**。

⇒ 真实形状是：**判定无处安放，而不是判定被覆盖。**
`质量部#7` 那格「两态并列」是**发出之后**由人手工补的，那时机器已经抹过一次了。

同时取证也发现，**起草人早就把判定写在「主要事项」列了**，写成了自由散文
（原文见 proposal）。全表 54 行里只此 1 处（实测 `grep -c 闭环形态` ＝ 1）。

⇒ 本包的任务是**把那句已经在写的话，改写到机器认得的形态上**，不是新造一个位置。

## 决策点 1（**须签认，无默认**）：闭环形态标注放在哪一列

**选项**

- **(a) 「主要事项」列内标注**（推荐）——形如 `→ 闭环形态：\`✅ 无需回复\`（依据：…）`，
  与队列 `#241` 的 `目标文件：\`xxx.md\`` **同构、同列、同手法**。
- **(b) 「发送状态」列首段化** —— 状态格改为 `<状态段>　━━━　<闭环形态段>`，七处等值比较
  一律改为「取首段后再等值」。
- **(c) 新增一列「闭环形态」** —— 表格从 6 列变 7 列。

**推荐 (a) 的四条理由**

1. **零门禁改动**。(b) 要动七处等值比较，其中一处是 D8 明文红线（门禁②）。
   把「不得放宽」的门禁从等值改成前缀，**无论技术上多么等价，它都需要 Shao Peishen 亲自
   签认**——而那笔签认应该花在真正需要放宽的地方，不该被这件事消耗掉。
2. **零表结构改动**。(c) 要改 `_validate_release_structure` 的列数校验、
   `_followup_readme_rows`／`readme_table.iter_rows` 两处解析，并**迁移 54 行**。
   `build_target_file_annotation` 的 docstring 已经把这条权衡写过一遍了：
   「只在既有单元格内追加文本，不新增列——不改变表格结构，…因此不受影响，无需同步修改」。
3. **它就是起草人已经在做的事**。(a) 落地后 `质量部#7` 那句散文只需改标点，语义一字不动。
4. **先例已在生产上跑了 20 天**（`#241`，2026-08-04 起）。`extract_target_filename` 的
   正则与回落逻辑可以逐字复刻，不新造范式。

**(a) 的代价，如实登记**

- 「这封信当前是什么状态」与「它要怎样才算闭环」**落在两列上**，人读的时候要合看两格。
  缓解＝`工具-跟进闸查询.py` 把两者拼在同一行输出（决策点 3 的快照进一步缓解：
  发出之后两者会同时出现在状态格里）。
- 「主要事项」列已经很长（`质量部#7` 那格 ≈ 700 字），再加一段会更长。
  接受它——这一列本来就是长文列，而另外两个选项各自要动红线或动结构。

## 决策点 2（**须签认，无默认；判据/口径类，永不默认生效**）：回填时要不要顺手开闸

即：若标注为 `✅ 无需回复`，`delivery.py` 回填时应写成——

- **(a) 直接写闭环态** `✅ 无需回复 <UTC>`：**发出即闭环，串行闸当场开**。
  `质量部#7 → #8` 那次就不需要 `串行豁免：` 了，本包的价值一步兑现。
- **(b) 仍写 `✅ 已推送 <UTC>`**，闭环形态只作为标注被保留下来；闸判据另行读它才放行。

**这一条是本包风险面最大的一条：(a) 等于让机器自动开一道人设的闸。**

**两个方向的代价不对称，且不对称的方向不明显**：

- 选 (a) 而判错 ⇒ 闸被错误打开 ⇒ 同一收信人手上出现两封在途信。串行原则是
  Shao Peishen 2026-08-03 定的、**明令优先于一切触发点规则**的那一条。
- 选 (b) 而判对 ⇒ 闸该开没开 ⇒ 起草人写一条 `串行豁免：` 绕过去。
  **代价是"逃生阀被用了一次"，而这恰恰是本项目已明确记为坏味道的形态**
  （`followup_gate.py` 模块文档：「拿逃生阀去绕它本来要拦的那件事」）。

⇒ **两边都难看。本包不代为选择，如实把两难摆出来。**
若倾向 (a)，建议附加一条护栏（可与 (a) 一并签认）：**只有当标注在「批准」那一刻就已存在
时才生效**——这条护栏在决策点 5 选 (c) 时是**结构性成立**的，不需要额外门禁。

## 决策点 3（**须签认，无默认**）：回填改为「保留式」，并在回填时**快照**闭环形态

**提议**：`delivery.py` 的回填不再整格覆盖，改用 S4 桥一**已在生产上跑着**的范式
（`followup_readme_bridge.build_reply_arrived_status`）：

```
✅ 已推送 <UTC>　━━━　闭环形态（发出时快照）━━━　✅ 无需回复（依据：…）
```

其 docstring 里那句理由**逐字适用于本包**：
> 「旧状态不删，是因为…**覆盖式写入会把它弄丢，而这一格没有任何别处的副本**。」

**为什么这一条独立于决策点 1，必须单独签**

它治的是**覆盖式写入本身**，不只是闭环形态。同一个 `write_status` 还会抹掉：

- `⏸ 暂缓` 的暂缓理由（队列 `#294` 修法⑴ 新增的第三态，理由必须由人手写在格里）；
- 起草人写在状态格里的任何临时备注。

⇒ 决策点 1 选 (a) 而决策点 3 不做，则本包只治了闭环形态一种，
**`⏸ 暂缓` 的理由仍会被静默抹掉**——已在 proposal「已知未闭合 2」显式登记，不蒙混。

**🔴 快照是本设计的关键一步，它顺带把决策点 5 变成结构性的**

回填那一刻，机器把「主要事项」列的标注**复制进状态格**。此后：

- 闸判据**只认状态格里的快照**，不再回头读「主要事项」；
- ⇒ 信发出之后再往「主要事项」里补写标注，**对闸零效果**；
- ⇒ 「起草时判定、非事后追认」这条防滥用约束**不需要任何门禁去守**，它由数据流保证。

**已核实不与既有机制冲突**：`✅ 已推送` 之后的状态格**不参与任何等值比较**
（七处等值比较全部发生在 `⏳ 待你审`／`🆕 待发`／`⏸ 暂缓` 三态上）；
`followup_gate.classify_status`／`normalize_status` 走**前缀匹配 + 归一化**，格内后缀不影响判定；
S4 桥一 `build_reply_arrived_status` 会把整个原状态原样接在自己后面 ⇒ **快照能一路活到第九态**。

## 决策点 4（**须签认，无默认；判据/口径类**）：标注的合法取值——限定枚举还是自由文本

- **(a) 限定枚举 ＋ 强制依据**（推荐）：取值 MUST 是
  `followup_gate.CLOSED_STATUS_PREFIXES` 四者之一（实测语料里唯一真实用过的是
  `✅ 无需回复`，另三态都是事后转态、不会在起草时判定）；且 MUST 附一句依据文本。
  取值不在枚举内 ⇒ **fail-loud**（报出来，按"无标注"处理，闸仍锁）。
- **(b) 自由文本**：怎么写都行，闸判据靠模糊识别。

**推荐 (a)。理由是本项目已经为 (b) 付过一次学费**：README 顶部「下一个可用号」段落
**连续失真四次**，诊断原文是「本段是自由文本、没有任何机器判据覆盖它」——
而 2026-08-21 那次校准又把诊断补了一刀：「**失真的不是一处而是两处，且两处会互相印证着
一起错**」。⇒ 一个机器要读的位置上放自由文本，结局本项目已经验证过四遍。

**(a) 的已知边界**：`✅ 无需回复` 之外的三态在起草时判定几乎无意义
（`📥 已回件并回灌` 起草时不可能成立），故枚举实际上退化为一个取值。
**刻意仍写成四态枚举而不是布尔开关**——判据从权威源
`followup_gate.CLOSED_STATUS_PREFIXES` 取，不在消费者侧另写一份（模块文档明令：
「判据只此一份，不得在消费者侧另写」）；写成布尔就等于在这里悄悄复制了一份口径。

## 决策点 5（**须签认，无默认**）：防「事后追认」的判据挂在哪

`质量部#7` 行内自己写着约束：「符合防滥用约束——**起草时判定、非事后追认**」。
**今天没有任何机器在执行这句话。** 三条路：

- **(a) 编辑锁 `release` 阻断**：比对 acquire 快照，若既有行新增了标注而其状态已过
  `⏳ 待你审`，拒绝 release。
- **(b) 只告警不阻断**。
- **(c) 结构性防止**（推荐）：**不新增任何门禁**，靠决策点 3 的快照——
  发出后再补写的标注对闸零效果，因为闸只读快照。

**推荐 (c)，两条理由都是本项目自己的实测**

1. **(b) 已被实证为无效**：协议〇.9 ⑵ 记着 2026-08-10→08-16 观察周——
   「6 次每次都响了、每次都被越过，**一个非阻断提示在连续 6 次被无视后信息量已经是零**」。
2. **(a) 是"再加一道网"**，而本包按 one-in-one-out 已经声明不新增拒绝写入的门禁；
   更要紧的是协议〇.9 ⑵ 的另一条教训——**一条阻断规则可能把自己的解法一起锁死**
   （「连来关行降 WIP 的那个 session 也会被挡在门外」）。这里的等价风险：
   一个来**修正**误写标注的 session 会被同一条规则挡住。

**(c) 的已知边界，如实登记**：(c) 只让事后追认**对闸无效**，**不阻止它被写下**。
⇒ README 上仍可能出现一条"看起来像判定、实际不起作用"的标注，读的人会被误导。
缓解＝`工具-跟进闸查询.py` 在两者不一致时**明确报出**「主要事项标注与发出时快照不一致，
以快照为准」。**这条缓解必须做，不做则 (c) 用一个静默失效换掉了一个静默滥用。**

## 决策点 6（**须签认，无默认**）：历史行的迁移范围

- **(a) 只回改 `质量部#7` 一行**（推荐）：它是唯一写过闭环形态判定的行，
  把散文归一化为标注、撤掉两态并列的人工留痕。**其余 53 行一字不动。**
- (b) 全表 54 行按现有状态格反推补标注。

**推荐 (a)**：根 `CLAUDE.md` §1「历史记录不追改」。且 (b) 是**考古式反推**——
53 行里绝大多数当年根本没做过闭环形态判定，补出来的标注是我们今天替他们编的，
**它会长得和真判定一模一样**（同族＝「一条『更正』把一条本来正确的记录改错了」，
OP-0819-F 教训⑶）。

**(a) 的已知边界**：历史 53 行的闭环形态覆盖率**永久为 0%**，已在 proposal
「价值指标」里如实写死，不含糊成"逐步补齐"。

## 已知边界（三条，与决策点无关，落地后仍然存在）

1. **标注只对「新起草」的信生效**。存量在途信（起草时无标注）走完原路径，与今天逐字同行为。
   这是刻意的兼容方向，写进 spec 的 MUST。
2. **闸判据的扫描面不变**。本包不扩大 `followup_gate` 的覆盖面——README 正文（串行原则段、
   「下一个可用号」段）**仍然是自由文本、仍然没有机器判据覆盖**。
   这是队列 `#352` 与 README lint 那条线的范围，不是本包的。
3. **本服务永不部署 `.51`**（Shao Peishen 2026-08-13 拍板）⇒ 本包无部署段、无冒烟段，
   验收只能在开发环境 ＋ 真实 README 上做。**「档 3」的含义因此比别的包弱一档**，如实登记。
