## Why

### 事故本体（2026-08-29 `OP-0829-A` 实测，提交 `6557047`）

按纪律「先登记 §二、后建造」，一个跨 worktree 的批次行 `B-0829_5_OP0829A_哨兵建造apply与安装单` 声明了 8 条文件（5 个代码件 ＋ 安装单 ＋ openspec tasks ＋ 队列文件）。sweep 于 23:18 UTC 抢先取活——而那一刻**代码还在 worktree 的分支上，主仓工作区只有队列文件是脏的**。

于是 `_resolve_batch_files` 给出 `resolved=[队列文件]`、`not_dirty=[其余 7 条]`；**当时的实现看见 `resolved` 非空就走正常批次分支**，`git add` 了队列这一个文件，却套用清单那条 `feat(hooks/#433): 写入时刻哨兵 apply——H3 乱码＋H4 代词＋公共框架（warn 上线）＋安装单` 的标题提交掉，并把该行销成「✅ 已完成」。

🔴 **它不报错、不留异常、账面完全正常**：§二 说这批已完成，git 历史里那个提交的标题也说它含哨兵代码，**实际上一行代码都没有**；真正含代码的是后来 ff 合入的 `e4c93f2`。这与本项目已多次点名的「工具静默回退」同族——**错误的唯一载体是一条读起来完全正常的账**。

### 为什么它必须进 spec，而不是留在代码注释里

三条，逐条都不是形式主义：

1. **IATF 16949 可追溯性**：git 历史里现存一个**标题与内容不符**的提交（`6557047`）。这类不符若无 spec 级的判据说明它已被堵死、堵法是什么、边界在哪，审计时无从证明这是一次性事故而非常态。
2. **这条判据带一个启发式**（`_looks_like_declared_path` 的形状判据），启发式**两个方向的失手都会造成真实代价**（见「已知残余风险」）。启发式的取舍必须在 spec 里被显式承诺与限定，否则下一个改它的人只能靠读 docstring 猜当初为什么这么写。
3. **它是「一道新检查」，而新检查本身会成为新的单点故障**——本实现刻意做成 fail-open，且这条 fail-open 是**用源码结构用例钉死的**（`ManifestCoverageFailOpenSourceTests`）。这种「用测试锁住代码形状」的做法必须有 spec 说明其意图，否则会被后来者当作多余的耦合删掉。

## What Changes

**本变更不改动任何代码。** 下述行为均已在 master 上线并由既有测试覆盖（清单见 §Impact），本包只把它们补写成 capability spec。

新增 capability `sweep-manifest-coverage-guard`，覆盖四段行为：

- **覆盖校验**：批次落库前，若 `resolved` 非空而清单中仍有「形状像仓库内路径、却对不到任何脏改动」的片段，则该批**整批跳过**、状态列不动、并在 sweep 日志点名（点名批次号、缺哪几条、本次只能对上哪几条、怎么处置）。
- **只拦「部分覆盖」**：`resolved` 为空时本校验一律不插手——那条路径是既有的「遗留尾巴补销」（队列 #328），不产生内容提交，不存在空壳提交问题。
- **形状判据先筛**：§二「文件清单」列不是纯路径列表，正文大量用反引号做普通强调。片段须先过形状判据才参与覆盖校验。
- **fail-open**：校验自身抛异常只留一条痕、按校验前的旧判据继续，**绝不让这道新检查把整轮 sweep 拖死**。

**BREAKING**：**是**，且已于 2026-08-29 生效——sweep 在「部分覆盖」这一输入下由放行变为跳过。本包只是补记录，不引入新的行为变化。

## 本次退休哪一个既有守卫（强制，协议〇.9 措施 B）

**不退休任何守卫，且本项目没有可退的对应人守条目——理由如下，不以「无」搪塞。**

one-in-one-out 的适用前提是「这条机器守接管了某条此前靠人守的规则」。本包的情形不同：**在 `6557047` 之前，「批次提交的内容必须与清单声明相符」这条约束在本项目里根本不存在**——不是靠人守着而失效，是从来没有人写下过它，因为在跨 worktree 建造成为常态之前，「清单声明了就一定在工作区」是个从未被违反过、因而从未被表述过的隐含假设。

⇒ **这不是「一进一出」，是「零出一进」**，属协议〇.9 明确允许的例外形态（新出现的失效模式，无对应旧守卫）。🔴 **如实写明而不硬凑一个退休项**：硬凑会导致真正在起作用的守卫被误退。

**可退休的是别处**：`6557047` 事故后，「先登记 §二」的纪律曾一度被口头补上「跨 worktree 建造时先别登记」的人守例外。**本机器守上岗后，该口头例外应被撤回**（登记照旧、由 sweep 自己判等不等得起）。⚠️ **本包不执行这一撤回**——它落在队列纪律侧、不在本包触碰区，登记为 design 审的待判项（design 决策点 5）。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？**
   - **「这个反引号片段是一条路径，还是正文强调」**——此前 100% 在人脑里，且人读一眼就知道，机器不知道。2026-08-29 实测：现存 182 行共 1544 个反引号片段里 **757 个（近一半）根本不是路径**（`master`／`origin/master`／`#422`／`.51`／`--ff-only`／`git status`／`bfeb3e6`／`**/reports/` 等）。本能力把这个判断显性化为一条**形状判据**，并同时显性化了「它是启发式、不是真值」这一点。
   - **「清单对不上时该拿一部分冒充整批，还是整批不动」**——此前无人表述过，因为无人预见过「清单声明的文件此刻在别的 worktree 上」这一形态。
2. **由谁显性化？** 持有人 ＝ CC 建造车间（2026-08-29 实现方，判据、实测数据、三条边界与两类失手均已落在源码 docstring 与测试断言里）；**backup ＝ Shao Peishen**（design 审拍板形状判据的松紧与残余风险接受度）。本包执笔方为本次 propose 的 CC session，**只转写已被代码与测试验证的行为，不新增任何未经验证的承诺**（沿用 `retroactive-mechanism-specs` 确立的转写纪律）。
3. **用什么方法提取？** **历史真实案例反推 ＋ 现网全量实测**：⑴ 从 `6557047` 这一真实事故反推判据；⑵ 对现网两份队列 §二 全部 182 行 1544 个反引号片段跑形状判据，逐类判定性质，据此定 reject 规则（`~` 前缀／`/` 结尾／含空白／含 `*?{}`／末尾非 `<非点非斜杠字符>.<扩展名>`）。**不涉及 LLM 判断**（纯正则与集合运算）。

## 已知残余风险（如实写明，不粉饰）

1. 🔴 **形状判据是启发式，不是真值。** 两个方向的失手都真实存在，且都已写进源码注释：
   - **漏认**（真路径被当成散文）⇒ 该片段不参与覆盖校验，**退化成校验前的旧行为**，即 `6557047` 型空壳提交仍可能发生。不新增破坏，但也不提供保证。
   - **误认**（散文被当成路径）⇒ 该批被整批跳过并点名，**人工去掉那对反引号即可**。2026-08-29 实测残余误认面很小：现存 344 个形状合格的片段里，只有 `word/document.xml`、`登记豁免：.claude/settings.local.json` 一类**个位数**写法可能命中，且它们本就是登记写法不规范。
2. **本校验只覆盖「主仓工作区」这一个观察面。** 它问的是「清单声明的路径在主仓有没有脏改动或已进索引」，**它不知道那些文件是不是在别的 worktree 上、也不知道它们是不是已经合入 master 了**。⇒ 一个「代码已 ff 进 master、清单仍写着它」的批次，本校验会判缺项并跳过。这一形态的正确处置是**登记方不要把已自行 commit 合入的代码件写进文件清单**（口径已写进 §四 `#136` 行「对登记方的口径影响」段）。🔴 **不得把本能力表述为「知道文件在哪」——它只知道「这次提交装不装得进去」。**
3. **出声形态只到 sweep 日志，未接企微 webhook。** 即：**跳过发生了，但没有人被主动通知**——要等有人去看 `reports/sweep-commit.log` 或发现批次行迟迟没销。接 webhook 要连阈值与去重状态机一起做（`#147`「狼来了」教训），越出 `38f3898` 写死的触碰区。🔴 **⇒ 本能力 MUST NOT 被表述为「会告警」，只能表述为「会留痕」。**
4. **本能力不校验「提交标题与内容相符」这件事本身**，只堵住了造出不符的那一条已知路径。同类不符若从别的路径产生（例如清单写全了、但某个文件在 `git add` 与 commit 之间被改动），本能力不覆盖。**不假装覆盖。**
