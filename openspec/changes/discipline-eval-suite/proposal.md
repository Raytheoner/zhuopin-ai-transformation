## 1. Why（为什么做）

**规则退休制是人守，而「能不能退」这个判断今天没有任何依据可依。**

- 守卫代码实测 **4822 行只增不减**（队列 `#308`）；
- 「人守条目被违反 3 次即须机制化或删除」（根 `CLAUDE.md` §5）本身是人守，违反计数落在队列 `#284`；
- **删一条规则之后，没有任何东西会告诉你哪里塌了** ⇒ 唯一安全的操作永远是「再加一条」⇒ 注意力预算
  被持续挤占，而注意力正是需求管理最缺的东西。

**eval 补的就是这一格**：它让「把某条人守规则降为一行指针，或直接删掉」这个动作**第一次变得可检验**。

### 1.1 一期只做 3 条，是盘出来的不是拍的

草案 §1 的守卫盘点结论沿用（本轮复测了其中三项，见括号内）：

| # | 纪律形态 | 现有机器守 | eval 的角色 |
|:--:|---|---|---|
| 1 | 从名字推断性别 | ✅ H4 代词哨兵（`0-学习与工具/hooks/sentinel-pronoun.ps1`，**本轮 `ls` 复测文件在**） | 回归网（二期） |
| 2 | 编号滞后 | 🟡 `queue-lint-appellation-guard` 已落包（`openspec/changes/` 内实测在） | 回归网（二期） |
| 3 | 串行闸误锁 | ✅ `followup_readme_bridge.py`（**本轮 `git ls-files` 复测在库**）＋闸查询 | 回归网（二期） |
| 4 | 队列拼接丢第二份 §一 | ✅ 已配反例单测 | 回归网（二期，优先级最低） |
| **5** | **`%ERRORLEVEL%` 解析期展开 ⇒ 假 0** | ❌ **无**（且**连人守载体都已消失**，见 §0 ③） | 🔴 **唯一守卫** |
| **6** | **写侧日期未当场重取** | ❌ **无**——`openspec/changes/editlock-write-side-date-guard/tasks.md` 实测 **`[x]` 0 条／`[ ]` 29 条**，未开工 | 🔴 **唯一守卫**（且在该包落地前一直是） |
| **7** | **提方案前未先查环境已有能力** | ❌ **无**——只有 `.claude/rules/场景建造与合规.md:20` 提到 skill `zhuopin-requirement-grill` 的「§一 M2 自查事实」，是人守 | 🔴 **唯一守卫** |

⇒ **先建「唯一守卫」那三条，回归网四条二期做。**

### 1.2 它与 hook／lint 不是重复建设

| | hook ／ lint | eval |
|---|---|---|
| 守的对象 | **产物**——写出来的文件里有没有违规字样 | **行为**——agent 在给定情境下会不会做出正确判断 |
| 触发时机 | 写入当刻拦截 | 配置变更（`CLAUDE.md`／`.claude/**`）时回归 |
| 判定性质 | 确定性 | 概率性，须多次采样看方差 |
| 能力边界 | 只能守正则表达得出来的那一部分 | 守边界情形与语义判断 |

**证据是哨兵自己写的**：H4 代词哨兵判据自陈「判定限『同一段落内出现名录人名，且其后最近的第三人称
代词与名录不符』这一形态」「名录外人物不触发」「**判据宁可漏报也不误报**」⇒ **它有意留下一大片
漏报区，那片区域今天没有任何东西在守。** 那就是 eval 的辖区。

**eval-6 最能说明这条分界**：写进队列行的那个日期是一个**合法日期**，产物侧的 hook／lint 看不出
它是沿用的还是重取的——**只有 transcript 里能看出那一步被跳过了。**

### 1.3 🔴 本次退休哪一个既有守卫（协议〇.9 措施 B，机制类强制回答）

**本包上线时不退休任何守卫；退休的是「无法判断能否退休」这个状态本身。**

**为什么不能退**（须论证，不得以「无」搪塞）：eval 是**元守卫**——它守的是其它守卫和规则本身是否
还在起作用。在它跑稳、并在真实注入回归中变红之前，**用它去换掉任何一个现役守卫，是拿未经验证的
东西替换已验证的东西**，方向正好反了。反向也核实过一次「有没有可退的」：§1.1 表中 1/2/3/4 四条的
现役守卫**没有一条能被本期三道题覆盖**（本期三条恰恰是那四条之外的补集），硬凑一个来退等于为了
满足格式而削掉一道真在用的网。

🔴 **但本包不能因此变成第 4823 行。** 故把退休义务写成**可检验的承诺，落进 tasks §6**：

> **上线后 4 周内，以 eval 覆盖为依据，对至少 3 条人守规则执行一次退休判定（机制化／降为一行指针／
> 删除，三选一），判定结果逐条登记；判定为「不退」的须写明理由。**

**新增一条本包自带的退休义务**（§0 ③ 直接催生）：**eval-5 一旦落地，`%ERRORLEVEL%` 这条纪律的
在库载体状态由 eval 自己报**——若 design 审决定把它补回 `.claude/rules/两桌同步与取证.md`，则该
补回条目自诞生日起即被 eval 覆盖，属「先有网再有规则」，是本项目第一条这样的规则。

## 2. What Changes（改什么）

**新增：**

1. `evals/evals.json` —— 一期 3 条题（id 5／6／7），schema 沿用 `skill-creator/references/schemas.md`
   的 `evals.json`（`id`／`name`／`prompt`／`expected_output`／`files`／`expectations`）。
2. `evals/files/` —— 各题的**冻结情境夹具**（脱敏后的队列片段等），入库。
3. `evals/rules-locus.json` —— **每道题所守纪律的「在库载体坐标」**（文件路径 ＋ 锚点字符串）。
   🔴 这是本包相对草案的**新增件**，成因＝§0 ③：注入回归要有靶点，靶点会漂，坐标须入库并被校验。
4. 一个**薄 runner**（`evals/run_discipline_eval.py`，行数下界由 design 决策点 1 定）——草案说的
   「不写跑法」已被 §0 ① 证伪，跑法必须写；但**只写编排层**，判分复用 `agents/grader.md`、
   聚合复用 `scripts/aggregate_benchmark.py`、看板复用 `eval-viewer/`。
5. CI：新建 `.github/workflows/discipline-eval.yml`（**不并进 `ci.yml`**，理由见 design 决策点 5）。
6. 运行产物落 `reports/`（已被 `.gitignore` 覆盖，实测见 §5）。

**🔴 明确不做的三件：**

1. **不自建判分器与看板**——`agents/grader.md`／`aggregate_benchmark.py`／`generate_report.py`／
   `eval-viewer/` 直接复用（这四件本轮实测存在，路径见 design 决策点 1）。
2. **不改任何既有 hook／lint／业务代码。** 本包只**观测**它们，不动它们。
3. **不进 design 审、不 apply**——本轮交付到 propose＋design 起草为止（队列 `#440` 状态列原文：
   「第一棒只到 propose＋design」）。

## 4. 验收与晋档条件（强制，四档口径）

**本变更包交付后场景所处档位**：**档 1（mock 验证）**——eval 在本机与 CI 上跑，不接真实业务数据、
不改任何生产行为。

**晋档 2（真实数据跑通）的条件**（逐条，🔴 不得放宽）：

1. CI 真实跑通一轮（含 `PYTHONUTF8` 与 windows-latest 编码坑的实测——本仓库 `ci.yml:50` 已全局设
   `PYTHONUTF8: "1"`，**新 workflow 文件不继承它，须自带**，见 design 决策点 5）；
2. 凭据就位且经 design 审确认其安全边界（design 决策点 2）；
3. **3 条 eval 各至少捕获一次人为注入的回归**——即故意把对应规则从其在库载体摘掉，eval 必须变红。
   🔴 **没有这一步，「eval 跑绿了」什么都不能证明**——同 `#82` 形状（告警建成 9 天、每天在跑、
   **一条都没真发出过**，中间任何一轮都没人察觉）。
   ⚠️ **eval-5 的注入回归在靶点补回库之前无法执行**（§0 ③）⇒ **它是 design 决策点 6 的硬前置**；
4. 连跑 5 轮记录方差，得出通过阈值的**经验值**（而不是拍一个）。

**价值指标**（两类）：

- **风险型**：同族复发次数。基线＝编号滞后 **6 次**、代词推断 **≥6 次**（其中 `财务部#14` 信已发出
  撤不回）、**「开工前未查现状」2026-08-30 一天 3 次 ＋ 2026-09-08 本包起草时复测出第 4 次**。
  目标：一期覆盖的三条形态**交付后 0 次**。
- **质量型**：🔴 **本包的真正产出不是「抓到几个错」，而是「敢退休几条规则」。** 指标＝**上线后 4 周
  内，以 eval 覆盖为依据完成退休判定（降指针或删除）的人守规则条数**，目标 **≥3 条**。基线由
  Shao Peishen 在启动前确认。

**LLM 判据黄金集**：🔴 **本包整体就是一份黄金集**——每条 eval 的「冻结情境 ＋ 专家认可的正确动作」
即是黄金集条目。首批 **3 组**，目标 **≥7 组**（补齐 §1.1 表中全部 7 条）。**无黄金集不晋档 3**
这条在本包上自动满足。

文件名形态，被 `git status` 恒报为未跟踪、被落库 sweep 判为孤儿脏文件**——**这正是 `#322` 的形状**

由本包产生；但**须在 tasks 内写死一条防御**——若 design 决策点 1 选了会落临时命令文件的方案，则
`.gitignore` **必须同批加 `.claude/commands/*-skill-*.md`**，并以 `git check-ignore -v` 实测坐实，

### 6.1 🔴 一个必须由 design 审拍板的安全边界变化（本包的拍板点）

**本仓库 CI 今天零 secret，2026-09-08 复测仍成立**：`grep -c "secrets\." .github/workflows/ci.yml`
→ **`0`**（退出码 1）；`ls .github/workflows/` → **只有 `ci.yml` 一个文件**；11 处 `runs-on` 全部
`windows-latest`。本包要跑 eval 就需要一份模型凭据，**这将是本仓库 CI 的第一个凭据**。

**现行凭据纪律的覆盖缺口，实测两侧**：

- **本机侧已有落点**：`.env.example:36` 实测**已有 `ANTHROPIC_API_KEY=`（空值占位）** ⇒ 本机侧
  「只进 `.env`」这条**已经成立、无需新立**；
- **CI 侧无任何口径**：`.env` 被 `.gitignore` 挡住、根本不进 CI checkout（`工具-密钥扫描lint.py`
  docstring 原话），⇒ **CI 里的凭据只能走 GitHub secret 这一形态，而这个形态今天没有任何纪律覆盖。**

**须 design 审明确四件**（design 决策点 2 已给候选与代价，**本轮不预定**）：① 组织 secret 还是 repo
secret；② 额度上限与超支行为（跑挂 vs 跳过）；③ 该 key 泄露的爆炸半径与轮换路径；④ **与既有
`secret-scan` job 的关系**——`工具-密钥扫描lint.py` 的四条结构化判据里**含「Anthropic 风格 API key」
一条**，须确认新 workflow 里的 `${{ secrets.* }}` 引用形态**不会被自己的凭据扫描判成泄漏**
（引用的是名字不是值，按该脚本「右值形如另一个大写常量/环境变量名则排除」的既有豁免应当放行，
🔴 **但这是读代码推的，落包时必须实跑一次坐实**）。
