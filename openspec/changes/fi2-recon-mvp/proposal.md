# FI2 三单匹配自动对账·MVP Proposal

## Why

财务/采购交叉月结靠人工逐笔核对 PO/入库单/发票/付款凭证，效率低且"总额对、明细错位"这类隐蔽差异极易漏检、导致按行核算的产品成本失真。U9C 财务接口/SRM 发票/OCR 9 月才通，但匹配规则现在就能理清——先用 mock 数据把四维匹配逻辑立起来，接口一通即换数据源、逻辑零改，才赶得上 2026-09 启动节奏。

## What Changes

- 新增 FI2-1 三单数据准备与完整性校验：PO 明细行 / GRN(入库单) / Invoice(发票) / Payment(付款凭证) 四表接入，按 `(po_no, line_no)` 串联 PO↔GRN↔Invoice、按 `inv_no` 串联 Invoice↔Payment；缺字段/缺单据显式退回（不静默丢弃）。
- 新增 FI2-2 PO+GR+INV 明细行级四维匹配：物料编码 + 数量 + 金额 + 税额逐行比对，结果分五类（🟢完全匹配 / 🟡金额微差 / 🔴明细错位 / 🔴数量金额不符 / 🔴无GR支撑），**"明细错位"检出为核心价值点**（总额对、行错位的成本失真场景）。
- 容差/分类边界为**临时口径**（仿 FI1 的 `fi1-temp` 模式）：落 `config.py` + 规则注册表，唐燕萍 R1-R6 规则定稿后只换配置层、不改引擎。
- 数据接入采用**三源统一接口**（`mock`/`csv`/`u9c`，仿 FI1 `feed_source.py`）：`u9c` 源当前 fail-loud（`RealEndpointNotReadyError`），接口就绪后切源不改匹配引擎。
- 每笔匹配判定/分类写平台 `audit`（`scenario="FI2"`，append-only）；新增 L3 人工改判 CLI（仿 FI1 `confirm.py`，`--reason` 必填、幂等）。
- 自动化等级 **L3**（建议/预警，人工确认，不自动过账）；MVP 不实现 L4 自动过账。
- 本期不做（二期叠加）：FI2-3 税率专项 / FI2-4 查重 / FI2-5 容差专项收口 / FI2-6 退单 / FI2-7 考核 / FI2-8 学习。FI3（付款校验）为独立场景，不在本次范围。

## v3 口径修正（2026-07-09 追加，见 design.md 补充决策 D10-D13）

Mock MVP（首版 32 tests）入库后，唐燕萍团队回传《核实对照表》——应付会计实操细化揭示实际配票流程的核对对象是 **AP 单 vs INV**（非逐 PO 行），且供应商发票无我方物料编码、明细存在多对多。Paul 全盘采纳，本次追加调整：

- **核对对象**：AP 单 vs INV（PO 降级为价格前置参照，不再逐行匹配）。
- **匹配粒度**：按料品汇总归集比合计（数量/未税金额/税额），非逐 PO 行；四维改「料品+数量+未税金额+税额」。
- **发票源**：U9C 应付单附件 + OCR（挂载 `ap_no`），不再经 SRM。
- **新增 AP-PO 单价强制比对**（堵配票改金额漏洞），R7 容差占位 ±3%（唐燕萍授权定稿）。
- **FI2-6 初期缩范围**：退单仅拦截通知，闭环统计后置（不新增代码，原 MVP 本未实现）。

引擎在 `fi2-recon-mvp`（未归档）内原地调整，不新开变更包；黄金测试用例由 CC 按本次口径自拟 strawman，唐燕萍 R1-R7 规则草案（约 2026-08 底）交付后批改回归。详见 `1-转型规划/财务域场景v3-局部定稿.md` §1 修正1-7、`1-转型规划/FI4-三单匹配-就绪清单与MVP细化.md` v3 banner。

唐燕萍团队 R1-R7 规则草案较原计划（约 2026-08 底）提前 7 周交付（队列 #14，产出《FI2-FI3-规则定稿-交CC-2026-07-10.md》），CC 分支 `feat/fi2-v3-recon-engine` 承接落地（队列 #16）：

- **R5 门禁（新增，原设计完全没有此概念）**：整单差异总额分级 L2（AP 自行消化）/L3（人工），仅对"金额微差"生效——**Paul 2026-07-16 已拍板确认不扩大到"明细错位"，为最终口径**（见 design D14-b）。

- **料品编码归一化预处理**：新增 `item_normalize.py`，覆盖空格/全半角/括号/"-"与"/"等价类书写差异；不含模糊匹配/置信度分档/自学习的长线映射机制（留待真实数据接入阶段）。

真实数据验证仍按 8 月底排期不变（规则提前定稿不等于提前上线）。

## Capabilities

### New Capabilities
- `fi2-feed-source`：三单五表（PO/GRN/AP/Invoice/Payment，v3 新增 AP 明细行）数据接入层——三源统一接口（mock/csv/u9c，切源不改引擎，`u9c` 未就绪 fail-loud）、Pydantic 边界校验、缺字段/缺单显式拒收（不静默丢弃）。
- `fi2-match-engine`：AP+INV 按料品汇总归集匹配纯算法引擎（v3：PO 降级为价格前置参照，非逐行匹配主体）——料品/数量/未税金额/税额四维比对、判定优先级、"总额对明细料品错位"专项检测算法（核心价值点）。
- `fi2-result-classify`：五类匹配结果判定——数据驱动规则注册表（容差/边界临时口径，唐燕萍规则定稿后只换配置层不改引擎），版本登记。
- `fi2-recon-report`：对账聚合 + L3 门禁 + audit + L3 人工改判 CLI——报告契约（`needs_review`/`l3_suggested_pass`）、并入 AP-PO 价格校验的强制路由、每料品判定写平台 audit（金额脱敏、仅记差异比例）、"AI 建议非终局"标注、改判 CLI（`--reason` 必填、幂等）。
- `fi2-price-check`（v3 新增）：AP-PO 单价强制比对——堵 ERP 配票环节可手动改 AP 金额、无 PO 强制校验的控制漏洞，R7 容差占位 ±3%（唐燕萍授权定稿），金额脱敏。

### Modified Capabilities
（无——不修改现有 spec 的既有需求；v3 口径修正在 ADDED Requirements 内直接反映最终口径，因本变更包尚未归档，无需走 MODIFIED 增量）

## Impact

- 受影响代码：新建 `4-数字员工/财务部/FI2-三单匹配自动对账/`（`fi2` 包），复用 `5-平台底座/zhuopin_platform`（`audit`），不改动底座既有接口。
- 与 FI1 场景（`4-数字员工/财务部/FI1-供应链仓库对账/`）无代码依赖，仅照搬其三源接入/审计接线/L2改判 CLI 三个模式，各自独立包。
- 红线核对：mock 先行（u9c 源 fail-loud，未切真实库）✅ / audit 留痕（append-only，`scenario="FI2"`）✅ / OEM 隔离不适用（财务/ERP 内部数据）✅ / L2-L3 门禁（MVP=L3 建议，不自动过账，超容差/错位类强制转人工）✅ / ISO 26262 不适用（非安全相关）✅。

## 知识资产三问（强制，全景规划 §1.4 第 2 条）

1. **本流程哪些判断是人脑默会经验？**
   - 四维容差量级怎么定（数量/金额/税额各容忍多少算"正常尾差" vs "异常"）——目前只在财务对账人员经验里，靠"感觉不对"人工判断。
   - 五类结果的判定边界（尤其"金额微差"vs"数量金额不符"的临界线）——财务人员凭经验一眼区分，无成文规则。
   - "明细错位"识别——目前完全靠人工逐行核对发现，无显性规则，是财务反复强调的高风险盲区。
   - 分批到货（一 PO 行对多次 GRN/Invoice）如何匹配（FIFO 还是指定批次）——目前由对账人员按经验手工配对。
   - 差异根因 9 类分类（单据缺失/价格差异/数量差异/重复入账/税率差异/跨期/汇率差异等）——财务人员脑中有分类直觉，未系统化。
   - **（v3 新增）AP-PO 单价容差量级（R7）**——配票环节手动改金额时，多大偏离算"正常汇率波动"、多大算"异常需拦截"，目前无成文规则，靠应付会计经验判断；本次 CC 占位 ±3%，非专家定稿。
2. **由谁显性化？**
   - 持有人：唐燕萍（财务部 AI 专员，负责 R1-R6 规则口径拍板，约 2026-08 底交付草案）。
   - Backup：待唐燕萍指定（财务部另一名对账骨干，本次 propose 阶段未定，落地前需补齐双人制）。
   - 登记：本次 propose 完成后同步登记进《跨场景前置数据与知识库任务总表》§一.2 知识资产台账（由 Cowork 规划线执行，CC 不改规划文档）。
3. **用什么方法提取？**
   - **AI 起草·专家批改**（主）：本 MVP 用 mock 备料稿（`1-转型规划/FI2-三单匹配口径-mock备料.md`）的 strawman 容差/五分类边界起草，唐燕萍在此基础上批改出 R1-R6 定稿，替换 `config.py` 临时口径，引擎不动。
   - **L2/L3 改判判例累积**（辅）：MVP 上线后 L3 人工改判记录（`confirm.py` 写入 `audit`）沉淀为判例库，用于校准临时口径与后续 L3→L4 晋级的查准/查全率评估。

## 验收与晋档条件（强制，四档口径）

- **本变更包交付后场景所处档位**：档1 mock 验证 → **D18（round-1，2026-07-23）已实质达成档2**（真实 U9C 数据跑通匹配逻辑，CLI/CSV 路径，6/8 样本 10 料品零假阳性）→ **D19（2026-08-03）把档2 的真实链路接到已发布的档3 内部服务（`.51:8094` 面板）上**，但发票源仍是人工誊录小样、非自动化规模化直读，故**不构成档4 对客交付**，也不改变"发票自动直读（OCR）晋档"这条主线依赖——完整晋档 4 前提仍是 OCR round-2（#82）+ 唐燕萍口径定稿。
- **晋下一档的条件**（晋档2·真实数据跑通）：
  1. U9C PO/GRN 端点或 CSV 应急桥接就绪（比照 FI1 CSV 桥接模式）。
  2. SRM 发票源接通（解 900401 凭据）+ OCR 选型定案（发票解析准确率验收标准由唐燕萍与 IT 确认）。
  3. 唐燕萍 R1-R6 规则草案定稿，替换 `config.py` 临时口径（引擎不改）。
  4. 真实小样本跑通（比照 FI1 CSV 桥接真实验证模式），核对无静默丢单/无假阳性明细错位。
  5. Paul 审 design.md 技术决策通过（本 propose 附带 4 项待拍板决策，见 design.md）。
- **价值指标**（D-4 两级验收）：
  - 工时型：三单匹配人工核对工时（对账人员当前逐笔核对耗时）→ 目标降幅待唐燕萍确认基线。
  - 质量型："明细错位"检出查准率/查全率（L3 阶段用改判判例统计，达标线待定，作为 L3→L4 晋级门槛之一）。
  - 风险型：因明细错位导致的成本失真规避金额（需财务提供历史案例估算基线）。
  - 基线由业务 Champion（唐燕萍）在启动前确认存档；MVP 阶段暂用 mock 回归数据估算，真实基线待晋档2 补齐。
- **LLM 判据黄金集**：本场景 MVP 阶段为规则引擎（四维比对+容差阈值），不含 LLM 运行时判断，不适用黄金集要求。若后续（如 FI2-8 学习子场景）引入 LLM 辅助判定，届时另行补齐黄金集计划。
