# 日常短入口与需求验收

用户日常只需说“开启泳道看护”“我已回LAN”或“看看泳道”。长开场词仅作说明，不是消费任务的前置材料；部门、场景、目标、输入和原批准由入队方维护、消费方读取，不让用户反复填表。原队列仍是任务状态唯一真源。

首次真实试跑接力见 `docs/codex/日常构建首次看护试跑-R5-20261114.md`（2026-11-15更新）；只定向取当前任务，原队列仍是状态真源。

## 入队时完成，消费时取回

收件登记可以先落原队列；升为正式待建任务前在原行及原来源中明确以下内容，行内放必要指针，不另建任务库。

| 信息 | 原载体 | 缺口处理 |
|---|---|---|
| 场景/域、目标、业务预期 | 任务、期望产出、原intent/PRD | 先查原件，不能从零重问已答事项 |
| 输入与决定 | 原件哈希、回灌记录、原决策/批准指针 | 未核实与不存在分开；没有证据不补猜 |
| 范围、责任与外部卡点 | 触碰区、领取方、状态 | 保持唯一写方、冻结、原专业签认及生产授权 |
| 包、模式和规格/测试 | INDEX、现有OpenSpec | 新构建先准入；待决/常驻/纯材料行不强迫造包 |
| 验收与下一动作 | 同一tasks、spec scenario、功能/audit证据、检查点 | 已有条件直接复用，缺口回原任务；不另起执行器 |

## 两条短入口

由Agent用原隔离Python执行，用户无需粘贴命令：

```powershell
python "0-学习与工具/codex-handoff/handoff.py" watch-context
python "0-学习与工具/codex-handoff/handoff.py" watch-context --row 670
```

默认复用原actionable过滤后再排除任务栏🛑，并补入到期timed的review_only复核项，指定行返回当前原字段、引用文件指纹、范围和历史。`--all-open`仅用于全池整理，包含blocked/hold/timed，不代表解冻。`--expected-sha256`可核检查点后原行漂移。工具只查询、不认领、不写状态、不派模型；执行会话核原来源后按已有授权直接行动，不因工具不签发权限而重问用户。

`missing`仅表示原行缺基础字段；`checks_required`表示要核原批准范围和验收映射，不等于批准缺失。`execution_ready:false`是只读装载器不授权执行的边界，不是新增业务阻塞标签。原目标、来源和批准明确时，Agent按原技能继续，而非停在输出JSON。

开启看护：核现有认领/触碰冲突→顺序取原任务→准备或执行已批准离网切片→检查点→下一独立可做项。回LAN：原探针确认→原留步清单→逐项原授权→快照/执行/冒烟/回写；probe失败或一项依赖失败不假报完成。已存在的headless冻结合同保留，前台新任务不被强制塞进旧提交链。

开启看护取回上下文后，已有批准且无冲突的首项须在本主会话实际推进，无需第二条催办。首写前由Agent核原来源并生成临时切片参数，在原锁内通过 `handoff.py claim-slice --plan <参数JSON>` 将原行唯一写方、原批准范围/指纹、精确目标文件及§二预登记落实并反查，再释放锁进入实施。尚未创建的文件沿用 **`在办（预登记，收工时精确化）`**，不先造业务/测试/候选文件；普通登记仍验证原Git实体。登记或反查失败则零目标写入，记录后取得下一独立合法项；每次留步或收口前重查原池。临时参数不是新批准、任务库或用户输入表。

## 原验收记录的机器检查

不增加评分类或模型裁判。每个本次delta中的场景必须映射实际pytest用例和功能/audit证据，保留设计、spec、候选代码和测试源指纹。沿原包保存 `acceptance.json`，原driver的功能证据可保存 `acceptance-functional.json`；同一记录用于本地主会话检查和新driver closeout。

```powershell
python "0-学习与工具/codex-handoff/handoff.py" check-acceptance --id "<原包名>" --evidence "<验收JSON>" --workspace "<实际候选目录>"
```

记录字段：`task_id`、`level`（mock或real-readonly）、`design`、`candidate`、`specs`、`coverage`。文件引用统一为 `{path, sha256}`；每个coverage项含 `scenario`（能力::Requirement标题::Scenario标题）、`junit`、`classname`、`testcase`、`test_source`、`functional`。格式的可运行示例见 `0-学习与工具/codex-handoff/tests/requirement_fixtures.py::acceptance_packet`，由Agent根据实际测试生成，不让用户填写。

机器检查完整场景集合、真实文件/哈希、映射用例通过且非skip、测试源在候选中、功能证据存在；新driver只接受原CI中已核的JUnit，不允许换一份自制报告。缺一项或漂移阻断新合同的closeout；旧已封存合同不伪造升级成功。

这些检查证明证据完整性与可追溯性，不能自动判断业务断言是否写对；执行会话仍须依据原意图逐项核对正常、边界、缺数、异常、来源及audit行为。完整受影响项目pytest保留，不用覆盖表替代回归。mock结果不产生真实/专业/生产验收；发布和跟进信仍走原闸。

## 原事件消费链保持

监听入档→原信号→原事件拆件→原队列；本次只增强正式任务内容和后续验收。周期“回件拆件巡逻”继续停用，Codex cron的PAUSED不代表事件消费者停止。不得启用重复巡逻、重置checkpoint、清信号凑完成或改写消费者开关。

直接转交件用现有receive-feedback/backfill-feedback进入同一拆件机制。收件、消化、构建、LAN发布、使用反馈分别记账；闸开且已有逐封发送批准才沿原派发执行，不能自动外发，也不重复索取有效旧批准。

## 存量整理的效力

本轮全池整理是读取时点的索引与缺口记录，不替代现时队列，不自动解除blocked/hold/timed、不改旧领取方、不批量销号。每次看护仍重新查询原行。报告内未核项先沿原指针核实，不一股脑转成要求用户重新决策的清单。
