# 卓品智能 AI 转型：滚动业务任务与全景重基线设计

- 日期：2026-10-02
- 状态：待 Shao Peishen 审阅
- 类型：架构设计规格；尚非实施计划
- 范围：全景规划、实施路线与活跃会话的业务任务发现/推进机制

## 1. 目标与成功标准

把“日历排期”与“可开工条件”分离：在 Codex 会话活跃且正式全景未完工时，持续从权威状态中发现、排序并推荐可推进的业务任务。没有真实前置阻塞的业务任务进入可开池；一个任务受阻不停止独立任务。新场景先完成事实核验和 Shao Peishen 的业务意图 grill，再进入设计审查与任务建造。

成功标准：

1. 计划日期描述目标完成/最迟节点，不作为最早开工日。
2. 可开任务能追溯到正式队列行、已批准的 intent/design/tasks 和当前公开状态。
3. 被阻塞任务说明具体前置条件；部分可行时拆出可独立推进的部分。
4. 活跃会话在任务完成、闸口变化、恢复等有意义事件后重扫可开池并提出下一项建议；不依赖无变化轮询。
5. 新场景经明确业务确认与设计审查后进入正式范围；全景完工定义随正式范围动态计算。
6. 每次分派保留证据、决策与批准链，禁止重复建造和无授权的合并、生产部署、外发或代签。

## 2. 已确认的业务设计决策

2026-10-02 Shao Peishen 在本会话确认：

- 全景采用**滚动正式范围**。现有已签认场景持续有效；新场景经查重、业务意图签认和设计审查后纳入正式范围。
- Phase 1/Phase 2 表示战略批次与目标节点，不是开工窗口。排期用于排序和最迟节点管理，不压住已满足前置条件的任务。
- 活跃会话按 Probe、公开 Guardian/Workflow 状态和官方队列状态刷新。无真实前置阻塞的业务任务全部进入可开池；不设业务 WIP 上限。真实并发仍受当前车道上限、同泳道串行与共享触碰约束。
- 启动须走正式 manifest、Guardian 和获准隔离工作树。ff、生产部署、对外发送、L2 决策继续按具体事项逐项授权。
- 任务推荐随会话活跃而持续；会话结束后不承诺后台自动续跑。
- 新场景流程：先查重和事实核验；Shao Peishen 决定业务边界；专业判据由专员基于案例确认；意图签认后做设计审查，再建正式任务并启动建造。未签认的阈值、红线和验收标准不设默认值。

## 3. 备选方案与选择

| 方案 | 做法 | 影响 |
|---|---|---|
| A. 固定 35 场景范围 | Phase 1/2 边界作为硬开工边界，新场景只登记候选 | 易于保持固定总量，但与“依赖就绪即可推进、可开新场景”的指令不符 |
| B. 滚动正式范围（选定） | 已签认场景不变；新场景通过 grill 与设计审查后纳入；日期只作目标节点 | 能提前并行推进已就绪业务项，同时保留新场景逐项决策和审计链 |
| C. 发现即扩范围 | 发现候选时就直接纳入 | 启动快，但会在业务意图和设计边界未明时造成范围漂移 |

选择方案 B。候选发现本身不等于正式立项；通过必要的业务与设计闸口后才扩大正式范围。

## 4. 活跃会话任务环

### 4.1 刷新权威状态

在会话启动/恢复、任务完成、人工闸口解除或出现新场景线索时执行一次状态刷新：

1. 调用仓库正式 Probe 入口确认 HEAD、工作树、Python/Codex 环境和 CI 矩阵。
2. 用 `工具-队列查询.py --digest --actionable` 获取业务池摘要；候选行再用官方 `--row N --section 一 --field all` 查询。不得通读或 grep 队列真身。
3. 只读取 Guardian/Workflow 的公开状态；不得读取私有 runtime 状态。
4. 对“已做/待做/阻塞”有冲突的行，先对账当前交付物、签认台账和队列日志，再决定是否续做，避免重复建造。

公开状态查询失败时保留失败证据，停止依赖该状态的启动步骤；不得转读私有运行时数据。队列摘要不等于可开工结论。

### 4.2 就绪分类与任务拆分

每个候选任务标记为：

- **可开**：其本阶段所需材料、前置任务、业务标准和权限均已满足。
- **部分可开**：有独立交付不依赖当前阻塞项；拆出该部分，不伪造整体已就绪。
- **真实阻塞**：缺材料/数据、未签认业务标准、未完成依赖、责任人决策未到位，或缺少针对该项的权限批准。
- **待对账**：队列状态疑似过期，先核对交付证据再分派。
- **终态**：验收/关闭证据齐全，不再推荐重复建造。

排期日期只作为任务排序信号或最迟目标，不作为最早开工闸。业务任务不设 WIP 数量上限；实际同一时刻运行数受既有车道并发上限、同车道串行规则、共享文件触碰和正式 Guardian 能力约束。

### 4.3 排序、推荐和启动

可开池排序依次考虑：关键路径/共享前置影响、业务价值与队列优先级、当前目标日期、可并行性、阻塞解除后的衔接收益。无真实前置阻塞且输入材料已齐的业务任务，应进入正式启动集合，并在既有并发能力内立即派入获准车道；超出并发能力的任务保持容量排队，不得误标为业务依赖阻塞。任务完成或槽位释放后自动补位。每轮向 Shao Peishen 提供：

1. 首选下一任务及为何现在可开；
2. 其它独立可开项及并行冲突；
3. 被阻塞项、具体缺口和责任动作；
4. 需 Shao Peishen 决定或批准的事项。

启动必须使用获准隔离工作树、明确 `gpt-6-luna`、正式任务/设计材料与 Guardian manifest。看护者主仓不建业务分支、不改业务代码。没有活动任务时不凭空声称后台会继续。

### 4.4 既有逐项闸口

以下权限不会由“全景滚动推进”概括授权替代：ff 合入、生产 `.51` 部署、真实对外发送、L2 最终决定、涉及真实 OEM 数据的使用。每项仍须找到对应审批证据。数据先 mock/脱敏；客户数据严格隔离。

## 5. 新场景发现与 Q9 APQP

### 5.1 场景发现流程

1. 从全景缺口、候选库和正式队列发现问题；检索场景目录与既有交付，先做 M2 事实自查和去重。
2. 只把业务范围、责任归属、风险接受、优先级和预期结果等 Shao Peishen 决策提交 grill。技术验收标准、阈值、反例和实现细节由相关专员以案例材料确认。
3. 所有待决业务选项均已签认后形成 `status: 已确认` 的 `intent.md`；未有明确签认的验收阈值/红线保持未决，不能用默认值填补。
4. 形成设计件并完成人工设计审查；审查通过后再写正式任务行，按锁工具登记，并经 Guardian/隔离工作树启动。

### 5.2 Q9 已确认边界

Q9 APQP 与 Q4 PPAP **分为两个场景**：Q9 负责一个 APQP 阶段的上游评审；Q4 继续负责 PPAP 最终提交包审查。Control Plan 是共享输入，但规则、阶段和验收边界分别维护。

Q9 首期只试点一个明确 APQP 阶段，再按证据扩展；质量部牵头，工程/项目提供阶段资料并共同签认。质量文档目录当前未发现 APQP 样本，因此先使用 mock/脱敏材料；专业人员需盘点可用证据并推荐具体试点阶段，阶段选择与专业判据须在设计审查前定稿。AI 输出保持 L2，由人最终确认；OEM 资料不跨客户混用。

## 6. 全景完工判据

当以下条件同时成立，才把全景标记为完工：

1. 正式范围内所有场景均有验收或正式退役记录；
2. 路线图级目标均已达成，或有 Shao Peishen 的正式退役决策与理由；
3. 正式范围及其共用前置项没有未闭合、仍需推进的业务任务；
4. 相关证据、交付、批准和跨文档回写闭环。

候选场景通过闸口加入正式范围会重新打开完工判定。单纯队列“open”字段不能单独证明未完工；须与实际交付和正式日志对账。
