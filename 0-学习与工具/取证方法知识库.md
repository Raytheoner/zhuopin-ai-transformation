# 取证方法知识库

> **本文件是什么**：`CLAUDE.md` §5 里那些**「是知识、不是纪律」**的条目的正本。它们没有「该做／不该做」，只有**「查这个别查那个」**——放在每会话必载入的 §5 里会持续消耗注意力预算，但删掉又会让同一类误判复发。
> **为何建在 `0-学习与工具/`**：① 这里是本仓库的方法与工具目录，取证方法是其自然归属；② 它会被 `工具-文档台账生成.py` 扫进《文档台账-自动生成.md》，**靠台账可检索，而不是靠谁记得有这么个文件**；③ 刻意**不并进 `专线opener模板库.md`**——那份已 12 条且只在写 opener 时才读，再堆进去正好复现队列 #311 根因链第 ② 段「入法但落在非必读载体，仍会在需要它那一刻缺席」。
> **§5 侧留了什么**：D1／D2 合并为一行指针；**D3（工具静默回退）在 §5 保留一行硬提示**——它是 B 类错误的主要来源，不能只剩指针（判定表原话）。

## 一、时序取证

### 1.1 判「本机是否重启过」只认 `ID=27 Kernel-Boot 引导类型`（原 §5 D1）

**同族第二条（Shao Peishen 2026-07-31 同日定）：判"本机是否重启过"只认 `ID=27 Kernel-Boot 引导类型`**——`0x0`＝冷启动／`0x1`＝**hiberboot（快速启动/混合关机后的引导）**／`0x2`＝从休眠恢复。**以下三个直觉判据在快速启动下全部静默失效，不得作为"未重启"的依据**：① `Win32_OperatingSystem.LastBootUpTime`（hiberboot 不更新，它反映的是**内核会话起点**而非上次开机）；② 由它算出的 uptime（同理，是内核会话时长）；③ 事件日志 `6006`/`6005`（事件日志服务停止/启动）与 `Kernel-General 13`/`12`（OS 关闭/启动）**配对**——hiberboot 因内核会话由休眠映像恢复，OS 视角无"关闭/启动"，这四个 ID 一个都不记。**实证（2026-07-31）**：Shao Peishen 手动关机后马上开机，我因只看 ②③ 而误判"PC 实际没重启"，据此把一次**正常的关机-重启**定性成"守护进程被会话终止杀掉的自愈缺陷"（队列 #193 原文），主语全错；补看 `ID=27` 后见 `17:04:14 本地 / 09:04:14Z 引导类型 0x1`，确证走的是快速启动，同日 07-30 那三次 Windows Update 重启则是 `0x0` 并伴随完整 13/12/6006/6005/6013。**取证清单**：查开关机一律 `Get-WinEvent` 取 **12/13/27/41/42/107/109/1074/6005/6006/6013 全集**，勿只取子集——**过滤清单漏 ID 与"判据在特定环境下失效"是同一类错**，都会让证据看起来完整而结论是反的。

### 1.2 时间戳基准的两个实测陷阱（原 §5「同步纪律」内，随 E3 拆分迁入）

> **规则本体（仍在 §5，未迁）**：引用任何时刻前先答一句「这个值是 UTC 还是本地」，并在输出里显式标基准。以下是它的两个取证陷阱。

> **两个实测陷阱（2026-07-31 同日各踩一次，均属误判前兆）**：① PowerShell 的 `ConvertFrom-Json`／`[datetime]::Parse` 会把 ISO 串解析成 `DateTime` 后**按本地时区显示**——同一批消息因此呈现 `09:07` 与 `17:07` 两种时刻，一度被误定性为"audit 时间基准不一致"（**险些多报一条不存在的缺陷**）；要真 UTC 须显式 `.ToUniversalTime()`，要对比就两个都打出来。② 时长差值**绝不用只含 `hh` 的格式串**（`.ToString("hh\:mm\:ss")` 会**丢掉 Days**，29 小时显示成 5 小时，差点据此误判"PC 今天重启过"），一律用 `TotalHours` 或 `d\.hh\:mm\:ss`。

## 二、工具行为

### 2.1 工具静默回退（原 §5 D3，**§5 仍保留一行硬提示**）

**同族第三条（Shao Peishen 2026-08-03 定）：⚠️ 工具静默回退 —— 一类工具在参数不符合预期时不报错，而是静默回退到一个「看起来合理」的默认行为**，于是返回值本身完全正常、结论却是反的。**两个实测实例（2026-08-03 同日各害一次，且都差点写进正式记录）**：① **`[System.IO.File]::*`（`ReadAllBytes`／`ReadAllText`／`WriteAllText`）的相对路径不按 PowerShell 的 `cd` 解析**，而按宿主进程 CWD——同一路径它返回「0 字节」、`Get-Content` 返回 134 行，据此几乎判定「队列清扫把文件写坏了」；更早一次「转义视图打印为空白」亦同源。**一律用绝对路径。** ② **`git -C <非 worktree 的普通目录>` 会静默向上找到最近祖先仓库的 `.git`**，返回**那个仓库**的状态——对一个 0 文件空壳目录跑它，返回的是主工作区的「分支=master／落后 0／领先 0／脏 0」，据此会把一个该清理的空壳记成「干净、无需处理」。**判 worktree 身份一律看两件事：该目录内 `.git` 条目是否存在 ＋ 是否在 `.git/worktrees` 注册项内；不看 `git -C` 的输出**（呼应 #166「身份以当刻实测为准」与 #98 体检口径）。 **共同判据（比记住这两个实例更有用）**：**当一个只读命令返回了「太干净」或「太正常」的结果，先问它是不是根本没读到我以为的那个对象**，而不是直接采信——**坏消息会让人追根因，好消息不会**，这正是防线 4 点名的高危触发条件。

### 2.2 新增实例 · 混合行内结束符文件（2026-08-09 本次执行时实测）

> 判一份 `.md` 用什么换行符时，`"\r\n" in text` **为真不代表每一行都是 CRLF**——`开场prompt-【Cowork】环境总线-接力交接-2026-08-08.md` 实测 **CRLF 仅 1 处、LF 146 处**，据 `in` 判定得出的分隔符去做 `replace` 会**命中 0 次**。本例因写了 `assert count==1` 而**当场 fail-loud**，未造成静默错误——**这正是 §〇.6 写后反查三件套要防的那一类**，登记于此作为「同一族错误换个外形又出现」的样本。**判法**：分别数 `count(b"\r\n")` 与 `count(b"\n")`，两者相等才是纯 CRLF。

## 三、文件与仓库

### 3.1 排查「文件像是变旧了」的顺序（原 §5「同步纪律」内，随 E3 拆分迁入）

> **排查"文件像是变旧了"的顺序（2026-07-07 定，先易后难，勿一上来就疑真损坏）**：① 先查 `git branch`/`git reflog`（是不是切错分支、或看的是旧提交）；② 再用桌面本机磁盘直读比对（桌面为真身，Cowork 挂载视图可能滞后）；③ 前两步都排除了，才怀疑真实损坏（走 fsck/重 clone 恢复流程）。

## 四、元判据

### 4.1 判据本身也需要被质疑一次（原 §5 D2）

**本段两条的共同教训**：判据本身也需要被质疑一次——「有无 X 事件」型判据在换了一种系统行为（快速启动、时区转换、清扫、锁忙推迟）后可能整体失效，而失效时它**不报错、只是安静地给出反向答案**。
