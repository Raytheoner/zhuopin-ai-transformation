## 一、时序取证

### 1.1 判「本机是否重启过」只认 `ID=27 Kernel-Boot 引导类型`（原 §5 D1）

**同族第二条（Shao Peishen 2026-07-31 同日定）：判"本机是否重启过"只认 `ID=27 Kernel-Boot 引导类型`**——`0x0`＝冷启动／`0x1`＝**hiberboot（快速启动/混合关机后的引导）**／`0x2`＝从休眠恢复。**以下三个直觉判据在快速启动下全部静默失效，不得作为"未重启"的依据**：① `Win32_OperatingSystem.LastBootUpTime`（hiberboot 不更新，它反映的是**内核会话起点**而非上次开机）；② 由它算出的 uptime（同理，是内核会话时长）；③ 事件日志 `6006`/`6005`（事件日志服务停止/启动）与 `Kernel-General 13`/`12`（OS 关闭/启动）**配对**——hiberboot 因内核会话由休眠映像恢复，OS 视角无"关闭/启动"，这四个 ID 一个都不记。**实证（2026-07-31）**：Shao Peishen 手动关机后马上开机，我因只看 ②③ 而误判"PC 实际没重启"，据此把一次**正常的关机-重启**定性成"守护进程被会话终止杀掉的自愈缺陷"（队列 #193 原文），主语全错；补看 `ID=27` 后见 `17:04:14 本地 / 09:04:14Z 引导类型 0x1`，确证走的是快速启动，同日 07-30 那三次 Windows Update 重启则是 `0x0` 并伴随完整 13/12/6006/6005/6013。**取证清单**：查开关机一律 `Get-WinEvent` 取 **12/13/27/41/42/107/109/1074/6005/6006/6013 全集**，勿只取子集——**过滤清单漏 ID 与"判据在特定环境下失效"是同一类错**，都会让证据看起来完整而结论是反的。

### 1.2 时间戳基准的两个实测陷阱（原 §5「同步纪律」内，随 E3 拆分迁入）

> **规则本体（仍在 §5，未迁）**：引用任何时刻前先答一句「这个值是 UTC 还是本地」，并在输出里显式标基准。以下是它的两个取证陷阱。

> **两个实测陷阱（2026-07-31 同日各踩一次，均属误判前兆）**：① PowerShell 的 `ConvertFrom-Json`／`[datetime]::Parse` 会把 ISO 串解析成 `DateTime` 后**按本地时区显示**——同一批消息因此呈现 `09:07` 与 `17:07` 两种时刻，一度被误定性为"audit 时间基准不一致"（**险些多报一条不存在的缺陷**）；要真 UTC 须显式 `.ToUniversalTime()`，要对比就两个都打出来。② 时长差值**绝不用只含 `hh` 的格式串**（`.ToString("hh\:mm\:ss")` 会**丢掉 Days**，29 小时显示成 5 小时，差点据此误判"PC 今天重启过"），一律用 `TotalHours` 或 `d\.hh\:mm\:ss`。

### 1.3 写入日期的两次事故（原 §5「时间戳必判 UTC vs Win 本地」条，2026-08-22 随 OP-0822-B 迁入）

> **判据本体（仍在 §5，未迁）**：写入日期一律取本机本地 `Get-Date`、每次写入前重取、禁用沙箱 `date`。以下是催生这两条判据的两次真实事故——**它们的共同形态是「错了不报错」**：日期写偏一天，所有以日期定位的判据（值周对账、协议〇.8 按日期分档、#107 归档↔队列配对）会安静地偏一格。

> **事故一 · 跨日估算（2026-08-04，队列 #246）**：**实证**：2026-08-04 22:34 本地（14:34Z）时，队列 #238／#236／#229／#227 四行与本文件顶部 Last Updated 共 **5 处**标注 `2026-08-05`——该日期既非本地也非 UTC（UTC 更早 8 小时，只会落在 08-04），系跨日估算所致。**影响**：凡以日期定位行/批次的判据（值周对账、协议〇.8 每周清扫按日期分档、#107 归档↔队列配对）会偏一天。**已写的 5 处按「历史记录不追改」保留不动**，本条只约束此后写入。

> **事故二 · 同一会话内沿用旧日期（2026-08-15）**：**实证（2026-08-15，本条即由此事故催生）**：环境总线某次会话开工时沙箱 `date` 报 2026-08-13（当时属实），该会话此后跨越约 39 小时，**日期取值一直沿用未重取**，导致两批产出（commit `0d0980b` 真实 08-14 08:44、`9bd6535` 真实 08-14 16:43）连同其中「Shao Peishen 2026-08-13 拍板」的**决策署期**一并写错一天。**已按 Shao Peishen 2026-08-15 拍板 (a) 追改「拍板署期」与队列 #315 那条观察的日期，批次名与文件名按「历史记录不追改」保持原样。** 🔑 **它当时有线索被漏掉**：同批读到的巡逻自述里写着「QD-B 上次改动 07-30 **今日刚滑出 14 天窗口**」——07-30＋14 已蕴含「当天必在 08-13 之后」，**读到了却没换算**。⇒ **凡文本里出现可反推当前日期的相对表述（窗口、天数差、到期），应顺手做一次换算校验。**

> **为何值得当硬规则（原 §5 同条内一句，同批迁入）**：**为何是硬规则**：#107 归档↔队列配对判据、#147 存活戳、#172 的 1/3/7 天递减去重全部依赖时间戳，**算错 8 小时即判据失效**；本条是「取证先于定性」在时序推理上的具体化——**时序是取证最容易翻车的一环**。

## 二、工具行为

### 2.1 工具静默回退（原 §5 D3，**§5 仍保留一行硬提示**）

**同族第三条（Shao Peishen 2026-08-03 定）：⚠️ 工具静默回退 —— 一类工具在参数不符合预期时不报错，而是静默回退到一个「看起来合理」的默认行为**，于是返回值本身完全正常、结论却是反的。**两个实测实例（2026-08-03 同日各害一次，且都差点写进正式记录）**：① **`[System.IO.File]::*`（`ReadAllBytes`／`ReadAllText`／`WriteAllText`）的相对路径不按 PowerShell 的 `cd` 解析**，而按宿主进程 CWD——同一路径它返回「0 字节」、`Get-Content` 返回 134 行，据此几乎判定「队列清扫把文件写坏了」；更早一次「转义视图打印为空白」亦同源。**一律用绝对路径。** ② **`git -C <非 worktree 的普通目录>` 会静默向上找到最近祖先仓库的 `.git`**，返回**那个仓库**的状态——对一个 0 文件空壳目录跑它，返回的是主工作区的「分支=master／落后 0／领先 0／脏 0」，据此会把一个该清理的空壳记成「干净、无需处理」。**判 worktree 身份一律看两件事：该目录内 `.git` 条目是否存在 ＋ 是否在 `.git/worktrees` 注册项内；不看 `git -C` 的输出**（呼应 #166「身份以当刻实测为准」与 #98 体检口径）。 **共同判据（比记住这两个实例更有用）**：**当一个只读命令返回了「太干净」或「太正常」的结果，先问它是不是根本没读到我以为的那个对象**，而不是直接采信——**坏消息会让人追根因，好消息不会**，这正是防线 4 点名的高危触发条件。

### 2.2 新增实例 · 混合行内结束符文件（2026-08-09 本次执行时实测）

> 判一份 `.md` 用什么换行符时，`"\r\n" in text` **为真不代表每一行都是 CRLF**——`开场prompt-【Cowork】环境总线-接力交接-2026-08-08.md` 实测 **CRLF 仅 1 处、LF 146 处**，据 `in` 判定得出的分隔符去做 `replace` 会**命中 0 次**。本例因写了 `assert count==1` 而**当场 fail-loud**，未造成静默错误——**这正是 §〇.6 写后反查三件套要防的那一类**，登记于此作为「同一族错误换个外形又出现」的样本。**判法**：分别数 `count(b"\r\n")` 与 `count(b"\n")`，两者相等才是纯 CRLF。

### 2.3 新增实例（第四、第五条）· `git worktree repair` 的作用对象由「它读到的路径」决定，不由「你在哪个仓库里执行」决定

> **实测来源**：`1-转型规划/0-全景路线图/OneDrive迁出回滚演练结果-队列407-2026-08-25.md` §1.2／§1.3（队列 §一 #407，一次性玩具仓库 `_lab1/_lab2/_lab3` 复现，**未在生产上验证猜测**）。

**🔴 判据（一句话）：`git worktree repair` 一律显式传路径，永不裸跑。**

裸跑 `git worktree repair` 会读取当前仓库管理文件里**记着的路径**，然后去修**那些路径指向的仓库**——哪怕那是别人的仓库。两种误用**都是静默的**，构成「工具静默回退」族的第四、第五个实例：

| # | 场景 | 裸跑的结果 | 为什么无声 |
|:--:|---|---|---|
| **④** | **复制**出一份仓库副本后，在**副本**里裸跑 | 🔴 **改的是源（＝生产）那一侧**——把源仓库的 26 个 worktree 全部改绑到副本的 `.git`；**副本自己一处也没修好**（演练目标根本没达成） | 每个 worktree 只输出一行 `repair: .git file incorrect: <路径>`，**读起来像诊断信息，不像「我刚把你的生产指针搬走了」**；被劫持后的 worktree 跑 `git status` **完全正常** |
| **⑤** | **移动**仓库后（旧路径已消失），在新路径裸跑 | 🔴 **什么也没做**——零输出、退出码 0、全部仍是 `prunable` | 退出码 0 ＋ 无输出，与「一切正常」不可区分 |

**正确写法**（两种场景通用）：

```powershell
$wts = Get-ChildItem "<新路径>\.claude\worktrees" -Directory | % { $_.FullName }
git -C "<新路径>" worktree repair @wts
```

**第二棒才是真正的杀伤**：④ 之后若再执行「收工前删除副本」，会**删掉源仓库 26 个 worktree 此刻所依赖的 git 目录**——连同其中未提交的改动一起报废，**而在此之前的每一条命令都显示成功**。

**⇒ 连带的验证判据**：**不得只用 `git worktree list` 作为清点分母。** 同次演练查实生产侧存在 **2 个「静默隐身」worktree**——`.git` 回指正确、`.git/worktrees/<n>/` 管理目录也在，只是里面的 `gitdir` **文件缺失** ⇒ 它们从 `worktree list` 里**整个消失**（连 `prunable` 都不报）。**须逐个 `git rev-parse --git-common-dir` 回读**。同次清点：磁盘 53 个目录 ＝ 健康注册 26 ＋ 孤儿幽灵 25 ＋ 静默隐身 2。

### 2.5 新增实例（第七、第八条）· 进程侧的两个恒假判据（2026-08-25 同晚各害一次）

> **来源**：队列 §一 #407 回滚演练当晚，两条被当场推翻的判据。

**⑦「杀了就没了」——被守护拉回，而复核窗口太短，读到的「干净」是假的。**

企微机器人是**三层**：`wscript.exe → run-hidden.vbs → powershell(守护) → python(服务)`。

- `Stop-ScheduledTask` **杀不掉它**——VBS 用 `WScript.Shell.Run` 起的链在中间脱钩，只终止它认得的那一层。
- 只 `Stop-Process` 掉 python **必被拉回**——守护 `start-aibot-service-dev.ps1` 是 `while ($true)` ＋ **三级退避 60／300／900 秒**，第 60 秒重启。
- 🔴 **实测事故**：杀完 `Start-Sleep 2` 就复核 → 返回**空**（看起来干净）→ 60 秒后进程无声回来。**一次返回「干净」的复核，对象在退避窗口后自己回来，全程零信号。**

**判据**：**停任何带守护/重启策略的常驻物，复核必须等过它的最长首级退避（本例 ≥70 秒）**；且**先杀守护、再杀被守护者，顺序不能反**。

**⑧「`Get-Process <名>` 数出来的不是我以为的东西」——一个恒假判据。**

`Get-Process claude` 实测恒为 **14+**：其中只有 1 个是真正的 Claude Code 会话（`…\AppData\Roaming\Claude\claude-code\<ver>\claude.exe`），其余全是 Claude Desktop 这个 Electron 应用的进程组（主进程 ＋ renderer ／ gpu ／ network ／ audio ／ video_capture ／ crashpad ／ node utility ×6，同父进程）。

- **按进程名写的「应为 0」自检永远过不了** ⇒ 恒假判据，要么被绕过、要么把人卡死。
- 正确写法按**可执行路径**筛：`Get-CimInstance Win32_Process -Filter "Name='claude.exe'" | ? { $_.CommandLine -like '*claude-code*' }`
- 🔴 **且它有边界**：`claude-code` 进程**每轮对话新起、答完即退** ⇒ 只能测「此刻有无会话在执行」，**测不出「有无窗口随时可能醒来」**。

**判据（比这两个实例更通用）**：**一个数字看起来「太多」时，和它看起来「太干净」时同样可疑**——但「太多」更不容易起疑，因为它符合「问题很严重」的预期。**先问它数的是不是我以为的那个对象。**

**⇒ 连带的一般原则**：判「能不能开始一段独占操作」，**须按「谁会自己动」两分**——① **自动触发物**（计划任务、守护、批处理 runner）能机器判、且必须停；② **人开着的窗口**判不出来，只能靠执行期间不去碰它、并把窗口压短。把两者混成一条判据，结果要么恒假、要么给出虚假的安全感。

### 2.6 新增实例（第九条）· 两个字面完全相同的路径，指向两个不同的目录（2026-08-27 实测）

> **来源**：Cowork 项目的 Outputs／Memory 面板「Failed to load file.」／「Unable to read file.」追因。🔴 **与 2026-08-26 的 OneDrive 迁移无关**——分裂早于迁移（容器侧探针文件日期 2026-07-04）。

   `%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\…`。

**14:09 那份是应用写的，14:12 那份是 `Write` 工具写的——同一条记忆写成了两份，落在两个目录。**

**⇒ 本项目 memory 层「fail-silent」的根因由此改判**（原记载见根 `CLAUDE.md` 顶部 memory 段、`memory与上下文预算治理-审核与方案-2026-08-21.md`）：

- **实为**：**注入侧读容器，写入侧写未重定向路径**——写进去了，只是一直从另一个目录里去查。2026-08-21 判死所用的两个探针 `_test_write_probe.md`（07-04）与 `_writetest_20260805.md`（08-05）**在容器侧完好存在**。
- 🔴 **结论不变**（此后不读不写 memory、跨会话纪律一律落 `CLAUDE.md` 与两份队列）——读写两侧确实对不上，该层依然不可信。**变的只是根因记载，不是处置。**

**通用判据（比这个实例更有用）**：

1. **凡遇「文件明明在、程序却读不到」或「写了却查不到」，先问一句：我这个进程被文件系统重定向了吗？** 常见重定向面：**MSIX/Store 打包应用**（`LocalCache\Roaming`）、**UAC 注册表/文件虚拟化**（`VirtualStore`）、**WOW64**（32 位进程访问 `System32` 被转到 `SysWOW64`）、容器与沙箱挂载。
2. **判两棵树是不是同一棵，不比路径字符串，比文件本身**——存在性 ＋ 大小 ＋ 哈希 ＋ mtime，四者一致才算同一份。
3. **本族的独特危险在于：两侧都不报错。** 写成功、读成功、路径显示一致，只有内容对不上——**与 2.1「工具静默回退」同源，但更隐蔽：那一族至少还只有一个对象，这一族有两个对象长着同一个名字。**

**查法（只读，可直接照抄）**：

```powershell
# ① 判进程是否打包运行
Get-CimInstance Win32_Process -Filter "Name='claude.exe'" | Select-Object -First 1 ExecutablePath
# 路径含 \Program Files\WindowsApps\ ⇒ 打包应用，其 %APPDATA% 写入被重定向

# ② 同一相对路径在两棵树里各是什么
$rel = "local-agent-mode-sessions\<sessionGuid>\<projGuid>\spaces\<spaceGuid>\memory"
$r = Join-Path $env:APPDATA "Claude\$rel"
$c = Join-Path $env:LOCALAPPDATA "Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\$rel"
foreach ($p in @($r, $c)) { "{0,4} 个  {1}" -f @(cmd /c "dir /b /a-d `"$p`" 2>nul").Count, $p }
```

⚠️ **`Get-ChildItem` 在此不可作为分母**（见本节 §2.5 之外的独立实测：同命令连读得 44,006 与 52,766）——用 `cmd /c dir /b` 或 .NET `Directory.GetFiles` 二次确认。

**处置**：**不要动这些文件。** 容器侧那份是应用真正在用的、内容更全；删或合并未重定向侧的残留不会修好面板，只会丢东西。面板读不出是应用侧路径解析的事，在文件系统上修不了。
