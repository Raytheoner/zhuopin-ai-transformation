# 项目PRD与UI正式整理材料盘点与建议

## 意图与当前缺口

Shao Peishen希望借财务需求调整，把整个项目的PRD与UI Design正式整理，再依据它扎实推进业务。这里按项目级整理理解：业务部门与AI专员能审需求和判例，IT/建造线能据明确合同实施，运营能看清上线、运行、验收及价值状态。成功标准是已有事实可追溯、待定项显式、规格与页面/验收有对应关系，而非文件齐全就算业务完成。

已查文档台账：存在`1-转型规划/质量旗舰PRD-项目立项审核门禁.md`（在办）及`质量旗舰PRD-Q2-8D不良分析与根因.md`（历史快照）。其它需求与设计分散于全景、场景intent、OpenSpec proposal/design/specs/tasks、财务局部定稿、真实回件及场景页面。台账中未发现以项目总PRD或统一UI Design命名的正式正本；这是当前台账范围的发现，不推定全仓所有交互资料不存在。

SC8、SC2、FI2、FI3、QD-B、Q2已各有webapp及内嵌样式。已有界面可以作为实物基线；不能直接把实现全部追认为批准设计，也不能把mock页面视作真实业务能力。#539已有SC2对齐SC8样式的需求，说明统一设计有具体承接点，改版仍依赖其原前置。

## 三种整理方案

| 方案 | 产出与代价 | 适用性 |
|---|---|---|
| A 财务域单独补件 | 一份财务PRD及财务页面稿，整理量较小；其它域继续各自组织 | 可先局部使用，难解决整个项目的共用体验和追溯问题 |
| B 项目总纲＋共用UI规范＋财务首个详细样板（推荐） | 总PRD保留目录/共性，场景细节引用原正本；统一UI规范覆盖高频任务；财务首批按已签认与待定分层 | 兼顾项目正式整理与近期业务推进；已有上线场景逐批接入，无需全部重做后才能发布 |
| C 所有场景一次重编完整PRD/UI | 一次性覆盖最广；大量未签认口径和历史分支会进入同一整理批，审阅和冲突成本大 | 当前财务调整及引擎收口仍未闭合，不推荐作为近期主线 |

## 推荐方案的可审产物

拟定三个文档系列，命名、维护owner及落点在批准组织方案后定稿并登记文档台账；正式文档提供同名md/docx。以下是章节清单，不宣称正文已经完成或获批。

1. **项目PRD总纲**：目标与价值度量；部门/用户角色；场景目录及优先级；用户任务端到端流程；统一能力边界；数据来源/时效与OEM隔离；L1/L2及人工责任；通知/审计/归档；验收与发布条件；当前运行事实；未定项和版本记录。数值目标和业务阈值按来源继承，缺签认的只记录待定。
2. **统一UI Design**：门户信息结构与导航；场景工作台、列表、异常明细和来源凭据入口；人工复核/决定/理由；反馈、导出和历史；字体、间距、表格与数字/日期格式；状态文字和颜色同时表达；加载/空数据/源不可用/部分数据/过期数据/无权限/待人工确认；mock/真实、数据时间与版本清楚可见；键盘/窄屏及权限体验。只讨论帮助业务作决定的信息，不把runtime或内部脚本细节塞给专员。
3. **财务域PRD＋首批场景页面设计**：FI1–FI10目录和已定/调整/暂停状态；角色与前后步骤；数据字段、规则、异常处理、人工签认与留痕；每页输入输出/可执行动作/反馈；判例到验收表。FI2/FI3现有页作为事实基线，正式首个调整场景以#20回灌及本人范围确认选择，不能预设FI1复启或FI2规则重写。

每条需求拟用稳定ID，建立一张追溯表：`PRD ID → 原批准/回件 → 业务规则/字段 → 页面/交互 → OpenSpec requirement → 判例/验证证据 → 发布版本/验收人`。UI状态、AI结论、人工决定及上线状态分别标识，避免“显示绿色”代替业务签认。

可直接整理已有v4/v3、FI3既有R1–R8与D1–D8签认、FI2已实现页面/税务接入资料，以及其它场景已持材料；记录现状、索引来源、列出空缺，不向IT/财务重复索取已入库答案。现有资料路径已经核对。

## 审阅与接续

本建议尚缺本人对方案B组织范围的确认。确认后写正式书面规格，先呈PRD业务骨架及UI关键流程，再经书面审阅进入实施计划。依据`.agents/skills/brainstorming/SKILL.md` Architectural闸："Conversational design approval only permits writing the spec; written-spec approval only permits invoking writing-plans." 本轮只形成可审组织建议和材料盘点，没有生成产品代码或把待定规则写成批准规格。

上线收口与文档整理可并行推进：近期先处理自动拆件及机器验收账差异；业务候选按确切版本、前置、验证和回滚形成单项发布件。财务回件到达时通过原入信/拆件/回灌流程更新需求，不能绕过正式串行闸发送新信。
