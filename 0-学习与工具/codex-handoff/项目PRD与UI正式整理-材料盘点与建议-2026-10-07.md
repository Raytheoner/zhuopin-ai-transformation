## 三种整理方案

| 方案 | 产出与代价 | 适用性 |
|---|---|---|
| A 质量域单独补件 | 一份质量PRD及质量页面稿，整理量较小；其它域继续各自组织 | 可先局部使用，难解决整个项目的共用体验和追溯问题 |
| B 项目总PRD＋统一UI规范＋质量详细样板（推荐） | 总PRD保留目录/共性，场景细节引用原正本；质量以QD-B为首样板、Q2补充评审/分级差异；财务只记录现状与待变更 | 已有质量规则、签认、真实样本及页面可供对照，减少因财务大改导致的样板返工；其它场景逐批接入 |
| C 所有场景一次重编完整PRD/UI | 一次性覆盖最广；大量未签认口径和历史分支会进入同一整理批，审阅和冲突成本大 | 当前财务调整及引擎收口仍未闭合，不推荐作为近期主线 |

## 推荐方案的可审产物

拟定三个文档系列，命名、维护owner及落点在批准组织方案后定稿并登记文档台账；正式文档提供同名md/docx。以下是章节清单，不宣称正文已经完成或获批。

1. **项目PRD总纲**：目标与价值度量；部门/用户角色；场景目录及优先级；用户任务端到端流程；统一能力边界；数据来源/时效与OEM隔离；L1/L2及人工责任；通知/审计/归档；验收与发布条件；当前运行事实；未定项和版本记录。数值目标和业务阈值按来源继承，缺签认的只记录待定。
2. **统一UI Design**：门户信息结构与导航；场景工作台、列表、异常明细和来源凭据入口；人工复核/决定/理由；反馈、导出和历史；字体、间距、表格与数字/日期格式；状态文字和颜色同时表达；加载/空数据/源不可用/部分数据/过期数据/无权限/待人工确认；mock/真实、数据时间与版本清楚可见；键盘/窄屏及权限体验。只讨论帮助业务作决定的信息，不把runtime或内部脚本细节塞给专员。
3. **质量域PRD＋首批场景页面设计**：质量场景目录与角色分工；先以QD-B立项审核门禁完整描述提交资料、检查、问题定位、预审报告、人工复核、留痕及归档，再用Q2 8D评审补充七维评分、分级区间、语义待人工和判例对照。按每页输入输出/可执行动作/反馈建立需求到验收表；已有签认直接继承，尚未签认与未实现部分显式区分。财务变更入档后，沿同一模板整理财务详细PRD/UI。

每条需求拟用稳定ID，建立一张追溯表：`PRD ID → 原批准/回件 → 业务规则/字段 → 页面/交互 → OpenSpec requirement → 判例/验证证据 → 发布版本/验收人`。UI状态、AI结论、人工决定及上线状态分别标识，避免“显示绿色”代替业务签认。

## 质量样板的选择与复用边界

**推荐QD-B先、Q2后。** QD-B已有PRD、发布/灰度SOP、规则和黄金样本，现网8093在位，适合形成一个完整的业务操作样板；Q2已有V3.2规则、已签判例和验收集，适合验证同一文档/界面体系能否表达评分、语义待人工及复杂评审状态。历史`质量旗舰PRD-Q2-8D不良分析与根因.md`描述QD-A历史范围，不能仅凭文件名当作当前Q2判定PRD；QD-A抽取与Q2评审分开映射。

稳定性判断来自业务输入与签认，不来自服务在线。QD-B两份C05枚举表及档三阻断效力未闭；Q2档1页面是mock，真实语义、校准、签认与接线未闭。样板整理不能替代这些门禁或重新批准历史设计。

共用规范提取导航、数据来源/时效、上传反馈、列表与明细、异常提示、人工复核、审计和历史等跨场景结构。质量评分、红线和档位保留为质量专属业务表达，不能推广成财务/采购统一算法。UI文档以业务任务清楚、证据可见、责任可辨为目标；组件提取或页面改版另走实施计划。
