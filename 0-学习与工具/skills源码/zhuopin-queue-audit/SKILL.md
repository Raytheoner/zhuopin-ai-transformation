# 卓品 · 跨会话对账审计（zhuopin-queue-audit v1.4）

多条专线/CC 并行推进时，《跨桌任务队列》可能与实际脱节（漏回写、字样过时、任务已被替代）。本审计**以文件系统真身为准**（R6：只认文件不认转述）校准队列，是值周巡检的前置质量闸——**先对账、后巡检**，否则《本周计划》会催已完成/已删除的事。首例 2026-07-11 执行（发现 6 处失真，含 7/10 端点到期无回填的红线项）。**v1.1（2026-07-17）**：补类型⑥（协调文件跨分支漂移/行号撞号）+ 证据源⑦（git/worktree 取证）+ §三 新增行号唯一性卫生项——2026-07-17 曾发生长期分支 checkout 独立续编号导致 §一/§四撞号的事故，见 memory `project-queue-file-worktree-divergence-incident`。**2026-07-23（队列 §四#32 backlog 回补）**：§四 修正纪律补一句"写回前先 acquire 协议〇.7 编辑锁、改完 release"——2026-07-23 当天又发生同一时段两 session 各自在本地未提交工作副本里直接改队列文件、后写覆盖先写的撞号事故（同分支，非跨分支漂移，本工具 v1.1 的类型⑥查不出），故补此锁步骤。**v1.2（2026-07-24，队列 #68④）**：补证据源⑧（`工具-孤儿worktree扫描.py`，只读扫 ahead=0 孤儿 worktree/陈旧分支）+ §三 新增处置规则（候选各追加 §一 待领行交 CC，扫描本身不删任何东西）——落地《构建自动化workflow设计-2026-07-21.md》§五"值周巡检兜底"项。**v1.3（2026-07-30，队列 #97）**：四项机制化——① 新增**类型⑦ 行内遗留未升格**（藏在长行正文里的 ⚠️/待办从不会被任何人认领）；② 新增**证据源⑨ 接力文件「⏳ 队列更新待补」扫描**（补上"抢不到编辑锁→降级写接力文件"这条链上最后一个断点，协议〇.7）；③ §三 卫生新增**重复劳动检测**与**高水位线回写核对**；④ 新增 **§六 每周清扫尾步**（协议〇.8：迁归档 + 回写高水位线）与**消费方高水位线兜底**（凡按高水位线划范围的步骤一律取"文内真实最大号"与"顶部高水位线"的**较大者**——#146 的源头修复只堵住机器人追加路径，人工写手漏回写时无任何代码兜底，消费方兜底是唯一防线）。**v1.4（2026-07-31，队列 #184）**：取号口径随 #163 落地更新为 `acquire --reserve N --section 一|四` **预留取号**（原"取回显值 +1"降级为 `--reserve` 覆盖不到时的退路，见 §四 修正纪律与队列 #185）。

## 读取纪律（先背再动手）

沙箱挂载/staged 副本对高频改动文件有**桥缓存滞后与尾截断假象**；队列这类文件的读与写回验证一律走 **Windows-MCP PowerShell 直读真身**（`ReadAllBytes`/`Get-FileHash`，只读用 cmdlet 全名）。读回出现 U+FFFD 先跨通道交叉验证再下结论（见 memory `project-encoding-incidents`）。

## 一、证据采集（七源）

1. **队列真身**：`1-转型规划/0-全景路线图/跨桌任务队列.md`（PS 直读，记 LEN+MD5 作写回基线）。
2. **专员回复落档**：`7-外部文档/<部门>/` 近 7 天新件清单（device_list_dir recursive + mtime 过滤）——有新件必须对应看板行的输入或销行证据。
3. **跟进信发送状态**：`6-人才与组织/部门AI专员跟进/README` 清单 + 已删除记录——核对"发信"类任务行。
4. **四条 session 接力**：Phase1收口/财务域/采购域/质量域 最近日期节——各线自述完成的事是否已回写队列。
5. **在途变更包**：`openspec/changes/` 目录清单——"design 待审/apply 中"是否有对应看板行与 §四 Shao Peishen 行。
6. **§二批次 vs git**：批次行的 commit hash、✅ 状态与 CC 备注里"检出但未登记"的改动（后者=漏登记信号）。
7. **git/worktree 取证（2026-07-17 补）**：`git worktree list` + 各 worktree `git log origin/master..<branch> --oneline`——凡长期分支（checkout 超过一天）**且**当前 checkout 里的队列文件相对 `origin/master` 有 diff，视为潜在漂移源，需在本轮审计里专门核对该分支上的队列行号是否与 master 主线撞号（见类型⑥）。
8. **孤儿 worktree/陈旧分支扫描（2026-07-24 补，队列 #68④，值周巡检兜底项）**：`python 0-学习与工具/工具-孤儿worktree扫描.py`——只读扫描所有 git worktree + 本地分支的 ahead 计数（相对 `origin/master`）。ahead=0 且工作区干净＝孤儿候选（内容已全部并入 master，删除不丢任何东西）；ahead=0 但有未提交改动＝观察项，不直接建议删；ahead>0（仍有独有提交）一律不进候选清单。**本脚本自身只读，不做任何 `git worktree remove`/`git branch -d`**——发现的候选按下面"处置"追加队列待领行交 CC 执行，不在审计里直接删。

9. **四条 session 接力的「⏳ 队列更新待补」小节（2026-07-30 补，队列 #97④）**：grep `session接力-Phase1收口.md` / `session接力-采购域*.md` / `session接力-财务域*.md` / `session接力-质量域*.md` **顶部固定小节名「⏳ 队列更新待补」**（协议〇.7 约定的降级落点）。**为什么必须扫**：抢不到编辑锁时内容写进接力文件等回补，但此前**无任何机制去捡**——对账审计不扫接力文件、拆件巡逻只认队列"机器人归档"行、sweep 只看 §二 批次声明，能否被捡起全凭"下个 session 恰好读到那份接力文件"，而域专线读本域接力看不到总线接力，漏接是真实发生过的（#97 本项登记自身即一例）。**处置**：有内容即在简报 ② 位置（最要紧一条）列出并催回补；回补完成后由**回补方**删除该小节，空节视为已清（审计不代删——删了就无人知道曾漏过）。

## 二、逐行核对：七类失真

| 类型 | 判据 | 处置 |
|------|------|------|
| ① 已完成未销行 | 产出文件/接力节/commit 在，状态仍"待领/在办" | 补记销行（注明"XX 审计补记"+证据指针） |
| ② 状态字样过时 | 日期性措辞失效（"今日X到期"已过、被新事替代、引用已删文件） | 按现状重写该单元格，登记列加"（MM-DD 刷新）" |
| ③ 到期无证据 | 红线日已过而证据夹无产出 | **升级**：标 ⚠️ 已过期+触发预案条款（如 CSV 降级/窗口保卫战），§四 对应行改"立即" |
| ④ Shao Peishen 动作缺行 | 看板有"待 Shao Peishen 审/拍板"状态但 §四 无行 | §四 补行（会卡执行方的优先） |
| ⑤ 触碰区撞车 | 待领行触碰区与在办行重叠 | 加防撞注：建议并入在办行或改由同一执行方顺带 |
| ⑥ 协调文件跨分支漂移/行号撞号（2026-07-17 新增） | 某长期分支的队列文件副本相对 origin/master 有独立编辑历史（§一/§四出现同号不同内容）——2026-07-17 曾因 `feat/fi2-v3-recon-engine` 多日未同步又被顺手编辑而实际发生 | **不得**盲目"全取一边"：逐冲突查每行引用的 commit hash 是否真实存在于 master，判断哪边是过时值；改动一律在 master 真实最大号之后续排，不覆盖任何一方；修复提交 push 前用 `git merge-base --is-ancestor origin/master <sha>` 核验可快进，否则改走临时 worktree cherry-pick 路线（详见协议第 6 条） |
| ⑦ 行内遗留未升格（2026-07-30 新增，队列 #97①） | 某行**正文里**藏着 `⚠️`／"未做"／"待确认"／"下次顺带"等**新的待办**，但该行状态已是"✅ 完成"、或该待办从未变成独立的待领行——**没有任何人会去认领一段藏在长行正文里的话** | 抽出为**独立 §一 待领行**（编号用 `acquire --reserve N --section 一` 预留取号，见 §四 修正纪律），原行保留原文并加"（已升格为 #N）"指针；已归档行里的遗留同样升格（#92/#93/#94/#95 即由归档行 #54/#66/#31/#19 升格而来，是本类型的既有判例）。**扫法**：`grep -n '⚠️\|未做\|待确认\|留待\|下次顺带' 队列.md 归档件.md` 后逐条判断"是否已有对应独立行"。 |

## 三、卫生检查（顺带）

批次 ID 唯一（同日多批加域后缀）；§二表块完整；冻结标挂/解与实际一致；外来文件混入专员夹；看板行序仅记录不重排（改动最小化）；**§一/§四行号无重复**（同号不同内容是类型⑥的确凿信号，逐一 `grep -oP '^\| [0-9]+ \|'` 或等效核对一次）。

**高水位线回写核对（2026-07-30 补，队列 #97④／#146 下游）**：核对顶部"编号高水位线"是否 ≥ §一/§四 文内真实最大号。**滞后是常态不是异常**——源头修复只覆盖机器人自动追加路径，业务总线/域专线**手工加行时无任何强制回写机制，全靠记得**。发现滞后即当场回写，并在简报观察项里记一句（累计频次是判断"是否需要更强制手段"的依据）。**同时，本审计及任何按高水位线划定扫描范围的步骤，一律取「文内真实最大号」与「顶部高水位线」的较大者**——本审计本就全量扫描、天然免疫，但拆件巡逻 cron prompt 与每周清扫步骤必须显式遵守。

**重复劳动检测（2026-07-30 补，队列 #97）**：扫 `6-人才与组织/部门AI专员跟进/` —— **同收件人、同日、多封未发（状态非"✅ 已推送"）的草稿**即报。**判例**：2026-07-23 主工作区同时存在两份内容重叠的价格核实信（一份发唐燕萍、一份发姚祖怡），两个并行 session 互不知情各写一份，靠 CC 送审前多问一句 Shao Peishen 才没重复打扰专员（见队列 #79 行）。判据只看"收件人+日期+未发状态"，不做语义判重（宁可多报一条让人扫一眼，不可漏）。

**孤儿 worktree/陈旧分支（2026-07-24 补，队列 #68④）**：跑证据源⑧的扫描脚本，把"① 孤儿 worktree 候选"与"③ 孤儿分支候选"两类结果，各按一条 §一 待领行追加（领取方 CC，触碰区写清具体 worktree 路径/分支名 + 建议命令），"② 观察项"类不建单独任务、只在简报里提一句留痕。**巡检本身不执行任何 `git worktree remove`/`git branch -d`**（只读+生成任务，删除动作留给 CC session 认领后执行，遵《构建自动化workflow设计-2026-07-21.md》§五"巡检只读不删"）。追加这些新行同样要走下面§四的编辑锁纪律。

## 四、修正纪律

- **写回队列前先 acquire 协议〇.7 编辑锁**（`python 0-学习与工具/工具-共享文档编辑锁.py acquire --who "queue-audit"`），占用中等其释放/陈旧再改，**改完立刻 `release`**——本审计的写回窗口通常不长，不需要跨整个审计过程持锁。
- **要新增行时，acquire 一并带 `--reserve N --section 一|四` 预留取号（队列 #163／#184，2026-07-31 起）**：工具在持锁窗口内原子完成「读高水位线→分配→回写」并返回**字面编号**，不再自己做加法（#162 已证「回显正确、人仍会看错」）；预留多了无妨——**编号不复用，留空即可**。⚠️ 每次 acquire 只能指定一个 `--section`，同时要 §一/§四 两套号时另一套仍取回显高水位线 +1，并在简报里写明用的哪个回显值（队列 #185 待 CC 小改）。
- **证据确凿才改**；存疑标"待核实（XX 审计）"，不臆断销行。
- 写回走 PS `WriteAllText`（UTF8 无 BOM，与原文件一致）+ 写后验证（长度/探针/FFFD=False）。
- 全部改动登记 §二 新批次 `B-MMDD总线审计` 交 CC commit。
- 审计**不重开业务口径、不动权威文档**——只校准队列这一张调度表（分工红线）。

## 五、输出简报（聊天）

顺序固定：① 总体结论一句（机制是否在转）；② **最要紧一条置顶**（通常是类型③过期项，写明今天该做什么）；③ 修正清单（每处一句：原状→改后）；④ 观察项（卫生类，不阻塞）；⑤ Shao Peishen 动作优先级列表。简报不落文件（队列本身即记录），除非 Shao Peishen 要求。

## 六、每周清扫尾步（协议〇.8，2026-07-30 补·队列 #97①）

**只在值周巡检那一轮（周一）做，日常临时对账不做。** 顺序不可颠倒：

1. **先完成上面全部对账修正**（清扫前必须先把状态改对——否则会把"其实没完成"的行迁进归档件，等于永久失踪）。
2. 将 §一/§二/§三/§四 **全部已完成行整行迁入**同目录《跨桌任务队列-归档-YYYYMM.md》（按月一档，**编号永不复用**）。
3. **迁完立刻回写顶部"编号高水位线"** = 迁移前 §一/§四 各自的真实最大号（**不是迁移后文内可见的最大号**——归档后文内看不到历史最大号，这正是高水位线存在的理由）。
4. 迁移与回写**同处一个编辑锁窗口内**（acquire → 迁 → 回写 → release），不可分两次持锁：中间空档若有人加行，新行编号会基于半截状态计算。**注**：清扫本身不新增行，故通常不需 `--reserve`；若清扫顺带升格出待领行（类型⑦），则在同一次 acquire 上带 `--reserve`。
5. 清扫结果在简报观察项里记一句：迁走 N 行、高水位线 §一 #X／§四 #Y。

> 首次清扫 2026-07-24（队列瘦身 88%）。清扫的副作用已被下游消费方适配：企微机器人 `queue_appender._next_task_id` 取 `max(可见最大号, 高水位线)+1`、`queue_reconcile_sentinel` 同扫归档件（队列 #99，2026-07-27 修）。

## 与值周巡检的关系

对账审计=**校准队列**（对文件真身），值周巡检=**消费队列**（出《本周计划》）——上下游不重复。标准节奏：周一巡检开跑前先跑本审计；巡检 prompt 首句应为"先用 zhuopin-queue-audit 对账并修正队列，再基于修正后的队列生成本周计划"。
