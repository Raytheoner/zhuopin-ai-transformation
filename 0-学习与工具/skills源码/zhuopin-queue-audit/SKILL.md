## 读取纪律（先背再动手）

沙箱挂载/staged 副本对高频改动文件有**桥缓存滞后与尾截断假象**；队列这类文件的读与写回验证一律走 **Windows-MCP PowerShell 直读真身**（`ReadAllBytes`/`Get-FileHash`，只读用 cmdlet 全名）。读回出现 U+FFFD 先跨通道交叉验证再下结论（见 memory `project-encoding-incidents`）——**沙箱 bash 输出里的 U+FFFD 多为管道显示假象**，2026-08-01 实证：同一文件 bash `cat` 显示 3 处 U+FFFD、PowerShell 直读 `FFFD存在?False`，须以 PowerShell 直读为准，勿据 bash 输出判定文件损坏。

🔴 **写完必须反查落盘**（2026-07-31 两次实证）：`Write` 工具与 PowerShell 字符串 `-replace` 都可能**报成功而实际没写进去**；写回后一律用 `Select-String`／`Get-FileHash` 反查一次，不能信"工具说成功了"。

🔴 **时间戳必判 UTC vs Win 本地**（本机 UTC+8）：审计 JSONL 存真 UTC；文件 mtime／计划任务 `LastRunTime`／事件日志是本地。PowerShell `ConvertFrom-Json`／`[datetime]::Parse` 会把 ISO 串按本地时区显示——要真 UTC 须显式 `.ToUniversalTime()`。时长差值一律用 `TotalHours` 或 `d\.hh\:mm\:ss`，**绝不用只含 `hh` 的格式串**（会丢 Days）。判"任务/服务为何没跑"之前，先确认机器这段时间是否在运行（查 `ID=27／42／107`，并对比两次读时钟的真实间隔——**时钟本身就是证据**）。

## 一、证据采集（九源）

1. **队列真身**：`1-转型规划/0-全景路线图/跨桌任务队列.md`（PS 直读，记 LEN+MD5 作写回基线）。
2. **专员回复落档**：`7-外部文档/<部门>/` 近 7 天新件清单（recursive + mtime 过滤）——有新件必须对应看板行的输入或销行证据。
3. **跟进信发送状态**：`6-人才与组织/部门AI专员跟进/README` 清单 + 已删除记录——核对"发信"类任务行。
4. **四条 session 接力**：Phase1收口/财务域/采购域/质量域 最近日期节——各线自述完成的事是否已回写队列。
5. **在途变更包**：`openspec/changes/` 目录清单——"design 待审/apply 中"是否有对应看板行与 §四 Shao Peishen 行。
6. **§二批次 vs git**：批次行的 commit hash、✅ 状态与 CC 备注里"检出但未登记"的改动（后者=漏登记信号）。
7. **git/worktree 取证（2026-07-17 补）**：`git worktree list` + 各 worktree `git log origin/master..<branch> --oneline`——凡长期分支（checkout 超过一天）**且**当前 checkout 里的队列文件相对 `origin/master` 有 diff，视为潜在漂移源，需在本轮审计里专门核对该分支上的队列行号是否与 master 主线撞号（见类型⑥）。**⚠️ 注**：沙箱 git 对 Windows 路径 worktree 一律标 `prunable`，那是视图假象、**不可据此判断**（本机 PowerShell 直读为准）。
8. **孤儿 worktree/陈旧分支扫描（2026-07-24 补，队列 #68④，值周巡检兜底项）**：`python 0-学习与工具/工具-孤儿worktree扫描.py`——只读扫描所有 git worktree + 本地分支的 ahead 计数（相对 `origin/master`）。ahead=0 且工作区干净＝孤儿候选（内容已全部并入 master，删除不丢任何东西）；ahead=0 但有未提交改动＝观察项，不直接建议删；ahead>0（仍有独有提交）一律不进候选清单。**本脚本自身只读，不做任何 `git worktree remove`/`git branch -d`**——发现的候选按下面"处置"追加队列待领行交 CC 执行，不在审计里直接删。🔴 **CC 执行时勿用 `git worktree remove`**：该命令**非原子失败**，遇句柄锁会先清空目标目录再报错（2026-07-27 队列 #125 P0 事故，无法排除他人未提交工作丢失），一律改用 PowerShell `Remove-Item -Recurse -Force` + `git worktree prune`；删前先 `Get-CimInstance Win32_Process` 核查目录是否被在跑进程占用。

9. **四条 session 接力的「⏳ 队列更新待补」小节（2026-07-30 补，队列 #97④）**：grep `session接力-Phase1收口.md` / `session接力-采购域*.md` / `session接力-财务域*.md` / `session接力-质量域*.md` **顶部固定小节名「⏳ 队列更新待补」**（协议〇.7 约定的降级落点）。**为什么必须扫**：抢不到编辑锁时内容写进接力文件等回补，但此前**无任何机制去捡**——对账审计不扫接力文件、拆件巡逻只认队列"机器人归档"行、sweep 只看 §二 批次声明，能否被捡起全凭"下个 session 恰好读到那份接力文件"，而域专线读本域接力看不到总线接力，漏接是真实发生过的（#97 本项登记自身即一例）。**处置**：有内容即在简报 ② 位置（最要紧一条）列出并催回补；回补完成后由**回补方**删除该小节，空节视为已清（审计不代删——删了就无人知道曾漏过）。

## 二、逐行核对：七类失真

| 类型 | 判据 | 处置 |
|------|------|------|
| ① 已完成未销行 | 产出文件/接力节/commit 在，状态仍"待领/在办" | 补记销行（注明"XX 审计补记"+证据指针） |
| ② 状态字样过时 | 日期性措辞失效（"今日X到期"已过、被新事替代、引用已删文件） | 按现状重写该单元格，登记列加"（MM-DD 刷新）"。**⚠️ 只扫标题会误判**——须同时看正文（2026-07-30 §四#35 判例：标题写"红线 7/31"而正文已正确记为 8/31 顺延，只看标题会当成次日到期的红线项误报） |
| ③ 到期无证据 | 红线日已过而证据夹无产出 | **升级**：标 ⚠️ 已过期+触发预案条款（如 CSV 降级/窗口保卫战），§四 对应行改"立即" |
| ④ Shao Peishen 动作缺行 | 看板有"待 Shao Peishen 审/拍板"状态但 §四 无行 | §四 补行（会卡执行方的优先） |
| ⑤ 触碰区撞车 | 待领行触碰区与在办行重叠 | 加防撞注：建议并入在办行或改由同一执行方顺带 |
| ⑥ 协调文件跨分支漂移/行号撞号（2026-07-17 新增） | 某长期分支的队列文件副本相对 origin/master 有独立编辑历史（§一/§四出现同号不同内容）——2026-07-17 曾因 `feat/fi2-v3-recon-engine` 多日未同步又被顺手编辑而实际发生 | **不得**盲目"全取一边"：逐冲突查每行引用的 commit hash 是否真实存在于 master，判断哪边是过时值；改动一律在 master 真实最大号之后续排，不覆盖任何一方；修复提交 push 前用 `git merge-base --is-ancestor origin/master <sha>` 核验可快进，否则改走临时 worktree cherry-pick 路线（详见协议第 6 条） |
| ⑦ 行内遗留未升格（2026-07-30 新增，队列 #97①） | 某行**正文里**藏着 `⚠️`／"未做"／"待确认"／"下次顺带"等**新的待办**，但该行状态已是"✅ 完成"、或该待办从未变成独立的待领行——**没有任何人会去认领一段藏在长行正文里的话** | 抽出为**独立 §一 待领行**（编号用 `acquire --reserve N --section 一` 预留取号，见 §四 修正纪律），原行保留原文并加"（已升格为 #N）"指针；已归档行里的遗留同样升格（#92/#93/#94/#95 即由归档行 #54/#66/#31/#19 升格而来，是本类型的既有判例）。**扫法**：`grep -n '⚠️\|未做\|待确认\|留待\|下次顺带' 队列.md 归档件.md` 后逐条判断"是否已有对应独立行"。**⚠️ 特别注意"一行两半"形态**：某行 CC 侧已完成、行内却另写着"需 Cowork 补"（或反之），整行看似已完结、实则半边未做——2026-07-31 队列 #172 即此形态，**只按"这行归谁"读会漏掉**，须逐字读行内正文才发现。 |

## 三、卫生检查（顺带）

批次 ID 唯一（同日多批加域后缀）；§二表块完整；冻结标挂/解与实际一致；外来文件混入专员夹；看板行序仅记录不重排（改动最小化）；**§一/§四行号无重复**（同号不同内容是类型⑥的确凿信号，逐一 `grep -oP '^\| [0-9]+ \|'` 或等效核对一次）。

**高水位线回写核对（2026-07-30 补，队列 #97④／#146 下游）**：核对顶部"编号高水位线"是否 ≥ §一/§四 文内真实最大号。**滞后是常态不是异常**——源头修复只覆盖机器人自动追加路径，业务总线/域专线**手工加行时无任何强制回写机制，全靠记得**。发现滞后即当场回写，并在简报观察项里记一句（累计频次是判断"是否需要更强制手段"的依据）。**同时，本审计及任何按高水位线划定扫描范围的步骤，一律取「文内真实最大号」与「顶部高水位线」的较大者**——本审计本就全量扫描、天然免疫，但拆件巡逻 cron prompt 与每周清扫步骤必须显式遵守。

**重复劳动检测（2026-07-30 补，队列 #97）**：扫 `6-人才与组织/部门AI专员跟进/` —— **同收件人、同日、多封未发（状态非"✅ 已推送"）的草稿**即报。**判例**：2026-07-23 主工作区同时存在两份内容重叠的价格核实信（一份发唐燕萍、一份发姚祖怡），两个并行 session 互不知情各写一份，靠 CC 送审前多问一句 Shao Peishen 才没重复打扰专员（见队列 #79 行）。判据只看"收件人+日期+未发状态"，不做语义判重（宁可多报一条让人扫一眼，不可漏）。**同族形态（2026-07-31 补）**：同一条 Shao Peishen 拍板被两条线同时接（§四#41 判例）——落字前先读一眼行内真身，看是否已被并行 session 落档。

**孤儿 worktree/陈旧分支（2026-07-24 补，队列 #68④）**：跑证据源⑧的扫描脚本，把"① 孤儿 worktree 候选"与"③ 孤儿分支候选"两类结果，各按一条 §一 待领行追加（领取方 CC，触碰区写清具体 worktree 路径/分支名 + 建议命令），"② 观察项"类不建单独任务、只在简报里提一句留痕。**巡检本身不执行任何 `git worktree remove`/`git branch -d`**（只读+生成任务，删除动作留给 CC session 认领后执行，遵《构建自动化workflow设计-2026-07-21.md》§五"巡检只读不删"）。追加这些新行同样要走下面§四的编辑锁纪律。

## 四、修正纪律

- **写回队列前先 acquire 协议〇.7 编辑锁**（`python 0-学习与工具/工具-共享文档编辑锁.py acquire --who "queue-audit"`），占用中等其释放/陈旧再改，**改完立刻 `release`**——本审计的写回窗口通常不长，不需要跨整个审计过程持锁。
- **要新增行时，acquire 一并带 `--reserve N --section 一|四` 预留取号（队列 #163／#184，2026-07-31 起）**：工具在持锁窗口内原子完成「读高水位线→分配→回写」并返回**字面编号**，不再自己做加法（#162 已证「回显正确、人仍会看错」）；预留多了无妨——**编号不复用，留空即可**。**队列 #185（2026-08-04 已落地）**：现可用 `--reserve-multi 一:N 四:M` 一次性跨两个分区预留（如 `--reserve-multi 一:2 四:1`），不再需要"另一套取回显值 +1"的退路；与 `--reserve`/`--section` 单分区用法互斥（选一种方式），单分区既有调用零破坏。**⚠️ 已安装版仍需回补**：本次只改了本源码文件，`save_skill --overwrite` 同步安装版留给下一次维护本 skill 的 session（同本文件 v1.4 加固回写段的既有惯例，改完源码即覆盖安装、不得只改一边）。
- **证据确凿才改**；存疑标"待核实（XX 审计）"，不臆断销行。
- 写回走 PS `WriteAllText`（UTF8 无 BOM，与原文件一致）+ 写后验证（长度/探针/FFFD=False/**列数=8**）。**⚠️ 勿用 PowerShell 字符串 `-replace`／`.Replace()` 改 md**——2026-07-31 当日三次静默失败（脚本打印成功、`Select-String` 反查 0 处），一律改用 Edit 工具并反查。
- 全部改动登记 §二 新批次 `B-MMDD总线审计` 交 CC commit；**状态列禁带 "✅"**（sweep 用 `"✅" not in status` 判待处理，带 ✅ 会被永久跳过）；**批次文件清单必须含队列文件自身**（否则 sweep 判"脏文件未被任何批次声明"整轮跳过）；**登记后立即触发一次 sweep**（协议〇.8 批次即扫，不把批次留在数小时敞口里）。
- 审计**不重开业务口径、不动权威文档**——只校准队列这一张调度表（分工红线）。

顺序固定：① 总体结论一句（机制是否在转）；② **最要紧一条置顶**（通常是类型③过期项，写明今天该做什么）；③ 修正清单（每处一句：原状→改后）；④ 观察项（卫生类，不阻塞）；⑤ Shao Peishen 动作优先级列表。简报不落文件（队列本身即记录），除非 Shao Peishen 要求。

## 六、每周清扫尾步（协议〇.8，2026-07-30 补·队列 #97①）

**只在值周巡检那一轮（周一）做，日常临时对账不做。** 顺序不可颠倒：

1. **先完成上面全部对账修正**（清扫前必须先把状态改对——否则会把"其实没完成"的行迁进归档件，等于永久失踪）。
2. 将 §一/§二/§三/§四 **全部已完成行整行迁入**同目录《跨桌任务队列-归档-YYYYMM.md》（按月一档，**编号永不复用**）。
3. **迁完立刻回写顶部"编号高水位线"** = 迁移前 §一/§四 各自的真实最大号（**不是迁移后文内可见的最大号**——归档后文内看不到历史最大号，这正是高水位线存在的理由）。
4. 迁移与回写**同处一个编辑锁窗口内**（acquire → 迁 → 回写 → release），不可分两次持锁：中间空档若有人加行，新行编号会基于半截状态计算。**注**：清扫本身不新增行，故通常不需 `--reserve`；若清扫顺带升格出待领行（类型⑦），则在同一次 acquire 上带 `--reserve`。
5. 清扫结果在简报观察项里记一句：迁走 N 行、高水位线 §一 #X／§四 #Y。
