# 卓品 · 跟进信一句话发送器（v1.0，2026-08-22 立）

> **它解决什么**：`push_followup_letter.py` 的调用要拼 5 个参数、3 条长路径，此前只能让 Shao Peishen 自己开终端或转 CC。**但 Cowork 有本机 PowerShell 通道（Windows-MCP），跑的就是他那台机器**——脚本、Python、企微凭据、网络全在，`stdout` 我直接就能读到。**⇒ 零新增代码，一句话即可发送并自我登记。**
>
> **它与 `zhuopin-followup-letter` 的分工**：那个管**写**（起草→docx→README 登记 `⏳ 待你审`），本 skill 管**发**（批准→推送→核验→登记）。两者不合并：触发语不同、护栏不同，合并会让本已很长的起草 skill 更难读。

---

## 🔴 §0 一条铁律：绝不凭一句话直发

**必须先读回、等他回一个「发」，才调发送脚本。**

**成因（本 skill 的诞生场景，2026-08-22）**：他提出这个需求时，用的示范句是「**发出给姚祖怡的#14号信**」——**而 #14 是给唐燕萍的**。姚祖怡是采购域专员，他名下最近一封是 `采购部#17`。

🔑 **这不是口误值不值得较真的问题，而是这个机制的设计依据**：如果做成纯直通，那句话会把一封谈 FI3 审批流、暂估价、发票导出的**财务信发给采购部的人**。**发信不可撤回**，而人名与编号在口语里最容易错配。

**⇒ 多一次往返换一次不可逆错误的拦截，这笔账永远划算。**

## §1 认信：编号与收信人必须**同时**匹配

从他的话里取两样：**部门编号**（`财务部#14`）与**收信人**（`唐燕萍`）。到 `6-人才与组织/部门AI专员跟进/README-跟进机制与命名约定.md` 定位行。

| 情形 | 动作 |
|---|---|
| 编号与收信人**都对得上同一行** | ✅ 进 §2 |
| 只给了编号 | 按编号定位，读回时**把收信人念出来**让他核 |
| 只给了收信人 | 取该收信人最近一封非闭环行，读回时**把编号念出来** |
| 🔴 **两者指向不同行** | **停手**，明说「#N 是给 A 的，不是 B」，请他确认要发哪一封。**不得自行选一个** |

⚠️ **收信人列写法是「财务部 · 唐燕萍（可分担李姣龙）」**，匹配时取姓名部分，别被括注干扰。

## §2 状态前置：只有 `🆕 待发` 能发

读该行「发送状态」列：

| 状态 | 能否发 |
|---|---|
| `🆕 待发` | ✅ 可发 |
| `⏳ 待你审` | 🔴 **不能发**——须先经 `approve_followup_letter.py` 批准（`--quote` 填他的放行原话，**10 分钟冷却窗口**，首跑必被拒、记录时刻，满窗后重跑才放行）。**告诉他要等这 10 分钟，别让他以为卡住了** |
| `✅ 已推送 …` | 🔴 **已经发过了，停手**并如实告知——重发会让专员收到两遍 |
| `⏸ 暂缓` | 🔴 不发，问他是否解除 |
| `📥 已回件并回灌` | 已闭环，停手 |

## §3 读回（复制这个格式）

> **收信人**：<README 收信人列原文>｜**编号**：<部门#N>｜**状态**：`🆕 待发`
> **标题**：<md 里的 H1>
> **首段**：<正文第一段，一句>
> **要她/他办的事**：<信里三要素表的「做什么」逐条>

后接一句：**「回『发』我就发，回『改』告诉我改哪。」**

## §4 发送：走本机 PowerShell，**不要走沙箱 bash**

🔴 **沙箱 bash 出不了网**（实测 `qyapi.weixin.qq.com` 403，这正是「发企微交 CC」那条老规矩的由来）。**本机 PowerShell 通道没有这个限制**——2026-08-22 财务部#14 即由此发出，WebSocket `wss://openws.work.weixin.qq.com` 直连成功，**off-LAN 亦可**（走公网，不依赖 `192.168.100.51` 网段）。

用 `mcp__Windows-MCP__PowerShell` 执行（`timeout` 给到 180）：

```
cd "C:\Users\Paul Shao\OneDrive\Projects\企业AI转型"
$b="6-人才与组织\部门AI专员跟进"
python "5-平台底座\wecom-aibot-service\scripts\push_followup_letter.py" `
  --readme "$b\README-跟进机制与命名约定.md" `
  --md   "$b\<信件文件名>.md" `
  --docx "$b\<信件文件名>.docx" `
  --chatid <收信人chatid> `
  --match-topic "<README 主要事项列的唯一定位关键字>" `
  --department <部门>
```

**四个参数的取法**：

- **`--md` / `--docx`**：README 该行「主要事项」列末尾的 `→ 目标文件：...` 已写明文件名；**没写就别猜**，按 R4 命名律 `<部门>-<姓名>-跟进-<日期>-*.md` 去 glob，**多于一个匹配即停手问他**（同 `_resolve_letter_files` 的判据，#241）。
- **`--chatid`**：🔴 **从 README 历史行的「✅ 已推送」记录里取该收信人用过的 chatid，不得从姓名拼音推断**。已知：**唐燕萍 ＝ `tangyanping`**。其余专员用到时先查历史行，查不到就问他一次。
- **`--match-topic`**：「主要事项」列里的一个**唯一**定位关键字。**用前先 `grep -c` 确认全库命中数 ＝ 1**，命中 0 或 ≥2 都会让脚本定位失败或改错行。
- **`--department`**：🔴 **一律带上**（见 §5）。

## §5 部门群抄送 ＝ 惯例，默认带 `--department`

**Shao Peishen 2026-08-22 拍板：「把抄送相关群也做成惯例」。**

⇒ **每封跟进信默认带 `--department <部门>`**，把同一份内容经机器人 chatid 通道抄送该部门群。不带只在他明说「这封别抄群」时。

⚠️ **这条通道是 fail-closed 静默跳过**：部门→群 chatid 映射未配置或为空时，脚本**不报错、不打印失败**，只记一条审计就过去了。**⇒ 「命令跑通了」不等于「群抄送发生了」，必须按 §6 到审计里看见 `followup_group_cc_delivered` 才算数。** 这正是本项目那条老教训的又一形态：**只读命令返回「太正常」的结果时，先问它是不是根本没做那件事。**

📌 另有一条**自动**抄送：脚本会把同一份内容抄给 `ShaoPeiShen`（审计 action `followup_cc_delivered`），**不需要传参数**，别重复配置。

## §6 核验：不许只信 stdout

stdout 打印 `[OK] 推送成功` 只覆盖主收信人那一路。**读审计文件看全四条**：

```
$p="C:\Users\Paul Shao\OneDrive\Projects\企业AI转型\5-平台底座\wecom-aibot-service\reports\wecom_aibot_audit.jsonl"
Get-Content $p -Tail 10 | ForEach-Object { ($_|ConvertFrom-Json).action }
```

**四条 action 齐了才算成功**（每条的 `acks` 里应是 `errcode=0`）：

| action | 含义 | 缺了意味着 |
|---|---|---|
| `followup_delivered` | 私信 ＋ docx 附件已送达 | 主链路失败 |
| `followup_cc_delivered` | 已自动抄送 ShaoPeiShen | 抄送链路异常 |
| `followup_group_cc_delivered` | **部门群抄送已送达** | 🔴 **群映射缺失被静默跳过**（§5），须如实报，不得当成功 |
| `followup_backfilled` | README 状态回填 `✅ 已推送 <UTC>` | 🔴 **信已到人手上但台账还是 `🆕 待发`** ⇒ 周一 `ZhuopinFollowupDispatchDaily` 会**再发一遍**，必须当场手工回填并告警 |

⚠️ **`reports/` 有两份同名审计文件**（主工作区一份、worktree `wecom-service-home` 一份）。**读主工作区那份**：`5-平台底座/wecom-aibot-service/reports/`；仓库根下没有 `reports/`，别在那儿找。

## §7 登记：多数情况**不需要**再登 §二

脚本自带一条 `followup_backfill_committed` —— **它会把 README 的状态回填自行 commit**（message 形如 `bot(跟进信): 回填「财务部#14…」发送状态`）。

**⇒ 只发信、没改别的文件时**：跑一次 `git status --porcelain` ＋ `git rev-list --count origin/master..master` 确认干净且 `ahead=0`，**不必登 §二、不必跑 sweep**。

**⇒ 若本次还改了别的文件**（补件、队列回写等）：照常按协议〇 登 §二 批次 → `Start-ScheduledTask -TaskName "ZhuopinCommitSweep"`。

🔴 **`git status` 要看 Windows 侧那一份**。沙箱 bash 的 `git status` 会因跨文件系统的 stat/换行差异**虚报几十个文件被改**（2026-08-22 实测），**照它判断会以为出了大事**。

## §8 三个会绊倒你的既有机制事实

**⑴ 批准之后那一行就冻住了。** `release` 的行身份判据 ＝ **除状态列外的全部单元格**，所以「已批准（`🆕 待发`）＋ 改任一其它列」会被判成「新增行直接写终态」而拒绝 release。**这道守卫是对的**（防止批准后偷换信的主题与交期，让批准依据名不副实）。**要改就走：状态先降回 `⏳ 待你审` → 改 → release → 重新跑批准脚本**（会重新计 10 分钟冷却）。**禁止手工把 `⏳` 改成 `🆕`。**

**⑵ 「交期要点」列不得出现任何字面日期，除非它真是收信人的交期。** 派发侧 `has_unmarked_imminent_deadline` 对该列做 **3 天窗口**扫描（按绝对值、含已过期），命中且未标 `🔒人工发送` 即**跳过该行、只发一条告警**。2026-08-22 财务部#14 就因为把我方内部时点 `2026-08-25` 写进这一列，**周一会被静默跳过**——发现时已批准，只能走 ⑴ 那条降级重批的路。**⇒ 我方内部时点一律留在队列行。**

**⑶ 每日派发任务跑在 worktree `wecom-service-home` 里，该 worktree 落后 master 一两百个提交，其 README 副本里有一堆陈旧的 `🆕 待发`。** 但 **不会误发**：启动包装 `run-followup-dispatch-check.ps1` 把 `WECOM_AIBOT_QUEUE_PATH` 硬钉到主工作区，`resolve_repo_root` 因此锚到 master 真身（注释里写明就是为防这件事，引队列 #126）。**知道这一点，免得每次看到那 13 行就重新惊一次。**

## 禁止

- ❌ **不读回就发**（§0 —— 本 skill 存在的全部理由）
- ❌ 编号与收信人对不上时自行选一个
- ❌ 发 `⏳ 待你审` 的信（须先经批准脚本，含 10 分钟冷却）
- ❌ 重发 `✅ 已推送` 的信
- ❌ 走沙箱 bash 发送（出网 403）
- ❌ 省略 `--department`（群抄送已是惯例）
- ❌ **只看 stdout 就报「发送成功」**——群抄送是静默跳过的，必须看审计
- ❌ `followup_backfilled` 缺失却不处理（会导致周一重发一遍）
- ❌ 从姓名拼音推断 chatid
- ❌ 用沙箱 `git status` 判断工作区是否干净
