# SC11 首期意图：固定周计划的 mock 调拨拟稿对照

## 一、M2 已自查的事实

1. `demands_from_plans` 输入 BOM、生产计划、计划→上线仓映射，缺映射抛 `KeyError`。需求含物料、目标仓、数量、上线日与成品；`run_draft` 接收需求、分仓库存、仓库、距离、显式原则顺序与可归责人，不直接接收 BOM/计划。
2. 现有拟稿含 lines、unmet、priority_assumption、approved_by/at。每条需求独立枚举非目标且单仓足量候选，再取排序首项；不拆分、不跨需求扣减共享库存。源仓6件、两条需求各4件，当前实现可能各自产生4件拟稿，合计8件超出6件：这是静态推论，未测试重现。
3. 四原则当前代码分别使用 hops、物料仓/委外仓标记、needed_by、调用者距离。四项顺序必须齐全且显式提供；数值和顺序是 mock 假设。某评分缺值时返回 None 并排在有值后，全部候选缺值时可能按输入顺序选首项，没有“全部缺数即停止”的现成规则。单需求的 needed_by 在其各候选间相同，不能据此宣称全局共用料分配已实现。
4. `approve()` 记录实名和 UTC；draft及行项可变，确认尚未绑定内容 hash/版本。执行侧以 approved_by 是否非空判断；未确认拒绝，已确认也因通道未接抛 NotWiredYet。现有拟稿 audit 为摘要、假设和阻塞前置；没有在 SC11 模块观察到确认动作的独立审计事件，audit 参数可选。
5. 当前共享 BOM/计划及 SC11 输入输出没有周计划快照版本链路。mock 的文档 ID 不能被当作已有运行追溯能力。真实计划、三委外仓库存、签认原则及物流矩阵前置分别约束对应能力；真实 ERP/邮件通道尚未接。
6. 存量包 `sc11-inventory-transfer` 有 proposal/tasks/spec，缺 design；历史22 tests/13 of 34 tasks 不是本轮结果。EE-5=(a) 已裁定补物流矩阵/口径前置与原则知识资产条目，实际落行、类型与实名角色待闭合。M2 由既有显式 gpt-6-luna 子代理只读完成，未运行产品测试。

### 本次完整意图待确认的交付与验收

**目的及使用者**：让 PMC 业务人员能逐条核对固定周计划下的调拨需求、候选来源、缺数/冲突及拟稿边界，在接真实库存和专业原则前确认哪些技术事实可复用、哪些需要修正。业务核对及最终 L2 责任仍属 PMC；实名及 backup 经正式流程点名。

**输入**：文档对照包 `SC11-MOCK-W01/r1`，一个固定模拟周窗口、1物料仓＋3委外仓、BOM/计划/目标仓映射/分仓库存/距离假设/全四原则假设顺序。窗口起止、各份资料版本、库存时点与 hash 分开记录；fixture 不含的版本元数据由准备目录显式标注。mock 距离单位与原则顺序仅用于反例对照，不能升级为签认口径。

**产出**：计划到需求追溯表、逐需求候选与不足原因、拟稿 lines/unmet、各原则输入与缺值、假设顺序、同物料同仓合计占用核对、人工参考及差异、输入/拟稿版本关联状态。正式运行产物还须能追到具体输入、假设和确认内容；版本绑定、分配算法、审计补足交后续 design 审，不在本件声称已支持。

**人工对照验收线**：需求量、目标仓、日期、候选足量与 unmet 逐格对照；模拟库存合计不能被重复当作可执行数量。“源仓6件→两需求4＋4”应明确暴露重复占用差异，不能拿逐条候选满足替代整张拟稿可执行判断。谁优先获得库存、能否分拆或替代仍待专业签认。缺距/缺日期/全部缺数场景须完整列出缺项及当前排序行为，不能用列表顺序冒充业务择优；如何决定停止或保留供人工处理属于 SC11-G-06。确认后修改内容必须作为版本关联的验收前沿，最终机制经 design 审；当前没有修复或实测通过。

**门禁对照**：新拟稿未确认；无确认、空白确认人、已确认而通道未接及确认后修改分别列观察项。首期拟稿对照采用 mock，ERP落库/邮件外发不属其交付。每次正式拟稿审计须留可归责人、输入与假设版本和差异；现有可选审计/摘要不足的修正范围由 design 明确。

**路线与价值**：完整 intent 明确确认 → 在原包补 design 与真实前置拆分 → design 审 → 实施计划审阅 → Guardian 隔离建造。月中插单、真实分仓库存、执行通道各按前置扩展；人工耗时/差错率基线待采集，不把历史预期当实测收益。首期不晋档或宣称场景上线；当前不改变原 tasks/主 spec。
