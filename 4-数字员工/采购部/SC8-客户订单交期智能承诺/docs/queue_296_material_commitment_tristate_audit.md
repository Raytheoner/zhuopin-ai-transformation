## 一、三态判据的真实字段映射（根因坐实，非推断）

真实穷举当前窗口内 763 条 record／1302 条 `itemList` 条目的全部字段（record/item/
poLine 三层 union），确认 SRM 供应计划看板原始响应**没有**独立的"单据状态"字段
（无 `diffStatus`/`confirmStatus`/`documentStatus` 一类字段）。姚祖怡描述的三态——
「待答交」／「差异已确认」／「无差异」——只能由 `answerQty`（供应商回复数量）与
`planQty`（我方计划数量）两个数字字段的关系派生：

| 她的判据 | 字段条件 | 展示要求 |
|---|---|---|
| 待答交 | `answerQty is None` | 答交数量/日期显示"无" |
| 差异已确认 | `answerQty is not None` 且 `!= planQty`（含 `0`） | 显示实际数字 |
| 无差异 | `answerQty is not None` 且 `== planQty` | 显示实际数字 |

真实统计（365 天窗口）：`answerQty is None` 的 item 共 **223** 个（真·待答交）；
`answerQty == 0` 的 item 共 **669** 个（已答交、答复为 0——此前被误判为"无"的那一类）。

## 二、两处代码修正（均由真实数据驱动坐实，非凭假设改码）

### 2.1 `sources._extract_board_commitments`——源头 None/0 混淆

现状 bug：`int(item.get("answerQty") or 0); if answer_qty <= 0: continue` 把
`None`（待答交）与 `0`（已答交=0）一并跳过。修复：只在 `answerQty is None` 时跳过，
`0` 作为合法记录保留。

### 2.2 `baoguan._component_supply_status`——状态列改挂同一数据源

现状 bug：状态列"已答交/未答交"（`confirmed`）来自 `mat.no_feedback_materials`
（旧 `/purchase/answer`+看板最早日期 60 天窗口口径），与驱动答交数量/日期展示的
`material_commitments`（`receiveType==2` 口径）是两条独立管线，会产生"答交数量/
日期显示无、状态却显示已答交"的自相矛盾（真实案例 `R02A.0019`）。修复：`confirmed`
改由 `material_commitments.get(m)` 是否非空派生，与⑦⑧同源；仅当 `material_commitments`
整体加载失败（`None`）时才退回旧口径兜底。

### 2.3 🔴 真实端到端验证过程中发现并修复的第二处同族缺陷

**这是"整体复核一遍"的直接价值所在**——修完 2.1/2.2 后，第一轮真实全量快照复现
`R01D.0015`：状态列正确显示"已答交"（2.2 生效），但答交数量却仍显示"无"（`cb=[]`），
**同一矛盾在下游重新出现**。根因定位：`_cumulative_confirmed_batches`（累计答交数量
展示函数）自身也有一行 `if q <= 0: continue`——2.1 已让上游正确保留 `answerQty=0`
的记录，但这个下游函数又把它们过滤掉了。这行代码写于 2.1 修复之前，当时上游从不
会产生 `q<=0` 的记录，这行是从未被真正触发过的死代码；2.1 让它第一次变成活跳的
真实缺陷。**修复**：`_cumulative_confirmed_batches` 改为只过滤负数（真实数据从未
出现，纯防御性保留），`q==0` 的记录正常纳入累计展示。

修复前后对照（`R01D.0015`，真实数据，两次全量快照前后对比）：

| | 修复前（第一轮真实快照） | 修复后（第二轮真实快照） |
|---|---|---|
| status | `transit_confirmed`（正确） | `transit_confirmed`（正确） |
| 答交数量/日期（`cb`） | `[]` → 前端显示"无"（**错误**，与"已答交"状态矛盾） | `[{"d":"2026-08-20","q":0.0},{"d":"2026-09-20","q":0.0}]` → 前端显示"0、0" |
