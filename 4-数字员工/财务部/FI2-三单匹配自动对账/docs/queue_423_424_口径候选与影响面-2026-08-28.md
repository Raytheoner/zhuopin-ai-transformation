### 2.4 🔴 轴 A：放宽容差能捞回多少 —— **答案是「很少」**

| 容差档 | 捞回行数 | 捞回发票 |
|---|---|---|
| 数量 ±1e-6　单价 ±1e-4 **（现状）** | 0 | 0 |
| 数量 ±1e-4　单价 ±1e-3 | 38 | 22 |
| 数量 ±1e-3　单价 ±1e-2 | 46 | 24 |
| 数量 ±1e-2　单价 ±1e-2 | 61 | 33 |
| 数量 ±5%　　单价 ±5% | **122** | **63** |

⇒ **即使把数量容差放宽到 ±5%（比现值大 4~5 个数量级，已远超任何「浮点噪声」的解释，
且 ±5% 的数量差在账上本身就该报出来而不是被容忍），也只捞回 1,813 行里的 122 行（6.7%）。**
🔑 **「先把容差调大一点看看」这条最省事的路，可以当场排除** —— 挡住这批行的不是精度，
是**计量单位换算**和**发票按合计开票**两件事，它们与容差无关。

### 2.5 轴 B：换匹配键能捞回多少

| 候选 | 捞回行数 | 捞回发票 | **让多少「今天零行」的 AP 单重新有发票**（分母 221） |
|---|---|---|---|
| `qty_price`（现状，对照组） | 0 | 0 | 0 |
| **⒜** `qty_price_then_amount` | 168 | 141 | **114 / 221** |
| **⒝** `qty_price_then_single_item` | 266 | 181 | **175 / 221** |
| **⒞** `qty_price_then_subset_sum` | 346 | 164 | **53 / 221** |
| **⒜＋⒝＋⒞ 依次回落（三者任一能解）** | **645** | **336** | **206 / 221** |

**被挡掉那 1,813 行的形态分布**（按 ⒜→⒝→⒞ 优先级切成互斥五档，合计 1,813）：

| 形态 | 行数 |
|---|---|
| 四种候选口径全都解不开 | **663** |
| 组合求和跨多料号（**须先接受「发票行拆分」才解得开**） | **505** |
| 组合求和唯一可解（同料号多行合计开票） | 316 |
| 金额唯一可解（计量单位/包装换算形态） | 177 |
| AP 单只有一个料号（可由单料号回落解开） | 152 |

⇒ **三者依次回落可覆盖 645/1,813 行（36%），并让 206/221 张「今天报无发票支撑」的 AP 单重新有发票。**
另有 505 行要先答「一张发票行能不能拆成多行写进 `invoice.csv`」，663 行四种候选全都解不开。

🔴 **⒝（单料号回落）单看最有效（175/221），而它恰好也是最容易被误会成「最松」的一个** ——
值得把道理讲清楚：**这张发票已经通过「数电发票号码 → AP 单」反查唯一确定了它属于哪张单**，
而这张单**通篇只有一个料号** ⇒ 它只可能挂在那一个料号上，**这一步不含任何猜测**。
它「松」在**不再要求数量与金额对得上**。但那正是要点：

> 🔑 **摄取层的职责是「认领」——这张发票属于哪张单、哪个料品；
> 「合不合得上」是判定引擎的职责。** 现在这道闸把两件事混成一件：
> 数量对不上的发票**不是被报出来，而是被丢掉**，于是它以「无发票支撑（发票还没到）」的
> 面目出现在面板上 —— **对账系统正好在它该失明的反面失明了。**
> ⒝ 的效果是把这批发票交还给引擎去判，**它们多半会落进「数量金额不符」那一档 —— 那才是
> 唐燕萍该看到的东西。**

⚠️ **但这仍然是她的口径决定，不是我方能定的**：接受 ⒝ 就等于接受「面板上『数量金额不符』
那一档会明显变长」，而那一档是要人去查的。**变长多少、她的团队接不接得住，只有她能判。**
