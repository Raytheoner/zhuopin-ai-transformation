## 核心理念

数字员工（AI Agent / Digital Employee）的管理，应该像管理真实员工一样有完整的生命周期。每新增一个数字员工，都应该经过从"岗位定义"到"知识归档"的标准流程。

```
规划与设计 → 开发与入职 → 运营与监控 → 评估与改进 → 退役与归档
   │              │              │              │              │
   需求分析       Skill 开发     日常运行       绩效评价       下线评估
   可行性评估     权限配置       异常处理       迭代优化       知识转移
   ROI 预测       知识注入       成本追踪       用户反馈       资产归档
                  验收测试
```

## 第一阶段：规划与设计（Phase 1: Plan & Design）

### 1.1 数字员工岗位定义卡

每个数字员工在立项前，填写一张"岗位定义卡"：

```yaml
---
# ═══════════════════════════════════════
# 数字员工岗位定义卡（模板）
# ═══════════════════════════════════════

# --- 基本信息 ---
岗位名称:              # 如 "供应商风险评估助手"
所属部门:              # 供应链部 / 财务部 / 销售部
直接负责人:            # 业务方对接人
AI 运营责任人:         # AIOps 团队负责人
立项日期:              # YYYY-MM-DD
目标上线日期:          # YYYY-MM-DD

# --- 业务背景 ---
核心痛点:              # 当前流程中什么问题最痛？
                       # 如 "人工评估供应商风险耗时 2 天/家"
                       # 如 "月末对账人工排查异常交易耗时 3 人天"
期望效果:              # 用数字描述
                       # 如 "评估时间缩短 80%"
                       # 如 "异常交易检出率从 60% 提升到 90%"

# --- 职责范围 ---
核心任务清单:           # 这个数字员工具体做什么？
  - 任务 1:            # 如 "读取供应商财务报告，输出风险评分"
  - 任务 2:            # 如 "标记评分低于阈值的供应商并触发预警"
  - 任务 3:            # 如 "生成周度供应商健康度看板"

明确不做的边界:         # 什么情况下必须转人工？
  - 边界 1:            # 如 "涉及价格谈判策略"
  - 边界 2:            # 如 "最终签约审批"
  - 边界 3:            # 如 "供应商资质认证首次审核"

# --- 输入输出 ---
输入数据源:             # 如 ERP 供应商主数据、外部征信 API、历史交付记录
输出形式:               # 结构化 JSON / 自然语言报告 / Excel / 看板
输出接收方:             # 人（采购经理） / 系统（ERP） / 其他 Agent

# --- 自动化等级（参考 L1-L4）---
自动化等级:             # L1=AI建议人决策 / L2=AI执行人确认
                       # L3=AI执行异常转人 / L4=全自动
人工介入节点:           # 如 "首次供应商评分需人工确认阈值"
```

### 1.2 可行性评估清单

在投入开发前，评估数字员工的可行性：

- [ ] **业务价值明确**：该任务是否高频、耗时、规则可标准化？
  - ✅ 好候选：每周供应商评分、每日库存预警
  - ❌ 差候选：一年 2 次的战略谈判、高度依赖人际关系的商务决策
- [ ] **数据可及**：所需的数据源是否已有 API 或可导出？
- [ ] **评估标准清晰**：能否定义"做对了"和"做错了"的判断标准？
- [ ] **失败成本可控**：数字员工出错的最坏后果是否在可接受范围内？
- [ ] **法律/合规无障碍**：该任务是否允许 AI 辅助或自动执行？

### 1.4 部门试点优先级矩阵

将各部门候选场景按 **价值高低** 和 **落地难度** 排列，优先推进"高价值 + 低难度"的场景：

```
                    │
   高价值 ▲         │  【优先试点】          【战略投入】
          │         │  供应链：供应商评分    供应链：需求预测
          │         │  财务：异常交易检测    销售：客户预测模型
          │         │  财务：发票自动核对    运营：全链路库存优化
          │         │
          │         │  【快速见效】          【条件成熟再推进】
          │         │  销售：日报自动生成    财务：自动付款审批
   低价值 │         │  运营：周报聚合        销售：定价策略建议
          │         │  人事：简历初筛        供应链：自动下单
          │         │
          └─────────┴──────────────────────────►
                    低难度               高难度
```

## 第二阶段：开发与入职（Phase 2: Build & Onboard）

### 2.1 数字员工开发检查清单

- [ ] **Skill 开发完成**：SKILL.md 遵循单一职责原则，一个 Skill 只做一件事
- [ ] **验证 Skill 配套**：每个数字员工至少有一个验证 Skill，用于自动检查输出质量
- [ ] **参考知识注入**：团队内部的 API 文档、业务规则、历史案例已录入 Skills/references/
- [ ] **MCP 工具就绪**：所需的外部工具连接已完成，列入白名单，测试通过
- [ ] **权限配置完成**：基于最小权限原则，已配置该数字员工可访问的数据和可调用的工具
- [ ] **审计日志接入**：该数字员工的所有决策已接入统一审计日志系统
- [ ] **人工审核节点配置**：根据自动化等级，在关键节点设置了人工确认环节
- [ ] **灰度发布方案**：明确了流量逐步放大的策略（10% → 50% → 100%）

### 2.2 知识注入清单

数字员工"入职"时需要学习的知识，按优先级排列：

```
P0 - 必须注入（缺失会导致严重错误）
  ├── 业务规则与约束（如"采购金额 > 50 万需 CFO 审批"）
  ├── 数据字典与字段含义
  └── 安全红线（如"绝不输出客户银行账号"）

P1 - 强烈建议（显著提升输出质量）
  ├── 历史案例库（过去 12 个月的典型决策案例）
  ├── 常见错误与踩坑清单
  └── 输出格式规范与模板

P2 - 锦上添花（让数字员工更像资深员工）
  ├── 行业最佳实践
  ├── 公司战略偏好（如"优先选择 ESG 评级高的供应商"）
  └── 跨部门关联知识（如供应链决策对财务现金流的影响）
```

### 2.3 验收测试（UAT）清单

上线前，业务方必须完成以下验收：

- [ ] **黄金用例通过**：准备 10-20 个"已知正确答案"的测试用例，数字员工 100% 通过
- [ ] **边界输入测试**：空值、极端值、缺失字段场景下表现符合预期
- [ ] **错误输入测试**：输入乱码、错误格式时能优雅降级而非崩溃
- [ ] **异常输出识别**：当模型输出异常时（如置信度过低），能触发转人工机制
- [ ] **人工确认**：业务方负责人签字确认输出质量和流程符合业务要求
- [ ] **灰度观察期**：设置 3-7 天灰度观察期，所有输出经人工复核后才生效

### 2.4 入职文档（数字员工档案）

每个数字员工上线时，建立一份档案：

```yaml
数字员工 ID: DE-2026-001
岗位名称: 供应商风险评估助手
所属部门: 供应链部
上线日期: 2026-06-01
模型版本: claude-sonnet-4-20260505
Skill 版本: v1.0.0
自动化等级: L2（AI 执行，人确认）
知识库版本: kb-supplier-2026-q1
负责人:
  业务方:  张经理（采购部）
  AIOps:  李工（IT 部）
MCP 依赖:
  - erp-read (只读)
  - credit-api (外部征信)
  - supplier-db (供应商数据库)
审计接入: ✅
回滚方案: 切换回人工评估流程，联系 AIOps 执行
```

## 第三阶段：运营与监控（Phase 3: Operate & Monitor）

### 3.1 运营仪表板（建议每周查看）

| 指标 | 说明 | 告警阈值 |
|------|------|---------|
| **执行次数** | 本周调用次数 | — |
| **成功率** | 正常完成的占比 | < 90% 告警 |
| **人工介入率** | 需要人类确认/修正的占比 | > 15% 告警 |
| **平均耗时** | 从输入到输出 | 超出基准 2x 告警 |
| **Token 消耗** | 本周 API 用量 | 超预算 80% 预警 |
| **用户满意度** | 有用 / 无用 反馈比率 | < 60% 告警 |
| **幻觉/错误数** | 经人工确认的错误输出 | > 3 次/周 告警 |

### 3.2 异常响应流程

当数字员工出现异常时，按以下流程处理：

```
发现异常（监控告警 / 用户反馈 / 人工发现）
    │
    ▼
┌─────────────────────────────────────┐
│ 第一步：评估影响范围                  │
│ - 本次错误还是系统性偏差？            │
│ - 影响了多少业务数据？                │
│ - 是否需要立即下线？                  │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│ 第二步：应急处理                      │
│ - 影响面大 → 立即下线，切回人工流程    │
│ - 影响面小 → 标记问题输出，继续观察    │
│ - 通知相关业务方                     │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│ 第三步：根因分析                      │
│ - Skill 规则遗漏？                   │
│ - 模型推理错误？                     │
│ - 输入数据异常？                     │
│ - 外部 API 返回异常？                │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│ 第四步：修复与复盘                    │
│ - 更新 Skill 防止再次发生             │
│ - 评估是否需要其他数字员工同步更新     │
│ - 记录到失败案例库                    │
│ - 灰度验证修复效果                    │
└─────────────────────────────────────┘
    │
    ▼
  重新上线（或决定永久下线）
```

### 3.3 成本追踪

- [ ] **月度 Token 账单**：按数字员工维度统计 API 消耗
- [ ] **模型调用分布**：Haiku / Sonnet / Opus 各占多少，是否存在"大材小用"
- [ ] **缓存命中率**：低于 20% 说明共享知识利用率不足
- [ ] **单位任务成本**：每次评估/每份报告的平均成本
- [ ] **同比趋势**：随着使用量增长，单位成本是否下降（规模效应）

## 第四阶段：评估与改进（Phase 4: Evaluate & Improve）

### 4.1 季度绩效评估卡

```yaml
数字员工 ID: DE-2026-001
评估季度: 2026-Q2

# --- 定量指标 ---
执行次数:        1,240 次
成功率:          96.3%（目标 > 90% ✅）
人工介入率:       8.2%（目标 < 15% ✅）
平均耗时:        2.8 分钟（基准 3 分钟 ✅）
Token 消耗:      ¥ 2,350/月（预算 ¥ 3,000 ✅）
用户满意度:       83% 有用（目标 > 60% ✅）
确认错误数:       5 次（阈值 3 次/周 → 需关注）

# --- 定性评估 ---
业务方反馈:       采购团队认为输出质量稳定，建议增加多语言支持
典型成功案例:     发现一家被遗漏的高风险供应商，避免了潜在损失
典型失败案例:     将一家正常经营的新供应商误标为高风险（财务数据未更新）
需改进方向:
  - 新供应商数据源需手动刷新后 Agent 才可读取（流程改进）
  - 多语言供应商文档解析能力待增强

# --- 迭代计划 ---
下季度目标:       错误率从 5 次/季降至 < 2 次/季
计划更新:         升级 Skill 到 v1.1，新增数据源刷新提醒
版本规划:         预计 2026-07-15 发布 v1.1
```

### 4.2 用户反馈闭环

建议在数字员工的输出界面集成简单的反馈机制：

```
┌──────────────────────────────────┐
│  本次回答对您有帮助吗？           │
│                                  │
│  ✅ 有用  │  ⚠️ 部分有用  │ ❌ 无用 │
│                                  │
│  [可选] 请描述问题：____________  │
└──────────────────────────────────┘
```

反馈数据定期汇总到评估卡中，作为改进的依据。

### 4.3 迭代机制

| 迭代类型 | 触发条件 | 流程 | 上线周期 |
|---------|---------|------|---------|
| **热修复** | 发现明显错误 / 安全漏洞 | 修复 → 灰度 → 全量 | 小时级 |
| **小版本** | 用户反馈 / 规则更新 | 开发 → 验证 → 灰度 → 全量 | 周级 |
| **大版本** | 季度评估 / 流程重构 | 重新走完整生命周期 | 月度 |

## 第五阶段：退役与归档（Phase 5: Retire & Archive）

### 5.1 退役条件

满足以下任一条件，应启动退役流程：

- [ ] **业务变更**：原流程已重构，数字员工不再适用
- [ ] **ROI 转负**：维护成本超过收益（如每次需大量人工修正）
- [ ] **技术升级**：被功能更强的数字员工替代
- [ ] **质量问题**：持续无法满足质量标准，且修复成本过高

### 5.2 退役流程

- [ ] **通知利益相关方**：提前 2 周通知所有使用该数字员工的团队
- [ ] **数据迁移/备份**：将数字员工产生的历史数据、决策日志归档到指定存储
- [ ] **知识转移**：如果数字员工积累了领域特有的规则和知识，整理成文档转交业务方
- [ ] **权限回收**：关闭 API 密钥、撤销数据访问权限、移除 MCP 工具白名单
- [ ] **资源清理**：下线相关 Skill、删除临时数据、释放沙箱环境
- [ ] **退役记录**：在档案中标注退役日期和原因

### 5.3 退役文档模板

```yaml
数字员工 ID: DE-2026-001
岗位名称: 供应商风险评估助手
退役日期: 2026-12-31
服役时长: 7 个月

退役原因: 被 DE-2027-003（新一代多源评估 Agent）替代

服役数据:
  总执行次数: 8,450 次
  累计节省工时: 约 420 人时
  累计 API 成本: ¥ 16,500
  累计 ROI: 约 8:1

知识资产归档:
  - Skill 代码 → /archive/skills/DE-2026-001/
  - 验证规则库 → /archive/rules/supplier-risk/
  - 失败案例库 → /archive/lessons/supplier-risk.md
  - 历史审计日志 → 保留在审计系统，按合规要求存续

替代方案: DE-2027-003（新增 ESG 评分和实时新闻监控能力）
```
