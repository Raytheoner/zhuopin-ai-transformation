## §0 结论摘要（先看这段）

1. **最大缺口不在队列，在仓库根目录**——实测 `.github` 目录**根本不存在**：无 CI、无 issue 模板、无 CODEOWNERS、无 PR 模板。本项目在一个 GitHub 仓库里，用 **4822 行自研工具**重新实现了 GitHub 原生就有的东西。
2. **但不建议整体迁移到 GitHub Issues**——离线可用是硬需求，企微机器人走文件追加，IATF 要求单一可信源在库内。迁移风险高于收益。
3. **只取一件：CI（GitHub Actions）**。它是唯一能一次性消灭多个「靠人记得」的东西，且**可作为退休若干现有守卫的容器**（满足协议〇.9 one-in-one-out，净减代码）。
4. **双队列拆分值得做，但它是「治理与注意力的解耦」，不是「技术解耦」**；且**硬阻塞于队列 #308**，提前做会把改造成本乘以 2。

### §2.1 第二批评估（2026-08-08 环境总线，CI 之外的低风险原生能力）

> **每项都给结论，不取的也写明理由——避免下次收到同类评审报告时重新论证一遍**（同 §6.6 立该节的动机）。

| 原生能力 | 结论 | 依据（一句话） |
|---|---|---|
| **`.github/ISSUE_TEMPLATE`** | ❌ **不取** | 模板服务于 Issues，而 Issues 已判定不迁（§2）——**模板没有对象**。更关键：协议〇.10 已把「建任务」的唯一入口锁死在 `acquire --reserve`（并入审核挂在那里），**Issue 模板会造出第二个建任务入口，直接绕开该咽喉**。 |
| **`.github/PULL_REQUEST_TEMPLATE`** | ❌ **不取** | 与 branch protection 是两回事（模板零强制、成本仅一个文件），**故不复用 §3.3 那条判断，另给理由**：本项目 ff-only 直推为主、**PR 多因零 diff 被 CLOSE**（§1.2 实测），模板服务于一个几乎不发生的流程。 |
| **CODEOWNERS** | ❌ **不取**，但**带重评触发条件** | 它的两个作用（自动请求评审、branch protection 的 owner 审批）在「单操作者 ＋ 不引入强制评审」下**双双落空**。🔑 **重评触发条件**（写死以免「不取」变成永久失明）：出现第二个常态操作者时重评——具体指 **AIOps 岗到位**（`6-人才与组织/` 招聘在办）**或**决策代理孙涛开始实际参与代码评审（根 CLAUDE.md §5 决策代理条）。 |
| **Dependabot · security alerts**（只读漏洞告警） | 🟢 **取** | 私有仓亦免费、**零 PR、零企微推送**——它落在 GitHub UI 里被动可查，**不构成第 9 类告警**，故不触发 §6.5 建议 2 那条「不得再加只报出现的告警」的红线。 |
| **Dependabot · version updates**（自动开 PR） | ❌ **不取** | 与上一行**必须拆开判**（多数人把 Dependabot 当一件事）：它会持续产出**没人合的 PR**，与「PR 不是主流程」直接冲突，制造的是常态噪声而非保护。 |
| **GitHub secret scanning ／ push protection** | 🟡 **可用性存疑，不改变 #309 步骤 2 第④项** | **不重复**——两者是「兜底」与「主线」关系：原生 secret scanning 对**私有仓需 GitHub Advanced Security（付费）**，本仓库含真实供应商与 OEM 数据、几乎必然私有，**故大概率不可用**。⇒ **CI 内自建 secret scan（#309 步骤 2 第④项）是唯一可依赖的那条，必须做，不因原生能力存在而缩范围。** 若实测 GHAS 可用则作为**免费叠加的第二道**（push 时拦截，早于 CI），仍不替代 CI 那道。**仓库公私与 GHAS 额度须实测**，已并入 §6 第 3 项一并确认。 |
| **Releases** | ❌ **不取** | 本项目 tag 的用途是**存档标记**（「收割完打 git tag 转只读存档」，根 CLAUDE.md §6），**不是版本发布**——无对外分发物、无下载者，而 Releases 的价值恰恰在于给下载者提供版本入口与 release notes。**无下载者则无价值。** |
| **tags 惯例规范化／机制化** | ❌ **不取，维持人守** | 「收割完打 tag」是**低频事件**（迄今仅 supplychain 一例），**无稳定机器判据**可挂（「收割完成」不是一个机器能识别的时刻）。按 §5 规则退休制的判断标准：**一条低频、且迄今未被违反过的人守规则，不值得机制化**——机制化它等于新增一个守卫去守一件一年发生一次的事，与协议〇.9 措施 B 的方向相反。 |

**⇒ 第二批净结论：只取一项（Dependabot security alerts），且它零配置代价、零新增告警通道。** 其余七项全部不取，理由已逐条写死。

## §3 CI 基线方案（决策 1，已批准 (a)）

### 3.1 交付条件（这是批准时的附加条件，不是可选项）

> **必须以「退休等量 sweep 检查」为交付条件**——CI 不是第 9 个守卫，是用来退休若干现有守卫的容器。满足协议〇.9 one-in-one-out，**净减代码**。

### 3.2 分三步，不得一次性全上

**步骤 1｜真实分类（不可跳过）**
在干净环境（无 `.env`、无 LAN）实跑一次全量测试，产出真实的「通过／失败／skip」三分清单。**CI 范围按真实清单定，不按 §1.3 的静态估计。**

**步骤 2｜CI 基线上线**
`.github/workflows/ci.yml`，在 push 与 PR 触发，跑四件：

1. 可离线测试全量（按步骤 1 清单）
2. `openspec validate --all --strict`
3. **队列结构 lint**（列数／裸竖线／§二 状态列格式）
4. secret scan（`.env` 类文件与疑似凭据字符串）

🔑 **第 3 项是本方案对既有机制的实质补强**：编辑锁的 release 校验**只在有人走锁时才生效**，而 `queue_appender.py` 那条机器人路径**完全绕过**（见队列 #305）。**CI 不论谁写、走哪条路都拦**——它比 #305 的写侧修复覆盖面更大，两者互补而非重复。

---

#### 🔴 步骤 2 追加设计输入（2026-08-08 环境总线独立复核步骤 1 产出时发现）

**先说复核结论**：本线对 CC 步骤 1 的产出做了独立复核，**未发现分歧**——测试文件 **157** 个（与 §1.3 登载值一致）；实测 **10 组同名文件**（`test_golden.py` 4 份、`test_webapp_gate.py`／`test_webapp_access_log.py`／`test_webapp.py`／`test_scoring.py`／`test_recon_report.py`／`test_real_integration.py`／`test_kit_engine.py`／`test_feed_source.py`／`test_confirm.py` 各 2 份），**与「root 一次性跑产生 20 个 collection error」的成因完全吻合**。§1.3 那条已证伪的盲区断言无需再处置，**不需独立立行，也不必并入 #300／#309**。

**但复核过程中撞出一条 CI 配置的真实约束，须在步骤 2 前解决** ——

🔴 **「逐子项目跑」的那份子项目清单，本身是一份隐性手写白名单，没有任何单一规则能自动推导出它。** 实测三种目录形态并存：

| 形态 | 实例 | 数量 |
|---|---|---|
| `X/tests/test_*.py`（标准约定） | SC8／FI2／QD-B／zhuopin_platform 等 | **11 个子项目** |
| `X/test_*.py`（**直接散在目录根，无 tests/**） | `0-学习与工具/` 下 7 个（`test_工具-落库sweep.py`／`test_工具-共享文档编辑锁.py`／`test_工具-队列查询.py` 等） | 7 个文件 |
| `X/子目录/test_*.py` | `0-学习与工具/md转Word工具/test_md2word.py`、`wecom-aibot-service/scripts/echo_test.py` | 2 个文件 |

**⇒ 后果**：`ci.yml` 若把 13 条路径写死，则**下一个新场景建成时若忘了加进 CI 配置，CI 照样全绿、而该场景零覆盖**。路线图上待建的 SC2／SC4／SC10／SC11、质量域 8D 与 IQC/SPC 都会走这条路。**这正是 CI 立项要消灭的「靠人记得」，在 CI 自己身上原样复活。**

**建议两道护栏（具体实现交 CC 定，此处只给方向与理由）**：

1. **自动发现优先于硬编码清单** —— 用一条规则找出全部含测试文件的目录（如自 `git ls-files` 匹配 `test_*.py` 上溯到最近的项目根锚点：`tests/`／`conftest.py`／`pyproject.toml`／`setup.py`），而非维护路径列表。
2. 🔑 **更重要的是计数护栏，因为它不依赖发现规则是否完美** —— CI 内断言三个下界，任一掉下去即红：
   - **收集到的用例数 ≥ 基线**（步骤 1 实测 **1704**）
   - **子项目数 ≥ 基线**（**13**）
   - **skip 数 ≤ 基线**（步骤 1 实测 **40**，分布 FI2 9／QD-B 25／SC8 4／aibot 1／platform 1）

> **第三项容易被忽略但同样重要**：CI 环境无 `.env`、无 `.51`，**skip 是预期的**；但 skip 数若**上升**，说明有测试在 CI 里悄悄不跑了——**表现同样是「全绿」**。这与 §1.3 那次误判是同一形态：**一个看起来完全正常的结果，只是它根本没测到我以为的那些东西。**（同根 CLAUDE.md §5「工具静默回退」）

**步骤 3｜退休等量守卫**
CI 稳定运行一段时间后，把 sweep 内已被 CI 覆盖的检查删除，并在队列行回写「本次退休了哪几项、代码净减多少行」。

### 3.3 明确不做

- ❌ 不引入 PR 强制评审／branch protection（单操作者场景，收益低于摩擦）
- ❌ 不迁 GitHub Issues
- ❌ 不在 CI 里跑需要真实凭据或 `.51` 的集成测试（那些留在本机建造流程）

## §4 双队列方案定稿（决策 2，已批准 (a)：只定稿、不立行）

### 4.1 能真解耦的（4 项，实的）

| 项 | 现状 | 分开后 |
|---|---|---|
| 文件锁 | 一文件一锁，2 小时内 8 次 acquire 全串行 | 两把独立锁 |
| 取号空间 | 单一高水位线，取号必串行 | 两套编号独立推进 |
| 批次流 | §二 混装两类 | 两条独立落库流水 |
| WIP 与注意力 | 措施 C 靠关键词猜分类 | 结构上分开，81:20 变成可独立治理的两条线 |

### 4.2 不能解耦的（3 项，必须写明，否则分完会失望）

🔴 **触碰区照样重叠**——实测机制类未收口 15 行里 **5 行触碰 `4-数字员工/5-平台底座`**（业务代码），业务类 11 行里 3 行触碰同一处。#305 改机器人服务、#308 改 7 个消费者含平台底座——**分队列不改变代码层争用**，worktree 冲突照旧。

🔴 **跨队列引用天然存在**——#22 源于业务可见性需求、#129 源于姚祖怡的业务反馈、#282 里挂着业务专员通道。**机制任务大多是业务问题的残渣**，两边会互相引用编号。

🔴 **读取侧成本翻倍**——值周巡检／看板／#302 判据都得读两边。

### 4.3 结论与硬前置

- **值得做，但卖点不是「文件锁」**（今日实测锁争用仍是烦扰级、未到阻塞级），而是**让 81:20 的失衡结构化、可独立治理**。
- 🔴 **硬阻塞于队列 #308**：现有 **7 份独立解析实现**，先分文件＝**7 × 2 = 14 处**要改；#308 的权威解析器与机器状态字段落地后再分，成本降一个量级。
- **本件定稿后不立行**，待 #308 落地并满足协议〇.9 措施 C（机制类未收口 ≤ 8）后再启动。

### 4.4.1 问一 · 跨队列引用语法 —— 🔴 结论：**不需要发明任何语法，因为不该分两套编号**

**先回答 §4.2 那条实况**（「机制任务大多是业务问题的残渣，两边必然互引」）：这条**成立，但方向被描述错了**。逐条看 §4.2 自己举的三例——#22 源于业务可见性需求、#129 源于姚祖怡的业务反馈、#282 里挂着业务专员通道——**三例全是「机制行指向业务出处」，没有一例是反向**。

⇒ **互引不是对称的，是单向为主的溯源**。真实需求是「一条机制行要能说清它源自哪个业务问题」，**这是一个溯源关系，不是一个跨命名空间寻址问题**。

**⇒ 由此得出的关键判断：两个队列 ≠ 两套编号。**

| | 分两套编号（§4.1 原设想） | **单一编号 ＋ 分两份文件（本节建议）** |
|---|---|---|
| 跨队列引用写法 | 须发明前缀（`#M-101`／`机#101`…） | **`#205`，与现在一字不差——无需发明** |
| 历史引用（队列内 ＋ 九份规划文档 ＋ 归档件 ＋ CLAUDE.md） | 全部需回填或永久歧义 | **全部继续有效，零回填** |
| 「行首＝分隔符＋纯数字＋分隔符」这一假设（7 份解析器 ＋ `--reserve` 取号工具）　※此处刻意不写该正则原文——它含裸竖线，按协议〇.8 三条禁令不进表格单元格 | 全部要改 | **不破坏** |

**⇒ 建议从 §4.1「能真解耦的 4 项」中剔除「取号空间」这一项，改为 3 项。** 理由：**它是四项里收益最小、代价最大的一项**——取号串行的真实代价是编辑锁窗口内的一次毫秒级读写（**从未构成过阻塞，无任何事故记录**），而两套编号空间的代价是全部历史引用 ＋ 三次修过的竞态逻辑重来一遍。

### 4.4.2 问二 · 归属判据 —— ✅ 结论：**并入 #308 机器字段，且这是唯一自洽的解法**

接力问的是「**评估是否**并入 #308 的机器字段，而非另造判据」。**答：是，且另造判据在方向上是错的。**

2. 🔑 **最关键的一点：「域」是建行那一刻就已知的，从来不需要任何人事后去猜。** 建行的人清楚自己在建什么。**当前之所以要猜，纯粹是因为建行时没被要求说**。
3. ⇒ **落点已经现成**：协议〇.10 已把「并入审核」挂在 `acquire --reserve` 上，**同一个咽喉、同一次交互，顺带要求声明域即可**——`--reserve 1 --section 一 --domain 机`（形态待 design 定）。**归属判据问题就此不存在，而不是被解得更准。**

**存量 106 行的回填**：随 #308 本就要做的状态字段回填**同批做掉，不多开一次遍历**。回填时的域判定可以用现有关键词判据做初筛 ＋ 人工复核（#308 design 本就要定复核抽样比例）。

> 🔑 **这里有一个必须写明的区分，否则会显得自相矛盾**：**一次性迁移用启发式 ＋ 人工复核兜底 ＝ 可接受；长期运行的判据用启发式 ＝ #308 要根治的病。** 差别在于前者有终点且有人看过，后者会在无人注意时持续产出错误答案。

### 4.4.3 问三 · 迁移路径 —— 建议**三阶段渐进，且前两阶段不分文件**

| 阶段 | 动作 | 收益 | 可逆性 |
|---|---|---|---|
| **阶段 1**（随 #308 同批） | 加域字段 ＋ 存量回填 ＋ 建行时声明域，**仍单文件** | 🔑 **拿到「WIP 与注意力」这一项的绝大部分**——看板／值周巡检可按域独立统计，**措施 C 的分母不再靠猜**（协议〇.9 自陈的那处「机械实现暂缺一半」当场闭合） | ✅ 完全可逆（只是多一个字段） |
