## 一、拆件巡逻迁移（#90 未覆盖，本件新增）

### 1.1 为什么它必须跟机器人走（已实测）

`7-外部文档/` **在 `.gitignore` 内，git 跟踪 0 个文件**。巡逻的工作是「读专员回件 → 拆件回灌」，**回件原件不入 git**。

- 巡逻留笔记本 + 机器人在 Mac → 巡逻**读不到**新回件（rsync 是**手动**触发的，救不了 09:00/13:00 **无人值守**的自动班）
- 二者同机 → 巡逻读 Mac 本地归档，天然可用

**结论：机器人与拆件巡逻是一个不可分割的迁移单元。**

### 1.2 它在 Mac 上需要什么（逐项，与 #90 的 tasks 互补）

| # | 事项 | 说明 |
|---|---|---|
| P1 | **载体形态确认** | 巡逻是 **Claude 定时任务**（`Claude\Scheduled\huijian-chaijian-patrol\SKILL.md`），不是 Python 服务。迁移＝在 Mac 的 Claude 桌面 app 里重建同名任务 + 同一份 prompt。**⚠️ macOS 真实物理路径未核证**（外部评审称 `~/Library/Application Support/Claude/Scheduled/`，无 Mac 无法证实）——**以 `0-学习与工具/定时任务源码/huijian-chaijian-patrol.SKILL.md` 镜像为准重建**（2026-07-30 已建立版本保护，哈希与真身一致） |
| P2 | **文件夹授权** | Claude 定时任务需对项目目录有授权才能读写（"云端 routine 无文件夹授权→Morning briefing 空转"是既有教训）。Mac 侧须重新授权并**实跑一次空巡验证** |
| P3 | **落库路径（🔴 唯一真正待设计项）** | 见 1.3 |
| P4 | **时区** | launchd/系统时区须固定 `Asia/Shanghai`，否则双班（09:00/13:00）漂移 8 小时 |
| P5 | **prompt 内的三.5 止血条款** | #168 根治已上线；迁 Mac 后机器人与巡逻**同机但不同进程**，仍可能并发写队列 → **三.5 建议保留**，不因迁移而删（退役与否见决策件 §十，须实测后定） |
| P6 | **编辑锁语义** | Mac 上巡逻与机器人共享**同一个 clone 的同一个 `.git`** → 协议〇.7 编辑锁在 Mac 侧**完整成立**（这是同机的额外好处，跨机器时才失效） |

### 1.3 🔴 待设计：巡逻在 Mac 上如何落库（两条路，本件不预设）

巡逻会产出：拆件巡逻报告（tracked）、队列行改动、§二 批次登记。现状靠**笔记本的 sweep**，而 sweep 留守笔记本、只管笔记本那个 clone。

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **(a)** Mac 另起一个 sweep | 指向 Mac clone，独立计划任务 | 改动最小、复用现成脚本 | **两个 sweep 各自 push master** → 放大 #171 分叉风险；两台机器的批次表是同一份文件，语义上会互相看到对方的批次 |
| **(b)** 巡逻自行 commit+push | 复用 `queue_git_sync` 的 fetch-重算-重推范式 | 不制造第二个 sweep；范式已在生产验证 | 需写代码（巡逻是 prompt 不是服务，得给它一个可调用的脚本） |

**起草方倾向 (b)**，但**这是 CC 的判断题**。**批准前不必现在定**——它属于"批准之后的第一件设计工作"。

> **⚠️ (a) 的一个隐患值得先写下来**：两个 sweep 会**读同一份 §二 批次表**。Mac 的 sweep 看到笔记本登记的批次时，它那个 clone 里对应文件可能根本不脏（改动在笔记本上）→ 会怎样？**未核证**。若选 (a) 必须先回答这个问题。
