## 一、诉求与判定

**Shao Peishen 2026-08-25 原话**：「目前多数情况下我的 OneDrive 是关闭的，但以后不能经常关闭，我需要把企业AI转型项目目录从 OneDrive 路径移出，以免和 github 冲突。」

**判定：诉求成立，且现行惯例本就是在拿「关掉 OneDrive」当补丁。**

- 根 `CLAUDE.md` §5 现行惯例白纸黑字写着「**平时全关、每周手动开一次作纯离线备份**」——这条惯例的存在本身就是承认：OneDrive 与 git 工作树同处一地是不相容的，只是靠「大部分时间不让它跑」压住了。
- 一旦「以后不能经常关闭」，这个压制条件消失 ⇒ **OneDrive 会开始实时同步 47,578 个文件**，其中包含 `.git/` 的 pack、index、`*.lock`。git 在写 index/lock 期间被同步客户端读写占用，典型症状是 `.git/index.lock` 残留、对象库半写、以及 OneDrive 自作主张产生「-SPSThinkpadWIN」式冲突副本。
- **这不是推测**：本仓库 `.git/` 目录下**已经存在** `config-SPSThinkpadWIN`、`config-SPSThinkpadWIN-2`、`FETCH_HEAD-SPSThinkpadWIN` 三个文件——**这就是 OneDrive 冲突副本命名法在 `.git` 内部留下的实物**。换言之，冲突不是将来时，是已经发生过、只是还没有酿成事故。

**⇒ 结论：迁出 OneDrive 是治本动作，不是优化项。**

### 🔴 冲突发生在哪一层（2026-08-25 补，Shao Peishen 问「git 本身没在 OneDrive 路径里吧」后取证）

**分两层，答案相反**：

| 层 | 位置 | 受不受影响 |
|---|---|---|
| git **程序** | `C:\Program Files\Git\cmd\git.exe` | ✅ 不在 OneDrive，迁移不碰 |
| git **全局配置** | `C:\Users\Paul Shao\.gitconfig` | ✅ 不在 OneDrive，迁移不碰 |
| 仓库的 **`.git` 目录** | `…\OneDrive\Projects\企业AI转型\.git`，**8,251 文件 / 632.5 MB** | 🔴 **就在 OneDrive 里，且它就是问题本身** |

`.git` 占整个仓库 1.26 GB 的**一半**，内容是 pack、index，以及 git 运行期不断创建又删除的 `*.lock`。OneDrive 不认得 git 语义，只看到"一堆文件在高频变动"，于是去读、去上传、去占句柄。

**⇒ 迁移的目标可以更精确地表述为：让 `.git` 这个目录不再有第二个进程去碰它。** 工作树搬走只是顺带的。

**这一节改变了方案的一处做法**：既然要搬的是一个 632 MB 的对象库，S2 的完整性校验必须升级为 `git fsck --full`（见 S3 第 10bis 步），而不是原先写的 `git fsck`。

**❌ 明确不改善的两项 —— 尤其别据此撤掉 §一 #414**：

**因为触发 #414 的是反引号，不是空格。** 事故命令形如 `--cell "…\`0-学习与工具/\` 新增脚本"`：**这里的双引号包的是含空格的中文正文，不是路径**；反引号来自队列行文规范里的 Markdown 代码跨度，**迁移后它写成 `0-study-tools/` 也一样带着反引号**。

```
路径有空格 → 必须加引号 → 习惯用双引号 → 双引号里反引号被执行
                                    ↑
                        迁移只砍断了这一段的前半截
```

⇒ **写脚本时的触发面确实大幅变小，但队列单元格这条路径完全不受影响**；**裸竖线撑列同样一点不受影响**（那是 Markdown 表格层的事）。**#414 的两条修复面（A 反引号侧走 `--cells-json`／B 绕过侧复用校验）迁移后仍全部必要。**

🔑 **一般判据**：**一次改动同时消掉多类问题时，要逐类问自己"它是被这次改动消掉的，还是只是恰好一起被提起的"**——否则会连带撤掉一批其实没被解决的防线。

5. 🔴 **停机器人（2026-08-25 实测重写，原写法「停任务、核进程已退出」不成立）**——机器人有**三层**，只停任务或只杀 python 都会被拉回来：

    ```powershell
    Stop-ScheduledTask -TaskName 'ZhuopinAibotDevListener'          # ① 停任务（不够）
    # ② 先杀守护 powershell，再杀 python —— 顺序不能反
    Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" | ? { $_.CommandLine -like '*start-aibot-service-dev*' } | % { Stop-Process -Id $_.ProcessId -Force }
    Get-CimInstance Win32_Process -Filter "Name='python.exe'"     | ? { $_.CommandLine -like '*run_aibot_service*' }       | % { Stop-Process -Id $_.ProcessId -Force }
    Start-Sleep 90                                                  # ③ 🔴 必须 ≥70 秒，见下
    Get-CimInstance Win32_Process -Filter "Name='python.exe'"     | ? { $_.CommandLine -like '*run_aibot_service*' }       # 应空
    Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" | ? { $_.CommandLine -like '*start-aibot-service-dev*' } # 应空
    ```

    **三条实测判据**：
    - **⑴ `Stop-ScheduledTask` 杀不掉它**——任务动作是 `wscript.exe → run-hidden.vbs → powershell → python`，VBS 用 `WScript.Shell.Run` 起的链在中间脱钩，`Stop-ScheduledTask` 只终止它认得的那一层。
    - **⑵ 只杀 python 必被拉回**——外层守护 `start-aibot-service-dev.ps1` 是 `while ($true)` ＋ **三级退避 60／300／900 秒**，服务退出后**第 60 秒**重启（守护日志 `reports/service-dev-*.log` 有 `第 1 级退避：等待 60 秒后重启…`）。
    - **⑶ 🔴 复核必须等 ≥70 秒**——2026-08-25 实测：杀完 `Start-Sleep 2` 就复核，返回**空**（看起来干净），60 秒后进程无声回来。**这是「工具静默回退」族又一形态：一次返回「干净」的复核，对象在退避窗口后自己回来，全程零信号。**

    🔴 **⑷ 停机器人期间的来件不可恢复（2026-08-25 实测代价，方案原先没写）**：T2 那次窗口造成 **29 分钟真实断线**（14:39–15:09 UTC ／ 22:39–23:09 本地），机器人自报**「企微没有离线消息补推能力，这段时间的来件不会补推」** ⇒ **窗口内任何专员发来的消息永久丢失，只能请对方重发**。
    **⇒ 迁移窗口（预计远长于 29 分钟）必须**：① 选低流量时段（建议深夜或周末）；② **事前在采购/财务/质量三个部门群告知起止时间**；③ 事后核一遍窗口期有无来件线索（对账哨兵／专员追问），有则请其重发。**这一条是对外影响，不是纯技术项。**

    🔴 **⑸ `Disable-ScheduledTask` 对 S4U 任务同样会被拒（2026-08-25 实测）**：`ZhuopinCommitSweep` 为 `LogonType=S4U`／`RunLevel=Limited`，**改其定义需 `SeTcbPrivilege`，与属主是不是本人无关**——非提权下 `Enable-ScheduledTask` 与 `schtasks /Change /ENABLE` **均报拒绝访问**（与 S3-13 的 `Register-ScheduledTask` 被拒是同一堵墙）。⇒ **本步与 S3-13 一样必须在管理员 PowerShell 里做**；非提权会话只能登记、不能执行，**且「登记完成」不等于「事情办完」，须有人补最后一步**。
