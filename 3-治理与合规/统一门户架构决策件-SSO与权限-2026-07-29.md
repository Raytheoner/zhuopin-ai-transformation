# 统一门户架构决策件

## 〇、一句话

**目标态＝一个门户（AI 运营指挥中心）+ 一次企微登录 + 各域场景挂在统一路由下；后端保持独立服务、不合并进程。** 演进分三条并行线，其中"地基线"完全不触碰业务代码，因此**架构修正与业务开发可以真并行，不抢时间**。

---

## 一、现状（2026-07-29 实测，非推断）

| 服务 | 端口 | 技术形态 | 鉴权 | 绑定 | 在门户里的呈现 |
|---|---|---|---|---|---|
| 采购 · 保供看板 | 8091 | Flask | **无** | `0.0.0.0` | 门户内 **iframe 内嵌** |
| AI 运营指挥中心 | 8092 | **静态文件服务器**（`SimpleHTTPRequestHandler`，标准库） | **无** | `0.0.0.0` | 门户本体 |
| 质量 · QD-B 立项门禁 | 8093 | Flask | **无** | `0.0.0.0` | 门户内**外链跳转** |
| 财务 · FI2 三单匹配 | 8094 | Flask | **无** | `0.0.0.0` | 门户内**外链跳转** |
| 销售 | — | 同源 JSON | — | — | 门户内 fetch 静态数据 |

**三个关键事实**：

1. **门户目前没有任何业务能力**——8092 只是静态壳，采购域那块是 iframe 直连 8091（2026-07-27 姚祖怡 V6 #16 诉求的实现）。**下线 8091，门户里那块即变白框。**
2. **四个服务零鉴权代码、全部绑全网段**。
3. **身份源已经存在且在跑**：企微 userid 体系（`whitelist.py` 中五位专员 + Shao Peishen 的真实 userid）已随企微机器人通道运行两周。

## 二、对现状的评价（避免误判为"设计失误"）

**每场景独立起服务，在探索期是正确选择**——换来快速验证、故障隔离、互不阻塞。若一开始即搭统一门户 + SSO + 权限模型，会在业务口径尚未定型时先投入两周做地基；而 2026-07-26~29 姚祖怡三轮改口径已证明，**口径一变，早期地基大概率作废**。

**真正的问题不是"当初没设计"，而是至今没有一条约束管住增量**：采购域还有 SC1/SC2/SC4/SC7/SC10/SC11 待上，质量域还有 8D、IQC/SPC，按现有惯性即再增 8+ 个端口。

> **结论：架构债不是欠下的，是正在攒的。当务之急不是还债，是止血 + 定标准。**

## 三、🔴 现存隐患（一项，需排期不需停工）

四服务零鉴权 + 绑全网段 ⇒ **公司任一联网终端可无凭据访问**：

- QD-B：真实立项申请书，含**项目收入 / 成本 / 毛利率 / 收益指标**
- 保供看板：真实**客户名称**（如上海东风汽车进出口有限公司）、订单量、计划出货日与交期
- FI2：真实**应付单、供应商、单价**

**风险等级判定：需要排期处置，不需要停止业务开发。** 处置分两步——

- **即刻止血（半天，已交 CC 环境保障线）**：共享口令 + Cookie。利用"浏览器 Cookie 按 host 隔离、不区分端口"这一特性，一次输入四端口全通，且门户 iframe 场景不会二次拦截。**明确它是门锁不是鉴权**：不区分人员、不留访问痕迹、口令在 HTTP 明文传输（LAN 内可接受）。
- **正式方案**：企微 OAuth SSO + 三层权限（见 §五、§六）。

## 四、目标态拓扑

```
                    员工（企微内点开 / 浏览器访问）
                              │
                    ┌─────────▼─────────┐
                    │   统一门户网关     │  ← 唯一对外入口
                    │  · 企微 OAuth SSO  │
                    │  · 权限判定        │
                    │  · 统一路由        │
                    │  · 访问日志(#112)  │
                    └─────────┬─────────┘
        ┌──────────────┬──────┴───────┬──────────────┐
        ▼              ▼              ▼              ▼
   /procurement/*  /quality/*    /finance/*     /sales/*
   保供看板 SC8    QD-B 门禁      FI2 对账       （待建）
   （独立服务）    （独立服务）   （独立服务）
```

**统一路由规范：`/{域}/{场景}`**，例如 `/procurement/baoguan`、`/quality/qd-b`、`/finance/fi2`、`/procurement/sc7`。

## 五、关键决策

### 决策 1：SSO 用企业微信 OAuth，不自建、不引入第三方 IdP

**采纳**。理由：

- 企微提供 **OAuth2 网页授权**：员工在企微内点开链接 → 自动带 code → 换取 userid，**全程无感、无需密码**。
- **身份体系已存在并在跑**——现有 userid（`YaoZuYi`/`tangyanping`/`ChenChen`/`2023458`/`ShaoPeiShen`）与机器人通道**同源**，人员变动只需维护一处。
- 100 人全员已在企微内，**零推广成本、零培训**。

**不采纳**：Keycloak / LDAP / 自建账号密码体系——均需独立部署、独立运维、独立的人员同步机制，而收益与企微 OAuth 相同。

### 决策 2：网关 + 独立服务，**不合并成单进程**

**采纳网关方案**。理由：

- 网关同样能实现统一门户、统一 URL 拓扑、统一 SSO 与权限、统一访问日志；
- **且保留故障隔离**——单域异常不会拖垮全公司门户。合并进程只换来运维略简，代价是故障域从"一个域"扩大到"整个门户"。
- 100 人规模远未到需要合并进程的量级。

> ⚠️ **本条修正了 2026-07-29 讨论早期的口头建议**（曾提出"第三阶段合并 Flask 为单进程"），该建议已收回。在业务仍高频变动的阶段，**隔离比省事值钱**。

### 决策 3：权限模型起步只做三层，不做 RBAC 矩阵

| 层级 | 含义 | 起步映射 |
|---|---|---|
| **公开只读** | 门户首页、各域概览、不含敏感明细 | 全体企微成员 |
| **域成员** | 可查看本域场景全部明细与导出 | 按部门映射（采购部→采购域，等） |
| **域管理员** | 可执行操作类动作（触发重算、上传、关闭等）与查看敏感字段 | 各域 AI 专员 + 指定一线（姚祖怡/唐燕萍/陈忱 + 解植雅/汤易水/朱映桦/李姣龙） |

**不在起步阶段做**：细粒度字段级权限、跨域授权矩阵、审批流。**理由**：现阶段没有真实的权限冲突案例，凭空设计的矩阵必然与实际不符；等出现具体冲突时再细分，成本更低且有据可依。

**敏感字段清单（域管理员及以上可见，需在实现时逐项确认）**：立项书财务指标（收入/成本/毛利率/收益）、客户名称、供应商名称与单价。

### 决策 4：🔴 硬约束——新场景一律不新起端口

**自本件生效起，新增场景不得新起独立端口对外**，一律注册到统一路由 `/{域}/{场景}` 下并接入网关的 auth 中间件（中间件未就绪期间可为空壳，但路由与接入点必须预留）。

**这是本决策件中最重要、也最省钱的一条**——它管的是未来 8+ 个场景。存量三个可以慢慢收编，但**增量必须当天止住**，否则收编成本随场景数线性增长。

配套：本条须写入根 `CLAUDE.md §5` 与 `专线opener模板库.md`，与「执行环境标注」「发布即收口纪律」同级。

## 六、演进路径：三条并行线，互不阻塞

### 线 ①：增量线（**立即生效，零成本**）

- 执行决策 4：新场景不新起端口、走统一路由、预留 auth 接入点。
- 无需等待网关就绪——**先定规范，实现可后补**。

### 线 ②：地基线（**独立推进，完全不触碰业务代码**）

**本件的核心设计**：网关是"在前面加一层"，不是"改后面"，因此可独立开发上线。

顺序：
1. 反向代理 + 统一路由（业务服务零改动）
2. 企微 OAuth 接入（登录、userid 获取、会话）
3. 三层权限判定
4. 访问日志（**与 #112 埋点天然同处**，一并落地，避免两次改造）

**验收**：员工从门户一次登录，可按权限访问各域场景；四个后端服务代码零修改。

### 线 ③：存量线（**条件触发，最后做**）

各域**业务数据对准 + 专员验收通过**后，逐个把现有服务收编到统一路由下。

**顺序：财务 → 质量 → 采购。** 8091 最后动——它最复杂（每小时重算、案例处置中心、导出、多级 BOM 展开）、数据最不稳定、专员反馈最高频。

## 七、对现有开发流程的影响（评估结论：几乎为零）

| 现有做法 | 是否改变 |
|---|---|
| CC 一场景一 worktree、走 openspec | **不变** |
| 部署到 `.51`、冒烟三件套、回滚 SOP | **不变** |
| §二 批次 + sweep 落库 | **不变** |
| 跨桌任务队列、编辑锁、值周巡检 | **不变** |
| 新场景起服务 | **变**：从"新起一个端口"改为"注册到网关路由表" |
| 给专员的访问地址 | **变**：一次性从 `:80xx` 改为 `门户/{域}/{场景}` |

## 八、风险与配套

1. **网关成为单点** —— 网关挂则全门户不可达。配套：进程守护 + 健康检查 + 后端服务保留直连能力作应急通道（仅限运维，不对外宣传）。
2. **止血口令期的残留风险** —— 共享口令不区分人员、无访问痕迹。**须设复审日期**：企微 SSO 上线即废止口令，若 SSO 迟迟未落地，最迟 **2026-10-31** 前重新评估。
3. **企微 OAuth 的外部依赖** —— 企微服务不可用时无法登录。配套：保留一个应急本地口令通道（仅 Shao Peishen 与运维知悉）。
4. **程序化访问被误伤** —— 每小时重算、同步脚本、健康检查、只读取证等非浏览器访问，须在止血与 SSO 两个阶段各清点一次并逐项验证。**这是最易翻车处**。

## 九、待 Shao Peishen 决策点（design 审时确认）

1. **三层权限的部门映射**是否按企微组织架构自动取，还是维护一张手工映射表？（自动取更省事，但依赖企微通讯录接口权限）
2. **敏感字段清单**（§五决策 3）是否完整——是否还有其他不应对全员可见的字段？
3. **止血口令的知悉范围**：全员告知，还是仅告知当前灰度使用者？
4. **线②地基线的启动时机**：立即启动（与业务并行），还是等保供看板业务数据对准后再启动？
