## 二、需要展开的四条

### A-1 ❌ 驳回：「第四个缝隙——PR 合并静默破坏高水位线」不成立

**评审描述的链条**：Laptop PR（非协调文件）→ Mac 侧 `acquire --reserve` 改写队列顶部高水位线 → PR 合入 master → 高水位线被静默破坏。

**核证**：**git 按文件合并**。PR 若未触碰 `跨桌任务队列.md`，合并该 PR **不会对该文件产生任何改动**，高水位线不可能被覆盖。评审自己给这个缝隙的定语是"非协调文件的 PR"，与结论自相矛盾。

其后半段（sweep 分叉）是**另一个独立问题**，被错误地缝进了同一条。**起草方原列的三个缝隙仍是完整的**，未新增第四个。

> 注：**协调文件的撞号风险确实存在**——但那正是起草方原缝隙 1，且前提是 PR **触碰**了队列文件。评审把"触碰"与"不触碰"两种场景混在一条里了。

### A-2 ❌ 驳回：「IATF 16949 Major Non-conformity」定性

评审称方案 C 会构成 IATF **中度不符合项**。核证：IATF 16949 **并无**要求"AI 协作工具须以物理隔离实现职责分离"的条款；把内部工作方式约定的弱化直接判为体系不符合项，属**过度外推**。

**但其实质关切成立且重要**——起草方原文已写"这是防护的实质弱化，不是免费午餐"。**采纳其修法建议**（机械化 Mode 校验），**剔除其合规定性**。给 Shao Peishen 的判断依据应是"工程可靠性"，不是"审计会判我们不合格"。

### A-3 ⚠️ 修正后采纳：sweep 死锁——结论对，机制错，且真正的缺陷更严重

**逐行核证 `工具-落库sweep.py`：**

| 环节 | 代码 | 行为 |
|---|---|---|
| 早期 | `_sync_master_if_behind_origin()` → `_verify_fast_forward(refetch=False, on_fail_exit_code=0)` | 纯落后 → **自动 `merge --ff-only` 追上**；已分叉 → 跳过，**exit 0** |
| 提交后 | `_verify_fast_forward(refetch=True, on_fail_exit_code=2)` | 推送前复检；此处失败时**本地提交已经做完** |

**由此得出的真实触发条件（与评审所述不同）**：

- PR 在 **sweep 空闲时**合并 → 下一轮 sweep 见"纯落后" → **自动 ff 追上 → 无死锁**。（今天 07-30 我实测撞见过一次本地落后 origin 1 个提交，正是被这个机制自愈的。）
- 死锁只发生在 PR 于 **sweep 运行窗口内**合并（早期 fetch 与提交后 fetch 之间，数十秒级）：此时本地提交已落、origin 已前移 → **分叉** → 此后每轮 `_sync_master_if_behind_origin` 都不动手、`_verify_fast_forward` 直接跳过 → **确实永久静默停摆直到人工介入**。

**→ 评审的结论（会死锁、需人工）对；触发条件（"PR 改了协调文件"）错。非快进由 commit 祖先关系决定，与改哪个文件无关。因此它的头号建议对此问题零作用。**

**核证中发现一个评审没说透、但更该修的点（起草方与评审双方都漏了）：**

1. 早期分叉走的是 **`on_fail_exit_code=0`** → 计划任务看到的是**成功**；
2. `工具-落库sweep.py` **全文无任何 webhook / notify / send_markdown**——只写 `reports/sweep-commit.log`。

**即：sweep 一旦进入死锁，对外表现是"每 4 小时成功运行一次"，无人会知道。** 今天 09:45 那次跳过，是我人工翻日志才发现的（当时的原因是批次漏声明，不是分叉，但暴露的是同一条通道缺失）。

**修法（取代评审建议）**：
- **主**：sweep 检测到分叉时，**复用既有企微 webhook 主动告警**（`shared_tools/notifiers/wecom.py` 已在库、机器人 gap_alert 已有同款兜底范式），并考虑把该情形的 exit code 从 0 改为非 0，让计划任务层面也能看见。
- **次**：连续 N 轮跳过即升级告警（区分"偶发跳过"与"卡死"）。
- **拦 PR 仍要做，但归到缝隙 1（编号/语义撞号）名下**，不作为 sweep 死锁的修法。

### A-4 ✅ 采纳 + 加护栏：2 分钟受控 WSS 双连接实验

评审建议低峰期实测替代等待独立 BotID——**方向正确，能拆掉当前唯一的红色卡口，值得做**。但**实验本身有把现役收件口打停的风险**，须加两条护栏：

1. **先确认"被踢下线后能否自愈"**——现有三级重启退避（1min/5min/15min）与 SDK 自动重连是否覆盖"被服务端主动踢"这一情形？**若不覆盖，实验可能从"2 分钟"变成"持续停摆"。** 这一条必须先在代码/文档层面确认，再动手。
2. **实验前后各核对一次审计**（`reports/wecom_aibot_audit.jsonl`）与队列，确认窗口内无真实来件被吞；实验窗口避开专员活跃时段（近期真实回件出现在工作日 11:00 与 22:xx，周日晚相对安全）。

**仍建议并行申请独立 BotID**——实验成功可解锁第 3 步，但独立测试凭据对**后续所有 Mac 侧回归测试**仍有长期价值，不因单次实验成功而取消。
