## 二、对抗性评审维度（逐项给结论，不许"总体良好"带过）

### 1. 🔴 核心论证是否成立（最重要，请优先攻这里）

决策件 §三 的核心论断是：**"笔记本不开 local session"这一条，使协议〇.7 编辑锁的跨机器致命性被消解**。请自己读 `工具-共享文档编辑锁.py` 与协议〇.7 条文后独立判断：

- 锁的实际作用域是什么？决策件称它靠 `git rev-parse --git-common-dir` 定位共享 `.git` 下的锁文件——**代码是否真的如此**？
- "只有 Mac 端会碰锁"这个前提，**在什么情况下会被悄悄破坏**？（例：某个 CC session 在笔记本上被顺手打开；某个自动化仍在笔记本上跑并写队列；Remote Control 会话中断后有人本地救火。）
- 决策件承认留下三个缝隙（§五 决策 3）。**还有第四个吗？** 请特别想：**语义冲突而非文本冲突**的其他形态（除编号撞号外，还有什么改动是 git 会"合并成功"但语义已坏的？例如 §二 待 commit 批次表、README 状态列、高水位线标注行）。

### 2. 🔴 PR 路径三条硬规则是否够（起草方自认最薄的三处之一）

§五 决策 3 三条：① PR 不碰协调类文件；② 需部署的改动须声明；③ PR 合并后 Mac 侧先 pull 再让 sweep 继续。

- 这三条是**纪律**，没有任何机械化强制。**如何被违反、违反后多久会被发现、发现时损失多大？** 请给出至少一个具体的违规剧本。
- 有没有**低成本机械化手段**可以把其中任一条从纪律变成检查（如 CI／pre-commit／sweep 侧校验）？若有，属 P1 建议。
- 第 ③ 条依赖 `工具-落库sweep.py` 的 `_sync_master_if_behind_origin` 行为。**请读代码核实**决策件对它的描述（"只处理纯落后可快进，分叉时告警跳过、不强推"）是否准确。

### 3. 🔴 安全面（起草方自认最薄的一处，明确请你攻）

决策件 §九 只提出了问题、**没给完整方案**：Mac Studio 上一个长开、具备文件系统与终端执行权限的 Claude Code，位于公司 LAN 内、可达 `.51`（四个 Web 服务）与 U9C／SRM 真实接口。

- 相比现状（笔记本，off-LAN 居多、非长开），**风险实际增加了多少**？请具体化，不要泛泛说"攻击面变大"。
- Remote Control 引入的新信任链（Anthropic 侧同步层 + web/手机端会话接入）在 IATF 16949 可追溯性与公司数据边界上有什么需要交代的？
- 现有合规红线（CLAUDE.md §7：审计 append-only 3 年留存、OEM 数据隔离、L2 人工门禁、ASIL C/D 为 AI 禁区）**有没有任何一条会因为迁移而被削弱**？
- `.env` 与凭据在迁移过程中如何不落入 git／不落入第二台机器？决策件**未涉及这一步**，请评估是否应作为前置。

### 4. 分阶段路径的可执行性与顺序

- 五步（0 只读试用 → 1 Dispatch → 2 CC 主力 → 3 机器人 → 4 Cowork）的**顺序**是否最优？决策件刻意把机器人排到第 3 位（理由：唯一有真实业务损失风险、且卡凭据）——**你同意吗？**
