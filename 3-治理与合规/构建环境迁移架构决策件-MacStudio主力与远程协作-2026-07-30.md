# 构建环境迁移架构决策件

## 〇、一句话

**目标态 ＝ Mac Studio 是项目仓库的唯一 local session 写手；笔记本不再开本地会话，只作 Remote Control 远程客户端；笔记本若需本地建造，走独立 clone + PR 合入，永不直接写主写手的工作树。**

这个模型的价值不在"设备更好"，而在**它是唯一能让协议〇.7 编辑锁继续成立的双机方案**——见 §三。

> **不影响项目开发是硬要求**（Shao Peishen 2026-07-30 定）：本件全部路径按"稳扎稳打、逐步迁移、每步可独立回滚"设计，**第 0 步完全不触碰生产**。

## 一、现状（2026-07-30 实测，非推断）

| 组件 | 跑在哪 | 实测证据 |
|---|---|---|
| 企微机器人常驻监听 | **Win 笔记本** | 计划任务 `ZhuopinAibotDevListener` → `wscript.exe run-hidden.vbs`；进程 PID 31608 = `python.exe …\wecom-service-home\scripts\run_aibot_service.py`；审计 `5-平台底座/wecom-aibot-service/reports/wecom_aibot_audit.jsonl` 798 行、18:09 仍在写 |
| 落库 sweep | **Win 笔记本** | 计划任务 `ZhuopinCommitSweep`（每 4 小时 + 开机） |
| 拆件巡逻 / 值周巡检 | **Win 笔记本** | Claude 定时任务（`Claude\Scheduled\`），随桌面 app 运行 |
| CC 建造 / Cowork 治理 | **Win 笔记本** | 一任务一 worktree，共享同一 `.git` |
| 四个 Web 服务 | **`.51`（Windows Server）** | 8091/8092/8093/8094，`/api/ping` 全 200、首页全 302（门禁生效） |

**关键事实**：企微机器人走的是**出站长连接**到 `qyapi.weixin.qq.com`（公网 WSS），不需要公网 IP、不需要入站端口——**这也是为什么它能在 off-LAN 的笔记本上工作**。`.51` 那四个服务相反：要别人连进去，必须在 LAN 内。

## 二、迁移动因（按重要性排序，第 1 条是新认识）

1. **🔴 单一写手是编辑锁成立的前提，而现状是"能用但脆"**。协议〇.7 编辑锁靠 `git rev-parse --git-common-dir` 定位共享 `.git` 下的锁文件——**它只能约束共享同一 `.git` 的写手**。今天（07-30）刚完成的 #168（机器人走锁）、巡逻 prompt 三.5 止血、协议〇.7 全部建立在这个前提上。任何"两台机器都开 local session"的方案都会让这一整套失效。
2. **笔记本的可用性上限 ＝ 机器人的可用性上限**。合盖/休眠/断网 = 监听下线 = 该时段来件**永久丢失**（企微 aibot 无离线补推）。2026-07-16 已发生一次 24h49m 停摆。#138 已留痕接受该风险，但它每天都在。
3. **定时任务不可靠**。拆件巡逻（工作日 09:00/13:00 双班）与值周巡检（周一 10:00）跑在笔记本的 Claude 桌面 app 里，合盖即不跑。
4. **off-LAN 时无法部署**。`sync-to-server.ps1` 必须在 LAN 内执行。Mac Studio 常驻办公室 → 部署能力从"必须回办公室"变为"随时"。

## 三、为什么"笔记本不开 local session"是关键（本件的核心论证）

**若两台机器都开 local session**：各自有独立 `.git` → 各自有独立锁文件 → **锁形同不存在** → 回到 2026-07-23 那类"后写者静默覆盖先写者"事故，且这次**没有任何机制兜得住**（#168 修的是机器人绕锁，不是跨机器）。

**本方案改为**：
- Mac Studio ＝ **唯一有 local session 的写手**，所有对仓库的直接写入（队列 / docs / openspec / 机器人代码）只发生在这里 → **锁的适用域完整**，协议〇.7 与 #168 继续成立。
- 笔记本 ＝ Remote Control 远程客户端（会话实际跑在 Mac 上），或独立 clone + 独立分支 + **PR 合入** → 走的是 GitHub 集中托管的常规多人协作路径（有冲突检测），**不是同 worktree 并发写**。

**结论：编辑锁的跨机器致命性在本方案下被消解。** 但留三个缝隙，必须写成显式规则（§五 决策 3）。

## 四、目标态

```
                    ┌─────────────────────────────────────┐
   任何地点          │   Mac Studio（办公室，长开，LAN 内）  │
  ┌─────────┐       │  ─────────────────────────────────  │
  │ 笔记本   │──①──▶│  Claude Code（唯一 local 写手）      │──▶ .51 四服务
  │ 手机/浏览器│      │  Dispatch 定时任务（真正 7×24）      │    （部署，LAN 内）
  └─────────┘       │  企微机器人常驻监听                   │
       │             │  落库 sweep                          │
       │             └──────────────┬──────────────────────┘
       │                            │ push master
       └────②─── PR ──▶ GitHub ◀────┘
```

① **Remote Control**（2026-02-25 发布，研究预览；**Shao Peishen 为 Max 订阅，已确认可用**）：会话跑在 Mac 上，web/手机只是窗口；**无需 VPN、无需端口转发**；内置自动重连，网络掉线或客户端睡眠时会话在后台存活。
② 笔记本本地建造走独立 clone + 分支 + PR，**永不直接 push 到主写手的工作树**。

**不迁的**：`.51` 服务器（仍是 Windows Server，`deploy-server.ps1` ×5 在其上执行、无需改写）。

## 五、关键决策

### 决策 1：Mac Studio 为唯一 local session 写手，笔记本停开本地会话

理由见 §三。**这是本件的地基，其余决策都依赖它。**

### 决策 2：远程接入用 Claude Code Remote Control，不自建 VPN / 不做端口转发

- Remote Control 原生支持、无需网络改造，且**不引入新的对外暴露面**（对比 SSH 暴露、VPN 运维）。
- **副作用：SSH 的必要性下降**——原 §四#34 第②项（Mac SSH 访问方式）从"迁移前置"降级为"IT 配置与排障便利项"，不再阻塞。
- **残留限制（如实记）**：① 仍是**研究预览**，非 GA；② **通知不是 OS 级**（截至 2026-03），需主动查看会话，不能依赖推送——故"专员回件"的实时感知仍须依赖机器人自身的企微告警通道，不得改由 Remote Control 承担。

### 决策 3：🔴 笔记本 PR 路径的三条硬规则（缺一即复发）

GitHub 的冲突检测**只覆盖文本冲突，不覆盖语义冲突**。以下三条必须与"笔记本停开 local session"**同日生效**：

1. **PR 一律不得触碰协调类文件**——`跨桌任务队列.md`、四条 session 接力、`专线opener模板库.md`、根 `CLAUDE.md`。
   **原因**：队列是 Markdown 表格，两边各自算出同一编号 `#N` 但写在文件不同位置时，git **无文本冲突 → 自动合并成功 → 队列出现两行同号**。#90 的 design 已明确指出"历史事故模式是'两写手各自算出同一编号'**而非文本冲突**"。**GitHub 的"合并成功"在此处是虚假的安全感。**
2. **PR 若含"需部署才生效"的改动，必须在 PR 描述中声明「待 Mac 侧部署」并登队列**。
   **原因**：合入 master ≠ 生效（今日新立的【设置】行「工作区」字段即为此）。部署只能由 Mac 执行（LAN 内）。
3. **PR 合并后，Mac 侧先 `git pull` 归位，再让 sweep 继续**。
   **原因**：`ZhuopinCommitSweep` 每 4 小时自动 commit+push；PR 合并会让 Mac 本地 master 落后，其 `_sync_master_if_behind_origin` **只处理"纯落后可快进"，分叉时告警跳过、不强推**（该 fail-safe 正确，但会导致 sweep 连续空转）。

### 决策 4：Cowork 的安置 —— 三选一，**待 Shao Peishen 拍板**（见 §八 决策点①）

**必须先澄清一处**：Remote Control 同步的是 **Claude Code 终端会话**；**Cowork 是桌面 app 的另一种模式，不在其覆盖范围内**。因此"笔记本只作远程客户端"对 CC 成立、**对 Cowork 不成立**。

| 选项 | 代价 |
|---|---|
| A. Cowork 搬 Mac，靠远程桌面使用 | 需 IT 配远程可达；体验不如本地；多一条通道要维护 |
| B. Cowork 留笔记本 | 🔴 **破坏单一写手**（Cowork 的活正是改队列/接力/CLAUDE.md 等协调文件），与决策 1 直接冲突 |
| C. 不用 Cowork，规划治理活并入 Mac 的 Claude Code | 只需 Remote Control 一条通道；**但双桌纪律从"工具边界"降为"提示词纪律"** |

**起草方观察（非结论）**：C 在技术上完全可行——2026-07-30 这一整个环境保障线 session 所做的每件事（环境体检、改 `.md`、改 skill 源码、持锁登队列、触发 sweep、只读取证）**Claude Code 全都能做**。Cowork 与 CC 的分工本质是**职责分工**，不是工具分工。
**但 C 的代价必须正视**：现状下 Cowork "不自行 commit、不写生产码"是**环境属性**（天然做不到），改为 Claude Code 后**全靠 prompt 纪律约束**——这是防护的实质弱化，不是免费午餐。

### 决策 5：分阶段路径 —— 先零风险验地基，最后碰有业务风险的

**关键排序原则：机器人迁移不是第一步。** 它卡在凭据上（§六），且是**唯一可能造成真实业务损失**（收件口静默停摆）的部分，不应作为第一个试验品。

| 步 | 内容 | 风险 | 回滚 |
|---|---|---|---|
| **0** | Mac 装 Claude Code + Remote Control，**只做只读**（跑环境体检 / grep 取证 / 读队列）；Shao Peishen off-LAN 试用一周 | **零**——不动生产、不需凭据 | 不用即止 |
| 1 | 迁 Dispatch / 定时任务（拆件巡逻 + 值周巡检 + sweep） | 低（无口径风险） | 笔记本侧任务重新启用 |
| 2 | 迁 CC 建造主力；笔记本停开 local session，§五 决策 3 三规则同日生效 | 中 | 笔记本恢复 local session（需同步暂停 Mac 侧） |
| 3 | 迁企微机器人（**前置＝独立测试 BotID**，见 §六） | **高**（收件口） | `ops/wecom-service-home` 在笔记本侧重启 |
| 4 | Cowork 安置（按决策 4 拍板结果执行） | 视选项 | 视选项 |

**第 0 步的作用是验证整个方案的地基**：Remote Control 在实际使用场景下到底够不够用。这一步不通过，后面全部不做，且零损失。

## 七、迁移工作量（2026-07-30 实测）

全库 13 个 Windows 专有脚本，**需改写的约 7 个**：

- ✅ **无需改（5）**：`deploy-server.ps1` ×5 —— **在 `.51`（Windows Server）上执行**，`.51` 不迁则不动。
- ⚠️ **需改（约 7）**：`sync-to-server.ps1` ×5（在源机器执行 scp 推送）、`工具-注册落库sweep计划任务.ps1`（Windows 计划任务 → launchd）、`工具-主工作区安全同步.ps1`。
- ✅ **反而简化**：`run-hidden.vbs`（Windows 隐藏窗口偏方）在 macOS 上不需要——launchd 原生即后台服务。
- ✅ **四个核心工具已是 Python**（编辑锁 / sweep / 台账 / 孤儿 worktree 扫描），跨平台改动小。
- 📌 **另有既有产出可复用**：openspec 变更包 `wecom-listener-macos-migration`（proposal + design + specs + tasks，`validate --strict` 通过）已就绪、**design 停等 Shao Peishen 审**（队列 #90），其中已核实并纠正总线草案 3 处关键假设。

## 九、风险与配套

| 风险 | 处置 |

| Remote Control 仍是研究预览，可能变更或中断 | 第 0 步即为验证期；笔记本 local session 能力在第 2 步前完整保留，随时可回退 |
