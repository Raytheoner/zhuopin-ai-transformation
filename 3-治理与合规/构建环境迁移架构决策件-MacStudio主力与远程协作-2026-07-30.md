# 构建环境迁移架构决策件

## 〇、一句话

**目标态 ＝ Mac Studio 是项目仓库的唯一 local session 写手；笔记本不再开本地会话，只作 Remote Control 远程客户端；笔记本若需本地建造，走独立 clone + PR 合入，永不直接写主写手的工作树。**

这个模型的价值不在"设备更好"，而在**它是唯一能让协议〇.7 编辑锁继续成立的双机方案**——见 §三。

> **不影响项目开发是硬要求**（Shao Peishen 2026-07-30 定）：本件全部路径按"稳扎稳打、逐步迁移、每步可独立回滚"设计，**第 0 步完全不触碰生产**。
>
> **v2 追加口径（Shao Peishen 2026-07-30 晚）**：「**如果影响本项目开发，我们不迁移也行——现有环境也能开发完，以后新项目直接从 Mac 启动即可。**」
> 据此，**迁移不是既定结论，而是三个并列选项之一**（见 §五 决策 5）。**零迁移是合法终局，不是失败。**

## 〇.1 🔴 中止判据（把关红线，Shao Peishen 要求"严格把关"的操作化）

**任一条触发，立刻停止当前步骤并回滚，不得"先做完再说"：**

1. **🔴 任何时刻需要笔记本与 Mac 同时开 local session** —— 这是唯一会让协议〇.7 编辑锁、#168、巡逻三.5 全部作废的动作。**判断"当前是否安全"的唯一标准＝队列的 local 写手是否仍只有一台机器。**
2. **机器人迁移前，"同 BotID 双连接"行为未有结论** —— 未验证即迁＝拿收件口赌（唯一能造成真实业务损失的一项）。
3. **任一步骤导致建造活动停摆超过半个工作日** —— 迁移的全部收益都不值这个代价，直接回滚。
4. **`.51` 四个服务的部署能力出现空窗** —— 违反"发布即收口"，等于用迁移换掉了交付能力。
5. **出现无法在 30 分钟内回滚到迁移前状态的中间态** —— 每一步的回滚点必须是真实可执行的，不是纸面声明。

**触发后的动作**：停 → 回滚 → 在队列登记原因 → 重新评估是否继续，而非绕过判据继续推进。

## 二、迁移动因（按重要性排序，第 1 条是新认识）

1. **🔴 单一写手是编辑锁成立的前提，而现状是"能用但脆"**。协议〇.7 编辑锁靠 `git rev-parse --git-common-dir` 定位共享 `.git` 下的锁文件——**它只能约束共享同一 `.git` 的写手**。今天（07-30）刚完成的 #168（机器人走锁）、巡逻 prompt 三.5 止血、协议〇.7 全部建立在这个前提上。任何"两台机器都开 local session"的方案都会让这一整套失效。
2. **笔记本的可用性上限 ＝ 机器人的可用性上限**。合盖/休眠/断网 = 监听下线 = 该时段来件**永久丢失**（企微 aibot 无离线补推）。2026-07-16 已发生一次 24h49m 停摆。#138 已留痕接受该风险，但它每天都在。
3. **定时任务不可靠**。拆件巡逻（工作日 09:00/13:00 双班）与值周巡检（周一 10:00）跑在笔记本的 Claude 桌面 app 里，合盖即不跑。
4. **off-LAN 时无法部署**。`sync-to-server.ps1` 必须在 LAN 内执行。Mac Studio 常驻办公室 → 部署能力从"必须回办公室"变为"随时"。

## 三、为什么"笔记本不开 local session"是关键（本件的核心论证）

**若两台机器都开 local session**：各自有独立 `.git` → 各自有独立锁文件 → **锁形同不存在** → 回到 2026-07-23 那类"后写者静默覆盖先写者"事故，且这次**没有任何机制兜得住**（#168 修的是机器人绕锁，不是跨机器）。

**本方案改为**：
- Mac Studio ＝ **唯一有 local session 的写手**，所有对仓库的直接写入（队列 / docs / openspec / 机器人代码）只发生在这里 → **锁的适用域完整**，协议〇.7 与 #168 继续成立。
- 笔记本 ＝ Remote Control 远程客户端（会话实际跑在 Mac 上），或独立 clone + 独立分支 + **PR 合入** → 走的是 GitHub 集中托管的常规多人协作路径（有冲突检测），**不是同 worktree 并发写**。

**结论：编辑锁的跨机器致命性在本方案下被消解。** 但留三个缝隙，必须写成显式规则（§五 决策 3）。

## 四、目标态

```
                    ┌─────────────────────────────────────┐
   任何地点          │   Mac Studio（办公室，长开，LAN 内）  │
  ┌─────────┐       │  ─────────────────────────────────  │
  │ 笔记本   │──①──▶│  Claude Code（唯一 local 写手）      │──▶ .51 四服务
  │ 手机/浏览器│      │  Dispatch 定时任务（真正 7×24）      │    （部署，LAN 内）
  └─────────┘       │  企微机器人常驻监听                   │
       │             │  落库 sweep                          │
       │             └──────────────┬──────────────────────┘
       │                            │ push master
       └────②─── PR ──▶ GitHub ◀────┘
```

① **Remote Control**（2026-02-25 发布，研究预览；**Shao Peishen 为 Max 订阅，已确认可用**）：会话跑在 Mac 上，web/手机只是窗口；**无需 VPN、无需端口转发**；内置自动重连，网络掉线或客户端睡眠时会话在后台存活。
② 笔记本本地建造走独立 clone + 分支 + PR，**永不直接 push 到主写手的工作树**。

**不迁的**：`.51` 服务器（仍是 Windows Server，`deploy-server.ps1` ×5 在其上执行、无需改写）。

## 五、关键决策

### 决策 1：Mac Studio 为唯一 local session 写手，笔记本停开本地会话（**仅选项 2 适用**）

理由见 §三。**这是选项 2 的地基。选项 0/1 下写手仍是笔记本，本决策不启用。**

**🔴 v2 新增·急救例外条款**（采纳评审 P1-2）：真实场景里必然会出现"Remote Control 断了、人在外地、有急事"。**不得**靠"纪律上不许"来防——须预先定好动作：
1. **首选**：走 Tier-2 通路（决策 2）恢复对 Mac 的控制，**仍在 Mac 上作业**。
2. 若 Tier-2 也不通、且事情不能等：允许在笔记本开 local session，但**必须**——(a) 事前/事后在队列显式登记"临时双写手窗口"起止；(b) 该窗口内**只碰非协调类文件**；(c) 窗口关闭后由 Mac 侧做一次对账审计（`zhuopin-queue-audit`）确认无撞号/无覆盖。
3. **绝不允许**：无记录地开一次 local session 改队列——那正是 07-23 事故的形态。

### 决策 2：远程接入用 Claude Code Remote Control，不自建 VPN / 不做端口转发

- Remote Control 原生支持、无需网络改造，且**不引入新的对外暴露面**（对比 SSH 暴露、VPN 运维）。
- **副作用：SSH 的必要性下降**——原 §四#34 第②项（Mac SSH 访问方式）从"迁移前置"降级为"IT 配置与排障便利项"，不再阻塞。
- **残留限制（如实记）**：① 仍是**研究预览**，非 GA；② **通知不是 OS 级**（截至 2026-03），需主动查看会话，不能依赖推送——故"专员回件"的实时感知仍须依赖机器人自身的企微告警通道，不得改由 Remote Control 承担。
- **🔴 v2 新增：须有 Tier-2 备用通路**（采纳评审 P0-2）。v1 只写了"可回退到笔记本 local session"，那是**放弃远程**、不是**第二条远程通路**。若 Remote Control 中断/变更/被网络策略拦截，选项 2 之后将无法远程操作 Mac。**故：SSH（Remote Login）+ 内部 Mesh VPN（Tailscale/WireGuard 之类）由"便利项"升格为 Tier-2 官方备用通路，并在第 0 步一并安装验证。** 注：这与"不做端口转发"不矛盾——Mesh VPN 恰恰是为免端口转发而选。**选项 0/1 下本条不适用**（无远程操作需求）。

### 决策 3：🔴 笔记本 PR 路径的三条硬规则（缺一即复发）（**仅选项 2 适用**）

> **v2 更正一处因果（采纳 triage §A-3）**：外部评审主张"拦截修改协调类文件的 PR"可防止 Mac 侧 sweep 死锁。**经逐行核证 `工具-落库sweep.py`，此因果不成立**——非快进由 **commit 祖先关系**决定，与 PR 改了哪个文件无关。下列第 1 条**仍要做**，但其理由是**编号/语义撞号**（§五 决策 3.1），**不是** sweep。sweep 死锁另有修法，已独立登记为队列 **#171**（且该缺陷**与迁移无关、现在就已存在**）。

GitHub 的冲突检测**只覆盖文本冲突，不覆盖语义冲突**。以下三条必须与"笔记本停开 local session"**同日生效**：

1. **PR 一律不得触碰协调类文件**——`跨桌任务队列.md`、四条 session 接力、`专线opener模板库.md`、根 `CLAUDE.md`。
   **原因**：队列是 Markdown 表格，两边各自算出同一编号 `#N` 但写在文件不同位置时，git **无文本冲突 → 自动合并成功 → 队列出现两行同号**。#90 的 design 已明确指出"历史事故模式是'两写手各自算出同一编号'**而非文本冲突**"。**GitHub 的"合并成功"在此处是虚假的安全感。**
2. **PR 若含"需部署才生效"的改动，必须在 PR 描述中声明「待 Mac 侧部署」并登队列**。
   **原因**：合入 master ≠ 生效（今日新立的【设置】行「工作区」字段即为此）。部署只能由 Mac 执行（LAN 内）。
3. **PR 合并后，Mac 侧先 `git pull` 归位，再让 sweep 继续**。
   **原因（v2 依代码核证修正）**：PR 在 sweep **空闲时**合并 → 下轮 `_sync_master_if_behind_origin` 见"纯落后"→ **自动 `merge --ff-only` 追上，无死锁**（2026-07-30 实测撞见并自愈过一次）。**死锁只发生在 PR 于 sweep 运行窗口内合并**（早期 fetch 与提交后 fetch 之间，数十秒级）：此时本地提交已落、origin 已前移 → 分叉 → 此后每轮跳过。本条是**降低撞上那个窗口的概率**，属操作习惯；**真正的根治是 #171（分叉时主动告警）**。

**决策 3.1：第 1 条的真实理由 —— 语义撞号，不是文本冲突**

队列是 Markdown 表格。两边各自算出同一编号 `#N` 但写在文件不同位置时，git **无文本冲突 → 自动合并成功 → 队列出现两行同号**。#90 的 design 已明确："历史事故模式是'两写手各自算出同一编号'**而非文本冲突**"。**GitHub 的"合并成功"在此处是虚假的安全感。**
**机械化建议（采纳评审 P1-1 的手段、不采纳其理由）**：一个轻量校验（CI/pre-commit/sweep 前置）——`git diff --name-only origin/master...HEAD` 命中协调类文件即拒绝，把这条从纪律变成检查。

### 决策 4：Cowork 的安置 —— 三选一，**待 Shao Peishen 拍板**（见 §八 决策点①）

**必须先澄清一处**：Remote Control 同步的是 **Claude Code 终端会话**；**Cowork 是桌面 app 的另一种模式，不在其覆盖范围内**。因此"笔记本只作远程客户端"对 CC 成立、**对 Cowork 不成立**。

| 选项 | 代价 |
|---|---|
| A. Cowork 搬 Mac，靠远程桌面使用 | 需 IT 配远程可达；体验不如本地；多一条通道要维护 |
| B. Cowork 留笔记本 | 🔴 **破坏单一写手**（Cowork 的活正是改队列/接力/CLAUDE.md 等协调文件），与决策 1 直接冲突 |
| C. 不用 Cowork，规划治理活并入 Mac 的 Claude Code | 只需 Remote Control 一条通道；**但双桌纪律从"工具边界"降为"提示词纪律"** |

**起草方观察（非结论）**：C 在技术上完全可行——2026-07-30 这一整个环境保障线 session 所做的每件事（环境体检、改 `.md`、改 skill 源码、持锁登队列、触发 sweep、只读取证）**Claude Code 全都能做**。Cowork 与 CC 的分工本质是**职责分工**，不是工具分工。
**但 C 的代价必须正视**：现状下 Cowork "不自行 commit、不写生产码"是**环境属性**（天然做不到），改为 Claude Code 后**全靠 prompt 纪律约束**——这是防护的实质弱化，不是免费午餐。

**v2 补充（部分采纳评审 P1-3）**：
- ✅ **采纳其修法**：若选 C，须配套**机械化 Mode 校验**——治理类会话注入模式标记（如 `SESSION_MODE=GOVERNANCE`），由 hooks 阻断对 `4-数字员工/`、`5-平台底座/` 源码目录的写入与 `git commit`。把弱化的部分补回成机械约束，而非只加一句纪律。
- ❌ **不采纳其定性**：评审称此举构成 IATF 16949「中度不符合项（Major NC）」。**IATF 16949 并无"AI 协作工具须以物理隔离实现职责分离"的条款**，该定性属过度外推。**判断依据应是工程可靠性，不是"审计会判我们不合格"**——用错误的合规恐惧驱动架构决策，本身是一种风险。
- 📌 **选项 0/1 下本决策整体不启用**（Cowork 留在笔记本，无岔路可选）。

### 决策 5（v2 重写）：迁移范围 —— 三个并列选项，**零迁移是合法终局**

v1 默认"要迁，只是分几步"。v2 按 Shao Peishen 追加口径改为**先选范围、再谈步骤**：

| 选项 | 内容 | 解决 | 未解决 | 对开发的扰动 |
|---|---|---|---|---|
| **0 · 零迁移** | 完全不动，现环境跑完 Phase 1（至 2027-12）；新项目直接从 Mac 起 | — | 合盖丢件／定时任务不稳／off-LAN 无法部署 | **零** |
| **1 · 只迁机器人 + Dispatch**（**起草方推荐**） | 机器人与定时任务上 Mac；**CC 与 Cowork 完全留在笔记本** | 合盖丢件（#138 根治）、定时任务可靠 | off-LAN 部署 | **零**——笔记本仍是唯一 local 写手 |
| **2 · 全迁** | 含 CC 主力与 Cowork 安置 | 全部三项 | — | 中～高（须停开笔记本 local session、PR 三规则生效、Cowork 岔路必须拍板） |

**为什么推荐选项 1（v2 新增判断，v1 未识别）**：

1. **三个痛点里只有一个真正"影响开发"**——合盖丢件影响的是**专员回件接收**（协作），定时任务不稳影响的是**调度机制**，二者都不阻塞建造；**只有 off-LAN 无法部署 `.51` 是实质拖累**（违反发布即收口），而它可以靠"回办公室再发布"绕过。**故 Shao Peishen 的"现有环境也能开发完"基本成立。**
2. **选项 1 不破坏单一写手**——这一点 v1 判断有误、v2 更正：机器人在 Mac 上确实会写队列文件，但 **D1 已明确否决"让 bot 也 acquire 编辑锁"**（跨 clone 结构性不可行），改为在 **git 层**做冲突控制：推送被拒 → fetch → **重新跑 `_next_task_id` 重算编号** → 重推（**"重算"而非"重放"**，因历史事故是语义撞号而非文本冲突，`pull --rebase` 只重放插入动作、不会重算编号）。笔记本侧仍是唯一**人类 local 写手**，编辑锁语义完整。
3. **🔴 且该能力已在生产运行，不是"待建"**——`5-平台底座/wecom-aibot-service/aibot_service/queue_git_sync.py` 已在库，并经 **#126**（跨 checkout 失效 + 审计文件分裂）与 **#168**（编辑锁集成、锁忙推迟补录不丢消息）两轮真实故障打磨。**故机器人迁移不是"造新能力"，而是"把已验证代码换个 OS 跑"——风险显著低于 v1 的估计。**
4. **选项 1 让三件麻烦事直接消失**：PR 路径三条硬规则（§五 决策 3）**不需要**、Cowork 三选一（§五 决策 4）**不需要决策**、跨机器语义冲突**不存在**。

**选项 1 → 选项 2 的升级不封死**：若日后 off-LAN 部署成为真实痛点，可在 Phase 1 收口后再评估；届时选项 1 已把机器人与 Dispatch 迁完，剩余工作量更小。

## 五.B 🔴 「Dispatch」必须拆开——三件事的约束完全不同（v3 新增）

v2 写的"迁机器人 + Dispatch"**过于笼统**。Shao Peishen 追问"归档是否需要 GitHub 同步"时暴露了这一点。逐项核实后：

**核实结论（2026-07-30 实测）**：`7-外部文档/` **在 `.gitignore` 内，git 跟踪 0 个文件**——归档件**根本不经 GitHub 传播**。这不是疏漏，是刻意的敏感层边界（专员回件含真实供应商/客户数据）。`#90` 的 **D3** 已定：Mac 为归档原件权威副本，笔记本回 LAN 时走 SSH **单向 rsync 拉取**（只拉不推、手动触发），实时可见性由 `forwarding.py`（全量进件转发 Shao Peishen 企微）兜底。

| 组件 | 归属 | 约束（为什么只能这样） |
|---|---|---|
| **企微机器人** | ✅ **迁 Mac** | 队列行走 `queue_git_sync`（已在生产、经 #126/#168 打磨，**零新增改动**）；归档件走 D3 |
| **拆件巡逻** | ✅ **必须跟机器人同机** | 它要**读 `7-外部文档/` 才能拆件**。归档件不入 git → 留在笔记本就读不到 Mac 上的新回件；rsync 是**手动**的，救不了 09:00/13:00 **无人值守**的自动班 |
| **落库 sweep** | 🔴 **绝不可迁** | 它的职责是**给 Cowork/CC 的改动落库**。Cowork/CC 留笔记本，sweep 一走，**笔记本上的工作就无人 commit**；且 `MAIN_WORKSPACE` 硬编码指向笔记本主工作区 |
| 值周巡检 | 建议留笔记本 | 读队列（在 git 里，哪都行），但写《本周计划》需落库 → 与 sweep 同机最省事 |

### 五.B.1 待决项：Mac 侧拆件巡逻的落库路径（交 CC 出 design）

巡逻迁 Mac 后，其**报告与队列行**如何进 git？现状靠笔记本的 sweep，而 sweep 只管笔记本那个 clone。两条路：

- **(a) Mac 上另起一个 sweep**（指向 Mac clone）——简单，但**两个 sweep 各自 push master**，会放大队列 **#171** 的分叉风险。
- **(b) 让巡逻自己 commit+push**，复用 `queue_git_sync` 的 fetch-重算-重推范式——干净、不制造第二个 sweep，但需写代码。

**起草方倾向 (b)**（范式现成、且不新增分叉源），但**这是 CC 的判断题，由领活 session 出 design 决定，本件不预设**。

## 五.A 🔴 凭据安全迁移 SOP（v2 新增，采纳评审 P0-1）

v1 完全未涉及这一步，是真实盲点。`.env` 含**生产库 sa 口令、企微 BotID/Secret 与群 webhook、`.51` 门禁口令、GitHub PAT**——任何一项泄漏后果都远大于迁移本身的收益。

1. **`.env` 严禁入库、严禁经邮件/微信/云盘明文传输**（`.gitignore` 已覆盖，迁移时不得为图省事临时提交）。
2. 传输走**物理介质或公司内部加密通道**，一次性写入 Mac Studio；写入后 `chmod 600`，属主为运行 Claude Code 的普通账户。
3. **Mac 上的 Claude Code 进程禁止以 root/sudo 运行**；工作目录限定在项目 clone 内。
4. **迁移不等于复制全部凭据**：只迁该阶段真正需要的（如仅迁机器人＝只需企微凭据 + GitHub PAT，**不需要** `.51` 门禁口令与 sa 账号）。**最小集原则，缺省不带。**
5. 迁移完成后，**笔记本侧对应凭据的处置须显式决定**（保留作回滚 / 或轮换作废），不留"两台机器都有全套凭据"的模糊态。
6. **前置联动**：队列 #91(a) 的 sa 超管口令轮换本就悬而未决（建议截止 8/1）——**若迁移会把该凭据带到第二台机器，应先完成轮换再迁**，不要把一个已知隐患复制一份。
