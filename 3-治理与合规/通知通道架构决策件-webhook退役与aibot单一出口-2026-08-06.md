# 通知通道架构决策件 · webhook 退役与 aibot 单一出口

## 〇、一句话

**群广播全部迁到 aibot、经常驻服务单一出口代发；sweep/SC8 等机制告警保留 webhook 作独立逃生通道，但逃生通道的受众收敛为「Shao Peishen ＋ IT 陈承」两人，业务部门此后不再从任何 webhook 收到消息。**

## 一、决策记录（Shao Peishen 2026-08-06）

| # | 决策 | 原话/要点 |
|---|------|-----------|
| 1 | **方案＝丙+甲组合** | 群广播经常驻服务代发迁 aibot；sweep/SC8 等告警**保留 webhook 作独立逃生通道** |
| 2 | **逃生通道受众收敛** | 「独立通道只发我和 IT 陈承，**所有业务部门不需要感受到 webhook 机制，免得他们直接给他回信**」 |
| 3 | 主工作区 reset 事故 | **暂不处理**，等 CC 端在跑的任务结束后统筹（见 §六） |

**第 2 条的分量**：它不只是"少发几个群"，而是**把 webhook 从"业务沟通渠道"降级为"纯运维逃生通道"**。理由是 webhook **单向**——群成员的回复进不到任何地方（正是队列 #270 立项时写明的"容易误导"），业务专员一旦对着 webhook 消息回信，那句话会静默消失。**两人运维群不存在这个风险，因为两人都知道它是单向的**（但陈承需要被告知一次，见 §五.3）。

## 三、为什么不能让每个调用点各自连 aibot（本决策最硬的技术约束）

**aibot 私信/群发都要长连接，而长连接受同 BotID 单实例约束。** sweep 是计划任务（每小时起一个新进程）、SC8 跑在 `.51`、`发企微.py` 是 CC 的一次性调用——**这三者若各自起连接，会把笔记本上那条常驻监听踢下线。**

**这不是推测，2026-08-06 已被真实复现**（CC `aibot-webhook-retire` 会话收工总结原话）：

> 「我做验证时开的临时 WebSocket 连接，会让主监听连接大约 **2-3 分钟后断开一次**——本次验证过程里**稳定复现了 3 次**……自动重连能恢复登录状态，但曾一度停在"**收得到心跳、收不到消息**"的僵尸态。」

**僵尸态比直接断开更危险——它看起来是活的。** 故目标态必须是**全局唯一一条 aibot 连接**。

## 四、目标态 · 通道矩阵

| 受众 | 通道 | 出口 | 变化 |
|------|------|------|------|
| **业务部门群**（财务/质量/采购/跨部门） | aibot 群 chatid | 常驻服务单一出口 | 🔄 三个 `WECOM_WEBHOOK_URL_*` **退役** |
| **Shao Peishen 本人** | aibot 私信 | 常驻服务（已在用） | ✅ 不变（`forwarding`／`cc_to_paul`／`decision_reminder`／`gap_alert` 均已在 aibot） |
| **运维逃生通道**（Shao Peishen ＋ 陈承 二人） | **webhook（保留）**，实际键名 **`WECOM_WEBHOOK_URL_OPS`**（2026-08-20 补注，见 §5.1 作废声明） | 直连，不经常驻服务 | 🔄 受众收敛；**不含任何业务部门** |

### 4.1 单一出口（甲）怎么落

常驻 `ZhuopinAibotDevListener` 已持有唯一那条 aibot 长连接 —— 让它额外监听一个 **localhost 端点**接受 `{chatid, content, attachments?}`，由它代发。

- 调用方改动极小：**把 webhook URL 换成 localhost URL，payload 结构保持兼容**
- 失败隔离沿用既有范式（`delivery.py::cc_to_paul` 的 try/except：代发失败只记 audit，不影响调用方主流程）
- **`.51` 上的 SC8 访问笔记本端点存在可达性问题** → 见 §五.2

### 4.2 逃生通道（丙）为什么必须留

**用 aibot 发"aibot 挂了"是自指矛盾。** `gap_alert.py` 这个模块的存在本身就证明了这一点——监控通道不能依赖被监控对象。今天那次踢线事故若发生在半夜，**能把它告诉你的恰恰只有 webhook**。

**⇒ 逃生通道的判据（可机械化）**：消息的**主题是"某个自动化机制自己出问题了"** → 走 webhook 运维群；**主题是业务内容** → 走 aibot。

## 六、取证基准说明（⚠️ 读错地方会得出相反结论）

**本件全部取证自 `origin/master`，不是主工作区。** 原因：主工作区磁盘内容与 git 记录不一致——`department_group_chatid_mapping.py/.yaml` 等 5 个文件**磁盘上物理不存在**、另几个测试文件**磁盘内容落后于 HEAD**（实测 `test_repo_paths.py` 磁盘 96 行 vs HEAD 155 行），`git status` 合计显示 **839 行删除**。

> **🔴 归因更正（2026-08-06，本线原判被建造端证伪，如实留痕）**：本件初版把成因写作「被 `git reset` 到旧的 origin/master 导致文件被退掉」——**该因果链不成立**。建造端用 `git ls-tree` 直接查了 reset 落点 `4a23993` 的 tree，本线复核确认：**那几个文件在 `4a23993` 的 tree 里本来就存在**（blob `7fc2fd3`），在当前 HEAD 的 tree 里是**同一个 blob**。reset 到一个含有这些文件的提交，不可能删掉它们。
>
> **真实情况＝磁盘工作区物理缺失/落后，与 git 历史无关**；更像是有其他 session/进程直接在共享主工作区目录里做了文件级操作（未经 git）。**根因仍未查明**，但不影响"内容在 git 里完好"这一结论。
>
> **我错在哪（值得记，因为它是同一形态第 3 次）**：我在 reflog 里看到 `reset:` 就把它当成因，**没有跑那条一步就能证伪它的命令**（`git ls-tree <该提交> -- <路径>`）。这与队列 #225 计数台账第 ③ 条「因果断言前先问有没有没核的变量」同族——**前两次分别由环境保障线自查与值周巡检线用 `git patch-id` 证伪，这次由建造端用 `git ls-tree` 证伪，三次都不是断言者自己发现的。**
>
> **⇒ 按 CLAUDE.md §5「规则退休制」，该条已达 3/3 阈值，须机制化或删除。** 本线建议的机制化形态（交环境保障线评估，本件不代定）：**下因果断言时，必须同时写出"如果我错了，哪一条命令会证明我错"**；写不出这条命令，说明该断言还不到可以下的时候。三次事故里证伪它们的都恰好是一条命令（`git patch-id` ／ `git ls-tree`），这不是巧合。

**本线曾因读工作区而误判"dispatch 没有任何群分支"**，实为群 cc 机制早已建成并合入 master。**教训**：当一个只读命令返回"太干净"的结果时，先问它是不是根本没读到我以为的那个对象（根 CLAUDE.md §5「工具静默回退」同族）。

**恢复路径（建造端给出，比本线初版更准确、成本更低）**：`git checkout HEAD -- <那几个路径>` 或 `git restore <路径>`，把磁盘拉回与当前 HEAD 一致即可——**HEAD 已含全部内容，不需要先 pull**；磁盘干净后再单独决定要不要 `git pull` 把 HEAD 推进到 `origin/master` 最新。两步都不丢东西。
