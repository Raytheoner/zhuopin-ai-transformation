### 根因初判回应（Paul 问：是否与财务域 API 接入混线？）

- **不是财务域代码污染**：财务三单接入（`get_purchase_lines`/`get_gr_lines`/`get_ap_lines*`）是独立新增方法，未改动 SC8 取数路径任何一行，全量回归 SC8 190 passed 零回归。
- **07-20 IT 新版 DLL 部署确有影响服务端返回内容**：审计日志显示 07-20 10:01（北京时间）左右"全成品直接子件去重总数"从 1124 升到 1131、07-21 15:57 左右 SRM 命中数从 396 跳到 456——证实服务端数据在这两个时间点确有变化，但**这类聚合计数变化不能证明/证伪某一行的瓶颈子件是否被错误标注**（快照不留历史版本，覆盖式存储，无法逆向复原姚截图那一刻的逐行数据去核对）。
- **07-20 apiKey 401 窗口（队列 #61）不会导致"半错"数据**：`/api/refresh` 是 fail-loud 设计，任一真实源报错则整次刷新失败、保留上一份好快照，不会把部分正确+部分错误的数据拼成一份快照对外展示——已读代码确认，且 07-19~07-22 审计日志显示刷新从未中断。
- **最可能的解释**：ERP 母件/BOM/预测订单状态在姚截图与本次复验之间的 ~15-20 小时内已经变化（这在真实 ERP 环境里是日常现象：BOM 被工程编辑、FO 订单被审核关闭等），并非可复现的系统性 bug。

### 已加的防御性修复（不等回灌，已实施+测试+待部署）

`BOM/Query` 响应体母件行自带 `m_itemMaster.m_code`（响应自证码），此前代码**从不核对**它与本次请求的料号是否一致——万一服务端未来在任意时点（无论何种成因）返回了错母件的数据，我方会静默信任、把错误子件挂到错误成品上，正是姚描述的症状。已加自证码校验：不符 → 该料号视为拉取失败（不静默采用），并写审计留痕（`bom_product_code_mismatch`），供未来批量核查是否复发。5 个新增单测 + 全量回归零漂移（平台 208 passed+1 skip / SC8 190+4skip / SC1 53 / SC7 41 / O2 20）。

## 二、问题 4/8/9a：现状取值字段（供口径确认）

### 口径确认① 需求量字段

- **现状代码取值**：FO API `Num` 字段，直接 `int(float(Num))`，**不做任何单位换算**（`sc8/loaders.py::parse_forecast_order_rows`）。
- **复验**：S07Y.0137（FO2026070002）当前 `Num=30.0`，看板显示 `qty=30`，两者一致；姚报告的"看板 2000 / ERP 30(套) / FO 30,000"当前无法复现（该 FO 单据 `Num` 字段当前即为 30，非 30,000）。
- **请确认**：□ `Num` 就是应采信的需求数量字段，单位以 FO 返回值为准，不需要换算　□ 需要按某种单位换算（请说明换算规则/依据字段）

### 口径确认② 需求日字段

- **现状代码取值**：FO API `ShipPlanDate` 字段，取其 `YYYY-MM-DD` 部分，**不做时区处理**（原始值本身是不带时区的日期时间字符串）。
- **复验**：S07Y.0137 当前 `ShipPlanDate=2026-07-20T00:00:00`，看板显示 `计划出货日=2026-07-20`，一致。
- **请确认**：□ `ShipPlanDate`（计划出货日期）就是应采信的需求日字段　□ 应采用其他字段（请指出 ERP 界面对应的字段名）

### 口径确认③ 客户名字段

- **现状代码取值**：FO API `CustomerName` 字段，**直接透传，代码无任何转换/映射逻辑**（`sc8/loaders.py`）。
- **F02N.0040 当前无有效 FO 订单**，无法直接复核该具体案例；但代码逻辑上，客户名完全来自 FO 单据自带字段，如与真实订货客户不符，根因在 **FO（预测订单）本身的客户字段与实际销售订单客户不是同一数据源**（预测订单是计划性文档，可能按内部规划维度归类客户，与最终实际接单客户存在偏差）。
- **请确认**：
  - □ 一成品同时对应多个真实客户时，看板显示规则 = **并列**列出全部客户
  - □ 一成品同时对应多个真实客户时，看板显示规则 = 只显示**主客户**（需定义"主客户"判定规则）
  - □ 其他（请说明）
