# IT/SRM 评估请求 · 采购提前期(L/T) 数据源

## 背景

SC8 保供看板的"追料"判断逻辑需要每个物料的**采购提前期（Lead Time，以下简称 L/T）**：当"需求日 − 今天 < 该物料 L/T"时才升级为紧急追料，避免过早打扰（L/T 内本来就该在途）或过晚提醒（临期才追、来不及协调）。

## 现状缺口

现有 ERP（U9C）/SRM（携客云）取数链路都还没有接到这个字段。当前兜底口径 = **净需求 > 0 即视为需要追料**（不区分远近，不精确，但不阻塞现有功能——保供看板照常运行，只是这一条判断粒度较粗）。

## 已定技术路线（2026-07-14）

采购部姚祖怡与 Paul 确认：走 **"IT/SRM 自动取数"** 路线（不做"人工可编辑字段"的替代方案）——即由 IT/SRM 侧数据源自动提供，不需要采购/PMC 手工逐条维护。

## 请评估/确认以下问题

1. **U9C 物料主数据**（与 `BOM/Query` 同类的物料主数据实体，如 ItemMaster）是否已有"采购提前期"字段？字段名是什么？
2. **携客云 SRM** 侧是否有等价字段（如供应商承诺的标准交期/Lead Time）？
3. 该数据由谁维护（PMC / 采购 / 供应商自报）？数据质量如何——是否普遍填写，还是大量空值/缺失？
4. 取数接口：走哪个 API？是否需要新增端点，还是现有物料主数据接口顺带返回即可？

## 优先级说明

不阻塞现有交付——SC8 保供看板已上线且运行正常，本项是"追料判断"精度的后续提升项，无特定截止日期压力。希望 IT/SRM 侧评估后给个结论（有/没有该字段、大致工作量），采购域再据此排期。

## 回复方式

回复给 Paul 即可，采购域侧后续跟进。

## IT 回复（2026-07-15，经 Paul 转达）

逐题对应：

1. **U9C 物料主数据是否有采购提前期字段？** 有，字段名 `PurProcessLT`（标准提前期），但**该值在 ERP 内部不可用于 MRP 运算**——MRP 要求按实际交期而非标准交期，IT 未展开说明是否也不适合我们这类"追料预警粒度"的用途，需谨慎对待（非高置信数据源）。
2. **携客云 SRM 是否有等价字段？** 有——SRM **核价单**上的"承诺交期"字段，语义即物料标准交期/Lead Time，与我们要的口径吻合。
3. **数据由谁维护、质量如何？** 目前**无有效维护，大量空缺**。计划改为供应商在核价单/询价单环节必填，**从今天（2026-07-15）起该字段设为供应商必填项**。
4. **取数接口/工作量？** **现状无合适 API 可走**（因为底层数据本身大量缺失，接了也读不到东西）。计划先把各物料标准交期填齐，才能从 SRM 核价单读取；覆盖率目标 **2027-03 达到 ≥95%**（当前基本是 0）。

## 结论与影响（2026-07-15，CC 登记）

- **"自动取数"路线（07-14 定案）方向不变，但近期不可行**：数据源（SRM 核价单承诺交期）现在基本是空的，没有可读的 API 落点；IT 给出的时间表是从今天起强制供应商必填，预计约 **8 个月后（2027-03）** 才能到 95% 覆盖率。
- **A2「追料 L/T 闸」的现状兜底（净需求>0 即追）需要长期维持**，不是临时过渡，是接下来大半年的实际运行状态——这一点已在 `shortage-baoguan-criteria-v3` 的实现与 spec 里如实记录（"L/T 数据源现状缺失，此兜底即当前实际行为"），无需改动代码，只是确认这个"缺口"的持续时间比原先设想的更长。
- **`PurProcessLT` 字段不建议采用**：IT 明确说明其内部不适用于按实际交期运算的场景，贸然接入可能引入一个"看似有值、实则不可信"的数据源，比"明确没有、走兜底"更危险（兜底口径至少是显式、可追溯的保守判断）。
- **不阻塞任何现有交付**（本项原本就非阻塞项，SC8 保供看板照常运行）。
- **建议排期节点**：2027-Q1 前后（覆盖率临近 95% 目标时）由采购域主动跟进核实覆盖率是否达标，再评估是否正式接入；不建议现在设自动提醒，避免过早打扰 IT（他们的计划本身就要到 2027-03）。
