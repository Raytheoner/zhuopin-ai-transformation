## 二、端点 A 为什么必须做：三个硬编码常量正在污染真实建议

**不是「缺个字段不好看」，是三条业务结论现在都是编的。** 取证位置＝
`5-平台底座/zhuopin_platform/zhuopin_platform/shared_tools/erp_connector/connector.py::get_suppliers()`
—— 该函数从 `ZpViewPurOrder/Query` 聚合供应商，其中三个字段是**写死的常量**：

```python
moq=           1,
mpq=           1,
lead_time_days=30,
is_approved=   True,
```

**逐条看它污染了什么**：

| 常量 | 下游算式 | 实际后果 |
|---|---|---|
| `moq=1, mpq=1` | `calc_purchase_qty` ＝ `max(ceil(缺口 / MPQ) × MPQ, MOQ)` | 代入 1 之后 ⇒ **建议采购量 ≡ 缺口本身**，完全不做起订量与包装倍数取整。⇒ 系统给出的每一个采购建议量，**真下单时都得被人重新凑整一次**，工具等于没算这一步 |
| `lead_time_days=30` | `calc_order_date` ＝ `计划生产日 − 提前期 − 3 天安全期` | **所有物料一律按 30 天**，不分是 2 天的通用件还是 90 天的车规芯片。⇒ **「最迟下单日」这个字段对短周期料过度提前、对长周期料严重滞后**，而它正是采购同事拿来排优先级的那一列 |
| `is_approved=True` | `select_supplier` ＝「**已认证**供应商中选单价最低者」 | 恒真 ⇒ **那道「已认证」过滤从来没有生效过**。⇒ 系统可能把未认证供应商推荐出来。**这一条是合规向的**，在 IATF 体系下尤其经不起审 |

🔑 **⇒ 端点 A 的价值不是「多三个字段」，是让这三条算式第一次真的成立。**

## 三、端点 A 字段清单（`/zp/api/PurPriceList/Query`）

**一行 ＝ 一个「供应商 × 料号」的价目条目。**

### 3.1 必需字段（缺任一条，该端点对我方无用）

| 字段 | 说明 | 我方怎么用 |
|---|---|---|
| `SupplierCode` | 供应商编码 | 与既有 `ZpViewPurOrder` 的 `supplyCode` 对齐，**须同源同值**（否则 join 不上） |
| `ItemCode` | 料号 | 同上，与 `itemCode` 对齐 |
| `MOQ` | 最小起订量 | 采购建议量取整 |
| `MPQ` | 最小包装量／包装倍数 | 同上 |
| `LeadTimeDays` | 采购提前期（**天**） | 最迟下单日 |
| `IsApproved` | 该供应商对该料号**是否已认证／合格** | 供应商筛选（当前恒真的那道门） |

### 3.2 强烈建议一并给（不给也能跑，但会退化）

| 字段 | 说明 |
|---|---|
| `SupplierName` | 供应商名称——只有编码的话，报表和给采购看的界面都要再查一次 |
| `UnitPrice` | 价目表单价。🔴 **请注明是含税还是未税**——我方既有 `finallyPriceTC` 的含未税口径已踩过一次坑（FI2 面板曾把两列写反） |
| `Currency` | 币种。外币供应商我方已有单独规则（FI2 R7 过渡规则），不能默认人民币 |
| `EffectiveDate` / `ExpireDate` | 价目有效期。**若同一供应商×料号存在多版本，我方需要按「`EffectiveDate ≤ 查询日 < ExpireDate`」选当前生效版**——这套判法我方在 BOM 上已经实现过（`_select_current_bom_version`），照搬即可，但**前提是接口把这两个日期给出来** |
| `IsPrimary` | 是否首选／主供应商（若 U9C 侧有这个概念）。有的话我方可以直接用，没有就退回「认证供应商中选单价最低」 |

### 3.3 过滤参数

`itemCode`（**支持多值**，逗号分隔或重复传参，我方常一次查几百个料号）／`supplierCode`／`effectiveOn`（按该日期取当时生效的版本，缺省＝今天）／`page`／`pageSize`

## 四、端点 B 字段清单（`/zp/api/MO/Query`）

**一行 ＝ 一张生产工单**（若 U9C 侧工单有行结构，请**按行返回并带行号**，理由见 §五.1）。

### 4.1 必需字段

| 字段 | 说明 | 我方怎么用 |
|---|---|---|
| `DocNo` | 工单号 | 主键、审计留痕 |
| `ItemCode` / `ItemName` | 产出品料号／名称 | 与 BOM、FO 对齐 |
| `PlanQty` | 计划产量 | 排程 |
| `CompletedQty` | 已完工数量 | 在制进度、FI1 完工对账 |
| `PlanStartDate` / `PlanEndDate` | 计划开工／完工日 | 排程基线 |
| 🔴 `ActualStartDate` / `ActualEndDate` | **实际**开工／完工日 | **这两个是 O1 的核心**——O1 要从**历史工单反推真实工时**（现在 SMT 工时全是 mock）。没有实际起止日期，O1 只能继续用估的工时，晋档无从谈起 |
| `Status` | 单据状态（并请给出取值字典：哪个值＝已审核／已完工／已关闭） | 过滤 |
| 🔴 `LineStatus` | **行级状态**（若工单有行） | 见 §五.1，这是我方吃过两次亏的地方 |

### 4.2 建议一并给

`WorkshopCode` / `LineCode`（车间／产线——排程要按产线排，只有工单没有产线就排不了）、`OrgCode`（组织）、`CreateDate`（下单日）、`BomVersion`（该工单用的 BOM 版本，与我方 BOM 版本选择逻辑对齐）

### 4.3 过滤参数

`docNo`／`itemCode`（多值）／`dateFrom`、`dateTo`／`status`／`workshopCode`／`page`／`pageSize`

🔴 **`dateFrom`／`dateTo` 请在文档里写明它过滤的是哪一个日期字段**（`PlanStartDate`？`ActualStartDate`？`CreateDate`？）——理由见 §五.2，这一条我方刚在另一个端点上被咬过。

## 五、四条通用要求 —— 每一条都来自我方真实踩过的坑，不是想象

### 5.1 🔴 行级状态字段请一次给到位

**这是同一个坑的第三次**：

- `ForecastOrder/Query` 最初只有**单据头** `Status`。我方据此写了「传 `status=2` 即可剔除关闭行」的过滤，**跑了一个多月**，直到 2026-07-28 用两个真实案例（`FO2026070001` 行 60 / 行 230，U9C 界面上明明是「关闭」）才证伪——**那 90 行的 `Status` 恒为 2，一个例外都没有**。IT 于 07-30 补了行级 `LineStatus`（2＝核准／3＝关闭）才解决。
- `Purchase/Query` 同样：我方一度只能用「365 天回溯窗口」这种折衷去猜哪些 PO 行已关闭，直到 07-30 补了行级 `LineStatus`（3／4／5）。

⇒ **若 MO 在 U9C 里是有行的，请按行返回、带行号与行级状态。** 头状态解决不了行的问题，而我方在拿到数据之前**无法判断**这两者会不会不一致——两次都是上线之后才发现的。

### 5.2 🔴 日期过滤参数，请写明过滤的是哪个日期字段、以及该字段为空时会怎样

**真实案例**：`AP/Query` 的 `dateFrom`/`dateTo` 过滤的是 `AccrueDate`＝**立账日期**，而**未立账的单据这个字段很可能是空的** ⇒ 用它去筛「未立账应付单」会把要找的单**全部排除，且返回 0 行、不报错**。我方是在设计评审阶段推演出来的，差一点就照着实现了。

⇒ MO 同理：一张**尚未开工**的工单，`ActualStartDate` 必然为空。**若日期过滤挂在实际日期上，就会把所有待开工工单静默过滤掉——而那恰恰是排程最需要的一批。**

### 5.3 🔴 参数不合法请报错，不要静默返回全表

**真实案例**：`POChange/Query` 传错 `PODocNo` **不报错**，静默返回全表。这类行为最难查——**返回值完全正常，结论却是反的**。

⇒ 新端点请遵循：**无法识别的参数 ⇒ 明确报错**；查不到 ⇒ 返回空集合并标明，**不要返回全表，也不要返回 200 空 body**。

### 5.4 形态与既有 `/zp/api/*` 完全一致，不要新造一套

沿用现有六个端点的既有约定即可：

- `GET`，鉴权用 **apiKey 走 URL query**（非 OAuth2）
- 响应体 `Data.Rows`，字段 **PascalCase**
- 分页 `page` / `pageSize`，响应带总行数
- Swagger 挂 `/zp/swagger/ui/index`

**我方连接器已按这套范式写好，新端点接进来只是加两个方法，不需要改架构。**
