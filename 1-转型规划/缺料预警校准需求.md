# 缺料预警校准需求（P0）

> **一句话**：缺料预警把"卓品有货、引擎看不见"的子件误判成缺料、推成追料对象。根因是**喂给引擎的库存快照覆盖不全 / 料号口径对不上**（不是算法错）。本需求定义"什么才算真缺料"的业务口径，并要求 CC 在引擎里加 **fail-loud 护栏**（快照缺失→不静默判缺料、显式告警），再补数据，真实回归到误判清零。
>
> **分工**：本文 Cowork 出口径 + 需求；CC 在 LAN 改代码、连真实库、跑回归。Cowork 不碰代码、不连库。

---

## 1. 现象（采购专员手工核对发现）

跑出的物料瓶颈子件里，**部分子件卓品库存充足、既无在途 PO 也无请购**，却被判缺料、列入追料清单。不需要追的料变成追料目标，预警失真——这直接动摇采购 AI 的可信度，是采购域 P0，优先于一切新部署。

## 2. 根因（已对真实代码确认，待 CC 在真实数据上落实）

引擎 `calc_shortage()` 现有逻辑：

```
可用量 = 当前库存 − 安全库存 + 在途未到货（qty_ordered − qty_received）   # 物料在库存快照中
缺口   = max(毛需求 − 可用量, 0)
B6 特例：物料【不在库存快照】时，可用量 = 在途（只算 PO，缺快照不再忽略）
```

问题出在 **B6 特例**：一个子件若**没进引擎读到的库存快照、又没有在途 PO**，可用量被算成 `0`，毛需求一减就报假缺口——哪怕仓里实物一大堆。代码现状：这类子件**既被记进 `missing_snapshot` 告警清单、又同时落进 `shortages` 缺料集合**，于是下游把它当确定缺料追了。

**关键确认**：源码注释明确 `ZpConnector.get_inventory` 真实切换后该路径"必踩"——即真实库存接口尚未把全仓真实库存喂进快照前，**大量子件都会落进"缺快照"分支**。所以这**大概率是数据覆盖问题**（库存快照没覆盖全仓 / SRM·BOM 料号 ↔ ERP 库存料号编码对不上 / 快照状态过滤把可用库存排掉了），引擎逻辑只需补一道"缺快照不当缺料"的护栏。

## 3. "真缺料"业务口径（定稿 v0.1）

> **净需求 = 毛需求 − 现有可用库存；净需求 > 0 才算缺料、才进追料集合。**

| 要素 | 口径 | 说明 |
|------|------|------|
| 毛需求 | BOM 展开 × 生产计划量 ×(1+损耗率) | 须由**真实订单驱动**（FO/SO 经 BOM 展开）。无真实订单驱动的子件，毛需求不应 > 0（见 §5 步4 副检） |
| 现有可用库存 | **现货 + 在途 − 安全库存** | Paul 2026-06-29 拍板口径（§6 决策三） |
| └ 现货 | 全仓现有库存 | **必须覆盖全部仓库**，状态过滤不得把可用库存误排 |
| └ 在途 | 已下 PO 未到货 = qty_ordered − qty_received | **仅计已下 PO**；已批准未下单的请购**暂不计入**（口径偏保守，追料偏早） |
| └ 安全库存 | 按料设定值，**从可用量中扣减** | 保护缓冲；安全库存偏高会压低可用量、放大缺口，专员复核各料设定是否合理 |
| 判定 | 净需求 > 0 → 真缺料；≤ 0 → 不缺、不追 | 库存够、或无真实订单驱动的子件，**一律不进追料集合**，无论有无在途 |

## 4. 改判定要求（交 CC，Paul 决策二＝数据补全 + fail-loud）

**A. 逻辑侧 —— 缺快照 fail-loud，不静默判缺料**

引擎须区分两种"可用量低"的情形，不再混为一谈：

1. **快照内·真零库存**（料号在快照、current_stock 据实为 0/不足）→ 按 §3 口径正常参与缺料判定，净需求 > 0 即真缺料。
2. **快照缺失·无法判定**（料号不在库存快照 = 现有 `inv is None` 分支）→ **不得**默认可用量=0 后落进 `shortages` 当确定缺料；改为：
   - 移出"确定缺料/追料"集合；
   - 单列"待核实——库存快照缺失"清单（沿用并强化现有 `missing_snapshot`）；
   - **fail-loud 显式告警**"库存快照覆盖不全，N 个子件无法判定缺料"，提示数据侧补全后重判；
   - 该清单**不混入**对采购员展示的追料清单。

> 即：把当前"缺快照→可用量0→进 shortages"的旁路，改成"缺快照→进待核实清单 + 告警，不进 shortages"。消费方（O2 齐套清单 / SC8 保供看板）相应分区展示：**确定缺料** vs **待核实(快照缺失)**。

**B. 数据侧 —— 补全快照覆盖 + 料号映射对齐**（治本，与逻辑护栏并行）

1. **库存快照全仓覆盖**：`get_inventory` 真实取数须覆盖全部相关仓库，状态过滤口径正确（在用/可用库存不被排除）。
2. **三方料号映射对齐**：SRM 物料需求/到位反馈 ↔ BOM 子件料号 ↔ ERP 库存料号编码，统一映射主键；消除"实物有货但料号对不上→落进缺快照分支"。
3. 数据补全后，原误判子件应落回"快照内"分支，净需求按 §3 算出 ≤ 0、退出追料集合。

> A 是护栏（先止血、立即让误判不外泄），B 是治本（让缺快照清单逐步清零）。两者都要。

## 5. 排查步骤（谁干什么）

| 步 | 查什么 | 谁 | 产出 |
|:-:|--------|----|------|
| 1 | 把误判的瓶颈子件清单 vs 引擎 `missing_snapshot`（不在快照的料）对一遍——验证是否全落在里面 | CC | 重合率（预期≈100%）|
| 2 | 这些子件库存口径定位：是**仓库范围漏**（某仓未纳入快照）/ **料号映射不一致**（SRM·BOM vs ERP 编码）/ **状态过滤误排**？ | 专员 + CC + IT | 根因归类 + 修复项 |
| 3 | 实施 §4-A 逻辑护栏（缺快照→待核实+告警，不进 shortages）| CC | 改后引擎 + 测试 |

| 5 | §4-B 数据补全（全仓覆盖 + 料号映射）→ 真实数据重跑 | CC + IT | 误判清零回归 |

## 6. 决策记录（Paul 2026-06-29）

1. **本次范围**：仅 P0 缺料预警校准需求（本文）+ 采购域专线接力文件；SC3/SC5/O2 部署规则、SC1/SC8 价值验收下次。
2. **快照缺失处理**＝**数据补全 + fail-loud**：补快照覆盖/料号映射，且子件快照缺失时引擎显式告警"覆盖不全"、不静默判缺料（与项目 fail-loud 家风一致）。
3. **可用库存口径**＝**现货 + 在途 − 安全库存**（在途=已下 PO 未到货；已批请购暂不计入；安全库存扣减）。

## 7. 验收标准（CC 真实数据回归）

- 之前被误判的子件（卓品有货/无真实净缺口）**全部退出**确定缺料·追料集合，误判清零。
- 库存快照缺失的子件**不再混入**追料清单，而是落"待核实(快照缺失)"清单并触发 fail-loud 告警（数量可见、可追）。
- "确定缺料"集合内每一项，**净需求(现货+在途−安全) > 0** 经手工抽验成立。
- 既有黄金基准不漂移（SC5 35850 / 640000 / 675850 等），平台 / O2 / SC5 / SC8 回归全绿。
- 所有判定结果写平台 `audit`（可追溯）。
