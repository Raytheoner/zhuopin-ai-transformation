## 1. 场景与范围

- **场景**：项目经理提交开发类立项申请书 → 数字人对照规则逐项预审 → 出**立项审核报告**（合格/有条件合格/不合格 + 逐项偏差 + 修改建议）→ 评审委员会/PMO 复核确认（L2）。
- **MVP 范围（Paul 2026-06-27 定）**：**只做开发类 `EQQR8082` A2.1**（有真实试评闭环）。**研发类 `EQQR8106` A3 规则书已备好但二期再做**，本期不实现。
- **自动化等级**：L2 —— AI 出预审报告，**立项决策权在评审委员会/PMO**，AI 结论非终局（PRD D1 红线）。
- **落位**：`4-数字员工/质量部/QD-B-立项审核门禁/`，`pip install -e` 平台底座（PRD §6 D6 工程结构）。

## 3. 82 条规则按"自动化可实现度"分三类（实现优先级）

> 这是本交接包对 design 最关键的加工：把 82 条按 J 列拆成三类，明确各类的实现方式与难度。

### A 类 · 可机器核（68 条，确定性，先实现、是 MVP 主体）
必填/格式/日期逻辑/数值计算勾稽/跨模块一致性。判定确定、可解释、可单测，**直接转译为规则函数**。例：
- 完整性：项目名称/经理/客户/事业部/等级/类型非空（阻断）。
- 日期逻辑：结束日期 > 开始日期；计划关闭日期 ≥ 应对日期。
- 计算勾稽：利润 F=D−E；折旧⑦=②×15%；小计⑩=Σ(②~⑨)；月净现金流=收入−支出；风险系数=严重度×频率。
- 一致性：人员安排合计=预算总工时；现金流各列汇总=模块九预算基准；收入依据合计=成本效益收入 D。
- 合规阈值：收益指标技术服务类 D/E≥1.5、产品类 (D+M)/E≥5；委外占比≤80%。

**实现建议**：每条一个纯函数 + mock 夹具单测（先测后实现，SuperPowers 纪律）。这 68 条是"零语义歧义"的，最该先吃下。

### B 类 · 半自动（10 条，需 LLM 语义判断，design 必须补判定准则）
靠语义理解，**G 列给了"要满足什么"但没给"AI 怎么判 / 判不准怎么办"**——这是 design 待收口项（§6-2）。清单：

| 规则ID | 检查项 | 语义判断点 |
|:---:|------|------|
| 20 | 立项依据是否说明产品"是什么" | 是否含产品定义/功能描述 |
| 21 | 立项依据是否说明产品"什么用途" | 是否含应用场景/用途 |
| 23 | 是否说明项目"目的" | 目的陈述是否存在 |
| 24 | 是否说明项目"意义" | 意义陈述是否存在 |
| 26 | 项目目标是否分类 | 是否按技术/成本/进度/质量分类 |
| 27 | 指标是否量化 | 是否含具体数值+单位 |
| 28 | 交付物与指标是否对应 | 交付物-考核指标逻辑关联 |
| 77 | 职责与人员安排对应 | 人员分类在职责中是否有对应 |
| 78 | 技术总结 | 是否涵盖方案/方式/风险 |
| 79 | 商务总结 | 是否涵盖合同/客户/收入/市场 |

**实现建议**：每条配明确 LLM 提示词 + 判定输出 schema（命中/未命中 + 证据片段 + 二级置信度，对齐 SC8 高/低口径）；**低置信默认标"需人工复核"不擅断**；严重度按 J 列保留（如 26/27 是阻断、77/78/79 是一般/提示）。

### C 类 · 转人工（4 条，AI 只验"在/不在"，不下结论）
| 规则ID | 检查项 | AI 角色 |
|:---:|------|------|
| 42 | 应对措施有效性 | AI 提示，最终人工判 |
| 80 | 项目经理签字及日期 | AI 验签字栏是否填，签字真伪人工 |
| 81 | 事业部总经理签字及日期 | 同上 |
| 82 | 立项决议 | 申请阶段不判（立项会后人工填） |

## 4. 合格判定逻辑（输出契约核心）

三档（采纳规则书封面阈值）：

| 结论 | 判定 | 处理建议 |
|------|------|---------|
| ❌ 不合格 | 存在任意"错误/阻断"项 **或** 得分<60 | 退回修改 |
| ⚠ 有条件合格 | 无错误项 **且** 60≤得分<80 | 补充/修正后重提 |
| ✅ 合格 | 无错误项 **且** 得分≥80 | 进入立项决议流程 |

> **⚠ design 必读**：见 §6-1，**评分细则（82 条各占几分）尚未定义**。没有分值，"得分"维度无法算，**"有条件合格"这一档产不出来，三档会塌成两档（有错误=不合格 / 无错误=合格）**。MVP 起步先用"错误项一票否决 + 警告/提示计数"的两档输出，评分制待业务方定后增量接入。

## 5. 跨模块一致性校验（C01–C10，必含）

C01 人员一致性（偏差>10%警告）｜C02 开发成本一致性（>10%警告）｜C03 收入一致性（>10%警告）｜C04 时间一致性（不一致警告）｜C05 风险-里程碑对应（不存在→错误）｜C06 ASIL-功能安全（ASIL≠NA 但模块四无功能安全目标→错误）｜C07 ISO21434-信息安全（→错误）｜C08 预算工时-里程碑（>10%警告）｜C09 收益计算自洽（毛利率=F/D，不符→错误）｜C10 全生命周期毛利率=P/(D+J)（不符→错误）。

> C06/C07 是合规强关联（功能安全/信息安全），属阻断级；C 类校验在试评里大多未被技术服务类样本触发，需产品类样本补验（见 §7）。

## 6. design 阶段必须收口的三处（apply 前的停审点）

**🔴 收口-1：评分扣分细则。** 82 条各占几分、扣分还是加分制——**Paul 已定交质量部/PMO 定，非 AI 预设**。design 写清楚：① MVP 先两档（错误项一票否决）；② 评分制作为可插拔模块，业务方给出权重表后接入，不阻塞首版。

**🔴 收口-2：10 条半自动规则的判定准则。** 为 §3-B 每条补 LLM 提示词 + 输出 schema + 置信度 + 低置信转人工策略。需陈忱（质量业务视角）确认"什么程度算说清了'产品是什么'"等业务判据。

**🔴 收口-3：产品类规则的真实样本验证。** 现唯一试评样本是技术服务类，产品类专属规则（量产数据 G/H/I/J/K、全生命周期毛利率、产品类收益指标≥5、C01–C03 部分）**写了但没跑过真实数据**。需补 ≥1 份产品类立项书做试评/黄金基准（陈忱补样本，见工作安排信）。

## 7. 工程风险提示（design 要正面回应）

- **doc_parser 解析可靠性 = 最大工程未知数**：立项书是**合并单元格的 Excel 表单**（A1:Z145、大量 merge），不是干净表格。82 规则假设字段可定位，但"能否稳定从这种表单解析出每个字段值"未经验证。**建议 design 第一刀就做解析探针**：先对 A2.1 模板 + 几份真实填写件验证字段抽取准确率，再谈规则判定。doc_parser 是质量域共性件，QD-A（8D）为第 1 消费方、QD-B 为第 2，**按 rule-of-three 提升进 `shared_tools`**（提升前查实际代码确认真复用，沿用供应链纪律）。
- **模板版本耦合**：取数来源是按章节定位的，但模板一个月内改了 A0→A1→A2→A2.1 四版。**取数锚"章节标题文本"而非绝对单元格坐标**，抗改版；并记录适配的模板版本号。

## 8. 平台底座衔接（复用，不重建，CLAUDE.md §4）

- **audit/**：每份审核报告（AI 预审结论 + 复核 + 最终判定）写 append-only，关联立项文档版本 ID（IATF 8.3 可追溯）。
- **L2 门禁（SC8 模板）**：AI 不自动判"通过/退回"为终局，评审委员会/PMO 确认才生效；规则重大调整走黄金基准回归。
- **data_isolation_layer/**：立项文档默认内部库、不强加 OEM 路由；**例外**：若附件含特定 OEM 技术方案/报价，标记后走隔离层（PRD §5）。
- **doc_parser**：见 §7。

## 9. 黄金基准约定（仿 SC8）

- 取历史已结案立项书，AI 重跑 vs 当年评审结论逐项对比。
- **覆盖**：技术服务类（已有华丰 1 份）+ **产品类 ≥1 份（待补，收口-3）**；含"有条件合格""不合格"各 ≥1。
- **通过标准**：确定性部分（A 类 68 条）零偏差；半自动部分（B 类）命中与人工一致率达约定阈值（MVP 80%）。
- **沉淀**：存 `data/golden/`，作回归基准；真实样本自包含、脱敏后入（立项数据脱敏要求低于 8D，但含 OEM 报价的附件仍需脱敏）。

## 10. 输出契约（审核报告结构）

参考已产出的 `EQQR10011立项申请书审核报告.docx` 结构，建议字段：① 总判定（三档）② 阻断项清单 ③ 警告/提示清单（逐条：规则ID/章节/检查项/判定/证据/修改建议）④ 跨模块校验结果 ⑤ 转人工待办项 ⑥ 审计元数据（模板版本/规则版本/时间戳）。**报告标"AI 预审建议，决策在评审委员会"。**
