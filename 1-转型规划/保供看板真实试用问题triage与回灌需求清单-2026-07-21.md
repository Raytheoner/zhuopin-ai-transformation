# 保供看板 11 问题 triage(2026-07-21)

> 一句话:**11 条分三类——取数/映射类疑似 bug 6 条(🔴P0,我方取证修复,不需要采购等)、功能需求 4 条(采购圈选优先级)、判据澄清 2 条(我方出说明+采购确认口径)。姚祖怡团队这轮试用质量很高:条条有截图、有 ERP 对照值,正是灰度想要的效果。**

## 〇、根因初判(Paul 问:是否与财务域 API 接入混了?)

**初判:财务域代码直接污染采购取数的可能性低,更可疑的是 IT 侧服务端变更与 401 窗口坏数据——待 #66 取证定论。** 依据:

1. **代码侧隔离**:FI2 接入是新增方法(`get_ap_lines_by_supplier` 等)与独立场景目录,未改 SC8 取数路径;每次合入全量回归 SC8 190 passed、黄金基准不漂移。静态看不出污染路径。
2. **但服务端同期变过两次(更可疑)**:①IT 07-20 部署**新版 DLL**(apiKey 改读 Web.config,同批还"顺带"修了 AP 批量 SQL bug)——服务端行为变更完全可能波及 FO/BOM/Stock 等其他端点的返回语义;②07-20 有 **apiKey 401 全失效窗口**(#61),窗口内若跑过 `/api/refresh`,库存/SRM 取数失败或回落,可能产出坏快照。
3. **强信号**:问题 2 的 R01A.0061 正是 07-14 净额开关翻 ON 时验证"不再误报"的样板料,如今复发误报——强烈指向**库存 feed(Stock/Query)在某个时点断供或语义变化**,而非引擎逻辑回退。
4. 问题 1/6 的"瓶颈子件张冠李戴/ERP 无此料号"则更像**成品↔子件关联错位或 BOM 版本/替代料展开残留**,与财务域无关,单独取证。
