## 一、#197（P0，主件）— 编辑锁 `acquire` 是 check-then-act，非原子

**缺陷**（2026-08-01 环境保障线只读审计取证）：
`0-学习与工具/工具-共享文档编辑锁.py::cmd_acquire` 的实现是
`existing = _read_lock(lock_path)` 判断无锁 → 随后 `lock_path.write_text(...)` 写入。
**两步之间存在窗口**：两个进程可同时读到"无锁"、双双写入成功，**后写者覆盖前写者，两边都认为自己持锁**。全文**无 `O_EXCL`**。

**为什么是 P0（Shao Peishen 2026-08-01 拍板插队第一位，理由其本人采纳）**：
- #192 三件套修的是"消息可能滞留几小时"＝**丢时效**；本行修的是"锁可能失效导致内容被覆盖"＝**丢内容**。
- **本行是其余所有队列纪律的地基**——协议〇.7/〇.8、批次登记、机器人写入、queue-audit 全部建立在"锁可靠"这个假设上。
- **依赖它的场景已不止队列一处**：2026-08-02 实证，某 CC session 用 `--file` 对 `CLAUDE.md` 取了共享编辑锁并**真实挡下一次并发撞车**——锁的适用面在扩大，地基却还没夯实。

**修法（改动极小，约 20 行 + 单测）**：
1. `acquire` 改用 `os.open(path, os.O_CREAT | os.O_EXCL | os.O_WRONLY)` 一步完成"不存在才创建"，由 OS 保证原子性；`FileExistsError` 即视为已被占用。
2. **写后回读校验**：写完再读一次，确认 `who`/`note`/时间戳确为本进程所写——**不信"写成功了"**（CLAUDE.md §5 既有纪律）。
3. **保留既有的 30 分钟陈旧自动接管逻辑**，但接管路径同样要原子化（否则窗口只是从 acquire 移到接管）。
4. **并发单测**：用真实多进程（非 mock）并发抢锁 N 次，断言**恰好一个成功**；建议再补一个"陈旧锁被两个进程同时接管"的用例。

**红线**：
- **不得改变现有 CLI 语义与退出码**（占用中返回非 0 是既有约定，多处消费方依赖）。
- `release` 现为"改写为释放标记、不删除文件"（2026-07-27 为沙箱兼容所改），**保持不变**。
- `--reserve N --section 一/四` 的取号逻辑（#163）**本次不动**，#185 双 section 是另一行。
