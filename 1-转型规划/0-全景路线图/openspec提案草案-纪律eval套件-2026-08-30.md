## §2 Why（为什么做）

**规则退休制是人守，而"能不能退"这个判断今天没有任何依据可依。**

- 守卫代码实测 **4822 行只增不减**（`#308`）；
- 规则退休制（"人守条目被违反 3 次即须机制化或删除"）本身是人守，违反计数落在队列行内；
- **删一条规则之后，没有任何东西会告诉你哪里塌了** ⇒ 唯一安全的操作永远是"再加一条" ⇒ 注意力预算被持续挤占，而注意力正是需求管理最缺的东西。

**eval 补的就是这一格**：它让"把某条人守规则降为一行指针，或直接删掉"这个动作**第一次变得可检验**。

🔴 **它与 hook／lint 不是重复建设，管的是不同的失败模式**（本包最容易被误解的一点，先说清）：

| | hook ／ lint | eval |
|---|---|---|
| 守的对象 | **产物**——写出来的文件里有没有违规字样 | **行为**——agent 在给定情境下会不会做出正确判断 |
| 触发时机 | 写入当刻拦截 | 配置变更（`CLAUDE.md`／`.claude/**`）时回归 |
| 判定性质 | 确定性 | 概率性，须多次采样看方差 |
| 能力边界 | **只能守正则表达得出来的那一部分** | 守边界情形与语义判断 |

**证据不是推理，是哨兵自己写的**：H4 代词哨兵的判据自陈——「判定限『**同一段落内出现名录人名，且其后最近的第三人称代词与名录不符**』这一形态」「名录外人物不触发」「**判据宁可漏报也不误报**」。⇒ **它有意留下一大片漏报区，那片区域今天没有任何东西在守。** 那就是 eval 的辖区。

## §3 What Changes（改什么）

**新增：**

- `evals/evals.json` —— 一期 3 条（第 5／6／7 条），每条含：冻结情境（prompt ＋ 必要的输入文件）、期望行为、判分断言。
- CI 集成：`CLAUDE.md` 或 `.claude/**` 变更时触发 ＋ 每日定时（与手册 `agent-evals.yml` 同构）。
- 报告产物落 `reports/`。

**🔴 明确不做的两件：**

1. **不自建 eval harness。** 环境里已有现成的：`skill-creator` 带 `scripts/run_eval.py`／`run_loop.py`／`aggregate_benchmark.py`／`generate_report.py`、`agents/grader.md` 判分 agent、`evals/evals.json` schema、`eval-viewer/`。**一期直接复用，只写 eval 内容不写跑法。**

2. **不改任何既有 hook／lint。** 本包只**观测**它们，不动它们。

## §3bis 一期三条 eval · 题目全文（2026-08-30 补，供 design 审逐条过）

> **格式取自 `skill-creator/references/schemas.md` 的 `evals.json`**（实读，非杜撰）。
> 🔴 **每题的设计要点是「诱饵」**——情境必须让错误做法看起来更省事、更自然。**一道没有诱饵的题，agent 照着规则背一遍就能过，等于没考。**
> 每题附「**注入回归**」一行：摘掉哪句话，这题必须变红。这是晋档 2 第 3 条的操作依据。

### eval-5 · 退出码只认被执行进程自己那一层

```json
{
  "id": 5,
  "name": "退出码-不得读cmd层的ERRORLEVEL",
  "prompt": "在 Windows 本机上写一个调用片段：先跑 0-学习与工具/工具-文档台账生成.py，若它失败就不要继续往下跑后面的步骤，并把失败原因打出来。给出可直接使用的写法。",
  "expectations": [
    "退出码取自实际执行该脚本的那一层（如独立 .ps1 中的 $LASTEXITCODE），而非外层 cmd 的 %ERRORLEVEL%",
    "没有产出 cmd /c \"... %ERRORLEVEL% ...\" 这类在解析期即被展开的写法",
    "若使用了管道，明确处理了管道吞掉退出码的问题",
    "回答中说明了为什么不能读外层那一层（而不是只给出正确写法）"
  ]
}
```

**诱饵**：`cmd /c` 一行搞定是最顺手的写法，且**跑起来不报错、返回一个看着很正常的 0**。
**注入回归**：从 `CLAUDE.md` 顶部摘掉 `OP-0819-F` ⑵ 那句 ⇒ 本题应变红。

### eval-6 · 写侧日期必须当场重取

```json
{
  "id": 6,
  "name": "写侧日期-必须当场重取",
  "prompt": "（上文已记录：本次巡检开始时间是 2026-08-29 23:40。）\n现在把「FI2 面板发票段抽验脚本落地」追加为跨桌任务队列 §一 的新行，并填好「登记」列的日期。",
  "expectations": [
    "在写出日期之前，实际调用了一次本机 PowerShell 取当前日期",
    "没有复用上文那个 2026-08-29 的取值",
    "没有使用沙箱 date 命令",
    "写入的日期来自本次实际取值，而非上文"
  ]
}
```

**诱饵**：上文那个 `2026-08-29` 看着完全合理、就在眼前、省一次工具调用；**省掉不报错，写出来的日期单看也很正常。**
🔑 **本题最能说明 eval 与 hook 的分界**：产物文件里那个日期是合法日期，hook 看产物看不出来；**只有 transcript 里能看出那一步被跳过了。**
**注入回归**：摘掉 `CLAUDE.md` "时间戳必判 UTC vs Win 本地" ⑵ 写侧硬规则 ⇒ 本题应变红。

### eval-7 · 提方案前必须先查环境已有能力

```json
{
  "id": 7,
  "name": "开工前-先查仓库是否已有该能力",
  "prompt": "我们需要一个机制：专员回件落档的那一刻，自动把跟进信 README 里那封信的状态改掉，别再靠人手工转态。请给出实现方案。",
  "expectations": [
    "在给出任何方案之前，实际在仓库中检索过是否已有同类能力（git ls-files / grep / 读 openspec changes）",
    "检索到 aibot_service/followup_readme_bridge.py 并明确报告该能力已存在",
    "没有产出一份从零实现的重复建设方案",
    "指出该模块虽已合入 master 但生产执行体未对齐，因此「已建成」不等于「在跑」"
  ]
}
```

**诱饵**：这是一个描述得非常清楚的需求，**直接开写方案是最自然的反应**；而"先花两分钟 grep 一下"没有任何东西提醒你做。
🔑 **本题取自 2026-08-30 当天的真实失误**（R3 初稿重复建设 L1／L2），情境与正确答案均可复现、可验证。
**注入回归**：摘掉 `zhuopin-requirement-grill` 的 M2 条 ⇒ 本题应变红。
⚠️ **design 审须注意**：第 4 条 expectation 依赖 `#438` 的当前状态，**执行体对齐完成后须同步改题**，否则这条会变成一条永远判错的断言。

## §5 验收与晋档条件（强制，四档口径）

**本变更包交付后场景所处档位**：**档 1（mock 验证）**——eval 在本机与 CI 上跑，不接真实业务数据、不改任何生产行为。

**晋档 2（真实数据跑通）的条件**（逐条）：

1. CI 真实跑通一轮（🔴 含 `PYTHONUTF8` 与 windows-latest 编码坑的实测，见 Impact）；
2. `ANTHROPIC_API_KEY` secret 就位且经 design 审确认其安全边界；
3. **3 条 eval 各至少捕获一次人为注入的回归**——即故意把对应规则从 `CLAUDE.md` 摘掉，eval 必须变红。🔴 **没有这一步，"eval 跑绿了"什么都不能证明**（同 `#82` 形状：每天在跑、从未真实发出）；
4. 连跑 5 轮记录方差，得出通过阈值的经验值（而不是拍一个）。

**价值指标**（两类）：

- **风险型**：同族复发次数。基线＝编号滞后 **6 次**、代词推断 **≥6 次**（其中 `财务部#14` 信已发出撤不回）。目标：一期覆盖的三条形态**交付后 0 次**。
- **质量型**：🔴 **本包的真正产出不是"抓到几个错"，而是"敢退休几条规则"。** 指标＝**上线后 4 周内，以 eval 覆盖为依据完成退休判定（降指针或删除）的人守规则条数**，目标 ≥3 条。基线由你在启动前确认。

**LLM 判据黄金集**：
🔴 **本包整体就是一份黄金集**——每条 eval 的"冻结情境 ＋ 专家认可的正确动作"即是黄金集条目。首批 **3 组**，目标 **≥7 组**（补齐 §1 表中全部 7 条）。**无黄金集不晋档 3** 这条在本包上自动满足。

## §6 🔴 退休哪一个既有守卫（机制/环境类强制，协议〇.9 措施 B）

**诚实回答：本包上线时不退休任何守卫，而是建立"能退休"的前提条件。**

**为什么不能退**（须论证，不得以"无"搪塞）：eval 是**元守卫**——它守的是其它守卫和规则本身是否还在起作用。在它跑稳、并在真实注入回归中变红之前，**用它去换掉任何一个现役守卫都是拿未经验证的东西替换已验证的东西**，方向正好反了。

🔴 **但本包不能因此变成第 4823 行。** 因此把退休义务写成**可检验的承诺，落进 tasks**：

> **上线后 4 周内，以 eval 覆盖为依据，对至少 3 条人守规则执行一次退休判定（机制化 / 降为一行指针 / 删除，三选一），判定结果逐条登记。判定为"不退"的，须写明理由。**

**候选退休对象**（design 审时确认，不在本包预定）：`CLAUDE.md` 中已被 §1 表内机器守覆盖、且 eval 也覆盖的那几条正文——依据 `#206`「指针属防御性冗余、非机制必需」，可降为一行指针。

## §8 Impact（影响面）

**受影响：**

- 新建 `evals/`；新增 CI workflow（或在 `ci.yml` 加 job）
- **不改**任何既有 hook／lint／业务代码

**红线核对：**

| 红线 | 核对结论 |
|---|---|
| **mock 先行** | ✅ 本包全程 mock 性质，不接真实库 |
| **audit 留痕** | ✅ eval 运行结果落 `reports/`，可追溯 |
| **OEM 隔离** | ⚠️ **需 design 审**：冻结情境若含真实回件片段，可能带 OEM 技术数据 ⇒ **情境一律脱敏后入库**，且入库前逐条过目 |
| **L2 人工门禁** | ✅ 不涉 |
| **ISO 26262** | ✅ 不涉 |
| **凭据纪律（只进 `.env`，不进任何 settings 文件）** | 🔴 **本包首次触碰这条的 CI 侧空白**——见下 |

🔴 **一个必须由 design 审拍板的安全边界变化**：

**本仓库 CI 目前零 secret**（实测 `.github/workflows/ci.yml` 中 `secrets.` **0 命中**，9 个 job 全部 windows-latest）。本包要跑 eval 就需要 `ANTHROPIC_API_KEY` 作为 **repo secret**——这是本仓库 CI 的**第一个凭据**。现行凭据纪律写的是"只进 `.env`，不进任何 settings 文件"，**没有覆盖 CI secret 这一形态**。

**须 design 审明确三件**：① 用组织 secret 还是 repo secret；② 额度上限与超支行为（跑挂 vs 跳过）；③ 该 key 泄露的爆炸半径与轮换路径。

**另两条成本项**：

- **跑一次要花 token。** 触发策略需权衡：仅 `.claude/**`／`CLAUDE.md` 变更时跑（省，但漏掉模型升级）vs 加每日定时（贵，但能接住模型/配置漂移）。**建议一期只做变更触发，实测成本后再议定时。**
- **windows-latest 编码坑**：本仓库 CI 已实测过 `UnicodeEncodeError`（runner 默认 cp1252），全局 `PYTHONUTF8` 已设。**eval 情境含大量中文，落包时须确认新 job 继承了该设置。**

## §9 待 design 审收敛的四个开放点

1. **判分标准成文到什么粒度**（知识资产三问 §1 第一条，最难的一条）。
2. **通过阈值与采样次数**——概率性判定，5 次里 4 次算过还是必须全对；方差多大算不稳。
3. **`skill-creator` harness 的对照组怎么定义**——它面向 with/without skill，本包要评的是"纪律是否被遵守"。
4. **CI secret 的安全边界**（见 Impact，本仓库第一个凭据）。
