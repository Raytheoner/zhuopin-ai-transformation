# memory 机制与开场上下文预算 · 审核与方案

## 〇、一句话结论

**症状甲（memory 写不进）与症状乙（开场 token 就很大）确是一条因果链，但链条的最后一环被此前所有人查错了方向。**

不是「memory 坏了 ⇒ 东西只能挤进 CLAUDE.md ⇒ 膨胀 ⇒ 规则失效」这么简单。今天用 git 逐 commit 量出的曲线证明：**根 CLAUDE.md 顶部进度段已被瘦身过两次，两次都在 5-6 天内被超额长回来，且回涨速率在加速（3.4 KB/天 → 7.7 KB/天）。** 一个被执行过两次、每次都立刻失效的规则，问题不在执行力。

🔑 **真正的根因**：顶部进度段**同时承担两个职能**——① 进度记录（该迁）② **未闭合项的唯一跨会话载体**（迁走即丢）。执行迁移的人一旦读到某条里挂着未闭合事项，唯一安全的动作就是不迁；久而久之全都不迁。**⇒ 只加一条 lint 会把它逼成「为了过 lint 而丢掉未闭合项」，比现状更糟。** 正确的机制化路径是**先分流、后迁移**。

本次已按该路径实际执行一次：**根 CLAUDE.md 122,702 B → 101,463 B（-21,239，-17.3%），顶部段占比 43.0% → 29.8%**，§1-§7 规则正文 SHA256 逐字节未变。

## 四、根因判定

### 4.1 为什么「只留最近一批」这条规则两次都立刻失效

不是懒。**是它与一个更强的需求正面冲突。**

今天逐条核 12 个待迁条目，发现 **SC2 那两条自己在正文里写着**：

> 「按 design 审 5(a) 仍未立队列 §一 行，故本段与上一段是本任务仅有的跨会话载体。」

即：SC2 的 9.2 archive、9.6-9.7 跟进信两项未闭合事项，**当前只活在根 CLAUDE.md 顶部**。机械执行「只留最近一批」就会把它们丢掉。

⇒ **执行迁移的人面对这种条目，正确的动作就是不迁。** 于是规则每次都在同一个地方卡死，然后整段一起不迁。

### 4.2 由此得到的前置判据（已在本次实际使用）

> **顶部进度段的条目要迁出，必须先能指出它的承接载体：一个被它点名的队列行号（§一／§四），或一个具名文件＋章节。指不出 ⇒ 不得迁，改为先立队列行。**

本次 12 条按此判据分流：

- **可迁 8 条**：队列 #308 ×3、#313 ×3、#267 ×1（各有队列 §一 行）＋ 全景 v6 重排（承接＝全景规划 §0.2 的 2026-08-18 登记行）
- **不可迁 4 条**：SC2 ×2（**无承接载体，已登记为缺口**）＋ OP-0819-F／OP-0819-A（属「最近一批」，本就该留）

**⇒ 这条判据把膨胀压力转化成了队列登记压力**，而队列有 WIP 守卫、有编辑锁、有 sweep——**是本项目唯一一条已经被机制守住的通道**。这就是「先分流、后迁移」。

## 六、lint 判据规格（交 CC 实现，本件只出规格不写代码）

放在 `0-学习与工具/工具-队列结构lint.py` 同族，或新增 `工具-CLAUDE进度段lint.py`，接 CI 硬门禁。**四条判据，J1 是安全阀、必须先于 J2/J3 生效。**

**J1 · 承接载体判据（安全阀，拒绝迁移用）**
- 输入：一条待迁的顶部进度条目原文。
- 通过条件：正文中至少命中其一 —— ⑴ `#\d{1,4}` 形式的队列行号，且该号在队列 §一 或 §四 真实存在；⑵ 一个仓库内真实存在的文件路径 ＋ 章节号（如 `§0.2`）。
- 不通过 ⇒ **拒绝迁移**，报「**该条无承接载体，请先立队列行再迁**」。**不得报「请迁移」。**

**J2 · 条目数上限**
- 判定行：顶部段（文件开头至第一条独占 `---` 行之间）内，以 `> **` 或 `> 🔴 **` 开头**且含 `（20\d\d-\d\d-\d\d` 日期模式**的行。
- 上限建议 **6 条**（本次瘦身后为 4，留 2 格缓冲）。超出即违规，提示「请对最早的 N 条跑 J1 后迁出」。
- ⚠️ **必须同时匹配 `> **` 与 `> 🔴 **` 两种前缀**——今天两份输入件都因只匹配前者而漏算（见 3.2）。

**J3 · 单条长度上限**
- 单条进度条目 **≤ 1,200 字符**（现状均值 2,190、最大 3,507）。超出即违规，提示「超出部分请写进对应队列行或场景 CLAUDE.md，顶部只留结论与指针」。

**J4 · 写入侧配套（非 lint，属编辑锁 `release` 校验族）**
- 新增顶部进度条目时，若正文含未闭合项措辞（「仍不做」「未执行」「留待」「待…定夺」「如实登记」等），**必须同批点名一个队列行号**；否则 `release` 拒绝并提示「未闭合项须有队列承接，不得只写进 CLAUDE.md 顶部」。
- 🔑 **J4 才是治本的那条**——J1/J2/J3 都是在事后收拾，J4 是在源头不让「顶部段兼任待办载体」这件事再发生。

## 七、memory 载体分工建议（待验证① 后定稿）

**现在就成立、与验证①无关的三条：**

1. **本地 Cowork 会话对 memory 一律按「只读」对待。** 能读注入的索引与条目，**不能写**。🔴 **任何会话自陈「我已经写进 memory 了」，未经本机 `Test-Path` 复核一律不算数**——这条今天已两次证实。
2. **跨会话纪律的权威载体不变**：根 CLAUDE.md §1-§7 ＋ 队列。**不因 memory 可写与否而改变**，也不把规则正文搬进 memory（守 08-16 报告「不造第二 rules 层」边界）。
3. **本机那 2 个陈旧文件：建议保留不动、零处置。** 理由：`Read` 已被边界拒绝、`Write` 落不进去 ⇒ **它对任何会话都已不可达**，既不危险也不有用；而按红线 1 删除需拍板。**真正该改的是系统提示不再指向它**（属产品侧，见 §八 定夺 3）。

**依赖验证①、暂不定稿的一条**：memory 该放什么。若①证实「并存」（某类会话可写），则 memory 定位为「**只放读了能改变行为、又不值得占用每会话预算的事实与指针**」，由有写权限的会话类型维护；若①证实「已整体不可写」，则 memory 层应判为**只读历史资产**，索引维护三步纪律作废，`#254` 阶段 2 不再推进。
