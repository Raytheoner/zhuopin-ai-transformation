## 四、一处历史口径的精确化：「55~78 处高亮」是什么口径

README 记的"财务部#14/#15 各 55~78 处高亮"，实测是对 `<w:highlight` 做**裸字符串计数**（`xml.count("<w:highlight")` 一类写法）。本次逐条核实发现：两份文件里各有 **7／4 个 `w:highlight` 落在 `w:pPr/w:rPr`（段落标记本身的格式），不含任何可读文字**——Word 把整段连同结尾隐藏换行符一起高亮时的副产物。按**实际承载文字的 run** 数，两份文件分别是 **71／51**（`78-7=71`，`55-4=51`，逐位对上）。

`reply_form_detection.HighlightSpan` 同时保留两个口径：`run_count`（原始 run 数，可与历史"N 处"对账）与合并后的 `text`（真正可读的"高亮段全文"）。**不是谁比谁更"对"，是历史数字的统计粒度本身包含了一部分无内容的格式残留，本模块的输出更适合直接拿来读，但两个数字都留着，不用一个覆盖另一个。**

## 五、章程 §二 改动建议（交总线落，本次不改章程本体）

**建议插入位置：拆件巡逻章程 §二「读回件形态」判断步骤的最前面，读文件之后、下判断之前。**

具体建议措辞（供总线参考，不是要求逐字照抄）：

> §二 读回件形态前，**先跑**：
> ```
> python 5-平台底座/wecom-aibot-service/scripts/check_reply_form_signals.py <本次待拆回件的 docx 路径>
> ```
> 输出的 `summary_line()` 若四类信号全为零，**不得据此直接判定「对方未作答」**——先确认文件是纯文本反馈（`.md`，本工具不适用）还是真的是一份空白 docx；输出非零时，按打印出的逐格 ☒/☐（含同行上下文）、高亮段全文、批注内容通读一遍再下判断，**这一步不能跳，跳了就是回到 `#446` 原文那 4 次真实事故的老路**。

**为什么建议插在"最前面、读文件之后"而不是别处**：

1. 章程 §二 现有三条硬约束的失效模式都发生在"人凭习惯扫一眼原文件"这一步——本探测脚本的价值就在于把"扫一眼"变成"跑一遍必然执行的命令"，插在判断之前、读文件之后是唯一能保证"每次都会被执行"的位置（同队列 `#446` 原文诊断的根因："读形态这一步压根没有必然会被执行的位置"）。
2. 不建议放在拆件流程更早（如信号探测 `check_patrol_signal.py` 那一层）——那一层只知道"有没有新回件"，不知道具体是哪个文件，无法定位到具体 docx 路径。
3. 不建议放在拆件流程更晚（如回灌权威载体之前才补跑）——那样人已经基于"扫一眼"的印象做完了大部分判断，探测结果只能起"事后对账"的作用，起不到"防止读错"的作用。

**明确不建议做的事（本次已实测踩过的坑，供总线参考）**：

- 🔴 不建议把 `summary_line()` 的输出直接拼进回灌权威载体的文本——它是给人读的中间产物，不是结论（见模块文首"只做识别与结构化提取，不做语义判断"的边界）。
- 🔴 不建议尝试让脚本自动判断"该按什么形态解读"——`采购部#19`／`#20` 等真实件证明复选框、高亮、裸字符经常在同一份文件里混用，预设"这类信封应该是哪种形态"正是 `#446` 要根治的错误模式本身。
