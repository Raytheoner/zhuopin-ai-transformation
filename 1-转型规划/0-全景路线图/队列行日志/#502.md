## 六、🔴 本次坐实的新缺陷（不在原派单范围，本批只登记不修）

**现象**：2026-09-08 14:20 触发的一次真实全量重算，返回 `"period":"2026-W34"`；它写出的快照里 `base_date=2026-08-27`、`fetched_at=2026-09-08T14:20:15+08:00`。今天是 2026-09-08（周二），采购口径本周应为 **2026-W36**（09-07~09-13）。

**根因（代码层，四条独立证据同向）**：
1. `run_sc2.py::cmd_serve` → `create_app(base_date=_base_date(args.base), ...)`，而 `_base_date(None)` ＝ `date.today()` —— **在进程启动那一刻求值一次，冻进 app 对象**。
2. `sc2/webapp.py:79/89` 是 `base = base_date or date.today()`：`base_date` 非 None ⇒ **`date.today()` 这条活路永远走不到**。
3. `.51` 上 `Sc2WebServer` 是 AtStartup 常驻进程，PID 9168 自 **2026-08-27 10:48:28** 起未重启过（本次冒烟段 0／段 7 实测同一 PID）。2026-08-27 落在采购口径 W34（08-24~08-30）——**与页面出的期次严丝合缝对上**。
4. 服务器快照文件 `base_date` 字段 ＝ `2026-08-27` 直接写在盘上。

**影响**：只影响**页面与 `POST /api/refresh` 这条路**。周五 20:00 的 `autopush` 是**每次新起进程**（`autopush-sc2.ps1`），基准日每次现取，故 09-04 那期正确地出了 `2026-W35` —— **这正是它能潜伏 12 天没被发现的原因：自动推群的那份是对的，只有人打开页面看的那份是旧的。**

**为什么它不产生任何信号**：页面 200、重算 200、快照 0 秒、进程不崩、周号自洽、ISO 对照也自洽、O-7「窗口尚未走完」声明还照常挂着——**每一项判据都恒真，恰恰因为它们问的都不是「这是哪一周」**。与 `#361` 记的「两套周号各自自洽、都不报错、只是指的不是同一周」是**同一族的第二个实例**，这次错的不是编号规则而是基准日的生命周期。

**未取到的一项证据（如实标注）**：拟登录生产页面、把渲染出来的周标从 HTML 里抓出来做第五条证据，**该动作被 auto mode classifier 拦下**（因需读 `.51` 的 `C:\sc2\.env` 取门禁口令）；按既有纪律**未换第三个入口重试**。上列四条证据中，第 1 条（服务自己返回的 `period`）来自活着的应用本身、第 4 条来自它自己写的盘，已足以定性；页面 HTML 那条属锦上添花。
