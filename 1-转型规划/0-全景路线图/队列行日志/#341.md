### 起草时未识别到、apply 阶段实测补上的四处

1. **`DEFAULT_QUEUE_RELATIVE_PATH` 身兼三职**——①机器人新行的写入目标；②仓库根解析锚点；
   ③"§四／协议〇／编号高水位线在哪"的读侧答案。**只翻转它**会让
   `scripts/decision_reminder_check.py`（每日 08:30 定时任务 `ZhuopinDecisionReminderDaily`）
   去一份**没有 §四** 的文件里读决策项 ⇒ 稳定输出"决策提醒命中 0 项"，**与"今天真的没有
   待决策"在输出上逐字相同**——本项目反复点名的"只读命令结果太干净"失效形态。
   ⇒ 新增 `QUEUE_MECHANISM_RELATIVE_PATH`，`decision_reminder_check.QUEUE_REL` 钉死机制
   环境文件；其补录路径（`flush_pending_queue_appends`，属**写侧**）另用
   `QUEUE_APPEND_TARGET_REL` 指业务场景文件，两个常量刻意分开、不合并。
2. **`queue_git_sync._commit` 原本只 `git add` 写入目标那一份** ⇒ 高水位线的推进永远滞留
   工作区、推不出去，撞号从"本地已避免"退回"跨 checkout 仍会发生"（下一个 checkout 读到的
   仍是旧值），等于决策点 2 只做了一半。⇒ 改为两份同批进同一个 commit；`#287` 那条"外来
   未提交内容"护栏一并覆盖到高水位线来源文件（对它的预期改动更紧：插入 ≤1／删除 ≤1）；
   冲突重算路径的 `git checkout --` 也一并覆盖两份。
3. **`queue_reconcile_sentinel._collect_reconciliation_text` 只读 `queue_path` 那一份** ⇒
   切换生效前若干天里写在机制环境文件、尚未被清扫搬走的行，会被逐条误判为"归档成功但队列
   里没有对应行"，产生一批假阳性私信（同 `#99` 那次"行搬了家就报漏行"、以及 `#312` 缺口一
   "一份拆成两份、下游只跟一份"的形态）。⇒ 改为按 `iter_queue_paths()` **逐份读后合并**，
   **不拼接后只解析一次**（拼接会让 `find` 只取第一个 `## 一、` 而静默丢掉第二份）。
4. 🔴 **最要紧的一处，前三处补漏时也没看见**——`scripts/run_aibot_service.py` 把
   `WECOM_AIBOT_QUEUE_PATH` **同时**当成"仓库根锚点"和"机器人往哪份文件写"。该变量在
   其余**全部**入口（`decision_reminder_check`／`dispatch_followup_letters`／
   `flush_pending_lock_appends`／`push_followup_letter`／`approve_followup_letter`／
   `annual_holiday_reminder`）的文件头里都写着同一句"**可选，仓库根解析锚点**"；只有本
   入口历史上混用了两者——拆分前只有一份队列文件，两者恰好重合，这个混用一直没有后果。
   **实测（2026-09-05）**：常驻监听 `ZhuopinAibotDevListener`（当前 `Running`）的启动
   脚本 `.claude/worktrees/wecom-service-home/…/start-aibot-service-dev.ps1` 把该变量
   **钉在机制环境文件上**（其目的是 `#126` 的"锚到主工作区、别锚到 worktree 自己的
   副本"，与"写哪份"无关）。⇒ **沿用旧写法，本决策点的写入目标切换在生产上完全不生效、
   且不报任何错**——常量改了、行为一点没变，是"改了个看起来对的地方、真实路径根本不经过
   它"这一形态。**修法**：锚点仍走环境变量（`#126`／`#269` 语义一字不动），写入目标改为
   `resolved_repo_root / DEFAULT_QUEUE_RELATIVE_PATH`；配源码断言单测
   `test_run_aibot_service_derives_write_target_from_constant_not_anchor` 钉死不得回退。
   **`start-aibot-service-dev.ps1` 一字未改**——它现在只提供锚点，语义正确。
