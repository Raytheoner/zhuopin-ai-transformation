### 二、🔴 为什么没走 ff-only、而走了 `--no-ff`（本棒 `OP-0909-P` 立，供后续同款情形复用）

**派单件 §五-1 写死「先 ff」，且 §二 现取表把 `分支..master = 1` 判成「可 ff-only」——该判据本身就是错的。** `git rev-list --count 分支..master` 大于 0 的含义是「master 上有分支没有的提交」，那正是**已分叉**的定义；分叉即 ff 不可能。派单件成文时该值已是 1（当时就 ff 不了），起棒时因 sweep 又推入一笔而变成 2。

**起棒现取（`git -c core.fsmonitor= --no-optional-locks`）**：

| 项 | 实测 |
|---|---|
| `master..claude/op0909m-heartbeat-vis-apply` | 3（`9464fe1`／`0bd577e`／`548741e`） |
| `claude/op0909m-heartbeat-vis-apply..master` | **2**（`ce0172a` 跟进信 bot 回填／`ea14c9a` 队列 #170 值周对账） |
| `merge-base` | `5aa22f3` |
| `git merge --ff-only` | 🔴 **实测 `fatal: Not possible to fast-forward, aborting.`，`exit=128`** |
| `origin/master...master` | `0/0`（master 全已 push） |
| `origin/claude/op0909m-…...claude/op0909m-…` | `0/0`（分支全已 push） |

**⇒ 三条路里只有一条可走**：

1. `rebase` 分支到 master 上 —— 分支已 push，须 force-push 改写**已发布**历史；
2. `rebase` master 到分支上 —— master 同样已 push，后果更重；
3. `--no-ff` 合入 —— 不改写任何已发布提交，**进 master 的产物与 ff 完全等价，只多一个 merge 节点**，且是本仓既有惯例（`bec15d5`／`e472016`／`241e178` 等一批 `merge(队列#N/OP-xxx): … apply`）。

取 3。**未向 Shao Peishen 端出选择题的理由**：三条路的**交付物相同**（那 3 笔进 master），差别只在是否改写已发布历史；1／2 需要的 force-push 属未授权的破坏性动作，3 是本仓成文惯例 —— 不构成需要他拍板的实质分歧。

**合入手段与实测**：`git merge-tree --write-tree master claude/op0909m-heartbeat-vis-apply` ⇒ **零冲突**（tree `001b5997`）；两侧改动文件集**交集为空**（分支侧 `0-学习与工具/*` ＋ `openspec/*`，master 侧 `1-转型规划/0-全景路线图/跨桌任务队列-机制环境.md` ＋ 跟进信 README）；与工作区脏文件交集亦为空 ⇒ merge commit **`b5e68e5`**。**回读核**：`git merge-base --is-ancestor` 逐个核 `9464fe1`／`0bd577e`／`548741e`，三笔**均已在 master**；sweep 随后自动推送，`origin/master...master` 现取 `0/0`。
