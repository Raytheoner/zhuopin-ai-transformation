## 二、重组闭环 SOP（域变更 → 全景重排）

**触发**：某域专线（或 CC 建造）出现 **需求变更**（场景增/减/细化）或 **构建时序变更**（某场景启动档位移动）。

1. **局部定稿**（域专线，不改全景）：在本域内重梳口径/范围/编号 → 产出 **局部定稿 + 移交单**（移交单含：定稿决策、原→新编号映射、逐文档改动清单、精确对齐散点、纪律）。
2. **全景触发**（全景路线图 Task，改全景）：据移交单执行跨文档重排——§2.1.4 段替换、§加速启动总览排期表、四阶段、甘特、实施计划§一/§二、前置总表、根 CLAUDE.md（场景总数等）。
3. **纪律**（根 CLAUDE.md §5）：全景规划 §0.2 **修订登记** + 单一可信源=§加速启动总览排期表 + **grep 全库零残差**（号义一致、无旧引用）+ 场景总数校对。
4. **登记**：本日志 §四 追加一条。

**分工红线**：域专线出局部定稿+移交单、**不直接改全景**；全景路线图 Task 执行重排、**不重开域业务口径**。

## 三、为什么要这个机制

局部一处场景增减/时序变更，会牵动全景规划、实施计划、甘特、前置总表、CLAUDE.md 等多文档的号义与排期——散点极易漏（本次财务重排审计即发现实施计划依赖表/散注是最易漏残差）。把它固化为"局部定稿→移交→全景重排→零残差自检→登记"的闭环，避免单一可信源漂移。
