## 二、复用频率（实测，含测法与其局限）

**#254 问的是"复用频率如何"。真正的复用频率＝"被后续 session 读到并影响行为的次数"，这个量在当前载体下无法测**（没有任何载体记录"谁读了什么"）。故本节用两个**可测的代理量**，并如实说明它们各自代表什么。

### 2.1 代理量①：跨载体复述次数（＝有多少人觉得它值得再写一遍）

| 事实 | CLAUDE.md | 队列 | 接力 | opener | 合计 |
|---|---:|---:|---:|---:|---:|
| 「工具静默回退」这一类名 | 1 | **9** | 3 | 1 | **14** |
| `git worktree remove`（B2） | 0 | **6** | 0 | 0 | 6 |
| `git patch-id`（因果断言证伪） | 1 | 5 | 0 | 0 | 6 |
| `System.IO.File`（A1） | 2 | 1 | 1 | 0 | 4 |
| `core.quotepath`（A8） | 1 | 2 | 0 | 0 | 3 |
| `ID=27`／`Kernel-Boot`（B1） | 1 | 1 | 0 | 0 | 2 |
| `ConvertFrom-Json`（A5）／`hiberboot`（B1） | 1 | 0 | 0 | 0 | **1** |

**读法**：复述次数高 ≠ 有用，**恰恰相反——它多半意味着这条事实反复被重新解释、每次都要在新场合重写一遍**。「工具静默回退」14 次是全场最高，而它正是下面 §3.1 里"写了也没防住"的那一条。**⇒ 高复述次数是需求信号，不是满足信号。**

## 三、三条对后续阶段有约束力的发现

### 3.1 🔴 「写进 CLAUDE.md」这一动作，已被实测证明不足以防住重犯

**至少 3 条实例**，全部有据可查：

1. **A1（`[System.IO.File]` 相对路径）** —— 该条**白纸黑字写在 CLAUDE.md §5「工具静默回退」里**，2026-08-05 做 Context 取证时**仍踩中**（首条命令对根 CLAUDE.md 报 0 字节）。来源：`Context体系诊断与精简方案-2026-08-05.md` §2.2 第 1 条。
2. **裸竖线** —— 已入法且反复实证，**2026-08-04 第 4 次仍靠事后拦截**，发生在"已判定机制化、CC 未落地"的空窗期。来源：环境保障线 opener §六。
3. **因果断言前先问没核的变量** —— 已写进 opener §六防线 4，仍 3/3 达阈值，且后两次**都不是断言者自己发现的**。来源：队列 #284 第 ③ 条。

**⇒ 对阶段 1 的直接约束**：#254 原文写的验收判据「**被后续 session 真读到并影响了行为**，不是『写下来了』」——本盘点为它补上了证据。**若阶段 1 只做"换个地方写"，可以预期它的结局与现有 memory 层相同**（那 2 个文件躺了一到两个月、从未被任何 session 用上）。

### 3.2 C 类的一半其实是规则，不该进 memory

C 类 15 条里，**至少 7 条已经以规则形态活在 CLAUDE.md §5 或 opener §六防线**（如"不信工具说成功了"、"判据本身也要被质疑一次"、"凡涉数量先 grep 再说"）。把它们再抄进 memory，正是 #254 自己警告的形态——「**它会变成第二个 rules 层、制造『同一条规则两处不同步』**」（#242／#204／#230 第二形态皆同族）。

**⇒ 建议阶段 1 的试写样本从 A/B 类里取，不取 C 类。** A/B 类有一个 C 类没有的性质：**它们是可证伪的客观陈述，不需要"遵守"，只需要"知道"**——因此不会与 rules 层重叠，也不存在两处不同步的问题（事实变了就改，不像规则会有"哪条优先"的争议）。

### 3.3 D 类已有更好的归属，不必进 memory

4 条 D 类事实的共同点是**极少变、且已在 CLAUDE.md §1／§5 有稳定归属**。称呼纪律那条尤其不该动——它带着一条**反向禁令**（"绝不替换路径里的 `Paul Shao`"），拆开放到另一个载体会增加拆散正反两半的风险。
