# 派单件 ·【CC】值周读取面瘦身与队列清扫（三条同源）

## 〇 为什么是一件事，而不是三个小毛病

🔑 **清扫不是卫生问题，是性能问题（Shao Peishen 2026-08-31 定，本轮讨论新得的判据）**：

> **队列不清扫 → 真身越来越大 → 值周越来越慢 → 更没时间清扫。这是一个正反馈回路。**
> **本次值周耗时 40 分钟，就是这个回路的读数。** 按 (b) 拖到下周变 560 行，等于再加一圈。

🔴 **三条同源**：`--digest` 不存在、归档件 2.9 MB 压在读取面上、清扫积压近 280 行 —— **它们是同一个结构问题的三个面**。同族的第四、第五个面本次也一并实测到了：

| 守卫 | 应该守什么 | 实测状态 |
|---|---|---|
| `--digest` | 让扫全池不必通读真身 | 🔴 **参数根本不存在**（三份章程都在指挥调用它） |
| R5 / J6 | 接力件 ≤ 8 KB | 🔴 四份活件 **8,279–8,487 B 全超**，J6 未报 |
| 值周计划 10,000 B 上限 | 计划定长 | 🔴 与 08-30 落地的 opener 守卫**互相挤压**：两个 CC opener 的 `set_session_title` 样板占去约 1,000 B（10%），**判据无一可删、只能挤内容** |

⇒ **结论：所有「限长/限量」类守卫都在失效或互相打架。** 本件只做前三条，后两条留登记。

## 一 · ① 给 `工具-队列查询.py` 加 `--digest`（🔴 排第一：收益最大、成本最低）

**为什么排第一**：**三份章程都在指挥调用一个不存在的参数** —— 照文档做会失败，而失败方式是"命令报 usage 错误"，不是静默，所以每个人都会当场绕开、然后去通读真身。

- `0-学习与工具/定时任务源码/weekly-status-update.SKILL.md:14`
- `0-学习与工具/skills源码/zhuopin-queue-audit/SKILL.md:61`
- `0-学习与工具/定时任务源码/huijian-chaijian-patrol.SKILL.md:20`

**规格（他给定）**：

- 输出格式 ＝ `编号｜[S:x][D:y]｜任务列首 N 字`；**两份真身合并输出，目标几 KB**。
- `--row` 由**必填改为与 `--digest` 互斥可选**（今天 `--row` 是 required，缺它直接 usage 报错）。
- 🔴 **两份真身缺一不可**：走 `queue_table.iter_queue_paths()` 逐份解析后合并，**绝不拼接文本再解析一次**（`_parse_table_rows` 只取第一个 `## 一、`，拼接会静默丢掉第二份的 §一，已有反例单测，见根 `CLAUDE.md` OP-0819-A ⑴）。
- 建议同时支持 `--section`（默认 §一）与 `--digest-width`（默认 N，便于巡逻/审计各取所需）。

**落地后须同批改三份章程**，把 `--digest` 从"指挥一个不存在的东西"变成真指针。

## 二 · ② 把 2.9 MB 归档件移出值周读取面

**现状**：`1-转型规划/0-全景路线图/跨桌任务队列-归档-202608.md` **2.9 MB**，对账审计每轮读它，**唯一用途是「防已完成误派」**。

**两条候选修法（择一，design 时定）**：

- **(甲) 归档件也出 digest** —— 同 ① 的实现，一次做两处受益。
- **(乙) 惰性查** —— 仅当某行**疑似已完成**时才去归档件查那一行，平时零读取。

🔴 **不得改的**：归档件本身的内容与编号（编号永不复用）；机器人取号与哨兵**同扫归档**这条既有行为（#99）不得破坏 —— 改读取面，不改语义。
