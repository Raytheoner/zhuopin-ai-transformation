## 一、#163 编辑锁增 `--reserve`：让工具**分配**编号，而不是**显示**编号

### 1.1 现状（已实读 `0-学习与工具/工具-共享文档编辑锁.py`）

`cmd_acquire()` 在占锁成功后做两件事：写锁文件、然后调 `_read_high_water_mark()` 读一次目标文件里的"编号高水位线"行并**打印**：

```
📍 持锁瞬间高水位线：§一 #164 ｜ §四 #37——新行编号从此值 +1 续排，
   勿用 acquire 之前读到的旧值（见协议〇.7）。
```

这是 2026-07-27 针对 #121(c) 打的补丁，方向正确：把"读高水位线"的时刻从 acquire **之前**挪到 acquire **之后**。

### 1.2 但它没有关闭撞号，因为把最后一步留给了人

2026-07-29 一天四次撞号，可分成两类：

| 类 | 例 | 成因 |
|---|---|---|
| **A：用了 acquire 之前的值** | #122/#126、#132-134、#147 | v1 补丁正是修这一类 |
| **B：回显是对的，读的人看错** | **#162**（原登 #160，与机器人同期追加的 #160 撞号） | acquire **已明确回显**"持锁瞬间高水位线：§一 #161，从此值 +1"，业务总线仍误用 #160 |

**B 类是关键证据**：它证明"把正确答案打印在屏幕上"不足以关闭这个缺陷。剩余的三个人工步骤——**读回显 → 做加法 → 写进表格**——每一步都可能出错，而且**错了没有任何反馈**（撞号要到下一个 session 读队列时才被发现，或者根本发现不了，直接静默覆盖）。

> 一句话定性：**当前设计把"分配编号"这件事的最后一公里交给了最不可靠的执行者。** 能不算，就不会算错。

### 1.3 建议修法

**核心**：`acquire` 增 `--reserve N --section 一|四`，由工具**直接分配并返回具体编号**，同时**原子回写高水位线**。

```
$ python 工具-共享文档编辑锁.py acquire --who "Cowork-采购专线" \
      --note "v2.4 回灌" --reserve 2 --section 一
✓ 已占锁：Cowork-采购专线（v2.4 回灌）
📍 已为你预留：§一 #165、#166
   （顶部高水位线已同步回写至 §一 #166；即使本次未写满，编号不复用、留空即可）
   改完请立刻 release。
```

**五个设计要点**（每点都对应一个已发生过的事故形态）：

1. **返回字面编号，不返回基数**——输出里**不出现**任何需要 +1 的数。这是 B 类事故的直接闭合。
2. **分区计数**：`§一` 与 `§四` 各自独立，`--section` 必填（缺省不猜）。
3. **acquire 时即回写高水位线**（此刻正持锁，写是安全的）。**这顺带解决了 #146 与 #97④ 指出的死角**：高水位线回写此前只在企微机器人 `queue_appender` 这一条代码路径上做，**业务总线/域专线手工加行时全靠记得回写、漏一次就复现滞后且无任何代码兜底**。改成"取号即回写"后，人工路径与机器人路径**共用同一个分配器**，死角消失。
4. **未写满允许留空洞**——协议〇.8 已定"编号永不复用"，预留后 session 中止造成的编号空洞是**可接受代价**（成本=表里少个号；收益=永不撞号）。不要为了消除空洞去做"释放时回收未用编号"，那会把竞态重新引进来。
5. **解析失败必须 fail-loud**：高水位线行缺失或格式漂移时**拒绝分配并非零退出**，绝不静默回落"文内可见最大号 +1"——清扫后文内看不到历史最大号，那个回落值必然撞已归档编号（#99(a) 已实证过同款）。

**兼容**：不带 `--reserve` 时行为完全不变（现有回显保留），可平滑过渡。

### 1.4 验收要求（建议写进变更包 tasks）

- [ ] `--reserve 1` / `--reserve N` 各返回连续且正确的字面编号
- [ ] `§一` / `§四` 计数互不干扰
- [ ] 分配后**再读一次目标文件**，确认高水位线行已回写到位（写后验证，非只看返回值）
- [ ] 高水位线行缺失／格式漂移 → **非零退出 + 不写任何内容**（fail-loud 用例）
- [ ] `--reserve` 必须在**成功占锁**之后才生效；占锁失败（他人持锁）时不得分配任何编号
- [ ] 两次连续 acquire+reserve 拿到的编号区间**不重叠**（模拟两桌并发）
- [ ] 预留后不写行、直接 release —— 高水位线**保持已推进**（空洞可接受，用例显式断言这一点）
- [ ] 协议〇.7 条文同步改写：从"按回显值 +1 续排"改为"用 `--reserve` 取号"，并保留旧口径作过渡期说明

### 1.5 顺带建议（可同批，也可不做）

`--reserve` 落地后，`0-学习与工具/skills源码/zhuopin-kickoff-prompt/SKILL.md` 与 `zhuopin-queue-audit/SKILL.md` 里"取回显值 +1"的措辞需同步改为"用 `--reserve` 取号"。**本次（2026-07-30，队列 #97）已按现行口径更新过这两份源码**，`--reserve` 上线后需再改一次——**建议 #163 与 #97 的 skill 重打包合并成一次**，避免让 Paul 两周内装两遍。

## 二、#147 `gap_alert` 把"空闲"误报成"中断"

### 2.1 现状（已实读 `5-平台底座/wecom-aibot-service/aibot_service/gap_alert.py`）

判据是一行：

```python
last_ts = last_event_timestamp(audit_path)   # 审计日志最后一条事件的时间戳
gap_seconds = (now - last_ts).total_seconds()
if gap_seconds > 180: → 发"中断约 N 分钟，消息可能丢失"
```

`last_event_timestamp()` 读的是 **审计 JSONL 的最后一条事件**。

### 2.2 缺陷：审计事件是「有事才写」，不是「活着就写」

审计事件由业务动作触发（消息归档、连接建立、转发、群通报……）。**没人发消息时，审计文件就不增长**——但连接可能全程健康。

于是：**周五 18:00 最后一条事件 → 周一 09:00 服务重启 → 判定"中断约 3780 分钟，消息可能丢失"**。实际上整个周末连接可能一直好好的，只是没人说话。

**后果不是"多发一条消息"，而是告警彻底失去信息量**：Paul 每次都收到"疑似中断+消息可能丢失"，真正的中断（如 07-16 那次 24h49m 停摆）反而淹没在噪音里——**这正是狼来了效应的定义**。当前这个告警**已经不能用来判断是否真的丢过消息**。

### 2.3 建议修法：把判据从「上次有事」改成「上次确认活着」

**需要一个与业务流量无关的存活心跳。** 建议实现：

- 连接存活期间，**每 N 分钟（建议 5 分钟）覆写一个独立的存活戳文件**，如 `reports/aibot_liveness.json`：`{"alive_at": "<ISO8601 UTC>"}`。
- 重连后：`gap = now - alive_at`，这才是**真实断线时长**。
- **不要把心跳写进审计 JSONL**：审计链有 hash 防篡改链（#126 刚统一并重算过），每天塞 288 条心跳会稀释可追溯性、拖慢 `verify_chain()`，且心跳不是"AI 决策"，本不该进审计（IATF 口径）。存活戳是**运行状态**，与审计是两回事。
- 单文件覆写（非追加）→ 体积恒定，无清理负担；进程被 kill 时最后一次写入天然就是"最后确认活着"的时刻，语义正确。

**通报文案应区分两个数**（它们回答不同问题）：

| 数 | 来源 | 含义 | 是否触发"消息可能丢失"警示 |
|---|---|---|---|
| **断线时长** | `now - alive_at` | 连接真的断了多久 | **是**——只有这段窗口里的消息才会永久丢失 |
| 无消息时长 | `now - 末条审计事件` | 多久没人说话 | 否，纯信息 |

建议文案示意：
- 断线 > 阈值：`监听已恢复。真实断线约 12 分钟（09:03–09:15 UTC）。这段时间的来件不会补推，如有请让对方重发。`
- 断线 ≤ 阈值：`监听已恢复，断线约 8 秒。期间无消息丢失风险。（距上次有人发消息 62 小时，属正常空闲。）`

Paul 2026-07-19 的要求"**每次重连都要收到确认消息、不只在超阈值时**"（`build_reconnect_notice`）**保持不变**，本次只改里面那个数字的算法与措辞。

### 2.4 验收要求（建议写进变更包 tasks）

- [ ] 长时间无业务消息但连接持续存活 → 重连后**不报**"中断/消息可能丢失"（**这是本次修复的核心用例**，用"审计末条 3 天前 + 存活戳 2 分钟前"构造）
- [ ] 真实断线（存活戳停在 T，T+30min 才重连）→ 正确报 30 分钟，且**带**消息丢失警示
- [ ] 存活戳文件不存在（首次运行/迁移）→ 回落现有"首次运行，无历史可比对"文案，不误报中断
- [ ] 存活戳格式损坏 → 视同不存在，**不抛异常**（告警本身绝不能影响服务运行，沿用现有 `send_gap_alert` 的不抛出语义）
- [ ] 心跳写入失败（磁盘满/权限）→ 服务继续运行，审计留痕一条，不中断长连接
- [ ] 审计 JSONL **未被心跳污染**（断言心跳期间审计文件行数不变、`verify_chain()` 仍 ok）
- [ ] 两个时长同时出现在文案里且不混淆

### 2.5 优先级判断

**P2，不紧急但别再拖**。理由：它不影响业务正确性（消息该收的照收、该归档的照归档），但它侵蚀的是**唯一一条"机器人是否健康"的人工感知通道**——而机器人现在承载着跟进信发送、回件归档、群通报、队列追加四条真实链路，且 07-16 已有过 24h49m 无人察觉的停摆先例。**告警一旦被当成噪音忽略，等于这条通道已经废了**，只是账面上还在。

## 三、两项的共同点（值得单独记一笔）

#163 与 #147 表面无关，实质是**同一种设计病**：

> **把「需要判断的事」交给了一个拿不到判断依据的执行者。**

- #163：把"下一个编号是几"交给人做加法，而人手上只有一个易读错的显示值。
- #147：把"是否中断"交给一个只知道"有没有人说话"的信号，而它拿不到"连接是否活着"的依据。

修法也同构：**不是加提醒、加纪律、加复核，而是把依据本身补上、把计算收进工具**。这与本项目已验证有效的几次修法一脉相承（#126 `resolve_repo_root()` 动态问 git 而非信任调用方传参、#99(a) `max(可见最大号, 高水位线)`、sweep 判据从"不含✅"改成显式"待"字样）。
