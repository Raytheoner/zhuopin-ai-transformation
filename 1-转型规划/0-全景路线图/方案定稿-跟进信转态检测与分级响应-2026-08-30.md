## §2 方案：三件，A 与 B 是本件的全部交付

### A · 存量一次性回扫（`工具-跟进信存量回扫.py`，跑完即弃）

**做什么**：对 README 主表（`readme_table.MAIN_TABLE_SECTION = "现有跟进信清单"`）中状态列为 `✅ 已推送` 的每一行——

1. 用 `readme_table.extract_target_filename(topic_cell)` 取该信文件名（**🔴 已有函数，不自己再写一个解析器**——第二个解析器就是第二个可漂移的口径）；
2. 在 `7-外部文档/<部门>/` 下按 **stem 精确匹配**找回件落档件；
3. **命中** → 写入待转态清单：信编号／文件名／落档件路径／落档日／发出到落档天数；
4. **未命中** → 写入残差清单，**不做二级配对**（🔴 二级配对是桥一的职责，一次性脚本不得复制它的判据——两份判据必然漂移）。

**输出**：一份 Markdown 清单文件，落 `reports/`。**🔴 不写 README、不改任何权威源。**

**为什么一次性脚本不常驻**：桥一上线后，新回件由桥一实时接住，存量只有这一批。**建成常驻＝又多一个要维护的守卫，而它此后永远扫出 0 条**——违反 one-in-one-out 精神。

**复用清单**（都是现成的，不新造）：
`readme_table.iter_rows` ／ `extract_target_filename` ／ `column_index` ／ `split_department_and_name` ／ `MAIN_TABLE_SECTION` ／ 状态常量。

### B · 第九态超期看守（常驻，挂进拆件巡逻）

**做什么**：扫 README 状态列为 `📨 回件已到，待拆件 <UTC>` 的行，按距落档时刻分级：

| 距落档 | 动作 | 谁看 |
|---|---|---|
| < 3 天 | 只记状态文件，不发声 | — |
| ≥ 3 天 | 进拆件巡逻的"待拆件"清单 | 巡逻班 |
| ≥ 7 天 | 升格进值周巡检《本周计划》，并列入会话末「需你定夺」 | 你 |

**为什么是 3/7 而不是别的数**：判例批改法实测中位 **2 天**（度量复盘 §一），拆件本身是我方动作、应快于专员回件；3 天已是中位的 1.5 倍，7 天是原闸目标（≤1 周）。**阈值有依据，不是拍的。**

🔴 **告警通道**：**不新起**。挂进已有的拆件巡逻／值周巡检输出。理由——本仓库已有 8 类告警，且有"只报出现不报解除"的历史（`#308` 子项 D1 的告警解除骨架未落地前，CI 那条告警建议已被否掉一次）。**第 9 类告警的代价大于收益。**

### C · 度量派生（A 的副产品，几行代码）

A 跑出的"发出 → 落档"天数即是真实的回件时延。与度量复盘的代理指标同期并跑一轮做对照，**用来回答一个悬着的问题：中位 2 天那个达标结论，在补齐 12 封之后还成不成立。**

## §3 🔴 三条边界（不变，且比原方案更该守）

1. **本件的任何产物都不改 README。** A 出清单、B 出告警，转态动作仍由人执行。
   **理由变强了**：桥一**已经**是一个会写 README 的机器（走编辑锁、有审计）。再加第二个能写权威源的东西，就有了两个写入者——而 `tasks.md` 8.1 明记「**S5 未做 ⇒ README 状态列此刻仍可被人手改**」，也就是说现在已经是"机器 + 人"两个写入者。**第三个写入者不能加。**

3. **检测层完全确定性、不涉模型。** A 是字符串匹配，B 是日期算术。**本件不引入任何模型判断**——需要判断的那一层（二级配对）已由桥一用"按位置配"解决。

**B 的验收**：

- 桥一在生产真实触发**至少 1 次**之后（即 `#438` 完成之后），B 能扫出那一行并按 3 天阈值正确沉默；
- 造一条时间倒推的测试行，验证 3 天／7 天两级各触发一次；
- 🔴 **验收 B 的前提是桥一真在跑**——`#438` 未完成前，B 的"扫出 0 条"**不构成通过**（那正是 `#82` 的形状：每天在跑、从未发出）。

**风险两条，及其解药**：

| 风险 | 解药 |
|---|---|
| stem 子串互相包含导致误配（如两封信标题一个是另一个的前缀） | 用**完整 stem 相等**而非 `in`；且 A 不自动转态，清单交人确认本身就是兜底 |
