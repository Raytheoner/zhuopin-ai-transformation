# 开场 Prompt：全域健康度体检与松耦合场景加速评估

> 用法：新会话（或本会话）读本文件 + 根 `CLAUDE.md` 当前进度即可恢复上下文并执行。执行方只做体检与建议，不越界替 Paul 或各域专线做业务决策。

## 一、背景与关切

卓品智能 18 个月 / 42 场景企业 AI 转型项目已构建一段时间（六部门并行、OpenSpec+SuperPowers+Hermes SDD 双驱动），项目本身也随之变复杂。Paul（分管供应链与质量 VP，项目决策人）的核心关切：

1. **全面铺开的风险**：场景之间可能存在隐性耦合（共享底座模块、共享外部依赖、共享稀缺人力），导致实现难度叠加、见效变慢，而不是像规划表面看起来的"六部门齐头并进"。
2. **想要的转向**：优先让**部门内、真正松耦合**的场景尽快上线见效，而不是等全域打通才算数——但不能因此放弃最终"打通部门间自动化协同、全面提升运营效能"的全域目标。
3. **团队可执行性**：各部门到位的 AI 专员（采购/财务/质量等）需要更清晰、更容易理解和推进的工作指引，而不是要在多份分散文档里自己拼凑"我该做什么、和别人怎么配合"。

本次体检的目的，是帮 Paul **确认自己是否走在正确的路上**，并给出让路径更稳、更快见效的具体调整建议——不是推倒重来。

## 二、审核范围

请系统性审核以下维度，每条结论须落到具体文件路径+行号、commit hash，或明确日期，不凭印象下结论。

### 1. 全景规划
`1-转型规划/0-全景路线图/卓品智能AI转型全景规划.md` —— §2.1.x 各场景定义、§加速启动总览排期表（单一可信源）、§0.2 修订记录的密度与可读性、四阶段框架（S1/S2/S3 + Phase 2）。

### 2. 实现路线图
`实施计划（最新版）.md`、`全景甘特图-42场景排期.html`、`跨场景前置数据与知识库任务总表.md` —— 时间线是否现实、前置依赖是否已充分暴露。

### 3. 技术架构
`5-平台底座/zhuopin_platform/` 四大子系统（`audit` / `data_isolation_layer` / `shared_tools` / `agents`）的**实际完备度** vs 文档声称的完备度；各场景独立工程（`4-数字员工/部门/场景名/`）与底座之间的耦合方式——是真正"引擎复用、场景独立"，还是场景之间已经产生了隐性交叉依赖。

### 4. SDD 战略构建过程
OpenSpec + SuperPowers + Hermes（L1 CLAUDE.md / L2 场景 CLAUDE.md / L3 记忆）三层工作流的真实执行质量。**请核查 `openspec/changes/` 下是否存在"代码已合并 master、但变更包确应归档而未归档"的真实遗留**——注意 `fix-a-security-compliance-p0`/`fix-b-data-integrity-audit`/`fix-c-sc8-golive-prereq` 三个目录仍在 active、未进 `archive/`，**这是已核实的正常情况，不是遗留**：三者均无 specs delta，按项目约定不走 `/opsx:archive`，tasks.md 已于 2026-07-02（PR #16）逐条核实全部勾选，Paul 已确认此处理方式——体检时**不要**把这三个当作问题重提，而是检查还有没有其它*真正*该归档却卡住的变更包（区分"设计上不需要归档"与"忘记归档"两类，避免像本条一样的误判）。

### 5. 已实现代码
已上线/已收割场景（SC1/SC8/SC3/SC5/O2/FI1/QD-B 等）的实际测试覆盖、真实数据验证情况，与 CLAUDE.md/规划文档中"已完成"的表述是否一致——有没有"规划/文档层面显示完成，但代码实际未达生产可用"的落差。

### 6. git 记录
提交节奏、分支卫生（`Off-LAN行动单-两天与周一.md` 已把 4 个旧 `feat/*` 分支清理列为低优先 CC 杂项——`feat/o2-kit-shortage-alert`/`feat/platform-hardening-p2`/`feat/sc1-platform-align`/`feat/sc8-delivery-date-commitment`，对应变更包均已在 `openspec/changes/archive/` 找到匹配归档记录，判断已可安全删除；体检时确认是否已清理，未清理则重申，不是新发现）、PR 合并历史是否顺畅、有无长期停滞的分支。

### 7. 就绪工作分配与团队回复过程
各部门 AI 对接人到位时间、任务单/就绪清单的响应速度与质量、跨部门共享依赖（U9C MCP 接口、OEM 隔离层 Chroma、SRM 900401）造成的级联阻塞——这类共享依赖可能是"全面铺开变慢"的真正源头，而非场景本身的复杂度。

### 8. 建议增补的维度（Paul 未必想到，但判断重要）

- **场景真实耦合度矩阵**：逐场景标注——部门内/跨部门、依赖的底座共享模块、依赖的外部系统、依赖的稀缺人力（AIOps 工程师长期仅 1 人、第 2 人仍在招募中，是否已构成事实上的全局瓶颈而非场景本身难度）、能否真正独立上线而不牵连其他场景。
- **流程开销与场景规模的匹配度**：OpenSpec propose→design→apply→archive 全套 + L2/L4 人工门禁，是否对小型部门内场景也无差别套用了与大型跨部门场景相同的重流程，造成不必要的减速。
- **"上线"定义的一致性**：42 个场景里"上线"口径是否统一（收割式 MVP / mock 验证 / 真实数据跑通 / 正式对客交付），避免团队产生虚假的推进感。
- **认知负荷**：各部门 AI 专员是否有一份清晰、可执行的"我该做什么、何时找谁"操作手册，还是需要自己在多份分散文档间拼凑。
- **外部依赖阻塞链的传导范围**：量化一个共享接口（如 U9C CommonEntity/Query）卡住了多少个"看起来独立"的场景——这决定了"全面铺开"风险的真实来源是场景耦合还是外部依赖集中，两者的解法完全不同。
- **治理开销的可读性**：全景规划 §0.2 修订记录、变更日志等治理机制本身，是否已经变得过于繁琐，反而不利于 Paul 和团队快速看清现状。
