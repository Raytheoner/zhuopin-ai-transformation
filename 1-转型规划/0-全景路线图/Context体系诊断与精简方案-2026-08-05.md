## 五bis、Context 之外的优化方向（Shao Peishen 2026-08-05 追问：「最近 session 错误频发、记忆有失、规则稀释、信噪比不好，我有点担心，除了 Context 体系还有什么优化方向」）

### 5b.1 先把「记忆有失」这个说法校准一下

**本 session 的 6 次错误里，没有一次是「忘记了规则」。** 规则全程都在上下文里——`[System.IO.File]` 相对路径那条就写在 §5，我做取证时把它读进来了，然后还是踩了。

**所以问题不是「记不住」，是「没有在该用它的那一刻检索到它」。** 这个区分决定了解法方向：
- 若是记忆丢失 → 解法是「多写几遍、写显眼点」（这正是过去一年在做的，也正是膨胀的来源）；
- 若是检索失败 → 解法是「减少竞争 ＋ 在动作点上加验证」，**再写一遍规则只会让情况更糟**。

**是后者。** 这也解释了为什么规则越加越多、错误却没减少。

### 5b.2 六次错误的根因分类：两类，且 Context 精简只能治一类

| # | 错误 | 类 |
|---|---|---|
| 1 | `[System.IO.File]` 相对路径不按 PowerShell `cd` 解析 | **A** |
| 5 | 决策路由标签机械套用（标了零信息量的代称，且按判据本应标总线） | **A** |
| 6 | 断言载体未取证（说「拆件巡逻 prompt 里」，实为 artifact） | **A** |
| 2 | 集合 `-ne $null` 被重载为元素过滤 → 六态全归「其他」 | **B** |
| 3 | `Edit` 工具报 success 但零落盘 | **B** |
| 4 | 状态列引用判据关键词 → 触发判据本身 | **B** |

- **A 类＝规则存在但没被触发**（3 次）。病因是信噪比 7.5%，**#253 清扫能治一部分**。
- **B 类＝判据或工具本身静默失效**（3 次）。**Context 精简对它零效果**——因为它不是「没想起规则」，是「规则本身在这种输入下失效了，而且不报错」。

🔴 **B 类更危险**：A 类错了通常当场别扭、能察觉；B 类返回值完全正常，只是答案是反的。**本 session 三次 B 类，全部靠事后交叉核对才发现，没有一次是当场察觉的。**

### 5b.3 四个方向（按性价比排序）

#### 方向 1 · 把「验证」从人守变成机制守（治 B 类，优先级最高）

**现状**：防线 2「不信工具说成功了，写完必反查落盘」是纯人守规则。本 session **违反 4 次**——而**凡是我真反查了的，都当场抓到了问题**（Edit 零落盘、Write 零落盘、#254 插错位置），**凡是没反查的就漏过去了**。这条规则的命中率完全取决于当时记不记得。

**建议**：把「写后反查三件套」（`Test-Path` ＋ 字节数变化 ＋ 关键词命中数）固化成一行可复制的 PowerShell 片段，写进 opener §五纪律与两份定时任务真身；进一步可包装成 `工具-写后反查.ps1`。
**为什么值得**：它把一条已被违反 4 次的人守规则，变成一个粘贴即用的动作——**符合规则退休制的处置方式（机制化，而非再写一遍）**。

#### 方向 2 · 定量转场判据（治「疲劳末端出错」）

**现状**：转场靠主观判断「session 过长」。
**实证**：本 session 的错误分布明显偏后段——#248 自触发、#254 连续两次插错位置、把「稳扎稳打」误读为「冻结」，**全部发生在第 6 次落库之后**。
**建议**：定量判据（数据可测，sweep 日志里有批次名）——例如「本 session 落库批次 ≥5」或「连续 3 次自查修正」即主动提示转场，而不是等人觉得长。

#### 方向 3 · 把高频手工操作工具化（治「同一个坑反复踩」）

**实证**：本 session 队列行插入位置错了 **2 次**（#248、#254），**根因完全相同**——用「全文最后一个 `| 数字 |` 行」定位 §一 末尾，而 §四 用同样的行格式，于是插到了 §四 去。第二次踩时我甚至刚修过第一次。

**建议**：`工具-共享文档编辑锁.py` 已有 `--reserve` 取号，可再加一个「追加行到指定分区」的子命令，由工具保证插入位置与列数正确。
**为什么值得**：这类错误**不可能靠小心避免**——它每次都长得像新问题（一次是 #248、一次是 #254），只有工具能一次性根治。

#### 方向 4 · 规则体检：29 条里有多少已经是死规则

**建议**（随 #253 清扫顺带做，不单独立项）：对 §5 的 29 条逐条判三件事——① 是否已有机制守（有则正文可降为一行指针，如 #206 对 propose 门禁段的处置）；② 是否从未被违反过（可能是废规则或已内化）；③ 是否已被别处覆盖（重复）。
**⚠️ 边界**：这一步**只判定、不删**，判定结果交你拍板。规则删除比新增更需要谨慎。

### 5b.4 明确不建议的方向

- **不建议新建「错误模式统计台账」**：跨 session 统计哪类错最多确实有价值，但**它本身又是一个需要人维护、且很可能没人读的载体**——正是本诊断要治的病。建议挂进已有的月度环境体检（#98）每月看一次，不新建载体。
- **不建议再加人守规则**：本 session 已新增数条（#246 日期基准、#248 判据关键词、决策路由标注）。**每加一条都在稀释其余所有条**。此后新规则应先问：能不能机制化？不能的话，它是否值得挤掉现有的某一条？
