# 审读件 · P1（第 1/3 批）· `opener-batch-archive-precheck` 6 点

> 🔴 **本包要治的病**：无头批派 opener 时，**不查那条队列行是不是已经做完了**，于是重复派出、白跑一轮。
> 🔴 **贯穿全包的底线是 fail-open**——判不准时**照常派出**（白跑一次），**绝不误跳过**（漏做且无人在场）。以下每一处「代价」都按这条底线权衡。

## 1 · 「这个 opener 对应的队列行已完成」用什么判据判？　🔴 无默认

- **(a) 四态判定：live ＋ 归档都查，归档命中即完成，模糊地带一律 fail-open〔荐〕**　代价：① 归档侧不读状态列，若值周清扫误迁过一条未完成的行，本判据会跟着跳过它（由「迁移本身是人工复核过的完成判定」兜底）；② 「写了行号但查不到」会带告警照跑，告警没人看就等于没拦。
- (b) 只读机器状态字段 `[S:done]`，live 与归档同一套判据　代价：🔴 **在真实数据上会原样重演白跑**——归档里 `#368` 的状态格实测是 `[S:open][D:业] 🆕 2026-08-21 立行，未开工`，按 (b) 判成 open、照样派出。一个「正确实现了规范」的校验器在真实数据上完全失效。
- (c) 只查归档、不查 live　代价：漏掉整个「已完成但还没被清扫」的窗口（清扫每周一次，窗口最长 7 天）；`#395` 当时正落在窗口内，按 (c) 会被派出。
- **手段**：读归档件 `跨桌任务队列-归档-202608.md` L583 `#368` 行原文；2026-09-12 用 `工具-队列查询.py --row 368 --section 一` 复核 live 仍查不到、exit=1。

## 2 · 行号从哪里取（锚点）？　🔴 无默认

- **(a) 沿用 opener 标题，不新增字段；多行号取合取（都完成才算完成）〔荐〕**　代价：标题是自由文本，可能漏写或格式不对 ⇒ 落到「告警＋照常派出」，**不会误跳过**。
- (b) 新增独立字段（如 `▶ 队列行：#397`）作唯一锚点　代价：① 要改全部历史计划文件才能回放验证，而回放正是本包的验收条件；② 计划件由人手写，新增必填字段＝**新增一条人守规则**，与本包「把人守变机制守」的立意自相矛盾。
- (c) 多行号取析取（任一完成即跳过）　代价：违反 fail-open——「一主一并」的 opener 会在并入行先完成时被整条跳掉，而**误跳过无人在场**。
- **手段**：2026-08-25 读两份计划件全部 `### A<N>` 标题原文；2026-09-12 `grep -n` 复核 v1／v2 解析循环都已捕获标题。

## 3 · 校验挂在哪一点、用哪一份实现？　🔴 无默认

- **(a) 解析完成、`-Only` 过滤之后、任何派出／分组动作之前；v1/v2 共用一份 `工具-opener派出前校验.ps1`，判据本体走 Python〔荐〕**　代价：两个 runner 各多一次 dot-source 与 N 次 Python 子进程调用（N＝opener 数，典型 5–15）。
- (b) 放在派出瞬间，各 runner 自带判据　代价：① 泳道清单会打印一批实际不会跑的 opener，**人看到的计划与执行不一致**；② 成员全被跳过的泳道仍会 `Start-Job` 白等一次错峰（默认 90 s）；③ **两份 PowerShell 判据必然漂移**。
- (c) 判据在 PowerShell 内重写表格解析、不调 Python　代价：造第二个会漂移的解析器，且 PowerShell 侧没有反引号游程屏蔽（`#314` 的教训）——含反引号路径的行会切错格。
- **手段**：2026-09-12 对 v1／v2 现取全部关键行号（`-Only`／`Start-Job`／`NO-SENTINEL`／`StaggerSec`／`DryRun`）。

## 4 · 查询结果要不要跨 opener 缓存？　**默认 (a)**

- **(a) 不缓存，每个 opener 各查一次〔荐 · 默认〕**　代价：重复 I/O，几百毫秒量级。
- (b) 缓存一份快照到 `reports/opener-batch/<stamp>/`　代价：🔴 造出一种此前不存在的文件名形态 ⇒ 必须回头补 `.gitignore` 并用 `git check-ignore -v` 实测取证；承担 `#328` 那族风险（凭空造的文件名没人回头看忽略规则，最终被判孤儿、企微群连响 17.1 小时）。
- **不答即按 (a) 执行**（执行者＝承接 apply 的 session；不答的代价是「停在原地」）。

## 5 · `工具-队列查询.py` 怎么扩？　**默认 (a)**

- **(a) 新增两个可选开关 `--include-archive`（默认关）与 `--format json`（默认 text），不传时输出与退出码逐字不变〔荐 · 默认〕**　代价：多两个开关要维护；归档侧章节匹配要另写（归档与 live 的章节标题写法不同）。
- (b) 直接改默认行为：默认查归档、「没找到」改非零退出码　代价：🔴 这本身就是一次「改变既有模块对外语义」，把既有调用方的成败判定静默改掉；而且 2026-09-12 现取发现「未找到」**已经**是 exit=1、与读取失败／参数错共用同一码 ⇒ 即便选 (b) **仍然需要** JSON 才能区分三种结局。
- **不答即按 (a) 执行**。

## 6 · 派单件 frontmatter `status` 回写义务归谁？　🔴 无默认

- **(a) 归执行 session（纯人守）**　代价：这正是已失效的那条路——从未成文却一直指望执行者自觉，2026-09-12 现取 56 份派单件里 **5 份仍是 `待执行`**。错误不产生信号 ⇒ 会一直重复，**单靠 (a) 原地打转**。
- **(b) 归机器：sweep 新增一类，扫全部 `派单件-*.md`，凡 `status: 待执行` 而其引用的队列行已 `done` 或已归档者即告警**　代价：改 `工具-落库sweep.py`（现 8162 行），约扩半天；告警首月可能有噪音。
- (c) 归派出前校验（本包顺带查派单件）　代价：🔴 **判据不可靠**——opener 标题不含派单件路径，只能靠标题文字模糊匹配文件名；**模糊匹配 ⇒ 误跳过 ⇒ 违反 fail-open 底线**。
- **起草方推荐 (a)＋(b) 并用、(c) 明确排除**：(a) 定义义务（机器只能告警、不能代判「这份派单件是否真执行完」），(b) 兜底；🔴 **并建议 (b) 另立一行、不并入本包**（保持单一职责）。
- **手段**：2026-09-12 `ls 派单件-*.md | wc -l` → 56，`grep -l "^status: 待执行"` → 5。
