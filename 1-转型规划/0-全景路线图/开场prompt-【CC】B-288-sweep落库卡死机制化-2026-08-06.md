## 二、问题（完整故障链见队列 #288，此处只给要点）

sweep `main()` 顺序：`_push_any_unpushed_commits` → **`_sync_master_if_behind_origin`** → `_verify_fast_forward` → **批次处理**。

`_sync_master_if_behind_origin` 跑 `git merge --ff-only origin/master`；**本地队列文件脏、而 origin 侧提交也改了队列文件** → git 拒绝 → `SweepAbort` → **批次处理走不到，整轮跳过**。

**🔑 这是必然而非偶发（决定性取证）**：**近 20 个提交触碰 `跨桌任务队列.md` 的是 20/20 ＝ 100%**。故「origin 新提交改了队列文件」概率≈1，而「本地队列脏」也几乎恒真——**两个近乎恒真的条件合取，卡死必然发生**。今日已两次手工介入。

**⇒ sweep 的核心工作对象（队列文件），恰恰是最可能挡住它自己 ff 的那个文件。这是设计缺口。**

## 三、三个候选修法（队列 #288 已写全，此处给取舍提示）

- **A · 先提交再同步再 rebase**（处理批次 → commit → `pull --rebase` → push）——根治；风险是自动 rebase 冲突会留半完成态，缓解＝冲突即 `rebase --abort` 回干净态并告警。
- **B · stash 保护式 ff** —— ⚠️ **本线判断大概率解不了主要场景**：挡住 ff 的常常正是**已被批次声明、不能 stash** 的那个文件。**列出仅供你排除，不建议直接采纳。**
- **C · sync 失败降级为"告警但继续"** —— 止血最快、改动最小：现状是"什么都不做、内容一直悬着"，改后是"至少 commit 到本地不会丢"；残留是本地积累未推送提交、最终仍需人工 rebase。

**Cowork 侧倾向「C 止血 ＋ A 根治」，但取舍由你定，design.md 里须写明为什么这么选、以及被否的那些为什么被否。**

## 四、🔴 一个更根本的观察，请在 design 里正面回应

**主工作区没有任何机制保证它跟上 origin** —— 唯一会 sync 的就是 sweep，而 sweep 恰恰因为脏而 sync 不了。**这是自锁循环：越需要同步越同步不了。**

**若只修 ff 那一步而不看这个循环，可能治标。** 请在 design 中明确：你的修法是打破了这个循环，还是只是让它不再阻塞批次？两者都可接受，但**必须说清是哪一种**。
