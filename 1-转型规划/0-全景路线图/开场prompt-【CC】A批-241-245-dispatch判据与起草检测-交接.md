## 一、#241 —— dispatch 的行→文件匹配判据缺一维（P2）

**触发（真实，非假想）**：#124 阶段二 apply 后**首次真实运行** `ZhuopinFollowupDispatchDaily`，扫到 2026-07-29 的历史积压行，该日期下有 **3 个**同收信人 `.md`，按「收信人＋日期」解析零匹配 → 安全降级 `dispatch_row_skipped_unresolvable`（未发送、未回填、零副作用）。

**机制表现是正确的**，问题在于：**它每天都会再跳一次、再告警一次，而人每次都要重新消歧**。这不是偶发，是判据缺一维。

**两条修法，建议取 ⑴**：

- **⑴ README 行直接带文件名**——新增一列，或在主题列末尾以固定格式附 `→ <文件名>`；起草时由 `readme_table` 统一写入，dispatch 直接读、不再猜。**额外好处**：与 #124 阶段二刚落地的两态语义天然契合（起草即写入行，此时文件名已知）。
- ⑵ 加主题关键词匹配——用 README 主题列关键词与文件名二次筛选，实现更绕且仍留歧义空间。

**🔴 边界（不可越）**：**不得**改成「歧义时猜一个发出去」。**对外发送不可撤回，安全降级是对的、必须保留**——本行只补判据，**不动降级行为本身**。

**历史积压行**：#150 那条（`采购部-姚祖怡-跟进-2026-07-29-批2上月未齐套跨月占用判例批改.md`）**消歧结论已在 #150 行内写死**，直接采用、不要重新消歧；它当前按串行原则暂不发，但**判据修好后应能唯一定位它**——这就是本行的验收样本。
