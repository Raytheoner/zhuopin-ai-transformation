## 〇、为什么这三件放一批

三项是**同一种设计病**的三个实例：**把需要判断的事，交给了一个拿不到判断依据的执行者**。

- **#168**：编辑锁只约束 session，**拿不到"机器人也在写"这个事实**。
- **#163**：把"下一个编号是几"交给人做加法，人手上只有一个易读错的显示值。
- **#147**：把"是否中断"交给一个只知道"有没有人说话"的信号。

修法也同构：**不是加提醒、加纪律、加复核，而是把依据本身补上、把计算收进工具**——与本项目已验证有效的几次修法一脉相承（#126 `resolve_repo_root()` 动态问 git 而非信任调用方传参；#99a `max(可见最大号, 高水位线)`；sweep 判据从"不含 ✅"改成显式"待"字样）。**一次 session 内做完这三件，顺带能把"还有哪些机制在靠人记得"扫一遍。**

**优先级：#168 (P1，有明确时间窗) > #163 (P1) > #147 (P2)。** 若时间不够，**#168 必须做完并部署**，#147 可留下批。

## 二、任务 A：#168 机器人追加队列绕过编辑锁（P1，先做）

### A.1 事实（本次已取证，勿重复怀疑）

`queue_appender.py` **全文零处引用**编辑锁——机器人归档回件时直接读改写队列文件，不 acquire、不 release。**编辑锁只在两个 Cowork/CC session 之间成立，从未管住机器人这个写入方。**

- **风险形态 = 整行丢失，不是撞号。** 取号本身已是全项目最规范的（`_next_task_id` 取 `max(可见最大号, 高水位线)+1`，且 `_bump_section_one_high_water_mark` 会回写，#99a 已修）。
- **触发窗口**：巡逻/专线持锁期间是思考时间、长达数分钟；机器人若在此期间追加一行，会被持锁方稍后的整文件写回**静默覆盖**——正是协议〇.7 建来防的 2026-07-23 事故形态。
- **现有兜底**：`queue_reconcile_sentinel` 每次连接成功后比对近 7 天已归档文件与队列行、漏行私信 Paul（#99b 已让它同扫归档件）。所以是**降级但可被发现**，不是完全静默。
- **已有临时止血（Cowork 侧，2026-07-30 已生效）**：拆件巡逻 prompt 新增「三.5 写回前重读比对合并」。**这是 prompt 层缓解，不是根治**——它只覆盖巡逻这一个持锁方，其他 session 仍裸奔。

### A.2 建议修法（择一，倾向①）

1. **（倾向）`queue_appender` 追加前 acquire、追加后立即 release。** 关键在**取不到锁时不得丢消息**——落 pending 待重试，或沿用 #126 已验证的"⏳未同步"显式标记范式（该范式已在生产跑过，可直接借鉴）。
2. 反向：改为"追加即持锁的极短窗口 + **持锁方**写回前重读比对"。更稳但改动面大、且要求所有持锁方都遵守。**①足以关闭本风险，除非你发现①有硬伤。**

### A.3 必须覆盖的测试

- [ ] 机器人追加时锁空闲 → 正常 acquire→追加→release
- [ ] **锁被他人持有 → 消息不丢**（落 pending / 标记待重试），且**审计留痕**
- [ ] pending 项在下次可拿锁时被正确追加，**不重复追加**（⚠️ #126 踩过"二次追加同一内容"的坑，见 `sync_after_archive` 的 `already_appended_row` 参数）
- [ ] 并发单测：模拟"持锁方读入 → 机器人追加 → 持锁方写回"，断言机器人那行**未被覆盖**
- [ ] release 失败/异常退出 → 锁走陈旧接管路径，不死锁
- [ ] 全量回归零漂移

### A.4 收口

协议〇.7 补一句「**企微机器人亦为受锁写入方**」；`queue_reconcile_sentinel` 的兜底地位在 CLAUDE.md 或场景 CLAUDE.md 中记明（它现在是这条链的最后一道网）。**服务需真实重启验证**（`ZhuopinAibotDevListener`，注意既有孤儿 `python.exe` 自愈逻辑）。
