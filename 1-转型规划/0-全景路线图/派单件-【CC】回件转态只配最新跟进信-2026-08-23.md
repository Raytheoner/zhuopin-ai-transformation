## 一、🔴 先说三个方案的取舍，免得你照着旧的做

## 一bis、🔴 实测：B 为什么不能进配对判据（这段是 `OP-0823-D` 开工前 CC 的实测 ＋ Cowork 独立复核，两方一致）

对生产 README 跑判定，**两种「在途」定义给出完全相反的结果**：

| 收信人 | 按 B（所有未闭环） | 按 C（最新一封是否闭环） |
|---|---|---|
| 采购部 · 姚祖怡 | **5 封** ⇒ 撞「≥2 拒绝」 | 最新 `采购部#17` 已闭环 ⇒ 闸开 |
| 财务部 · 唐燕萍 | **7 封** ⇒ 撞拒绝 | 最新 `财务部#15`（08-23 发）⇒ 闸锁 |
| 质量部 · 陈忱 | **4 封** ⇒ 撞拒绝 | 最新 `质量部#8` 已闭环 ⇒ 闸开 |
| IT部 · 陈承 | **4 封** ⇒ 撞拒绝 | 最新 `IT部#9`（08-18 发）⇒ 闸锁 |

⇒ **按 B 实现，四位收信人一个都不会命中，机制上线当天就是哑的**（同「建成 9 天从没响过」那一族）。

**卡住的是什么**：`采购部#1-#5`／`财务部#1-#6`／`质量部#1-#4`／`IT部#1-#3` —— 全是 **2026-07-31 建立编号体系之前**的早期信，状态列大概率从未被维护。**真正在途的只有 `IT部#9` 与 `财务部#15` 两封。**

🔑 **B 的根本错误（比「恒不命中」更要紧）**：跟进闸的判据是「**该收信人最近一封的状态是否已闭环**」——**只看最新一封**。B 引入的是**第三种「在途」定义**，与闸不一致 ⇒ **配对和开闸用两把尺子，必然出现「配上了但闸没开」或反过来**。**C 与闸是同一把尺子，这才是它真正的优势**，不只是「更简单」。

⚠️ **还有一个更早的提议也已作废**：「读回件正文首行『关于 title: "…" 的回复』提取标题再配对」——**实测 `7-外部文档` 下「文本反馈」类回件 32 份，具备该首行格式的仅 4 份（12%），且四份全部出自陈承一人**。样本同源，不成立。

## 二、为什么「匹配不上就不动」不能留（它的理由曾经是对的）

桥一 docstring 写：「一条文本回件无法确定地指向哪一封信，硬配会造出比漏配更难发现的错误」。

**这个判断在「靠内容猜」的前提下成立**，但它导致的后果已实测到：
- 2026-08-23 实测：README 中 **12 封信状态列停在「✅ 已推送」，全部是 2026-08-03 及更早发出的**，最久积压 20 天以上；
- 后果有两个，第二个此前没被点破：**⑴ 串行闸误锁**（该发的信发不出）；**⑵ 度量失真**——「未转态」与「回得慢」在数据上长得一模一样，我们在一份自己没维护好的账上做度量决策。

⇒ **Shao Peishen 的解法是换掉前提，不是改进猜法**：不按内容配，**按位置配**——回件永远属于该收信人最新的那封信。

## 三、规格（可实现）

### 3.1 配对规则（本件的全部核心）

> **两级通道，第一级命中即止：**
> **① stem 精确匹配**（现有 `reply_matches_letter`）⇒ 命中即配那封信。
> **② 未命中时的后备：配「该收信人最新一封已发出的信」** —— 不看文件名、不看正文、**docx 与纯文字一视同仁**。
> **「最新一封已发出」＝ 排除状态列为 `⏳ 待你审` 的行后，按日期／编号取最大的那一行**（**与跟进闸的判据同一把尺子**，见 §一bis）。

**实现要点**：
1. 取收信人（机器人落档时已知发件人企微 userid，映射到 README「收信人」列）；
2. **先跑 ① stem 精确匹配**；命中即转态，**不进 ②**；
3. **① 未命中 ⇒ 走 ②**：取该收信人最新一封已发出的信 —— **该信未闭环** ⇒ 命中，按 §3.2 转态；
4. **该信已闭环** ⇒ **不动 README**，记审计 ＋ **低噪提示**。这是 §3.3 说的「闭环后的补充说明」，**是预期内常态，不得升级为需人处置的告警**；
5. **该收信人无任何已发出的信** ⇒ 不动 README，记审计 ＋ WARN（**fail-loud**，可能是收信人映射错了）；
6. **审计事件须记录本次命中的是 ① 还是 ②、或落在第 4／5 条哪个分支**，便于日后复盘误配。

⚠️ **为什么保留 ① 为第一优先**：它的确定性最高（文件名逐字对上），且**去掉它会造成净回归** —— 今天能正常转态的 docx 回件，改动后反而会因为走 ② 而受制于「最新一封」的判断。**两者结果一致时本就是同一封；不一致时以确定性更强的为准。**

### 3.1bis 独立健康检查（不进配对，另出一条低噪提示）

方案 B 的价值不作废，但**位置换掉**：另做一条检查 —— **某收信人有 N 封已发出且未闭环的历史信** ⇒ 低噪提示（当前实测：姚祖怡 5／唐燕萍 7／陈忱 4／陈承 4，共 20 封，多为 2026-07-31 编号体系建立前的早期信）。
🔴 **它只报数、不参与任何转态判定**，也**不得阻塞配对**。

### 3.2 转态与解锁

- **桥一（回件到达）**：把该信状态改写为第九态 `📨 回件已到，待拆件 <UTC>`。**闸仍锁**——回件到达 ≠ 已回灌。
- **桥二（拆件回灌完成）**：人在编辑锁 `release` 时声明本次已完成回灌 ⇒ **机器自动把该信转闭环态并开闸，不再要求人手工去 README 改那一格**。

🔴 **这一步是本件相对现状的真正增量**：现状是桥二**校验**人有没有改（`_validate_followup_reply_state_sync` 把人拦下来），**改成由机器代写**。人只需声明「回灌完了」，不需要知道是哪封信、也不需要手写状态列。

### 3.3 🔴 补充与更改：只吸收语义，不影响状态机（Shao Peishen 2026-08-23 定案，**本节是硬边界，不要扩**）

他的原话：「**一次回灌对上就转态、闭环、开闸；补充内容你只吸收语义，不影响串行机制**，我让专员业务问题尽量精准回复，补充内容提供说明。」

**实际形态**：专员回件之后，常会再用平信补充说明，偶尔还会更改前述内容。**但这不改变状态机**：

1. ✅ **一次回灌对上，就一次走完**：`转态 → 闭环 → 开闸`，**不分两步、不设等待期、不因为「可能还有补充」而推迟闭环**。
2. ✅ **闭环后到达的补充／更改照常落档**（`7-外部文档/<部门>/`），拆件时照常读、语义照常吸收进队列与口径 —— **但 README 状态列一字不改、闸不重新锁、不重开在途**。
3. 🔴 **因此 §3.1 第 4 条那个「最新一封已闭环 ⇒ 不动」分支是预期内常态，不是异常**：闭环后的补充必然走到它。**告警级别须相应压低**（记审计 ＋ 低噪提示即可），**不得升级为需要人处置的告警** —— 否则每一条补充说明都会制造一次假警报，而那正是 §四 `#87` ⑶ 记的「误报训练人忽略告警」。

⚠️ **本项目对这条取舍的风险是知情且接受的**：后到的「更改」若推翻了前一份回件的结论，**机器不会拦**——**这一段由组织侧兜底**：他已明示会要求专员「业务问题尽量精准回复，补充内容只提供说明」。**⇒ 实现方不得因担心这个而自行加回等待期或可重入态。**

**📌 本条口径当日经三次调整才定稿，沿革记此免得后人重推**：初版「只配最新」→ 纠正为「唯一在途」（更完整）→ 一度按「回灌全貌、等补充齐了再闭环」设计 → **他本人叫停并恢复已定的两桥机制**，理由是那把简单问题复杂化了，且组织侧有更省的解法。

### 3.4 必须保留的行为（不在本次改动范围，别顺手删）

- **走编辑锁**，不得绕开协议〇.7；`acquire` 拿不到锁须指数退避重试，放弃时打日志并告警（现有实现已有，保留）。
- **审计事件照记**，并**新增记录本次命中的是哪条规则**（便于日后复盘误配）。
- **fail-loud**：收信人映射不到、或该收信人在 README 中一封已发出的信都没有 ⇒ 记审计 ＋ WARN，**不静默跳过**。

## 四、✅ 原歧义已由他本人消解，此处记录结论与理由（不必再问）

他初版说「确认是回灌就状态，解锁」时，曾有两种读法：**⑴ 回件到达只打第九态、由人确认回灌后才闭环开闸；⑵ 回件到达即视为回灌，直接闭环开闸。**

✅ **2026-08-23 他本人定案：读法 ⑴，理由是「回灌」本身就是人做的语义动作，机器判不了**——不是因为要等补充（那条已被 §3.3 明确排除）。

⇒ **定案**：**回件到达打第九态**（可见性，闸仍锁）；**人拆件回灌 → 一次走完 `转态 → 闭环 → 开闸`**，机器代写 README、代开闸，人不必知道是哪封信、也不必手写状态列。**两桥各司其职，这正是他说的「恢复已定机制」。**

**⇒ 本节不再是待问项，开工直接按 §3.2＋§3.3 实现。**

## 五、验收

1. **真实回件复现（不许只跑 fixture）**：造一条纯文字回件（历史上必然配不上的那类），确认它现在**能**打上第九态，且命中分支被审计记录。
2. 🔴 **两级通道与三分支各一条，缺一不可**（对应 §3.1）：
   - **① stem 命中** ⇒ 配到 stem 对上那封，**断言没有走 ②**（即使 ② 会给出另一封）；
   - **② 后备命中** ⇒ 纯文字回件、stem 无法命中，配到「最新一封已发出且未闭环」的那封；
   - **② 但最新一封已闭环** ⇒ README 一字未改，**只有低噪提示、无需人处置的告警**（专防「每条补充说明制造一次假警报」）；
   - **该收信人无已发出的信** ⇒ README 一字未改，WARN 已打。
3. **`⏳ 待你审` 跳过验证**：构造「该收信人最新一封是待审、次新一封已发出未闭环」的场景，断言配到的是**次新那封**。
4. 🔴 **生产真身冒烟（不许只跑 fixture）**：对当前 README 跑一次判定，断言 **`IT部#9` 与 `财务部#15` 能被正确定位为各自收信人的目标信** —— 这两封是实测中仅有的真在途件；同时断言**那 20 封历史未闭环信没有阻塞任何一次配对**（专防方案 B 那个「上线即哑」的形态）。
5. **回归零漂移**：`wecom-aibot-service` 全量 ＋ `0-学习与工具`（编辑锁桥二侧）全量，`openspec validate --all --strict` 不新增失败。
6. 🔴 **补充不影响状态机（§3.3）**：对一封**已闭环**的信再投一条回件，断言 ⑴ 该回件**已落档**；⑵ README 状态列**一字未改**、闸**未重新锁**；⑶ 该分支**只记审计＋低噪提示，未产生需人处置的告警**（**这条专防「每条补充说明都制造一次假警报」**）。
