## 一、T1 · worktree repair 演练 —— 完成，但派单件写法有致命缺陷

### 1.1 步骤 1 复制：`/COPYALL` 直接跑不起来（**坑 D1**）

派单件与迁移方案 §八 指定的 `robocopy … /COPYALL`，在**非管理员** shell 下 **0.1 秒即退出、退出码 16、一个字节没复制**：

```
ERROR : You do not have the Manage Auditing user right.
*****  You need this to copy auditing information (/COPY:U or /COPYALL).
```

`/COPYALL` ＝ `/COPY:DATSOU`，其中 `U`（审计信息）需要 `SeSecurityPrivilege`。
**改用 `/COPY:DAT /DCOPY:DAT` 后成功**（这是**改判 D1**，见 §四）：

| 项 | 值 |
|---|---|
| 退出码 | 1（＝有文件被复制，`≤7` 为成功） |
| Dirs / Files / Bytes | 14,817 ／ **57,210** ／ **1.393 GB** |
| **FAILED** | **0** |
| 墙钟耗时 | **165.3 s（2 分 45 秒）**，均速 655 MB/min |

⚠️ **派单件预期的「副本文件数应 ≈ 47,578」这条核对判据已失效**：实测 **57,210**，差 20%。原因是本会话开工时新建了一个 worktree（`onedrive-migration-drill`，约 1,700 文件）——**即「文件数」这个校验目标本身每天都在漂，不适合当迁移的一致性判据**。建议 S3 改用「源与目的地文件数**相等**」这一相对判据，而非写死的绝对数。

### 1.2 🔴 步骤 2 是本次演练最重要的发现：裸 `git worktree repair` 会劫持生产

**复制完成后的实测状态**（只读取证，未执行任何写操作）：

```
副本 .git/worktrees/<x>/gitdir        → C:/Users/Paul Shao/OneDrive/.../企业AI转型/.claude/worktrees/<x>/.git
副本 .claude/worktrees/<x>/.git       → gitdir: C:/Users/Paul Shao/OneDrive/.../企业AI转型/.git/worktrees/<x>
副本 git worktree list                → 27 条，prunable = 0
```

**两侧管理文件全部指向生产**，且 `worktree list` **一条 prunable 都不报**——因为那 26 个路径**真的存在**（它们就是活着的生产 worktree）。

⇒ 若此时按派单件字面「在副本主仓库跑 `git worktree repair`」，`repair` 会沿着这些记录的路径找到**生产** worktree 并去「修」它们。

**没有在生产上验证这个猜测，而是先在一次性玩具仓库里复现了完全相同的拓扑**（`C:\Dev\_drill\_lab1`，原始仓库 ＋ 其副本），然后在**副本**里跑裸 `repair`：

```
### 在【副本】跑裸 git worktree repair
repair: .git file incorrect: C:/Dev/_drill/_lab1/orig/wts/wt1

--- 之后 · 原始仓库（模拟生产）---
orig/wts/wt1/.git  : gitdir: C:/Dev/_drill/_lab1/copy/.git/worktrees/wt1     ← 🔴 被改指到副本
--- 之后 · 副本 ---
copy/wts/wt1/.git  : gitdir: C:/Dev/_drill/_lab1/orig/.git/worktrees/wt1     ← 副本自己一个字没修

原始 worktree 的 git-common-dir → C:/Dev/_drill/_lab1/copy/.git             ← 🔴 已绑到副本
```

**危害确认，且比预判更糟——三件事同时成立**：

1. **改的是原始（＝生产）那一侧**，把 26 个生产 worktree 全部改绑到 `C:\Dev\_drill\zhuopin-ai\.git`；
2. **副本自己一处也没修好**——即"演练目标"根本没达成；
3. **不报错**。每个 worktree 只输出一行 `repair: .git file incorrect: <路径>`，读起来像诊断信息，不像"我刚把你的生产指针搬走了"；被劫持后的 worktree 跑 `git status` **完全正常、静默通过**。

🔴 **最致命的是第二棒**：派单件 T1 末尾写着「收工前删除副本 `C:\Dev\_drill\`」。若前一步照做，这一步会**删掉 26 个生产 worktree 此刻所依赖的 git 目录**——26 个 worktree 连同其中未提交的改动一起报废，而在此之前的每一条命令都显示成功。

### 1.3 正确形式（已在实验室验证，可直接写进 #170 的 S3-10）

在 `_lab2` 里复现**真实迁移场景**（整树移动、旧路径消失，`worktree list` 报 `prunable`、worktree 内报 `not a git repository`——与生产 #406 的症状一致），对比两种写法：

| 写法 | 结果 |
|---|---|
| **(a)** `git worktree repair`（裸） | 🔴 **什么也没做**。零输出、退出码 0、仍然全部 `prunable` |
| **(b)** `git worktree repair <每个新路径>` | ✅ **全部修好**。prunable 归零，`status` 正常，`git-common-dir` 正确 |

并在 `_lab3` 验证**副本场景下 (b) 是否安全**：在副本里 `repair` 并显式传**副本自己的路径**——
✅ 副本两侧修好，**原始仓库两个文件逐字未变、`git-common-dir` 仍指向自己**。

> 🔑 **判据（建议写进 #170 与取证知识库）**：
> **`git worktree repair` 的作用对象由「它读到的路径」决定，不由「你在哪个仓库里执行」决定。**
> 在一个"管理文件仍指向别处"的仓库里跑裸 `repair`，它会忠实地去修**别处**。
> ⇒ **一律显式传路径，永不裸跑。** 两种误用的失败**都是静默的**：移动场景静默什么都不做，复制场景静默改坏源仓库——正是根 CLAUDE.md「工具静默回退」同族的第四、第五个实例。

### 🔴 3.1 顺带发现：注册脚本**不是原子的**，失败会留下"任务被删掉且没建回来"

脚本第 3 步的写法是：

```powershell
if (Get-ScheduledTask -TaskName $TASK …) { Unregister-ScheduledTask -TaskName $TASK -Confirm:$false }
Register-ScheduledTask -TaskName $TASK …      # ← 本次在这里 Access denied
```

**本次侥幸无恙，只因 `$TASK` 已被改成影子名、那个任务本来就不存在，先删那一步被跳过了。**
**若照 S3-13 在真实迁移中重跑本脚本刷新 4 个生产任务、而 shell 恰好没提权**，顺序会是：**先把生产任务注销掉 → 再注册失败** ⇒ **落地状态是"任务没了"**，且脚本已退出、不会自愈。

⚠️ **如实标注：`Unregister-ScheduledTask` 在非提权下究竟能不能删掉本用户的任务，本次没有实测**（要测就得拿生产任务当靶子，已放弃）。所以上面是**一条有依据的风险，不是已证实的事实**。
**建议 S3-13 加一条前置守卫**：注册脚本开头先自检是否提权，未提权即**在动任何任务之前**直接退出。

**动作集合与派单件完全相同**（9 个 uninstall ＋ 9 个 install，一个不多一个不少），只是交错执行。
