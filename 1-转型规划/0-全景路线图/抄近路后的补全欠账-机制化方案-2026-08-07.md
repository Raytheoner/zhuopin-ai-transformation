# 抄近路之后，谁保证流程被补全（2026-08-07）

## 〇、把问题定准（这一步决定后面全部对不对）

抄近路跳过的**不是"登记"，是"分发"**——他直接给出建造指令，绕开值周巡检／拆件巡逻的派活环节。

**分发被跳过，本身没有危害**：任务照样登记在队列、照样有行号、照样被 sweep 落库。

**真正会静默丢失的，是建造「之后」本该发生、却没有任何东西盯着的补全动作。** 因为：

> **分发有人催（巡检每周一出计划），补全没人催——它排在建造之后，而建造完成的那一刻，注意力就转移了。**

所以本方案不去管"能不能抄近路"（能，那是他的判断），只管**抄完之后欠的账会不会被机制自己找出来**。

## 一、欠账分三类，其中一类已经有机制了

| 类 | 欠什么 | 现状 |
|---|---|---|
| **① spec 同步** | 变更包完工但**未归档** ⇒ 其 spec delta 永远进不了 `openspec/specs/` | 🔴 **无任何机制**，且**已在真实产生后果**（见 §二） |
| **② 任务登记认领** | 认领了不留痕、批次不预登记 | ✅ **已机制化** —— #236(1) 的 `queue-claim-time-preregistration` 已 apply 并归档进 `openspec/specs/`（2026-08-06）。**本方案不重复造。** |
| **③ 权威件同步** | 建造先落地，而口径变更该同步的全景规划／实施计划／前置总表停在旧口径 | 🟡 **无机制，且本方案也盖不住**（见 §四，如实登记） |

**⇒ 本方案只做 ①，并如实说明 ③ 盖不住。**

## 二、① 不是理论风险 —— 它此刻正咬着 #295

**实测（2026-08-07，逐条附证伪命令）：**

| 事实 | 证伪命令 | 实测结果 |
|---|---|---|
| FI2 在 spec 层**完全不存在** | `ls openspec/specs/ \| grep -i "fi2\|invoice"` | **零命中** |
| 而 FI2 的 spec 其实早写好了 —— **5 个** capability delta | `find openspec/changes/fi2-recon-mvp -name spec.md` | `fi2-feed-source`／`fi2-match-engine`／`fi2-price-check`／`fi2-recon-report`／`fi2-result-classify` |
| 它们进不去的唯一原因：**包没归档** | `git log -1 --date=short -- openspec/changes/fi2-recon-mvp` | 最后改动 **2026-08-04**，仍在 `changes/` |
| 而这个包**实际上已经做完 90%** | `grep -c '^- \[x\]' tasks.md` ／ `'^- \[ \]'` | **已完成 116 ／ 未完成 13** |

**⇒ FI2 已部署 `.51:8094`、已在给唐燕萍试用、现在还要接 #295 的新建造 —— 而它在 `openspec/specs/` 里根本不存在。**
**⇒ #295 的 CC 一旦跑 `/opsx:propose`，它要 delta 的那个基线是空的。**

这正是「完工即归档」作为**人守规则**的失效形态：规则写在 CLAUDE.md §5，**没有任何机制检查它**，于是一个 116/129 完成度的包在 `changes/` 里躺了 3 天，把整个 FI2 的 spec 层一起扣在里面。

## 三、方案：两项检测挂 sweep，纯提示不阻断

**为什么挂 sweep**：它是**唯一同时覆盖 CC 与 Cowork 两条路径**的机制（每小时跑，不依赖任何人记得），且已有两个同构先例可直接复用——`_find_missing_deployment_trace`（#229：命中白名单却缺留痕即提示）与 #236(2) 的孤儿超时告警（阈值 + 周期性再提醒 + 消失即清除）。

### M1 · 已部署场景的 spec 覆盖缺口检测（**优先做这个**）

- 对已部署场景白名单（**复用 #229 既有的 `DEPLOYED_SCENARIO_PREFIXES`，不新建第二份清单**）逐个检查：该场景在 `openspec/specs/` 是否至少有一个 capability。
- 零命中 → 告警「**该场景已上线并在接新建造，但 spec 层不存在**」，并**顺带指出它的 spec delta 躺在哪个未归档的包里**（扫 `changes/*/specs/` 即可定位，无需人去猜）。
- **为什么它比 M2 更该优先**：它直接回答「可追溯吗」这一问 —— 一个已上线场景在 spec 层是空的，就是可追溯链断了，与包滞留几天无关。

### M2 · 在途变更包滞留提示

- 扫 `openspec/changes/*/`（排除 `archive/`），算最后 git 改动距今天数 + `tasks.md` 完成率。
- 告警判据**不是单纯的天数**，而是「**完成率高 + 长期无改动**」（如 ≥80% 完成且 ≥7 天无改动）—— 这正好命中 `fi2-recon-mvp`（90%／3 天）与 `wecom-aibot-channel`（82%／16 天），而**放过** `wecom-listener-macos-migration`（19%，明显还没做完）。
- 🔴 **必须支持降噪**：包内 `proposal.md` 或对应队列行**已写明"刻意暂不归档"及理由**的，只列不催（`aibot-queue-sync-checkout-guard` 即为此类）。**不做这一条，本检测第二周就会被无视。**
- 复用 #236(2) 的周期性再提醒语义（每满一个阈值周期提醒一次，归档即清除）。

### 边界（**实现说明必须原样写明，不得表述为质量保证**）

- **纯提示、不阻断、不改退出码** —— 同 #229。
- **只判「spec 存不存在」，不判「spec 对不对」** —— 一个空壳 capability 也能让 M1 静音。**它拦住的是"压根没同步"，拦不住"同步得不对"。**
- **不自动归档** —— 归档要跑 `/opsx:archive` 并做完工判断，那是 CC 的事，机制只负责让欠账不静默。

### openspec 判定

对照 CLAUDE.md §5 机制类三条门槛：①改变全项目口径？**否**（纯新增告警输出，不改任何既有判据）；②涉鉴权？否；③改既有模块对外语义？否。**⇒ 建议不触发 openspec**，与 #229／#236(2) 两个同构先例一致。若 CC 实现时判断命中门槛，以 CC 判断为准。

## 四、③ 权威件同步 —— 本方案**盖不住**，如实登记

**场景**：#295 建造 FI2 新发票源；而 #252（重组循环第 6 例第②步：把发票源口径变更落进全景规划／实施计划／前置总表）**是另一条线的另一行**，目前状态为「📤 已派发 Cowork 全景路线图线」、尚未完成。

**若 #295 先落地而 #252 没跟上**：三份权威件继续描述旧的「U9C 应付单附件 ＋ OCR」口径，而生产已经是税务导出 Excel。

**为什么 M1／M2 盖不住**：那三份是 `.md` 权威件，**不是 openspec spec**，不在 M1 的扫描域内。

**能盖住它的是 #203 的 (a)**（sweep 检出 commit 触碰判据类文件却无复检声明）—— 而 **#203 已于今日拍板 (b)，明确不做**。

**⇒ 这道口子如实敞着。** 本方案不假装闭合，也不建议为它翻案（(a) 须 design 审，当前在途包已 5 个）。**当前唯一的防线是 #295 行内已写死的指针（指向 #249／#252）＋ 派单件里的提示 —— 那是人守，会不会守住取决于 CC 读不读到。**
