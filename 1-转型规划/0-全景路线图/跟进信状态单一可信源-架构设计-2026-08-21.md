# 跟进信状态 · 单一可信源架构设计

## 〇、先纠正一个前提：**不是同一份状态存了两遍**

这个前提如果成立，合并就是正解。但实测不成立：

| 载体 | 存的是什么对象 | 状态字段 |
|---|---|---|
| `README-跟进机制与命名约定.md` | **一封信**（编号／收信人／事项／交期） | 发送状态列 —— 八态语义，机器可写，`release` 有校验 |
| `跨桌任务队列 §一` | **一个任务**（领取方／输入指针／期望产出／触碰区） | `[S:xxx][D:x]` ＋ 中文状态正文 |

**信不是任务。** 队列里没有一格叫「这封信发出了没」。

**真正发生的是交叉引用，而且量很大（2026-08-21 实测）**：

| 指标 | 机制环境队列 | 业务场景队列 | 合计 |
|---|---|---|---|
| 队列正文引用 `部门#N` | 373 | 133 | **506** |
| 队列正文出现「串行闸」 | 99 | 28 | **127** |
| 明确的快照式引用（「等/待 部门#N 闭环/回件」） | 1 | 4 | **5** |
| README 反向引用 `§一 #N` | — | — | **31** |

⇒ **两个载体互相引用 500 多次，是双向耦合，不是数据冗余。**

🔴 **由此得到本件最要紧的一条判断**：

> **合并到一个文件，那 506 处交叉引用一处都不会消失，只是都搬进同一个文件里。**
> **引用只要是「人写的文字」就会过时——与它写在哪个文件无关。**

今天实测的漂移全部是这个形态：`#361` 行内更正了、接力件 §六 没跟着改；README 状态列脚本改了、编号列没跟着改；6 处文本还停在「等 #16」。**这几处本来就在同一个文件里，照样漂。**

---

## 一、对「合并成一处」的评估

**可行，但治不了病，且有三条实打实的成本。**

1. **README 有一整套只属于「信」的规范**：按部门连续编号且不回收、四态→八态语义、命名四律、docx 必发、判例批改法格式、作废与删除规则。这些搬进队列会让队列（现 1.9 MB ＋ 0.35 MB）再涨一大截，而队列每个 session 开工必读。
2. **两处机器判据绑着 README 的物理结构**：`_validate_followup_readme_release`（release 门禁）与 `push_followup_letter.py --match-topic`（按「主要事项」列定位）。合并＝改生产脚本 ＋ 改门禁，须走 openspec。
3. **串行闸的判据是「按收信人取最近一封」**——README 天然按信排列，做这个聚合是一次线性扫描；队列按任务排列，要另建索引才能算。

**⇒ 结论：方向对（要单一可信源），但「一处」不该是「一个文件」。**

---

## 二、我的建议：**写侧单一化 ＋ 读侧派生化**（两侧都做，才是真的单一可信源）

本项目已经有这个模式的成功先例——协议〇.5：**「查队列行状态一律用只读 CLI（`工具-队列查询.py`），不裸读/裸截断」**。队列有唯一权威文件，但**没有人被允许直接读它来判断状态**。**跟进信状态缺的正是这一层。**

### S1 · 明文确立：**「信的状态」唯一权威 ＝ README 发送状态列**

已是事实（脚本只写它、门禁只校验它），但从未写进任何纪律。写下来，**并明确队列不是信状态的载体**。

### S2 · 队列**禁止复述**信状态，只允许写指针

- 违规形态：`等姚祖怡采购部#16 闭环` ／ `串行闸锁着` ／ `待 #17 回件`
- 合规形态：`串行闸状态见 README 该收信人最近一行（跑 <闸查询命令>）`
- **机器守**：`工具-队列结构lint.py` 加一条判据，命中「(等|待)…部门#N…(闭环|回件|回灌)」即违规。
- 💡 **改造成本极低**：**存量只有 5 处**（实测），一次改完。

### S3 · 新增只读派生入口：`工具-跟进闸查询.py`（或并入 `工具-队列查询.py --gate`）

```
python 0-学习与工具/工具-跟进闸查询.py --to 姚祖怡
# → 闸：🔒 锁  ｜ 依据：采购部#17（2026-08-20 12:20 UTC 已推送，在途）
#   最近入信：§一 #362/#364（2026-08-21 13:13 落盘，待拆件）
#   下一个可用号：采购部#18
```

**所有消费者一律跑它，不读任何一处文字。** 它是**派生的、不可写**，所以永远不会与权威源漂移。

🔑 **这一条同时解决了他真正的诉求**——「唯一读写入口」中的**读**。今天之所以要问「是不是还锁着」，就是因为**没有一个地方能一句话回答这个问题**，只能去读六处文字然后自己拼。

### S4 · 补上两座机器桥（写侧，＝ `#366` 的 M1／M4）

- **入信桥**：机器人自动追队列行的**同一次动作**里，把 README 该行标为**中间态「📨 回件已到，待拆件」**（新增第九态）。⇒ 「回件到了」立刻在权威源上可见，不必等人拆件。
- **回灌桥**：`release` 反向校验——队列中存在指向某封信的入信行且已 `[S:done]`，而 README 该行仍非闭环态 ⇒ **拒绝 release 并提示转态**。⇒ 拆件的人**不可能忘**。

### S5 · 🔴 写侧单一化（本设计的关键一步，也是最容易被跳过的一步）

**README 发送状态列改为「机器专有列」——只能由脚本写，人手改一律被 `release` 拒绝。**

- 唯一写入口：`push_followup_letter.py`（发送）／`approve_followup_letter.py`（批准）／新增 `set_letter_state.py`（转闭环态，须带 `--evidence` 指向队列行号）
- **人要转态，也走命令，不手改单元格。**

**为什么这一步不能省**：S3 只是把「读」收敛到一个出口；**只要那一格还能被人手写，它就还会与队列里的 506 处引用打架**。**两侧都单一化，才是真的单一可信源。**

## 三、更激进的一个选项，以及我不推荐它的理由

**S6 · 把信台账整体结构化**（`followup_letters.yaml` 或 SQLite），`README.md` 由脚本渲染生成、人不得直接编辑。

- **优点**：从根上消灭手写状态，查询/聚合/校验全都变简单。
- **不推荐的三条理由**：⑴ 与本项目 md ＋ git ＋ 编辑锁的整套文化冲突，所有既有工具都要重写；⑵ README 里**大量内容是人写的叙述**——闭环依据、取证过程、勾选控件读法、同族复发分析，这些结构化不了，硬塞进 YAML 会失去可读性；⑶ 渲染产物入 git 会产生大量 diff 噪音，反而伤害「原文原样、可 grep」这条已被验证的优势。
- **⇒ S5 就是它的折中版**：**只把「发送状态」这一列变成机器专有**，其余保持人写的 md。收益的大头拿到，成本的大头避开。

## 四、建议的落地次序（S2 与 S3 可立刻做，且不碰生产码）

| 步 | 内容 | 归属 | 成本 |
|---|---|---|---|
| **1** | S1 写进 README 顶部与根 CLAUDE.md §5 一行 | Cowork | 极低 |
| **2** | S2 改掉存量 5 处快照 ＋ 加 lint 判据 | Cowork 改文 ／ CC 加判据 | 低 |
| **3** | S3 只读闸查询 CLI | CC | 中（纯读，无风险） |
| **4** | S4 两座桥（`#366` M1／M4） | CC，须走 openspec | 中高 |
| **5** | S5 状态列机器专有 ＋ `set_letter_state.py` | CC，须走 openspec | 高 |

🔑 **次序是有讲究的**：**先做 3（读侧派生），再做 5（写侧收口）**。因为只要 S3 一上线，「状态到底是什么」就有了唯一答案，**此后任何手写漂移都会被这个命令当场照出来**——这为 S5 提供了它需要的证据基线。反过来先做 S5，会在没有观测手段的情况下改写路径。

## 五、需拍板

**本设计整体走不走？走的话到哪一步为止？**

- **(a) 只做 1-3**（明文化 ＋ 禁复述 ＋ 只读闸查询）—— 成本最低，**立刻解决「问一句就能知道闸开没开」**，但状态列仍可手写。
- **(b) 做 1-4** —— 加上两座机器桥，**回件到达与回灌完成都不再依赖人记得**。
- **(c) 全做 1-5** —— 状态列机器专有，人肉同步从写侧彻底消失。
- **(d) 按他原议合并成一个文件** —— 本件不推荐，理由见 §一。

**推荐 (b)，并把 (c) 作为 (b) 跑顺后的下一步**。理由：(b) 已经覆盖了今天实际咬人的两次（质量部#8 回灌完闸没开、采购部#17 回件到了没人知道）；(c) 的收益是防「人手改错」，而那个形态目前**还没有实测发生过**——按本项目「先取证、后动作」的惯例，等它真发生一次再做也不迟。
