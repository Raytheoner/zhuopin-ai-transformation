### 🔴 ⑶ 之专段 · 裸竖线根治（Shao Peishen 2026-08-19：「裸竖线这个顽固我们刚刚花大力气治愈，又发作了，必须根治」）

**根因已定位到具体代码，可证**：`0-学习与工具/工具-共享文档编辑锁.py::_build_append_row_line`

```python
if len(cells) != expected:
    raise AppendRowFailedError(f"§{section} 需要 {expected} 个 --cell（不含编号列），收到 {len(cells)} 个")
for i, cell in enumerate(cells, start=1):
    if _cell_has_bare_pipe(cell):
        raise AppendRowFailedError(f"第 {i} 个 --cell 含竖线「|」…")
```

🔴 **arity 检查在裸竖线检查之前，且失败即 `raise`。而裸竖线最高频的形态——「漏写 `--cell` 分隔符，竖线连同下一列内容粘进上一个 cell」——必然同时使 cell 数变少 ⇒ arity 先失败 ⇒ 裸竖线检查永不执行。**
**⇒ 作者看到的诊断是「收到 N 个」，指向"数数"；真因是那根竖线。守卫存在，但在最常走的那条路上被自己前面那道检查遮蔽了（shadowed）。** 这就是 #164／#225／#258 花大力气装了守卫却仍在 2026-08-19 第 6 次复发的机制解释。

**要做两件：**

**⑵-a（必做，零争议，几行代码）**：arity 失败时**顺带扫一遍所有 cell**，若任一含 `|`，错误信息合并为——「收到 N 个（期望 M）；**且第 i 个 cell 内含裸竖线「|」，极可能是漏写了 `--cell` 分隔符、把两列粘成了一列**」。**把误导性诊断改成指向根因的诊断。** 配单测：**复现 2026-08-19 那次真实调用**（commit message 连同一根 `|` 粘进上一个 cell），断言错误信息里同时出现列数与裸竖线两项。

**⑵-b（须 design 审，不得自作主张）**：考虑新增 `--row-md '| a | b | c |'`，允许直接传整行 markdown 由工具切分。
🔴 **理由是表示法失配**：人在写表格内容时天然以「行」为单位思考、天然打竖线，而现接口要求把一行手工拆成 N 个 `--cell`——**这道转换本身就是错误来源，6 次复发里至少 2 次是它造成的**。
⚠️ **但它与既有设计意图正面冲突**：模块 docstring L116 明写「**不接受预拼好的整行字符串**」，那是为了替代旧的"用全文最后一个竖线定位"的脆弱做法、刻意定的。**⇒ 必须作为 design 决策点交 Shao Peishen 拍，不得直接实现。** 若否决，则退而求其次：错误信息里直接给出**修正后的完整命令行**供复制。

🔑 **⑴ 与 ⑵ 必须同车的理由（这是本条最该记住的一句）**：`append-row` 是**真正写盘的那个咽喉**，而它身上**已被发现两次守卫缺位**——锁归属不校验（`acquire`/`release` 两侧都校验，唯独中间这个写盘的不校验）、裸竖线诊断被 arity 遮蔽。**问题不是某一条规则没守住，是那个咽喉一直没有被当成咽喉对待。** 两件分开做，等于承认还会有第三次。
