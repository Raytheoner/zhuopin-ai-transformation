# 需求收敛第一道把关 · grill 机制融合方案

> **一句话结论：可行，但不能按它原样的用法用。** `grilling` 治的是「**需求所有者 ↔ agent**」这一段，判例批改法治的是「**专线 ↔ 部门专员**」那一段——**两段路不重叠，也不互相替代**。我们目前的缺口恰恰在前一段：**全景规划只是需求概要，从概要直接写 openspec propose 之间，现在没有任何机制。** grill 补的就是这一格。
>
> 🔴 **但必须先钉死一条边界，否则它会立刻造成伤害**：**grill 的受访者是 Shao Peishen（或场景发起人），不是部门专员。** 把 grilling 原样对着姚祖怡跑，会同时违反我们已生效的三条纪律（禁止抽象设问／一信 ≤3 决策点／跟进信串行闸）——详见 §三。

## 一、grilling 到底是什么（已取原文，非转述）

`grill-me` 的 `SKILL.md` 正文只有一行：`Call the Skill tool with "grilling".` ⇒ **真正的机制全在 `grilling` 里；只装 `grill-me` 不装 `grilling` 会直接失效。** 这是一个必须先知道的安装事实。

`grilling` 全文约 350 词，机制有且只有三条：

| # | 机制 | 原文要点 |
|---|---|---|
| **M1** | **设计树 ＋ 前沿（frontier）** | 把待定事项建成一棵**决策树**；**前沿 ＝ 前置条件已经落定、现在就能问的那批决策**。**一轮问完整个前沿**，逐条编号并**各给一个推荐答案**，然后等答复。答复重塑树 → 重算前沿 → 下一轮。**「一个问题的答案若取决于本轮另一个尚未答的问题，它属于下一轮、不属于本轮。」** |
| **M2** | **找事实是 agent 的活，永远不是用户的活** | 前沿问题若需要环境里的事实（文件系统、工具、数据），**派子代理去查，不许问用户任何你自己能查到的东西**。且**不阻塞**：只有依赖该子代理结果的那几问等它，其余前沿照问。 |
| **M3** | **前沿为空才算完** | 设计树每一枝都走到、没有任何一处被默默假设，才算收敛；**且用户确认达成共识前不得开工**。 |

## 二、为什么它对我们有用 —— 用我们自己记录的事故来验，不用它的宣传语

**M2 是三条里价值最高的一条，因为它正好对着本项目最高频的那类错误。**

| 我们的真实事故 | M2 会不会拦住它 |
|---|---|
| **#82／A2 派单件两个前提双双被证伪**（2026-08-17）：派单说「唐燕萍每日投放、我方无定时触发」，实测**定时任务 08-10 即已部署且当日照跑**、**她自 08-10 起已停投 5 个工作日** | ✅ **会**。「她是否在投」「我方有没有定时任务」**都是环境里能查的事实**，按 M2 一律不得写成前提，必须先查 |
| **2026-08-17 §五 记录的六次同族错误**，全部形态相同：**把某处写下的旧陈述当成当下事实复述、没核**（#315「共用锁」／#45「只有他本人能做」／#308 到期日／SC8「无部署状态段」…） | ✅ **会**，同一根因 |
| **2026-08-05 他答的四项里三项是「过时题」**——问的时候没先核前置，白耗他三次决策 | ✅ **M1 会**。前沿的定义就是「前置已落定」，未核前置的问题**根本不该进本轮** |

**M1 补的是「需你定夺」清单目前缺的那一半。** 我们现有的清单已经有**编号 ＋ 选项差异 ＋ 代价 ＋ 推荐 ＋ 默认项**（2026-07-31／08-02 立），**唯独没有依赖分层**——它是一张平铺清单，于是会出现「问了一个其实取决于另一个还没答的问题」。M1 的 frontier 概念正好把这一层补上，**且与现有四条格式完全兼容、不需要改任何既有规则**。

**M3 给了一个我们没有的终止判据。** 现有的「开放点计数」数的是**数量**，答不了「是不是每一枝都走到了」。

## 三、🔴 它不能怎么用 —— 三条会立刻造成伤害的误用

**误用：把 grilling 对着部门专员跑。** 后果是同时违反三条已生效纪律：

| 冲突 | 具体 |
|---|---|
| **禁止抽象设问** | 判例批改法硬规则第 1 条明写「"提前期应该设几天？""关闭状态该怎么定义？"这类问题**一律不得**直接发给专员」，必须转成 ≤10 条真实案例三选一。**而 grilling 问的天然就是抽象决策。** |
| **一信 ≤3 决策点** | grilling **一轮问完整个前沿**，可能 8-10 问。 |
| **跟进信串行闸** | grilling 是**多轮**的，每轮一次往返 ＝ 每轮一封信；而同一收信人**同时只能有一封在途**。 |

**⇒ 结论：grill 的受访者只能是 Shao Peishen（或场景发起人）。** 判例批改法在专员那一侧的地位**一字不动**。

**为什么这个分工是对的，而不是权宜之计**：判例批改法 §〇 的诊断是「**AI 专员是业务实操者、不是需求分析师**，让他们评抽象规则是用错媒介」。**这句话反过来同样成立——Shao Peishen 是需求所有者，让他去批判例是用错媒介**。两种媒介各配各的人，才都跑得快。

## 四、融合方案：三段串联，不是三选一

```
①  grill（我方内部）                    受访者 ＝ Shao Peishen
    ├─ M2 先扫：凡环境可查的事实，agent 自查，不进任何人的问题清单
    ├─ M1 分轮：一轮问完前沿，各带推荐答案与默认项
    └─ 产出：① 已收敛决策树  ② 「必须问专员的真开放点」清单
                    ↓
②  判例批改包（专员侧，规范一字不动）    受访者 ＝ 姚祖怡／唐燕萍／陈忱／泓钦
    ├─ ≤10 条真实案例三选一、一信 ≤3 决策点、串行闸、判据类永不默认生效
    └─ 产出：批改结果 → 专线反推规则条文 → 回发一行请确认
                    ↓
③  openspec：propose → design（Shao Peishen 审）→ apply → archive
```

### 四条接缝（真正的技术活在这里，不在装不装 skill）

**接缝 1 · 分流判据（整个融合的核心）。** grill 每问出一个问题，先过一道三选一分流：

| 判据 | 去向 |
|---|---|
| **能从环境查到**（仓库文件、场景 CLAUDE.md、队列、`.51` 服务、ERP/SRM 真实数据、git） | 🔴 **不问任何人，agent 自查**（M2） |
| **只有 Shao Peishen 能定**：范围边界／优先级／风险取舍／要不要做／做到哪一档 | **本轮 grill 问他** |
| **只有专员知道**：实操判据／业务口径／阈值／真实单据长什么样／哪种情形算异常 | **不在 grill 里问**，落入「判例包待办」，出 grill 后按判例批改法成包 |

⇒ 这条分流同时防两个方向的越界：**grill 不去问专员该答的事；判例包也不再夹带本可内部拍板的事。**

**接缝 2 · grill 产出直接充当 openspec 的输入，消除一次重复劳动。** 现状 `design.md` 的决策点是 Cowork 到那一步现想的。改为：**grill 树上已 settled 的分支 ＝ `design.md` 的 Decisions；仍 open 的 ＝ Open Questions；判例包待办 ＝ Open Questions 里标注「待专员」的那一类。** 三者本来就是同一棵树的三种状态。

**接缝 3 · 「一轮问完前沿」与「一信 ≤3 决策点」不冲突，因为受众不同——但必须写死。** grill 对 Shao Peishen（同步、可连续答、一轮 8-10 问合理）；判例包对专员（异步、≤3）。**不写死这条，早晚会有人把 grill 一轮 10 问直接发给姚祖怡。**

**接缝 4 · 度量并入既有指标，并给一条可证伪判据。** 现有指标是「开放口径点从提出到销点的中位天数，目标 ≤1 周」（4 周窗口 2026-08-24 到期）。**新增一个前置指标：`进入判例包的开放点数量`。**

> 🔑 **可证伪判据（照 #315 的路数写死，便于将来打脸）**：**grill 的全部价值主张是「把本不该问专员的点拦下来」。若一个场景走完 grill 后，进入判例包的开放点数量相对同类场景没有下降，则本机制无效，应当退休。** 首个观测样本见 §六。

## 五、其余 skill 的处置：`grilling` 必装，其余一律不激活

> 判据不是「好不好」，是「**与我们已有机制是否争同一个位置**」。

| skill | 处置 | 理由 |
|---|---|---|
| `grilling`（model-invoked） | ✅ **必须有** | `grill-me` 的全部实现；缺它则 `grill-me` 是空壳 |
| `grill-me`（user-invoked） | ✅ 取 | 入口 |
| `tdd` | ❌ | 与 SuperPowers 先测后实现 ＋ 黄金基准零漂移纪律争位 |
| `code-review` | ❌ | 与 openspec ＋ S 阶段外部对抗性评审争位 |
| `to-spec` / `to-tickets` / `implement` / `triage` / `wayfinder` | ❌ | 与 openspec propose/design/apply/archive ＋ 跨桌任务队列争位 |
| `handoff` | ❌ | 与 `zhuopin-kickoff-prompt` ＋ session 接力件争位 |
| `setup-matt-pocock-skills` | ❌ | 会要求指定 issue tracker 并写配置；我们的 tracker 是队列文件 |
| `grill-with-docs` | ❌ | 附带 `CONTEXT.md` ＋ ADR 体系，与 CLAUDE.md ＋ openspec design 争位。**但它背后的「共享语言」想法值得单独评估**——我们有同类痛点（`Paul` 一词三义那次），不在本次范围 |
| `to-questionnaire` | ❌ | 定位与判例批改法几乎重合，且我们那一版已按本项目实况调过三轮 |
| `research` | ❌ **且是最需要点名的一个** | 它「作为后台代理运行，把结论写成带引用的 Markdown 文件落进仓库」——**会绕过文档台账与 R4 命名四律直接在仓库落文件**，静默产生孤儿档 |
| `resolving-merge-conflicts` | ❌ | 我们是 **ff-only ＋ sweep 强制对齐**，本就不该出现需要逐 hunk 解冲突的场面 |
| `diagnosing-bugs` / `prototype` / `domain-modeling` / `codebase-design` / `wizard` / `improve-codebase-architecture` / `writing-for-agents` / `ask-matt` / `teach` / `wait-what` | ❌ | 各有现成对位或不适用 |

🔴 **一个必须知道的安装事实：「不激活」对 model-invoked 那批是无效的。** 官方 Claude Code plugin 是**整包只读安装**，其中 `tdd`／`code-review`／`research`／`resolving-merge-conflicts` 等 **11 个是 model-invoked，模型可以自行触发**——它们不需要谁去「激活」。**⇒ 若走 plugin 路线，「其余不激活」这句话落不了地。** 处置选项见 §七 决策 G1。
