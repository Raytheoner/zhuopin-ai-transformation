# 跟进信「出信 → 队列」回写缺口 · 取证与修法

## 〇、结论先行（与提问的假设不同）

**假设**：手动催发的信状态没登记，轮巡发的登记了 ⇒ 两条发送路径行为不一致。

🔴 **实测：两条路径在 README 层面完全一致，都正确回填。真正的缺口在队列，而队列侧两条路都没有回写机制——从来就没有。**

> **`push_followup_letter.py` 文件头第 27 行自己写着：`WECOM_AIBOT_QUEUE_PATH  可选，仅作仓库根解析的锚点（**本脚本本身不读队列**）`**

🔑 **为什么会产生「轮巡的登记了」这个错觉**：**入信侧有自动机制，出信侧没有。** 专员一旦回件，企微机器人会**自动往队列追一行**（实测 `§一 #357`／`#359`／`#360` 都是这样来的）。所以只要那封信等到了回件，队列里就会出现痕迹——**那不是发信登记的，是回件登记的**。紧急手动催发且专员尚未回件时，队列里自然一片空白。

**⇒ 这是本项目今日反复撞见的同一形态：一个环节从来没有机制，只是平时恰好有别的东西替它留了痕，所以看起来像有机制。**

## 一、取证（三条，均可复现）

### 1.1 两个发送脚本都不写队列

| 脚本 | 用途 | `§一` 命中 | `编辑锁` 命中 | 结论 |
|---|---|---|---|---|
| `5-平台底座/wecom-aibot-service/scripts/push_followup_letter.py` | 手动催发 | **0** | **0** | 不写队列 |
| `5-平台底座/wecom-aibot-service/scripts/dispatch_followup_letters.py` | 每日轮巡 `ZhuopinFollowupDispatchDaily` | **0** | **0** | 不写队列 |

两者出现的「队列」字样**全部是把队列文件当作仓库根解析锚点**（`resolve_default_queue_anchor`），与写入无关。

### 1.2 README 回填在两条路径上都正常，且由脚本在发送当刻完成

用 `git log -S <状态原文> -- <README 路径>` 定位引入该状态的 commit：

| 信 | README 状态 | 引入 commit | commit 时间（本地） | 送达时刻 |
|---|---|---|---|---|
| 采购部#17（**手动催发**） | `✅ 已推送 2026-08-20 12:20 UTC` | `30469bf` `bot(跟进信): 回填「采购部#17（待发，暂不占号）」发送状态` | 2026-08-20 **20:20:28** | 12:20 UTC ＝ 20:20 本地 ✅ 逐秒对上 |
| 质量部#8（**手动催发**） | `✅ 已推送 2026-08-20 03:01 UTC` | `24e4430` `bot(跟进信): 回填「质量部#8（待你审，暂不占号）」发送状态` | 2026-08-20 **11:01:39** | 03:01 UTC ＝ 11:01 本地 ✅ 逐秒对上 |
| IT部#9（轮巡） | `✅ 已推送 2026-08-18 07:23 UTC` | `07995c0` `bot(跟进信): 回填「IT部#9」发送状态` | 2026-08-18 **15:23:33** | 07:23 UTC ＝ 15:23 本地 ✅ 逐秒对上 |

⇒ **手动路径的 README 回填与轮巡完全同质、同时、同形态。**

### 1.3 🐛 但 commit message 顺手暴露了第二个缺陷

看那两条 commit 的标题：`回填「采购部#17**（待发，暂不占号）**」` ／ `回填「质量部#8**（待你审，暂不占号）**」`。

⇒ **脚本只改「发送状态」列，不动「编号」列** ⇒ 每次自动回填都会留下一处内部矛盾：**状态说已推送、编号还写着「待发，暂不占号」**。

**这不是个例，是每封信必然发生一次。** 采购部#17 的这处失真直到 2026-08-21（发出后第 2 天）才被人发现并修正，且**同批还带偏了 README「下一个可用号」段**（写着「拟占 #17，须等 #16 闭环」，而 #17 早已发出）。

⚠️ **同族已第五次**：README「下一个可用号」段三次（08-10／08-12／08-18 各一次）＋ 编号列两次（本次两封）。**前三次的诊断是「本段是自由文本、无机器判据覆盖」，本次证明该诊断不完整——「编号」列同样是自由文本、同样没被 `_validate_followup_readme_release` 覆盖，它只看「发送状态」列。**

## 二、还有一个尚未咬人、但结构上确实存在的静默失败通道

`push_followup_letter.py` L143／L151 两个分支：

```
[OK]   推送成功，README 已回填：{result.new_status}
[WARN] 已发送成功，但 README 回填失败：{exc}
```

⇒ **`--match-topic` 定位不到或不唯一时，信已经发出去了、README 没回填，只在 stdout 打一行 WARN。** 若在计划任务／隐藏窗口（`run-followup-dispatch-hidden.vbs`）里跑，这行**没有任何人看得见**。

**本次三封都没走到这条分支**（三条 commit 都在），但它是「发了却没留痕」的真实通道，且失败模式是 **fail-silent** ——与本日判死的 `Write` 缺陷同族。

## 三、修法（三条，按优先级；均须 CC 实现）

### M1 · 出信后回写队列（主修）

**不要让脚本自己拼字符串写队列文件**——那会绕开协议〇.7 编辑锁。**正确接法是复用既有 CLI**：

```
python 0-学习与工具/工具-共享文档编辑锁.py --file <队列> acquire --who "aibot-followup-push" --note "<信编号> 已推送回写"
python 0-学习与工具/工具-共享文档编辑锁.py append-row --section 四 --number <预留号> --cell ... 
python 0-学习与工具/工具-共享文档编辑锁.py --file <队列> release --who "aibot-followup-push"
```

**写什么**：优先**回填该信在队列中已有的承接行**（如 SC2 之于 `§一 #361`）；查不到承接行时，**追一条 §四 提示行**「<部门#N> 已于 <UTC> 推送，尚无队列承接行」，使「这封信没有承接载体」这件事本身变得可见。

🔴 **必须处理并发**：轮巡任务与人工命令行可能同时跑；`acquire` 拿不到锁时**必须重试而非跳过**，且**跳过必须打日志**——否则又造一个静默失败。

### M2 · 回填状态时一并同步「编号」列（顺手修，成本最低）

脚本已经在改那一行了，**在同一次写入里把 `（待发，暂不占号）`／`（待你审，暂不占号）` 括注去掉、正式占号**即可。**这条如果不做，M1 做了也还是会每封留一处矛盾。**

**配套**：给 `_validate_followup_readme_release` 增加一条校验——**「发送状态为 `✅ 已推送` 的行，编号列不得含『待发』『待你审』『暂不占号』字样」**，把这条从人守变成机器守。

### M3 · 把 `[WARN] README 回填失败` 改为 fail-loud

至少三选一：⑴ 退出码非零；⑵ 往运维群 `WECOM_WEBHOOK_URL_OPS` 发一条告警（该通道 2026-08-19 已验通、真发过消息）；⑶ 写进 `reports/` 下的失败清单供 sweep 扫。**推荐 ⑵**——已有通道、零新增载体。
