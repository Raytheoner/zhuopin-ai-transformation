## 〇、为什么做这件事（一句话，别跳过）

**串行闸永远不会自己开。** 闸的判据源是 `README-跟进机制与命名约定.md` 的发送状态列，而**机器只写队列**——回件到达时机器人自动追 §一 行（做到了）、拆件回灌由人写队列行（做到了）、**唯独没有任何东西去改 README 那一格**。

**2026-08-21 当天两次真实咬人**：
- **质量部#8**：回件已拆件、已原样回灌 `§一 #340`、还派生了 `§四 #83` —— **README 那格仍是 `✅ 已推送`，闸锁着**，直到 Shao Peishen 追问才由人转态。
- **采购部#17**：回件 13:13:24 落盘、队列 13:15 自动追行 —— README 仍 `✅ 已推送`，至今四行 `[S:open] 待领`。

🔴 **不要把本件理解成「加个提醒」**。设计正本已论证：`README` 与队列不是存了同一份状态，而是**双向交叉引用 506 处**；**合并成一个文件解决不了，因为引用只要是人写的文字就会过时。** 正解是**写侧单一化 ＋ 读侧派生化**。本件做其中的 S2/S3/S4。

## 一、S3 · 只读闸查询 CLI（**先做这个**，它是后面一切的观测基线）

**新建 `0-学习与工具/工具-跟进闸查询.py`。**

### 输出契约（请严格按此，它会被人和脚本同时消费）

```
$ python 0-学习与工具/工具-跟进闸查询.py --to 姚祖怡
闸：🔒 锁
依据：采购部#17 · 2026-08-20 12:20 UTC 已推送 · 在途
最近入信：§一 #362 / #364（2026-08-21 13:13 落盘，均 [S:open] 待领）
下一个可用号：采购部#18
⚠ 入信已到但 README 未转态 —— 拆件回灌后须回改 README 状态列（见 §一 #366 M4）
```

- `--to <收信人>`：按收信人算闸。
- `--all`：一次列出全部收信人的闸状态（值周巡检用）。
- `--json`：机器消费用；**人读格式与 json 必须由同一份数据渲染，不得两套逻辑**。
- **退出码**：闸开 `0`／闸锁 `0`（**闸锁不是错误**）；README 解析失败或收信人不存在 `2`。

### 判据（与既有 `_validate_followup_readme_release` 保持同源，不得另写一套）

- 取该收信人在 README 表格中**最近一封**（按表格顺序，非日期——日期列存在补记情形）。
- 闭环态四选一即放行：`📥 已回件并回灌`／`✅ 无需回复`／`📨 已确认闭环`／`❌ 已作废`。
- 其余（`⏳ 待你审`／`🆕 待发`／`⏸ 暂缓`／`✅ 已推送`）一律视为在途 ⇒ 闸锁。
- 🔴 **复用现有解析器**：`aibot_service/readme_table.py` 的 `iter_rows`。**不要自己写正则拆 README 表**。

### ⚠️ 一个必须处理的边界

**「最近一封」的判定在 README 里靠表格顺序，而编号列可能含 `（待发，暂不占号）` 这类括注**（2026-08-21 实测两处）。**解析编号时须容忍括注**，并在发现「状态为 `✅ 已推送` 而编号列含『待发／待你审／暂不占号』」时**打印一条警告**（这正是 `§一 #366` M2 要修的失真）。

## 二、S4 · 两座机器桥

### 桥一 · 入信到达即在 README 打中间态

- **新增第九态 `📨 回件已到，待拆件 <UTC>`**，语义＝**回件物理到达，尚未拆件回灌；仍属在途、闸仍锁**。
- **写入时机**：企微机器人自动追队列 §一 入信行的**同一次动作里**，一并改 README 对应行。
- **对应关系怎么找**：入信文件名形如 `<部门>-<发件人>-回复-<日期>-<原信标题片段>-<hash>.docx`，其中 `<原信标题片段>` 含原信的 `跟进-<日期>-<主题>`。**匹配不上时不要猜**——只追队列行、README 不动，并打印一条 WARN 说明未匹配（**fail-loud，不是静默跳过**）。
- 🔴 **必须走编辑锁**：`工具-共享文档编辑锁.py --file <README> acquire/release`，**不得让机器人直接写文件绕开协议〇.7**。`acquire` 拿不到锁**必须重试**（建议指数退避、上限 3 次），**放弃时必须打日志并告警**，不得静默。

### 桥二 · 回灌完成由 `release` 反向校验强制转态

给 `0-学习与工具/工具-共享文档编辑锁.py` 增加 `_validate_followup_reply_state_sync`，挂 `release`（与既有三个 `_validate_*` 同族）：

> **若队列中存在一条指向某封信的入信行且其状态已 `[S:done]`（＝已拆件），而 README 该信所在行的发送状态仍非闭环四态之一 ⇒ 拒绝 release**，提示：
> `§一 #<入信行号> 已拆件，但 README「<部门#N>」仍为「<当前状态>」。请先转闭环态再 release。`

- **逃生阀**：`转态豁免：<理由>`，理由须落进 release 的 history（与既有逃生阀一致）。
- ⚠️ **上线即会拦住存量**：先跑一次全量扫描，**把当前所有不同步的信列出来**，人工清完再开硬拦；否则第一次 release 就会挡住所有人（同 `claude-progress-section-lint` 的一期 `--warn` 教训）。

## 三、S2 · 队列禁止复述信状态（lint 判据）

给 `0-学习与工具/工具-队列结构lint.py` 增加一条判据：

- **违规模式**：队列行正文中出现 `(等|待)…(采购部|财务部|质量部|IT部|销售部)#\d+…(闭环|回件|回灌)`。
- **提示**：`队列不得复述信状态（它会过时）。改为写指针：「串行闸状态跑 python 0-学习与工具/工具-跟进闸查询.py --to <收信人>」`
- 💡 **存量极少**：2026-08-21 实测全库仅 **5 处**，其中 **4 处在 §二 历史批次行**（按「历史记录不追改」豁免），**真正需要改的只有 `§四 #65` 一处**。
  ⇒ **判据须跳过 §二 批次行**，否则会对历史记录持续误报。
- **一期 `--warn`**，与 `claude-progress-section-lint` 同策略。

## 四、次序与并行

| 项 | 能否立即开工 | 并行 |
|---|---|---|
| **S3 闸查询 CLI** | ✅ 零依赖，**先做** | 可与 S2 并行（触碰区不重叠：新文件 vs `工具-队列结构lint.py`） |
| **S2 lint 判据** | ✅ 零依赖 | 同上 |
| **S4 桥二（release 校验）** | 🔶 **软序：建议 S3 之后**——S3 提供「哪些信不同步」的扫描能力，正好用来清存量 | 与 S2 触碰区重叠（都改 `工具-共享文档编辑锁.py`？否——S2 改 lint、S4 改编辑锁，不重叠）可并行 |
| **S4 桥一（入信桥）** | 🔶 **软序：建议最后**——它改的是常驻机器人，风险最高；且桥二上线后即使桥一没做，也不会漏（release 会拦） | 触碰 `wecom-aibot-service`，与前三项不重叠 |

🔑 **先 S3 后 S4 是设计正本里明确论证过的**：S3 一上线，「状态到底是什么」就有了唯一答案，**此后任何漂移都会被这个命令当场照出来**，从而为 S4 的存量清理提供基线。反过来先做 S4，等于在没有观测手段的情况下改写路径。
