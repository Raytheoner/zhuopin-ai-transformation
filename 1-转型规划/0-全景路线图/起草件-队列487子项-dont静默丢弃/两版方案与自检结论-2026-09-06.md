# `--dont` 静默丢弃 —— 两版方案（`OP-0906-I`，2026-09-06）

> 派出线：Cowork 业务总线 B-0906_G ｜ 分支：`claude/op0906i-dont-guard-487` ｜ 队列行：§一 `#487` 子项（`OP-0906-B` 并入）
> 🔴 **本件只到「起草＋自检」**：两版都没有合入 master，工作区亦不留任一版的改动，全部落在同目录两份 `.patch` 里。

## 〇、缺陷复述与本次新增的取证

**已知形态**（队列行原文）：`工具-opener生成.py --env Cowork --dont "…"` 传进来的硬约束
**既不生效也不报错**——不是工具 bug，是 `opener骨架.md` 的【Cowork】骨架本身只有
「做什么／收工」两段。2026-09-06 实撞一次（三条约束：销售域暂缓／不催姚祖怡／不代改
其余四张接力卡），靠「那三条本来也写在接力卡 §三/§四 里」侥幸兜住。

**本次逐行读代码新查到的三件事**（队列行未记，直接影响两版的取舍）：

1. 🔴 **`--variant guardian` 是同一族的第二处静默丢弃**。`generate_opener` 的 guardian
   分支拼的是「四行 ＋ P4 扇出口径」，**`--do` 与 `--dont` 一个都不拼**。同样不报错。
   ⇒ 只修 Cowork 而不管 guardian，等于只堵了两个洞里的一个。

2. 🔴 **(甲) 不是「改骨架 ＋ 同步 lint」两件事，是三件**。派单件写的是
   「改 `opener骨架.md` 正文 ＋ 同步 `工具-opener块lint.py` 的形态判据」——但**只做这两件，
   `--dont` 仍然被丢弃**：`工具-opener生成.py` 的 Cowork 分支 `body_lines` 压根没拼
   `dont_block`。骨架有段、lint 认段、生成器不出段 ⇒ 缺陷原样存在，只是多了一条会误报
   自己产物的门禁。**(甲) 必须同时改生成器**，本件的 `方案甲` patch 已含这一改。

3. 🔴 **`工具-共享文档编辑锁.py` 无需任何改动，但会自动跟着变严**。release 侧的
   `_opener_guard_violations` 是**逐字复用** `check_block`（不重写第二份），新形态自动
   传导过去；且该守卫**不做「当前在用 vs 历史」分层**——只要本次触碰的 `.md` 里有命中就
   fail-closed 拒绝 release。这是 (甲) 唯一的真实兼容性风险面，量已实测（见 §一.3）。

🔑 **判据（队列行原文，两版都同意）**：**一个参数被接受却不生效，比它被拒绝更危险。**
分歧只在「接下来该让它生效，还是该让它拒绝」。

**判据的字面（这是本版最容易写歪的一处）**：

```python
DO_SECTION_RE   = re.compile(r"^\s*\*{0,2}做什么\*{0,2}\s*[：:]\s*\*{0,2}\s*$")
DONT_SECTION_RE = re.compile(r"^\s*\*{0,2}不做什么\*{0,2}\s*[：:]\s*\*{0,2}\s*$")
```

必须**行锚 ＋ 要求行尾无正文**，两条理由都不是风格问题：

- 🔴 **子串陷阱**：`"做什么："` 天然是 `"不做什么："` 的子串。裸 `in` 判据会把「已经写了
  不做什么段」误判成「写了做什么段」。行锚让 `不做什么：` 那一行不命中 `DO_SECTION_RE`。
- 🔴 **散文陷阱**：库里大量 opener 把「做什么：建造到底。」写成**一整行散文**（非段标题）。
  不要求行尾为空，这些块会被一起拖进形态⑦——而它们本就没有分段结构，补一个空的
  「不做什么：」段毫无意义。**判据只管「已经采用分段写法的块」。**

（这两条都配了单测：`test_不做什么这一行不得被误判成做什么段`／`test_无分段结构的裸块不受约束`。）

### 1.2 判据不做环境分流（与形态①相反，这是刻意的）

形态①当年**收窄成只判 CC**，因为 `set_session_title` 在 Cowork 侧根本不存在，不收窄会对
78 个 Cowork 块报出「按规则去修全都是错的」告警。**形态⑦没有这个问题**——「不做什么」段
在两侧都成立、都可写、都该有。实测（严格行锚判据，全库 270 个 opener 块）：

| 环境 | opener 块 | 有「做什么：」独立行 | 其中缺「不做什么：」 |
|---|---|---|---|
| CC | 214 | 28 | **0** |
| Cowork | 48 | 2 | 2 |
| 环境未标 | 8 | 0 | 0 |

⇒ CC 侧**零回归**，且形态⑦顺带把【CC】骨架那一段也纳入机器守（此前从未被任何一层守过）。

## 二、方案(乙)：生成器 fail-loud，不改格式正本

`git apply 1-转型规划/0-全景路线图/起草件-队列487子项-dont静默丢弃/方案乙-生成器fail-loud.patch`

### 2.1 改动范围（2 个文件，+177 −0；**不碰 `.md` 格式正本、不碰 lint**）

| 文件 | 改什么 |
|---|---|
| `0-学习与工具/工具-opener生成.py` | 新增 `BODY_PARAM_SUPPORT` 白名单（「环境×变体」→ 该组合真的会拼进成品的正文参数）＋ `_BODY_PARAM_FLAG`／`_BODY_PARAM_ALTERNATIVE`；新增 `_reject_silently_dropped_body_params()`，挂在 `_validate_spec` 之后、`_check_op_id_not_reused` 之前；模块 docstring 加一节 |
| `0-学习与工具/test_工具-opener生成.py` | 新增 `SilentlyDroppedBodyParamTests` 9 例（Cowork+dont 报错／Cowork 只传 do 正常／不传 dont 不受影响／传空列表不算传／guardian 传 do 或 dont 均报错／CC standard 与 subtask_lane 两个都传正常／CLI 层退出码 1 且写 stderr／白名单未登记组合 fail-closed） |

白名单登记的是**拼装函数的事实**，不是「骨架应该长什么样」：

```python
BODY_PARAM_SUPPORT = {
    ("CC", "standard"):     {"do_items", "dont_items"},
    ("CC", "subtask_lane"): {"do_items", "dont_items"},
    ("CC", "guardian"):     set(),          # §三bis 固定形态，两个都不拼
    ("Cowork", "standard"): {"do_items"},   # 骨架只有做什么／收工两段
}
```

两个实现细节值得记：

- 🔴 **白名单而非黑名单**。黑名单要求「每加一个变体就记得登记它不支持什么」，忘了
  ⇒ 回到静默丢弃（fail-open，看不见）；白名单忘了登记 ⇒ 该组合所有可选正文参数一律
  被拒（fail-closed，噪音大但当场看得见）。配了单测把这条钉死。
- 🔴 **判「传没传」只看 `kwargs`，不看 `spec`**。`OpenerSpec.__init__` 会把 `None` 兜成
  `["…"]`，读 `spec` 分不出「没传」与「传了空」——判据必须站在兜底之前。

报错信息**同时给出路**（只报错不给替代，调用方会把硬约束塞进 `--do` 的某条尾巴，
读者当成待办而不是禁令，形态更糟）：Cowork ⇒ 写进派单件正文或队列行「不做什么」栏；
guardian ⇒ 改看护件。

### 2.2 对已有 opener 的兼容性影响

- **对已产出的 opener ＝ 零影响**：不改任何 `.md`、不加任何 lint 形态，全库 688 处命中
  与 57 处当前在用件一个不变，release 守卫、CI 均不受影响。
- **对调用方的影响 ＝ 一次性**：此前敲了 `--env Cowork --dont` 的命令从「静默出件」
  变成「报错退出、不出件」。**这正是本方案的目的**；但要认清代价——**它不给这些调用方
  任何地方去写那些约束**，只是不再假装收下了。
- `--variant guardian` 同族洞一并堵上（(甲) 做不到这一点）。

### 2.3 后续新增字段时的维护成本

- 🔴 **`BODY_PARAM_SUPPORT` 是第二份会漂移的判据**——它登记的是 `generate_opener`
  里 `body_lines` 各分支的事实。**改了任一分支必须同步这张表，否则表本身开始撒谎**：
  漏登记 ⇒ fail-closed（拒绝一个其实支持的参数，噪音，但看得见）；错登记成支持 ⇒
  **回到静默丢弃**。本项目对「同一判据两处各自实现然后悄悄漂移」已付过多次学费
  （`#312`、状态归桶、opener 守卫 D3 都是同一族）。当前用注释＋单测钉住，**没有机器守**。
- 每加一个新变体或新正文参数，都要在表里做一次「支持不支持」的判断；组合数是
  环境 × 变体 × 参数，随字段增加而乘性膨胀。
- 反过来：**不动格式正本 ⇒ 不需要走 Shao Peishen 的格式审，也不需要重跑全库量化。**

### 2.4 自检（派单件第 3 条要求的那一项）

**手动构造 `--env Cowork --dont "x"`，确认真的报错退出**：

```
$ python 0-学习与工具/工具-opener生成.py --op-id OP-1231-Z --env Cowork … \
      --do "拆件回灌" --dont "不动销售域"
✗ `--dont` 传入了内容，但 env=Cowork／variant=standard 的成品**不会包含**它们——
  若不报错就会被静默丢弃（参数被接受却不生效，比被拒绝更危险；2026-09-06 实撞一次，
  队列 §一 `#487` 子项／`OP-0906-I`）。【Cowork】骨架…只有「做什么／收工」两段，
  没有「不做什么」段可放。硬约束请写进**派单件正文**或**队列行的「不做什么」栏**……
exit=1
```

**两条回归（守卫不能把正常出件拦死）**：

- `--env Cowork` 不传 `--dont` ⇒ 正常出件，exit 0。
- `--env CC` 传 `--dont` ⇒ 正常出件、「不做什么」段照旧，exit 0。

**单测**：`test_工具-opener生成.py` 47 passed（+9）；两份 opener 测试文件合跑 **93 passed**，零回归。
