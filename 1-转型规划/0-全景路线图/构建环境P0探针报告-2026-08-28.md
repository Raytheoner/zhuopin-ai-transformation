## P0-1 · hooks 在 Cowork 会话是否触发 —— ❌ **不触发**（结论确定，附机理）

**判定：Cowork（Claude Desktop 本地代理模式）会话完全不加载 `~/.claude/settings.json`，全局 hooks 对它一条都不生效。⇒ 支柱二的收益覆盖面 ＝ 仅 CC 一桌。**

Cowork 的「构建环境方案线」在 **2026-08-28 23:21:33 → 23:27:11**（本地时间）之间连写 4 个文件（`CLAUDE.md` 勘误 ＋ 3 个新档），而同期审计日志一条不落：

# ⇒ 23:21:33 / 23:21:39（另两份 opener 为 23:26:33 / 23:27:11）

> 「该规则文件**不是**在会话开场注入的，而是在我 Read 了 `0-学习与工具/发企微.py` **之后**才注入——即 `paths` 作用域按『触碰到匹配路径时才挂载』的方式生效了。」

**⇒ 两件事同时被证实**：① 开场不注入（省预算）；② 触碰即注入（不丢规则）。
🔴 **试验件已按「用后即删」删除**（`rm -rf .claude/rules`；`ls .claude/` 复核已无该目录）。

### 取证二：随附二进制的自述（交叉印证，可复跑）

```powershell

**第二段一句话同时答了 P0-2 与 P0-4。**

## P0-5 · H1 日期哨兵的误拦风险面 —— 🔴 **实测把方案原定义的 H1 判死**

**判定：按方案 §四 H1 的原定义（「新写入内容含与本机 `Get-Date` 不符的日期」）实测误报 ≈ 39 条/天；即便收窄到四类「日期位」仍有 11.7 条/天，而验收线是 ≤1 条/周。⇒ H1 不能按原形态上线；warn 期跑多久都不会收敛——因为误报不是调参问题，是判据选错了对象。**

### 方法（可复跑）

对 7 份高频日期载体（两份队列真身 ＋ 跟进信 README ＋ 根 `CLAUDE.md` ＋ 4 份 session 接力件），取 `2026-08-15 → 2026-08-28` 十四天的 `git log -p --unified=0`，逐条**新增行**判定：行内是否出现 `20\d{2}-\d{2}-\d{2}`，其中有没有一个等于该次提交的日期。

### 结果一：原形态

| 指标 | 实测 |
|---|---|
| 含日期的新增行 | **2,000** |
| 其中含当日日期（H1 放行） | 1,448 |
| **只含非当日日期（H1 会拦）** | **552** |
| 折算 | **≈ 39.4 条/天** |

误报的**主导形态**是长状态格里的合法历史引用，例如新增高水位线那一行里的 `2026-07-24 首次清扫起启用`——**这一行是对的，H1 却会拦它。**

### 结果二：收窄到「日期位」之后

| 位置 | 命中新增行 | 其中不含当日日期（会触发） |
|---|---|---|
| `Last Updated` 行 | 11 | **1** |
| 接力／章节日期标题 | 90 | 51 |
| 跟进信文件名日期 | 226 | 37 |
| §二 批次号 `B-MMDD_` | 627 | 75 |
| **合计** | 954 | **164 ≈ 11.7 条/天** |

### 结果三：🔑 三条可直接落进 design 的结论

1. **「内容里出现不是今天的日期」这个判据本身不成立。** 队列行的天职就是记录历史，含旧日期是**正确写法**。方案里 H1 的定义把「文本里有旧日期」当成了「写错了日期」，**这两件事在本项目的语料里几乎不相关**。
2. **未来日期同样不能当判据**：十四天里写入未到达日期的新增行 **192 条**，绝大多数是合法的到期日／`[S:timed=…]` 定时触发行／专员回件截止日。
3. **可用的 H1 只剩两个位置，而它们恰好误报接近零**：
   - **`**Last Updated**: <日期>`** —— 14 天 11 次，仅 1 次非当日（**0.07 条/天**）；
   - **新增的 §二 批次号 `B-MMDD_`** —— 须按 **diff 判「这是不是一条新出现的批次行」**，而不是按内容 grep（grep 会把每次改状态格都算一遍，那 75 条误报正是这么来的）。

   ⇒ **建议 design 把 H1 的 scope 收成这两条**；原来那个宽形态**不进变更包**，理由与数字一并写进 design 的「已否决方案」，免得下次有人重提。

## 六、连带发现（本棒范围外，但影响支柱二成败）

### 🔴 F1 · 项目级 `settings.json` 会因「工作区未信任」被**静默忽略**——直接威胁支柱二

P0-2 起新会话时，命令行原样吐出：

> `Ignoring 7 permissions.allow entries from .claude/settings.json: this workspace has not been trusted.`

根因实测（`C:\Users\Paul Shao\.claude.json`）：**同一个目录在信任表里有两条记录，斜杠方向不同、结论相反**——

| 键 | `hasTrustDialogAccepted` |
|---|---|
| `C:\Dev\zhuopin-ai` | **True** |
| `C:/Dev/zhuopin-ai` | **False** |

命中哪一条取决于启动时 cwd 字符串怎么归一化。**支柱二的全部配置都打算放在这个文件里** ⇒ 一旦命中未信任那条，**哨兵不响、不报错、命令行一切正常**——正是本项目反复吃亏的「工具静默回退」族。

⚠️ **本次只观察到 `permissions` 被忽略；hooks 是否同样受信任门控制，本棒未测，不得推断。**

**对策必须进 design**：① **哨兵须能自证在岗**（SessionStart 注入一行，或落库 sweep 增一类「最近 N 天零哨兵记录即告警」）——否则就是 OP-0819-F「机制建成 9 天、从没真正响过一条」的第二次；② 顺手合并那两条重复的信任记录。

### 🟡 F2 · `protected-paths.json` 会拦住支柱二自己的部署，而 #398 的同类留步已挂了 3 天

现行 patterns（`~/.claude/protected-paths.json`，`mode: block`）：

```
*/.claude/hooks/*                *claude_desktop_config.json
