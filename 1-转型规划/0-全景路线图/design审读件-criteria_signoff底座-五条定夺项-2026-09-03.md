## 一、① 占位词黑名单要不要留 ⇒ 推荐 **(a) 留**

**实测原文**（`criteria_signoff/models.py:19-23`，13 个词）：

```python
_PLACEHOLDER_TOKENS = frozenset(
    {"tbd", "todo", "n/a", "na", "none", "null", "-", "?", "待定", "待确认", "待补", "未定", "无"}
)
```

**为什么留**：五份手抄的守法是「用例断言 `is None`」，**两步可破**（填个数、顺手改断言）。本包 D2.2 把它改成构造期不变式后，绕过的唯一路径变成**伪造一个 `Signoff`**。而伪造 `Signoff` 最省事的形态就是 `signed_by="TBD"` —— 黑名单堵的正是这一步。**构造期不变式与黑名单是同一道防线的两半，只留一半等于漏。**

**「黑名单永远列不全」这条反对意见不成立**：它不是穷举式防线，作用是**把"顺手糊弄"的成本抬到"明知故犯"**。列不全的那部分已由 `Signoff` 四项必填兜住 —— 你得编一个真人名、一个日期、一份**可被第三方翻出来核对**的凭据路径。那已经不是顺手，是留了名字的作假。

**真实代价（只有一个，概率极低）**：某天凭据文号恰好是 `-`，或签认人姓名恰好在黑名单里。报错文案清晰、当场可辨，不会静默出错。

**🔴 本件加一条起草方没做的补充**：黑名单会拒 `signed_on` 字段里的占位词，**但不校验日期格式** —— `signed_on="2026-13-45"` 现在能通过构造。既然 `Signoff` 的全部价值是"可被第三方翻出来核对"，一个非法日期与占位词是同一类问题。建议 (a) 时一并加一行 `YYYY-MM-DD` 格式校验（约 3 行代码，无外部依赖）。

## 二、② 三类「1 次」缺口（权限／存在性／前置）收不收 ⇒ 推荐 **(a) 不收**

**三份 config 原文实测，三类缺口的解除路径各不相同**：

| 缺口 | 场景 | 它到底缺什么 | 解除动作 | 谁去做 |
|---|:--:|---|---|---|
| `BANK_BALANCE_ACCESS` | FI8 | **这份数据能不能取都没人批**（涉资金安全） | 拿授权 | **你本人**（EE-2 已拍板） |
| `TIMESHEET_SYSTEM_EXISTS` | FI9 | **不知道这个系统存不存在**（全仓库零取数指针） | 去核实 | 承接方开工第一件事 |
| `CHIP_PRICE_API` | FI10 | 上游尚未选型签约 | 选型＋签约 | 队列 `#475`（已独立立行） |

**不收的理由，第二条比第一条重要**：

1. rule-of-three 未触发（各 1 次）；
2. 🔴 **五个场景包明确要求"性质各不相同、分别立牌不合并"**（FI8 config 首部与 FI10 `__init__` 均有原文）。把四种解除路径压成一个 `None`，等于把「**谁该去做什么才能解除**」这个信息抹掉 —— 而那恰是这些立牌的全部价值。

**🔴 本件补一条起草方没说、但足以独立支撑"不收"的论据**：**你自己的 EE-2 裁决已经把 FI8 那条判成了"权限不属判据"**（原文「属权限非判据」）。若现在把它收进 `criteria_signoff`，就与你三小时前的裁决直接打架 —— 一个被收进"判据签认注册表"的东西，下一个读代码的人当然会以为它等的是一次签字。

**若你仍要收（选 (b)）**，起草方给了唯一正确的做法，本件同意：**不是**塞进 `Criterion`，而是加一个并列的 `Blocker` 概念、带**必填的 kind 判别字段**（`signoff` / `authorization` / `existence` / `prerequisite`）。🔴 **请勿批准"合并成一个 `None`"的做法。**

## 三、②′ FI10 `SLOW_MOVING_CRITERIA` 归不归注册表 ⇒ 推荐 **(a) 归进去**（起草方无倾向，本件给判）

🔴 **本件的核心发现：你的 EE-4 裁决已经改变了这条东西的性质，起草方写 design 时还没意识到。**

- **EE-4 之前**：它是「无源可取」—— 要从 SC7 取，而 SC7 呆滞口径**根本不存在**（实测：`sc7_inventory/business_rules.py` 只有 R1 金额阈值 / R2 未认证供应商两条，呆滞处置属②期 2027-01）。这种形态属**前置未满足**，与 §二 的 `CHIP_PRICE_API` 同类，不该进注册表。
- **EE-4 之后（(a) FI10 先定、SC7 后对齐）**：它变成了「**我方自己出口径、找人签认**」—— 这就是一条标准的待签认判据，**该进注册表**。

⇒ 起草方在心跳里提醒「EE-4 定的是谁先出口径、②′ 问的是归不归注册表，两问不同、都还悬着」。这句提醒本身是对的（防止误读），**但两问并非无关**：EE-4 已经把 ②′ 的前置条件解掉了。

**归进去要解决的唯一遗留问题 —— owner 填谁？**（起草方正是卡在这里）

- 填**姚祖怡**：她是 SC7 业务口径的确认人，但 FI10 是财务场景、口径要用于**存货跌价计提**（进财务报表）。让她签一条会影响财报的口径，超出她的职责面。
- 填**财务侧**（唐燕萍线）：口径归属与场景归属一致，且计提口径本就该财务签。但 SC7 将来要来对齐，需要她们知情。
- **本件推荐：owner 填财务侧，并在 `Criterion.question` 里写明「本口径 FI10 先出、SC7 后对齐（EE-4），签认前须知会 SC7 口径确认人」。** 这样两边都不丢。

⚠️ **归进去有一个连带后果，必须让你知道**：`tasks.md` 4.3 的验收硬条件是「迁移前后未签认判据数量**必须相等**（17 条进、17 条出）」。归进 `SLOW_MOVING_CRITERIA` 会变成 **17 进 18 出** —— **这条验收条件须同步改成 18，否则 A4 会按"迁移失败"退回**。（这正是那条验收条件在起作用的证明，不是它的缺陷。）

## 四、③ L2 模型层纪律（5/5 命中）要不要另起一个包 ⇒ 推荐 **(b) 立行但不排期**

**先看实测 —— 这三条纪律现在已经在漂移了**：

| 场景 | 实际写法 | 类型 | 默认语义 |
|:--:|---|---|---|
| FI5 | `needs_manual_review: bool = True` | bool | 默认需人工 |
| FI6 | `needs_manual_review: bool = True` ＋ `confirmed_by: str`（必填） | bool + str | 默认需人工；确认人无默认 |
| FI8 | `confirmed_by_cfo: bool = False` | **bool** | **默认未确认** |
| FI9 | `needs_manual_review: bool = True` ＋ `disclaimer: str`（必填） | bool + str | 默认需人工 |
| FI10 | `needs_manual_review: bool = True` ＋ `disclaimer: str`（必填）＋ `confirmed_by: str = ""` | bool + str | `confirmed_by` **有默认空串** |

🔴 **三个不同的名字（`confirmed_by` / `confirmed_by_cfo` / 无）、两种不同的默认语义（必填 vs 默认空串）—— 而这五份是同一天、同一条泳道写出来的。** 这正是 D0 说的 `#345` 形状，只是还在第一天。

**所以"该收"这一点毫无疑问 —— 但"现在收"是错的**：

- rule-of-three 触发的是「**该收**」，不是「**现在就收**」。
- 五个包**目前全是骨架，引擎一个都没建**（FI5 的 U9C 报销端点未核实、FI6 案例库要从零建、FI8 银行授权未取得、FI9 工时系统存在性未知、FI10 前置卡 `#475`）。此刻收编，等于**凭五份 dataclass 的字段名去猜公共契约** —— 而 `criteria_signoff` 之所以敢收，是因为它的契约在五份实现里 4 项全部 5/5 命中、形态一致；L2 这三条恰恰**形态不一致**，不一致的部分正是要等引擎跑起来才知道谁对。
- 🔴 收早了的代价与收晚了的代价不对称：**收晚了是多手抄几份（可测、可查、可批量改）；收早了是底座绑死了一个猜错的契约（要动底座，五个场景陪着改）。**

**推荐 (b)**：立一条队列行，标明「**触发条件：至少两个财务引擎落地后启动**」，不并进本包、不排期。

## 五、④ 签认／读取要不要接 `AuditLogger` ⇒ 推荐 **(a) 不接**（起草方不代判，本件给判）

**实测底座既有 `AuditLogger` 的事件形状**（`zhuopin_platform/audit/logger.py`）：

```python
AuditEvent(scenario=..., action=..., evaluator=..., automation_level="L2",
           decision={...}, data_sources={...}, content_hash=...)
```

**这是为「AI 每一次决策」设计的流水**（一天可能几千条）。而**签认是人的一次性动作**（全项目 17～18 条判据，一年发生十几次）。把两者塞进同一条 jsonl，会让审计日志的语义变糊 —— 查"AI 做过哪些决策"时混进"某人某天签了个字"。

**三条不接的理由，第三条最硬**：

1. **零依赖是 `criteria_signoff` 可被任意场景安全引用的原因之一**（D3 自律）。接上即产生对 `audit` 的依赖。
2. 五份本地实现 **0/5** 有此需求，接上就是起草方自己发明了一条要求。
3. 🔴 **IATF 可追溯的诉求已经被满足了，而且满足得比 jsonl 更好**：`Signoff` 四字段（**实名 / 日期 / 落档凭据 / 规则版本**）本身就是完整审计轨迹，且它**写在代码里、进 git、有 commit 历史与作者** —— 一条 jsonl 记录可以被覆盖，一次 git 提交不能被静默改掉。用日志去追溯一个已经在版本控制里的事实，是降级不是升级。

**🔴 但若你要保险，正确做法是把依赖方向反过来**（本件建议，不需另立包）：让**引擎**在 `record(AuditEvent)` 时把当时的 `RULE_VERSION` 写进 `decision` 字段 —— 审计日志指向判据版本，而不是判据模块去写审计日志。这样既满足"每条 AI 决策可回溯到当时用的哪版口径"，又不破坏底座零依赖。**这一条可并进 A4 顺手做，成本约一行。**

## 七、🔴 第六件事：design 未列，本次尽调查出 —— FI9「工时系统存在性核实」无人认领

**不需要你现在拍板，但需要你知道，因为它正在重演一条你已经批过一次的判词。**

§二 那三类缺口，其中两类都已经有主人：

- FI8 `BANK_BALANCE_ACCESS` ⇒ **你本人推**（EE-2 已拍板）；
- FI10 `CHIP_PRICE_API` ⇒ **队列 `#475` 已独立立行**（立行理由原文：「跨域基础设施挂在单域名下，那个域一停，它就会连带失去主人」）；
- 🔴 **FI9 `TIMESHEET_SYSTEM_EXISTS` ⇒ 无主。**

**实测**：全仓库 `工时系统` 四字仅出现在 4 份规划文档的依赖名里；代码侧唯一一处是 `shared_tools/models.py:126` 的一句注释（`product_id` 字段的用途说明，**不是连接器**）。队列侧只在 `#473`（FI9 场景行）的状态列里被提及，**没有独立行**。

⇒ **而 FI9 排 2027 年。** 这与 `#475` 立行时用的是同一条判词的同族形态：一件"要有人去核实"的事，只挂在一个排在一年多以后的场景名下 ⇒ 那个场景一顺延，它就没人管了。区别只在于 `#475` 那件是"基础设施"、这件是"一次核实"——**但"无人管"的机理完全一样**。

**成本对比**：现在去核实"公司有没有工时系统、谁维护、能不能取数"，大约是问两个人的事；等到 2027 年 FI9 开工才发现没有，那时人工费用归集要重做设计。

## 附录 · 本包已做到的两处净增量（供审读时对照，不需你答）

这两点是"收进底座"相对"五份手抄"的**实质增量**，不是搬运：

1. **把承诺变成了代码**：五份实现只做到「值是 `None`」，「读到 `None` 会 fail-loud」是各自 docstring 里的**一句承诺**、尚无代码兑现（引擎都还没建）。本包用 `value` property 兑现了它。
   - 🔬 且**已实测证明守卫在承重、非声称**：删掉 `models.py` 里 `value` 的 fail-loud 守卫后重跑 ⇒ **4 条用例转红**，还原后 45 passed。另有两条元测试把这个证明常驻进套件。
2. **把防线从用例挪到构造期**：用例断言两步可破（填数＋改断言，一个 commit，CI 全绿）；构造期不变式要绕过必须伪造 `Signoff`，而它四项必填、拒占位词 —— **绕过从"顺手"变成"留了名字的明知故犯"**。

**测试实据**：底座新增 45 passed，全量 452 passed / 1 skipped（原 407，**零回归**）；`openspec validate --all --strict` 127 passed / 0 failed。
