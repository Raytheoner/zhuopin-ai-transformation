# memory 与 CLAUDE.md 配置 · 审核输入件

> **本件的由来**：2026-08-21 处置「专员性别纠正 ≥5 次仍复发」时，我说了一句「根 CLAUDE.md 早记过 memory 本机层是半死的」，Shao Peishen 认为这更像**环境缺陷**而非既成事实，要求描述清楚后交环境总线全盘审核。
> 🔴 **本件的全部内容都是当场实测，不是转述 CLAUDE.md 里的既有说法**——因为那个说法本身也是待审对象之一。

## 一、实测事实（六条，均可复现）

**测法**：本机 PowerShell 直读文件系统（不经沙箱、不经文件工具），命令附在每条后面。

### 1. 本机只有一个 memory 目录，2 个文件，近一个月零新增

```
Get-ChildItem 'C:\Users\Paul Shao\AppData\Roaming\Claude' -Recurse -Directory -Filter 'memory'
```

命中**唯一一个**：
`…\local-agent-mode-sessions\67dd5f56-…\48fd41f0-…\spaces\88cb0587-…\memory`

内含**仅 2 个文件**：
- `feedback_prompt_must_label_target_app.md`（681 B，**2026-07-27**）
- `project_harvest_progress.md`（2,709 B，2026-06-11）

⇒ **最新一条停在 2026-07-27，此后近一个月没有任何新记忆落进来。**

### 2. 🔴 `MEMORY.md` 在本机整个 Claude 目录下**不存在**

```
Get-ChildItem 'C:\Users\Paul Shao\AppData\Roaming\Claude' -Recurse -Filter 'MEMORY.md'
```
**零命中。**

**但是**：每个会话开始时，我的上下文里都会被注入一份 `MEMORY.md`，标题「# Memory Index」，列了 **40+ 条**本项目条目（称呼纪律、部门 AI 专员名录、环境定位、取证方法…），并自称「2026-08-16 全量重建」。

⇒ **那份索引不在本机磁盘上，来自服务端。** 本机那个目录与它**不是同一份东西**。

### 3. 🔴 写入静默失败：工具报成功，文件不存在

2026-08-21 我按系统提示给出的路径，用 `Write` 工具往上述 memory 目录写了一个新文件 `dept_specialist_gender.md`（记录九人性别名录）。

- **工具返回**：`File created successfully at: …\memory\dept_specialist_gender.md`
- **本机实测**：`Test-Path` → **`False`**，目录里根本没有这个文件

⇒ **写入类工具报成功而实际未落盘，且不产生任何错误。** 这是本项目已多次记载的「工具静默回退」家族里**最危险的一种形态**——读类工具回退只是拿到错的答案，写类工具回退是**以为存下来了、其实什么都没有**。

### 4. 🔴 同一路径读写权限不对称 ⇒ 结构上无法自证

同一个文件路径：
- `Write` → 返回成功（尽管实际没落盘）
- `Read` / `Edit` → 报错 **`is outside this session's connected folders`**

⇒ **我无法回读自己刚写的东西。** 而本项目 memory 纪律明写「**验证一律用回读**」——**这条纪律在当前配置下物理上无法执行**。

### 5. 🔴 `project_memory_*` 工具在本会话中不存在

根 CLAUDE.md 顶部写着「云端层（现役，健康）：`project_memory_*` 工具读写，42+ 件」。

实测：`ToolSearch` 以 `memory read write project memory recall` 检索，返回的是浏览器 console、剪贴板读写、widget context、session transcript、Google Drive 读文件——**没有任何一个 memory 读写工具**。

⇒ **本 Cowork session 对云端 memory 是只读的**：能读到被注入的索引与内容，**无法增、删、改**。CLAUDE.md 那句「云端层现役、可读写」**至少对本会话类型不成立**。

### 6. 三处指向互相打架

| 说什么 | 实际 |
|---|---|
| 系统提示：memory 在 `…\spaces\…\memory\`，「直接用 Write 工具写入」 | 那个目录只有 2 个陈旧文件；写进去会静默丢失 |
| 根 CLAUDE.md：云端层现役、用 `project_memory_*` 读写 | 本会话没有这套工具 |
| 注入上下文的 `MEMORY.md`：40+ 条、2026-08-16 全量重建 | 本机磁盘上无此文件 |

⇒ **一个 session 若照系统提示行事，会把记忆写进一个没人读、且不会报错的地方。** 今天就发生了一次。

## 三、建议环境总线回答的问题（按重要性排序）

1. **权威 memory 到底在哪、谁能写？** 云端 memory 由什么写入？是否只有特定 session 类型（如 Claude Code、或带 `project_memory_*` 工具的会话）才有写权限？**Cowork 会话是否本就该是只读？** 如果是，系统提示里那段「直接用 Write 工具写入 memory 目录」的指引就是错的，应予纠正。
2. **写入静默失败是配置问题还是产品缺陷？** 若是目录未挂载导致 Write 落到虚空，应让它**fail-loud**；若是本会话本就不该写 memory，则应直接拒绝而不是报成功。
3. **本机那 2 个陈旧文件要不要清理？** 它们是 2026-06/07 的残留，与云端索引不同源，**留着会让下一个 session 误判"本机层是权威"**。
4. **读写权限为何不对称？** 同一路径 Write 通过、Read 拒绝——这使「回读验证」这条纪律无法执行，应统一。
5. **项目 CLAUDE.md 40.8% 是流水账，怎么治？** 现有规则是人守且已失效。可选方向：把「顶部进度段只留最近 1 条」做成 lint 判据（与 §一 `#351` 子项 ⑷⑸ 同族，都是"人守规则该机制化"）；或把进度段整体移出 CLAUDE.md、改为按需读的指针。
6. **14 份场景级 CLAUDE.md 的一致性**：本次未审，建议一并纳入。
