# FI4 / FI5 通盘考虑

## 〇、摘要（30 秒）

财务 AI 专员把财务域重心从 **FI1 仓库对账 / FI2 月结加速** 转到 **三单匹配自动对账** 与 **付款申请自动校验**，并把它们命名为 **FI4 / FI5**、时间提前到 **2026-09 / 2026-10**、自动化等级拉到 **L3-L4**、拆成 **8 + 7 个子场景**（细化程度远超原路线图一句话描述）。方向我判断**成立且价值更高**（直击"应付会计每天 2-3h 逐笔核对"的效率黑洞 + "打错账户/重复付款/超合同付款"的资金安全红线）。但有三处必须先钉：

- **D1 🔴 命名冲突**：专员的"FI4/FI5"与全景规划现有 **FI4=异常交易检测 / FI5=预算执行监控** 同号不同义。不裁定会让全景规划 / 排期表 / 甘特 / 前置总表 / CLAUDE.md 全线漂移。
- **D2 🟡 自动化等级**：专员大量用 **L4 自动拦截**。需辨析它与 §7 红线的关系，并定"分期 L3→L4"还是"直接 L4"。
- **D3 🔴 数据可行性闸**：FI4/FI5 依赖的正是**当前被卡的 U9C 财务/PO/GR/应付端点 + SRM 发票 + OCR**。"更紧急"不消除数据闸——9 月能否启动取决于这批数据 9 月前通不通。

## 三、自动化等级：L4 自动拦截的辨析（D2 底稿）

专员把 FI4-B/C/D、FI5-A/B/C/D 等定为 **L4（系统自动校验 + 自动拦截，财务仅处理异常/紧急特批）**，与原路线图财务全 L2 不同。**先厘清一个关键区别，否则会误以为踩红线**：

- §7 红线管的是 **"自动放行 / 自动执行"**（采购 >50 万、新供应商、交付预测推客户 = 不可自动执行）。
- 专员的 L4 是 **"自动拦截 / 自动退回"**——挡住坏发票/坏付款，是**保守方向**。而且**真正的付款执行仍在人**（财务经理/CFO 审批流），L4 只自动化"校验闸"这一步，不自动付钱。
- 结论：**L4 自动拦截与 §7 红线不冲突，反而强化内控**。人始终在环：所有异常/紧急特批/最终付款放行都由人处理。

需要治理的是**另一侧风险——误拦截**：

1. **误拦成本**：错误挡下合法付款会伤现金流和供应商关系。→ 需"误拦申诉/快速复核通道"SOP。
2. **分期落地建议**：新规则先以 **L3（建议/预警，人工确认）** 跑 1-2 个月，统计查准/查全率，达标后再升 **L4 自动拦截**。避免上来就硬拦、误拦砸信任。
3. **留痕**：专员已设计"每次拦截/放行全程留痕"——符合 §7 audit 红线，保留。
4. **紧急特批**：专员已设计三单未匹配的紧急付款走 CFO 审批 + 限期补配票——好，保留。

## 四、数据可行性闸（D3 —— 决定 9 月能否真启动）

FI4/FI5 的数据依赖（汇总自外部文档"数据依赖"字段）：

- **U9C**：应付单配票状态、采购订单明细行、入库单(GR)、供应商主数据(含收款账户/约定税率)、已付款凭证、采购合同(含变更/框架/暂估价)、预付款记录、预算模块。
- **SRM**：供应商发票上传(PDF/图片/Excel 混传) + 发票明细行 + **OCR 结构化解析**。
- **其他**：物料编码映射表(供应商编码↔我方编码)、法定节假日日历、纳税人资质。

对照现状（CLAUDE.md + 前置总表 L38）：**U9C 财务模块接口🔴卡（IT 攻关，~9 月）；`CommonEntity/Query` 外网 404；SRM 凭据未迁入本仓库（900401 未解）**。→ FI4/FI5 依赖的恰恰是这批被卡端点，**且新增了 SRM 发票 + OCR 这条原 FI1 没有的依赖链**。

**硬结论**：9 月启动 FI4 的前提，是下列至少成立——需 Paul 拉 IT/SRM 钉死：

- ① U9C 的 PO 明细行 / GR / 应付单 / 已付款 端点开放（直读）**或** 比照 FI1 做 **CSV 应急桥接**（导 PO/GR/INV/应付/付款）。
- ② SRM 发票数据连通（解 900401）+ **OCR 方案选型**（发票版式杂，OCR 准确率直接决定 FI4-A 数据准备成败）。
- ③ 物料编码映射表的初始来源（有无现成对照？还是靠 FI4-B 自学习冷启动）。

> 建议把 FI4/FI5 端点纳入前置总表已有的 **"7/15 IT 双反馈门"**（无接口时间表则 8/1 启用 CSV 备选）——现在就把这两场景的端点清单挂进去，别等 9 月才发现没数据。
