### 1.2 脱敏 SOP（进开发环境前必做）

第一，**OEM 客户分级令牌化（✅ 2026-06-27 采纳陈忱实操方案，取代原固定 3 令牌设想）**：客户令牌格式 = **`OEM-级别-序号`**（如 `OEM-A-01`），级别按战略权重 + 采购额分 **A 战略级 / B 重要级 / C 一般级**（A 级预留 01-20、B 级 01-30，便于后续新增客户顺延）。映射关系拆**机密映射表**（含真实客户全称，质量部本地加密保管、绝不进录入包/库）与**公开令牌表**（仅令牌+级别，可对外/内一般沟通）两份。既满足 OEM 分库隔离（CLAUDE.md §4 扩展），又保留按客户检索能力，且可扩展。
> ⚠ **示例与前提修正（2026-06-27）**：本就绪包原以"比亚迪/上汽/理想→OEM-A/B/C"举例，与卓品**真实客户清单不符**——实际客户以工程机械/商用车/发动机动力厂商为主（柳工/徐工/玉柴/道依茨/宇通/吉利等，无比亚迪/上汽/理想）。故全文 OEM 示例一律改用**通用令牌**（`OEM-A-01`/`OEM-B-03`…），不再绑定具体厂名。是否上溯修正 CLAUDE.md / 全景规划"直供比亚迪/上汽/理想"的前提，留待 Paul 与质量部确认（本就绪包不擅自改总纲）。

第二，**去个人信息**：经办人姓名、联系方式去除或角色化（如"质量工程师-A""计划工程师-A"）。第三，**技术实体屏蔽层（Entity Scrubbing）**：仅令牌化客户名**不够**——8D 正文/根因(D4)常含可反推客户身份的技术细节（专属车型/平台代码、特定器件/位号命名、具体量产线别、专属接口/信号名）。这些**强制模糊化**为通用占位。陈忱实操已建立可沿用的占位范式：**车型/平台 → `某车型平台-A/B/C`；器件/位号 → `电容-A`/`开关-A`/`某软件模块-A`；供应商 → `供应商-A/B`；产线/地点 → `工厂-A`/`客户端地点-A`；零件编号 → `料号-A/B/C`；本公司名 → `本公司`**，切断"靠技术细节反推 OEM"的链路。第四，**保留可学信息**：失效机理、根因逻辑、对策类型这些跨客户通用知识保留（AI 价值所在）——屏蔽的是"身份指纹"，不是"失效知识"，二者要分清、别过度 scrub 掉机理（陈忱 7 份样本在这点上平衡得好，可作范例）。

### 1.3 OEM 分库检索设计（落 data_isolation_layer）

历史 8D 库按客户令牌（`OEM-A-01`、`OEM-B-03`…）分库；RAG 检索时由 `OEMRouter` 按当前案例的客户路由到对应库 + 通用库（跨客户通用机理），跨库抛 `CrossOEMAccessError`。**一个客户的历史 8D 不进另一客户的检索结果**（CLAUDE.md §4 红线）。通用机理（不含 OEM 专属信息）进共享通用库，供所有客户案例检索。（注：分库可按"客户令牌"或"级别"粒度落地，由 AIOps 在 data_isolation_layer 设计时定；最敏感的 A 级战略客户建议客户级独立 Collection。）

> **物理隔离，非逻辑过滤（吸收外部评审强化）**：必须在向量库**物理层面**为每个 OEM 建独立的 Database/Collection（如 `oem_a_db` / `oem_b_db`），靠容器/密钥级权限保证跨库在底层物理通道上不通——**不可只用单 Collection + `OEMRouter` 逻辑过滤**。理由：逻辑过滤一旦检索逻辑溢出，或向量空间因"技术问题相似"把 OEM-A 的 8D 匹配给 OEM-B 的提问，就会击穿隔离、构成主机厂商业机密泄露（法律+丧失供货资格的灭顶风险）。物理分库 + Entity Scrubbing 双保险。此口径与全景规划 §4.3 OEM 隔离架构（分客户知识库实例）一致，落地时由 AIOps 钉死。

### 1.4 黄金基准取样标准（仿 SC8 门禁）

旗舰上线前要用历史已结案 8D 跑黄金基准（AI 重跑 vs 工程师当年结论）。取样标准：

- **数量**：5-10 份已结案 8D。
- **覆盖**：四类不良各 ≥1（设计/制程/物料/使用不当）；**安全相关 ≥1**（验证 26262 门禁触发）；OEM 分布覆盖主要客户。
- **通过标准**：确定性部分（格式/字段/双语）零偏差；根因候选命中率（工程师采纳）≥ 约定阈值（MVP 60%）；安全相关 100% 走功能安全工程师额外门禁。
- **沉淀**：核对过程存为 8D 黄金基准（`data/golden/`），作回归基准。

> **⚠ 2026-06-27 黄金基准缺口提醒（据陈忱首批 7 份样本）**：当前样本**无安全相关案例（E 列全=否）、无物料类案例**，且填写说明对 2 份样本的"根因验证有效"与数据存在矛盾——这三项是黄金基准取样的硬条件，**必须先补齐**：① 复核动力/H桥案例 ASIL 相关性产出 ≥1 安全相关；② 补 ≥1 物料类已结案 8D；③ 核定矛盾案例验证有效口径。详见《质量就绪工作审核报告-2026-06-27》G1–G3。

## 第二部分 · 立项门禁治理共识（PMO + 财务牵头）

> 立项门禁的开工瓶颈是**标准明文化**：AI 只能核"已被明确为规则"的东西。下列两张清单是 PMO 与财务的治理工作，**先于开发立项**。

### 2.1 立项红线 → 机器可核清单（PMO 牵头）

把公司立项 SOP/红线，逐条转成"AI 能机器核"的判定项。判定项分三类严重度（沿用 PRD D1：阻断/重要/提示）。

> **✅ 2026-06-27 此项已由陈忱团队大幅超额完成**：下表原为 8 行示例，陈忱团队已产出**开发类 EQQR8082 的 82 条完整机器可核规则**（含规则ID/章节/检查项/严重度/判定标准/阈值/取数来源/自动化级别），并**对一份真实立项书完成逐条试评**（华丰 EPA 项目，已能出 [通过]/[不合格]/[待改进]/[不适用]）；另附**开发类+研发类两套完整规则说明书**（合格分级 ≥80/60-80/<60、错误/警告/提示三级、跨模块校验 C01–C12、特殊场景）。**立项门禁开工前置基本就绪**，规则规格直接以陈忱工作包为准（见《AI质量智能建设就绪工作汇总.xlsx》"立项门禁/规则说明（开发）"页）。**仅剩缺口**：评分扣分细则（82 条各占几分）未定义——Paul 2026-06-27 定**交质量部/PMO 定**，开发先以"错误项一票否决"起步。下表示例保留作概念说明。

| 检查域 | 机器可核项（示例，PMO 定稿） | 严重度 |
|--------|------------------------------|:------:|
| 模板完整性 | 必填字段齐全、章节完整、附件齐全 | 阻断 |
| 风险评估 | 是否有风险评估章节 + 风险等级 | 阻断 |
| 退出机制 | 是否定义项目退出/止损条件 | 阻断 |
| ROI 目标 | 是否有量化 ROI 目标 + 测算 | 重要 |
| 里程碑 | 里程碑是否有明确验收标准 | 重要 |
| 关键路径 | 是否识别关键路径 | 重要 |
| 计划合理性 | 周期>N月是否有阶段拆分（防"假大空"，PRD D3） | 重要 |
| 资源分配 | 人力/预算是否分配到里程碑 | 提示 |

> PMO 需补全本表为完整清单 + 定阈值（如"N 月"、ROI 测算最低要素）。每条判定都要**可解释**（标出触发的规则），满足 IATF 可追溯。**最终立项决策权在评审委员会**（PRD D1，AI 只预审）。

### 2.2 财务"可机器核规则 vs 专业判断"边界清单（财务牵头）

这是 PRD D2 的开工前置共识——划清 AI 核什么、财务核什么。

| 财务审查项 | 归类 | 谁来判 |
|-----------|------|--------|
| 预算模板格式符合性 | 可机器核 | AI 标偏差 |
| 成本分类完整性（是否缺项） | 可机器核 | AI 标偏差 |
| ROI 公式正确性、合计勾稽 | 可机器核 | AI 标偏差 |
| 预算明细缺项 | 可机器核 | AI 标偏差 |
| 投资合理性 / 假设是否成立 | **专业判断** | 转财务复核 |
| 市场/收入预测可信度 | **专业判断** | 转财务复核 |
| 战略契合度 | **专业判断** | 转评审委员会 |

> 财务需确认本表边界并补全。AI 对"专业判断"项只做"提请财务复核"标记，不下结论（PRD D2 选 A）。
