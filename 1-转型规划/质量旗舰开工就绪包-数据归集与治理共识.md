# 质量旗舰开工就绪包

> 8D（旗舰①，2026-10 入轨）与立项门禁（旗舰②，2026-11）的开工瓶颈在**数据与共识**，不在代码。历史 8D 库脏/缺、立项标准没明文化，AI 就无据可学、无规则可核。本包给出可立即执行的模板与清单，让质量部/PMO/财务在 7-9 月把前置做完，10/11 月直接开工。**全程 off-LAN，脱敏后才进开发环境。**

## 第一部分 · 8D 旗舰数据就绪（质量部牵头）

### 1.1 历史 8D 库结构化模板

把存档的历史 8D（邮件/QMS/文件）按下表字段结构化，是 RAG 检索与根因学习的语料基础。每份 8D 一行/一条记录。

| 字段 | 说明 | 必填 | 用途 |
|------|------|:---:|------|
| 案例ID | 唯一编号（内部流水） | ✓ | 关联键、审计追溯 |
| 客户(脱敏) | OEM 客户 → 令牌化（见 1.2） | ✓ | **OEM 分库检索键** |
| 失效现象描述 | D2 问题描述原文 | ✓ | RAG 检索主语料 |
| 不良分类 | 设计/制程/物料/使用不当 | ✓ | 分类学习 |
| 安全相关 | 是/否（涉 ASIL 功能） | ✓ | **触发 26262 额外门禁** |
| 临时对策(D3) | 围堵措施 | ✓ | 对策候选 |
| 根本原因(D4) | 确认的根因 + 5Why/鱼骨 | ✓ | 根因候选学习核心 |
| 纠正/预防(D5-D7) | 措施 + 验证结果 | ✓ | 对策候选 |
| 关联FMEA条目 | DFMEA/PFMEA 条目号 | 选填 | 关联提示 |
| 关联物料/供应商 | 料号/供应商（与 SC1 联动） | 选填 | 跨域联动 |
| 结案日期/有效性 | 是否验证有效 | ✓ | 只学"已验证有效"的（防污染） |

> **数据质量底线**：只把**已结案且根因经验证有效**的 8D 进库（D1 选 A 的逻辑：AI 学组织已验证的经验，不学未采纳的误判）。先小批高质量（建议首批 30-50 份覆盖四类不良），再扩。

### 1.2 脱敏 SOP（进开发环境前必做）

第一，**OEM 客户令牌化**：比亚迪/上汽/理想 → `OEM-A/B/C`（映射表**另存质量部本地加密文件，绝不进录入包/库**），既满足 OEM 分库隔离（CLAUDE.md §4 扩展），又保留按客户检索能力。第二，**去个人信息**：经办人姓名、联系方式去除或角色化（"质量工程师A"）。第三，**技术实体屏蔽层（Entity Scrubbing，吸收外部评审强化）**：仅令牌化客户名**不够**——8D 正文/根因(D4)常含可反推客户身份的技术细节（OEM 专属车型/平台代码、特定芯片/引脚命名、具体量产线别如"SMT-Line 3"、专属接口/信号名）。这些**强制模糊化**为通用占位（如 `BYD-DiLink-MCU1`→`Generic-MCU`、`SMT-Line 3`→`产线X`），切断"靠技术细节反推 OEM"的链路。第四，**保留可学信息**：失效机理、根因逻辑、对策类型这些跨客户通用知识保留（AI 价值所在）——屏蔽的是"身份指纹"，不是"失效知识"，二者要分清、别过度 scrub 掉机理。

### 1.3 OEM 分库检索设计（落 data_isolation_layer）

历史 8D 库按 `OEM-A/B/C` 分库；RAG 检索时由 `OEMRouter` 按当前案例的客户路由到对应库 + 通用库（跨客户通用机理），跨库抛 `CrossOEMAccessError`。**比亚迪历史 8D 不进上汽检索结果**（CLAUDE.md §4 红线）。通用机理（不含 OEM 专属信息）进共享通用库,供所有客户案例检索。

> **物理隔离，非逻辑过滤（吸收外部评审强化）**：必须在向量库**物理层面**为每个 OEM 建独立的 Database/Collection（如 `oem_a_db` / `oem_b_db`），靠容器/密钥级权限保证跨库在底层物理通道上不通——**不可只用单 Collection + `OEMRouter` 逻辑过滤**。理由：逻辑过滤一旦检索逻辑溢出，或向量空间因"技术问题相似"把 OEM-A 的 8D 匹配给 OEM-B 的提问，就会击穿隔离、构成主机厂商业机密泄露（法律+丧失供货资格的灭顶风险）。物理分库 + Entity Scrubbing 双保险。此口径与全景规划 §4.3 OEM 隔离架构（分客户知识库实例）一致，落地时由 AIOps 钉死。

### 1.4 黄金基准取样标准（仿 SC8 门禁）

旗舰上线前要用历史已结案 8D 跑黄金基准（AI 重跑 vs 工程师当年结论）。取样标准：

- **数量**：5-10 份已结案 8D。
- **覆盖**：四类不良各 ≥1（设计/制程/物料/使用不当）；**安全相关 ≥1**（验证 26262 门禁触发）；OEM 分布覆盖主要客户。
- **通过标准**：确定性部分（格式/字段/双语）零偏差；根因候选命中率（工程师采纳）≥ 约定阈值（MVP 60%）；安全相关 100% 走功能安全工程师额外门禁。
- **沉淀**：核对过程存为 8D 黄金基准（`data/golden/`），作回归基准。

### 1.5 8D 前置任务清单（7-9 月，质量部）

## 第二部分 · 立项门禁治理共识（PMO + 财务牵头）

> 立项门禁的开工瓶颈是**标准明文化**：AI 只能核"已被明确为规则"的东西。下列两张清单是 PMO 与财务的治理工作，**先于开发立项**。

### 2.1 立项红线 → 机器可核清单（PMO 牵头）

把公司立项 SOP/红线，逐条转成"AI 能机器核"的判定项。判定项分三类严重度（沿用 PRD D1：阻断/重要/提示）。

| 检查域 | 机器可核项（示例，PMO 定稿） | 严重度 |
|--------|------------------------------|:------:|
| 模板完整性 | 必填字段齐全、章节完整、附件齐全 | 阻断 |
| 风险评估 | 是否有风险评估章节 + 风险等级 | 阻断 |
| 退出机制 | 是否定义项目退出/止损条件 | 阻断 |
| ROI 目标 | 是否有量化 ROI 目标 + 测算 | 重要 |
| 里程碑 | 里程碑是否有明确验收标准 | 重要 |
| 关键路径 | 是否识别关键路径 | 重要 |
| 计划合理性 | 周期>N月是否有阶段拆分（防"假大空"，PRD D3） | 重要 |
| 资源分配 | 人力/预算是否分配到里程碑 | 提示 |

> PMO 需补全本表为完整清单 + 定阈值（如"N 月"、ROI 测算最低要素）。每条判定都要**可解释**（标出触发的规则），满足 IATF 可追溯。**最终立项决策权在评审委员会**（PRD D1，AI 只预审）。

### 2.2 财务"可机器核规则 vs 专业判断"边界清单（财务牵头）

这是 PRD D2 的开工前置共识——划清 AI 核什么、财务核什么。

| 财务审查项 | 归类 | 谁来判 |
|-----------|------|--------|
| 预算模板格式符合性 | 可机器核 | AI 标偏差 |
| 成本分类完整性（是否缺项） | 可机器核 | AI 标偏差 |
| ROI 公式正确性、合计勾稽 | 可机器核 | AI 标偏差 |
| 预算明细缺项 | 可机器核 | AI 标偏差 |
| 投资合理性 / 假设是否成立 | **专业判断** | 转财务复核 |
| 市场/收入预测可信度 | **专业判断** | 转财务复核 |
| 战略契合度 | **专业判断** | 转评审委员会 |

> 财务需确认本表边界并补全。AI 对"专业判断"项只做"提请财务复核"标记，不下结论（PRD D2 选 A）。

### 2.3 立项门禁前置任务清单（7-10 月，PMO + 财务）

- [ ] PMO 设"立项标准 owner"（PRD D5）。
- [ ] PMO 补全 2.1 机器可核清单 + 阈值定稿。
- [ ] 财务确认 2.2 边界清单。
- [ ] 归集历史立项文档 + 评审记录（脱敏），供 AI 学评审重点（PRD D4：只学人工确认采纳的偏差）。
- [ ] 各部门 KPI 定义集中（ROI 合理性核用）。
