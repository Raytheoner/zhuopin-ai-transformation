# 陈承，你好

财务这边 07-17 给的《U9C 自定义 API 接口文档》我们已经在做真实只读联调，三单端点（采购单/收货单/应付单）整体质量很高、字段齐全。联调过程中发现 **`AP/Query` 有一个服务器端真实 bug**，会挡住 FI2 后续"按期批量对账"这个用法，麻烦你这边看一下。

## 一、问题现象（真实复现，非猜测）

`AP/Query` 从报错栈能看到控制器真实签名支持这些参数：

```
UFIDA.U9.Cust.ZP.APController.Query(String apiKey, String docNo, String supplierCode,
                                     String invoiceNo, String itemCode, String orgCode,
                                     Int32 page, Int32 pageSize)
```

但实测下来，**`docNo` 之外的三个过滤参数一用就报 SQL 异常**（数据库列名写错，不是我们这边调用姿势的问题）：

| 传参 | 报错 |
|------|------|
| `supplierCode=ZA0066`（不带 docNo） | `System.Data.SqlClient.SqlException: 列名 'Supplier_Code' 无效。` |
| `itemCode=R01A.0175`（不带 docNo） | `System.Data.SqlClient.SqlException: 列名 'ItemInfo_ItemCode' 无效。` |
| `invoiceNo=26942000000425333446`（不带 docNo） | `System.Data.SqlClient.SqlException: 列名 'InvoiceNo' 无效。` |

三个参数报的都是"列名无效"，看着像是这几个过滤条件拼 SQL 时用的列名和实际表结构对不上（大概率是字段改过名/换过表，过滤条件那段代码没跟着更新）。

**作为对比**：`Purchase/Query`（采购单）和 `GR/Query`（收货单）这两个端点，不传 `docNo` 时能正常返回全表 + `page`/`pageSize` 分页也正常工作，`Purchase/Query` 的 `supplierCode` 过滤我们也实测通过（能正确按供应商筛出全部历史 PO）——说明批量查询这个能力在其他端点上是好的，问题集中在 `AP/Query` 这一个控制器。

## 二、影响

目前 `AP/Query` 只能靠 `docNo` 单号精确查，"给一批 AP 单号逐个核对"没问题；但"按期间/按供应商批量拉一批待对账的 AP 单"这一步做不了——这正好是 FI2 三单匹配后续要规模化跑批时需要的能力，现在只能停留在"财务专员手工给单号清单"的阶段，效率上不去。

## 三、请你帮忙

1. **做什么**：核对 `AP/Query` 控制器里 `supplierCode`/`itemCode`/`invoiceNo` 三个过滤条件对应的数据库列名，修正 SQL 拼接（大概率是列名/表结构变过、这几个过滤分支没同步更新）。
2. **怎么做**：不需要我们提供更多信息了——上面的报错信息和触发参数已经是完整复现步骤，你直接在测试库上试 `http://192.168.100.49:6666/zp/api/AP/Query?apiKey=...&supplierCode=ZA0066` 就能重现。修完后麻烦告诉我们一声，我们这边立刻回归验证。
3. **什么时候交**：不阻断我们现在的 FI2 数据整备（先用 `docNo` 单查路径推进），但**这是我们争取把 FI2 真实验证从 8 月下旬提前的一个关键缺口**——如果本周内能给个评估结论（能不能修、大概什么时候）就非常帮忙，具体修复时间你按你那边排期定就行。
