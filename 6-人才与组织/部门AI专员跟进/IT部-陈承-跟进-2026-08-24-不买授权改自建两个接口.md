## 三、改走你已经走通过六次的那条路

我们不需要 `CommonEntity/Query` 本身，需要的只是它背后的**两类数据**。而这两类数据，完全可以照 `/zp/api/*` 的老套路各加一个接口——**这条路你已经交付过六次了**：`ForecastOrder`、`Stock`、`Purchase`、`GR`、`AP`、`ZpViewPurOrder`。

| | 接口 | 对应 U9C 的东西 | 我们拿它干什么 |
|---|---|---|---|
| **A** | `GET /zp/api/PurPriceList/Query` | 采购价目表（`UFIDA.U9.ISV.PM.IQueryPurPriceListSRV`） | 真实的最小起订量、包装倍数、采购提前期、供应商认证状态 |
| **B** | `GET /zp/api/MO/Query` | 生产工单（`UFIDA.U9.MO.MO.MO`） | 生产排程；以及从历史工单反推真实工时 |

## 四、A 为什么排第一：现在有三个数是我们编的

不是「少几个字段不好看」。**是三条算式现在算出来的结果都不能用。**

我们的供应商数据现在从 `ZpViewPurOrder` 聚合，里面有三个值是代码里写死的常量：

| 写死的值 | 造成的结果 |
|---|---|
| 最小起订量 ＝ 1<br>包装倍数 ＝ 1 | 建议采购量的公式是「按包装倍数向上取整，且不低于起订量」。两个都代 1 进去 ⇒ **算出来的建议采购量恒等于缺口本身**，等于这一步根本没算。采购同事拿到之后还得自己按供应商的起订量重新凑一遍 |
| 采购提前期 ＝ 30 天 | **所有物料一律按 30 天倒推最迟下单日**，不管它是 2 天能到的通用件，还是 90 天的车规芯片。⇒ 短周期料过度提前、长周期料严重滞后，**而「最迟下单日」正是采购同事拿来排优先级的那一列** |
| 供应商认证状态 ＝ 恒为「已认证」 | 我们选供应商的逻辑是「**已认证的**里面选单价最低的」。恒为真 ⇒ **那道认证过滤从来没生效过**，有可能把没认证的供应商推荐出去。这一条在 IATF 体系下是要出问题的 |

**⇒ 接口 A 一到位，这三条算式才第一次真的成立。**

## 五、A 的字段清单（`/zp/api/PurPriceList/Query`）

**一行 ＝ 一个「供应商 × 料号」的价目条目。**

**必须有的六个**（缺任何一个这接口对我们就没用）：

| 字段 | 说明 |
|---|---|
| `SupplierCode` | 供应商编码。🔴 **请与 `ZpViewPurOrder` 的 `supplyCode` 同源同值**，否则我们两边对不上 |
| `ItemCode` | 料号。同上，与 `itemCode` 对齐 |
| `MOQ` | 最小起订量 |
| `MPQ` | 最小包装量／包装倍数 |
| `LeadTimeDays` | 采购提前期，**单位：天** |
| `IsApproved` | 该供应商对该料号**是否已认证／合格** |

**有的话更好的五个**（没有也能跑，但会退化）：

`SupplierName`（只给编码的话，报表和界面还要再查一次）／`UnitPrice`（🔴 **麻烦注明是含税还是未税**，这个口径我们在别处已经踩过一次）／`Currency`（外币供应商我们有单独规则，不能默认人民币）／`EffectiveDate` 和 `ExpireDate`（价目有多版本时，我们要按「生效日 ≤ 查询日 < 失效日」取当期那一版——这套判法我们在 BOM 上已经实现过，照搬就行，**但前提是接口把这两个日期给出来**）／`IsPrimary`（是否首选供应商，U9C 里有的话直接用，没有我们就退回按单价选）

**查询参数**：`itemCode`（🔴 **要支持多值**，我们常常一次查几百个料号）、`supplierCode`、`effectiveOn`（按某天取当时生效的版本，不传就是今天）、`page`、`pageSize`

## 六、B 的字段清单（`/zp/api/MO/Query`）

**一行 ＝ 一张生产工单。**（如果 U9C 里工单是有行的，**麻烦按行返回并带行号**，理由见第七节第 1 条。）

**必须有的**：

| 字段 | 说明 |
|---|---|
| `DocNo` | 工单号 |
| `ItemCode` / `ItemName` | 产出品料号／名称 |
| `PlanQty` | 计划产量 |
| `CompletedQty` | 已完工数量 |
| `PlanStartDate` / `PlanEndDate` | 计划开工／完工日 |
| 🔴 `ActualStartDate` / `ActualEndDate` | **实际**开工／完工日。**这两个是最关键的**——我们要靠历史工单的实际起止日期**反推真实工时**，现在这块全是估的。没有这两个字段，排程就只能一直用估的工时 |
| `Status` | 单据状态。**麻烦一并给出取值字典**（哪个值＝已审核／已完工／已关闭） |
| 🔴 `LineStatus` | 行级状态（如果工单有行）。见第七节第 1 条 |

**有的话更好的**：`WorkshopCode` / `LineCode`（车间／产线——排程要按产线排，只有工单没有产线就排不了）、`OrgCode`、`CreateDate`、`BomVersion`

**查询参数**：`docNo`、`itemCode`（多值）、`dateFrom`／`dateTo`、`status`、`workshopCode`、`page`、`pageSize`

🔴 **`dateFrom`／`dateTo` 麻烦在文档里写明它过滤的是哪一个日期字段**（计划开工日？实际开工日？创建日？）——理由见第七节第 2 条。

## 七、四条通用要求，每条都是我们真踩过的坑

**这一节不是提要求，是把我们摔过的地方告诉你，省得再摔一次。**

**1. 🔴 行级状态请一次给到位。**
这已经是同一个坑的第三次了。`ForecastOrder/Query` 最初只有单据头的 `Status`，我们据此写了「传 `status=2` 就能剔除关闭行」的过滤，**跑了一个多月**，直到用两个真实案例（`FO2026070001` 的行 60 和行 230，U9C 界面上明明写着「关闭」）才发现——**那 90 行的头状态恒为 2，一个例外都没有**。后来你补了行级 `LineStatus`（2＝核准／3＝关闭）才解决。`Purchase/Query` 也是一样，你 7/30 补了行级状态我们才不用再靠「365 天回溯窗口」去猜。
**⇒ 所以这次想请你一次给到位。** 我们在拿到数据之前，是**没有办法判断**头状态和行状态会不会不一致的——两次都是上线之后才发现的。

**2. 🔴 日期过滤参数，麻烦写明过滤的是哪个日期字段。**
真实例子：`AP/Query` 的 `dateFrom`/`dateTo` 过滤的是立账日期，而**未立账的单据这个字段是空的** ⇒ 用它去筛「未立账应付单」会把要找的单全部排除掉，**而且返回 0 行、不报错**。
工单同理：**一张还没开工的工单，实际开工日必然是空的**。如果日期过滤挂在实际日期上，就会把所有待开工工单静默过滤掉——**而那恰恰是排程最需要的一批**。

**3. 🔴 参数不合法请直接报错，不要静默返回全表。**
真实例子：`POChange/Query` 传错单号**不报错**，会静默返回全表。这类最难查——**返回值看着完全正常，结论却是反的**。
查不到就返回空集合并标明，不要返回全表，也不要返回 200 空 body。

**4. 形态跟现有的六个接口一样就行，不用新造。**
`GET`、apiKey 走 URL query（不用 OAuth2）、响应体 `Data.Rows`、字段 PascalCase、分页 `page`/`pageSize` 并带总行数、Swagger 挂 `/zp/swagger/ui/index`。
**我们的程序已经按这套写好了，新接口接进来只是加两个方法，不改架构。**
